# v0.15.0 Documentation Expert Foundation Plan

## Release Goal

`v0.15.0` introduces the Documentation Expert as the fourth operational expert. The Code Assistant currently has implementation correctness through the GAUSS Language Expert, methodological correctness through the Econometrics Expert, and maintainability/design correctness through the Software Engineering Expert. None of the three owns documentation quality as such: whether an explanation, reference page, example, comment, or docstring is clear, complete, well-structured, and matched to its reader — independent of whether the underlying code is syntactically valid, the underlying method is methodologically sound, or the underlying design is maintainable. The Documentation Expert closes that gap:

- **GAUSS Language Expert** — implementation correctness.
- **Econometrics Expert** — methodological correctness.
- **Software Engineering Expert** — maintainability/design correctness.
- **Documentation Expert** — explanation clarity, reference structure, examples, comments, and user-facing usage guidance.

This remains documentation/evaluation-driven expert routing, exactly like the three experts before it: an operational profile, activation triggers, decision rules, and manually-evaluated benchmarks — not a runtime orchestration engine. No code parses or enforces any of this at runtime; a response is checked against it manually, the same way task-mode fit is checked today. Adding a fourth expert changes the *shape* of routing (more combinations to document and evaluate) but not its *mechanism*.

## Expert Ownership

The Documentation Expert owns:

- Documentation clarity
- Reference structure
- Examples and usage snippets
- Explanation quality
- Comments and docstrings
- API/reference page organization
- Task-oriented usage guidance
- Audience-appropriate wording
- Terminology consistency
- Reader assumptions
- Warning/caution notes
- Prerequisites and setup notes
- Input/output explanation
- Parameter/return-value explanation
- Troubleshooting notes
- Documentation completeness checks
- Reducing ambiguity in user-facing docs
- Transforming notes/code into documentation

The Documentation Expert does not own:

- Exact GAUSS syntax
- Verified GAUSS command signatures
- The GAUSS package/base distinction
- Econometric model appropriateness
- Causal interpretation
- Statistical diagnostics
- Code maintainability/design as its primary domain
- Instructional sequencing over time as its primary domain
- Curriculum design
- Product strategy
- Release management
- Official GAUSS documentation authority

## Expert Boundary Rules

- GAUSS-specific syntax claims must defer to the GAUSS Language Expert and verified evidence — the Documentation Expert never asserts exact GAUSS syntax on its own authority.
- Econometric/statistical claims must defer to the Econometrics Expert — the Documentation Expert never asserts model appropriateness or causal validity on its own authority.
- Code design/refactoring claims must defer to the Software Engineering Expert — the Documentation Expert never asserts maintainability on its own authority.
- The Documentation Expert may improve wording, structure, and examples but cannot invent GAUSS syntax to fill an example.
- The Documentation Expert may clarify statistical concepts for a reader but cannot certify a method's methodological appropriateness.
- The Documentation Expert may suggest comments or docstrings but cannot claim code is maintainable merely because it is well documented — documentation quality and code quality are independent claims.
- The Documentation Expert is distinct from the (future) Education Expert:
  - **Documentation** helps a user complete a task or understand a reference right now.
  - **Education** helps a user learn over time through sequencing, scaffolding, exercises, and pedagogy.
- If multiple experts activate, implementation, methodology, maintainability, and documentation claims must remain separate and separately attributable in the response, extending the same coordination principle `v0.9.0` and `v0.14.0` established for two and three experts to four.

## Multi-Expert Routing Impact

Current routing types (`v0.9.0`-`v0.14.0`, three experts): GAUSS-only, Econometrics-only, Software-engineering-only, GAUSS + Econometrics, GAUSS + Software Engineering, Econometrics + Software Engineering, all three, Neither (eight types).

`v0.15.0` adds a fourth axis:

1. GAUSS implementation
2. Econometric methodology
3. Software engineering/code quality
4. Documentation/explanation quality

A fully enumerated four-expert combination table would have 16 rows (2⁴). That is a real risk to routing-document readability, and this plan deliberately does **not** commit to enumerating all 16 in full. Instead, `workflows/expert-routing.md`'s eventual four-expert update should:

- Keep explicit, worked examples for the combinations most likely to occur in practice: Documentation-only, GAUSS + Documentation, Econometrics + Documentation, Software Engineering + Documentation, GAUSS + Software Engineering + Documentation, GAUSS + Econometrics + Documentation, all four, and Neither — the eight combinations named in this plan's Benchmark Plan below.
- Represent the remaining combinations (three-of-four subsets not already covered, e.g. Econometrics + Software Engineering + Documentation without GAUSS) through a compact activation matrix or table — one row per expert, one column per axis, "activates when X" — rather than a worked prose example for every one of the 16 possible subsets.
- Preserve the existing coordination principles (strictest applicable evidence/context requirement wins; claims stay separable) as the general rule that covers any combination, so a combination without its own worked example is still fully governed.
- Preserve Neither-expert routing unchanged for ordinary writing tasks unrelated to technical documentation (e.g., a release-note blurb, a changelog entry) — adding a Documentation Expert must not cause routine non-technical writing to start activating it.
- This is the same "readable at N combinations, not a combinatorial engine" discipline `v0.14.0`'s own Multi-Expert Routing Impact section committed to at eight; this plan extends that discipline to sixteen rather than abandoning it.

### reasoning.md

Should describe a step-by-step reasoning workflow, following the `experts/software-engineering/reasoning.md` precedent (a numbered workflow plus special-case sections):

1. Identify the reader and the task they're trying to accomplish.
2. Identify the documentation type (reference, task-oriented guide, example, comment/docstring, troubleshooting note).
3. Identify missing context (what the reader needs that isn't stated yet: prerequisites, assumptions, inputs/outputs).
4. Separate explanation from implementation correctness — documenting code clearly is never evidence the code itself is correct.
5. Separate documentation from teaching/curriculum — a clear reference or task guide is not a lesson plan.
6. Check structure and flow — does the document lead the reader through the task in a sensible order.
7. Check examples and assumptions — do examples match the described behavior, are assumptions stated rather than implicit.
8. Coordinate with the GAUSS Language Expert, Econometrics Expert, and/or Software Engineering Expert when the content also touches their domains, rather than answering on their behalf.
9. Recommend documentation improvements, prioritized by what would most reduce reader confusion or risk.
10. Avoid overclaiming — never let documentation clarity stand in for syntax verification, methodological soundness, or maintainability.

### best_practices.md

Should include, following the flat-numbered-list precedent:

- Start with the user's task, not the implementation.
- State prerequisites explicitly.
- Explain inputs and outputs.
- Use examples that match verified syntax.
- Define terms before using them.
- Keep warnings near the risky step they apply to, not buried at the end.
- Separate reference from tutorial content where useful.
- Avoid unexplained jargon.
- Document assumptions explicitly.
- Keep examples small and focused.
- Label pseudocode clearly.
- Avoid duplicating official docs inaccurately — cite or point to them instead of restating from memory.
- Link or cite official docs when appropriate.
- Keep comments focused on intent, not mechanics.

### common_mistakes.md

Should include, following the flat-numbered-list precedent, explicitly naming boundary-crossing mistakes as failure modes:

- Documenting unverified syntax as fact.
- Examples that do not match the described API.
- Unclear audience.
- Missing prerequisites.
- Missing inputs/outputs.
- Burying caveats where a reader is likely to miss them.
- Mixing tutorial and reference content without structure.
- Overlong explanations that bury the actionable step.
- Unexplained jargon.
- Comments that repeat obvious code mechanics instead of explaining intent.
- Failing to document assumptions.
- Implying statistical validity from documentation clarity (a direct restatement of the Expert Boundary Rules above, phrased as a failure mode to avoid).
- Implying code quality from documentation quality (same pattern).
- Replacing learning design with reference docs (i.e., treating a well-written reference page as a substitute for the Education Expert's sequencing/scaffolding role).

## Risks and Design Questions

- **How to keep the Documentation Expert distinct from the (future) Education Expert?** Bounded by the Expert Boundary Rules above: documentation helps a reader complete a task or understand a reference right now; education helps a reader learn over time through sequencing, scaffolding, exercises, and pedagogy. Benchmark `22.6` exists specifically to test this boundary.
- **How to prevent documentation clarity from implying syntax or statistical correctness?** Bounded by the same independence principle already established for the Software Engineering Expert (clean code ≠ statistical validity, valid syntax ≠ good design) extended one more time: clear documentation ≠ correct syntax, clear documentation ≠ sound methodology, clear documentation ≠ maintainable code. Benchmark `22.7` exists specifically to test the syntax case.
- **How to keep routing readable with four operational experts?** By keeping the "explicit examples for common combinations, compact matrix for the rest" discipline described in Multi-Expert Routing Impact above, rather than writing 16 full worked examples.
- **Should routing enumerate all combinations, or use compact matrices/examples?** This plan recommends compact matrices/tables for coverage plus worked examples only for the eight combinations most likely in practice (named above) — full enumeration of all 16 is explicitly not required and is a design choice for the implementation task to make concrete against the real routing file structure.
- **Should the Documentation Expert cover README/release notes, or only technical/user documentation?** Recommended: technical/user documentation (reference pages, task guides, examples, comments/docstrings, troubleshooting notes) is clearly in scope; a README's user-facing sections (e.g., usage instructions) are in scope; release notes and changelog entries remain Neither-expert territory (pure project tracking) unless the release note itself is genuinely technical documentation (e.g., documenting a breaking API change's new usage) — this distinction should be made explicit in the Non-Activation Cases when the operational profile is written.
- **How should official documentation citations be handled?** The Documentation Expert should point to or cite official GAUSS documentation rather than restating it from memory, and any GAUSS-specific claim inside a citation still needs the GAUSS Language Expert's evidence discipline — this expert does not get its own separate citation authority.
- **How much beginner-friendly rewriting belongs to Documentation vs. Education?** Recommended: making a single piece of documentation beginner-friendly (clearer wording, defined terms, a simpler example) is Documentation Expert territory; sequencing multiple beginner-friendly documents into a learning path, with exercises and pacing, is Education Expert territory. Benchmark `22.6` is the concrete test case for this line.
- **How to avoid turning the Documentation Expert into general prose editing?** The Non-Activation Cases list is the primary guardrail — general prose editing unrelated to technical/product documentation is explicitly excluded, keeping this expert's territory to code/product/technical documentation specifically, the same discipline the Software Engineering Expert's Non-Activation Cases used to avoid becoming a general programming catch-all.
