# v0.31.0 Canonical Execution Request Contract

This document is the **authoritative, implementation-ready specification** of the Canonical Execution Request first introduced conceptually in `planning/v0.31.0-runtime-orchestration-design.md`'s "Execution Request Contract" section. Where the two documents differ in field naming or detail, this document governs; `planning/v0.31.0-runtime-orchestration-design.md` has been updated to reference this document as the source of truth (see "Required Consistency Updates" in the final report).

This is planning and interface-definition work only. No runtime orchestration is implemented, no Python classes/dataclasses/protocols are added, no formal JSON Schema is created, and no execution helper code, tests, or `schemas/gauss_code_execution.schema.json` are changed. `gauss.exe`/`tgauss.exe` were not invoked to produce this document.

## 1. Purpose and Scope

**What the Canonical Execution Request represents:** a single, immutable-once-confirmed snapshot of everything a future orchestration controller needs to construct, review, display, confirm, and eventually pass to the execution helper for one specific real GAUSS execution attempt. It is the one artifact that eligibility review, safety review, user confirmation, and helper invocation all operate on — never four different, possibly-drifting representations of "the plan."

**Where it exists in the future orchestration flow:** it is built during `collecting_inputs`, finalized at `proposed`, displayed at `awaiting_confirmation`, bound to consent at `confirmed`, and consumed exactly once by the Helper Adapter at `executing` — the same states and transitions defined in `planning/v0.31.0-runtime-orchestration-design.md`'s "State Machine" section, which this document does not redefine.

**Which component creates it:** the Execution Request Builder (per the Proposed Components list in the runtime orchestration design), informed by the Execution Intent Classifier's recognition that an execution request is underway.

**Which components consume it:** the Eligibility Evaluator, the Safety Review, the Consent Manager, the Response Composer (for display), the Helper Adapter (for invocation), the Result Validator (for `expected_output_files` comparison), and the Execution Record (by reference, once frozen).

**What it does not represent:**

- It is not a claim that execution has occurred, is occurring, or will occur — it represents *what would run if confirmed and invoked*, nothing more.
- It is not the execution *result* — that is a wholly separate structure, `schemas/gauss_code_execution.schema.json`'s existing, unchanged result contract.
- It is not a durable record — see "Persistence, Logging, and Redaction" below for exactly what may and may not survive beyond the request's own lifecycle.
- It is not itself a safety guarantee — the request records the *outcome* of eligibility/safety review; the review logic itself lives in the Eligibility Evaluator/Safety Review components, not in this contract.

**Why it is separate from `schemas/gauss_code_execution.schema.json`:** the result schema validates what the helper actually returned after a real (or fake, in self-tests) invocation — `execution_status`, `exit_code`, `stdout`, `output_files`, and so on. The Canonical Execution Request is the *input* side: what was asked for, reviewed, and confirmed, before any invocation occurs. Conflating the two would blur the evidence/interpretation boundary this project has maintained since `v0.26.0`'s execution-aware analysis workflow — an execution request is a plan; an execution result is evidence of what actually happened. They must never be represented by the same object, and this document explicitly does not modify or extend the result schema in any way.

**Explicit scope statements:**

- The execution request defined here is an **orchestration input contract**.
- `schemas/gauss_code_execution.schema.json` remains the **execution-result contract**, unchanged.
- This task does **not** create a formal production schema (JSON Schema or otherwise) for the request — see "Open Decisions" (§15) for why this remains deferred.

## 2. Contract Lifecycle

| Step | Description | Request state |
|---|---|---|
| 1 | Execution intent recognized | No request object exists yet |
| 2 | Inputs collected (working directory, code/script, etc.) | No request object exists yet — this is dialogue, not the object itself |
| 3 | Draft request assembled | **Mutable.** Fields populate incrementally; not yet a coherent, reviewable whole |
| 4 | Eligibility review completed | **Mutable.** A failed review returns the request to step 3 (fields must change to become eligible) |
| 5 | Safety review completed | **Mutable.** A failed review returns the request to step 3; a passed review is a precondition for step 6, but the request object itself is still editable up to this point |
| 6 | Canonicalization completed | **Snapshot taken.** The request's field values are captured into the canonical serialized form defined in §9. Any edit after this point invalidates the snapshot and restarts from step 3 — the snapshot itself is not edited in place |
| 7 | Request hash computed | Computed deterministically over the step-6 snapshot; a new snapshot (from any subsequent edit) produces a new hash, never a mutation of the existing one |
| 8 | Exact plan displayed | The user sees precisely the step-6/7 snapshot — never a re-derived or re-summarized version |
| 9 | User confirmation attached | `confirmation_scope` is set to the step-7 hash; `user_confirmed` becomes `true` only if the confirmation-evidence test in §8 passes |
| 10 | Confirmed request frozen | **Immutable from this point forward.** No field may change without discarding this request object entirely (a new `request_id`, back to step 3) |
| 11 | Helper Adapter consumes the request | Read-only. The Helper Adapter projects the frozen request into helper parameters (§12) and never writes back into it |
| 12 | Execution record references the request | Read-only. The Execution Record (per the runtime orchestration design's Observability section) stores a reference/summary, not a mutable copy |
| 13 | Rerun creates a new request | A rerun is never step 3-13 replayed on the *same* object — it is a wholly new request (new `request_id`, new `request_hash`, fresh steps 3-10), per the Rerun and Repair Design in `planning/v0.31.0-runtime-orchestration-design.md` |

**Which steps may mutate the request, and when it becomes immutable:** the request is mutable during steps 3-5 (draft/review cycle) and remains conceptually revisable through step 6/7/8 only in the sense that a *new* canonicalization/hash/display cycle can be triggered by a field edit — the canonical snapshot itself, once taken, is never edited in place. The request becomes **fully immutable at step 10** and stays immutable through steps 11-13; nothing downstream of confirmation may write back into it.

## 3. Authoritative Field Inventory

This inventory supersedes the field list in `planning/v0.31.0-runtime-orchestration-design.md`'s "Execution Request Contract" section, which is now a summary pointing here (see final report, "Consistency changes"). **18 fields total.** Three fields were renamed from the prior draft, and their rationale is documented immediately after the table so the discrepancy is explicit rather than silent:

- `allowed_write_directory` → **`output_directory`** — renamed to exactly match the verified helper parameter name (`execute_gauss_code(..., output_directory=...)`), rather than an orchestration-invented synonym. Task instructions for this document use `output_directory` directly.

- `confirmation_timestamp_or_turn_reference` → **`confirmation_timestamp`** — shortened per this task's requested field name; semantically unchanged (§8 clarifies it may hold a wall-clock timestamp or a turn-reference depending on the hosting environment's available clock, since this design assumes no durable cross-session persistence — see §15).

The 18th field (not explicitly named in this task's list of 17) is **`request_id`**, already present in the prior draft as the request's own opaque identity field.

No fields beyond these 18 are part of the Canonical Execution Request. Fields the task's own list implied but that are deliberately **excluded**, with rationale:

- **`mode`** (Advisory / Proposed / Assisted / Post-Execution Analysis) — state-machine-owned, not a request field; storing it redundantly on the request risks the two disagreeing.
- **`allow_file_write`** — the helper accepts this parameter but it is a documented no-op (writes are unconditionally confined to `working_directory` regardless of its value; see §12). Carrying it as a canonical-request field would misrepresent it as a meaningful decision point.
- **`allow_network`** — always `false`; not a genuine per-request choice (network access is an explicit Non-Goal of the entire orchestration design), so it is a Helper Adapter invocation constant, not a request field.
- **`strict`** — always `true` when the Helper Adapter invokes the helper (per the Environment Determinism principle in §6), so likewise a Helper Adapter invocation constant, not a per-request field.
- **`capture_stdout`/`capture_stderr`/`validate_schema`** — all documented no-ops on the helper function itself (see §12); not meaningful request fields.
- **"Known limitations"** (named in `workflows/real-execution-user-workflow.md`'s Execution Request Structure) — a Response Composer *disclosure*, derived at display time from `environment_summary` and `safety_review`, not an independently stored field that could itself go stale relative to those two.

## 4. Code and Script-Path Modes

**Exclusivity rules:** exactly one of `code`/`script_path` must be non-null; both non-null or both null are structurally invalid (§11 stage 2, "mode validation"). This mirrors the helper's own independently-enforced rule (`execute_gauss_code` returns `blocked` if both are supplied, `skipped` if neither is) — the orchestration layer's own check is a preflight convenience, not a substitute for the helper's authoritative enforcement, which remains the actual safety boundary.

**Empty-value rules:** an empty string (`""`) for either field is treated as equivalent to `null` for exclusivity purposes — a request with `code: ""` and `script_path: null` is treated as "neither mode selected" (structurally invalid), not as "inline mode with empty code."

**Normalization:**

- `code`: line-ending normalization only (see §9 — canonicalization normalizes newlines for hashing purposes; the actual code text shown to the user and passed to the helper is not otherwise rewritten, reformatted, or "cleaned up").
- `script_path`: normalized to an absolute, resolved path relative to `working_directory` before being placed in the canonical request, mirroring the helper's own `_resolve_inside` resolution — but this is a *preflight* resolution for display/hashing purposes; the helper independently re-resolves and re-validates the path at invocation time regardless.

**Identity and hashing behavior:**

- For `code`: the literal newline-normalized text is what contributes to the hash (see §9, §10) — two requests with byte-identical code (after newline normalization) produce the same code-identity contribution to the hash; any textual difference, however small, changes it.
- For `script_path`: the *resolved path string* contributes to the hash, not the file's contents. This is a deliberate, documented limitation — see "What happens when the script cannot be fingerprinted reliably" below.

**Whether raw code may be persisted:** see §13. In short: the request's `code` field may persist for the lifetime of the request object (through step 13 of the lifecycle) but is never written to a durable audit log in full; only its hash-contribution and a bounded preview are retained in the Execution Record.

**How the exact code or script identity is displayed before confirmation:** per `workflows/real-execution-user-workflow.md`'s Consent Prompt requirements, the full `code` text (or a clear, complete summary sufficient for review) is shown for inline mode; the resolved `script_path` and, where feasible, the script's own content (read and shown, not merely referenced by path) are shown for script-path mode — a user must never be asked to confirm "the script at this path" without having seen what that script actually contains, since an unseen script cannot be genuinely reviewed under the Pre-Execution Safety Review's "code has been shown or summarized clearly" requirement.

**How script changes after confirmation are detected or handled:** this design does **not** implement content-based script fingerprinting (hashing the file's bytes) as part of `request_hash` — the hash covers the *path*, not the file's live content, because the helper itself reads the file fresh at invocation time and this design has no mechanism to snapshot file bytes independently of that read. This is a genuine, documented gap: **a script file could be edited on disk between confirmation and invocation without the `request_hash` changing.** §15 records this as a deferred policy decision ("script fingerprinting") rather than silently treating it as solved. Until resolved, the safest documented mitigation is procedural, not technical: orchestration should re-display the script's content immediately before invocation if any meaningful time has passed since confirmation, and treat "was this script possibly edited since I last saw it" as an open question the Consent Manager cannot currently answer on its own.

**What happens when the script cannot be fingerprinted reliably:** given the above, this design does not attempt content-based fingerprinting at all in this phase — "cannot be fingerprinted reliably" is the *default* state for `script_path` mode, not an edge case. `inline` `code` mode does not have this gap, since the code text itself is already part of the canonical request and needs no separate file read.

**How future file materialization remains out of scope:** this design assumes the user (or a prior, separately-scoped step) has already placed any script and input files at their expected paths before the request reaches `proposed`. No mechanism exists here, or is implied to exist, for orchestration to *create*, stage, download, or otherwise materialize files on the user's behalf — that remains a Non-Goal, consistent with `planning/v0.31.0-runtime-orchestration-design.md`'s existing Non-Goals list.

No GAUSS syntax is invented anywhere in this section; no example in this document claims to be executable or executed.

## 5. Path Contract

Applies to `script_path`, `working_directory`, `output_directory`, `expected_input_files`, and `expected_output_files`.

**Absolute versus relative paths:** `working_directory` must be supplied as an absolute path (or resolvable to one without ambiguity) since there is no "current directory" fallback, matching the helper's own behavior. `script_path`, `output_directory`, and each entry in `expected_input_files` may be supplied relative to `working_directory`; the canonical request stores the *resolved* (post-containment-check) form for hashing and display consistency.

**Normalization:** paths are normalized (redundant separators collapsed, `.`/`..` segments resolved) before containment checking, mirroring `Path.resolve(strict=False)` as used by the helper's own `_resolve_inside`. This is documented as the *verified* helper behavior, not an orchestration invention — the orchestration preflight check exists to give the user accurate pre-confirmation feedback, but the helper performs its own equivalent resolution independently at invocation time regardless.

**Symbolic links or junctions:** the helper's own path resolution does not special-case symlinks/junctions beyond ordinary OS-level path resolution (confirmed by direct inspection of `_resolve_inside`, which uses `Path.resolve(strict=False)` and a `relative_to` containment check with no separate symlink handling). This document does **not** claim symlink-aware containment is verified or guaranteed — a symlink inside `working_directory` that resolves outside it is a known, documented risk category inherited from the helper's current implementation, not something this contract resolves. Orchestration's preflight review should flag any detected symlink for extra scrutiny but cannot claim to close this gap, since the underlying resolution mechanism is the helper's, not orchestration's own.

**Containment expectations:** `script_path`, `output_directory`, and every entry in `expected_input_files` must resolve inside `working_directory` — path traversal (e.g., a `../` segment resolving outside) is rejected. This is enforced twice: once by orchestration's own preflight check (for early, honest user feedback before confirmation) and again, authoritatively, by the helper itself at invocation time (`_resolve_inside` returns `None` → `blocked`). Orchestration's preflight check is advisory/early-warning; **the helper's own enforcement remains the actual safety boundary**, and this document does not claim orchestration's preflight check alone would be sufficient if the Helper Adapter boundary were ever bypassed.

**Existence checks:** `working_directory` must exist and be a directory before a request can reach `proposed` (mirrors the helper's own `path_exists_fn`/`is_dir_fn` checks). `script_path` and `expected_input_files` entries are checked for existence during preflight review where feasible, but the authoritative existence check remains the helper's own at invocation time — a file could theoretically be removed between preflight and invocation, which the Failure Taxonomy's "Pre-invocation stale-state validation" stage (§11 stage 11) exists to catch as a fail-closed condition, not silently proceed past.

**File versus directory checks:** `working_directory` must be a directory; `script_path` must be a file (not a directory) once resolved; `output_directory`, if supplied, must be a directory (or a path that can validly become one — the helper itself does not create directories, so this design does not claim `output_directory` creation is supported).

**Case sensitivity assumptions:** this design makes **no cross-platform claim** about path case sensitivity. On the one verified environment (Windows), paths are case-insensitive for containment/comparison purposes, consistent with `_default_command_builder`'s own case-insensitive executable-basename matching (`basename.lower()`). This document does not claim this generalizes to case-sensitive filesystems (Linux, some macOS configurations) — cross-platform path-case behavior remains an open, unverified question, consistent with every other cross-platform caveat already documented in `KNOWN_LIMITATIONS.md`.

**Windows path considerations:** the verified environment uses Windows-style paths (`C:\gauss26\tgauss.exe`, backslash separators). This document's path-normalization rules must accommodate both `/` and `\` separators for the one verified platform, but makes no claim about POSIX-path behavior beyond what the helper's own `pathlib.Path`-based logic would presumably provide — "presumably" because this has not been verified on a non-Windows environment, and this document does not claim otherwise.

**Collision detection:** see `planning/v0.31.0-runtime-orchestration-design.md`'s File Lifecycle Design — the Safety Review's preflight review should flag a foreseeable filename collision against `expected_output_files` and existing directory contents *before* confirmation, but this is advisory, not an enforcement mechanism; the helper itself does not rename, version, or protect against overwriting colliding output files, and this document does not claim it does.

**Missing paths:** a missing `working_directory` blocks at structural/path validation (§11 stage 3). A missing `script_path` likewise blocks. A missing entry in `expected_input_files` is flagged during preflight review as a likely (not certain, since the helper performs its own authoritative check) blocking condition.

**Unreadable paths:** a path that exists but is not accessible (permissions) is treated the same as "cannot be verified safe" — fail closed, per the Architectural Principle "fail closed on ambiguity" in `planning/v0.31.0-runtime-orchestration-design.md`.

**Path changes after confirmation:** any change to `working_directory`, `output_directory`, `script_path`, or `expected_input_files` after `confirmed` invalidates confirmation (§8, §10) and returns the lifecycle to step 3.

**User-visible path presentation:** all four path-bearing fields are shown in their resolved, absolute form in the displayed plan (per `workflows/real-execution-user-workflow.md`'s Consent Prompt requirement to show the working directory, and this document's extension of that same principle to `output_directory` and expected input/output files) — never shown only as an unresolved relative fragment, so the user can see exactly where on disk the run is scoped.

**Prohibited path behavior:** path traversal outside `working_directory` in any of the four fields; a `working_directory` that is the repository root, a home directory, or another broad/system directory without explicit, informed user approval (per `workflows/real-execution-user-workflow.md`'s Working Directory and File Rules); any path pointing outside the local filesystem (e.g., a network share used without explicit review, since this design makes no claim about network-path safety).

**Helper enforcement vs. orchestration preflight review, kept distinct throughout this section:** every containment/existence/type claim above is phrased to distinguish "the helper itself already verifiably does this" (grounded in direct code inspection) from "orchestration's own preflight check adds early, non-authoritative feedback." The helper remains the actual enforcement boundary in every case; orchestration's preflight review exists for better user experience (catching problems before confirmation rather than after), not as a claimed independent safety layer.

## 6. Environment Determinism

**Explicit environment context, required:** the Helper Adapter must always invoke the helper with either an explicit `environment_check_result` or a direct `executable_path`+`gauss_version` pair — never by omitting both and letting the helper fall back to its own automatic detection. This binds the request to exactly the environment shown in `environment_summary` before confirmation.

**Strict environment matching, required:** the Helper Adapter must always pass `strict=True` to `execute_gauss_code(...)`. Per direct inspection of `_resolve_environment_context`, `strict=True` prevents the helper from calling `gauss_environment_check`'s automatic detection when no explicit context is supplied — combined with always supplying explicit context (above), this makes environment resolution happen exactly once, during Eligibility Evaluation, and never silently again at `executing` time.

**Fail-closed behavior when the confirmed environment is unavailable or changed:** if, at invocation time, the frozen `environment_summary`'s `executable_path` no longer exists or is no longer accessible, the Pre-invocation stale-state validation stage (§11 stage 11) must treat this as a blocking condition requiring a fresh request — **not** a silent fallback to whatever environment the helper might otherwise auto-detect (which is structurally prevented anyway by always passing explicit context + `strict=True`, but is called out here as an explicit behavioral guarantee, not merely an emergent property of the flags).

**No silent fallback to newly detected executables:** even if a newer or different GAUSS installation becomes available between confirmation and invocation, the frozen `environment_summary`'s `executable_path` is what gets used — or the request fails closed if that path is no longer valid. A "better" newly available executable is never silently substituted.

**No substitution of GUI `gauss.exe`:** `executable_path` must resolve to a terminal executable basename (`tgauss`/`tgauss.exe`); this is validated both by orchestration's Eligibility Evaluator (preflight) and, authoritatively, by the helper's own `_default_command_builder`, which returns an empty command (causing a `blocked` result) for any other executable basename, including `gauss.exe`. Neither layer ever substitutes a terminal executable for a GUI one, or vice versa — an ineligible `executable_path` is rejected, not silently corrected.

**No claim that environment matching proves cross-version compatibility:** binding a request to a specific, unchanged `executable_path`/`gauss_version` guarantees only that the *same* environment context is used at invocation as was shown at confirmation — it does not, and must not be described as, evidence that the executed code would behave identically on a different GAUSS version or platform. Every cross-platform/cross-version caveat already established in `KNOWN_LIMITATIONS.md` remains fully in force.

**Conceptual attributes of `environment_summary` (inputs to the fingerprint/summary, not an implementation):**

- `executable_path` — the resolved GAUSS executable path used to build this request.
- `gauss_version` — the version string, if known (per the helper's own optional `gauss_version` parameter); `null` if unknown, which the helper itself already handles by emitting a version-unknown warning rather than blocking.
- `platform` — the observed OS platform this environment context was resolved on, disclosed to the user but making no cross-platform generalization claim.
- `detection_provenance` — how this context was obtained: a directly supplied `executable_path`/`gauss_version` pair, or a supplied `environment_check_result`. (Automatic detection is explicitly excluded from provenance, since the Helper Adapter never triggers it — see above.)

This document does **not** implement environment fingerprinting logic — it only specifies which attributes a future implementation must capture and freeze into `environment_summary`.

## 7. Eligibility and Safety Representations

**Internal representation, conceptual only (no new runtime classes or schemas are created here):**

- **Eligibility outcome:** a pass/fail result plus, on failure, the specific unmet criterion (or criteria) from `workflows/real-execution-user-workflow.md`'s Execution Eligibility Decision list — represented as a short structured summary (criterion name + human-readable reason), not free text alone, so a future implementation can programmatically distinguish failure categories for the Failure Taxonomy.
- **Safety-review outcome:** a pass/fail result plus a per-item checklist, mirroring `workflows/real-execution-user-workflow.md`'s 14-item Pre-Execution Safety Review verbatim (code shown/summarized, purpose understood, no delete, no unrelated overwrite, no package install, no license activation, no network access, no global config mutation, writes bounded, working directory safe, output directory in scope, terminal executable, timeout set, user confirmation status) — each item recorded as pass/fail/not-applicable, not merely an aggregate boolean, so a specific failing item can be disclosed to the user (per the "explain why" requirement in the Safety Review component).
- **Blocking findings:** a list of specific reasons execution cannot proceed as requested — sourced from either the eligibility outcome or the safety-review outcome, never invented independently.
- **Non-blocking warnings:** informational items that do not prevent `proposed` but should still be disclosed (for example, an unknown GAUSS version, or an `unknown_packages` entry from package inspection, both of which the helper itself already treats as warn-not-block).
- **Approved write locations:** derived directly from `working_directory`/`output_directory` — not an independent list, to avoid two sources of truth for the same containment boundary.
- **Expected files:** `expected_input_files`/`expected_output_files`, already part of the field inventory (§3) — not duplicated here.
- **Unsupported capabilities:** a fixed, non-request-specific list (package installation, license activation, network access, global configuration mutation, GUI execution, cross-platform/cross-version certainty) — this is effectively constant across all requests and is disclosed as part of the Response Composer's "known limitations" framing rather than stored per-request.
- **Known limitations shown to the user:** as established in §3's exclusion list, this is a *derived disclosure*, computed at display time from `environment_summary` (platform/version scope) and `safety_review` (what was and wasn't checked) — not an independently persisted field.

**Where this information lives:**

- **Embedded directly in the request:** `safety_review` (field 17) — yes, embedded, because its exact content is part of what the user confirms and must be immutable alongside the rest of the frozen request.
- **Referenced by identifier:** eligibility outcome is **not** stored as a separate top-level request field in this inventory — a request that failed eligibility never reaches `proposed`/canonicalization at all (per the lifecycle in §2, an eligibility failure returns to step 3), so there is no confirmed request instance to attach a failed eligibility outcome to. A *passing* eligibility outcome is implicitly represented by the request having successfully reached `proposed` at all, plus the underlying facts (`working_directory`, `executable_path`, etc.) that made it eligible — this document does not introduce a redundant `eligibility_review` field duplicating what's already provable from the other 18 fields.
- **Summarized in immutable fields:** `safety_review`, as above.
- **Retained in the execution record:** both eligibility and safety outcomes are retained via the Execution Record's `failure_category`/audit fields (per the runtime orchestration design's Observability section) when a request is blocked, so a blocked attempt is not silently lost — but this is Execution Record content, not Canonical Execution Request content, keeping the two artifacts' responsibilities distinct.

## 8. Confirmation Contract

**Minimum evidence of genuine confirmation** (restated precisely from `planning/v0.31.0-runtime-orchestration-design.md`'s Consent Model, now bound to this document's exact fields): all three of the following must hold before `user_confirmed` may become `true`:

1. A plan was displayed (lifecycle step 8) with every user-visible field (§3's "must be user-visible" set) populated, and `safety_review` shows a passing outcome.
2. The user's very next contribution is affirmative and specifically responsive to *that displayed plan* — not a general affirmative statement made elsewhere in the conversation, and not inferred from silence, a topic change, or an unrelated reply.
3. No edit has occurred to the request between display (step 8) and the confirming reply — if one has, the displayed plan is stale and this test fails until the plan is re-displayed and re-confirmed.

**Exact relationship between confirmation and `request_hash`:** `confirmation_scope` (field 14) must equal `request_hash` (field 18) exactly. `user_confirmed: true` is only meaningful in conjunction with `confirmation_scope == request_hash` — a `user_confirmed: true` with a `confirmation_scope` that does not match the request's *current* `request_hash` is not valid confirmation and must be treated identically to `user_confirmed: false` for the purposes of gating the `confirmed` state transition.

**Required confirmation scope:** always the whole request's `request_hash` — there is no notion of "partial confirmation" of a subset of fields in this design. A user cannot confirm the code but not the working directory; the entire canonicalized snapshot is confirmed as one unit or not at all.

**Confirmation timestamp semantics:** `confirmation_timestamp` records *when/where* consent occurred, for audit purposes (§13) — it is explicitly not part of the hashed content (§10), since a timestamp changing does not mean the technical plan changed, and requiring reconfirmation purely because time passed (absent an actual expiry policy — see next point) would be an unjustified friction cost.

**Confirmation expiry — explicitly unresolved policy:** this document does **not** define a precise timeout after which a `confirmed` request must be reconfirmed purely due to elapsed time. The default posture, carried over from `planning/v0.31.0-runtime-orchestration-design.md`, is: fail closed on genuine doubt (a long gap, an intervening unrelated topic, a resumed conversation) by re-presenting the plan, but no numeric threshold is specified here. This remains an open policy question (§15).

**Session binding:** a `confirmation_scope`/`user_confirmed` pair is valid only within the session it was recorded in (per the Consent Model's "not reusable across sessions" rule) — this document assumes no durable, cross-session persistence of confirmation state (see §13, §15).

**Invalidation triggers:** any change to a hash-included field (§10) after `confirmed` immediately resets `user_confirmed` to `false` and clears `confirmation_scope`/`confirmation_timestamp`, returning the lifecycle to step 3.

**Cancellation before invocation:** a user declining, withdrawing, or failing to respond affirmatively at `awaiting_confirmation` results in a `cancelled` terminal state for this specific `request_id` (per the state machine) — `user_confirmed` remains `false` permanently for this request object; a later attempt to proceed requires a wholly new request, never a revival of the cancelled one.

**Prohibition against inferred, inherited, or reusable consent:** consent is never inferred from code presence, from a prior unrelated confirmation, from a prior session, or from a rerun's predecessor request — every one of these is explicitly ruled out by the minimum-evidence test (point 2 above) and the session-binding/reuse rules in `planning/v0.31.0-runtime-orchestration-design.md`'s Consent Model.

**Explicit restatement, as required by this task:** `user_confirmed: true` alone is **never sufficient**. Valid confirmation additionally requires `confirmation_scope` to equal the canonical request's current `request_hash`, and the three-part minimum-evidence test above to have genuinely held at the moment of confirmation. A future implementation that checks only the `user_confirmed` boolean without also verifying `confirmation_scope == request_hash` would violate this contract.

## 9. Canonicalization Rules

A deterministic procedure for producing the serialized form `request_hash` (§10) is computed over. This section specifies the *rules*, not an implementation (no hashing code is written here).

- **Fixed field order:** the canonical serialization always orders fields in the exact sequence they appear in §3's table (by field number, 1-18) — never construction order, never alphabetical, never any order that could vary between two logically identical requests built differently.
- **Explicit representation of null and omitted values:** every optional field is represented explicitly as `null` when absent — never as a missing/omitted key. A field that is "not yet set" and a field that is "explicitly empty" must be distinguishable and consistently represented (e.g., `expected_input_files: []` for "explicitly no input files" is distinct from a hypothetical omission, which this design does not permit — the field is always present, defaulting to `[]`).
- **Default expansion:** any field relying on a default value (for example, `allow_output_files` defaulting to `true`) must have that default *expanded into the canonical form explicitly* before hashing — never left implicit, since an implicit default could silently change if the default itself changed in a future version, without the hash reflecting that the effective behavior changed.
- **String normalization:** leading/trailing whitespace is preserved as-is for `code` (whitespace can be semantically meaningful in some contexts and this design does not claim authority to strip it); `execution_purpose` and other free-text descriptive fields are not normalized for hashing purposes since they don't contribute to the hash at all (§10).
- **Path normalization:** every path-bearing field (`working_directory`, `output_directory`, `script_path`, each `expected_input_files` entry) is stored in its fully resolved, absolute form (per §5) before canonicalization — two logically identical paths expressed differently (relative vs. absolute, redundant separators, `.`/`..` segments) must canonicalize identically.
- **Collection ordering:** `expected_input_files`, `expected_output_files`, and `required_packages` are sorted into a fixed, deterministic order (e.g., lexicographic) before canonicalization — two requests differing only in the *order* items were entered must produce the same hash, since order has no execution-relevant meaning for these fields.
- **Boolean representation:** canonical `true`/`false` literals only — no truthy/falsy string or numeric substitutes.
- **Numeric representation:** `timeout_seconds` is represented in a fixed numeric form (e.g., always as a float with consistent precision) so that `30` and `30.0` and `30.00` canonicalize identically.
- **Timestamp exclusion:** `confirmation_timestamp` is **excluded** from the canonicalized/hashed form entirely (consistent with §8, §10) — it is metadata *about* the confirmation event, not part of what is being confirmed.
- **Environment-summary normalization:** `environment_summary`'s conceptual attributes (§6) are canonicalized as a fixed-order sub-structure, following the same null/default-expansion rules as the top-level request.
- **Safety-review normalization:** `safety_review`'s per-item checklist (§7) is canonicalized as a fixed-order sub-structure (following the same 14-item order as `workflows/real-execution-user-workflow.md`'s own checklist), not an unordered set.
- **Code newline handling:** `code`'s newlines are normalized to a single convention (e.g., `\n` only, converting any `\r\n`) *for hashing purposes only* — this normalization does not alter what is displayed to the user or passed to the helper, both of which use the code text as originally provided; it exists solely so that a purely line-ending difference (which carries no GAUSS-semantic meaning) does not spuriously change the hash while a genuine content difference always does.
- **Encoding:** UTF-8 is assumed throughout, consistent with the helper's own file-writing behavior (`encoding="utf-8"` when it writes the generated inline-code script).
- **Canonical serialization format:** this document does not mandate a specific format (JSON with sorted keys, a custom delimited format, etc.) — only the *properties* the format must have (deterministic field order, explicit nulls, normalized paths/booleans/numbers/newlines, sorted collections). The specific format is deferred to Phase 1 implementation (§15).
- **Hash algorithm:** **explicitly unresolved** in this document — see §14/§15. Any cryptographic or non-cryptographic hash with acceptably low collision probability for this use case (uniqueness within a session, not adversarial resistance) would satisfy the design's needs, but a specific algorithm is not selected here.

**The overriding requirement these rules exist to satisfy:** the canonicalization procedure must avoid *accidental* hash instability (the same logical request, expressed two different ways, must hash identically) while guaranteeing that any *execution-relevant* change (per §10's hash-inclusion matrix) always produces a different hash, with no exceptions.

## 10. Hash-Inclusion Matrix

All execution-relevant values are treated conservatively — included in the hash and confirmation-invalidating unless a specific, documented reason excludes them. `allow_output_files` was included here after re-review (an earlier draft of this design had excluded it); the discrepancy and reason for reversing that decision are noted below the table.

| # | Field | Included in hash? | Reason | Change invalidates confirmation? | Example of a meaningful change | Example of a nonmeaningful, presentation-only change |
|---|---|---|---|---|---|---|
| 1 | `request_id` | No | Identity, not content — the same content under a different ID would still be the same plan | N/A (never changes for a given request) | — | Regenerating the ID for the exact same content (not a supported operation, but if it occurred, would not represent a plan change) |
| 2 | `code` | Yes | Directly determines what GAUSS executes | Yes | Adding/removing/changing a line of code | A newline-ending-only difference (already normalized away in §9, so it never reaches this point as a "change") |
| 3 | `script_path` | Yes | Determines which file GAUSS executes | Yes | Pointing to a different script file | Expressing the same resolved path with a different relative spelling (already normalized in §9) |
| 4 | `working_directory` | Yes | Determines the entire execution/file-write scope | Yes | Changing to a different directory | N/A — this field has no purely presentational variant once normalized |
| 5 | `output_directory` | Yes | Determines where output-file discovery looks, and (via helper enforcement) where writes are permitted | Yes | Changing to a different subdirectory | Omitting it vs. explicitly repeating `working_directory`'s own value (both canonicalize to the same effective default per §9) |
| 6 | `executable_path` | Yes | Determines which GAUSS binary runs, and whether it's the verified terminal executable at all | Yes | Switching from `tgauss.exe` to a different installation's `tgauss.exe`, or to `gauss.exe` | N/A |
| 7 | `timeout_seconds` | Yes | Determines how long execution is permitted to run before forced termination | Yes | Doubling the timeout | N/A — any numeric change is execution-relevant here |
| 8 | `expected_input_files` | Yes | Determines what files execution is permitted to read | Yes | Adding a new input file | Reordering the same set of files (already normalized in §9) |
| 9 | `expected_output_files` | Yes | Part of the disclosed plan; a change here changes what the user was told to expect and later compare against | Yes | Adding an output file the user wasn't told about before | Reordering the same set (already normalized) |
| 10 | `required_packages` | Yes | A change in package dependencies can change whether the request is even eligible (missing-package blocking) | Yes | Adding a package dependency not previously disclosed | Reordering the same set (already normalized) |
| 11 | `allow_output_files` | **Yes** (revised) | Changes whether `output_files` metadata is captured at all after execution — this affects what evidence will exist, which is disclosed pre-confirmation and therefore execution-relevant to the user's understanding of the plan | **Yes** (revised) | Turning output-file metadata discovery off after the user was told it would be on | N/A |
| 12 | `execution_purpose` | No | Purely descriptive label; does not change what GAUSS executes, where, or how | No, *unless* the changed text discloses a previously-hidden behavior — in which case the underlying behavioral field (e.g., `code`, `expected_output_files`) is what actually changed and already triggers invalidation on its own | Rewording "quick test" to "quick test" with a typo fixed | Any purely cosmetic rewording |
| 13 | `user_confirmed` | No | This field *is* the confirmation flag; hashing it would make the hash depend on the very thing it's meant to gate | N/A (this field's own value is not "invalidated," it's the thing being set/reset) | — | — |
| 14 | `confirmation_scope` | No | Records a hash value; including it in the hash it records would be circular | N/A | — | — |
| 15 | `confirmation_timestamp` | No | Metadata about *when* consent occurred, not part of *what* was consented to | No | — | Any timestamp value, since time passing alone is not a plan change |
| 16 | `environment_summary` | Yes | Determines which GAUSS environment actually runs the code | Yes | A different `gauss_version` becoming the resolved context | N/A |
| 17 | `safety_review` | Yes | The exact reviewed-and-passed checklist is part of what the user is confirming | Yes | A checklist item's outcome changing (e.g., a newly detected collision risk) | N/A — any content change here is by definition execution-relevant |
| 18 | `request_hash` | N/A | Self-referential — the hash cannot include itself | N/A | — | — |

**Discrepancy note (as required — no silent changes):** the original conceptual draft in `planning/v0.31.0-runtime-orchestration-design.md` marked `allow_output_files` as *not* hash-included / not confirmation-invalidating, reasoning that it "does not change execution behavior beyond metadata reporting." This document reverses that decision under the conservative-treatment instruction for this task: while it's true the GAUSS process itself behaves identically either way, the field changes what evidence orchestration will later have and disclose about the run, which is part of the confirmed plan the user reviewed. `planning/v0.31.0-runtime-orchestration-design.md` has been updated to note this reversal explicitly rather than leaving the two documents in silent disagreement (see "Required Consistency Updates," final report).

## 11. Validation Sequence

The exact order every request passes through before confirmation, and again before invocation. Each stage's failure is blocking unless noted otherwise.

| Stage | Inputs | Output | Blocking failure? | Responsible component | Invalidates confirmation? |
|---|---|---|---|---|---|
| 1. Structural validation | Draft request (all 18 fields as currently populated) | Pass, or a list of missing/malformed fields | Yes | Execution Request Builder | N/A (pre-confirmation) |
| 2. Mode validation | `code`, `script_path` | Pass, or "both populated"/"neither populated" error | Yes | Execution Request Builder | N/A |
| 3. Path validation | `working_directory`, `output_directory`, `script_path`, `expected_input_files` | Pass, or specific path-containment/existence/type failures | Yes | Eligibility Evaluator / Safety Review (preflight; helper re-validates authoritatively at invocation) | N/A |
| 4. Environment validation | `executable_path`/`environment_check_result` | Resolved, frozen `environment_summary`, or a blocking "environment unavailable" outcome | Yes | Eligibility Evaluator | N/A |
| 5. Package and input review | `required_packages` | Frozen package-inspection outcome (missing/unknown), or a blocking "missing package" outcome | Yes, if `missing_packages` non-empty; warning-only if only `unknown_packages` | Eligibility Evaluator | N/A |
| 6. Eligibility validation | All prior stages' outputs, per `workflows/real-execution-user-workflow.md`'s Execution Eligibility Decision | Pass, or a specific unmet-criterion outcome | Yes | Eligibility Evaluator | N/A |
| 7. Safety validation | All prior stages' outputs, per the 14-item Pre-Execution Safety Review | `safety_review` (field 17), pass or fail with per-item detail | Yes | Safety Review | N/A |
| 8. Canonicalization | The fully reviewed, passing request | The canonical serialized form (§9) | No (a canonicalization failure would indicate an internal defect, not a user-facing rejection) | Consent Manager | N/A |
| 9. Hash generation | The canonicalized form | `request_hash` (field 18) | No (same as above) | Consent Manager | N/A |
| 10. Confirmation validation | `user_confirmed`, `confirmation_scope`, the three-part minimum-evidence test (§8) | Pass (→ `confirmed`), or fail (remains `awaiting_confirmation`/`cancelled`) | Yes | Consent Manager | N/A (this stage *produces* the confirmed state, it doesn't invalidate one) |
| 11. Pre-invocation stale-state validation | The frozen, confirmed request; a fresh check of `working_directory`/`executable_path`/environment availability immediately before invocation | Pass, or a "stale, must reconfirm" outcome | Yes | Helper Adapter (immediately before calling `execute_gauss_code`) | **Yes**, if staleness is detected — returns to lifecycle step 3 |
| 12. Duplicate-execution validation | `request_hash`, the current in-flight/completed-request registry (conceptual — see §15's "duplicate-execution store") | Pass, or a "duplicate attempt refused" outcome | Yes | Helper Adapter | No (the *original* confirmed request is unaffected; only the duplicate *attempt* is refused) |

Stages 1-7 gate `proposed`; stages 8-10 gate `confirmed`; stages 11-12 gate `executing`. This precisely matches the lifecycle in §2 and the state machine already defined in `planning/v0.31.0-runtime-orchestration-design.md`, without introducing any new states.

## 12. Helper Adapter Projection

Every mapping below is grounded directly in `scripts/gauss_code_execution.py`'s real `execute_gauss_code(...)` signature and behavior (confirmed by direct code inspection during this and the prior review task) — nothing here is invented.

| Canonical field | Helper parameter | Transformation | Notes |
|---|---|---|---|
| `request_id` | *(not passed)* | — | Orchestration-only identity; the helper has no concept of a request ID |
| `code` | `code` | Passed as-is | Mutually exclusive with `script_path`, re-enforced by the helper independently |
| `script_path` | `script_path` | Passed as the resolved path string | Re-resolved and re-validated by the helper's own `_resolve_inside`, independent of orchestration's preflight check |
| `working_directory` | `working_directory` | Passed as-is | Required by the helper; no default |
| `output_directory` | `output_directory` | Passed as-is, or omitted/`None` to let the helper default to `working_directory` | Re-validated by the helper independently |
| `executable_path` | `executable_path` | Passed as-is | Per the helper's own precedence rule, a direct `executable_path` bypasses any `environment_check_result` |
| `gauss_version` (part of `environment_summary`) | `gauss_version` | Passed as-is, or `None` if unknown | The helper warns but does not block on an unknown version |
| `environment_summary` (remaining attributes) | `environment_check_result` | Projected into the helper's `environment_check_result` dict shape *only if* `executable_path` was not resolved directly — otherwise the direct `executable_path`/`gauss_version` pair is used instead, per the helper's own precedence | Whichever form was actually used to build `environment_summary` is the form projected back — orchestration never reconstructs a different form at invocation time |
| `required_packages` (frozen package-inspection outcome) | `package_inspection_result` | The frozen `missing_packages`/`unknown_packages` dict is passed, not the bare `required_packages` name list | The helper blocks on non-empty `missing_packages`, warns on `unknown_packages`; never installs |
| `timeout_seconds` | `timeout_seconds` | Passed as-is (always explicit, per §3 field 7's required-by-policy note) | The helper's own default (30.0) is never relied upon, since orchestration always supplies a value |
| `expected_input_files` | `input_files` | Passed as a list | Name differs — orchestration's "expected" framing (a pre-confirmation disclosure concept) vs. the helper's literal `input_files` parameter (an execution-time allow-list); the values themselves are the same resolved paths |
| `expected_output_files` | *(not passed)* | — | No helper parameter exists for "expected outputs" — this field is orchestration-only, used solely for the Result Validator's post-hoc comparison against the helper's *actual* `output_files` result |
| `allow_output_files` | `allow_output_files` | Passed as-is | The helper's own default is already `true`, matching field 11's default |
| `execution_purpose` | *(not passed)* | — | Display-only; the helper has no concept of "purpose" |
| `user_confirmed`, `confirmation_scope`, `confirmation_timestamp` | *(not passed)* | — | Consent bookkeeping; irrelevant to the helper's own call signature |
| `safety_review` | *(not passed)* | — | The helper has no concept of a safety review; this is orchestration/display/audit only |
| `request_hash` | *(not passed)* | — | Used by the Helper Adapter itself for the duplicate-invocation check (§11 stage 12), never passed into the helper's own call |

**Orchestration-level invocation constants — always set by the Helper Adapter, not derived from the request:**

- `strict=True` — always, per §6's Environment Determinism requirement.
- `allow_network=False` — always; network access is a fixed Non-Goal, never a per-request choice.
- `allow_file_write` — **documented no-op**: confirmed by direct code inspection (`del ... allow_file_write` at the top of `execute_gauss_code`) that writes are unconditionally confined to `working_directory` regardless of this flag's value. The Helper Adapter may omit it entirely or pass its default (`False`); either is behaviorally identical.
- `capture_stdout`/`capture_stderr` — **documented no-ops**: accepted for input-contract completeness only; capture is always attempted whenever the runner is invoked, regardless of value. The Helper Adapter need not set these meaningfully.
- `validate_schema` — **documented no-op on `execute_gauss_code` itself**: this parameter performs no validation inside the function. Real schema validation is the separate function `validate_against_schema(result, schema_path)`, which the CLI calls explicitly and which the Result Validator component (not the Helper Adapter, and not any flag passed into `execute_gauss_code`) must call itself, after the result returns, as a distinct post-call action.

**Helper defaults that orchestration must not rely on silently:** `timeout_seconds` (the helper's own 30.0-second default is never relied upon — orchestration always supplies an explicit value, per §3); automatic environment detection (never triggered, since explicit context + `strict=True` are always supplied); `allow_output_files`'s helper-side default of `true` happens to match this contract's own default (field 11), but this document treats that as a documented coincidence to verify against, not an assumption to silently inherit if the helper's default ever changes.

This document does not call the helper at any point in its own production.

| `timeout_seconds` | Safe to persist | Safe to log |
| `required_packages` (package names) | Safe to persist | Safe to log |
| `expected_output_files` | Safe to persist | Safe to log |
| `allow_output_files` | Safe to persist | Safe to log |
| `execution_purpose` | Safe to persist | Safe to log |
| `user_confirmed` | Safe to persist | Safe to log |
| `confirmation_scope`, `request_hash` | Safe to persist (hash values, not raw content) | Safe to log |
| `confirmation_timestamp` | Safe to persist | Safe to log |

**Explicit statement, as required by this task:** none of the 18 canonical-request fields carry credentials, secrets, or environment-variable values — no such field exists in this contract, and none should ever be added to it. `code` is the one field requiring the most care: it is not itself a secret (the user already sees it in the displayed plan), but it must never be duplicated in full into a durable log or audit trail beyond what the user has already been shown, since GAUSS code could incidentally contain sensitive literals (a data path, a value) that the user did not intend to have logged a second time in a different system.

```
Confirmed request: expected_output_files = ["<file-1>"], request_hash = "<hash-D>"
User asks to also expect "<file-2>" after already confirming.
-> Per §10 (expected_output_files is hash-included and confirmation-invalidating), this is a plan change.
user_confirmed resets to false; confirmation_scope/confirmation_timestamp are cleared.
A new canonicalization/hash ("<hash-E>") and a fresh confirmation are required before proceeding.
```

**Example H — Rerun represented as a new request:**

```
Original request: request_id = "<opaque-id-3>", request_hash = "<hash-F>", execution_status (from the helper's result) = "failed"
User asks to fix and rerun.
-> Per the Rerun and Repair Policy, this is NEVER a mutation of "<opaque-id-3>".
A wholly new request is built: request_id = "<opaque-id-4>", with the proposed fix reflected in `code`/`script_path`.
Its own fresh eligibility review, safety review, canonicalization, hash ("<hash-G>", unrelated to hash-F), and confirmation cycle (steps 3-10) all occur independently.
No field of "<opaque-id-3>" is edited; both requests, and their eventual results (if any), remain distinct and separately attributable.
```

## 15. Open Decisions

**Decisions resolved by this contract:**

- The full 18-field inventory, including two fields the prior draft omitted (`required_packages`, `allow_output_files`) and three renamed for helper/task-name alignment (`output_directory`, `executable_path`, `confirmation_timestamp`).
- The complete hash-inclusion matrix (§10), including the `allow_output_files` reversal.
- The exact validation sequence and which component owns each stage (§11).
- The exact Helper Adapter projection, grounded in the verified helper signature (§12), including which helper parameters are no-ops and which are always-constant at invocation time.
- The persistence/logging classification for every field (§13).
- The confirmation-evidence minimum test and the `user_confirmed`-alone-is-insufficient rule (§8).
- That `script_path` mode does not attempt content-based file fingerprinting in this phase, and why (§4) — this was previously an implicit gap; it is now an explicit, acknowledged limitation.

**Implementation mechanisms deferred (the *what* is settled; the *how* is not):**

- The specific hash algorithm (§9, §14) — any collision-acceptable function satisfies the design; none is chosen.
- The specific canonical serialization format (JSON with sorted keys, or otherwise) — properties are specified, format is not.
- `request_id` generation mechanism.
- The duplicate-execution store's concrete form (an in-memory set, a session-scoped structure, something else) — only its *existence and check point* (§11 stage 12) is settled.
- Cross-process locking, if orchestration is ever hosted across multiple processes — this document assumes a single-process, single-invocation-at-a-time model implicitly but does not design for concurrent processes.

**Policies still requiring a future decision:**

- **Formal schema versus internal typed model:** whether the Canonical Execution Request ever becomes a formal JSON Schema (like the result contract) or remains an internal typed structure only. This document deliberately does not create one either way.
- **Script fingerprinting:** whether/how to eventually detect that a `script_path`-mode script's on-disk content changed between confirmation and invocation, given that `request_hash` currently covers only the path, not the file's bytes (§4). This is flagged as a genuine, currently-unmitigated gap, not merely deferred as a nice-to-have.
- **Confirmation expiry:** whether a precise timeout should govern how long a `confirmed` request remains valid absent any field change, versus the current "fail closed on doubt" posture with no numeric threshold (§8).
- **Session identifier source:** where a `session_identifier` (referenced in the runtime orchestration design's Observability section) actually comes from — this document assumes one exists in the hosting environment but does not define it.
- **Persistence location:** where the Execution Record (which references, but is distinct from, the Canonical Execution Request) is actually stored, even within a single session — in-process memory, a session-scoped file, something else.
- **Sensitive-path treatment:** whether paths containing what *look like* sensitive segments (a username, a project name) warrant any special redaction beyond the general "paths are safe to log since they're already user-visible" rule in §13 — not addressed here, flagged for future consideration.
- **Environment fingerprint attributes:** whether `environment_summary`'s conceptual attributes (§6) should ever be extended (e.g., an OS build number) once cross-platform/cross-version work is actually undertaken — not decided, since that work itself remains unscoped.
- **Duplicate-execution store:** as above, both its concrete form and its scope (per-session only, or something broader) remain open.
- **Cross-process locking:** as above, entirely unaddressed by this design.
