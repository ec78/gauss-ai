## Real Execution Workflow Summary

- Execution is advisory-first — it is never the default response to a code-generation, debugging, or review request.
- Real execution requires explicit user consent before it may occur.
- The assistant must distinguish review/explanation requests from execution requests; a review request does not imply consent to run code.
- Proposed Execution Mode must come before Assisted Execution Mode — the plan is shown and confirmed before anything runs.
- The assistant must show the execution plan (code, working directory, executable, timeout, expected outputs/files) before execution.
- The assistant must perform a pre-execution safety review before any execution.
- The assistant must refuse unsafe execution and explain why, offering a safe alternative.
- The assistant must preserve file-handling boundaries — writes confined to the allowed working directory.
- The assistant must apply execution-aware analysis after execution occurs.
- The assistant must apply the report-generation workflow when the user requests a report, summary, or structured write-up.
- The assistant must not claim execution proves methodology, statistical, or code validity.

## Execution Modes Summary

### Advisory Mode

No execution. Used for review, explanation, debugging guidance, teaching, a missing/unsafe environment, missing consent, or conceptual requests.

### Proposed Execution Mode

The assistant presents the exact execution plan and asks for explicit confirmation.

### Assisted Execution Mode

The assistant may execute only after eligibility passes, the safety review passes, and the user confirms the exact run.

### Post-Execution Analysis Mode

The assistant interprets execution results through `workflows/execution-aware-analysis.md` and `workflows/report-generation.md` as appropriate.

## Consent and Safety Summary

**Consent must be:**

- Explicit.
- Specific to the code/context.
- Given after the execution plan is shown.
- Renewed if code, working directory, files, packages, timeout, or write behavior changes.

**Safety review must confirm:**

- Code is visible or clearly summarized.
- Purpose is understood.
- Working directory is known and safe.
- Executable is the terminal `tgauss`/`tgauss.exe`.
- GUI `gauss.exe` is not used.
- No package installation.
- No license activation.
- No network access.
- No global configuration mutation.
- No delete/destructive behavior.
- File writes are bounded to the allowed directory.
- Timeout is set.
- `output_files` are treated as metadata only.

## File and Output Boundary Summary

- `output_files` metadata is not file content.
- Generated helper scripts are excluded from `output_files`.
- File contents require explicit user-provided content or an explicit safe file-reading workflow.
- The assistant must not infer CSV/plot/table contents from metadata.
- Output file existence does not prove analytical correctness.
- Explicit `output_directory` behavior remains separately scoped unless verified.

## Rerun / Repair Policy Summary

- No automatic rerun loop.
- The assistant may propose a fix after failure.
- Rerun requires renewed user confirmation.
- Changed code must be shown.
- File-write changes require a fresh safety review.
- Timeout changes require renewed confirmation.
- The assistant must not silently broaden scope.

## Evidence and Trust Boundary Summary

- Execution result fields are evidence of execution behavior, not truth.
- stdout/stderr are captured output, not methodology validation.
- `exit_code` is unreliable for GAUSS.
- GAUSS error detection is heuristic.
- Completed execution does not prove code correctness.
- Completed execution does not prove statistical/model validity.
- Failed execution does not prove method invalidity.
- Cross-platform/cross-version limitations remain.
- Methodological validity requires expert reasoning and diagnostics, routed through the Econometrics Expert.
