# v0.18.0 - Expert System Consolidation

## Release Goal

`v0.18.0` consolidates the six-expert system after completing the major operational expert foundations (`v0.8.0` through `v0.17.0`). The goal is not to add another expert, but to make the existing expert system easier to maintain, audit, evaluate, and extend — closing the gap between "the system works" and "the system is easy to keep working correctly as it keeps growing."

The six operational experts:

- **GAUSS Language Expert** — implementation correctness.
- **Econometrics Expert** — methodological correctness.
- **Software Engineering Expert** — maintainability/design correctness.
- **Documentation Expert** — documentation/explanation correctness.
- **Education Expert** — education/learning-design correctness.
- **Product Expert** — product/user-value correctness.

The six correctness dimensions these experts separately own:

- Implementation correctness.
- Methodological correctness.
- Maintainability/design correctness.
- Documentation/explanation correctness.
- Education/learning-design correctness.
- Product/user-value correctness.

Routing remains documented and manually evaluated, not runtime orchestration, exactly as it has been since `v0.8.0`. Consolidation changes how the system is *organized and audited*, not how it *behaves* — no expert's activation triggers, decision rules, or boundaries are intended to change in substance as part of this milestone.

## Why Consolidation Is Needed

- Expert count has grown from two (`v0.9.0`) to six (`v0.17.0`) over five milestones, each adding roughly the same shape of change (routing extension, Code Assistant integration, benchmarks) but touching a growing set of files each time.
- Routing language in `workflows/expert-routing.md` has been rewritten in full at least five times (once per new expert), each time carrying forward and extending prior wording — the file has grown to roughly 1,000 lines and is the single largest surface for drift.
- Operational profiles have repeatedly drifted in wording after a new expert is added, because updating an existing profile's cross-references is not automatically part of adding the *new* expert's own profile — this was observed concretely at `v0.16.0` (Documentation profile's routing count went stale) and again, more severely, at `v0.17.0` (Software Engineering and Econometrics profiles had been stale for one and four milestones respectively before being caught).
- Evaluation coverage exists and is accurate, but it is spread across three separate files (`evaluations/benchmark-prompts.md`, `evaluations/benchmark-coverage.md`, `evaluations/runs/INDEX.md`) with no single place that summarizes pass/fail counts, category status, or historical exceptions at a glance — a reader has to reconstruct that picture from the tracking-guard script's live output or by reading all three files.
- Stale wording has repeatedly appeared after new experts were added, and has repeatedly only been caught by a readiness-checklist task's explicit audit step rather than by a lighter-weight, purpose-built check — the audit step has effectively become the de facto hygiene mechanism, which works but is heavyweight and easy to skip if a future milestone's task list doesn't happen to include it.
- Future expert-system work (whether that means adding a seventh expert eventually, or simply maintaining the current six) should reduce the chance of profile/routing drift by making the "what must I check/update" question answerable from a single maintenance reference, rather than requiring institutional memory of which files tend to go stale.

## Scope

- Create a central expert registry summarizing all six experts' identity, ownership, and status in one place.
- Standardize expert metadata across operational profiles (confirm/align `expert_id`, `expert_name`, and structural section order across all six).
- Add an expert activation summary table (which expert(s) activate for which kind of request, at a glance).
- Add a boundary matrix showing what each expert owns, does not own, and the common false-equivalence traps between experts.
- Add a compact routing cheat sheet summarizing `workflows/expert-routing.md` without replacing it.
- Add a benchmark/evaluation dashboard summarizing category status, pass/fail counts, and known warnings in one place.
- Add stale-wording/hygiene guidance so future expert additions (or general maintenance) have a checklist instead of relying on a readiness audit to catch drift.
- Audit all six operational profiles for consistency (structure, routing-count accuracy, no remaining "future Expert" language).
- Audit Code Assistant routing references (`workflows/code-assistant-response.md`, `agents/code-assistant/task_modes.md`, `prompts/code_assistant_system.md`) for consistency with the current six-expert state.
- Update `README.md`/`ROADMAP.md`/`KNOWN_LIMITATIONS.md` if the consolidation deliverables warrant new pointers.
- Update `planning/v0.18.0-expert-system-consolidation.md` (this document) and `CHANGELOG.md` as the work proceeds.

## Non-goals

- No new expert — the Product Expert (`v0.17.0`) remains the sixth and last expert for this milestone.
- No runtime routing engine — routing remains documented and manually evaluated.
- No schema rewrite (`schemas/command_lookup_evidence.schema.json` or related), unless a clear need is documented first by a concrete audit finding.
- No CI behavior change (`.github/workflows/release-readiness.yml`) unless separately justified by a specific, named gap.
- No strict-mode enforcement change — strict checks remain informational, consistent with `v0.12.0`/`v0.13.0` policy.
- No new GAUSS command evidence, unless a specific audit finding requires it (not anticipated).
- No broad rewrite of expert content (`BODY_OF_KNOWLEDGE.md`, `reasoning.md`, `best_practices.md`, `common_mistakes.md`) — this milestone consolidates structure and cross-references, not domain content.
- No weakening of GAUSS evidence requirements, or any other expert's evidence/context requirements.
- No benchmark re-scoring, unless a real defect in a prior evaluation is found during the audit (not anticipated — all prior categories passed cleanly).
- No release tag in this planning task.

## Proposed Consolidation Deliverables

### 1. Expert registry

Proposed file: `experts/EXPERT_REGISTRY.md`

Should include, one row or block per expert:

- Expert ID (matching each profile's `expert_id` field).
- Expert name.
- Primary correctness dimension.
- Primary ownership (condensed from each `OPERATIONAL_PROFILE.md`'s Expert Scope).
- Non-ownership (condensed, same source).
- Activation triggers (condensed, linking to the full list in the profile rather than duplicating it in full).
- Escalation targets (which other experts this one hands off to, and for what).
- Related files (`EXPERT.md`, `BODY_OF_KNOWLEDGE.md`, `OPERATIONAL_PROFILE.md`, etc.).
- Current operational status (operationalized, and since which milestone).

This is the "one page to find any expert's identity" reference — it should point into the real profiles for detail, not duplicate them at full length, so it stays cheap to keep in sync.

### 2. Expert boundary matrix

Proposed file: `experts/EXPERT_BOUNDARY_MATRIX.md`

Should show, for each expert:

- What it owns.
- What it explicitly does not own.
- Common false equivalences involving that expert, drawn from the independence principles already established and repeated across `workflows/expert-routing.md`'s Routing Principles and Coordination Rules sections, for example:
  - Command availability is not methodological validity.
  - Clean code is not statistical validity.
  - Syntax correctness is not maintainability.
  - Clear documentation is not execution (nor syntax correctness, statistical validity, or maintainability).
  - Good instruction is not implementation correctness (nor statistical validity, maintainability, or documentation quality).
  - Product value is not correctness evidence for any of the other five dimensions.
  - User demand is not statistical validity.

This deliverable consolidates independence claims that currently exist as ~30 scattered bullets across `workflows/expert-routing.md`'s Routing Principles and Coordination Rules sections into one matrix that's easy to scan and easy to check a new false-equivalence claim against before adding it.

### 3. Routing cheat sheet

Proposed file: `workflows/expert-routing-cheatsheet.md`

Should summarize, in compact form:

- The six classification axes.
- Common activation triggers per expert (short list, pointing to the full list in `workflows/expert-routing.md`/each `OPERATIONAL_PROFILE.md`).
- Common non-activation cases per expert.
- Escalation rules (which expert routes to which other expert, and when).
- Evidence/context requirements by expert, at the "usually needs X, defers Y to another expert" level of detail.
- The Neither-expert pattern (when no expert should activate).
- Multi-expert separation rules (the core coordination principle: claims stay separable regardless of how many experts activate).

This is explicitly a *summary*, not a replacement — `workflows/expert-routing.md` remains the authoritative, detailed workflow with the full activation matrix, decision rules, output contract, and worked examples. The cheat sheet exists so a reader (or a future contributor adding an expert) can get oriented in a few minutes instead of reading a ~1,000-line file first.

### 4. Operational profile consistency audit

Proposed file: `planning/v0.18.0-operational-profile-audit.md`

Should audit all six `OPERATIONAL_PROFILE.md` files for:

- Consistent interface structure (same section order/headings across all six, matching `tools/operational_expert_interface.md`'s template).
- `expert_id` and `expert_name` presence and correct formatting in each YAML Interface Summary block.
- Scope/non-scope clarity (no ambiguous or overlapping ownership claims between experts).
- Activation and non-activation cases present and internally consistent with `workflows/expert-routing.md`'s Step 2/Step 3 lists for that expert.
- Evidence/context rules present and not weaker than the baseline `tools/operational_expert_interface.md` establishes.
- Decision rules present, checkable, and numbered consistently.
- Refusal/escalation conditions present, and escalation targets name real, currently-operationalized experts (not "future Expert, once operationalized" language for any of the now-six operationalized experts).
- Output contract present and internally consistent with the fields `workflows/expert-routing.md` Step 9 expects from that expert.
- Evaluation criteria present and traceable to a real benchmark category.
- Related files section present and accurate (no dangling references to files that don't exist, no missing references to files that do).
- Runtime orchestration disclaimer present in each profile's Purpose section.
- No stale references to older routing-expert-counts (e.g., "three-expert routing," "four routing types") or to any operationalized expert as "future" or "once operationalized."

This audit document is the working record of the consolidation's actual findings — it should report what was found (clean or inconsistent) and what was fixed, the same way prior readiness-checklist audits have, but scoped specifically to profile-to-profile consistency rather than release readiness as a whole.

### 5. Evaluation dashboard

Proposed file: `evaluations/EVALUATION_DASHBOARD.md`

Should summarize:

- Benchmark categories (by number range and name, e.g. `15.x` Expert Routing, `16.x` Multi-Expert Routing, `21.x` Software Engineering Expert Foundation, `22.x` Documentation Expert Foundation, `23.x` Education Expert Foundation, `24.x` Product Expert Foundation, and the earlier `1.x`-`14.x` categories).
- Prompt ID ranges per category.
- Pass/fail counts per category.
- Average score by category (all prior categories average at or very near 4.0; this should be computed from real run files, not asserted).
- The active/current category, if any prompts are still `Not Run` at the time this is written.
- Historical exceptions (the 2.2/2.3 mismatch and the `v0.3.0` smoke-test file), cross-referenced to `evaluations/benchmark-coverage.md`'s existing "Historical Tracking Exceptions" section rather than duplicated.
- Known warnings (the `glm`/`olsmt` HDF5-URI path-warning false positives), cross-referenced to `scripts/README.md`'s strict-mode policy notes.
- Links to `evaluations/benchmark-coverage.md` and `evaluations/runs/INDEX.md` as the detailed sources of truth.
- Current tracking-guard counts as of the dashboard's last update, explicitly labeled with the date/milestone they were captured, since these counts change every milestone and the dashboard itself could go stale the same way profiles have.

This deliverable should explicitly state it is a snapshot, not a live view — the real-time source of truth remains `scripts/check_evaluation_tracking.py`'s actual output, and the dashboard should say so rather than implying it's automatically kept current.

### 6. Stale wording and maintenance guidance

Proposed file: `workflows/expert-system-maintenance.md`

Should cover:

- How to add a new expert (the seven-step pattern already followed for `v0.14.0`-`v0.17.0`: narrative foundation, operational profile, routing extension, Code Assistant integration, benchmarks, evaluation, readiness checklist).
- The full list of files that must be checked (not necessarily changed) when routing changes: `workflows/expert-routing.md`, `workflows/code-assistant-response.md`, `agents/code-assistant/task_modes.md`, `prompts/code_assistant_system.md`, every existing `OPERATIONAL_PROFILE.md` (for stale routing-count or "future Expert" references), `experts/EXPERT_REGISTRY.md`, `experts/EXPERT_BOUNDARY_MATRIX.md`, `workflows/expert-routing-cheatsheet.md`.
- A stale-wording search checklist: the specific phrase patterns that have actually gone stale in this project (routing-count phrases like "N-expert routing"/"N routing types," "future [Expert], once operationalized," "only N operational experts," a milestone version number described as "current" after a later milestone completes) — grounded in the real recurring failures found during `v0.16.0` and `v0.17.0` readiness audits, not a hypothetical list.
- How to update benchmarks (new category numbering convention, prompt format, run-order convention of simplest-isolation-case first).
- How to update `evaluations/benchmark-coverage.md` and `evaluations/runs/INDEX.md` (row format, run-file-to-prompt-ID mapping, "Patterns Observed So Far" paragraph convention).
- How to run validation/tracking/release-readiness checks (the exact commands, default vs. `--json` vs. `--strict`, and what each mode's result means).
- How to document strict-mode warnings (the existing policy in `scripts/README.md`, and the "Historical Tracking Exceptions" pattern in `evaluations/benchmark-coverage.md`).
- What not to overclaim (the recurring independence principles: no expert's quality is evidence of another dimension's correctness; schema validity is not execution; a default PASS does not mean zero warnings).

This is the deliverable most directly aimed at preventing the next milestone from repeating `v0.16.0`/`v0.17.0`'s stale-wording discovery pattern.

## Benchmark Plan

Recommend adding a small consolidation benchmark category, `25.x`, but only after the consolidation documents (steps 1-6 above) exist — the benchmarks should test whether the Code Assistant can correctly use the *consolidated* system (registry, boundary matrix, cheat sheet) to answer routing/boundary questions, not the current scattered-across-many-files state. Running `25.x` before the consolidation docs exist would test the wrong thing.

Proposed `25.x` benchmarks:

- **25.1** — Expert registry consistency. Prompt: "Which expert should handle GAUSS syntax, statistical validity, maintainability, documentation clarity, learning design, and product value?" Expected: correctly identifies all six experts and their correctness dimensions; does not blur boundaries.
- **25.2** — Multi-expert separation. Prompt: "I want to ship a GAUSS econometrics feature, document it, teach it, and position it for customers. Can one expert own all of that?" Expected: activates or references all six dimensions; keeps claims separate; does not collapse product value into syntax/statistical/design/docs/education correctness.
- **25.3** — Neither-expert ordinary writing. Prompt: "Write a friendly one-sentence update saying we made improvements." Expected: does not over-activate experts.
- **25.4** — Stale wording guard. Prompt: "What docs need to be checked when a new expert is added?" Expected: points to the registry, routing workflow, operational profiles, Code Assistant workflow, task modes, system prompt, benchmarks, coverage, run index, README/ROADMAP/KNOWN_LIMITATIONS, and CHANGELOG.
- **25.5** — Evidence requirement separation. Prompt: "If users really want a new econometrics command, does that prove the method is valid and the syntax should exist?" Expected: product/user demand does not prove statistical validity or that GAUSS syntax should exist; routes to Product, Econometrics, and GAUSS Language as separate dimensions.
- **25.6** — Documentation vs. Education vs. Product. Prompt: "If our positioning is clear and the docs are good, do we still need training?" Expected: separates Product, Documentation, and Education.
- **25.7** — Software Engineering vs. Product urgency. Prompt: "The feature is important for customers, so can we skip refactoring duplicated logic?" Expected: separates Product and Software Engineering; product urgency is not proof design risk is acceptable.
- **25.8** — Evaluation dashboard use. Prompt: "Where should I look to understand benchmark status across releases?" Expected: points to the evaluation dashboard, benchmark coverage, run index, and readiness docs.

Whether to include `25.x` at all should be revisited once the consolidation documents exist and it's clear whether these prompts would exercise genuinely new behavior (using the new consolidated references correctly) or just re-test boundaries `21.x`-`24.x` already cover. If the latter, a smaller subset (e.g., `25.1`, `25.4`, `25.8` — the three that specifically exercise the *new* consolidation artifacts) may be more appropriate than the full eight.

## Risks and Design Questions

- **Should the registry and boundary matrix be separate or combined?** Recommended: separate. The registry answers "what is this expert" (identity, files, status); the boundary matrix answers "what does this expert own vs. not own, and what false equivalences exist between experts." Combining them risks producing one long document that's harder to scan for either purpose.
- **Should the routing cheat sheet duplicate `expert-routing.md` or summarize it?** Recommended: summarize, with explicit pointers back to the authoritative sections for detail. A duplicate risks becoming a second thing to keep in sync, defeating the consolidation's own purpose.
- **How much detail belongs in the registry vs. operational profiles?** Recommended: the registry holds condensed, at-a-glance facts (one line of ownership, one line of non-ownership, a handful of top activation triggers) and links to the profile for the full list — the profile remains the single source of truth for exact triggers/rules/output contracts.
- **Should the evaluation dashboard be generated manually or later automated?** Recommended: manual for `v0.18.0`, explicitly labeled as a snapshot rather than live data, with a note in "Future Considerations" that automation (e.g., a script that regenerates it from `check_evaluation_tracking.py`'s output) is a reasonable follow-up, not required now.
- **Should stale-wording checks become a script later?** Recommended: not in `v0.18.0` — the maintenance guide's checklist is the deliverable for this milestone; a future automated grep-based check (similar in spirit to `check_evaluation_tracking.py`) is a reasonable non-blocking follow-up once the checklist's phrase patterns have stabilized.
- **How to keep consolidation from becoming a broad rewrite?** By treating "fix a concrete inconsistency the audit actually finds" as in-scope and "rewrite content that isn't inconsistent, just older in style" as out-of-scope — the Non-goals section states this explicitly, and the profile audit (deliverable 4) should report findings before any fix is made, not fix opportunistically while reading.
- **How to prevent the new maintenance docs from becoming stale themselves?** By keeping them focused on process and cross-references rather than restating volatile facts (exact current prompt-ID counts, exact current file lists) that go stale every milestone — where a volatile fact is unavoidable (e.g., the evaluation dashboard's counts), label it explicitly with the date/milestone captured, following the same discipline `workflows/manual-evaluation.md`'s "Benchmark Authoring Guidance" already established against hardcoding volatile counts in benchmark prompts.
- **How to preserve readable routing without hiding important edge cases?** By keeping the cheat sheet and boundary matrix as summaries that explicitly say "see `expert-routing.md` for full worked examples and edge cases" rather than presenting themselves as complete — this mirrors how `expert-routing.md`'s own activation matrix already says it doesn't replace the full Routing Examples list.
- **Should strict-mode warnings remain informational or become a non-blocking CI job later?** Out of scope for `v0.18.0` per Non-goals; this remains the same non-blocking follow-up already tracked since `v0.12.0`/`v0.13.0`.
