# v0.82.0 — Bounded Control-Flow Syntax Coverage: Design

Status: **implemented** (2026-10-08). The plan (§1–§8) was approved with every recommendation in §8. §9 records what changed during implementation, including one user-approved scope addition (§9.2). §10 is testing; §11 is the live evaluation.

## 1. Why

Live finding 71.3: a client model, asked to "create a 5x1 vector of zeros, then fill it with the squares of 1 through 5", wrote the natural answer:

```gauss
v = zeros(5, 1);
for i(1, 5, 1);
    v[i] = i^2;
endfor;
print v;
```

It got `review_required`, and the only blocker was syntax coverage. `_detect_unknown_syntax_constructs(...)` reports any line that starts with a block keyword as `control_flow_block`. That makes syntax `PARTIAL`, so `compute_evidence_profile` cannot return `BROAD`.

Goal: simple, idiomatic `for` loops reach `HANDOFF_CANDIDATE` on real evidence. `compute_handoff_readiness`, `compute_evidence_profile`, `compute_eligibility` and `_SYSTEM_STATEMENT_REGISTRY` stay unchanged. Any construct the new rule does not fully model stays an unknown construct.

## 2. Investigation findings

### 2.1 How loop bodies interact with the rest of validation today

I ran probes through the real `validate_code` against `C:/Users/Owner/.gauss-ai/docs` on v0.81.0:

| Probe | Verdict | Why |
|---|---|---|
| 71.3 snippet (multi-line) | review_required | syntax `partial` (`control_flow_block`) and nothing else |
| hallucinated `colmean(i)` inside the body | **not_ready** | call extraction and the symbol check are line-based and ignore blocks |
| `dos "dir";` inside the body | **not_ready** | the system-statement gate is line/statement-based and ignores blocks |
| `x = {-1 0, 0 -1}; for …; y = invpd(x); endfor;` | **not_ready** (VIOLATED) | `_governing_assignment` traces `x` to the top-level literal before the loop |
| same, but `x` is reassigned *inside* the body after the call | review_required (UNVERIFIED) | `_governing_assignment` refuses a variable written inside a block |
| doubly-nested `for` | review_required | `control_flow_block` |

So every existing `NOT_READY` protection already reaches into loop bodies. The only thing standing between 71.3 and candidacy is the syntax layer. The new rule must not weaken that layer in any other way.

### 2.2 Pre-existing fail-open defects found during the investigation

These are not loop-specific, but they sit right next to the change. All but the first were confirmed with real `tgauss.exe -b`.

1. **A one-line `for` loop is invisible to the syntax layer.** `v = zeros(5, 1); for i(1, 5, 1); v[i] = i^2; endfor; print v;` currently gets syntax **`validated`**, because block detection only looks at line starts. The loop variable `i(` is also misread as a call, because `call_scan_text` only blanks a `for` counter at the start of a line. It ends up `review_required` only by accident (no signature for `i`).
2. **`threadfor … threadendfor` and `threadbegin … threadend` are invisible.** Both get syntax `validated` with no unknown construct. These are parallel constructs (`threadfor.rst`, `threadbegin.rst`) that this layer does not model at all.
3. **An assignment whose right-hand side starts with `{` is a `let` statement, and the validator does not know it.** Real GAUSS rejects all of these, and the validator reports every one as `validated`:

   | Snippet | Real GAUSS 26.1.4 |
   |---|---|
   | `x = {1, 2, 3}';` | `G0008 Syntax error '''` |
   | `x = {1, 2} + 1;` | `G0008 Syntax error '+ 1'` |
   | `x = {2 1, 1 2} * -1;` | `G0008 Syntax error '* -1'` |
   | `x = {1, 2} .* 3;` | `G0008 Syntax error '.* 3'` |
   | `v[1:2] = {7, 8};` | `G0008 Syntax error '[1:2] = {7, 8}'` |
   | `v[., 1] = {1, 2, 3};` | `G0008 Syntax error` |
   | `v[2] = {5};` | `G0047 Rows don't match` + `G0008` |

   The literal is fine anywhere it does not *begin* the right-hand side: `x = ({1, 2}) + 1;`, `x = 2 * {1, 2};`, `y = meanc({1, 2, 3}) + 1;`, `y = sumc({1, 2, 3}');` and `v[., 1] = ones(3, 1);` all run. That matches `let.rst`: "If curly braces are used, the let is optional", so `x = {…}` *is* a `let`, and a `let` takes a constant list and nothing else. The indexed-write form matters directly here, because indexed writes are what loop bodies are made of. `x = {…}'` is a shape models write routinely.

### 2.3 Documented `for` syntax

`for.rst` (Format) and `user-guide/fundamentals/control-flow.rst` ("Counted Loops: for"):

```
for i (start, stop, step);
    ...
endfor;
```

- `i` is the counter name. It is "**strictly local** to the loop. It does not affect any global variable with the same name, and it is not accessible after the loop ends."
- `start`, `stop` and `step` are "scalar expressions, evaluated **once** when the loop initializes".
- `break` and `continue` are supported.
- Both pages' canonical preallocate-and-fill example is a **nested** `for` (`x = zeros(…); for i (1, rows(x), 1); for j (1, cols(x), 1); x[i, j] = i*j; endfor; endfor;`).

## 3. Proposed design

All changes are deterministic, stdlib-only and in `scripts/gauss_pre_execution_validation.py` unless noted.

### 3.1 One statement scanner

Add a small whole-code statement splitter. It works on comment-stripped code (as every caller already passes), masks string contents, splits on `;` across lines (so a multi-line matrix literal is one statement), and records each statement's start line. Block detection, the new `for` rule and the `let` rule all use it.

`_detect_unknown_syntax_constructs` switches from "line starts with a keyword" to "statement starts with a keyword". That fixes defect 2.2(1). `_BLOCK_CONSTRUCT_KEYWORDS` gains `threadfor`, `threadendfor`, `threadbegin`, `threadend` and `threadstat`, so defect 2.2(2) fails closed as unknown. `call_scan_text` blanks a `for`/`threadfor` counter at any statement start, not only at line start. That is the shared definition, so the symbol checker gets the same fix.

### 3.2 The `for` block rule

A new pass, `_check_for_blocks(...)`, walks the statements with a stack of open blocks.

**Validated** (new validated construct `for_block`) only when every one of these holds:
- the header is exactly `for NAME (a, b, c);`: one identifier, then a parenthesized list of exactly three non-empty top-level arguments, then end of statement; keywords are matched case-insensitively;
- the header arguments contain no `{` matrix literal and no string (both are silently accepted by GAUSS or undocumented, so they are **unknown**, not validated);
- the block is closed by its own `endfor;`;
- every body statement is on the allowlist in 3.3.

**INVALID**, each with recorded `tgauss.exe -b` provenance (2.4):

| Rule | Catches | Evidence |
|---|---|---|
| `for_header_shape` | wrong argument count; `for i = …`; a `for` with no parenthesized list (incl. C-style); trailing text after `)` (missing `;`) | G0105, G0008, G0113, G0063 |
| `for_block_balance` | `endfor` with no open `for`; open `for` at end of code; a `for` closed by `endo`/`endif`/`endp`; `endfor` closing an open `if`/`do`; `endfor` followed by more text (missing `;`) | G1001 (×4), G0008 |
| `for_counter_reuse` | a nested `for` reusing an enclosing loop's counter | G0736 |
| `for_counter_assignment` | a plain or indexed write to any enclosing loop's counter inside the body | G0541 |

INVALID is complete coverage (unchanged policy), so these make the snippet `NOT_READY`, the same as every other syntax violation.

### 3.3 Body allowlist

Inside a `for` body (including nested `for` bodies), a statement is modelled only if it is one of:
- a nested `for` header or `endfor`;
- a plain assignment `name = expr` that passes the existing assignment rules;
- an indexed assignment `name[idx] = expr` (no member `.field`, no multiple targets `{a, b} = …`);
- a `print` statement;
- an empty statement (`print i;;`).

Anything else marks that loop **unknown** (`control_flow_block`, as today), so the snippet stays `PARTIAL` at best. That covers `if`/`do`/`break`/`continue`/`proc`/`local`/`fn`/`goto`/`gosub`/`threadfor`, any other keyword-led statement, multi-target or member writes, and bare expression or command statements (`format …`).

This is deliberately stricter than top-level code, where unrecognised statements are not flagged today. Changing top-level behaviour is out of scope.

The existing rules (delimiters, matrix literals, dangling assignment, bare multi-token literal, call-argument separator, unterminated string) already run over the whole text, body included. So do the call extraction, symbol, signature, role, precondition and system-statement checks. Nothing about them changes.

### 3.4 The `let`-statement rule (fixes 2.2(3))

New INVALID rule `let_statement_shape`. In an assignment whose right-hand side **begins** with `{` (with or without `let`):
- the target must be a plain identifier (not indexed or member);
- nothing but whitespace may follow the matching `}`.

Provenance: `let.rst` (Format, and "If curly braces are used, the let is optional"), plus the seven real G0008/G0047 results and five accepted counter-examples in 2.2(3). This applies to top-level code too: it is a real false negative wherever it appears. Before implementing I will also run `{…} ~ {…}` and `{…} | {…}` through `tgauss.exe -b`. If either is accepted, the rule narrows to match the evidence.

### 3.5 Variable tracing (the open design question)

Today any indexed write `v[…] = …` makes `v` untraceable for the whole snippet, in both the role check and the precondition tracer. Options:

- **A. Leave tracing unchanged.** 71.3 itself does not need tracing (it ends in `print v;`). But "fill, then use" (`…; endfor; m = meanc(v);`) stays `review_required`, because `meanc`'s role check is UNKNOWN.
- **B. (Recommended) Look through indexed writes for *category* only.** The role check asks one question: is `v` a scalar, vector or matrix? Real GAUSS shows an indexed write cannot change that: out-of-range writes are `G0058` (no growth, in 1-D and 2-D), and a value of a different type stored into a numeric element leaves a 3x1 matrix (type 6). So for the role check, `_governing_assignment` would skip indexed writes to `v` when the governing right-hand side is numeric (literal matrix/vector/scalar, or a documented numeric return). String targets keep refusing (`G0071`). The **precondition tracer keeps refusing**, because an indexed write changes values, and a literal is no longer evidence of what `invpd` receives. Plain writes inside any block, member writes, multi-target writes, `clear` and the counter-name rule all keep refusing, as now.

With B, `v = zeros(5, 1); for i (1, 5, 1); v[i] = i^2; endfor; m = meanc(v);` reaches candidacy. `x = {2 1, 1 2}; x[1, 1] = -5; y = invpd(x);` stays UNVERIFIED, never SATISFIED.

The counter is documented and observed as strictly local, so `for i` does not actually write an outer `i`. I propose to **keep** refusing to trace a variable that shares a counter's name anyway. It is rare, and the conservative answer costs nothing.

### 3.6 71.5 search findings

- **Garbled Syntax line (in scope, small).** `command_doc_lookup.extract_function_directive_details` appends any indented line containing `(…)` to `syntax`, even a continuation of a `:param` description. That is how `vcmvcx.rst`'s ddof text ("will be :math:`(N - ddof)`…") lands in Syntax. The fix: only collect such lines while no `:param`/`:return` block is open. `syntax_blocks` feeds signature extraction, so before merging I will diff extracted syntax blocks across all 1,826 published pages, and diff signatures and verdicts on the v0.81.0 re-baseline snippet set. Every page that changes will be listed in §4 of this doc.
- **`gauss_search_docs` grounding noise (out of scope).** Grounding a free-text query ("covariance matrix") is a query-classification design question, not a defect with a bounded fix. Validation grounds on the code's own calls and is unaffected. It stays disclosed; 72.x may observe it again.

## 4. Scope boundary

In scope: `for … endfor` at any nesting depth, with the body allowlist above; the two INVALID families; the `let` rule; the fail-closed fixes in 2.2(1)/(2); option B tracing (if approved); the vcx Syntax-line fix.

Out of scope (stay `control_flow_block` → at best `review_required`):
- **`if`/`elseif`/`else`.** A condition needs expression modelling, and branches make "the governing assignment" conditional. That is a real tracing change, not a syntax rule. `break`/`continue` come with it, since an unconditional `break` is not idiomatic.
- **`do while`/`do until`.** Termination is not syntactic, so a validated `do` loop would still say nothing about whether it ends. (The handoff has a 30 s timeout, but syntax coverage should not lean on that.)
- **`proc`/`keyword`/`fn`.** Scoping (`local`, `retp`) changes what tracing means.
- **`threadfor`/`threadbegin`.** Parallel semantics. Now detected and reported as unknown (previously invisible).

Nested `for` is **in** scope, against the handoff's suggestion that it might stay out. Both official pages use a nested loop as *the* preallocate-and-fill example, so a 2-D fill is the matrix version of 71.3. The stack makes nesting no harder than one level, and its only nesting-specific failure (`G0736`) is evidenced.

## 5. Known limitations this design accepts

These are runtime semantics, not syntax. They would all be disclosed in `KNOWN_LIMITATIONS.md`:
- Out-of-range indexed writes (`G0058`), writes to a never-assigned variable (`G0458`) and a zero step (`G0538`) fail at run time. The handoff reports the failure honestly. Nothing silent.
- A fractional step with indexed writes silently truncates indices (2.4). That is a validated loop that computes something surprising. Header expressions are not evaluated (the same "expressions are never evaluated" limitation as v0.81.0), so a literal `0.5` step is not singled out. **Alternative if you prefer:** treat a non-integer *literal* step as unknown. It is cheap, and it removes the one silent case I found.
- A variable holding a matrix as a header bound is not checked (GAUSS silently accepts a matrix `start`). Only a literal `{…}` header argument is caught (as unknown).

## 9. Implementation and deviations from the approved plan

All five §8 decisions were approved as recommended: nested `for` in scope, option B tracing, the `let` rule, a non-integer literal step treated as unknown, and the vcx Syntax-line fix.

### 9.1 As planned

- `_split_statements(...)` (whole-code, cross-line `;` splitting) and `_check_control_flow_blocks(...)` replace `_detect_unknown_syntax_constructs(...)`. They add the validated construct `for_block` and the INVALID rules `for_header_shape`, `for_block_balance`, `for_counter_reuse` and `for_counter_assignment`. All are in `_SYNTAX_RULE_REGISTRY` with their `tgauss.exe -b` provenance.
- `_check_let_statements(...)` adds `let_statement_shape`. Before implementing, `{…} ~ {…}` and `{…} | {…}` were run through real GAUSS as promised in §3.4: both give G0008, and `-{1, 2}` runs. So the rule stands as designed ("an assignment whose right-hand side *begins* with `{`").
- `call_scan_text` blanks a `for`/`threadfor` counter at any statement start. `threadfor` joined `_LANGUAGE_CONSTRUCT_KEYWORDS` (both copies), because a blanked `threadfor i(...)` header reads as `threadfor (...)`.
- `_BLOCK_CONSTRUCT_KEYWORDS`, `_BLOCK_OPEN_KEYWORDS` and `_BLOCK_CLOSE_KEYWORDS` gained the `thread*` keywords. Thread blocks are now unknown for syntax and refusing for tracing.
- Option B: `_governing_assignment(..., allow_indexed_writes=False)`. `resolve_argument_category` makes a second, category-only pass with it set and accepts only `scalar`/`vector`/`matrix`. The precondition tracer never sets it.
- **Small extension:** a non-integer literal *start* is treated as unknown, not just the step (§5). A fractional start truncates indices exactly as a fractional step does.
- `command_doc_lookup.extract_function_directive_details`: an indented line inside an open `:param`/`:return` block is no longer also collected as syntax (live finding 71.5).

### 9.2 Deviations found by the all-pages diff

The §3.6 diff (all 1,826 published pages, syntax blocks and every `= name(` signature, before vs after) surfaced three things the plan did not anticipate.

1. **Nested optional groups were mis-parsed (pre-existing).** `_parse_signature_occurrence` treated `[` as nesting depth, so `plotSave(filename[, size[, units[, dpi]]])` read as `filename` plus one name `size[, units[, dpi]]` (max 2 args). A 4-arg example spliced in from the `dpi` description (the very 71.5 defect) had been masking it. Fixing the splice alone would have made a valid 4-arg `plotSave` call a false count mismatch. Nested groups are now flattened before splitting.
2. **A documented `...` counted as exactly one argument (pre-existing).** `sprintf(fmt, ...)` accepted exactly 2 arguments, so any 3-argument `sprintf` was a false `NOT_READY`. `fred_load(formula[, ...])`'s own documented 7-argument key/value example was also masked by the prose splice. `...` now means no upper bound (`VARIADIC_MAX_ARGS`) and contributes nothing to the minimum. A mismatch message says "N or more".

   Net effect on the published docs: 131 own-page signatures change. Every change is a max-arity correction toward the documented form (e.g. `plotXY(myPlot, x, y)`, `xlsWrite(data, file, range, sheet, vls)`, `gmmFit(&fct, y, ...[, gCtl])`) or the removal of an arity that only a prose example had supplied. 17 further changes are spurious "signatures" of *other* names that had been read from parameter prose (e.g. `rows(vtyp)` on `create.rst`); validation never uses those, since it takes a symbol's signature from that symbol's own best-match page. 117 pages' Syntax lists change.

3. **System-statement registry gap (user-approved scope addition, 2026-10-08).** With correct signatures, `plotSave("f.png", {800, 600});` (a file write) reached `HANDOFF_CANDIDATE`. It had been `review_required` only because its garbled signature left a role check unknown. Checking that found a pre-existing gap: `x = fred_load("GNPCA");` (a FRED web API call) was **already** `HANDOFF_CANDIDATE` in v0.81.0, contrary to the project rule that code reaching outside GAUSS's memory is always `NOT_READY`.

   On the user's decision ("audit + fold in"), I audited every published page: Purpose and Format text for files, datasets, disk, databases, archives, HDF5, Excel, CSV, web sources and printers, plus the `db*`/`gda*`/`h5*`/`fred_*`/`dbnomics_*` name families. That added **163 doc-verified entries (50 → 213)**:
   - `file_write`: 38 (e.g. `plotSave`, `putf`, `datasave`, `gdaWrite`, `h5write`, `spreadSheetWrite`, `dataloop`, `tempname`, `compile`, `errorlog`);
   - `file_read`: 51 (e.g. `dataload`, `asciiload`, `gdaRead`, `h5read`, `spreadSheetReadM`, `rowsf`, `getnamef`, `fseek`);
   - `source_inclusion`: 2 (`use`, `includedir`);
   - `process_launch`: 1 (`edit`);
   - new `network` category: 4 (`fred_load`, `fred_search`, `dbnomics_search`, `dbnomics_series`);
   - new `database` category: all 67 `db*` functions.

   Every name was checked to appear on its cited page. Deliberately excluded, with reasons in the code comment: `cdir`, `getGAUSSHome`, `getnr`/`getnrmt`, `xlsMakeRange`, `copyMetadata`, `fred_set`/`dbnomics_set` (they only build a parameter map), `new` and `stop`. Matching is still by name, so a variable named after a registered function in statement position (`edit[1] = 2;`) is a false `NOT_READY`, the safe direction. Functions that merely *accept* a dataset filename argument (`ols("mydata", ...)`) are not covered; that is disclosed.

### 11.3 Findings (all minor, safe direction)

1. **Expression-assigned variables are never traced (72.3).** The client's first, idiomatic answer `v = 1 ./ seqa(1, 1, 10); mu = meanc(v);` stays review_required: meanc's role check is unknown because `v` comes from an expression. This is the existing "expressions are never evaluated" limitation, but live it had a visible cost: the client rewrote correct vectorized code into a loop until it reached candidacy. Candidate for a later milestone: category-only inference for elementwise expressions over traced operands.
2. **Misleading reason text for code with no documented calls (72.6, 72.8).** The not_ready verdict is the v0.80.0 policy and correct, but `validate_code` reports it as "generation policy does not permit code generation (block)", which is the `ask()` path's wording; nothing was generated. Only the note gives the real cause. In 72.8 the same policy also fires before the syntax-partial gap, so the designed review_required for an `if` body was not observable. Candidate small fix: report the note's own wording as the reason on `validate_code`.
3. **Variadic arguments never get a documented category (72.15).** `sprintf.rst` names its parameter `:param ....:` (four dots), so the `:type` never attaches to the signature's `...`, and every variadic argument's role is unknown. Candidate fix (needs the CLAUDE.md all-pages diff): treat a `....` parameter as `...`.
4. **`gauss_search_docs` fails a plain question (72.16).** "compute a covariance matrix" returns ungrounded with no sources (the preliminary observation in `PROJECT_STATUS.md`, now reproduced). The client's live answer was right only because it already knew to search for `vcx`. This is worse than 71.5 and stays out of scope (§3.6). Candidate for a later milestone: give search the concept-to-function resolution that `ask()` already has (`resolve_concepts`).
5. **Partial verdicts don't say which check was partial.** Twice (72.3, 72.15) the client's in-conversation explanation of "validation coverage is partial" was a wrong guess (`./`, variadic count), corrected only by post-run diagnosis. The response carries `syntax` but not the role-check gap that actually caused it. Candidate small fix: name the symbol and parameter whose role check stayed unknown.
6. **Readiness is not correctness (72.14).** `meanc` on a row vector is legal GAUSS that returns the wrong thing for "its mean", and it reaches handoff_candidate. This is by design and already disclosed. The client caught it itself.
