# v0.71.0 — Local Ollama Provider & Live Conversational Validation

## 1. Objective

Add first-class local Ollama support behind the existing `ModelProvider` abstraction established in `v0.70.0`, and perform this repository's first genuine, real end-to-end conversational validation: a user question flows through `ConversationEngine`, gets grounded against GAUSS-specific evidence, reaches a real locally running Ollama model, and produces a grounded conversational answer. Not the full conversational code-generation milestone; not a redesign of `ConversationEngine`'s architecture.

## 2. What this milestone is not

Not conversational code generation, not autonomous execution or repair, not multi-file repair, not durable chat storage, not telemetry, not an IDE plugin, not auto-install of Ollama, not a silent model download, not a bundled model, not fine-tuning, not a RAG rewrite, not a general-purpose shell/filesystem tool for the model, not billing. The pipeline `Execution -> Interpretation -> Diagnosis -> Strategy -> Draft -> Application -> Verification -> Review` is untouched, zero diff.

## 3. Repository state at the start of this milestone

`v0.70.0` (Conversational GAUSS Q&A Foundation) was the current released state: a provider-agnostic `ModelProvider` abstraction, `ConversationEngine`, `FakeModelProvider`, `AnthropicMessagesProvider` (unit-tested only, never network-tested — no API key available), documentation/catalog grounding, an execution boundary, and process-local conversation state. Six alpha findings from manual `v0.70.0` testing motivated this milestone (see the Changelog/`KNOWN_LIMITATIONS.md` entries for this version for the full list): chat not recognizing `gauss-ai doctor` typed at its own prompt, unhelpful `config --help`, an unclear real-provider setup path, unset `docs-root`, a real `gauss-ai init` regression silently wiping chat settings on re-run, and a workspace-parent prompt accepting a CLI-command-shaped string as a path.

## 4. Architecture

```
gauss_ai_chat.py              -- CLI loop: banner/status (now generic per provider), prompt,
        |                        help/reset/exit, gauss-ai-command interception, formatting
gauss_conversation_engine.py  -- ConversationEngine (unchanged design; _EXECUTION_KEYWORDS
        |    |                    extended -- see Section 8)
        |    +-- gauss_error_catalog.lookup_error(...)      (reused, zero duplication)
        |    +-- command_doc_lookup.lookup(...)             (reused, zero duplication)
        |
gauss_chat_provider.py        -- ModelProvider protocol + ProviderResult
        +-- FakeModelProvider          -- deterministic, unchanged
        +-- AnthropicMessagesProvider  -- unchanged
        +-- OllamaProvider (NEW)       -- stdlib urllib only; POST /api/chat, no API-key field
        +-- check_ollama_service(...)  (NEW) -- read-only GET /api/tags, shared by doctor/init
        +-- ollama_model_matches(...)  (NEW) -- bounded name-matching, no fuzzy matching
```

Provider-specific request/response shapes never leak past `gauss_chat_provider.py`; `ConversationEngine` and the CLI only ever see `ChatMessage`/`ProviderResult`, exactly as in `v0.70.0`.

## 5. Ollama provider design

Verified against the current, authoritative Ollama API documentation before implementation (`https://docs.ollama.com/api/chat`, `https://docs.ollama.com/api/errors`, `https://github.com/ollama/ollama/blob/main/docs/api.md`) — never guessed. `POST /api/chat` with `{"model", "messages": [{"role","content"}...], "stream": false, "options": {"num_predict": max_tokens}}`; response `{"message": {"role","content"}, "model", "done", ...}`. Errors are a flat `{"error": "<string>"}` shape, unlike Anthropic's nested error object — `_extract_ollama_error(...)` handles this distinctly. A new `ProviderErrorKind.MODEL_UNAVAILABLE` is raised specifically when the error string contains a "not found"-shaped message, giving an exact `ollama pull <model>` remedy instead of a generic HTTP error. `OllamaProvider` has **no API-key-shaped field of any kind** — proven structurally by a test enumerating its dataclass fields (`{"model", "endpoint", "transport"}`) — since local Ollama requires no authentication. Default endpoint `http://localhost:11434`; default model `qwen2.5-coder:7b` (see `docs/ollama-models.md`).

`check_ollama_service(...)` and `ollama_model_matches(...)` are separate, explicitly read-only helpers: `check_ollama_service` calls only `GET /api/tags`, structurally proven (by test) never to call `/api/chat` or `/api/pull` — it can never trigger generation or a model download. Shared identically by `gauss-ai doctor` and `gauss-ai init`.

## 6. Configuration

New setting `ollama_endpoint` (config key `ollama-endpoint`, env var `GAUSS_AI_OLLAMA_ENDPOINT`, CLI flag `--ollama-endpoint`), following the exact same CLI > env > config-file > default precedence as every existing setting, with no default asserted at the config layer (the provider applies its own documented default), mirroring `resolve_chat_model`'s convention. `VALID_CHAT_PROVIDERS` extended to `("fake", "anthropic", "ollama")`.

## 7. CLI and setup UX fixes (addressing the six alpha findings)

- **`gauss-ai config --help` / bare `gauss-ai config`**: now print a full reference (every config key, a provider comparison table, a grounding pointer) instead of an error or a bare one-line usage string.
- **Doctor**: two new, conditional, read-only checks (`ollama_service`, `ollama_model`), only run when `chat-provider` resolves to `ollama` — never fails installation just because Ollama is absent when it isn't selected, never a PASS merely because a string exists (an unreachable service or a missing model is an honest FAIL with a concrete next step, never an automatic pull). Doctor's own module docstring now honestly documents this one narrow, explicit, local-loopback-only exception to its previous "never accesses the network" claim.
- **Chat startup status**: generalized from the `v0.70.0` fake-provider-only notice to report provider/model/endpoint (for Ollama) and documentation-grounding status for any provider, never claiming grounding is configured when `docs-root` is unset.
- **Shell-command interception in chat**: `gauss-ai <subcommand>`-shaped input (e.g. `gauss-ai doctor` typed at the chat prompt) is now deterministically recognized via `gauss_ai_config.looks_like_cli_invocation(...)` and redirected to "exit and run it in your terminal" — never executed, never sent to the model.
- **`gauss-ai init`**: fixed a real regression where every re-run silently wiped `chat_provider`/`chat_model`/`docs_root`/`ollama_endpoint` back to unset (the final config-construction step never carried them forward); added a new interactive conversational-provider selection step with a read-only Ollama reachability check (no auto-install/auto-download); added a `looks_like_cli_invocation` guard on the workspace-parent prompt, directly addressing the alpha finding where the literal string `gauss-ai doctor` was accepted as a workspace-parent path.
- **Update workflow documented**: `docs/alpha-installation.md` now documents `git pull origin main` → `pip install -e .` → `gauss-ai version` → `gauss-ai doctor` as the expected update sequence, and corrects a previously inaccurate claim that nothing ever needs reinstalling after a pull.

## 8. Live validation

**REAL OLLAMA MODEL VALIDATED.** Ollama was installed on the actual development machine (`OllamaSetup.exe /VERYSILENT /NORESTART`, no admin rights required) after explicit user confirmation, and `qwen2.5-coder:7b` was pulled. `pip install -e .` was rerun to point the installed `gauss-ai` command at this repository's own working checkout (it had been pointing at a separate `gauss-ai-alphatesting` clone — itself a live demonstration of the update-workflow issue this milestone documents). `gauss-ai doctor` confirmed `[PASS] ollama_service` and `[PASS] ollama_model` against the real service before any conversational scenario was run.

Ten scenarios (Prompt IDs `61.1`-`61.10`) were then run end to end through the installed `gauss-ai` CLI against the real model and a real local GAUSS documentation checkout, each captured as a real transcript in `evaluations/runs/2026-09-08-code-assistant-local-ollama-provider-run-*.md`:

1. Documentation-grounded question (`reshape`) — real, genuinely synthesized answer, correctly disclosed as documentation-grounded.
2. Catalog-grounded question (`G0036`) — correctly disclosed as catalog-grounded.
3. Multi-turn follow-up ("give me a short example") — `last_topic` context retention confirmed with a real provider.
4. Conceptual comparison question (matrix vs. scalar) — honestly disclosed as ungrounded despite fluent real-model prose; a genuine grounding-coverage gap was found and disclosed (not fixed — see Section 12).
5. Off-topic question (capital of France) — honestly disclosed as ungrounded, answered directly and correctly.
6. Execution-trigger request ("run this code") — instant fixed redirect, real model never invoked (confirmed by latency contrast against every genuinely-answered scenario).
7. Repair-intent phrasing ("fix my file ... apply the change") — **found live to reach the real model instead of being redirected**, a real defect in execution-keyword coverage; fixed within this same milestone (`_EXECUTION_KEYWORDS` extended) and re-verified live against the same model and session.
8. `gauss-ai doctor` typed into chat — instantly intercepted, never reached the model.
9. Provider-unavailable (wrong endpoint) — honest, specific `NETWORK` error naming the endpoint, no silent fallback.
10. Model-unavailable (unpulled model name) — honest `MODEL_UNAVAILABLE` error with the exact `ollama pull` remedy from both chat and `gauss-ai doctor` independently.

This is genuine real-LLM validation, not `FakeModelProvider` architecture testing — the distinction `v0.70.0` could not make.

## 9. Grounding validation

Real documentation grounding (the same real local GAUSS documentation checkout used in `v0.70.0`'s own development) was genuinely exercised against a real model, not just a deterministic template — confirmed by the model producing fluent, correct, but non-verbatim prose describing real `reshape.rst` and catalog content (scenarios 1-3 above). One genuine limitation was found and disclosed, not fixed: a multi-topic conceptual comparison question does not resolve to the single documentation-lookup token the current retrieval design expects, so it is honestly left ungrounded even though a real model could answer it fluently (scenario 4). This is a grounding-*coverage* gap, not a disclosure-*honesty* failure — the system did not fabricate grounding it didn't have.

## 10. Safety validation

`OllamaProvider` cannot execute GAUSS code (**NO** — no import of any execution module), cannot modify any file (**NO** — no `open(`/file-write call anywhere in its source), cannot approve anything (**NO** — no import of any approval/gate module), cannot apply a repair (**NO** — no import of any repair-application module), and cannot bypass any existing confirmation/verification/provenance mechanism (**NO** — its only public method is `complete`, structurally proven; it has no path back into the pipeline at all). These are structural guarantees (import-scanning and dataclass/method-enumeration tests), not merely conventions, and were re-confirmed for the new Ollama code paths specifically (`test_57`, `test_58` in `test_gauss_chat_provider.py`), in addition to the pre-existing whole-module import-scanning test that already covered them. The one real defect found during live validation (Section 8, scenario 7) was a routing/interception gap, not a safety-boundary breach: at no point could the model have executed or applied anything, regardless of which branch handled the question.

## 11. Testing

46 new deterministic, network-free tests were added: `test_gauss_chat_provider.py` (+24, including two dedicated to this milestone's safety validation), `test_gauss_ai_config.py` (+5), `test_gauss_ai_doctor.py` (+6), `test_gauss_ai_chat.py` (+6), `test_gauss_ai_init.py` (+5), `test_gauss_conversation_engine.py` (+1, covering the live-discovered repair-intent gap), and `test_gauss_ai_cli.py` (+5). The full existing regression suite (40 files) passes; zero diff on every core execution/repair/verification/approval module. No test in the automated suite requires a running Ollama service — every `OllamaProvider`/`check_ollama_service` test uses an injected fake `transport`, exactly like `AnthropicMessagesProvider`'s own convention. Live-service validation (Section 8) is a separate, explicitly-labeled manual procedure, never conflated with the deterministic suite.

## 12. Remaining limitations (not fixed in this milestone)

- **Grounding-coverage gap for multi-topic conceptual questions** (Section 9) — a known, disclosed limitation of the current single-token documentation-lookup design, not specific to Ollama. A genuine fix needs real intent parsing across multiple candidate tokens, deferred to a future milestone.
- **Anthropic provider still not live-network-tested** — no API key is available in this development environment; unchanged from `v0.70.0`, stated again explicitly rather than silently carried forward.
- Every item in Section 2 ("What this milestone is not") remains not implemented, by design.

## 13. Recommendation

All planned phases for this milestone are complete: architecture review, Ollama provider design and implementation, configuration, CLI/setup UX fixes for all six alpha findings, live validation (ten real scenarios, one real defect found and fixed), comprehensive automated testing, a new evaluation category, and documentation updates. **Do not begin the next milestone automatically** — this report, and the user's own review of the live-validation evidence in `evaluations/runs/2026-09-08-code-assistant-local-ollama-provider-run-*.md`, should inform what comes next (the milestone's own explicit scope exclusions in Section 2 are a reasonable starting menu, but the choice belongs to the user).
