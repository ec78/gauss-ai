# v0.62.0 - Bounded Single-File Repair Application Transaction

## Release Goal

Implement Section 14 (Application Transaction) of `planning/v0.58.0-repair-application-safety-design.md` under a deliberately conservative bound: exactly one existing UTF-8 `.gss` file, in exactly one workspace, for exactly one already-approved `RepairDraft` that has passed strategy approval, draft approval, application approval, and a freshly re-evaluated Application Gate. This is the first module in this repository's history capable of writing to a real file.

Clean working tree. `scripts/gauss_repair_planner.py`, `scripts/gauss_repair_approval.py`, `scripts/gauss_repair_draft.py`, `scripts/gauss_repair_draft_approval.py`, `scripts/gauss_repair_application_approval.py`, and `scripts/gauss_repair_application_gate.py` unmodified throughout this milestone.

## Architecture

```
apply_repair(..., replacement_text, workspace_registry) -> ApplicationResult
    1. read_workspace_file(...)              re-validate source identity (real, hash-verified read)
    2. evaluate_application_gate(...)         re-evaluate every approval-chain precondition
    3. resolve backup path, write, hash       create workspace-contained backup, before any target write
    4. construct candidate (in-memory only)   bounded line-range text substitution
    5. validate candidate                     non-empty, changed, size ceiling, no NUL bytes, line bound
    6. write temp file (target's own directory)
    7. os.replace(temp, target)               atomic swap; fails closed, never falls back to unsafe overwrite
    8. re-read + verify post-write hash
    9. return immutable ApplicationResult
    10. stop -- no rerun triggered anywhere
```

`scripts/gauss_repair_application.py` reuses, rather than re-derives, every precedent available: `gauss_workspace_file_reader.read_workspace_file(...)` is the one real, verified, hash-computing read path in this repository (extension allowlist, binary sniff, size ceiling, UTF-8-strict); `gauss_workspace.WorkspaceRegistry.resolve_within_workspace(...)` is the one path-containment check (symlink-following via `Path.resolve()`, traversal-rejecting); `gauss_repair_application_gate.evaluate_application_gate(...)` is called fresh, at the last possible moment before any write, re-verifying the entire four-record approval chain and structural draft validation in one call rather than re-deriving any of it. This module imports no execution/orchestration module, and never launches GAUSS or triggers a rerun.

## No Content Is Generated

Every repair-layer module through `v0.61.0` was deliberately incapable of carrying literal replacement code — `EditScope` describes only a bounded location and a short intent, never content. This module is the one place literal content is finally needed, and it is supplied **explicitly by the caller** (`replacement_text`) — never inferred, generated, or reconstructed. This module does not validate GAUSS syntax or semantic correctness; it validates only that the resulting substitution is well-formed, bounded, UTF-8 text.

## Fail-Closed Design

Every check is evaluated in order; the first failure halts the transaction immediately and no subsequent step runs. `ApplicationResult.checks` therefore contains only the checks actually reached — its length varies by how far the transaction got, and this is itself meaningful, tested behavior (`test_19_checks_list_stops_at_first_failure`). Two outcome categories exist below `applied`:

- **`blocked`** — a precondition failed before any write was attempted. The target file byte-for-byte unchanged in every blocked scenario (verified directly, `test_18`). A backup may or may not exist, depending on how far the transaction reached — backup creation happens *before* candidate construction/validation per this milestone's own specified step order, so a candidate-validation block still leaves a (harmless, never-deleted) backup behind.
- **`failed`** — a write was attempted (a temporary file was created) but did not reach a verified, successful state: the temp write itself failed, the atomic replace failed, or the post-write hash didn't match the constructed candidate. The backup is the recovery path in every case; no automatic rollback is attempted.

## Backup Model

Exactly one backup per attempt, named `<relative_path>.prerepair-<hash_prefix>-<timestamp>.bak`, written as a sibling of the target inside the same workspace directory (no new directory is ever created). If a file already occupies the computed name, a numeric suffix is appended and retried (up to 999 attempts) — a backup is **never** overwritten. The backup's own content hash is computed and verified immediately after writing; a verification mismatch blocks before any target write. Backups are never deleted by this module, including when a transaction subsequently blocks or fails.

## Atomic Replace, Not Best-Effort

`os.replace(temp_path, target_path)` is the one, sole replace path — atomic on both POSIX and Windows when the temp file lives in the target's own directory (a hard precondition this module enforces by construction, never optional). If it raises `OSError`, the transaction reports `failed`, the orphaned temp file is removed, and the target is left exactly as it was (an atomic replace either fully succeeds or doesn't happen at all — there is no partial-replace state to clean up on the target side). `replace_fn` and `write_temp_file_fn` are injectable, mirroring `WorkspaceRegistry`'s own `clock`/`id_factory` constructor-injection convention, so atomic-replace and temp-write failures are deterministically testable without relying on flaky OS-level failure conditions.

## ApplicationResult

Immutable, frozen. Carries `application_id`, `draft_digest`, `workspace_id`, `relative_path`, `pre_application_content_hash`, `post_application_content_hash` (`None` unless `applied`), `backup` (a `BackupIdentity` or `None`), `outcome`, `reason`, the full `checks` tuple, `applied_at`, and a fixed `application_boundary` disclosure (one of three fixed strings, one per outcome category — never dynamically composed per specific reason). No rerun field of any kind exists on this type.

## CLI

`apply-repair <draft_digest> --replacement-text TEXT` mirrors every prior layer's stale-digest-rejection convention exactly. `show-application-result` displays the adapter's own `last_application_result`. Every response discloses `file_modified`, `backup_created`, and `rerun_performed: false` explicitly, plus a `next_step` line stating that a separate, explicit rerun confirmation (the ordinary `request`/`plan`/`confirm`/`execute` path) is required before executing the repaired code — this command never triggers one. `reset` clears `last_application_result`.

## Out of Scope (unchanged from the authorizing task)

Multiple files, new files, renames, deletes, directory creation, whole-file replacement, binary files, non-UTF-8 content, patch merging, diff fuzzing, AST rewriting, cloud storage, durable sessions, automatic reruns, automatic rollback, automatic retries, an `apply-repair`-triggered rerun of any kind.

## Recommendation for the Next Milestone

With a bounded, tested, single-file transaction now in place, the natural next candidate is Section 20's separately-scoped rerun workflow — wiring an applied repair's resulting code identity into a fresh, ordinary execution request through the existing `request`/`plan`/`confirm`/`execute` path, explicitly not a repair-specific execution shortcut. This milestone deliberately does not request or imply that authorization.
