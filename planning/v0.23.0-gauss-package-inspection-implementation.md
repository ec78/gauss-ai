# v0.23.0 - GAUSS Package Inspection Implementation

## Release Goal

`v0.23.0` implements the read-only GAUSS package inspection helper based on the `v0.22.0` package-inspection contract (`tools/gauss_package_inspection.md`, `schemas/gauss_package_inspection.schema.json`).

The goal is to implement a helper that can:

- Consume environment-detection output from `scripts/gauss_environment_check.py`.
- Inspect the selected GAUSS version context.
- Identify package/application-module candidates where possible.
- Report requested package status as installed, missing, unknown, unavailable, or partial.
- Return schema-valid output matching `schemas/gauss_package_inspection.schema.json`.
- Preserve Advisory Mode fallback.
- Remain read-only and conservative.

`v0.23.0` should **not**:

- Run user GAUSS code.
- Execute statistical analysis.
- Install packages.
- Activate Execution Mode.
- Implement runtime orchestration.
- Generate reports from execution output.

## Version-Specific Package Context Rule

Package inspection must use the selected GAUSS environment from environment detection.

**Rules:**

- If environment detection selected GAUSS 26, inspect the GAUSS 26 package context by default.
- If the user selected GAUSS 25, inspect the GAUSS 25 package context.
- If the user provided an explicit executable path, inspect the package context associated with that executable path.
- Do not mix package results across GAUSS versions unless explicitly requested.
- Package availability may differ by GAUSS version.
- The selected GAUSS version and executable path should be reported in the package-inspection output.

Important:

- If the environment result is not `found`, package inspection should return unavailable, unknown, or advisory fallback.
- If the package context cannot be determined from the selected executable, do not guess with false certainty.
- Prefer `unknown` or `partial` over overclaiming.

This rule extends `v0.21.0`'s newest-version default rule to a second capability: environment detection already established which GAUSS version to treat as "selected" by default; package inspection inherits that selection rather than re-deciding it.

## Relationship to Environment Detection

The package inspection helper should accept one or more of:

- An environment check result JSON object.
- A path to an environment check result JSON file.
- A direct executable path.
- A direct GAUSS version.
- A platform hint.

If no environment result is provided:

- It may call or reuse `detect_environment(...)` from `scripts/gauss_environment_check.py`.
- Or it may return `unavailable` if strict mode requires explicit environment context.

Clarify:

- Environment detection `found` does not mean packages are installed.
- Environment detection version known does not mean package availability is known.
- Environment detection `execution_candidate` does not activate Execution Mode.
- Package inspection remains separate from execution.

## Package Discovery Strategy

### Requested-package first

If `requested_packages` are provided:

- Inspect those names first.
- Return one package object per requested package.
- Classify each as `true`, `false`, or `"unknown"`.
- Populate `missing_packages` and `unknown_packages` accurately.
- Do not treat unknown as missing.

### Filesystem-based inspection

Use read-only filesystem inspection where possible.

Potential locations to investigate:

- Directories near the selected GAUSS executable.
- Version-specific GAUSS installation directories.
- Application-module directories.
- Package/library directories.
- User-provided `package_search_paths`.
- Configuration/library path hints, if safely readable.

Important:

- Do not assume exact GAUSS package paths without verification.
- Use conservative heuristics.
- Keep path exposure privacy-conscious.
- Prefer `partial` or `unknown` when only some paths can be inspected.

### Package name matching

Matching rules:

- Normalize case.
- Normalize simple separators such as hyphen, underscore, and spaces.
- Allow common aliases only when documented in code comments or a mapping table.
- Do not infer unrelated packages from vague names.
- Keep matching conservative.
- Record source and notes for each package result.

Examples:

- `tsmt` might correspond to a TSMT/time-series module only if verified by filesystem evidence or explicit mapping.
- `tscsfit` should not automatically imply all TSMT functionality unless verified — `tscsFit` is one command within TSMT, not a synonym for the whole package.
- Package docs names and installation names may differ, so mappings should be explicit and conservative.

### Base vs package distinction

The helper may include `package_type: base` only when a result is explicitly about a base capability.

But:

- Base command availability should still rely on command evidence, not package inspection alone.
- Package inspection should not become a command documentation resolver.

### Metadata query

Defer actual GAUSS metadata invocation unless a safe metadata-only command is confirmed.

If implemented later:

- Require explicit `allow_metadata_query`.
- Use a timeout.
- Do not run user code.
- Report that GAUSS was invoked for metadata only.
- Do not mutate files or state.

For `v0.23.0`, prefer filesystem and synthetic/self-testable behavior first — the same discipline `v0.21.0` applied to `--allow-version-query`, which was accepted into the input contract but deliberately left as a documented no-op until a safe flag is confirmed.

**Function:** `inspect_packages(...)`

**Potential parameters:**

- `environment_check_result=None`
- `executable_path=None`
- `gauss_version=None`
- `platform_hint=None`
- `requested_packages=None`
- `package_search_paths=None`
- `allow_metadata_query=False`

- `strict=False`

**Return:** a dictionary conforming to `schemas/gauss_package_inspection.schema.json`.

This mirrors `v0.21.0`'s `detect_environment(...)` design — a plain-dict return, keyword arguments matching the input contract, and dependency-injection-friendly internals so a future self-test suite can exercise it without a real GAUSS installation.

## Output Mapping Requirements

Every result must conform to `schemas/gauss_package_inspection.schema.json`.

Implementation must populate: `checked`, `environment_status`, `executable_path`, `gauss_version`, `package_inspection_status`, `packages`, `requested_packages`, `missing_packages`, `unknown_packages`, `package_search_paths`, `inspection_method`, `operating_mode_recommendation`, `can_assume_package_availability`, `warnings`, `errors`, `next_steps`.

Guidance:

- `package_inspection_status` should be `complete` only when the requested scope was inspected enough to classify packages.
- `partial` should include warnings.
- `unavailable` should recommend advisory mode.
- `error` should include errors.
- `can_assume_package_availability: true` should only be used when all requested packages appear installed and inspection confidence is sufficient.
- `missing_packages` must never coexist with `can_assume_package_availability: true`.
- `installed: true` does not mean code ran.
- `installed: "unknown"` is not missing.

These mapping rules are already encoded as hard constraints in `schemas/gauss_package_inspection.schema.json`'s `allOf`/`if`/`then` blocks — the implementation must satisfy them, not just describe them.

## Fallback Requirements

- If the environment is not found, package inspection returns unavailable/advisory.
- If the environment is ambiguous, return unavailable/advisory unless the user chooses a specific environment.
- If the environment is inaccessible, return unavailable/advisory.
- If package search paths are inaccessible, return `partial` or `unknown`, not a crash.
- If a requested package cannot be determined, return `installed: "unknown"`.
- If no requested packages are provided and no packages can be listed, return `unknown` or `partial` conservatively.
- The assistant can still provide advisory guidance without package inspection.

- No user GAUSS code execution.
- No analysis execution.
- No package installation.
- No license activation.
- No environment mutation.
- No file modification.
- No deletion.
- No hidden GAUSS invocation.

- Structured errors.
- Path exposure minimized where possible.

## Testing Strategy

Synthetic tests for:

- Environment not found → unavailable/advisory.
- Environment found but no package paths → unknown/partial.
- Requested package found.
- Requested package missing.
- Requested package unknown.
- Partial inspection with an inaccessible search path.
- Selected GAUSS 26 context inspected by default.
- User-selected GAUSS 25 context carried through.
- No cross-version mixing.
- Missing package does not imply GAUSS missing.
- Installed package does not imply execution.
- Schema validation passes.
- Metadata query flag accepted but does not invoke GAUSS if no safe query exists.

Use synthetic directories/fixtures where possible. Do not require a real GAUSS installation for tests. If a real GAUSS installation is available, manual verification can be noted separately but should not be required — the same split `v0.21.0` used (a built-in `--self-test` suite with injected fixtures, plus separate manual verification against this development machine's real GAUSS 24/25/26 installations).
