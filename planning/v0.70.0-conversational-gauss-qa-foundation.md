# v0.70.0 — Conversational GAUSS Q&A Foundation

## Objective

Begin the transition from a guided GAUSS repair CLI toward a conversational GAUSS coding agent by implementing the first genuine conversational capability: general GAUSS Q&A with multi-turn follow-up context. Not a redesign of the repair pipeline; not execution routing; not code generation.

## Pre-implementation verification

`HEAD` confirmed at `fbb9532` on `main`, matching the v0.69.0 handoff exactly; working tree clean; `origin/main` in sync. No discrepancy found. See the pre-implementation report delivered in-conversation for the full verification, architecture survey, and reuse analysis.

## What this milestone is not

Not conversational execution routing, not conversational code generation/repair, not a durable session store, not multi-provider support, not a redesign of any existing safety layer. The pipeline `Execution -> Interpretation -> Diagnosis -> Strategy -> Draft -> Application -> Verification -> Review` is untouched, zero diff.

## Architecture

```
gauss_ai_chat.py              -- CLI loop only: banner, prompt, help/reset/exit, formatting
        |
gauss_conversation_engine.py  -- ConversationEngine: bounded history, grounding lookup,
        |    |                    execution-intent boundary message, code-disclaimer footer
        |    +-- gauss_error_catalog.lookup_error(...)      (reused, zero duplication)
        |    +-- command_doc_lookup.lookup(...)             (reused, zero duplication)
        |
gauss_chat_provider.py        -- ModelProvider protocol + ProviderResult (frozen dataclass)
        +-- FakeModelProvider          -- deterministic, template-driven off real grounding
        +-- AnthropicMessagesProvider  -- stdlib `urllib.request` only, no new dependency;
                                          API key read fresh from `ANTHROPIC_API_KEY` at
                                          call time, never stored on the instance or config
```

Provider-specific request/response shapes never leak past `gauss_chat_provider.py`; the engine and CLI only ever see `ChatMessage`/`ProviderResult`.

## Grounding

Two structured, deterministic sources are consulted before any model call:

1. **Error catalog** — a `G####` token in the question is looked up via `gauss_error_catalog.lookup_error(...)` directly; no new catalog, no duplication.
2. **Local official documentation** — when `docs_root` is configured (new `gauss-ai config set docs-root <path>` setting, same CLI>env>config>default precedence every other setting uses) and exists, question tokens are checked against real `.rst` filename stems under that root, and a match is looked up via `command_doc_lookup.lookup(...)`. No docs are bundled with this repository; grounding is only as available as the tester's own local checkout.

If neither source produces a hit, the answer is honestly disclosed as model-generated, not documentation-grounded. `docs_root` is genuinely configured and populated on this development machine (a real local GAUSS documentation checkout, gitignored via `configs/knowledge_sources.local`), so real retrieval was exercised during development — this will not be true on a fresh tester machine unless they configure their own `docs_root`.

## Model provider

`ModelProvider` is a two-method-surface protocol (`complete(messages) -> ProviderResult`). `FakeModelProvider` is fully deterministic (no randomness, no network) and is the default provider (`chat_provider` defaults to `"fake"`, mirroring `default_runner`'s own `"fake"`-is-the-safe-default precedent) so the entire conversational system is testable and usable without network access or API charges.

`AnthropicMessagesProvider` is implemented as the one real provider, using only `urllib.request` (stdlib) to avoid introducing this repository's first-ever third-party runtime dependency. **No live network round trip against the real Anthropic API was performed during this milestone's own development or testing**: this sandboxed environment has no `ANTHROPIC_API_KEY` configured. The adapter's own logic (auth header construction, request-body shape, response parsing, HTTP-error handling, missing-credential handling) is fully unit-tested via an injected fake transport callable — real, executed tests of real code, just not a genuine network call. This is stated here explicitly rather than fabricated, per this milestone's own explicit instruction.

## Conversation state

Process-local only, cleared on `reset`/`new` or process exit — no database, no file, no cross-process sharing. Bounded to `MAX_HISTORY_TURNS = 20` (10 exchanges); oldest turns drop first. A `last_topic` field (the most recently detected command name or error code) lets the deterministic fake provider and the grounding lookup resolve simple pronoun references ("that", "it") in follow-up questions without requiring real model comprehension — real providers get the same context for free via the full transcript passed in `messages`.

## Execution and code-generation boundary

`gauss_conversation_engine.py` and `gauss_chat_provider.py` import nothing from `gauss_execution_workflow`, `gauss_repair_application*`, `gauss_repair_draft*`, `gauss_repair_application_approval`, `gauss_repair_application_gate`, or `gauss_verification_*` — verified structurally by a dedicated architectural test, not merely by convention. A bounded heuristic detects an execution-imperative question ("run this", "execute that") and returns a fixed, honest redirect to `gauss-ai repair <file.gss>` without ever calling the model for that turn. Any answer text that looks code-shaped (a triple-backtick fence, or GAUSS-statement-shaped lines) always receives a fixed, non-model-dependent "this example has not been executed in this conversation" footer, appended by the rendering layer -- never left to the model to remember.

## CLI UX

`gauss-ai` (bare, no subcommand) now launches conversational mode -- the new, preferred entry point. The prior bare-invocation behavior (the full command-by-command workflow REPL) is preserved, unchanged, behind a new explicit subcommand, `gauss-ai repl`, so nothing that worked before v0.70.0 is removed; it is relocated behind an explicit, discoverable name. `gauss-ai doctor`/`init`/`config`/`repair` are completely unaffected. `python scripts/gauss_code_assistant_cli.py` continues to work exactly as before, unaffected by anything in this milestone.

## Alpha feedback status

The first alpha-feedback cycle (five findings, addressed in `v0.69.0`) is complete and shipped. This is stated as "addressed in implementation and verified through v0.69.0's own real-GAUSS and installed-CLI evaluation," not as "all UX is now permanently solved" -- future alpha sessions may surface further feedback on the new AI-drafting UX, exactly as v0.68.0 surfaced feedback that became v0.69.0's own scope.

## Not implemented

Conversational execution routing, conversational code generation/repair/application, multi-provider support, durable conversation history, multi-user sessions, a second real LLM provider, loading the full `experts/gauss-language/` corpus into the system prompt (a reasonable future extension, deliberately deferred to keep this milestone's system prompt small and bounded).
