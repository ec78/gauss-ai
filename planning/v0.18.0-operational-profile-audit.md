## Expert-by-Expert Findings

### GAUSS Language Expert

- **Structure consistency:** Matches the shape used by all later profiles (Purpose, Interface Summary, Expert Scope, Activation Triggers, Non-Activation Cases, Required Inputs, Optional Inputs, Required Evidence, Decision Rules, Refusal Conditions, Escalation Conditions, Output Contract, Response Visibility, Evaluation Criteria, Relationship to Existing Files).
- **`expert_id`/`expert_name`:** Present and correctly formatted (`gauss-language-expert` / "GAUSS Language Expert").
- **Ownership/non-ownership clarity:** Clear — owns GAUSS syntax, procedures/APIs, native command selection, base/package distinction, data structures, debugging patterns, cross-language contamination risk, and command evidence requirements; explicitly does not own econometric methodology, project management, release tracking, generic documentation style, or non-GAUSS programming.
- **Escalation clarity:** Was incomplete — escalated to Econometrics, Software Engineering, and Documentation/Education, but never to the Product Expert. **Fixed**: added a Product Expert escalation bullet ("Route to the Product Expert when the central issue is user value, adoption, positioning, or prioritization rather than GAUSS correctness").
- **Related-file references:** Was incomplete — this profile is the oldest in the system (`v0.8.0`) and predates multi-expert routing (`v0.9.0`); its `related_files` YAML list and prose "Relationship to Existing Files" section never referenced `workflows/expert-routing.md` or `workflows/code-assistant-response.md` at all, even though both of those files explicitly reference this profile in the other direction. **Fixed**: added both files to the YAML `related_files` list and added two corresponding prose bullets describing the current six-expert routing state.
- **Stale wording:** The Purpose paragraph never mentioned that multi-expert routing exists at all (accurate for `v0.8.0`, stale for six operational experts). **Fixed**: added one sentence noting this expert was the first of what is now a six-expert system, with a pointer to `workflows/expert-routing.md`.
- **Runtime disclaimer:** Present in substance (states no engine parses/executes the file) but did not previously address multi-expert orchestration specifically. **Fixed** by the same sentence above.
- **Issues found:** Missing Product Expert escalation; missing routing-workflow related-file references; Purpose section silent on multi-expert routing; Evaluation Criteria section used stale "reused for future benchmark category 15.x" language even though `15.x` was run and passed years of milestones ago (in evaluation-history terms — this repository's `v0.8.0`/`v0.9.0` era).
- **Remediation:** All four issues fixed directly in `experts/gauss-language/OPERATIONAL_PROFILE.md` (Purpose sentence, `related_files` YAML entries, Escalation Conditions bullet, Relationship to Existing Files bullets, Evaluation Criteria intro rewording to past tense).

## Recommended Maintenance Practice

- Run this audit whenever a new expert is added, renamed, operationalized, or retired.
- Search for stale phrases:
  - "future Expert"
  - "once operationalized"
  - "not yet operationalized"
  - "narrative-only"
  - "placeholder"
  - "three-expert routing"
  - "four-expert routing"
  - "five-expert routing"
  - "six-expert routing" (if the expert count changes later)
  - "not yet run"
  - "pending integration"
  - "other N operational experts'" (the specific number, cross-checked against the current total minus one)
  - "planned as" / "future benchmark category" (cross-checked against whether that benchmark category has actually been run)
- Compare each `OPERATIONAL_PROFILE.md` against:
  - `experts/EXPERT_REGISTRY.md`
  - `experts/EXPERT_BOUNDARY_MATRIX.md`
  - `workflows/expert-routing.md`
  - `workflows/expert-routing-cheatsheet.md`
  - `workflows/code-assistant-response.md`
  - `prompts/code_assistant_system.md`
  - `agents/code-assistant/task_modes.md`
- Avoid broad rewrites unless a concrete inconsistency exists.
- Document any profile changes in the audit file and `CHANGELOG.md`.
- **New lesson from this audit, worth carrying forward explicitly:** when a prior task's own remediation note claims "N entries were fixed," verify the actual count against the file rather than trusting the note — this audit found that Education's profile had a remediation note claiming "two `Relationship to Existing Files` entries" were fixed during the Product Expert integration task, when in fact five such entries existed and only one (the `workflows/expert-routing.md` entry) had actually been updated. Recording an accurate count, or re-grepping to confirm, would have caught this earlier.
