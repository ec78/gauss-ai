# v0.22.0 Readiness Checklist

## Release Goal

`v0.22.0` defines the second read-only GAUSS tooling capability area: package inspection.

`v0.22.0`:

- Creates the `gauss_package_inspection` tool specification.
- Creates the result schema.
- Creates validated synthetic example outputs.
- Adds and evaluates `27.x` response-behavior benchmarks.
- Documents package-status uncertainty handling.
- Preserves Advisory Mode fallback.
- Explicitly separates package availability from syntax, methodology, execution, and product-value claims.

`v0.22.0` does **not**:

- Implement actual package inspection.
- Inspect installed packages.
- Run GAUSS code.
- Execute statistical analysis.
- Generate reports from actual output.
- Activate Execution Mode.
- Implement runtime orchestration.

## Scope Decision

`v0.22.0` is the Package Inspection Tool specification/evaluation milestone.

Implementation is deferred to:

**`v0.23.0` - GAUSS Package Inspection Implementation**

**Reason:** package-inspection implementation depends on unresolved details about real GAUSS package/application-module locations, version-specific package contexts, licensing, and whether metadata-only package inspection can be done safely. Following the same precedent already established for environment detection (`v0.20.0` specification / `v0.21.0` implementation), package inspection is split the same way rather than bundling unresolved implementation risk into a specification milestone.

### Result Schema

**Path:** `schemas/gauss_package_inspection.schema.json`

**Purpose:** Validates structured output for the future package inspection tool.

- Draft 2020-12.
- Sixteen required top-level fields plus one optional (`raw_inspection_details`).
- `environment_status` enum, aligned with `gauss_environment_check.schema.json`'s `detection_status`.
- `package_inspection_status` enum: `complete`, `partial`, `unavailable`, `error`, `unknown`.
- `operating_mode_recommendation` enum: `advisory`, `verified_knowledge`, `execution_candidate`.
- A fully-specified package object schema (`name`, `installed`, `version`, `version_known`, `source`, `path`, `package_type`, `notes`).
- Tri-state (`true`/`false`/`"unknown"`) fields: `installed` (per package), `can_assume_package_availability`.
- `allOf`/`if`/`then` package-status consistency constraints (e.g., `complete` requires `checked: true` and zero `errors`; a non-`found` `environment_status` forbids `complete` status and forbids `execution_candidate` mode; non-empty `missing_packages` forbids `can_assume_package_availability: true`).

## Relationship to v0.21.0 Environment Detection

- `v0.21.0` implemented environment detection.
- `v0.22.0` specifies package inspection.
- Package inspection should use the selected GAUSS environment from environment detection.
- If environment detection selects GAUSS 26, package inspection should inspect the GAUSS 26 package context by default.
- If the user selects GAUSS 25, package inspection should inspect the GAUSS 25 package context.
- Package results must not be mixed across GAUSS versions unless explicitly requested.
- Environment detection does not reveal package availability — the two are separate, dependent capabilities.

## Package Inspection Status Summary

| Status | Meaning | Operating Mode / Response Behavior | What the Assistant Must Not Claim |
|---|---|---|---|
| `complete` | Inspection completed for the requested scope with low enough uncertainty to report as complete. | `verified_knowledge` or `execution_candidate` | Code has run, or that inspection alone validates syntax/methodology. |
| `partial` | Some package locations or requested packages inspected; uncertainty remains. | `advisory` or `verified_knowledge`; requires at least one warning | Confidence beyond what was actually resolved. |
| `unavailable` | Environment detection was not `found` (or otherwise unusable); inspection cannot proceed safely. | `advisory` (required) | Any specific package's status. |
| `error` | Inspection failed unexpectedly. | `advisory` (required) | That the failure means a package is missing, or that execution is safe. |
| `unknown` | Status cannot be determined; inconclusive or unsupported method. | `advisory` (typical) | Installed or missing in either direction. |

Important:

- Complete inspection does not mean code execution.
- Partial inspection requires warnings.
- Unavailable inspection preserves Advisory Mode.
- Unknown is not missing.
- A missing package is not GAUSS missing.

## Package Object and Availability Summary

Each package object tracks: `name`, `installed`, `version`, `version_known`, `source`, `path`, `package_type`, `notes`.

- `installed: true` does not mean code executed.
- `installed: true` does not validate syntax.
- `installed: false` does not mean GAUSS is missing.
- `installed: "unknown"` is not the same as missing.
- `version_known: false` does not mean the package is missing.
- `package_type: base` does not replace command evidence.
- Package availability may differ by GAUSS version.

## Operating Mode and Fallback Summary

- Advisory Mode remains the fallback.
- Verified Knowledge Mode remains available when command evidence supports claims.
- `execution_candidate` is not Execution Mode.
- Execution Mode does not exist yet.
- Package inspection does not activate execution.
- The assistant can still write, explain, review, document, teach, and product-frame GAUSS work without package inspection.

## Expert Boundary Summary

- Package inspection supports implementation-feasibility reasoning but does not replace GAUSS command evidence.
- Package availability does not validate GAUSS syntax.
- Package availability does not validate statistical methodology.
- Package availability does not validate maintainability/design quality.
- Package availability does not validate documentation quality.
- Package availability does not validate education/learning design.
- Package availability does not validate product/user value.
- Package availability does not imply execution occurred.
- A missing package should not be treated as proof that a method is invalid.
- An installed package should not be treated as proof that a method is appropriate.
- Even future successful execution would not prove statistical validity or product value.

## Important Findings

- `v0.22.0` defines the package-inspection contract without implementing inspection.
- The schema and examples make future package-inspection implementation testable — any real implementation can be validated against the same schema and compared to the same expected-shape examples.
- The `27.x` benchmarks protect against the highest-risk overclaims this capability area introduces: installed package means code can run; installed package means syntax is valid; installed package means methodology is valid; missing package means GAUSS is missing; unknown package status means missing or installed.
