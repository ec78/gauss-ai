# v0.34.0 Implementation Report: Confirmed Controller Execution Path

## Milestone Purpose

`v0.34.0` verifies, for the first time, the real execution path through the **complete** orchestration controller confirmation/state-machine flow — not just the standalone `GaussExecutionAdapter` boundary that `v0.33.0` verified:

`RequestDraft` → `MockOrchestrationInstance.submit_for_review()` → `display_plan()` → `confirm(ConfirmationEvent)` → `invoke(build_production_adapter_runner(...))` → `GaussExecutionAdapter` → `execute_gauss_code(...)` → `tgauss.exe -b <script_path>` → structured result routing → `begin_analysis(...)`

This milestone performed exactly **two** real, minimal, non-destructive GAUSS invocations through a dedicated controller-path harness, under explicit, narrowly-scoped user authorization for up to three. **This does not constitute production readiness or user-facing automatic execution** — see `planning/v0.34.0-readiness-checklist.md` for the full readiness assessment and the explicit distinction between an operational, controller-verified real-execution path, a production-ready system, and user-facing automatic execution.

This document is the authoritative audit report for this milestone, as explicitly requested by the task specification (`planning/<milestone-version>-implementation-report.md`). `planning/v0.34.0-confirmed-controller-execution-path.md` is a short cross-reference pointing here, kept because the milestone's 20 evaluation run files (`evaluations/runs/2026-07-19-code-assistant-controller-execution-path-run-*.md`) were authored citing that filename as their evidence source before this consolidation.

## Explicit Authorization Received

The task that produced this milestone included an explicit, scoped authorization to perform up to three real GAUSS invocations, provided every preflight and safety requirement passed, limited to: the verified Windows environment, GAUSS 26.1.1.5516, `C:\gauss26\tgauss.exe`, inline code only, minimal non-destructive code grounded in verified prior evidence, contained disposable directories, no network, no credentials/secrets, no arbitrary user-file access, and no GUI execution. No automatic retry was authorized; each invocation had to be individually justified and recorded. The task explicitly noted that using fewer than three total invocations was acceptable. Every constraint below documents how that scope was honored.

## Stage 2 — Dedicated Controller-Path Harness

`scripts/test_gauss_runtime_orchestration_real.py` (new file) was built specifically to drive the **full** controller through a real invocation, mirroring `scripts/test_gauss_execution_adapter_real.py`'s doubly-gated safety pattern exactly:

- Requires `--run-real-gauss` (CLI flag) **and** `GAUSS_AI_ALLOW_REAL_EXECUTION=1` (environment variable) simultaneously; any single-gate or no-gate combination prints a `SKIPPED` message and exits 0 without touching GAUSS.
- Exposes two verified scenarios, both grounded in prior real evidence, never invented:
  - `"success"`: `"x = 2 + 2;\nprint x;"` — verified as `v0.28.0` Test 3, "Scalar calculation."
  - `"runtime_error"`: `"x = ;"` — verified as `v0.28.0` Test 4, "Intentional syntax error," producing `error G0105`.
- Preflight helpers (`_verify_platform()`, `_verify_executable(...)`) mirror the `v0.33.0` harness's own checks, confirming Windows and a `tgauss`/`tgauss.exe` basename before any invocation.
- `_run_controller_path(...)` builds a real `orch.EnvironmentSummary`, `orch.SafetyReviewOutcome` (6 passing `SafetyReviewItem`s: code_shown, no_delete, terminal_executable, timeout_set, no_network, no_credentials), and `orch.RequestDraft`, then drives the instance through `submit_for_review()` → `display_plan()` → `confirm(ConfirmationEvent(scope=request.request_hash, ...))` → `real_runner = orch.build_production_adapter_runner(request_identity=request.request_hash)` → `instance.invoke(real_runner)`, printing state, confirmation status/consumption, request hash, helper invocation ID, execution status, exit code, stdout, stderr, output-file count, and structural-validation result at every step. If the resulting state is `EXECUTION_COMPLETED` or `EXECUTION_FAILED` (not `MALFORMED_RESULT`), it proceeds to `begin_analysis(...)` with minimal deterministic hooks, then prints the final state, transition count, full transition sequence, and `instance.record.to_safe_summary()`.
- `_run_self_tests()` covers only pure gate logic, preflight helpers, and scenario-code verification, explicitly clearing `GAUSS_AI_ALLOW_REAL_EXECUTION` from the ambient environment before testing skip paths (never trusting the ambient shell), restoring it afterward.

**Verified live before any real invocation:** self-test passed (`SELF-TEST PASSED: gating and preflight logic verified; no GAUSS was touched.`); all three no/one-gate CLI combinations independently confirmed to skip cleanly with exit code 0.

## Stage 4b — Decision to Stop at 2 of 3 Authorized Invocations

Two clean, high-value real invocations achieved both primary objectives: the required successful controller-path traversal (Stage 3) and the recommended priority-one failure-path scenario, a real GAUSS runtime error (Stage 4). Per the task's explicit "using fewer than three total invocations is acceptable" guidance and its stated preference for one or two high-value scenarios over exhausting the full budget, the third authorized invocation (a contained expected-output case) was deliberately not used — it would not have demonstrated anything beyond what Stages 3 and 4 already established, and using it without a distinct, justified purpose would have been an unjustified extra real invocation rather than added value.

**Real-execution budget used: 2 of 3 authorized invocations.**
