# v0.14.0 Software Engineering Expert Foundation Plan

## Release Goal

`v0.14.0` introduces the Software Engineering Expert as the third operational expert. The Code Assistant currently has implementation correctness through the GAUSS Language Expert (owns GAUSS syntax, command selection, data structures, the package/base distinction) and methodological correctness through the Econometrics Expert (owns model choice, assumptions, diagnostics, causal/predictive framing, statistical validity). Neither owns code quality as such: whether a working, methodologically-sound piece of GAUSS code is also well-organized, testable, and safe to change later. The Software Engineering Expert closes that gap — it owns maintainability, structure, readability, testing, refactoring, and safe change management.

This remains documentation/evaluation-driven expert routing, exactly like the GAUSS Language Expert (`v0.8.0`) and Econometrics Expert (`v0.9.0`) before it: an operational profile, activation triggers, decision rules, and manually-evaluated benchmarks — not a runtime orchestration engine. No code parses or enforces any of this at runtime; a response is checked against it manually, the same way task-mode fit is checked today. Adding a third expert changes the *shape* of routing (more combinations to document and evaluate) but not its *mechanism*.

## Expert Ownership

The Software Engineering Expert owns:

- Code organization
- Modularity
- Decomposition into procedures/functions
- Naming clarity
- Readability
- Maintainability
- Refactoring strategy
- Testability
- Edge-case thinking
- Error handling strategy
- Code review patterns
- Reducing duplication
- Safe change management
- Separation of concerns
- Complexity management
- Lightweight design guidance
- Migration/refactor planning

The Software Engineering Expert does not own:

- Exact GAUSS syntax
- Verified GAUSS command signatures
- The GAUSS package/base distinction
- Econometric model appropriateness
- Causal interpretation
- Statistical diagnostics
- Official GAUSS documentation authority
- Product strategy
- Instructional sequencing
- User-facing documentation quality as its primary domain (it may comment on code comments/docstrings as a maintainability concern, but polished user-facing documentation is the Documentation Expert's eventual domain, not this one's)

## Expert Boundary Rules

- GAUSS-specific syntax claims must defer to the GAUSS Language Expert and verified evidence — the Software Engineering Expert never asserts exact GAUSS syntax on its own authority.
- Econometric/statistical claims must defer to the Econometrics Expert — the Software Engineering Expert never asserts model appropriateness or causal validity on its own authority.
- The Software Engineering Expert may recommend structure but cannot invent GAUSS syntax to fit that structure.
- The Software Engineering Expert may recommend tests but cannot claim code was executed unless it actually was.
- The Software Engineering Expert may flag maintainability risks even when GAUSS syntax is valid — syntactic validity and good design are separate claims, and a response should not conflate "this compiles/runs" with "this is well-organized."
- The Software Engineering Expert may flag poor design even when the econometric method is appropriate — methodological soundness and code organization are separate claims.
- If all three experts activate, implementation, methodology, and maintainability claims must remain separate and separately attributable in the response — extending the same coordination principle `v0.9.0` established for two experts to three.

## Multi-Expert Routing Impact

Current routing types (`v0.9.0`-`v0.13.0`, two experts): GAUSS-only, Econometrics-only, Both, Neither.

`v0.14.0` extends this to eight documented routing-type combinations across three experts:

- GAUSS-only
- Econometrics-only
- Software-engineering-only
- GAUSS + Econometrics
- GAUSS + Software Engineering
- Econometrics + Software Engineering
- GAUSS + Econometrics + Software Engineering
- Neither (none of the three)

This is a genuine expansion of `workflows/expert-routing.md`'s structure — Step 1's task classification, Step 2's trigger-matching, Step 3's non-activation checks, and Step 4's routing-type determination all need a third axis, and the "Operational Experts Currently Supported" table grows from two rows to three. The goal is to keep this readable and inspectable at eight combinations, not to build a combinatorial routing engine: each combination should still be describable in one sentence plus a worked example, the same way the four two-expert combinations are today. If a future fourth expert is ever added, this same pattern (documented table, enumerated combinations, one-sentence coordination rule per combination) should still hold reasonably at sixteen — but that question is out of scope for this milestone and not designed for preemptively.

### reasoning.md

Should describe a step-by-step reasoning workflow, following the `experts/econometrics/reasoning.md` precedent (a numbered workflow plus a "when to ask clarifying questions" section):

1. Identify the user's actual goal (is this a correctness question, a design question, or both?).
2. Separate correctness from maintainability — a response should never silently swap one for the other.
3. Identify design risks in the current code or plan.
4. Identify decomposition opportunities.
5. Preserve behavior during any recommended refactor — flag explicitly if a suggested change would alter behavior.
6. Recommend tests or validation checks appropriate to the risk.
7. Coordinate with the GAUSS Language Expert and/or Econometrics Expert when the task also touches their domains, rather than answering on their behalf.

Should include, following the `experts/econometrics/best_practices.md` precedent (a flat, numbered list):

- Avoid duplicated logic

- State assumptions
- Avoid premature optimization
- Document non-obvious decisions
- Prefer incremental changes

### common_mistakes.md

## Risks and Design Questions

- **How large should the Software Engineering Expert foundation be before it becomes too broad?** Bounded by the Expert Ownership list above — general code-quality reasoning applicable to any language, deliberately not a GAUSS-specific style guide (that would blur into the GAUSS Language Expert's territory) and not a full software-architecture curriculum.
- **Should testing strategy be general only, or include GAUSS-specific testing conventions later?** General only for `v0.14.0` — GAUSS-specific testing conventions (if any exist) would need verified evidence the same way any GAUSS-specific claim does, which is the GAUSS Language Expert's territory; this expert recommends *that* testing happen and *what kind*, not GAUSS-specific test-framework syntax.
- **How should performance advice be bounded so it does not overclaim?** Keep it at the design level (avoid premature optimization, flag obvious complexity issues) rather than claiming specific GAUSS performance characteristics without evidence — a specific GAUSS performance claim would need the same evidence discipline as a syntax claim.
- **How should the expert handle pseudocode vs. verified GAUSS code?** Explicitly, per Benchmark `21.2`'s expected behavior — refactoring suggestions must either use verified GAUSS syntax (per the GAUSS Language Expert's evidence requirements) or be clearly marked as illustrative/pseudocode, never presented as verified GAUSS without evidence.
- **How should routing remain readable with three operational experts?** By keeping the "one sentence plus a worked example per combination" discipline from the Multi-Expert Routing Impact section — eight combinations is the ceiling this milestone commits to keeping readable; a fourth expert is explicitly not being designed for now.
- **Should Documentation/Education/Product remain narrative-only for now?** Yes — explicitly out of scope per Non-goals; this milestone does not touch them.
- **How to avoid turning the Software Engineering Expert into a general catch-all?** The Non-Activation Cases list is the primary guardrail — pure documentation, pure education, pure product strategy, and pure prose editing are explicitly excluded, keeping this expert's territory to code/design quality specifically.
