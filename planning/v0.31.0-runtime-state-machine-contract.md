# v0.31.0 Runtime State Machine Contract

This document is the **authoritative, implementation-ready specification** of the runtime orchestration state machine first introduced conceptually in `planning/v0.31.0-runtime-orchestration-design.md`'s "State Machine" section. Where the two documents differ, this document governs; `planning/v0.31.0-runtime-orchestration-design.md` has been updated to reference this document as the source of truth (see "Required Consistency Updates" in the final report).

This is planning and interface-definition work only. No controller is implemented, no Python classes/dataclasses/enums/protocols/reducers/transition functions are added, no formal state-machine schema is created, and no execution helper code, tests, or `schemas/gauss_code_execution.schema.json` are changed. `gauss.exe`/`tgauss.exe` were not invoked to produce this document.

## 1. Purpose and Scope

**What the runtime state machine governs:** the lifecycle of exactly one Canonical Execution Request (per `planning/v0.31.0-canonical-execution-request-contract.md`), from the moment execution intent is recognized through to a final response, including every eligibility/safety/confirmation/invocation/analysis/reporting step in between. It governs *when* a transition may occur, not *how* the underlying work (building a plan, calling the helper, interpreting a result) is performed — that remains the responsibility of the Proposed Components already named in `planning/v0.31.0-runtime-orchestration-design.md` (Execution Intent Classifier, Execution Request Builder, Eligibility Evaluator, Safety Review, Consent Manager, Helper Adapter, Result Validator, Analysis Router, Response Composer).

**Where it begins and ends:** it begins at `advisory` — the session-level state of having no active execution request — and ends, for any one request, at one of three terminal states (`completed`, `cancelled`, `blocked`) or at a terminal sub-case of `execution_failed` (a malformed result; see §12, §14). It does not govern what happens after a terminal state beyond the fact that the *next* execution request, if any, is a wholly new instance (see §14's resolution of "terminal versus resumable").

**Which future component owns state transitions:** the **State Machine** component itself (already named in `planning/v0.31.0-runtime-orchestration-design.md`'s Proposed Components) is the sole owner of the current-state value and the sole authority for whether a proposed transition is valid. No other component may mutate `current_state` directly.

**Which components may propose transitions:** the Execution Intent Classifier, Execution Request Builder, Eligibility Evaluator, Safety Review, Consent Manager, Helper Adapter, Result Validator, and Analysis Router / report-generation routing may each *propose* that a specific transition occur (for example, "eligibility passed, propose `collecting_inputs → proposed`"). A proposal is not itself an authorization.

**Which component authorizes transitions:** the State Machine authorizes a proposed transition only if the transition is in the valid-transition table (§4) and every guard for that transition (§6) passes. An unauthorized proposal is rejected, and the State Machine's own behavior on rejection is to leave `current_state` unchanged and surface the specific failed guard for disclosure (§6, §11).

**What data belongs to the state machine:** the state-owned data model in §3 — `current_state`, `previous_state`, transition bookkeeping, confirmation/invocation/analysis/report *status* flags, and references (not copies) to the canonical request and the execution result.

**What remains owned by the Canonical Execution Request:** all 18 fields defined in `planning/v0.31.0-canonical-execution-request-contract.md` — the code/script identity, paths, timeout, environment summary, safety-review content, and the confirmation fields (`user_confirmed`, `confirmation_scope`, `confirmation_timestamp`). The state machine *references* `canonical_request_id`/`request_hash`; it does not duplicate the request's own field content.

**What remains owned by the execution result:** everything in `schemas/gauss_code_execution.schema.json`'s unchanged result contract — `execution_status`, `exit_code`, `stdout`, `stderr`, `output_files`, and so on. The state machine references the result (`execution_result_reference`) once the helper returns; it does not redefine or duplicate result fields.

**What remains outside the state machine entirely:** the actual mechanics of building a plan, running eligibility/safety checks, computing a hash, invoking the helper, or interpreting a result — all of that lives in the Proposed Components, per `planning/v0.31.0-runtime-orchestration-design.md`. The state machine only governs *when* those components' outputs are allowed to move the request from one state to the next.

**Explicit statement, as required:** this document defines **behavior**, not executable runtime code. No state, transition, guard, or data field described here exists as a Python object anywhere in this repository as a result of this task.

## 2. Authoritative State Inventory

The current 13-state inventory from `planning/v0.31.0-runtime-orchestration-design.md` is retained **unchanged in count and name**. Direct review found no case requiring a new state, a removed state, or a rename — but it did find that four previously-listed *transitions* into `collecting_inputs` from terminal-or-near-terminal states were conceptually mislabeled as intra-instance transitions when they are actually **new-request creation events**; this discrepancy is resolved in §4/§5/§14, not by changing the state inventory itself.

For every state: purpose, entry conditions, required state-owned data, permitted/prohibited actions, valid exits, terminal/resumable status, and the canonical-request/confirmation/invocation/result posture at that state.

### `advisory`

- **Purpose:** the session-level "no active execution request" state.
- **Entry conditions:** session start; or, implicitly, whenever no request is currently active (this is not itself a transition target reached *from* a terminal state — see §14).
- **Required state-owned data:** none — `advisory` is not owned by any `canonical_request_id`.
- **Permitted actions:** advisory-mode responses (explanation, review, debugging guidance); recognizing a new execution intent.
- **Prohibited actions:** any helper invocation; any reference to a stale request's confirmation.
- **Valid exits:** creation of a new request, entering that new request's own `collecting_inputs` or `proposed` state (see §4).
- **Terminal?** No — it is the default, always-available state.
- **Resumable?** N/A — it has no request identity to resume.
- **Canonical request may exist?** No.
- **Request must be frozen?** N/A.
- **Confirmation must exist?** N/A.
- **Confirmation consumed?** N/A.
- **Helper invocation may have occurred?** No.
- **Validated result may exist?** No (a *prior*, unrelated request's result may exist in the session's history, but is not "in" `advisory`).
- **User-visible behavior:** ordinary advisory responses; per Pattern A.
- **Recovery behavior:** N/A — there is nothing to recover from in this state.

### `collecting_inputs`

- **Purpose:** an execution intent was recognized for a *specific new request*, but required inputs are incomplete.
- **Entry conditions:** (a) a new request is created from `advisory` with incomplete inputs, or (b) a pre-confirmation edit occurs from `awaiting_confirmation` for the *same* `canonical_request_id` (§14).
- **Required state-owned data:** `canonical_request_id` (assigned at creation); `current_state = collecting_inputs`.
- **Permitted actions:** requesting the smallest missing input (Pattern C); updating the draft request's fields.
- **Prohibited actions:** any helper invocation; presenting a confirmation prompt.
- **Valid exits:** `proposed`, `blocked`, `cancelled`.
- **Terminal?** No.
- **Resumable?** Yes, within the same instance — this state is inherently mutable and revisitable pre-confirmation.
- **Canonical request may exist?** Yes, in draft form (per the request contract's lifecycle steps 3-5).
- **Request must be frozen?** No — this is precisely the mutable phase.
- **Confirmation must exist?** No.
- **Confirmation consumed?** No.
- **Helper invocation may have occurred?** No.
- **Validated result may exist?** No.
- **User-visible behavior:** Pattern C ("Request Missing Inputs").
- **Recovery behavior:** N/A — nothing has failed yet; this is a normal working state.

### `proposed`

- **Purpose:** a complete execution plan has been built and eligibility/safety review has passed; the plan is ready for display.
- **Entry conditions:** all required-before-confirmation fields populated (per the canonical request contract's §3 "must be user-visible before confirmation" set) and `safety_review` shows a passing outcome.
- **Required state-owned data:** `canonical_request_id`; `request_hash` (computed at canonicalization, per the request contract's lifecycle step 6-7).
- **Permitted actions:** preparing the displayed plan.
- **Prohibited actions:** helper invocation; treating plan readiness itself as consent.
- **Valid exits:** `awaiting_confirmation`.
- **Terminal?** No.
- **Resumable?** Yes, within the same instance.
- **Canonical request may exist?** Yes, canonicalized (snapshot taken).
- **Request must be frozen?** Not yet — freezing happens at `confirmed` (request contract lifecycle step 10), but the *displayed* snapshot from this point forward must not silently change without a fresh canonicalization.
- **Confirmation must exist?** No.
- **Confirmation consumed?** No.
- **Helper invocation may have occurred?** No.
- **Validated result may exist?** No.
- **User-visible behavior:** the plan is about to be shown (Pattern B).
- **Recovery behavior:** N/A.

### `awaiting_confirmation`

- **Purpose:** the plan has been displayed; the system is waiting for the user's response.
- **Entry conditions:** the plan from `proposed` was actually displayed to the user (lifecycle step 8).
- **Required state-owned data:** `canonical_request_id`; `request_hash`; `confirmation_status = requested`.
- **Permitted actions:** waiting for a reply; evaluating whether a reply is genuine confirmation (§6, §7).
- **Prohibited actions:** helper invocation; treating an unrelated or ambiguous reply as confirmation.
- **Valid exits:** `confirmed`, `cancelled`, `collecting_inputs` (a pre-confirmation edit — same `canonical_request_id`, per §14).
- **Terminal?** No.
- **Resumable?** Yes, within the same instance.
- **Canonical request may exist?** Yes.
- **Request must be frozen?** No — still pre-confirmation.
- **Confirmation must exist?** Not yet — this state exists precisely to obtain it.
- **Confirmation consumed?** No.
- **Helper invocation may have occurred?** No.
- **Validated result may exist?** No.
- **User-visible behavior:** the confirmation prompt itself.
- **Recovery behavior:** N/A.

### `confirmed`

- **Purpose:** the user has explicitly confirmed the exact displayed plan; the request is now frozen.
- **Entry conditions:** the three-part minimum-evidence confirmation test (per the canonical request contract's §8) passes, and `confirmation_scope == request_hash`.
- **Required state-owned data:** `canonical_request_id`; `request_hash`; `confirmation_status = accepted`; `confirmation_event_reference`.
- **Permitted actions:** preparing to invoke the Helper Adapter.
- **Prohibited actions:** any further edit to the request (would require returning to `collecting_inputs` for a **new** request, per the request contract's immutability rule — not a same-instance transition once frozen; see §14).
- **Valid exits:** `executing`.
- **Terminal?** No.
- **Resumable?** No — once confirmed, the only forward path is invocation; there is no "un-confirm and keep editing this same instance" path (that would violate the frozen-request guarantee).
- **Canonical request may exist?** Yes, frozen.
- **Request must be frozen?** Yes — this is the freeze point (request contract lifecycle step 10).
- **Confirmation must exist?** Yes.
- **Confirmation consumed?** Not yet — consumption happens atomically with/immediately before invocation (§7, §8).
- **Helper invocation may have occurred?** No.
- **Validated result may exist?** No.
- **User-visible behavior:** none required — this is a brief, internal pre-invocation state.
- **Recovery behavior:** N/A.

### `executing`

- **Purpose:** the Helper Adapter has invoked (or is about to invoke) `execute_gauss_code(...)`, and the synchronous call has not yet returned.
- **Entry conditions:** stage 11 (pre-invocation stale-state validation) and stage 12 (duplicate-execution validation), per the canonical request contract's §11, both pass.
- **Required state-owned data:** `canonical_request_id`; `request_hash`; `confirmation_consumption_status = consumed`; `helper_invocation_status = in_progress`; `helper_invocation_identifier`.
- **Permitted actions:** waiting for the synchronous call to return.
- **Prohibited actions:** a second invocation for this `request_hash` (§8); any claim of cooperative mid-call cancellation (§9, §10).
- **Valid exits:** `execution_completed`, `execution_failed`.
- **Terminal?** No.
- **Resumable?** No — this state exists only for the duration of one synchronous call.
- **Canonical request may exist?** Yes, frozen (unchanged since `confirmed`).
- **Request must be frozen?** Yes.
- **Confirmation must exist?** Yes.
- **Confirmation consumed?** Yes, as of entry to this state (§7).
- **Helper invocation may have occurred?** Yes — exactly once, in progress.
- **Validated result may exist?** No, not yet.
- **User-visible behavior:** none required while waiting (a "running" indicator is a UI concern, not a state-machine requirement).
- **Recovery behavior:** if the process hosting the state machine is interrupted while in this state, §15 governs — fail closed, treat as `unknown`, require a new request.

### `execution_completed`

- **Purpose:** the helper returned a structurally valid result with `execution_status: completed`. See §12 for the precise, resolved definition of this threshold.
- **Entry conditions:** the returned result passed schema validation (`validate_against_schema(...)`) **and** its `execution_status` field equals `"completed"`.
- **Required state-owned data:** everything from `executing`, plus `execution_result_reference`; `validation_outcome = pass`; `helper_invocation_status = returned`.
- **Permitted actions:** proceeding to analysis.
- **Prohibited actions:** any further helper invocation for this request; treating `completed`/`exit_code: 0` as methodology validity (Invariant 10, §17).
- **Valid exits:** `analyzing`.
- **Terminal?** No.
- **Resumable?** No — it exists only as a brief checkpoint before analysis.
- **Canonical request may exist?** Yes, frozen.
- **Confirmation consumed?** Yes.
- **Helper invocation may have occurred?** Yes, exactly once, returned.
- **Validated result may exist?** Yes.
- **User-visible behavior:** none required yet — disclosure happens after analysis, per Pattern E.
- **Recovery behavior:** N/A.

### `execution_failed`

- **Purpose:** the helper returned a result indicating failure (`execution_status` in `{failed, timed_out, error}`), **or** the returned result failed structural (schema) validation entirely (the malformed-result case). See §12.
- **Entry conditions:** either (a) a structurally valid result with `execution_status` in `{failed, timed_out, error}`, or (b) a result that failed schema validation.
- **Required state-owned data:** everything from `executing`, plus `execution_result_reference` (if any was returned at all); `validation_outcome` (pass with a failure status, or fail); `failure_category` (one of the Failure Taxonomy's post-invocation categories, §11).
- **Permitted actions:** proceeding to analysis (for non-malformed categories); disclosing the failure (Pattern F/G, or the malformed-result disclosure).
- **Prohibited actions:** any automatic rerun (Invariant 4); treating a malformed result as valid execution evidence (§12).
- **Valid exits:** `analyzing` (non-malformed categories only, per §11's "Analysis allowed?" column) — **not** `collecting_inputs` (see §14's resolution).
- **Terminal?** For the malformed-result sub-case, **yes** (this specific request's lifecycle ends here — analysis is not entered until the result is somehow re-diagnosed, which this design does not define a same-instance mechanism for). For every other category, **no** — the state proceeds to `analyzing`.
- **Resumable?** No, in either case, within the same instance — a rerun is always a new request (§14).
- **Canonical request may exist?** Yes, frozen.
- **Confirmation consumed?** Yes (except for pre-invocation blocking/cancellation categories that never actually reach `executing` — see §11's per-category detail, which is authoritative over this state description for edge cases).
- **Helper invocation may have occurred?** Yes, for post-invocation categories; no, for categories that block before `executing` (§11 clarifies per-category).
- **Validated result may exist?** Yes, for non-malformed categories; a flagged-invalid result for the malformed case.
- **User-visible behavior:** Pattern F (GAUSS runtime error), Pattern G (timeout), or the malformed-result disclosure.
- **Recovery behavior:** none within this instance — see §14 for the new-request path.

### `analyzing`

- **Purpose:** the result (successful or failed, but not malformed) is being routed through `workflows/execution-aware-analysis.md`.
- **Entry conditions:** `execution_completed`, or `execution_failed` with a non-malformed `failure_category`.
- **Required state-owned data:** everything from the prior state, plus `analysis_status = in_progress`.
- **Permitted actions:** expert-routed interpretation, per `workflows/execution-aware-analysis.md`.
- **Prohibited actions:** rewriting `execution_status` or `execution_result_reference` (Invariant 8); treating execution success as methodological validity (Invariant 10).
- **Valid exits:** `report_generating` (if a report was requested), `completed` (otherwise).
- **Terminal?** No.
- **Resumable?** No.
- **Canonical request may exist?** Yes, frozen.
- **Confirmation consumed?** Yes.
- **Helper invocation may have occurred?** Yes (for the `execution_completed`/non-malformed-`execution_failed` entry paths) or no (this state is never entered from a pre-invocation block, per the valid-entry conditions above).
- **Validated result may exist?** Yes.
- **User-visible behavior:** none required yet — this is interpretation work feeding the final response.
- **Recovery behavior:** if analysis itself fails (§11, §13), `analysis_status = failed`, but the state still proceeds to `completed` with the raw execution evidence preserved and disclosed instead of an interpretation.

### `report_generating`

- **Purpose:** `workflows/report-generation.md` is being applied, because a report/summary was explicitly requested.
- **Entry conditions:** analysis finished (successfully or with `analysis_status = failed`, in which case report generation itself may still attempt a plain execution-aware summary per its own fallback rules) and a report was requested.
- **Required state-owned data:** everything from `analyzing`, plus `report_status = in_progress`.
- **Permitted actions:** report composition, per `workflows/report-generation.md`.
- **Prohibited actions:** erasing or reinterpreting the validated execution/analysis evidence (Invariant 8).
- **Valid exits:** `completed`.
- **Terminal?** No.
- **Resumable?** No.
- **Canonical request may exist?** Yes, frozen.
- **User-visible behavior:** none required yet — the report itself is the final response.
- **Recovery behavior:** if report generation fails, `report_status = failed`, but the state still proceeds to `completed` with a plain execution-aware summary substituted (per the Failure Taxonomy's "Report-generation failure" row).

### `completed`

- **Purpose:** the full flow (execution, if any + analysis, if applicable + report, if requested) has concluded and a final response was produced.
- **Entry conditions:** `analyzing → completed` (no report requested) or `report_generating → completed` (report produced or its fallback applied).
- **Required state-owned data:** the full accumulated record for this request.
- **Permitted actions:** none further for this instance — this is a terminal state.
- **Prohibited actions:** any further transition of this instance; any helper invocation referencing this `request_hash`.
- **Valid exits:** none (terminal). See §14 for the new-request lineage relationship.
- **Terminal?** Yes.
- **Resumable?** No, within this instance.
- **User-visible behavior:** the final response.
- **Recovery behavior:** N/A — nothing to recover; this is success (or a disclosed failure that was fully processed).

### `cancelled`

- **Purpose:** the user withdrew the request, or explicitly declined to proceed, before or during execution.
- **Entry conditions:** an explicit decline at `awaiting_confirmation`, or an explicit withdrawal at `collecting_inputs`, or a cancellation acknowledgment during `executing` (§10).
- **Required state-owned data:** `canonical_request_id`; `cancellation_status`.
- **Permitted actions:** acknowledging, per Pattern D/general acknowledgment.
- **Prohibited actions:** any further transition of this instance.
- **Valid exits:** none (terminal). See §14.
- **Terminal?** Yes.
- **Resumable?** No, within this instance.
- **User-visible behavior:** acknowledgment, no further action.
- **Recovery behavior:** N/A.

### `blocked`

- **Purpose:** eligibility or safety review failed; execution cannot proceed for this request as currently specified.
- **Entry conditions:** a failing outcome from the Eligibility Evaluator or Safety Review (§11).
- **Required state-owned data:** `canonical_request_id`; `failure_category` (an eligibility/safety-review category).
- **Permitted actions:** explaining the specific blocking reason (Pattern D/D-adjacent).
- **Prohibited actions:** any further transition of this instance; any helper invocation.
- **Valid exits:** none (terminal). See §14.
- **Terminal?** Yes.
- **Resumable?** No, within this instance.
- **User-visible behavior:** the blocking explanation and a safe alternative, if any.
- **Recovery behavior:** N/A within this instance.

## 5. Prohibited Transitions

| # | Prohibited transition | Why |
|---|---|---|
| 1 | `advisory → executing` | Must pass through proposal, display, and explicit confirmation — no shortcut. |
| 2 | `collecting_inputs → executing` | Incomplete or unreviewed inputs can never reach invocation. |
| 3 | `proposed → executing` | The plan must be displayed and confirmed first — reaching a valid plan is not itself consent. |
| 4 | `awaiting_confirmation → executing` | Confirmation is a distinct, logged event (transition 7 in §4) — never inferred from silence, a vague reply, or the mere passage of time. |
| 5 | `execution_failed → executing` | Any rerun is a new request (transition through `collecting_inputs → proposed → awaiting_confirmation → confirmed → executing` for a **new** `canonical_request_id`), never a direct retry of the failed instance. |
| 6 | `cancelled → executing` | A cancelled instance is terminal; nothing about it can be resumed into execution. |
| 7 | `blocked → executing` | A blocked instance is terminal; the blocking condition must be resolved via a new request, not by forcing the same instance forward. |
| 8 | `completed → executing` | A completed instance is terminal; a rerun is a new request. |
| 9 | `confirmed → analyzing` | Analysis requires an actual execution result; skipping `executing`/`execution_completed`/`execution_failed` would analyze nothing. |
| 10 | `confirmed → completed` | Skipping invocation and analysis entirely would produce a "completed" response for a request that never ran — a direct violation of "no execution claims without an actual attempt." |
| 11 | `executing → awaiting_confirmation` | Once invocation has begun, there is no returning to a pre-invocation state for the same instance — the synchronous call must resolve to `execution_completed` or `execution_failed` first. |
| 12 | Any second helper invocation for the same `request_hash` | Enforced by transition 10's `request_not_already_executed` guard (§6, §8) — `executing` may be entered at most once per `canonical_request_id`. |
| 13 | Any transition using stale or mismatched confirmation | Enforced by transition 7's `confirmation_scope_matches_hash` and `request_unchanged` guards, and transition 10's `environment_still_matches`/`paths_remain_valid` guards. |
| 14 | Any transition that resurrects a terminal request | Enforced structurally: `completed`, `cancelled`, `blocked`, and the malformed-result sub-case of `execution_failed` have **no valid exits** in §4's table — nothing transitions out of them. |

**Note on the four removed pseudo-transitions:** an earlier draft of `planning/v0.31.0-runtime-orchestration-design.md` listed `execution_failed → collecting_inputs`, `blocked → collecting_inputs`, `cancelled → collecting_inputs`, and (implicitly, via the compact transition table's "valid exits" column) `completed → collecting_inputs`/`completed → advisory` as if they were transitions of one instance. This document's review determined that treating them as same-instance transitions would violate the request-immutability guarantee established in `planning/v0.31.0-canonical-execution-request-contract.md` (a confirmed/executed/terminal request must never be edited in place) and the "terminal requests are never resurrected" invariant (§17, Invariant 5). They are therefore **removed from the transition inventory** and reframed as **request-lineage relationships** (§14) — a new, distinct `canonical_request_id` may be created after any of these four terminal outcomes, optionally referencing the terminal request's ID for user-facing "here's what changed" framing, but this is bookkeeping about two separate instances, not a transition of one.

**Terminal states lead only to the creation of a distinct new orchestration instance / request**, per the above — never to a literal transition back into a live state for the same `canonical_request_id`.

## 7. Confirmation Lifecycle

Confirmation state values, precisely defined (mirrors `confirmation_status` in §3):

- **`none`** — no confirmation has been requested yet (states `advisory` through `proposed`).
- **`requested`** — the plan has been displayed and a confirmation prompt issued (`awaiting_confirmation`).
- **`accepted`** — the three-part minimum-evidence test passed and `confirmation_scope == request_hash` (`confirmed` onward).
- **`rejected`** — the user explicitly declined (leads to `cancelled`).
- **`stale`** — the request changed after display but before a reply was given, or a reply arrived but no longer matches the current `request_hash` — treated identically to `none` for gating purposes, but tracked distinctly for disclosure ("Consent stale," §11).
- **`invalidated`** — a previously `accepted` confirmation was voided by a post-acceptance-but-pre-invocation change or staleness discovery (§6's `request_unchanged`/`environment_still_matches`/`paths_remain_valid` guards failing at stage 11 of the canonical request contract's validation sequence).
- **`consumed`** — confirmation has been used to authorize exactly one invocation attempt (`executing` onward).
- **`expired`** — a session-boundary or elapsed-time invalidation, per §15's fail-closed default (no precise numeric policy is defined — see Open Decisions, §21).

**When confirmation becomes attached to the request:** at the `awaiting_confirmation → confirmed` transition (§4, transition 7) — `confirmation_scope` and `confirmation_event_reference` are set at that instant, not before.

**When it becomes immutable:** immediately upon attachment. `confirmation_scope`/`confirmation_event_reference` are never edited in place once set — any invalidation clears them and requires a wholly new confirmation event (a new `awaiting_confirmation → confirmed` transition), not a mutation of the old one.

**Whether it is consumed immediately before or at helper invocation:** **at** invocation — this document adopts the conservative rule that `confirmation_consumption_status` transitions from not-consumed to `consumed` **atomically with (not merely "just before") the `confirmed → executing` transition itself** (§4, transition 10). This is the conservative choice required where the current design otherwise leaves ambiguity: treating consumption as happening strictly *before* invocation would create a window where consumption occurred but invocation never did (for example, if the transition were interrupted between the two), which this document judges riskier than binding them as one atomic event, per Invariant 6 (state loss fails closed).

**Whether helper-launch failure consumes confirmation:** **yes.** Per the atomic-consumption rule above, confirmation is consumed as part of attempting the `confirmed → executing` transition, regardless of whether the subsequent launch succeeds. A launch failure (the "Helper/tool invocation failure" category, §11) still requires a **new** confirmation for any retry — the original confirmation is not "given back" because the attempt failed. This is the conservative reading: treating a failed attempt as not having consumed confirmation would create a route to reattempt invocation without fresh review, which this design explicitly forecloses.

**Whether pre-invocation validation failure consumes confirmation:** **no**, if the failure occurs at stage 11/12 of the canonical request contract's validation sequence (pre-invocation stale-state / duplicate-execution validation) *before* the `confirmed → executing` transition is actually authorized — in that case the transition itself never occurs, `confirmation_status` moves to `invalidated` (not `consumed`), and the instance falls back toward `blocked` or a fresh `collecting_inputs`/`proposed` cycle for a **new** request, per §14. The distinction from the previous point is precise: **launch failure** (the transition was authorized and attempted, but the process itself could not start) consumes confirmation; **pre-invocation validation failure** (the transition was never authorized at all) does not.

**Whether cancellation consumes confirmation:** cancellation *before* `confirmed` never had confirmation to consume. Cancellation *during* `executing` (§10) occurs after confirmation was already consumed at transition 10 — cancellation does not "return" consumed confirmation to a valid state.

**Whether confirmation can ever return from consumed to valid:** **no.** Once `confirmation_consumption_status = consumed`, it never reverts — this is a one-way, monotonic transition, matching the "exactly once" invocation guarantee (§8, Invariant 3).

## 8. Helper Invocation Uniqueness

- Only the `confirmed → executing` transition (§4, transition 10) may authorize a helper invocation — no other transition, and no path outside the state machine, may call the Helper Adapter.
- `helper_invocation_identifier` must be recorded **atomically with** the launch attempt (not merely "before" or "after") — the same atomicity rule as confirmation consumption (§7), for the same reason: a window between recording and launching (or launching and recording) creates ambiguity this design must not tolerate.
- The same `request_hash` cannot authorize a second invocation: guard `request_not_already_executed` (§6) checks whether a `helper_invocation_identifier` already exists for this `canonical_request_id` before authorizing transition 10; if one exists, the attempt is refused (§11, "Duplicate execution attempt").
- A process restart must not silently retry: per §15, a state machine instance recovered after an interruption in `executing` (with an ambiguous or unknown launch outcome) is treated as unresolved and requires a **new** request — never an automatic re-invocation of the interrupted one.
- An ambiguous launch outcome fails closed: if it cannot be determined whether the helper actually launched (for example, after a process restart mid-call), this design treats the outcome as `unknown` and forbids any further transition of that instance, per Invariant 6.
- A rerun must use a new `canonical_request_id` and a new confirmation — per §14, there is no valid transition path from any post-invocation state back to `confirmed`/`executing` for the same instance.
- Prior results remain distinct and immutable: `execution_result_reference` is never overwritten once set (§3); a rerun's result is a new instance's own new reference, never merged with the original.
- Duplicate requests are not equivalent to authorized reruns: a duplicate invocation *attempt* for an already-`executing`/-completed/-failed `request_hash` is refused outright (§11); a genuine rerun is an entirely separate, freshly reviewed and freshly confirmed request, not a "duplicate" in this sense.

**Conceptual need for idempotency and locking, without an implementation mechanism:** the guarantees above (record atomically, check before authorizing, fail closed on ambiguity) describe *what* must be true — that at most one invocation ever occurs per `request_hash`, verifiably. *How* this is implemented (an idempotency key check against a store, a mutex/lock, a database constraint, or something else) is explicitly **not** decided here — see §16 and §21.

## 9. Execution Transition Semantics

- **Entering `executing`:** occurs only via transition 10 (§4), with confirmation consumed and `helper_invocation_identifier` recorded atomically with the launch attempt.
- **Helper launch attempted:** the Helper Adapter calls `execute_gauss_code(...)` (per `planning/v0.31.0-canonical-execution-request-contract.md`'s §12 Helper Adapter projection) with the frozen request's data.
- **Helper launch rejected:** if the Helper Adapter's own preflight (mirroring the helper's structural checks) rejects the call before even attempting a subprocess, this is treated identically to a pre-invocation `blocked` outcome for auditing purposes, but since it occurs *after* the `confirmed → executing` transition was authorized, it still consumes confirmation (§7) and routes to `execution_failed` with an appropriate `failure_category`, not back to `blocked`.
- **Helper unavailable:** if the execution helper itself cannot be reached in this environment (a hosting/environment problem, not a GAUSS-side one), this is detected by the `helper_available` guard (§6) *before* transition 10 is authorized — it therefore does **not** consume confirmation and does not enter `executing` at all (§11's "Executable/environment unavailable" and general "Helper unavailable" categories are pre-invocation, per the Failure Taxonomy).
- **Helper returns structured result:** the Result Validator receives the schema-shaped result object and immediately applies `helper_result_structurally_valid` (§6).
- **Timeout result:** `execution_status: timed_out`, `executed: true` — a structurally valid failure result; routes to `execution_failed` with `failure_category = timeout`.
- **GAUSS runtime-error result:** `execution_status: failed`, `executed: true` — a structurally valid failure result; routes to `execution_failed` with `failure_category = gauss_runtime_error`.
- **Malformed helper result:** fails `helper_result_structurally_valid`; routes to `execution_failed` with `failure_category = malformed_result`, and this is the **terminal** sub-case (§2, §12, §14) — analysis is not entered for this category within the same instance.
- **Orchestration interruption during invocation:** per §15, treated as an unresolved/`unknown` outcome; the instance cannot proceed further, and a new request is required to attempt anything again.
- **Unknown launch outcome:** identical treatment to interruption — fails closed, no further transition, new request required.
- **Execution completes after cancellation was requested:** per §10, if a cancellation was requested *during* `executing` but the synchronous call still returns a real result, that result is retained and disclosed honestly (the cancellation could not actually interrupt the call) — the instance still proceeds through `execution_completed`/`execution_failed` → `analyzing` → `completed` normally, with the cancellation request itself recorded in `cancellation_status` for disclosure purposes but not altering the execution outcome.

**Helper status, orchestration state, and methodological validity are kept explicitly distinct throughout this section:** a helper `execution_status` value determines which *orchestration state* (`execution_completed`/`execution_failed`) is entered — it never, by itself, constitutes or implies a methodological-validity claim (Invariant 10, §17). No claim of cooperative mid-call cancellation is made anywhere in this section, consistent with `planning/v0.31.0-runtime-orchestration-design.md`'s File Lifecycle Design finding that `execute_gauss_code(...)`'s default runner is a blocking call with no cancellation hook.

**Whether cancellation creates a terminal state:** yes, when cancellation occurs at or before `confirmed` (the instance moves to `cancelled`, a terminal state). When cancellation is requested *during or after* `executing`, it does **not** independently create a terminal state — the instance still reaches its normal terminal state (`completed`, or the malformed-result terminal case) through the ordinary post-invocation path, with the cancellation request recorded for disclosure only.

**How a user resumes work through a new request:** in every case, per §14 — a wholly new `canonical_request_id`, with its own fresh eligibility review, safety review, canonicalization, hash, and confirmation cycle.

## 12. Result-Validation Transitions

Precise distinctions, as required:

- **Helper returned:** the synchronous `execute_gauss_code(...)` call has produced a Python dict — nothing about its content has been examined yet.
- **Execution result received:** the Helper Adapter has the dict in hand and hands it to the Result Validator; `execution_result_reference` is set.
- **Result structurally validated:** `validate_against_schema(result, schema_path)` (per `scripts/gauss_code_execution.py`, confirmed as a separate call from `execute_gauss_code(...)` itself — see `planning/v0.31.0-canonical-execution-request-contract.md`'s §12) has been run against the result; `validation_outcome` is set to pass or fail.
- **Result semantically interpreted:** happens only in `analyzing`, via `workflows/execution-aware-analysis.md` — this is downstream of, and strictly later than, structural validation.
- **Expected outputs reviewed:** the Result Validator's comparison of `expected_output_files` (canonical request contract, field 9) against the result's actual `output_files` — occurs alongside structural validation, before `analyzing`.
- **Analysis started:** the `execution_completed → analyzing` or non-malformed `execution_failed → analyzing` transition (§4, transitions 13-14).

**Resolved definition of `execution_completed`, precisely, as required:**

`execution_completed` means **a structurally valid, nonfailure result** — specifically: (1) the helper returned, (2) the result passed schema validation against `schemas/gauss_code_execution.schema.json`, **and** (3) the result's `execution_status` field equals exactly `"completed"`. This is option (c) among the four candidates the task posed ("structurally valid nonfailure result"), not merely "helper return" (option a, which would let a malformed or failing result masquerade as success) and not merely "structurally valid" alone (option b, which would still conflate `completed` with `failed`/`timed_out`).

Symmetrically, `execution_failed` means: **either** (a) a structurally valid result whose `execution_status` is in `{failed, timed_out, error}`, **or** (b) a result that failed schema validation entirely (the malformed case). These two sub-cases share a state name for simplicity (per "do not silently add states," §2) but are distinguished by `failure_category` and, critically, differ in downstream eligibility: sub-case (a) may proceed to `analyzing`; sub-case (b) may not (§11).

**This resolution required updating the main design:** `planning/v0.31.0-runtime-orchestration-design.md`'s one-line description of `execution_completed`/`execution_failed` in its State Machine section has been revised to reference this precise threshold rather than repeating the looser original phrasing (see "Required Consistency Updates" in the final report).

**Guarantee, as required:** a malformed result **never** enters `analyzing` as valid execution evidence — guard `analysis_inputs_available` (§6) is defined to require `execution_result_reference` from a path that excludes the malformed sub-case entirely (§4, transition 14's explicit `failure_category != malformed_result` condition), and §11's row for "Malformed helper result" states plainly: "Analysis allowed? **No**."

## 13. Analysis and Reporting Transitions

- **Eligibility to enter `analyzing`:** `execution_completed`, or `execution_failed` with any `failure_category` other than `malformed_result` (§4 transitions 13-14; §12).
- **Analysis after successful execution:** the ordinary `execution_completed → analyzing` path; routes through `workflows/execution-aware-analysis.md`'s `completed` handling.
- **Analysis after GAUSS runtime failure:** `execution_failed → analyzing` (category `gauss_runtime_error`); routes through that workflow's `failed` handling — debugging evidence, not model-invalidity claims.
- **Analysis after timeout:** `execution_failed → analyzing` (category `timeout`); routes through that workflow's `timed_out` handling — partial evidence, not a code-is-wrong claim.
- **Analysis after missing expected output:** occurs within the `execution_completed → analyzing` path (execution itself succeeded); the discrepancy is disclosed as part of that interpretation, not as a separate failure category requiring its own state.
- **Analysis when only output metadata exists:** the ordinary path; the Analysis Router and Response Composer apply the `output_files`-is-not-content boundary (Invariant 9, §17) regardless of which execution outcome produced the metadata.
- **Analysis failure:** `analysis_status` is set to `failed`, but the transition to `completed` (§4, transition 16) still occurs — analysis failing does not strand the instance. The raw `execution_result_reference` remains intact and is disclosed instead of an interpretation.
- **Transition to report generation:** `analyzing → report_generating` (§4, transition 15), gated by `report_inputs_available` — only when a report/summary was actually requested.
- **Report-generation failure:** `report_status = failed`; the transition to `completed` (§4, transition 17) still occurs, with the plain execution-aware summary fallback (per `workflows/report-generation.md`'s own fallback rule) substituted for the report.
- **Preservation of validated execution evidence:** restated as an explicit guarantee (also §12): neither an analysis failure nor a report-generation failure ever mutates `execution_result_reference`, `validation_outcome`, or `failure_category` — these three fields, once set at the `executing → execution_completed`/`execution_failed` transition, are **immutable for the remainder of this instance's lifecycle**, full stop.

## 14. Terminal and Resumable Semantics

| State | Terminal per request? | Resumable within the same instance? | Resumable only via a new request? |
|---|---|---|---|
| `advisory` | No — it's not a request state at all | N/A | N/A |
| `collecting_inputs` | No | Yes | — |
| `proposed` | No | Yes | — |
| `awaiting_confirmation` | No | Yes | — |
| `confirmed` | No | Not once frozen — the only forward path is `executing` | — |
| `executing` | No | No — resolves to `execution_completed`/`execution_failed` | — |
| `execution_completed` | No | No — proceeds to `analyzing` | — |
| `execution_failed` (non-malformed) | No | No — proceeds to `analyzing` | — |
| `execution_failed` (malformed) | **Yes** | No | Yes |
| `analyzing` | No | No — proceeds to `report_generating`/`completed` | — |
| `report_generating` | No | No — proceeds to `completed` | — |
| `completed` | **Yes** | No | Yes |
| `cancelled` | **Yes** | No | Yes |
| `blocked` | **Yes** | No | Yes |

**Recoverable after missing input:** yes, within the same instance — `collecting_inputs` simply remains until inputs are complete (§11's "Missing inputs" row).

**Recoverable after user rejection:** no, within the same instance — rejection reaches `cancelled` (terminal); recovery is a new request.

**Recoverable after blocking safety outcome:** no, within the same instance — `blocked` is terminal; recovery is a new request with a materially different plan.

**Recoverable after helper failure:** no, within the same instance, for any post-invocation failure category (helper/tool invocation failure, timeout, GAUSS runtime error, malformed result) — all terminal for that instance; recovery is a new request.

**Recoverable after process restart:** no, within the same instance, if the restart occurred during `executing` with an ambiguous outcome — treated as `unknown` and unresolved, per §8/§15; recovery is a new request.

**Resolution of `cancelled → collecting_inputs`, as explicitly required:** this document determines the answer is **(c) — the original notation was misleading shorthand, and it is removed** in favor of explicit request-identity boundaries, per the option the task itself steered toward ("prefer explicit request identity boundaries"). It is **neither** (a) a true same-instance transition (that would resurrect a terminal state, violating Invariant 5) **nor** (b) framed as "creation of a new request under the same session" in a way that implied it was still a state-machine *transition* — it is simply **not a transition at all**. What actually happens is: the `cancelled` instance remains cancelled, permanently and unmodified; if the user wants to proceed, an entirely new `canonical_request_id` begins its own lifecycle, starting at `collecting_inputs` (or `proposed`, if the new request happens to be immediately complete), within the same `session_identifier`. This new instance may, for user-facing continuity, reference the cancelled instance's `canonical_request_id` as informal lineage (mirroring `planning/v0.31.0-runtime-orchestration-design.md`'s "Rerun history" note about a lightweight predecessor reference), but this is a *data* relationship between two instances, not an *edge in the state graph* of one. The identical resolution applies to the removed `blocked → collecting_inputs`, `execution_failed → collecting_inputs`, and `completed → collecting_inputs`/`completed → advisory` notations.

## 15. Session Boundaries

Fail-closed behavior, for every scenario named:

- **Session loss:** any state-owned data (§3) not independently confirmed to still exist is treated as absent; no transition may be authorized based on assumed-but-unverified prior state.
- **Process restart:** an instance found `executing` (or between `confirmed` and `executing`) at restart, with no confirmed outcome, is treated as `unknown`/unresolved — no automatic resumption, no automatic retry (§8).
- **Expired transient state:** any state-owned data past a reasonable "this session is likely still active" boundary is treated as no longer reliable — the precise boundary/timeout is an unresolved policy question (§21), but the default posture (per the canonical request contract's own confirmation-expiry stance) is to fail closed on doubt.
- **Missing confirmation evidence:** if `confirmation_event_reference` cannot be independently verified, `confirmation_status` is treated as `none`/`stale`, never assumed `accepted`.
- **Missing execution record:** if `execution_result_reference` is claimed to exist but cannot be retrieved, the instance is treated as if no result exists — never assumed successful.
- **Recovered request without reliable state:** treated as unusable; a new request is required rather than attempting to reconstruct or guess the missing fields.
- **Request-hash mismatch:** if a recovered `request_hash` does not match a freshly recomputed canonicalization of the same nominal fields, the mismatch itself is treated as disqualifying — the request is stale, full stop, regardless of how small the apparent discrepancy.
- **Result discovered without invocation record:** an `execution_result_reference`-shaped object found without a corresponding `helper_invocation_identifier` is **not** trusted as this instance's real result — it is treated as unverifiable and disclosed as such, never silently adopted.
- **Invocation record discovered without result:** a `helper_invocation_identifier` found without a corresponding `execution_result_reference` is treated as an interrupted/unknown invocation (per "process restart," above) — not retried, not assumed to have failed or succeeded either way.

**Explicit statement, as required:** this document does **not** assume cross-session confirmation reuse anywhere — every scenario above defaults to treating unverifiable state as absent, consistent with the canonical request contract's own "not reusable across sessions" rule (§8 of that document) and Invariant 7 (§17).

## 16. Concurrency and Duplicate Prevention

Conceptual behavior only — **no locks, queues, databases, or idempotency keys are implemented by this document.**

| Scenario | Deterministic precedence rule |
|---|---|
| Two confirmation messages for the same displayed plan | The first genuinely matching confirmation (per §6's guards) is authoritative; a second, redundant confirmation for an already-`confirmed`/`executing` instance is a no-op, not a second authorization. |
| Two controller workers (a hypothetical multi-process/multi-worker hosting scenario) | Not designed for in this phase — this document assumes a single logical owner of `current_state` per instance (§21, "cross-process locking" remains an open, unaddressed question). |
| Repeated delivery of the same event (e.g., a duplicated "user confirmed" message) | The `transition_sequence_number` (§3) provides the conceptual basis for detecting and ignoring an exact-duplicate event; the second delivery of an already-applied event is a no-op. |
| Duplicate helper-launch attempts | Refused by `request_not_already_executed` (§6) — at most one `helper_invocation_identifier` per `canonical_request_id`, ever. |
| Simultaneous cancellation and execution | Precedence: if the `confirmed → executing` transition has already been authorized (§4, transition 10) at the moment a cancellation arrives, the cancellation is treated as "during execution" (§10) — it does not retroactively prevent an already-authorized invocation. |
| Simultaneous result and cancellation events | The result, once genuinely returned by the synchronous call, is always retained and disclosed (§9, §10) — a concurrent cancellation event does not cause the result to be discarded. |
| Stale UI or conversation state | Any user action referencing a `request_hash` that no longer matches the instance's current state is treated per §6's `request_unchanged` guard — rejected as stale, not silently accepted. |
| Reordered events | The `transition_sequence_number` provides the conceptual ordering basis; an event that would represent an out-of-order transition (for example, a "confirm" arriving after a "cancel" was already processed) is rejected, since `cancelled` has no valid exits (§5). |
| Delayed helper result | If a result arrives for an instance that has already been abandoned/treated as `unknown` due to an interruption (§15), the late result is **not** silently adopted into a live instance — it is, at most, logged for diagnostic purposes as an orphaned/unverifiable result (§15's "result discovered without invocation record" is the closest-matching fail-closed treatment). |

## 17. Invariants

1. No execution without a frozen canonical request.
2. No execution without valid confirmation tied to the current request hash.
3. At most one helper invocation per confirmed request.
4. No automatic retry or rerun.
5. Terminal requests are never resurrected.
6. State loss fails closed.
7. Confirmation cannot be reused across requests or sessions.
8. Downstream failures (analysis, reporting) do not rewrite execution evidence.
9. Output metadata is not output-file content.
10. Execution success does not prove methodological validity.
11. GUI `gauss.exe` is never substituted.
12. Environment mismatch blocks execution.
13. Ambiguous script identity blocks execution unless a later approved policy resolves it.
14. Cancellation during a synchronous helper call does not imply process termination.
15. A rerun is always a distinct request with fresh review and confirmation.
16. Confirmation consumption is monotonic — once consumed, it never reverts to valid (§7).
17. Malformed results never enter analysis as valid execution evidence (§12).
18. Every state transition is authorized by the State Machine component alone; no other component mutates `current_state` directly (§1).
19. All 19 Failure Taxonomy categories route distinctly — none are collapsed into a generic outcome (§11).
20. A helper `execution_status` value determines orchestration state only; it never independently constitutes a methodological or safety claim beyond what it literally reports (§9, restates 10).

**Whether confirmation is required:**

|---|---|

| Condition | Allowed? |
|---|---|

| Condition | Fresh request required? |

## 19. Trace Examples

All traces use **pseudodata only**; none was executed or claims to represent a real run.

**Trace 1 — Advisory-only response:**
`advisory` (stays). Guards: none applicable (no intent to execute). Confirmation: none. Helper invocation: none. Terminal state: N/A (advisory is always available). Disclosure: ordinary advisory answer.

**Trace 2 — Incomplete execution request:**
`advisory → collecting_inputs` (stays, awaiting the missing working directory). Guards: `intent_exists` passes; `inputs_complete` fails. Confirmation: none. Helper invocation: none. Terminal state: none yet. Disclosure: Pattern C.

**Trace 3 — Eligible request, confirmed, successfully executed:**
`advisory → collecting_inputs → proposed → awaiting_confirmation → confirmed → executing → execution_completed → analyzing → completed`. Guards: all pass in sequence. Confirmation: requested at `awaiting_confirmation`, accepted at `confirmed`, consumed at `executing`. Helper invocation: exactly one, returns `completed`. Terminal state: `completed`. Disclosure: Pattern E, with methodology caveats per Invariant 10.

**Trace 4 — Confirmation rejected:**
`... → proposed → awaiting_confirmation → cancelled`. Guard: user declines (no guard failure — this is a valid user-directed transition, §4 transition 8). Confirmation: never accepted. Helper invocation: none. Terminal state: `cancelled`. Disclosure: acknowledgment.

**Trace 5 — Request modified after confirmation:**
`... → confirmed` (attempted) → guard `request_unchanged` fails at pre-invocation validation → `confirmation_status = invalidated` → falls back toward a **new** request's `collecting_inputs`. Confirmation: invalidated, not consumed. Helper invocation: none for the original. Terminal state: none for the original instance (it simply never reached `executing`); a new instance begins. Disclosure: re-present the changed plan, request fresh confirmation.

**Trace 6 — Stale confirmation:**
`proposed → awaiting_confirmation` (hash-A displayed) → user edits before replying → `awaiting_confirmation → collecting_inputs` (same instance, §4 transition 9) → re-canonicalizes (hash-B) → `proposed → awaiting_confirmation` again. Confirmation: never attached to hash-A. Helper invocation: none. Terminal state: none yet. Disclosure: "Consent stale," re-present.

**Trace 7 — Helper unavailable:**
`collecting_inputs/proposed` → guard `helper_available` fails → `blocked`. Confirmation: never requested (blocked before `proposed` could even be reached, or blocked at `proposed` before display). Helper invocation: none. Terminal state: `blocked`. Disclosure: Advisory-Mode fallback.

**Trace 8 — Helper launch failure:**
`confirmed → executing` (attempted, process cannot launch) → `execution_failed` (`failure_category = helper_tool_invocation_failure`). Confirmation: consumed (§7). Helper invocation: attempted, did not complete. Terminal state: `execution_failed` (proceeds to `analyzing` as a tool-error record, then `completed`). Disclosure: honest tool-error disclosure.

**Trace 9 — GAUSS runtime error:**
`confirmed → executing → execution_failed (failure_category = gauss_runtime_error) → analyzing → completed`. Confirmation: consumed. Helper invocation: one, returned a `failed` result. Terminal state: `completed` (the request's own execution outcome was a disclosed failure, but the *instance* still reaches `completed` after analysis). Disclosure: Pattern F; explicitly no automatic rerun.

**Trace 10 — Timeout:**
`confirmed → executing → execution_failed (failure_category = timeout) → analyzing → completed`. Confirmation: consumed. Helper invocation: one, `timed_out`. Disclosure: Pattern G, partial output if any.

**Trace 11 — Malformed result:**
`confirmed → executing → execution_failed (failure_category = malformed_result)`. **No further transition** — this is the terminal sub-case (§12, §14). Confirmation: consumed. Helper invocation: one, structurally invalid. Analysis: not entered. Disclosure: flagged as a tool/helper problem.

**Trace 12 — Missing expected output:**
`confirmed → executing → execution_completed → analyzing` (discrepancy noted: an expected file was absent) `→ completed`. Confirmation: consumed. Helper invocation: one, `completed`. Disclosure: state plainly the expected output was not found; do not assume it exists.

**Trace 13 — Cancellation before launch:**
`... → confirmed` → user withdraws before invocation is attempted → `cancelled`. Confirmation: had been accepted, but the instance never reaches `executing` — treated as a pre-invocation cancellation (§10). Helper invocation: none. Terminal state: `cancelled`.

**Trace 14 — Cancellation during execution:**
`confirmed → executing` (cancellation requested while in flight) → the synchronous call still returns → `execution_completed`/`execution_failed` → `analyzing → completed`, with `cancellation_status` recorded but the result still disclosed honestly. Disclosure: the synchronous-call limitation is disclosed explicitly.

**Trace 15 — Analysis failure after valid execution:**
`... → execution_completed → analyzing` (analysis itself fails; `analysis_status = failed`) `→ completed`. `execution_result_reference` unaffected (Invariant 8). Disclosure: raw execution evidence preserved and presented instead of an interpretation.

**Trace 16 — Report-generation failure:**
`... → analyzing → report_generating` (fails; `report_status = failed`) `→ completed`, with a plain execution-aware summary substituted. Disclosure: fallback summary, not an error dead-end.

**Trace 17 — Duplicate execution attempt:**
Original instance: `... → confirmed → executing → execution_completed → ...`. A second, duplicate invocation attempt for the same `request_hash` is proposed while the original is still `executing` (or already resolved) — the attempt is refused by `request_not_already_executed`; **no new state, no new instance** — the original instance's own state sequence is unaffected. Disclosure: the existing result is reported instead of re-invoking.

**Trace 18 — Session loss after confirmation:**
`... → confirmed` in session S1 → session ends before `executing` is reached → session S2 resumes, references the same nominal plan → per §15, `confirmation_session_valid` fails → treated as `confirmation_status = expired` → falls back to a fresh `collecting_inputs`/`proposed`/`awaiting_confirmation`/`confirmed` cycle in S2. Disclosure: re-present the plan as if new.

**Trace 19 — Rerun as a new request:**
Original instance: `... → execution_failed (gauss_runtime_error) → analyzing → completed`. User asks to fix and rerun. A **new** `canonical_request_id` begins: `advisory → collecting_inputs → proposed → awaiting_confirmation → confirmed → executing → ...`, with its own fresh guards, its own fresh confirmation, and (per §14) an optional informal lineage reference to the original's `canonical_request_id`. The original instance is never mutated or re-entered.

## 21. Open Decisions

**State semantics resolved by this contract:**

- The precise, threshold-based definition of `execution_completed`/`execution_failed`, including the malformed-result sub-case (§12).
- The removal of four pseudo-transitions in favor of explicit request-lineage relationships (§4, §5, §14).
- The atomic-consumption rule for confirmation and helper-invocation recording (§7, §8).
- The full transition inventory, guard set, failure-routing table, and cancellation-by-stage table (§4, §6, §10, §11).
- The 20-item invariant list (§17).

**Implementation mechanisms deferred (the *what* is settled; the *how* is not):**

- State persistence mechanism (in-process memory, a session-scoped store, or otherwise).
- Atomic invocation recording's concrete implementation (a single write, a two-phase commit, something else).
- The duplicate-execution store's concrete form.
- Cross-process locking, if orchestration is ever hosted across multiple processes.
- Event ordering's concrete implementation (the `transition_sequence_number` concept is settled; its generation mechanism is not).
- `session_identifier`'s source.
- Cancellation detection's concrete mechanism (how a "cancel" signal actually reaches the state machine).
- Crash recovery's concrete implementation (this document specifies the fail-closed *behavior*, §15, not the recovery *procedure*).

**Policy questions still unresolved:**

- Confirmation expiry's precise timeout/threshold (§7, §15, and already flagged in the canonical request contract's §15).
- Script fingerprinting (§6's `script_identity_trustworthy` guard currently always fails closed, per the canonical request contract's own documented gap — no mechanism is proposed here either).

- [x] Every state is fully defined, with entry/exit/data/terminal/resumable/recovery semantics (§2).
