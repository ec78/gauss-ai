# v0.28.0 - Real GAUSS Invocation Research

## Release Goal

`v0.28.0` is a focused research and verification milestone for real GAUSS command-line invocation.

The goal is to determine and document whether GAUSS can be invoked safely and non-interactively to run a `.gss` script and exit.

`v0.28.0` should:

- Research GAUSS command-line invocation options.
- Identify candidate command forms.
- Test harmless scripts in a disposable working directory.
- Verify whether GAUSS exits non-interactively.
- Verify stdout/stderr behavior.
- Verify exit-code behavior.
- Verify timeout behavior.
- Verify whether output files can be written inside the working directory.
- Document known-good and known-bad invocation forms.
- Recommend command-builder changes for `scripts/gauss_code_execution.py`.

`v0.28.0` should **not**:

- Add runtime orchestration.
- Add automatic execution by the Code Assistant.
- Install packages.
- Activate licenses.
- Access the network.
- Mutate global GAUSS configuration.
- Run destructive code.
- Run user projects or real analyses.
- Claim production-ready execution before verification.
- Change report-generation or execution-aware workflows unless documentation needs an update.

## Current State

- Environment detection works (`scripts/gauss_environment_check.py`, `v0.21.0`).
- Package inspection works (`scripts/gauss_package_inspection.py`, `v0.23.0`).
- Code execution helper exists (`scripts/gauss_code_execution.py`, `v0.25.0`), built around an injectable runner abstraction and command builder.
- Fake-runner self-tests pass (18 cases + 1 bonus case, both with and without `--validate-schema`).
- Execution-aware analysis workflow exists (`workflows/execution-aware-analysis.md`, `v0.26.0`).
- Report-generation workflow exists (`workflows/report-generation.md`, `v0.27.0`).
- Real invocation remains unresolved.
- The naive `[executable_path, script_path]` command form entered the interactive GAUSS 26 prompt and timed out, confirmed by a manual smoke test during `v0.25.0` implementation.

## Research Questions

1. What is the correct command-line syntax for running a `.gss` script non-interactively in GAUSS 26?
2. Is there a batch mode, run flag, script flag, command flag, or startup option?
3. Does GAUSS have different executables for GUI vs. terminal/batch execution?
4. Is `tgauss.exe` the correct executable for terminal execution?
5. Does invocation differ between Windows, macOS, and Linux?
6. Does invocation differ by GAUSS version?
7. Does GAUSS return meaningful process exit codes?
8. Does GAUSS write normal output to stdout, stderr, a log file, or the GUI?
9. Does GAUSS exit after script execution?
10. How does GAUSS behave if the script has a syntax error?
11. How does GAUSS behave if the script writes files?
12. How does GAUSS behave if the license or GUI prompt appears?
13. Can invocation be safely detected or configured by the helper?
14. What command form should the helper use by default, if any?
15. Should real execution require an explicit verified invocation mode?

## Research Notes

**What was inspected:**

- Repository-wide grep search across `.md`, `.py`, and `.json` files for `tgauss`, `gauss.exe`, `command line`/`command-line`, `batch`, `non-interactive`, `interactive`, `.gss`, `startup`, `console`, `terminal`, `launch`, and related terms.
- `tools/gauss_code_execution.md`'s "Command Construction Status" section (the existing documented finding from `v0.25.0`).
- `scripts/gauss_code_execution.py`'s `_default_command_builder` and its module docstring.
- `scripts/gauss_environment_check.py`'s `PLAUSIBLE_EXECUTABLE_NAMES` and `COMMON_LOCATION_TEMPLATES` (confirms `tgauss`/`tgauss.exe`, `gauss`/`gauss.exe`, `wgauss`/`wgauss.exe` as the project's existing candidate executable names, but no invocation flags).
- `experts/gauss-language/COMMAND_CATEGORIES.md`, `knowledge.md`, and `BODY_OF_KNOWLEDGE.md` for any command-line-related knowledge (none found).
- The real local GAUSS 26 installation directory (`C:\gauss26\`, referenced as an additional working directory in this environment), inspected read-only:
  - Top-level directory listing (executable names, README files, config files).
  - `C:\gauss26\README.txt` — read in full. Contains explicit "Release Notes for GAUSS Terminal Version" documentation, including a "Command line syntax" section.
  - `C:\gauss26\res\startup.install` — a template startup-file, confirming GAUSS's startup-file mechanism and the interactive `run <program>` command.
  - `C:\gauss26\gauss.cfg` — confirms `PACKAGEDIR`/`src_path`/`lib_path` configuration, no additional invocation-flag information.
  - `C:\gauss26\examples\` directory listing — example programs use the `.e` extension, not `.gss`.
  - Searched for other README/install/release-note files in the installation directory — only one relevant file (`README.txt`) found; `README.gdt.txt` and `README.vwr.txt` cover unrelated tools (the data tool and viewer).
- No GAUSS executable (`gauss.exe`, `tgauss.exe`, or any other `.exe`/installer/updater/license tool) was invoked at any point. All inspection was read-only file/directory access (`ls`, `find`, reading text files).

**Candidate forms found:**

- `tgauss -b program` — a documented batch-mode flag directly addressing the observed `v0.25.0` failure (the naive form omitted `-b`, which is plausibly *why* it dropped into an interactive prompt instead of exiting).
- `-o` (suppress sign-on banner), `-l logfile` (batch-mode log file), and `-e expression` (inline expression execution) — three additional documented flags from the same source, combinable with `-b`.

**Candidate forms considered but not supported by evidence:**

- Using `gauss.exe` (the GUI executable) for non-interactive execution — the local README explicitly separates the GUI version from the terminal version and only documents batch flags for the terminal version (`tgauss`); no evidence supports GUI-executable batch use.
- stdin-piped execution (`tgauss < script.gss`) — no local or repository source mentions this; not recorded as a credible candidate, only as a considered-and-rejected option so future research doesn't re-investigate it without new evidence.

**What could not be inspected:**

- `C:\gauss26\help\gauss.qch` and `gauss.qhc` — Qt Compressed Help binary files. These likely contain the full official GAUSS documentation (including possibly more detailed command-line reference material) but require a Qt Assistant-compatible help viewer to read; they are not plain text and were not opened. This is the single largest known documentation gap from this research pass.
- Official Aptech online/PDF documentation — not fetched in this task; this research relied entirely on local repository and local-installation sources, per the task's "local repository knowledge" and "local GAUSS installation metadata" scope.
- Whether the `-b` flag's documented behavior is identical on Windows — the `README.txt` file's header explicitly labels itself "Release Notes for GAUSS 26 and later for Linux 64-bit," but the same file (found inside a genuine Windows installation directory containing `tgauss.exe`, `gauss.exe`, and `winpostinstall.exe`) also contains a "Release Notes for GAUSS Terminal Version" section that does not itself claim to be Linux-specific and reads as a generic cross-platform reference for the terminal executable's flags. This is a real, unresolved ambiguity: the flag syntax is plausibly OS-agnostic (consistent with a single shared terminal-mode binary interface), but it was found in a document whose header targets a different OS, so it should be treated as a strong, well-sourced lead rather than a confirmed-for-Windows citation until an actual Windows smoke test confirms it.
- The exact process exit-code contract (Research Question 7) — the documentation describes batch mode "executing and exiting" and a log file, but does not state what exit code is returned on success, syntax error, or runtime error.
- Behavior on license/GUI prompts (Research Question 12) — no local documentation addresses this.
- Whether `.gss` or `.e` (or both) are valid `program` arguments to `tgauss` — the README uses the generic term "program" and the local installation's own example files use `.e`, while this project's tooling and schema assume `.gss`. This discrepancy is unresolved and should be confirmed before or during smoke testing, not assumed either way.

**What still needs manual verification:**

- Whether `tgauss -b <path>.gss` actually exits non-interactively on this development machine's real GAUSS 26 installation (the core, highest-priority open question).
- Exit-code, stdout, and stderr behavior for the `-b` candidate on success, syntax error, and runtime error.
- Whether the default batch-mode log file (`wksp/gauss.log.###`) appears inside the disposable working directory or elsewhere, and what it contains relative to stdout.
- Whether `-o` changes anything observable beyond the banner.
- Whether `.gss` files work identically to the `.e` files the local examples use.

**Next step:** this research pass found one well-sourced, untested candidate family (`-b`, optionally combined with `-o`/`-l`) directly addressing the exact failure mode observed in `v0.25.0`. The next step should be **safe smoke testing** of this candidate (see "Recommended Smoke-Test Candidates" below), not further documentation research — the documentation gap that remains (the Qt help files, official online docs) is unlikely to be more authoritative than this GAUSS-shipped, installation-local release-notes file for basic batch-mode flag syntax, and a real smoke test can resolve the remaining open questions (exit codes, stderr behavior, Windows applicability) faster and more conclusively than further reading.

## Safe Smoke-Test Design

**Safe smoke-test policy:**

- Use only a disposable working directory created specifically for the test, never a directory containing real user files or projects.
- Use only harmless, trivial scripts with no destructive operations, no network calls, no package installation, and no license-activation triggers.
- Always run under a bounded timeout, using the same timeout-guard discipline `scripts/gauss_code_execution.py` already implements.
- Confirm process cleanup after every test (no lingering `tgauss.exe` or equivalent), the same way the `v0.25.0` smoke test was verified via `tasklist`.
- Record the actual observed behavior for every test, whether it succeeds, fails, or times out — do not skip recording a negative result.
- Never run a candidate command form against a real project directory, even after a candidate looks promising in isolated testing.

**Test 1 — Hello World**

```gauss
print "hello";
```

Purpose: the simplest possible non-interactive-exit check, identical in spirit to the code used in the `v0.25.0` smoke test that first surfaced the interactive-prompt problem.

**Test 2 — Script with a deliberate syntax error**

```gauss
print "hello
```

Purpose: observe whether GAUSS reports a syntax error to stdout, stderr, or a log file, and whether it still exits (rather than dropping into an interactive prompt to let the user fix the error), addressing Research Question 10.

**Test 3 — Script that writes an output file**

```gauss
output file = results.txt reset;
print "hello";
output off;
```

Purpose: confirm whether a script-created file appears in the disposable working directory as expected, addressing Research Question 11 and the output-file-writing assumption `scripts/gauss_code_execution.py`'s output-file discovery already depends on.

**Test 4 — Script with a deliberate runtime error**

```gauss
x = ones(2,2);
y = ones(3,3);
z = x + y;
```

Purpose: observe exit-code and stderr behavior for a runtime (not syntax) failure, complementing Test 2 and addressing Research Questions 7-8.

**Test 5 — Repeat of a known-good candidate across a second GAUSS installation, if available**

Purpose: check whether invocation behavior is stable across the two real GAUSS installations already referenced elsewhere in this project's environment-detection work (this development machine has multiple GAUSS versions available), addressing Research Question 6.

Each test should be run only after a specific candidate command form has research-based rationale — this section defines the test design, not a schedule for testing every candidate blindly.

## Recommended Smoke-Test Candidates

Two candidates are worth testing next, both from the same sourced `-b` family. No other candidate found during this research pass has sufficient evidentiary support to justify a live test yet.

**Candidate 1 — `tgauss.exe -b hello.gss` (highest priority)**

- **Command form:** `tgauss.exe -b <script_path>` where `<script_path>` is a disposable copy of Test 1 ("Hello World," `print "hello";`) inside a disposable working directory.
- **Why it is worth testing:** it is the only documented candidate directly addressing the exact failure mode observed in `v0.25.0` — the naive form's missing `-b` flag is the most plausible explanation for why GAUSS dropped into an interactive prompt instead of exiting.
- **Expected success signal:** the process exits on its own (no timeout needed to terminate it), stdout contains `hello` (or the batch-mode log file does, per the "Actual behavior" observation to be recorded), and no interactive prompt is observed.
- **Expected failure signal:** the process still does not exit on its own within a short bounded window (for example, 10-15 seconds — well under the helper's 30s default) and must be terminated by the timeout guard, the same outcome as the known-bad naive form.
- **Timeout:** short and strict — 15 seconds is more than enough for `print "hello";` to run if `-b` works; a longer timeout only delays discovering a failure.
- **Cleanup check:** confirm no lingering `tgauss.exe` process remains after the test (via `tasklist` on Windows), the same verification step used for the `v0.25.0` finding.
- **Interactive-mode risk:** low-to-moderate — `-b` is explicitly documented as "execute in batch mode and exit," so the documented intent is exactly to avoid the interactive prompt; the risk is that the flag is undocumented for this platform/version combination or behaves differently than described, not that it's expected to fail.

**Candidate 2 — `tgauss.exe -b -o hello.gss` (secondary, only after Candidate 1)**

- **Command form:** identical to Candidate 1 with `-o` added to suppress the sign-on banner.
- **Why it is worth testing:** if Candidate 1 succeeds, this refinement clarifies whether the banner is a stdout-parsing nuisance the helper's output capture should account for, or whether `-o` changes anything else observable.
- **Expected success signal:** same as Candidate 1, with a visibly shorter/cleaner stdout (no banner text).
- **Expected failure signal:** same as Candidate 1's failure signal, or any behavior divergence from Candidate 1 beyond the banner.
- **Timeout:** same as Candidate 1 (15 seconds).
- **Cleanup check:** same as Candidate 1.
- **Interactive-mode risk:** same as Candidate 1 — `-o` is documented as an output-formatting flag, not a mode flag, so it should not independently affect interactivity.

**If Candidate 1 fails:** do not proceed to guessing further flags. Instead, escalate to the "what could not be inspected" gap identified in Research Notes — specifically, attempt to make the Qt Compressed Help files (`C:\gauss26\help\gauss.qch`/`.qhc`) readable, or contact GAUSS/Aptech support or consult official online command-line documentation, before running additional live tests. A credible, documented candidate failing outright would mean this project's local documentation source is incomplete or platform-mismatched, and further live testing without new evidence would become guessing rather than research.

A credible candidate exists for this milestone (unlike a scenario with no leads at all), so the "contact support" escalation above is conditional — it applies only if Candidate 1 is actually tested and fails, not as an immediate next step ahead of testing.

## Recommended Command-Builder Changes (For a Future Implementation Milestone)

This section documents recommendations only — it does not implement them. Actual changes to `scripts/gauss_code_execution.py`'s `command_builder` are out of scope for `v0.28.0` and belong to a future implementation milestone once a candidate is confirmed.

- If a confirmed-good command form is found, it should become the new default inside the existing injectable `command_builder`, preserving the same isolation principle `v0.25.0` established (real-invocation behavior stays swappable without touching the rest of the helper).
- If invocation differs by platform or GAUSS version, the command builder should likely need per-platform or per-version logic, not a single hardcoded form.
- If GAUSS requires a specific flag/mode to avoid the interactive prompt, that flag should be added conditionally and tested against the existing fake-runner self-test suite to confirm no regression in helper logic.
- Any new command form must still pass through the same safety validation `scripts/gauss_code_execution.py` already performs (working-directory containment, timeout enforcement) — invocation research does not relax any existing safety control.
- Real invocation should only be enabled behind an explicit verified mode (Research Question 15) rather than becoming the silent new default the moment one candidate appears to work in isolated testing — a single successful smoke test is evidence, not proof of general reliability.

## Risks and Open Questions

- GAUSS invocation behavior may be genuinely different across platforms (Windows/macOS/Linux) and this project's research is currently limited to whatever GAUSS installations exist on this development machine (Windows).
- A candidate that appears to work in a single smoke test may not generalize — false confidence from a small sample is a real risk this milestone must guard against.
- License/GUI prompts may behave differently in different environments (interactive terminal vs. CI vs. headless), and this research cannot exhaustively cover all of them.
- Some invocation research may require official Aptech support or documentation that is not available locally, in which case the research should say so explicitly rather than guessing.
- There is a risk of scope creep from "research invocation" into "implement the fix," which this milestone must resist — implementation is explicitly deferred.
- If no safe candidate is found, the project needs a clear policy for how long real execution stays "experimental" versus being reconsidered entirely.
