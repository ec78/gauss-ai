# v0.27.0 - Report Generation Workflow

## Release Goal

`v0.27.0` plans a workflow for generating structured reports from GAUSS-related analysis artifacts.

The goal is to define how the Code Assistant should turn inputs such as:

- User question or analysis goal.
- GAUSS code.
- Execution result object, if available.
- stdout/stderr summaries.
- Output file metadata.
- User-provided output files or tables, if available.
- Expert-routed interpretation.
- Assumptions, limitations, and next steps.

into a safe, structured report.

The workflow should help produce report drafts, summaries, technical notes, diagnostic reports, or teaching-oriented explanations, while preserving evidence boundaries.

`v0.27.0` should **not**:

- Run GAUSS code.
- Fix non-interactive GAUSS invocation.
- Add runtime orchestration.
- Read output files automatically without explicit file/tool support.
- Fabricate missing results.
- Infer file contents from metadata.
- Claim methodology validity from execution.
- Generate final publication-ready conclusions without expert review.
- Install packages.
- Activate licenses.
- Access the network.
- Add automatic rerun/repair loops.

## Report Inputs

The workflow should support reports based on any combination of:

- User prompt or report goal.
- GAUSS code.
- Execution result object.
- Captured stdout/stderr.
- `output_files` metadata.
- User-provided result tables.
- User-provided charts or images.
- User-provided output files, if explicitly read by a file workflow/tool.
- Econometric context.
- Dataset description.
- Assumptions and limitations.
- Expert-routed interpretation.

**The workflow must distinguish between provided/read evidence and inferred/missing evidence.**

## Evidence Hierarchy

1. User-provided source documents, tables, code, output, or files that have been explicitly read.
2. Structured execution result fields from `gauss_code_execution`.
3. Captured stdout/stderr included in the execution result.
4. Output file metadata, but not file contents.
5. Expert interpretation based on available evidence.
6. General domain knowledge.
7. Assumptions clearly labeled as assumptions.

**Rules:**

- Do not treat output file metadata as file contents.
- Do not treat completed execution as methodology validation.
- Do not treat synthetic/fake-runner output as real execution evidence.
- Do not fabricate missing tables, plots, coefficients, diagnostics, or data descriptions.
- Label assumptions clearly.
- Include limitations when evidence is incomplete.

## Report Types

### Technical Analysis Summary

For: summarizing code and results, explaining what was run, reporting captured output, listing limitations, recommending diagnostics/next steps.

### Econometric Interpretation Note

For: coefficient interpretation, model assumptions, diagnostics, model limitations, whether conclusions are warranted.

### Debugging Report

For: failed execution, stderr/errors, package/environment issues, path/working-directory problems, timeout causes, safe retry plan.

### Teaching Explanation

For: beginner-friendly explanation of output, conceptual interpretation, step-by-step learning summary, misconception warnings.

### Product/User Workflow Report

For: impact on user workflow, time-to-value, what user can do next, what should be automated later.

**The report type should determine expert routing and level of detail.**

## Default Report Structure

1. Title.
2. Purpose / user question.
3. Evidence used.
4. Execution status, if available.
5. Key findings.
6. Interpretation.
7. Limitations.
8. Recommended next steps.
9. Appendix / technical details, if useful.

**Optional sections:**

- Model specification.
- Data notes.
- Diagnostics.
- Warnings/errors.
- Reproducibility notes.
- Output files listed but not read.
- Questions to resolve.

## Expert Routing Rules

- **GAUSS Language Expert:** code behavior, syntax/runtime interpretation, command usage, implementation details, debugging report sections.
- **Econometrics Expert:** model interpretation, assumptions, diagnostics, coefficient meaning, forecast/evaluation claims, statistical limitations.
- **Software Engineering Expert:** maintainability, performance, timeout/root-cause analysis, reproducibility, safe rerun plan.
- **Documentation Expert:** report structure, clarity, audience framing, caveats, reference-style explanation.
- **Education Expert:** learner-friendly explanation, scaffolding, conceptual sequencing, misconceptions.
- **Product Expert:** workflow impact, prioritization, value to user, what should be automated next.

**The Documentation Expert should often shape the final report structure, but technical/statistical claims must be routed to the relevant expert dimension.**

## Handling Execution Results

Require use of `workflows/execution-aware-analysis.md`.

**Rules:**

- Summarize execution status first.
- State what was captured.
- State what execution does and does not prove.
- Route interpretation through experts.
- Include warnings/errors.
- Include timeout/failure/blocking context.
- Preserve Advisory Mode when execution did not occur.
- Never claim execution occurred unless `executed: true`.
- Never claim blocked/skipped/error/unknown results produced output.

## Handling stdout/stderr

- Summarize important stdout/stderr.
- Quote only short relevant snippets.
- Do not overquote long output.
- Surface stderr warnings even with `exit_code 0`.
- Mention truncation.
- Do not invent omitted output.
- Separate captured output from interpretation.

## Handling Output Files

- `output_files` metadata means files were listed, not read.
- Do not describe CSV/plot contents unless files are explicitly read or the user provides contents.
- `created_by_execution: "unknown"` should be reported as unknown if relevant.
- Avoid exposing unnecessary sensitive local paths.
- Include an "output files listed but not reviewed" section when appropriate.
- Recommend the user provide files or use an explicit file-reading workflow if content interpretation is needed.

## Handling Missing or Partial Evidence

Define safe language for:

- Missing execution result.
- Partial stdout/stderr.
- Output file metadata without contents.
- User-provided coefficients without code.
- Code without results.
- Results without dataset context.
- Model output without diagnostics.
- Unclear user goal.

**Rules:**

- State what is missing.
- State what can still be summarized.
- Avoid invented details.
- Ask one focused clarification only if needed.
- Otherwise provide a scoped report with assumptions and limitations.

## Handling Real Invocation Limitation

- `v0.25.0` found the naive `[executable_path, script_path]` command entered the interactive GAUSS 26 prompt and timed out.
- `v0.27.0` report generation must not imply real GAUSS execution is production-ready.
- Fake-runner or synthetic execution results must be labeled as such.
- The report should include an execution limitation note if real invocation is relevant.
- Do not hide this limitation in technical appendices only if it affects user trust.

## Report Quality Rules

Reports should be:

- Structured.
- Concise enough to be usable.
- Explicit about evidence.
- Explicit about limitations.
- Clear about next steps.
- Appropriate to user audience.
- Free of fabricated results.
- Careful with statistical claims.
- Careful with causal claims.
- Clear when outputs were not read.
- Clear when execution was not performed.

## Response Pattern

1. Identify report type and audience.
2. Inventory evidence.
3. Apply execution-aware analysis if execution result exists.
4. Route technical/statistical/product claims through experts.
5. Draft report with limitations.
6. Add safe next steps.
7. Avoid unsupported claims.
