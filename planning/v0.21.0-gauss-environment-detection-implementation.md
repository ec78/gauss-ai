# v0.21.0 - GAUSS Environment Detection Implementation

## Release Goal

`v0.21.0` implements the first real read-only GAUSS tooling capability: detecting whether GAUSS is installed or discoverable. `v0.20.0` fully specified the `gauss_environment_check` contract (tool spec, result schema, five synthetic examples, and eight evaluated benchmark prompts); `v0.21.0` moves from specification to implementation for that already-specified contract.

`v0.21.0` should:

- Implement detection logic.
- Validate output against `schemas/gauss_environment_check.schema.json`.
- Preserve Advisory Mode fallback.
- Select the most current GAUSS version by default when multiple versions are available.
- Avoid executing user GAUSS code.
- Avoid inspecting installed GAUSS packages.
- Avoid activating Execution Mode.
- Avoid runtime orchestration.

This is still environment detection only. It is not package inspection or code execution.

## Current State

- `v0.20.0` specified the `gauss_environment_check` tool (`tools/gauss_environment_check.md`).
- `v0.20.0` created the result schema (`schemas/gauss_environment_check.schema.json`) and five synthetic example outputs (`examples/tools/gauss-environment-*.json`), all schema-valid.
- `v0.20.0` evaluated expected assistant response behavior with `26.x` benchmarks (`26.1`-`26.8`, 8/8 passed at 4.0).
- No actual detection implementation exists yet — there is no `tools/gauss_environment_check.py` (or equivalent), no code that inspects a real filesystem, `PATH`, or executable.
- Current assistant behavior remains advisory/verified-knowledge only, exactly as it has been since before `v0.19.0`.

## Implementation Scope

**Implement:**

- Local environment/path inspection.
- User-provided executable path handling.
- `PATH` lookup.
- Common install-location scan where reasonable.
- Candidate collection.
- Candidate accessibility checks.
- Version parsing when available and safe.
- Newest-version default selection when multiple versions are detected.

- Graceful error handling.
- An example-validation helper or test fixture, if appropriate.

**Do not implement:**

- GAUSS package inspection.
- Running user GAUSS code.
- Statistical analysis execution.
- Result reporting from execution.
- Runtime orchestration.
- License activation.
- Package installation.
- Environment mutation.
- CI changes, unless explicitly planned later.

## Default Version Selection Rule

When multiple GAUSS installations or executable candidates are detected, the tool should default to the most current/highest GAUSS version unless the user explicitly specifies:

- A preferred executable path.
- A preferred GAUSS version.
- A strict detection mode that forbids automatic selection.

**Example:** if GAUSS 24, GAUSS 25, and GAUSS 26 are detected, select GAUSS 26 as the default execution candidate.

**Selection priority:**

1. User-provided executable path, if valid and accessible.
2. User-specified GAUSS version, if provided and found.
3. Highest detected GAUSS version.
4. If versions cannot be determined, use a documented deterministic fallback or return `ambiguous`.

Important:

- Do not silently choose among candidates if version cannot be determined and no deterministic policy applies.
- Report all candidate paths where safe.
- Report the selected candidate and the reason it was selected.
- If the newest version is inaccessible but an older version is accessible, do not silently downgrade without warning.
- If the user explicitly requests GAUSS 25, do not override with GAUSS 26.
- If candidate versions are unknown, do not pretend one is newest.

This rule extends, and does not conflict with, `tools/gauss_environment_check.md`'s existing Detection Strategy section — "user-provided path" already took precedence there; this milestone adds the concrete tie-breaking policy for the case that section left open (multiple plausible candidates with known versions).

## Detection Strategy

### User-provided path

- Highest priority.
- Validate existence and accessibility.
- If valid, select it even if a newer version exists elsewhere.
- If invalid or inaccessible, report that directly and recommend Advisory Mode unless fallback search is permitted.

### User-specified version

- Match requested version where possible.
- Example: user asks for GAUSS 25, select GAUSS 25 if found and accessible.
- If the requested version is not found, return `not_found` or advisory with next steps.
- Do not substitute another version without stating clearly.

### PATH lookup

- Search `PATH` for plausible GAUSS executables.
- Collect candidates.
- Try to infer version from path, executable metadata, or an optional version query if allowed.
- Apply the newest-version default rule if versions are known.

### Common installation locations

Consider categories, not exact hardcoded paths:

- Windows Program Files / GAUSS install directories.
- macOS Applications.
- Linux `PATH`, `/opt`, `/usr/local`, or user-local locations.
- WSL/container considerations.

Do not overclaim exact path support until implementation confirms it.

### Version detection

Two possible approaches:

- Parse version from executable path/directory name.
- An optional minimal version query, if safe.

Important:

- A version query must not run user code.
- A version query should use a timeout.
- Version query failure should not make `installed` false.
- Version unknown should remain distinct from `not_found`.
- License-related failures should be represented carefully — an unlicensed installation is not the same as a missing one.

## Candidate Selection Semantics

### found

Use when:
- One selected candidate is chosen safely.
- The candidate is accessible.
- Ambiguity is resolved either by user preference or the newest-version rule.

### ambiguous

Use when:
- Multiple candidates exist and version/preference rules cannot safely choose.
- Candidates have unknown versions and no deterministic fallback is appropriate.
- Candidates conflict in ways that require user clarification.

### inaccessible

Use when:
- A relevant candidate exists but cannot be accessed.
- A user-provided path exists but cannot be accessed.
- The newest candidate exists but is inaccessible and downgrade requires user confirmation.

### not_found

Use when:
- No plausible executable is found.

### unknown/error

Use when:
- The environment cannot be checked, or detection fails unexpectedly.

## Output Requirements

All implementation outputs must conform to `schemas/gauss_environment_check.schema.json`.

Implementation must populate: `checked`, `installed`, `accessible`, `executable_path`, `executable_candidates`, `version`, `version_known`, `platform`, `detection_method`, `detection_status`, `operating_mode_recommendation`, `can_execute_gauss_code`, `warnings`, `errors`, `next_steps`.

Implementation-specific guidance:

- `executable_candidates` should include all plausible candidates when safe.
- `detection_method` should identify whether selection came from user path, requested version, `PATH` lookup, common-location scan, version sorting, or a mix of these.
- `warnings` should include a statement that no user code was executed.
- `next_steps` should identify package inspection or an execution tool as future steps when appropriate.
- `raw_detection_details` should be minimal and privacy-conscious.

## Graceful Fallback Requirements

- Detection failure must not break the assistant.
- Missing GAUSS must return an advisory recommendation.
- Inaccessible GAUSS must return an advisory recommendation.
- Ambiguous candidates must return an advisory or clarification recommendation.
- Version-query failure must not erase an otherwise plausible executable.
- The assistant can still write, explain, review, document, teach, and product-frame GAUSS work without detection.

## Safety Requirements

- Read-only inspection.
- No user GAUSS code execution.
- No package inspection.
- No file modification.
- No environment mutation.
- No license activation.
- No package installation.
- No long-running commands.
- Timeouts for any executable metadata/version query.
- Structured errors.
- No hidden fallback to another executable when the user specified one.
- No false execution claims.

## Testing Strategy

Unit-test-style cases:

- No GAUSS found.
- One candidate found.
- Multiple versioned candidates found: 24, 25, 26 → selects 26.
- User specifies GAUSS 25 while 26 exists → selects 25.
- User provides an explicit path → selects the explicit path.
- Explicit path inaccessible → inaccessible/advisory.
- Newest version inaccessible, older accessible → warning/clarification, no silent downgrade.
- Multiple candidates with unknown versions → ambiguous.
- Version unknown but candidate found → `found` with `version_known: false` if unambiguous.
- Unexpected detection error → error/advisory.
- Schema validation passes for all returned result shapes.

Example fixture strategy:

- Synthetic filesystem fixtures or mocked path discovery.
- Mocked `PATH` lookup.
- Mocked platform labels.
- Mocked version query.
- No dependency on a real GAUSS installation for tests.

## Benchmark Strategy

Do not add a new benchmark category yet unless assistant response behavior changes.

Instead:

- Keep `26.x` as response-behavior benchmarks — they test what the assistant says about detection results, not the detection code itself.
- Add implementation tests separately for detection function behavior (see Testing Strategy above); these are code-level unit tests, not manual-evaluation benchmark prompts.
- Consider adding a `27.x` category later only if the Code Assistant workflow is integrated with actual tool output — at that point there would be real assistant responses to real (not synthetic) detection results worth evaluating.
