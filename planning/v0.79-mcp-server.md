# v0.79.0 — MCP Server: Design

## 1. Goal and scope

Expose `gauss-ai`'s two existing subsystems — the conversational assistant (`gauss_conversation_engine.ConversationEngine`, including the v0.78.0 controlled execution handoff) and the full guided repair pipeline (`gauss_code_assistant_cli.InteractiveMvpAdapter`) — as a local MCP (Model Context Protocol) server, so other MCP clients (Claude Code, Claude Desktop) on the same machine can call them as tools over stdio. Both subsystems are in scope; the execution handoff is a genuine bridge (a real, approved GAUSS invocation can happen through it), not advisory-only. Distribution is via this repository: a new optional dependency group, a new console script, and a Claude Code plugin wrapper.

This is a transport-layer addition only. The repository's governing constraint — no safety-relevant decision (readiness, eligibility, approval) may be computed or overridden by a model — applies exactly as it does to every other front-end. The new module adds no new decision logic anywhere.

## 2. Phase 1 findings (repository review)

- **`ConversationEngine.ask(question: str) -> AnswerResult`** (`gauss_conversation_engine.py`) is the single-turn entry point for the whole conversational subsystem — intent classification, grounding, generation gating, code extraction, and the full pre-execution validation chain (culminating in `handoff_readiness: ReadinessResult | None`) all happen inside this one call. It must be wrapped whole. Exposing its internal primitives (doc lookup, syntax validation, etc.) as separate tools would hand a safety-relevant judgment (is this code ready?) to whichever model is driving the calling MCP client — exactly what this repository's deterministic-by-design rule forbids.
- **The execution handoff is two human round-trips, not three.** `gauss_ai_chat._run_execution_handoff_flow` (v0.78.0) shows the real shape: step 1 (`create_execution_handoff_request`, render, wait for yes/no) is the only point needing a fresh human round-trip; step 2 (`create_execution_handoff_approval` + `store.record`) and step 3 (`select_helper` + `execute_execution_handoff`) run back-to-back once a decision is in hand. `gauss_ai_chat._execution_offer_eligible(result)` — `result.handoff_readiness.state == "handoff_candidate" and len(result.generated_code) == 1` — is the existing, exact gate for whether an offer should even be shown; it is imported and reused directly here rather than duplicated, despite its leading underscore, so the two front-ends can never silently drift apart on this specific boolean.
- **`InteractiveMvpAdapter.handle_line(line: str) -> tuple[bool, list[str]]`** (`gauss_code_assistant_cli.py`) is explicitly designed to be driven by something other than a terminal loop ("Tests call `handle_line(...)` directly"), already catches every internal exception and returns it as a plain output line, and already accepts an optional `session_id`. `gauss_ai_guided_repair.run_guided_repair` constructs one standalone exactly the same way this module does. Because `handle_line` already does its own error-to-string mapping, one generic command-forwarding tool covers the entire ~30-command REPL vocabulary with no new error-handling code.
- **`pyproject.toml`** had no `[project.dependencies]` and no `[project.optional-dependencies]` table before this milestone — the `mcp` extra added here is the first. The base `gauss-ai` CLI remains stdlib-only; `gauss_ai_cli.py` only imports the new module lazily, inside its `mcp` subcommand, so every other subcommand is unaffected by whether the extra is installed.
- **MCP SDK verified at implementation time, not assumed**: the published `mcp` package is currently at `2.3.0`, where the v1-era `FastMCP` class was renamed to `MCPServer` (`from mcp.server.mcpserver import MCPServer`). Confirmed directly against the installed package (not from training-era memory) that `@server.tool()` registers a plain Python function unchanged — it remains directly callable with no transport involved, which is what the test file relies on — and that `server.run()` defaults to `transport="stdio"`.

## 3. New module and dependency direction

New module: `scripts/gauss_mcp_server.py` — session bookkeeping, 9 MCP tool functions, and `main()`. It imports only existing, unmodified modules (`gauss_ai_config`, `gauss_chat_provider`, `gauss_conversation_engine`, `gauss_execution_handoff`, `gauss_ai_chat` — for the shared `_execution_offer_eligible` gate — and `gauss_code_assistant_cli`) plus the `mcp` SDK. It does not import `gauss_pre_execution_validation` — every readiness/eligibility value it touches arrives pre-computed on an `AnswerResult`.

Dependency direction:

    gauss_ai_cli.py (lazy import, "mcp" subcommand)   gauss-ai-mcp (console script)
            \_______________________________________________/
                                    v
                        gauss_mcp_server.py (new)
                /              |                \
    gauss_conversation_engine  gauss_execution_handoff   gauss_code_assistant_cli
    (existing, unmodified)     (existing, unmodified)    (existing, unmodified)

## 4. Tool surface (9 tools)

**Chat** (wraps `ConversationEngine.ask`): `gauss_chat_start`, `gauss_chat_ask`, `gauss_chat_reset`, `gauss_chat_close`.

**Execution handoff** (wraps `gauss_execution_handoff.py`; the real execution bridge): `gauss_execution_prepare` reads the session's own last `(code, readiness_state)` pair — never a caller-supplied argument, so an MCP client cannot assert its own readiness verdict — and returns the exact code/runner/executable/timeout/digest for the human to review. `gauss_execution_decide` parses the human's yes/no text with the existing narrow parser, and on approval immediately records the approval and invokes the existing adapter exactly once.

**Guided repair** (wraps `InteractiveMvpAdapter`): `gauss_repair_start`, `gauss_repair_command` (one REPL command per call — covers the entire command vocabulary, errors included), `gauss_repair_close`.

## 5. The server-operator real-GAUSS gate

Real GAUSS execution (`runner="gauss"`) requires the server process itself to have been started with `GAUSS_AI_MCP_ALLOW_REAL_GAUSS=1` in its own environment — read fresh from `os.environ` at `gauss_execution_prepare`/`gauss_repair_start` time, never from a tool-call argument. This is in addition to, not instead of, the existing per-request digest/approval flow: an MCP client is one step further removed from the human at the keyboard than a terminal user typing `--runner gauss` directly, so this milestone adds one deliberate, server-operator-controlled gate on top. The gate removes only the server-side refusal — it does not, and cannot, bypass the existing adapter's own environment probe or executable allowlist (verified in `test_gauss_mcp_server.py` by enabling the gate against a nonexistent executable path and confirming the outcome is `INFRASTRUCTURE_FAILURE`, never a launched process).

## 6. Session lifecycle

Two independent, process-local, in-memory registries (`ChatSession`, `RepairSession`), server-assigned `uuid4().hex` keys by default with an optional caller-supplied `session_id` — the same non-durable, no-persistence shape as `ExecutionHandoffApprovalStore`/`ApplicationApprovalStore`. An `atexit` hook closes every live repair session's adapter (releasing its real `tempfile.TemporaryDirectory`/SQLite state) on process exit, since an abrupt stdio disconnect has no terminal EOF to trigger the REPL's own cleanup path.

## 7. Efficiency choices

- **stdio only.** This is a local bridge for other MCP clients on the same machine; there is no remote client to justify an HTTP/SSE transport's auth/TLS/binding surface.
- **`ollama` is the documented recommended provider**, not a new default inside `resolve_chat_provider` itself (which keeps its existing `"fake"` default, used elsewhere). Routing the server's own `ConversationEngine.provider.complete(...)` call to a cloud Anthropic API when the calling MCP client is itself a Claude session would be a redundant second LLM hop for no benefit, since grounding/validation/gating are already deterministic regardless of which provider renders the final prose.
- **One long-lived `ConversationEngine`/`InteractiveMvpAdapter` per session, one config load per server process.** No tool handler re-reads `gauss-ai config` from disk or reconstructs a provider/engine per call.

## 8. Testing

`scripts/test_gauss_mcp_server.py` follows the repository's standalone `check(name, condition)` harness, is network-free, and never touches this machine's real `~/.gauss-ai/config.json`, GAUSS executable, or Ollama/Anthropic endpoint — every test pins `provider`/`runner`/`docs_root`/`workspace_parent` via explicit CLI-argument-precedence tool parameters. It skips cleanly (exit 0) when the optional `mcp` extra is not installed, so the base test suite is unaffected either way. Covers: tool registration (9 tools, called directly with no real transport); chat/repair session isolation; the execution-offer gate refusing to prepare a request with no eligible pending turn; the full handoff flow (prepare → approve → fake-runner success; decline; unrecognized-response-creates-no-approval); the `GAUSS_AI_MCP_ALLOW_REAL_GAUSS` gate (blocked by default, and — once enabled — still safely contained by the adapter's own environment probe); REPL decline-paths and `exit`/`quit` teardown via `gauss_repair_command`; and a structural source-scan proving the module never redefines `compute_handoff_readiness`, `create_execution_handoff_request`, `execute_execution_handoff`, or `InteractiveMvpAdapter`, and reuses `gauss_ai_chat._execution_offer_eligible` rather than duplicating it.

## 9. Claude Code plugin wrapper

`.claude-plugin/plugin.json` + `.mcp.json` (stdio, `command: "gauss-ai-mcp"`) plus `.claude-plugin/marketplace.json`, all in this repository, so the server can also be installed via `/plugin marketplace add`. Documented prerequisite: `pip install -e ".[mcp]"` must be run first — a plugin install does not itself run `pip`.

## 10. Known limitations (see `KNOWN_LIMITATIONS.md` for the authoritative list)

No idle-session eviction (only explicit close + the `atexit` sweep); no persistence across server restarts; single-code-block execution offers (inherited unchanged from v0.78.0); not yet exercised by a live `evaluations/` run against a real MCP client the way the CLI paths are (tracked as a follow-up manual evaluation, next sequential category after `68.x`).
