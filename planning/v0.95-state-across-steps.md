# v0.95.0 — State Across Steps: Design

The second of the three milestones toward a complete analysis workflow, agreed on 2026-11-14: v0.94 import and export, v0.95 state across steps, v0.96 the next coverage candidates (v0.93 plan §13.6; v0.94 plan §1). On 2026-11-18 the user added two items from live evaluation 86.x and the Codex pilot (`planning/evaluation-automation.md` §8):
- each input CSV's header row in `gauss_session_start`;
- a run prompt flagging an input file that was added or changed during the session.

Status: **implemented as `v0.95.0` (§9-§12).** Decisions 1-6 were taken as recommended on 2026-11-18 (§8.1); item 3.3's relaxation of the file-access constraint has the user's sign-off and is in `CLAUDE.md`.

## 1. Why

After v0.94 a client can read the user's data and write results, but every run starts empty (`KNOWN_LIMITATIONS.md`):
- A three-step analysis loads its input three times.
- A file one run wrote is not an input to the next until the user copies it into `input/` by hand.

The 85.x and 86.x clients worked around this by putting every step into one program, which makes each prompt longer and each verdict harder to reach.

The two added items come from what clients did live:
- **Column names.** A client without its own file access (the Codex pilot) cannot learn an input file's column names before a run. It guessed `female`, and the program stops in GAUSS with `G0472` "column 'female' not found" (pilot, 86.1). The Claude client read the CSV with its own tools.
- **Where the data came from.** In 86.5 the client downloaded FRED data with `curl` into `input/` and wrote an `awk`-computed trend file beside it. The user then approved a run whose prompt named both files, with digests, exactly as if they were the user's own data.

## 2. Investigation findings

- **A run is a fresh temporary directory** (`execute_execution_handoff`, `tempfile.TemporaryDirectory(prefix="gauss_ai_handoff_")`), deleted afterwards. Each input is copied in and its SHA-256 checked against the prompt's (`_stage_inputs`). Each named write that GAUSS created is copied to a new folder under `output/` (`_collect_outputs`, `_new_output_folder`). Nothing else survives a run.
- **Session state is in memory only** (`gauss_mcp_server.Session`) and lives as long as the MCP server process, which is one per client window. Kept outputs are reported in the decide response (`files_kept`), but the server keeps no record of them.
- **The input listing** (`_analysis_folder_report`, v0.94 decision 7) gives names and sizes, "never their contents". It is computed at every `gauss_session_start`, so a client that starts a new session sees a fresh listing.
- **The validator resolves a read by name** against `input/` and the GAUSS `examples` folders (`FileAccessContext`). A file in `output/` is not readable: a write-then-read in one program was disclosed in 86.x (plan v0.94 §16.3 item 7).
- **`loadd`'s result is typed `matrix`** (plan v0.94 §13.4 finding 7): "the role check cannot tell a loaded table ... from a plain matrix ... without reading the file's header". That is why `x[., "Female"]` stays unread (v0.94.2, `G0117` on a plain matrix).

## 3. Proposed design

### 3.1 Input header rows (accepted 2026-11-18)

- `gauss_session_start`'s `analysis_folder.input_files` entries for a `.csv` file gain `columns`: the names in the file's first line.
  - The first line is read with at most 64 KiB, decoded as UTF-8 (BOM stripped, undecodable bytes replaced), and split with the stdlib `csv` module.
  - Each name is stripped; at most 500 names, each cut to 200 characters, with `columns_truncated: true` when either cap applies.
  - A file whose first line cannot be read gives `columns_error` with the reason, never an exception.
- **Only the header row is read, never a data row.** This changes v0.94 decision 7 ("names and sizes, never contents") to "names, sizes and the header row of a CSV". The `note` says so.
- The header is reported as written: the server does not judge whether the first line *is* a header. GAUSS's `loadd` reads the first line as names too (`loadd.rst`).
- `.xlsx`, `.xls`, `.dat`, `.gdat`, `.txt` and other types are listed without `columns` in v0.95 (decision 4).

### 3.2 Inputs added or changed during the session (accepted 2026-11-18)

- **The baseline.** The first time a server process lists an `input/` folder, it records each file's name, size and SHA-256 (files up to `MAX_INPUT_FILE_BYTES`; a larger file can never be read by a run anyway). The baseline is kept per input folder for the life of the server process, **not per session**, so starting a new session does not reset it.
- **The prompt.** When `gauss_execution_prepare` builds a file plan, each `input` read is compared with the baseline:
  - not in it → `added`;
  - a different SHA-256 → `changed`;
  - otherwise unmarked.

  The prompt's read line then says, for example, `gdp_fred.csv (6,548 bytes, sha256 …) -- added after 06:01, when gauss-ai first listed your input folder`. It states only what gauss-ai observed and never claims who wrote the file.
- **The digest.** The mark is part of the read and of the request digest, appended only when present, so every unmarked prompt and digest is unchanged.
- **A warning, not a block.** A user may legitimately add a file mid-session.
- The validation response is unchanged. The mark appears in the prompt, which is where the user decides.

### 3.3 A later run reads what an earlier run kept (needs sign-off: decisions 1-3)

The smallest state that works with how runs already execute is files, not memory:
- step 1 writes `clean.csv`;
- the user approves;
- `clean.csv` is kept under `output/<run>/`;
- step 2's `loadd("clean.csv")` reads that kept copy.

**What the server records.** After a launched run, `gauss_execution_decide` records each kept file in the server process: name, the path it was copied to, size, SHA-256, the run's `request_id` and the time. This is the provenance an approved run gives it. Only kept files are recorded, which means only names the code wrote and the prompt listed.

**What the validator does.** `FileAccessContext` gains the kept files. A bare-name read that is not in `input/` but was kept earlier in this server process resolves to that copy, with a new location, `kept`. Everything else about an allowed read is unchanged: the same call registry and the same bare-name rules.

**What the prompt shows.** `Reads (kept by an earlier run in this conversation; copied in, not changed):`, then `clean.csv (… bytes, sha256 …) -- kept by run 3f2a91c0 at 06:14`.

**Tampering.** The copy is staged and its SHA-256 is checked exactly like an input. A kept file that changed on disk after its run, for example one a client edited with its own tools, no longer matches the record and is refused: "changed after run 3f2a91c0 kept it".

**Collisions** (decisions 2 and 3):
- A name both in `input/` and kept by a run is `not_ready`, and the reason names both. Recommended: fail closed and let the user rename.
- A name kept by two runs resolves to the latest, and the prompt says which run.

**The constraint text.** `CLAUDE.md`'s v0.94 exception says "a read comes from the user-configured analysis folder's `input/` or from the GAUSS installation's own `examples` folders". It would add: "or is a file an earlier approved run in the same gauss-ai server process kept under `output/`, unchanged since". That is a relaxation of a project-wide constraint, so it is decision 1.

### 3.4 What does not change

- Nothing carries in memory between runs: no GAUSS workspace, variables or `.fmt` files, and no long-lived GAUSS process. Every run still starts a fresh `tgauss.exe -b` in a fresh directory.
- Everything else about the v0.94 file-access exception stays as it is: system-touching statements, the single-use `validation_id`, digest binding, copy-in/copy-out, and the user's folders never being opened for writing.
- `output/` in general is not readable. Only files the server itself recorded as kept by an approved run are, so a file a client drops into `output/` is not.

## 4. Scope boundary

- No variable carry (§3.4). GAUSS's own `save`/`load` of a `.fmt` would need the validator to know the types of carried names. A file read through `loadd` is already typed.
- No persistence across server restarts. The kept-file record and the baseline live in memory. A new client window starts empty, and its prompts mark every input file the user added since as unmarked (the new baseline). Disclosed.
- Header rows are not used by the validator in v0.95 unless decision 5 says otherwise.

## 5. Known limitations this design accepts

- A file the client wrote **before** the server process started is in the baseline and is not marked (§3.2). File timestamps are not trusted to cover it.
- A client can still fetch data by other routes and type the numbers into the code. The validator cannot see where a literal came from.
- Only CSV headers are reported (decision 4).
- A kept file is readable only in the server process that recorded it. To reuse a result in a later conversation, the user copies it into `input/`, as today.

## 6. Testing plan

### 6.1 Automated tests (synthetic fixtures, temp dirs, network-free)

- **Headers:**
  - a plain header, a BOM, quoted names with commas, an empty file, a file with no newline;
  - a 64 KiB first line, more than 500 columns, undecodable bytes, a non-CSV file (no `columns`).
  - A data row is never read: a fixture whose second line is a sentinel string must not appear anywhere in the response.
- **Added/changed:**
  - baseline at the first listing; a file added after gives `added`, a file rewritten gives `changed`, an unchanged file gives no mark;
  - a second session in the same process keeps the first baseline;
  - the digest is unchanged for an unmarked plan and differs when a mark is present.
- **Kept reads (if decision 1):**
  - a run keeps `a.csv` and the next validation resolves `loadd("a.csv")` to `kept`;
  - the prompt line and digest;
  - a kept file edited on disk is refused at staging;
  - a name in both places is `not_ready`;
  - two runs keeping one name resolve to the latest;
  - a file a test drops into `output/` itself is not readable;
  - a new server process (a fresh module state) has no kept files.
- **The fake runner** drives every handoff test. No test runs GAUSS.

### 6.2 GAUSS spot checks

- `loadd` on a CSV whose header has quoted names with commas and a BOM, to confirm GAUSS reads the same names `csv` gives. If they differ, the report follows GAUSS.
- A two-step chain by hand: write `clean.csv` with `saved`, then read it back with `loadd`.

### 6.3 Verdict diff

- The 1,410-program corpus with and without the synthetic analysis folder. Expected: no change at all, because headers and marks do not touch verdicts, and kept reads exist only after a run.
- The 85.x and 86.x snippets through `evaluations/tools/replay_snippets.py` against `v0.94.2`.

## 8. Decisions needed

1. **Reading what an earlier run kept** (§3.3), with the `CLAUDE.md` constraint text above? *Recommended: yes.* It is the smallest form of state that keeps every existing guarantee: digest-bound, copied in, shown in the prompt, and only what an approved run produced.
2. **A name both in `input/` and kept:** `not_ready` (recommended), or `input/` wins?
3. **A name kept by two runs:** the latest wins, and the prompt names the run (recommended), or `not_ready`?
4. **Header formats:** CSV only in v0.95 (recommended), or also `.xlsx`? `.xlsx` is readable with the stdlib through `zipfile` and XML, but needs shared-string and sheet handling.
5. **Use the header in the validator:** read `x[., "Name"]` as a column when `x` is traced to `loadd` of an input CSV whose header has exactly `Name` (case-sensitive, so 86.1's `"female"` would be a definite error)? This is v0.96's finding 4. *Recommended: keep it in v0.96*, so v0.95 changes no verdict.
6. **Baseline scope:** per server process (recommended, §3.2), or per session?

### 8.1 Decisions (2026-11-18)

The user accepted every recommendation:
1. Yes, a later run reads what an earlier run kept. `CLAUDE.md` was updated.
2. A name in both places is `not_ready`.
3. The latest run of a name wins.
4. CSV only.
5. Column names stay out of the validator until v0.96.
6. The baseline is per server process.

## 9. Implementation of 3.1 and 3.2 (2026-11-18)

### 9.1 Change

- **`gauss_mcp_server._csv_header`.** Each listed `.csv` file gets `columns`, plus `columns_as_written`, `columns_truncated`, `columns_uncertain` or `columns_error` where they apply, within the §3.1 caps. Only the first line is read.
- **`_record_input_baseline` / `_with_input_provenance`.** The first listing of an input folder in the server process is the baseline (decision 6 as recommended). `gauss_execution_prepare` marks each `input` read as `added after <when>` or `changed after <when>`, followed by ", when gauss-ai first listed this input folder".
- **`gauss_execution_handoff.HandoffFileRead.provenance`.** It is shown after the read's prompt line and bound into the digest only when present, so an unmarked plan's payload is v0.94's five fields.

### 9.2 Deviation: `columns` are GAUSS's names, not the line as written

§3.1 said to report the header "as written", and §6.2 said "if they differ, the report follows GAUSS". The spot checks show they differ.

GAUSS 26.1.4, `tgauss.exe -b`, 2026-11-18, `loadd` then `getcolnames`:

| Written | GAUSS |
|---|---|
| `My Var` | `My Var` |
| `a-b`, `a.b` | `a_b`, `a_b_2` |
| `1st` | `1st` |
| `dup,dup` | `dup`, `dup_2` |
| `"x,y"` | `x_y` |
| `café` | `caf_` |
| `"q""t"` | `q_t` |
| an empty tenth name | `X10` |
| `$s` | `_s` |
| a tab | `_` |
| `semi;c` | `semi_c` |
| ` Wage ` | `Wage` |
| `" pad "` | `pad` |
| `d,d,d` | `d`, `d_2`, `d_3` |

So `columns` applies those rules, and `columns_as_written` is added whenever any name differs.

Three cases did not follow any rule the checks could pin down, and each is flagged in `columns_uncertain` ("check with getcolnames") rather than guessed:
- `d,d,d,d_2," pad ",X2,` (seven fields) gave five columns;
- a trailing empty name was dropped;
- `Wage, "Region, US" ,LogWage` (a quote after a space) gave `CSV_ERR_DIFF_NUMBER_FIELDS` and `Wage_`, `Region_ US`, `_LogWage`.

The real 86.x files need no renaming:
- `wage_returns.csv` gives `Wage, Education, Experience, Female, Union, Region, LogWage`;
- `fred_macro.csv` gives `date, GDPC1, CPIAUCSL, FEDFUNDS, UNRATE, GS10`.

## 10. Implementation of 3.3

### 10.1 Change

- **Validator** (`gauss_pre_execution_validation`):
  - `FileLocation.KEPT` and `KeptFile(name, path, sha256, run, kept_at)`.
  - `FileAccessContext.kept_files` and `kept(name)` (case-blind, latest).
  - In `_classify_file_argument`, a bare-name read not in `input/` resolves to the latest kept copy that still exists. A name in both places is refused, and the refusal names the run.
  - Writes are unchanged.
- **Engine.** `file_access_context(..., kept_files=...)` takes plain tuples, so the server still never imports the validator.
- **Server** (`gauss_mcp_server`):
  - `_kept_files`, per output folder and per process, is filled by `_record_kept_files` from a launched run's own kept list, with SHA-256 measured right after the run.
  - `_file_context` passes the record to validation.
  - `_with_kept_provenance` refuses at prepare a kept read whose content is not what its run kept ("changed after run … kept it"), and otherwise names the run.
  - `gauss_session_start` lists `kept_files`.
  - The decide response adds `files_kept_note`.
  - The server instructions and the session note say a later run may read a kept file.
- **Handoff** (`gauss_execution_handoff`):
  - `kept` reads are copied in and checked like inputs (`_COPIED_LOCATIONS`).
  - `_collect_outputs` does not report them as created files.
  - The prompt shows them as their own group: "Reads (kept by an earlier run in this conversation; copied in, not changed):".
