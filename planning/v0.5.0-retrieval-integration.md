# v0.5.0 Retrieval Integration and Response Quality Plan

## 1. Release Goal

`v0.4.0` proved that a local-first command documentation lookup script can find official GAUSS command pages and extract enough evidence to answer specific, previously-unresolved questions (exact syntax, intercept behavior, not-found behavior, control-structure defaults) instead of deferring to the user.

`v0.5.0` moves from "the lookup script works when run manually against a pilot command" to "the Code Assistant behaves consistently as if retrieval-backed evidence is always the basis for command-specific claims." Concretely, this milestone should prove:

- The Code Assistant follows a consistent, repeatable response pattern whenever command-specific syntax, defaults, return values, or behavior matter — not just for the two pilot commands already tested.
- The assistant handles all four realistic retrieval outcomes (docs found and complete, docs found but incomplete/truncated, docs ambiguous, docs missing/unavailable) in a well-defined, non-inventive way.
- Responses that use retrieved evidence for a translation or debugging task also include a concrete validation step, closing the gap identified in the `v0.4.0` evaluation of Prompt 11.1.
- Retrieval-backed behavior generalizes beyond `olsmt` and `strindx` to a broader pilot set.

## 2. Scope

- Define and document standard retrieval-backed response patterns for the task modes where exact command behavior matters most: Code Translation, Debugging, Code Generation, and Documentation.
- Define explicit rules for when command-specific documentation retrieval is required versus when category-level or general knowledge is sufficient.
- Define handling for each retrieval outcome the prototype can already report: docs found (`status: found`), docs found but ambiguous (`status: ambiguous`), docs not found (`status: not_found`), and docs found but extraction incomplete (non-empty `unresolved_questions` or `extraction_warnings` on an otherwise `found` match).
- Add a validation-step requirement to response guidance for Code Translation and Debugging modes when the response includes retrieval-backed code (for example, comparing translated output against the source language's result, or suggesting one runnable check tied to the specific claim just verified).
- Address the specific `v0.4.0` evaluation weaknesses and follow-ups (Section 6, "Response Behavior Improvements" below) rather than only adding new unrelated capability.
- Broaden pilot command coverage beyond `olsmt` and `strindx` to at least one additional category (see Section 10).

## 3. Non-Goals

- Full semantic search over documentation.
- A hosted or shared retrieval service.
- Full GAUSS runtime execution or code validation by actually running GAUSS.
- Replacing official GAUSS documentation as the authoritative source.
- Indexing every GAUSS command; pilot expansion stays small and evaluated, not exhaustive.

## 4. Required Deliverables

- Updated `workflows/command-documentation-retrieval.md` (or a new companion workflow) defining the four-outcome handling rules from Section 6 below, so response behavior is specified once and reused rather than re-derived per evaluation.
- Updated `prompts/code_assistant_system.md` and/or `agents/code-assistant/task_modes.md` to require a validation step whenever a Code Translation or Debugging response relies on retrieval-backed claims.
- A short curated command note for `strindx` in `experts/gauss-language/commands/`, matching the existing `olsmt.md` pattern, per the `v0.4.0` follow-up.
- At least one new retrieval example under `examples/retrieval/` for a command outside the `olsmt`/`strindx` pilot pair (see Section 10).
- Extraction improvement in `scripts/command_doc_lookup.py` so `olsmt`'s full `olsmtOut` field list is captured instead of truncating after `out.b` (or, if that proves difficult, an explicit multi-part extraction fallback that still avoids inventing untruncated content).
- New benchmark prompts covering ambiguous-match handling, incomplete-extraction handling, and retrieval-unavailable handling (Section 8), added to `evaluations/benchmark-prompts.md`.
- Manual evaluation runs for the new benchmark prompts, following the existing `evaluations/runs/` pattern.
- Updated `evaluations/runs/INDEX.md`, `evaluations/benchmark-coverage.md`, and `CHANGELOG.md` reflecting the above.
- A `v0.5.0` readiness checklist, following the `v0.4.0` precedent, before this milestone is proposed for tagging.

## 5. Response Behavior Improvements

Concrete, testable changes to how the Code Assistant should respond, derived directly from `v0.4.0` evaluation findings:

- **Add a validation step to retrieval-backed translation responses.** Run 001 (Prompt 11.1) scored only 2/4 on Testing or Validation because the `olsmt` translation did not suggest comparing `out.b` against R's `coef(model)`. Going forward, any translation response that presents retrieval-verified GAUSS code as a replacement for source-language code should suggest one concrete comparison or check.
- **Show both the found and not-found branches in retrieval-backed examples.** Run 002 (Prompt 11.2) only demonstrated the not-found (`idx == 0`) branch for `strindx`. Examples built from verified syntax should show the normal case and the edge case being asked about, not just the edge case, when both are cheap to show.
- **Make illustrative-only command mentions explicit.** Run 003 (Prompt 11.3) noted that naming `olsmt`/`strindx` as generic examples of "the kind of candidate this applies to" could read as if their syntax were being asserted for the current unnamed command. Response guidance should require an explicit disclaimer when a previously-verified command is named purely as an illustration, not as the answer to the current question.
- **Report incomplete extraction as an unresolved question, not silently omit it.** All three `v0.4.0` runs correctly flagged truncated or missing fields (e.g., `olsmtOut` members beyond `out.b`) as unresolved rather than guessing. This behavior should be codified as a rule (Section 6) so it survives beyond the specific evaluated prompts.

## 6. Retrieval Decision Rules

Building on `workflows/native-command-selection.md` and `workflows/command-documentation-retrieval.md`, `v0.5.0` should make the following explicit and testable:

**When command-specific docs are required (not just category discovery):**
- Exact argument names, order, or optional-argument syntax are requested or needed for runnable code.
- Default values or control-structure fields matter to the answer (for example, intercept/constant defaults, missing-value handling modes).
- Return value structure or field names are requested or needed to consume the command's output.
- The user asks to compare behavior against another language or tool (translation), where a wrong default could silently produce different results.

**When category discovery alone is sufficient:**
- The user is asking whether a native command exists at all for a task category, with no claim about exact syntax.
- The response is explicitly scoped as "candidate for further verification," matching Prompt 11.3's expected behavior.

**Handling each retrieval outcome:**

| Outcome | Script signal | Required response behavior |
|---|---|---|
| Docs found, extraction complete | `status: found`, empty `unresolved_questions` | Present verified syntax/behavior, cite the source file, proceed with a concrete example and a validation step. |
| Docs found, extraction incomplete | `status: found` with non-empty `unresolved_questions` or `extraction_warnings` | Present only the fields actually extracted; explicitly list what remains unverified (e.g., a truncated struct field list); do not fill gaps from general knowledge. |
| Docs ambiguous | `status: ambiguous` | State that multiple candidate pages matched, list them, and ask the user to confirm which one applies (or pick the most likely one only if the user explicitly accepts that ambiguity). Do not silently pick the first match. |
| Docs missing / lookup unavailable | `status: not_found` or `status: error`, or no retrieval tool available in context | State plainly that command-specific verification could not be performed, name the category-level candidate if one exists, and offer the manual retrieval step (`scripts/command_doc_lookup.py <command> --docs-root <path>`) rather than guessing syntax. |

## 7. Evaluation Plan

- Re-run Prompt 11.1 after the validation-step improvement lands, to confirm the Testing or Validation score improves without regressing other dimensions.
- Add and run new benchmark prompts for ambiguous-match, incomplete-extraction, and retrieval-unavailable handling (Section 8), since none of the three `v0.4.0` runs exercised a true ambiguous or missing-docs case end-to-end.
- Evaluate at least one command from a category other than modeling/string-handling to test whether retrieval-backed response quality generalizes (Section 10).
- Continue applying `evaluations/scoring.md` with `N/A` dimension handling; expect Dimension/Numerical Awareness, Maintainability, and Testing/Validation to remain frequently `N/A` for pure retrieval-explanation prompts, as seen in `v0.4.0` runs.
- Keep evaluation run files immutable once written, consistent with `v0.4.0` practice; corrections happen via new runs, not edits to old ones.

## 8. Candidate New Benchmark Prompts

Proposed additions to the "Retrieval" category in `evaluations/benchmark-prompts.md` (stable IDs to be assigned at benchmark-file update time, tentatively 11.4-11.7):

- **11.4 — Ambiguous command match.** Present a command name where the local docs checkout plausibly contains more than one matching `.rst` candidate (or simulate this by lowering `--max-results` scoring separation). Expected behavior: the assistant reports ambiguity and lists candidates instead of silently picking one.
- **11.5 — Incomplete extraction acknowledgment.** Ask a question whose answer depends on a field known to be truncated in the current extraction (for example, an `olsmtOut` member beyond `out.b`). Expected behavior: the assistant states what is verified, states what is not, and does not guess the missing field.
- **11.6 — Retrieval unavailable.** Ask a command-specific syntax question when no local docs root is available (or the lookup tool cannot be run in the current context). Expected behavior: the assistant says verification could not be performed and avoids exact syntax, rather than falling back to general knowledge silently.
- **11.7 — Validation-step compliance in translation.** Repeat a retrieval-backed translation prompt (similar to 11.1) and specifically check whether the response includes a concrete validation step against the source language's result, closing the gap found in evaluation run 001.

## 9. Known Risks

- Adding response-pattern requirements (validation steps, found/not-found pairs, explicit unresolved-question reporting) could make responses longer than necessary for simple questions; guidance should require these only when they add real verification value, not by default on every response.
- Broadening pilot commands increases the chance of hitting a `.rst` page with unusual formatting that the heuristic extractor mishandles; this should surface as an honest `unresolved_questions` entry, not a silent bad answer, and any such case should become a benchmark rather than a bug fixed and forgotten.
- Codifying decision rules in workflow files risks drifting out of sync with actual script behavior (for example, if `scripts/command_doc_lookup.py`'s status values or fields change); the workflow update should reference the script's actual output fields rather than duplicating logic that could rot.
- Expanding benchmark coverage without also running the evaluations risks the coverage tracker implying more verification than has actually occurred; new prompts should stay `Not Run` in `evaluations/benchmark-coverage.md` until actually evaluated.
- `ROADMAP.md` currently describes `v0.5.0` as "Expanded Benchmark Suite and Automated Evaluation Support," which is a different framing than "Retrieval Integration and Response Quality." This document assumes the milestone focus is being redefined; `ROADMAP.md` will need a corresponding update before or alongside tagging (see Open Questions in the final report).

## 10. Suggested Implementation Stages

1. Update `workflows/command-documentation-retrieval.md` with the four-outcome handling table (Section 6) so response rules are defined in one place before prompt/agent files reference them.
2. Update `prompts/code_assistant_system.md` and `agents/code-assistant/task_modes.md` to require a validation step for retrieval-backed Code Translation and Debugging responses.
3. Add the `strindx` curated command note and a found-case example, closing two small `v0.4.0` follow-ups.
4. Attempt the `olsmtOut` full-field extraction improvement in `scripts/command_doc_lookup.py`; if it proves nontrivial, document the limitation explicitly rather than half-fixing it.
5. Pick one new pilot command from a category not yet tested (for example, a DataFrame or optimization command already listed in `COMMAND_CATEGORIES.md`) and run the lookup script against it to produce a new `examples/retrieval/*.lookup.json` file.
6. Add the new benchmark prompts (Section 8) to `evaluations/benchmark-prompts.md`, initially marked `Not Run` in the coverage tracker.
7. Run manual evaluations for the new prompts plus a re-run of Prompt 11.1 to confirm the validation-step improvement, recording results as new run files.
8. Update `evaluations/runs/INDEX.md`, `evaluations/benchmark-coverage.md`, and `CHANGELOG.md`.
9. Draft a `v0.5.0` readiness checklist modeled on `planning/v0.4.0-readiness-checklist.md`, including a check that `ROADMAP.md`'s `v0.5.0` description matches what was actually delivered.
