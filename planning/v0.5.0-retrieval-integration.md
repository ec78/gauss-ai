# v0.5.0 Retrieval Integration and Response Quality Plan

## 1. Release Goal

`v0.4.0` proved that a local-first script (`scripts/command_doc_lookup.py`) can find an official GAUSS command page and extract usable evidence for at least two pilot commands (`olsmt`, `strindx`), and that when a Code Assistant response is built by hand from that evidence, it passes evaluation (Prompts 11.1-11.3, all Pass).

`v0.5.0` should prove a different, stronger claim: **the Code Assistant consistently uses retrieval evidence in its responses whenever command-specific behavior matters — not merely that lookup JSON can be generated on demand.** That means:

- The behavior generalizes across task modes (translation, debugging, generation, documentation), not just retrieval-explanation prompts.
- The behavior generalizes across retrieval outcomes (found, incomplete, ambiguous, missing), not just the clean "found and complete" case exercised by `olsmt` and `strindx`.
- The behavior generalizes across more than two pilot commands.
- Retrieval-backed responses that produce code also include a concrete validation step, closing the specific gap found in `v0.4.0` evaluation run 001.

`v0.5.0` is still a prototype-stage milestone. It should not claim automated, always-on retrieval inside a live agent runtime — no such runtime exists yet in this repository. It proves *consistent response behavior when retrieval is performed*, manually or via the script, not a fully wired retrieval pipeline.

## 2. Scope

- **Retrieval-backed response patterns.** A documented, reusable pattern for how a response should be structured when it relies on command-specific documentation evidence (what to state as verified, what to cite, what to flag as unresolved).
- **Rules for when command-specific docs are required.** Explicit criteria distinguishing "category discovery is enough" from "exact docs must be retrieved before giving syntax," extending `workflows/native-command-selection.md` and `workflows/command-documentation-retrieval.md` rather than duplicating them.
- **Handling docs found, docs missing, ambiguous matches, and incomplete extraction.** All four outcomes the lookup script can already report (`status: found`, `not_found`, `ambiguous`, and `found`-with-`unresolved_questions`) need a defined, testable response behavior, not just the one outcome tested in `v0.4.0`.
- **Validation-step requirements for code translation and debugging responses.** Any retrieval-backed response that hands the user runnable code should include one concrete check (e.g., compare against the source language's result, or a small assertion tied to the specific verified behavior).
- **Improvements based on `v0.4.0` evaluation follow-ups**, specifically: add a validation suggestion to `olsmt`-style translations, add a found-case example alongside `strindx`'s not-found example, consider a curated `strindx` note, improve extraction of full `olsmtOut` fields, add more command lookup examples, and add more retrieval failure-mode benchmarks.
- **Broader pilot command coverage** beyond `olsmt` and `strindx`, spanning more than one command category (Section 9).
- **More retrieval failure-mode benchmarks** covering ambiguous matches, missing docs, and incomplete extraction, which none of the three existing Retrieval benchmarks (11.1-11.3) exercise end-to-end (Section 8).

## 3. Non-Goals

- Full semantic search over documentation.
- A hosted or shared retrieval service.
- Full GAUSS runtime execution or code validation by actually running GAUSS.
- Indexing every GAUSS command; pilot expansion stays small and evaluated, not exhaustive.
- Replacing official GAUSS documentation as the authoritative source.
- Building a full agent runtime (tool-calling loop, live retrieval invocation, memory, etc.). `v0.5.0` is about response behavior and evaluation given retrieval evidence, whether that evidence was fetched by a human running the script or pasted into context — not about wiring the script into an autonomous agent loop.

## 4. Required Deliverables

- A retrieval-backed response pattern document (new file, e.g. `workflows/retrieval-response-patterns.md`, or a clearly-scoped addition to `workflows/command-documentation-retrieval.md`) defining the answer patterns in Section 5.
- Updated `workflows/command-documentation-retrieval.md` with the outcome-handling rules in Section 6, so the four retrieval outcomes are specified once and referenced, not re-derived per evaluation.
- Updated `agents/code-assistant/task_modes.md` (Code Translation and Debugging modes) requiring a validation step when a response relies on retrieval-backed claims.
- Updated `prompts/code_assistant_system.md` if the validation-step and outcome-handling rules should affect default runtime behavior broadly, per the existing guidance in that file about when to update the system prompt versus a workflow.
- New retrieval failure-mode benchmark prompts (Section 8) added to `evaluations/benchmark-prompts.md`.
- Additional command lookup examples under `examples/retrieval/` for at least one new pilot command (Section 9).
- Updated `evaluations/benchmark-coverage.md` and `evaluations/runs/INDEX.md` once new prompts are evaluated.
- Updated `KNOWN_LIMITATIONS.md` if the scope of what's automated changes (for example, if response-pattern rules become codified in the system prompt rather than left to manual judgment).
- A `v0.5.0` readiness checklist, following the `v0.4.0` precedent, before this milestone is proposed for tagging.

This plan intentionally does not list changes to `scripts/command_doc_lookup.py` itself as a required deliverable — extending the script is out of scope for this pass (see Constraints).

## 5. Response Behavior Improvements

Expected answer pattern for each situation:

- **Verified syntax.** State the exact syntax as found in the retrieved doc, cite the source file, and do not add unverified optional arguments or overloads.
- **Verified defaults.** State the documented default value and what each accepted value means, quoting or closely paraphrasing the retrieved text rather than inferring intent from the argument name.
- **Verified return behavior.** State the documented return fields/types actually extracted; if only some fields were extracted (see below), say so explicitly rather than implying the list is exhaustive.
- **Docs found but extraction incomplete.** Present only what was actually extracted, explicitly name what's missing (e.g., "the struct's field list is truncated after `out.b`"), and do not fill the gap from general knowledge or by guessing a plausible-sounding field name.
- **Docs not found.** State plainly that command-specific verification could not be performed, name a category-level candidate if one exists, and offer the manual retrieval step (`scripts/command_doc_lookup.py <command> --docs-root <path>`) instead of guessing syntax.
- **Ambiguous matches.** State that more than one candidate page matched, list the candidates (file names/headings), and ask the user to confirm which applies rather than silently picking the top-scored one.
- **Category-only discovery.** State that the command is a plausible candidate based on category membership only, and that exact syntax, arguments, and return values are unverified until command-specific docs are retrieved.
- **Curated note available but official docs missing.** Use the curated note as a convenience summary, explicitly flag that it has not been re-verified against official docs in this session, and state the note's last-verified date/source so the user can judge its freshness.
- **Conflict between curated note and official docs.** State the conflict explicitly, prefer the official docs text as authoritative, and recommend updating or removing the stale curated note rather than silently picking one source without comment.

## 6. Retrieval Decision Rules

The assistant should:

- **Use existing lookup JSON** when a matching `examples/retrieval/<command>.lookup.json` (or equivalent retrieved evidence) is already available in context and its `status` is `found` with no unresolved fields relevant to the question.
- **Ask for or run command-specific lookup** when exact syntax, defaults, control-structure fields, or return values matter to the answer and no retrieval evidence is yet available in context — per the criteria already in `workflows/native-command-selection.md` Section 5 and `workflows/command-documentation-retrieval.md`.
- **Refuse exact syntax until docs are retrieved** when retrieval has not been attempted or has failed, rather than substituting a plausible-sounding signature from general knowledge.
- **Provide only high-level guidance** when retrieval is unavailable in the current context (no docs root, no lookup tool) but the user still needs to move forward — describe the shape of the solution and the category-level candidate without asserting exact syntax.
- **Offer manual implementation as a teaching fallback** only, per `workflows/native-command-selection.md`, and only after the native-command candidate has been named — manual code should not silently replace a native command recommendation.
- **State unresolved documentation questions** explicitly whenever extraction was incomplete, ambiguous, or failed, consistent with how all three `v0.4.0` evaluation runs already behaved; this plan aims to make that behavior a documented rule rather than an emergent pattern from three examples.

## 8. Candidate Benchmark Prompts

**Numbering note:** all of these are still retrieval-focused scenarios, so this plan proposes continuing the existing "Retrieval" category (category 11 in `evaluations/benchmark-prompts.md`) as **11.4-11.9**, rather than opening a new category 12. The repo's existing convention maps one category number to one `##` section (Code Generation = 1, Debugging = 2, ... Retrieval = 11); these prompts are all still retrieval scenarios, not a distinct new category. If a reviewer prefers a dedicated category instead (e.g., separating "response quality" from "retrieval mechanics"), 12.1-12.6 is the natural fallback numbering — that choice is left open for the benchmark-file update itself, since this plan does not modify `evaluations/benchmark-prompts.md`.

Draft prompts (final wording to be refined when actually added to the benchmark file):

- **11.4 — Docs found but extraction incomplete.** Ask a question whose answer depends on a field known to be truncated in a current extraction (for example, an `olsmtOut` member beyond `out.b`). Expected behavior: state what's verified, state what's missing, do not guess the missing field.
- **11.5 — Docs not found.** Ask for exact syntax of a command when the local docs root does not contain a matching page (or the docs root itself is unavailable). Expected behavior: say verification could not be performed and avoid exact syntax, rather than falling back to general knowledge silently.
- **11.6 — Ambiguous command match.** Ask about a command name where more than one `.rst` candidate plausibly matches (or scoring separation between top candidates is small). Expected behavior: report ambiguity and list candidates instead of silently picking one.
- **11.7 — Curated note available but official docs missing.** Ask about a command that has a short curated note (e.g., `olsmt`) in a context where the official docs root is not accessible this session. Expected behavior: use the curated note as a convenience summary, state its last-verified date/source, and flag that it has not been freshly re-verified against official docs in this session.
- **11.8 — Translation response with required validation step.** Repeat a retrieval-backed translation prompt (similar in spirit to 11.1) and specifically check whether the response includes a concrete validation step against the source language's result. Direct regression test for the 11.1 weakness.
- **11.9 — Debugging response that needs command-specific return behavior.** Present a bug report where the root cause depends on a documented return-value detail (for example, misreading a struct field, or assuming a return value that isn't what the command actually documents). Expected behavior: the assistant retrieves or requests command-specific return documentation before diagnosing, rather than guessing the cause from the field name alone.

## 9. Candidate Pilot Commands

All five are real, category-verified command names taken directly from `experts/gauss-language/COMMAND_CATEGORIES.md`. None of their syntax, arguments, defaults, or return values are asserted here — they are candidates for future `scripts/command_doc_lookup.py` retrieval and evaluation only, exactly like `olsmt` and `strindx` were before `v0.4.0`.

| Role | Command | Category (per `COMMAND_CATEGORIES.md`) |
|---|---|---|
| DataFrame command | `loadd` | Data Import and Export |
| Matrix/statistical utility | `dstatmt` | Descriptive Statistics and Computation |
| Modeling/estimation command | `glm` | Estimation Methods |
| String command | `strsplit` | String Handling |
| Control structure / nontrivial return object | `qnewtonmt` | Optimization and Solution |

`qnewtonmt` is a good fifth candidate specifically because, like `olsmt`, its category strongly suggests a paired control-structure/output-structure pattern (an existing `minimizecontrolcreate` sibling command is already listed in the same category), which is exactly the failure-prone pattern `v0.4.0` proved retrieval can help with for `olsmt`.

## 10. Risks and Open Questions

- How much response logic belongs in prompt files (`prompts/code_assistant_system.md`) versus workflow files (`workflows/*.md`)? Putting too much in the system prompt risks bloat and drift; putting too much only in workflows risks the assistant not applying it without being explicitly pointed there. This plan defaults to workflow-first, system-prompt-only-if-broadly-applicable (matching existing guidance in `workflows/manual-evaluation.md` Section 4), but this should be revisited once the new workflow content is drafted.
- Should lookup JSON be committed for every new pilot command, or only for a curated subset? Committing more raises repo size and staleness-tracking burden; committing fewer weakens the evaluation evidence trail. This plan assumes committing one new example (Section 9) is the right size for `v0.5.0`, not all five candidates at once.
- How do we prevent stale cached lookup output from being treated as current? `v0.4.0` already hit this once (the `strindx` "not found" keyword bug produced a misleading committed file). A lightweight convention (e.g., noting the generation date/command in the JSON, or re-running lookups as part of the readiness checklist) may be needed before trusting more committed examples.
- How should retrieval evidence be cited or summarized in a response — full quoted text, paraphrase with citation, or structured field list? `v0.4.0` responses mixed direct quotes and paraphrase; Section 5 above is a first pass at standardizing this, but it is not yet tested across multiple evaluators.
- Should lookup JSON have a schema or basic structural test, given it's read by both evaluation prompts and (eventually) response generation? This plan does not commit to building one yet (see Constraints — no new script features this pass), but flags it as worth deciding early in `v0.5.0` rather than after more examples accumulate.
- How should the prototype handle commands whose official documentation is split across multiple files (for example, a command plus a separate control-structure-creation function page)? None of `olsmt`, `strindx`, or the Section 9 candidates are confirmed to need this yet, but `qnewtonmt`/`minimizecontrolcreate` being separate commands in the same category makes this a plausible near-term case worth deciding on deliberately rather than discovering by accident.

## 11. Suggested Implementation Stages

1. **Planning and response patterns.** Finalize Sections 5 and 6 above into the actual workflow document(s); resolve the "prompt vs. workflow" open question enough to know where each rule lives.
2. **Benchmark prompts and evaluation cases.** Add prompts 11.4-11.9 (or 12.1-12.6, per the numbering decision) to `evaluations/benchmark-prompts.md`, initially marked `Not Run` in the coverage tracker.
3. **Additional pilot command lookups.** Run `scripts/command_doc_lookup.py` against one or more of the Section 9 candidates and commit the resulting `examples/retrieval/*.lookup.json` file(s), following the same redaction and honesty practices established in `v0.4.0`.
4. **Workflow/prompt updates.** Land the response-pattern and decision-rule updates in `workflows/command-documentation-retrieval.md`, `agents/code-assistant/task_modes.md`, and `prompts/code_assistant_system.md` as scoped in Stage 1.
5. **Manual evaluations.** Run the new benchmark prompts plus a re-run of Prompt 11.1 to confirm the validation-step improvement, recording results as new run files without editing prior ones.
6. **Readiness checklist.** Draft a `v0.5.0` readiness checklist modeled on `planning/v0.4.0-readiness-checklist.md`, including a check that `ROADMAP.md`'s `v0.5.0` description matches what was actually delivered and that `KNOWN_LIMITATIONS.md` reflects any scope changes.
