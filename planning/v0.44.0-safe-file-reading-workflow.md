# v0.44.0 Safe Workspace File Reading Workflow

## Release Goal

Implement a controlled workflow for explicitly reading supported files from a validated workspace and returning structured content evidence for later analysis — closing the gap `v0.41.0` named and `v0.42.0`/`v0.43.0` deliberately left unimplemented: workspace manifest metadata exists (`v0.42.0`) and execution now runs within a validated workspace with output provenance (`v0.43.0`), but nothing in this codebase can read a file's actual contents.

This milestone enables the sequence:

> User: "Explain the contents of results.csv."
>
> 1. Identify the workspace file.
> 2. Validate that the path is inside the workspace.
> 3. Confirm that the file is eligible for reading.
> 4. Read it through a controlled reader.
> 5. Return structured evidence.
> 6. Preserve the distinction between file content and methodological interpretation.

**This milestone does not add autonomous or automatic file reading.** Every read requires an explicit `WorkspaceFileReadRequest`; nothing in `v0.43.0`'s output-provenance registration, execution completion, or workspace-manifest population triggers a read on its own.

## Supported File Scope

Allowlisted, bounded text formats only: `.txt`, `.csv`, `.tsv`, `.out`, `.log`, `.gss`, `.dat` (the last accepted only after the same binary-content sniff every other extension also undergoes — extension alone is never sufficient). Rejected by default and out of scope for this milestone: binary files, executables, archives, images, PDFs, spreadsheets (`.xlsx`/`.xls`), and any unlisted extension. A future, separately scoped milestone would be required to add any of these.

## File-Read Request Contract

`WorkspaceFileReadRequest` (`scripts/gauss_workspace_file_reader.py`):

- `workspace_id` — the owning workspace, per `scripts/gauss_workspace.py`'s existing identity.
- `relative_path` — must be relative (never absolute) and must resolve inside the workspace's own root.
- `requested_purpose` — an audit-only, caller-supplied descriptive string; never used to authorize anything by itself.
- `expected_file_type` — the caller's own declared expectation; if supplied and it does not match the file's actual extension-derived type, the read is rejected (`file_type_mismatch`) rather than silently proceeding against a caller's stale assumption.
- `max_bytes` — an optional, caller-supplied cap; always clamped to this module's own absolute ceiling, never trusted to raise it.
- `encoding` — must be `"utf-8"`; any other value is rejected (`unsupported_encoding`) rather than silently substituted, matching the "prefer failure over incomplete/wrong content" principle applied to encoding too.
- `allow_truncation` — defaults to `False`; when `False`, a file exceeding the effective size limit is rejected outright (`file_too_large`) rather than partially returned.

## Eligibility Rules (Failure Taxonomy)

Every rejection is a structured `WorkspaceFileReadResult` with `status="rejected"`/`"error"` and a specific `error_code` — never a raised exception for an ordinary validation failure (mirroring `gauss_execution_workflow.py`'s own established "structured outcome, not an exception" convention for eligibility-shaped failures):

| `error_code` | Cause |
|---|---|
| `workspace_not_found` | `workspace_id` does not exist in the supplied registry. |
| (reused from `WorkspaceValidationOutcome.reason_category`: `deleted`, `path_escaped_root`, `ownership_mismatch`) | The workspace itself fails `WorkspaceRegistry.validate_workspace(...)`. |
| `path_not_relative` | `relative_path` was supplied as an absolute path. |
| `path_escapes_workspace` | The resolved path (traversal, or a symlink resolving outside) does not stay inside the workspace root. |
| `file_not_found` | The resolved path does not exist. |
| `not_a_regular_file` | The resolved path is a directory (or otherwise not a regular file). |
| `unsupported_file_type` | The extension is not in the allowlist. |
| `file_type_mismatch` | `expected_file_type` was supplied and does not match the actual extension-derived type. |
| `file_too_large` | The file exceeds the effective size limit and `allow_truncation=False`. |
| `binary_content_detected` | A NUL byte (or an excessive non-printable-byte ratio) was found in the read bytes, regardless of extension. |
| `decode_error` | The (untruncated) bytes could not be decoded as UTF-8. |
| `unsupported_encoding` | `request.encoding != "utf-8"`. |
| `io_error` | An unexpected OS-level error occurred during an otherwise-eligible read (`status="error"`, not `"rejected"` — a genuine unexpected fault, not a validation refusal). |

## Workspace and Path Validation

Every read reuses, rather than re-implements, `scripts/gauss_workspace.py`'s own containment logic: `WorkspaceRegistry.get_workspace(...)`, `.validate_workspace(...)`, and `.resolve_within_workspace(...)` (the same public method `v0.43.0` added for exactly this kind of external containment check). This reader never duplicates `_resolve_inside` a third time in the codebase.

## Size and Encoding Limits

- `DEFAULT_MAX_BYTES = 262_144` (256 KiB) — a conservative default sized for the kind of output artifacts (`results.csv`, `.out`/`.log` files) this milestone targets, not for arbitrary large datasets.
- `ABSOLUTE_MAX_BYTES = 5_242_880` (5 MiB) — a hard ceiling no request-supplied `max_bytes` may exceed, regardless of caller intent.
- Encoding: UTF-8 only. No fallback chain (`latin-1`, `cp1252`, etc.) is implemented in this milestone — a file that fails to decode as UTF-8 is rejected (`decode_error`), never silently reinterpreted under a guessed encoding. This is a disclosed, deliberate limitation, not an oversight.
- Truncation: disabled by default (`file_too_large` on an oversized file). When a caller explicitly sets `allow_truncation=True`, the file is read only up to the effective byte limit, `truncated=True` is set, `size_bytes`/`checksum` describe exactly the bytes actually read (never the full file's size/checksum), and a UTF-8 decode failure exactly at the truncation boundary is tolerated via `errors="replace"` (only when truncated — an untruncated file must still decode cleanly or be rejected).

## Provenance Model

`FileReadProvenance`: `workspace_id`, `relative_path`, `size_bytes` (of the bytes actually returned), `checksum` (SHA-256 of those same bytes — never the whole file's checksum when truncated), `read_at` (this module's own clock, never caller-supplied), `source_manifest_entry` (looked up from the workspace's existing manifest by matching `relative_path`, `None` if the file was never registered there — e.g. a file present on disk but never added via `add_file_to_manifest(...)`), `complete` (`not truncated`).

Provenance never mutates an execution result and is never treated as methodology validation — restated from every prior milestone's evidence/interpretation boundary (`workflows/execution-aware-analysis.md`, `workflows/report-generation.md`).

## Result Contract

`WorkspaceFileReadResult`: `workspace_id`, `relative_path`, `status` (`completed`/`rejected`/`error`), `file_type`, `size_bytes`, `checksum`, `encoding`, `content` (the decoded text, or `None` on any non-`completed` status), `truncated`, `provenance` (`None` on any non-`completed` status), `error_code`, `error_message`. **No field on this type can hold a methodology conclusion** — structurally, not just by convention; the type has no such field to accidentally populate.

## Workflow Integration

A narrow, additive integration point on `scripts/gauss_execution_workflow.py`'s `ExecutionWorkflow`: a new `read_workspace_file(...)` method that requires an explicit `WorkspaceFileReadRequest`, requires `self._workspace_registry` to be configured, and delegates entirely to `gauss_workspace_file_reader.read_workspace_file(...)`. It is never called by `propose_execution(...)`, `execute(...)`, or any output-provenance registration step — execution completion and output metadata never trigger a read on their own. A read failure (`WorkspaceFileReadResult.status != "completed"`) is a distinct kind of outcome from an execution failure and is never conflated with `ResponseReadyResult`'s own `runtime_error_detected`/`missing_expected_output` fields.

The file reader itself (`gauss_workspace_file_reader.py`) has no dependency on `gauss_runtime_orchestration.py`, `gauss_execution_adapter.py`, or `gauss_code_execution.py` — it depends only on `gauss_workspace.py`, preserving the one-way dependency direction every prior milestone in this session has maintained.

## Interpretation Boundary

Restated, not weakened: reading a file's content proves what that file contains at the moment of reading, not code correctness, not methodological or statistical validity, and not that the content was fully reviewed when `truncated=True`. A user asking whether read content "proves the model is valid" must be routed to the Econometrics Expert exactly as an execution result already is (`workflows/execution-aware-analysis.md`'s Pattern J, restated for file content).

## Security Risks

Path traversal; a symlink resolving outside the workspace; a binary file mislabeled with a text extension; an oversized file exhausting memory if read without a limit; a decode failure silently substituting the wrong encoding and producing plausible-looking garbage; a caller-declared `expected_file_type` masking an actual mismatch; treating a `source_manifest_entry` lookup miss as evidence the file is untrustworthy (it only means the file was never explicitly registered — not that it is unsafe); truncated content being presented as if it were the complete file.

## Testing Strategy

`scripts/test_gauss_workspace_file_reader.py`: successful reads (UTF-8 text, CSV, a `.gss`-adjacent output file, checksum/size reporting, provenance preservation), safety (traversal, absolute path, outside-workspace file, escaping symlink, missing file, directory, unsupported extension, binary content, oversized file, mismatched `expected_file_type`, wrong encoding), boundary behavior (output metadata never auto-reads, execution completion never auto-reads, a completed result never carries a methodology conclusion, truncation is clearly marked when it occurs), and isolation (one workspace cannot read another's files). A second file, `scripts/test_workspace_file_read_integration.py`, exercises the same set of guarantees through `ExecutionWorkflow.read_workspace_file(...)` specifically, plus the explicit-request-only boundary at the workflow layer. Every test uses only temporary directories and fake data; no test invokes GAUSS.

## Non-Goals

Automatic reading of every output file; arbitrary filesystem access; binary parsing; spreadsheet parsing; image interpretation; PDF parsing; cloud storage; uploads; persistent artifact storage; distributed execution; automatic methodology conclusions; execution helper changes.

## Readiness Criteria

- All new tests pass; no existing regression.
- Every rejection path is exercised and produces the documented `error_code`.
- No code path anywhere reads a file without an explicit `WorkspaceFileReadRequest`.
- `output_files`/manifest metadata remains distinct from content everywhere this milestone touches.
- Workflow/agent documentation updated narrowly, consistent with this contract.
- Evaluation tracking remains internally consistent; release readiness passes at default.
