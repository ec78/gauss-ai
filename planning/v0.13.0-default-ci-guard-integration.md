# v0.13.0 Default CI Guard Integration Plan

## Release Goal

`v0.12.0` prepared the local guard scripts for eventual CI use — `scripts/check_release_readiness.py` wraps the default (non-strict) evidence-validation and evaluation-tracking checks in one command, and `scripts/README.md` documents exactly which strict-mode failures are currently expected and why. `v0.13.0` takes the next, deliberately narrow step: it moves that same local guard into CI by running the default release-readiness checks automatically on pull requests and pushes. It does not add strict-mode enforcement, does not resolve or allowlist any warning, and does not change what "release-ready" means — it only makes the existing, already-documented default check run automatically instead of requiring someone to remember to run it locally.

## Suggested CI Workflow

`.github/workflows/release-readiness.yml`:

- Triggers on `pull_request` and `push` (matching the "should CI run on both" design question below — the working assumption is yes, both, since a push-only or PR-only workflow would leave a gap: pushes directly to a branch without a PR would go unchecked under PR-only, and PR-merge commits would go unchecked under push-only unless the merge itself triggers `push`).
- Checks out the repository (`actions/checkout`).
- Sets up a current, repo-compatible Python version (`actions/setup-python`) — the scripts use `from __future__ import annotations` and modern type-hint syntax in annotations only (no runtime use of `X | Y` union syntax was found), so they are compatible with a wide range of Python 3 versions; absent a pinned minimum anywhere in the repo, the workflow should use a current, actively-supported version rather than guessing a strict floor.
- Installs the one confirmed external dependency: `jsonschema` (required by `scripts/validate_lookup_evidence.py`, and therefore by `validate_all_evidence.py`). No other third-party dependencies were found across `scripts/validate_all_evidence.py`, `scripts/check_evaluation_tracking.py`, or `scripts/check_release_readiness.py` — all three otherwise use only the standard library.
- Runs `python scripts/check_release_readiness.py` — default mode, no `--strict`.
- Fails the job if that command exits nonzero (i.e., if either default check fails) — this is the command's own existing exit-code behavior; the workflow does not need to reimplement pass/fail logic.
- Does not run `--strict` and does not add a separate "warnings" step that could be mistaken for a required gate.
- Does not filter, grep, or otherwise post-process the command's output — the full output (including every warning) goes to the CI log exactly as `check_release_readiness.py` already prints it, so warnings stay visible in CI without needing a second mechanism to surface them.

## Risks and Design Questions

- **Which Python version should CI use?** No minimum is pinned anywhere in the repo today. Recommend a current, actively-supported version (for example, the same major.minor family used in this development environment) rather than the oldest theoretically-compatible one, since there's no compatibility requirement forcing an older floor and a current version gets security/bugfix support for longer.
- **Are dependencies fully standard-library, or does the workflow need installs?** Confirmed: not fully standard library. `jsonschema` is required by `validate_lookup_evidence.py` (and thus `validate_all_evidence.py`). The workflow needs one explicit `pip install jsonschema` step (or equivalent). No `requirements.txt` exists yet; introducing one is optional scope this milestone could take on but doesn't have to — an inline `pip install jsonschema` keeps the workflow self-contained without inventing a new dependency-management convention.
- **Should CI run on both push and pull_request?** Recommend yes, per the Suggested CI Workflow section's reasoning above (avoids gaps from direct pushes or PR-only merge paths) — open to revisiting if it produces redundant duplicate runs on this repo's actual branch/PR workflow.
- **Should strict checks be included as non-blocking later?** Plausible future follow-up (a separate, `continue-on-error: true`-style job that runs `--strict` and reports without failing the workflow), explicitly deferred — not in this milestone's scope per the Non-goals above.
- **How should known warnings be surfaced in CI logs without failing default checks?** Answered by construction: `check_release_readiness.py`'s default mode already prints every warning from both underlying scripts to stdout; the workflow just needs to not suppress that output (no `2>/dev/null`, no `-q`/quiet flags, no piping through a filter) for warnings to be visible in the CI log without any extra mechanism.
- **Should future strict allowlists be docs-only or config-based?** Not decided in this milestone (explicitly out of scope — see Non-goals); the current two strict-mode exceptions remain docs-only (`scripts/README.md`, `evaluations/benchmark-coverage.md`'s "Historical Tracking Exceptions" section). A machine-readable allowlist would only be justified if the number of exceptions grows enough to make manual policy-reading unwieldy, which two exceptions does not.
