# v0.78.0 — Controlled Execution Handoff: Design

## 1. Phase 1 findings (repository review)

- Starting state: `main` at `707226b` (v0.77.0 tag, pushed/released). 45 test files, all passing (baseline re-confirmed this session).
- **Authoritative execution entrypoint**: `gauss_execution_adapter.GaussExecutionAdapter.invoke(AdapterRequest)` (`scripts/gauss_execution_adapter.py`). This is already "the single controlled route from orchestration to the execution helper" — constructed with an *injected* `helper` callable (a fake in every test; `gauss_execution_adapter.load_real_helper()` for the real `gauss_code_execution.execute_gauss_code` production path). It never imports the real helper at module import time, never launches a subprocess itself, and performs its own pre-invocation guards (script-path rejection, missing code, executable allowlist, environment-still-matches probe, required-package context, duplicate-invocation) before ever calling the injected helper.
- **Precedent for exactly this kind of narrow, out-of-band reuse**: `gauss_differential_harness.RealGaussRunner` (v0.77.0) already wraps `GaussExecutionAdapter` + `load_real_helper()` directly (not the heavier `gauss_execution_workflow.ExecutionWorkflow` / `gauss_runtime_orchestration.MockOrchestrationInstance` state machine), using a fresh `tempfile.TemporaryDirectory()` per invocation as the working directory. v0.78 follows this exact precedent.
- **Why not `ExecutionWorkflow`/orchestration state machine**: `gauss_runtime_orchestration.py` + `gauss_execution_workflow.py` implement a full 13-state, durably-persisted, multi-phase machine (`CanonicalExecutionRequest`, `SafetyReviewOutcome`, `MockOrchestrationInstance`, workspace registry, rerun/session semantics) purpose-built for the file-based guided-repair pipeline's execute→diagnose→repair→verify→review loop. Reusing it for one ephemeral conversational snippet would force an inappropriate scope expansion (durable workspace registry, session boundaries, a 13-state machine for a single one-shot run) that the milestone's own "snippets only" / "do not invent persistence" scope restrictions rule out. The low-level adapter is the correct, narrower reuse point, and is already evidence-proven safe to use this way (v0.77.0's own differential harness).
- **Execution evidence**: `gauss_execution_interpreter.ExecutionEvidence` (frozen dataclass: `runner`, `gauss_ran`, `executed`, `execution_status`, `exit_code`, `stdout_chars`/`stderr_chars`, `timed_out`, `stdout_text`/`stderr_text`, ...) plus `interpret_execution(...)` (deterministic, catalog-backed explanation). `ConversationalExecutionResult` composes this type rather than re-defining it.
- **Readiness pipeline** (`gauss_pre_execution_validation.py`, v0.74–v0.77): `ExecutionEligibility` → `HandoffReadiness` (`NOT_READY` / `REVIEW_REQUIRED` / `HANDOFF_CANDIDATE`), computed by `compute_handoff_readiness(...)`, fully deterministic, no model call. Surfaced on `gauss_conversation_engine.AnswerResult.handoff_readiness` (a `ReadinessResult`) alongside `AnswerResult.generated_code` (a `tuple[str, ...]` of fenced code blocks extracted from the answer). This is the ONLY legitimate gate for creating an `ExecutionHandoffRequest`.
- **Config resolution primitives already exist** (`gauss_ai_config.py`), used by `gauss_ai_guided_repair.run_guided_repair` and reused unchanged here: `resolve_default_runner` (values `"fake"`/`"gauss"`, default `"fake"`), `resolve_gauss_executable`, `resolve_workspace_parent`, `resolve_default_timeout_seconds` (default `30.0`).
- **Approval-store precedent**: `gauss_repair_application_approval.ApplicationApprovalStore`/`ApplicationApprovalRecord` — in-memory dict, digest-bound, frozen records, boundary-statement constants. `ExecutionHandoffApprovalStore` follows this shape but adds single-use *consumption* tracking (repair-application approval has no such concept; execution approval must, since GAUSS execution is a real side effect the repair-application layer doesn't have at that step).
- **Explicit-consent precedent**: `gauss_ai_guided_repair._confirm(...)` — "the one and only place a yes/no approval decision is read." v0.78 adds a dedicated, narrower, three-way (`APPROVED`/`DECLINED`/`UNRECOGNIZED`) parser instead of `_confirm`'s two-way (`y` / anything-else-is-no) parser, because Phase 6 of the milestone brief explicitly requires that an *unrecognized* response must not be silently coerced into a decline — it must re-prompt (bounded) or cancel safely, never execute.
- **Digest precedent**: `gauss_runtime_orchestration.compute_request_hash` — SHA-256 over a fixed-order canonical JSON serialization of hash-included fields. v0.78 mirrors the algorithm (SHA-256, canonical JSON, fixed field order) but **deliberately does NOT apply that module's `\r\n`→`\n` code normalization** — the milestone brief is explicit that exact textual code binding is preferred and canonicalization must be extremely conservative. The generated code string is hashed byte-for-byte as received.

## 2. New module and dependency direction

New module: `scripts/gauss_execution_handoff.py` — pure data model, digest logic, approval store, and the pre-launch-gate/execute orchestration function. It imports `gauss_execution_adapter` (safe — no import-time side effects) and `gauss_pre_execution_validation` (for `HandoffReadiness`) and `gauss_execution_interpreter` (for `ExecutionEvidence`). It does **not** import `gauss_conversation_engine`, `gauss_chat_provider`, or `command_doc_lookup` — the builder takes primitive values (`code: str`, `readiness_state: str`, ...), not an `AnswerResult` object, so the handoff module has no reason to know about conversation/provider types at all.

Wiring point: `scripts/gauss_ai_chat.py` (the CLI-level chat orchestration loop, not the conversational engine's core intent/grounding/generation logic) gains the new capability: after an answer with `handoff_readiness.state == "handoff_candidate"` and exactly one generated code block, it recognizes an explicit user execution request, builds the request via `gauss_execution_handoff.create_execution_handoff_request(...)`, displays it, parses an explicit approval response, and — only on `APPROVED` — calls `gauss_execution_handoff.execute_execution_handoff(...)`.

Dependency direction achieved:

    gauss_ai_chat.py (conversation orchestration)
        -> gauss_execution_handoff.py (new handoff module)
            -> gauss_execution_adapter.py (existing, unmodified)
                -> gauss_code_execution.py (existing, unmodified; real helper, lazily imported)
            -> gauss_pre_execution_validation.py (existing, unmodified; readiness enum only)
            -> gauss_execution_interpreter.py (existing, unmodified; ExecutionEvidence only)

`gauss_conversation_engine.py`, `gauss_chat_provider.py`, and `command_doc_lookup.py` are **not modified** and gain no new import. The model-provider layer remains structurally execution-incapable. Structural tests (mirroring `test_gauss_differential_harness.py`'s `test_25`/`test_26` source-text-scan style) prove: (a) `gauss_execution_handoff.py` never imports `gauss_conversation_engine`/`gauss_chat_provider`/`subprocess`/`gauss_code_execution` directly; (b) `gauss_conversation_engine.py`/`gauss_chat_provider.py`/`command_doc_lookup.py` never import `gauss_execution_handoff`/`gauss_execution_adapter`/`subprocess`.

## 3. Objects

### `ExecutionHandoffRequest` (frozen dataclass)

Fields: `request_id`, `code`, `readiness_state`, `runner` (`"fake"`/`"gauss"`), `executable_path` (`str | None`), `gauss_version` (`str | None`), `timeout_seconds`, `workspace_parent` (`str | None`), `created_at`, `digest`.

Digest-bound fields (in fixed order, SHA-256 over canonical JSON, exact code text, no normalization): `code`, `runner`, `executable_path`, `gauss_version`, `timeout_seconds`, `workspace_parent`, `readiness_state`. Excluded: `request_id` (identity only), `created_at` (display-only timestamp) — mirrors the existing `compute_request_hash` convention of excluding identity/confirmation-only fields.

Built only by `create_execution_handoff_request(...)`, which requires `readiness_state == HandoffReadiness.HANDOFF_CANDIDATE.value` (raises `HandoffNotEligibleError` otherwise), non-empty code, a positive timeout, `runner` in `{"fake", "gauss"}`, and (`runner == "gauss"`) a non-empty `executable_path`. No execution, no file write, no model call.

### `ExecutionHandoffApproval` (frozen dataclass)

Fields: `approval_id`, `request_digest`, `decision` (`APPROVED`/`DECLINED`), `decided_at`, `consent_statement` (fixed boundary text). Built only by `create_execution_handoff_approval(request, decision=..., approval_id=..., decided_at=...)` — binds `request_digest = request.digest` directly off the request object, never independently supplied.

Consumption is tracked **outside** the frozen approval object, in `ExecutionHandoffApprovalStore` (an in-memory `{approval_id: consumed_bool}` map plus the record itself) — mirrors the milestone brief's explicit instruction not to mutate a frozen approval for convenience.

### `ConversationalExecutionResult` (frozen dataclass)

Fields: `request_digest`, `approval_id`, `launched` (bool), `outcome` (one of `HandoffOutcome` — the failure taxonomy, Section 5 below), `evidence` (`ExecutionEvidence | None`), `blocked_reason` (`str | None`), `result_digest` (SHA-256 over `request_digest + approval_id + launched + outcome` + a summary of `evidence`, for the audit chain).

## 4. Pre-launch gate (`_prelaunch_check`, called first thing inside `execute_execution_handoff`)

In order, fail closed on the first violation, all BEFORE any adapter call:

1. `approval.decision == DECLINED` → `DECLINED`.
2. `approval.request_digest != request.digest` → `APPROVAL_MISMATCH`.
3. Recompute the request's own digest fresh from its fields and compare to `request.digest` → mismatch → `STALE_REQUEST` (proves "same inputs ⇒ same digest" holds at the gate, not just at construction).
4. `store.is_consumed(approval.approval_id)` → `ALREADY_CONSUMED`.
5. `request.readiness_state != HANDOFF_CANDIDATE` → `NOT_ELIGIBLE` (defense in depth; unreachable in practice since it's digest-bound, but checked explicitly per Phase 8).

None of these consume the approval — only an actual adapter invocation attempt does (Section 5).

## 5. Consumption point and failure taxonomy

`HandoffOutcome` values: `NOT_ELIGIBLE`, `DECLINED`, `APPROVAL_MISMATCH`, `STALE_REQUEST`, `ALREADY_CONSUMED`, `EXECUTION_BLOCKED`, `EXECUTION_FAILED`, `EXECUTION_TIMEOUT`, `INFRASTRUCTURE_FAILURE`, `SUCCESS` — exactly the Phase 25 taxonomy.

Consumption rule (documented precisely, no ambiguity):

- Any pre-launch gate failure (Section 4) → **not consumed**, `launched=False`.
- `adapter.invoke(...)` returns `outcome.invoked is False` (the adapter's own pre-invocation guard rejected it — e.g. executable no longer exists, a race since the request was built) → **not consumed** (`launched=False`, outcome `INFRASTRUCTURE_FAILURE`). This is deterministically provable: the adapter's own `invoked` flag is authoritative, and it is set only after all of the adapter's guards pass. Not consuming here does not create an autonomous retry — a human must still issue a new explicit "run this" turn; nothing in this module retries automatically.
- `outcome.invoked is True` (the helper was actually called, or the adapter attempted the call and it raised) → **consumed**, `launched=True`, regardless of what the helper returned: success (`completed`), GAUSS error (`failed`/`error`/`blocked`/`skipped`), `timed_out`, or a post-call adapter-level anomaly (`HELPER_LAUNCH_EXCEPTION`/`MALFORMED_RESULT`/`UNKNOWN_HELPER_STATUS`, mapped to `INFRASTRUCTURE_FAILURE` but still consumed, since an attempt was made).

Mapping `outcome.execution_status` → `HandoffOutcome`: `"completed"` → `SUCCESS`; `"timed_out"` → `EXECUTION_TIMEOUT`; `"failed"`/`"error"`/`"blocked"`/`"skipped"` → `EXECUTION_FAILED`; adapter-level anomaly categories → `INFRASTRUCTURE_FAILURE`. This module never reinterprets exit codes or stdout/stderr content itself — that remains `gauss_execution_interpreter.interpret_execution(...)`'s job, invoked separately by the rendering layer if the user asks "why did it fail."

## 6. Consent contract implementation

- Approval parser `parse_execution_approval_response(text) -> "approved" | "declined" | "unrecognized"`: exact (case-insensitive, stripped) match against `{"yes", "approve"}` → approved, `{"no", "decline"}` → declined, anything else → `unrecognized`. No fuzzy matching, no "looks affirmative" heuristic.
- Chat loop: on `unrecognized`, re-prompt once with the same exact question; a second `unrecognized` cancels safely (treated as not-approved; no request is created/executed, no approval object is created at all).
- Approval binds to exactly one `request.digest` (Section 3). A declined request produces no `ExecutionHandoffApproval` with `decision=APPROVED` — declining is itself recorded (for audit) but can never later be treated as approval.
- Trigger phrase detection (`looks_like_execution_request(text) -> bool`): a small fixed phrase set (`"run this"`, `"run this code"`, `"execute this"`, `"execute this code"`, case-insensitive) — deliberately narrow, mirrors `gauss_ai_config.looks_like_cli_invocation`'s existing "small fixed detector, not a general classifier" convention. Only checked when a pending `HANDOFF_CANDIDATE` answer with exactly one code block exists; otherwise the phrase is just ordinary chat text.

## 7. Scope narrowing decisions (disclosed, not silent)

- **Single code block only**: a conversational execution offer is made only when `AnswerResult.generated_code` has exactly one element. Multiple fenced blocks in one answer are out of scope for v0.78 (avoids inventing multi-snippet/multi-file orchestration, explicitly excluded by the brief).
- **Workspace**: a fresh `tempfile.TemporaryDirectory(prefix="gauss_ai_handoff_")` per execution attempt (mirrors `gauss_differential_harness.RealGaussRunner` exactly) — never the user's project directory, never a durable workspace registry entry, never a named script file (inline `code=` only, `script_path` is never populated, so the adapter's own unconditional script-path rejection is structurally never triggered by this path).
- **No new subprocess code**: confirmed by structural test — `gauss_execution_handoff.py` contains no `subprocess` import and no `import gauss_code_execution` at all (it only ever reaches the real helper indirectly, via `gauss_execution_adapter.load_real_helper()`, called explicitly by the chat orchestration layer only when `runner == "gauss"`).
- **Approval persistence**: process-local only (`ExecutionHandoffApprovalStore` is an ordinary in-process dict, discarded on process exit) — no new persistence mechanism is introduced, matching every other approval store in this repository.

## 8. Test plan (see Phase 26 of the milestone brief for the full checklist)

New `scripts/test_gauss_execution_handoff.py` covers: digest determinism/mutation-sensitivity (code/runner/executable/timeout/workspace/readiness each independently), eligibility gate (only `HANDOFF_CANDIDATE` builds a request), approval binding/immutability, pre-launch gate (all five failure branches), consumption semantics (success/failure/timeout all consume; adapter-level pre-invocation rejection does not), replay prevention (same approval twice; approval for request A used against request B), decline-cannot-become-approval, fake end-to-end success/failure/timeout, structural safety (no subprocess, no conversational imports, model/provider layer cannot reach execution).

Extended `scripts/test_gauss_ai_chat.py` covers the conversational wiring: offer only appears for `HANDOFF_CANDIDATE` + single code block; approval parser narrowness in the actual chat loop; a full fake-runner approve→execute→render cycle; decline path; a second "run this" after execution is a brand new request+approval (no consent inheritance); `NOT_READY`/`REVIEW_REQUIRED` answers never trigger an offer.

## 9. Scope exclusions (unchanged from the brief, restated for this doc's own record)

No autonomous execution, no implicit consent, no standing/remembered approval, no execution of `REVIEW_REQUIRED`/`NOT_READY` code, no automatic retry, no automatic timeout extension, no automatic repair, no source-file modification, no multi-file orchestration, no persistent approval database, no telemetry.
