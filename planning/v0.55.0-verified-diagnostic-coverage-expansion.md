# v0.55.0 - Verified Diagnostic Coverage Expansion

## Release Goal

Broaden and deepen the verified GAUSS error knowledge available to the interpreter (`gauss_execution_interpreter.py`) and diagnostic engine (`gauss_execution_diagnostics.py`) — improving verified error-code coverage, semantic category coverage, diagnostic trigger quality, and provenance transparency, and attempting real-runtime verification of `G0290` where practical. Does not implement repair behavior.

## Evidence-Gathering Method

A bounded, safe real-runtime probe was run against this development machine's real GAUSS 26.1.1 installation (`C:\gauss26\tgauss.exe -b <script>`), following the same command form verified in `v0.28.0`/`v0.29.0`. Each candidate scenario ran as its own small `.gss` script inside a disposable scratch subdirectory (outside the repository, under this session's temp scratchpad); stdout, stderr, and exit code were captured directly; no package was installed or removed, no license or global configuration was touched, and a `tasklist` check after the full probe confirmed zero lingering `gauss`/`tgauss` processes.

Fifteen scenarios were run in total. Ten reproduced a genuine GAUSS error; five did not (silent type coercion, `+INF` from division by zero, value-recycling reshape) and were discarded without further action. Of the ten reproduced errors, six were added to the catalog as new entries, one (`G0290`) upgraded an existing entry, one (`G0117`) was investigated and deliberately not added, and one (a `csvRead` "file not found" failure with no `G####` code at all) was documented as a discovered gap rather than cataloged.

| Scenario | Script | Result |
|---|---|---|
| Library not found | `library optmum;` | `error G0290 : Library not found 'optmum.lcg'` — **added, upgrades existing entry** |
| Index out of range (over) | `x = ones(2,2); print x[5,5];` | `error G0058 : Index out of range` — **added** |
| Index out of range (under) | `x = ones(2,2); print x[-1,1];` | `error G0058 : Index out of range` — same code, corroborates |
| Missing procedure argument | `proc(1) = myproc2(a, b); retp(a+b); endp; y = myproc2(1);` | `error G0159 : Wrong number of parameters` — **added** |
| Negative size argument | `x = eye(-1);` | `error G0104 : Argument must be positive` — **added** |
| String argument to numeric function | `x = sqrt("abc");` | `error G0071 : Type mismatch` — **added** |
| Inversion of a singular matrix | `x = ones(2,2); y = inv(x);` | `error G0048 : Matrix singular` — **added** |
| Horizontal concat, mismatched rows | `x = ones(2,2); y = ones(3,3); z = x~y;` | `error G0047 : Rows don't match` — **added** |
| String-indexed non-dataframe access | `x = ones(2,2); print x["a","b"];` | uncoded `indexing error: ...` line, then `error G0117 : Invalid argument` — **investigated, not added** (compound/indirect trigger) |
| Missing data file via `loadd` | `x = loadd("does_not_exist.csv");` | `error : csvRead error: file '...' not found` (no `G####` code) — **documented as a schema gap, not cataloged** |
| Zero missing second argument | `y = zeros(2);` | `error G0105 : Bad expression or missing arguments` — already cataloged, corroborates `G0105` |
| Undefined procedure call | `y = myundefinedproc(1,2);` | `error G0025 : Undefined symbol` — already cataloged, corroborates `G0025` |
| String + matrix | `x = ones(2,2); y = x + "abc";` | no error (silent coercion) — discarded |
| Reshape with recycling | `x = ones(2,2); y = reshape(x, 3, 3);` | no error (value recycling) — discarded |
| Divide by zero | `x = 1/0;` | no error (`+INF`) — discarded |

## Catalog Additions

Six new `GaussErrorCatalogEntry` records, all `verification_status=(VerificationStatus.REAL_RUNTIME,)` — the strongest evidence tier this catalog recognizes, and stronger than three of the five pre-existing entries were before their own documentation cross-checks. None has yet been independently cross-checked against official Aptech documentation in this repository; this is disclosed explicitly rather than implied otherwise.

| Code | Title | Category (new unless noted) |
|---|---|---|
| `G0058` | Index out of range | `indexing_subscript` (new) |
| `G0159` | Wrong number of parameters | `argument_validation` (new) |
| `G0104` | Argument must be positive | `argument_validation` (new) |
| `G0071` | Type mismatch | `type_mismatch` (new) |
| `G0048` | Matrix singular | `numerical` (existing, first entry) |
| `G0047` | Rows don't match | `matrix_dimension` (existing, second entry alongside `G0036`) |

`G0290` ("Library not found") was upgraded from `(OFFICIAL_DOCUMENTATION,)` to `(REAL_RUNTIME, OFFICIAL_DOCUMENTATION)`; confidence raised from `medium` to `high`, consistent with this catalog's other dual-sourced entries. No discrepancy was found between the runtime-observed title and the documented title — both read "Library not found."

Three new `GaussErrorCategory` enum values were added (`INDEXING_SUBSCRIPT`, `ARGUMENT_VALIDATION`, `TYPE_MISMATCH`). `ARGUMENT_VALIDATION` deliberately covers both "procedure invocation" (`G0159`, wrong argument count) and "argument count or argument type" (`G0104`, an out-of-range positional argument) from this milestone's own candidate-area list, since both `G0159` and `G0104` are, at the semantic level, "an argument supplied to a callable failed validation" — splitting them into two categories would not have added diagnostic value. No new dataclass field was added to `GaussErrorCatalogEntry`; the existing `known_triggers`/`diagnostic_questions`/`required_evidence_for_diagnosis` schema from `v0.54.0` covered every new entry cleanly.

## What Was Not Added

- **`G0117` ("Invalid argument")** — genuinely reproduced, but only via a compound trigger (an uncoded `indexing error: ...` diagnostic line preceding the coded error, from attempting to string-index a plain matrix as if it were a dataframe). The exact condition mapping specifically to `G0117` — as opposed to the dataframe-indexing message before it — was not isolated cleanly enough to state a `known_trigger` without speculating about which part of the compound failure the code itself represents. Left for a future, more targeted reproduction.
- **A `csvRead` "file not found" failure** (via `loadd` against a missing file) — a genuine, real GAUSS runtime failure, but reported in a format (`error : csvRead error: file '...' not found`, sourced from `c:\gauss26\src\csv.src`) that carries no `G####` code at all. `gauss_execution_interpreter.py`'s error-detection regex (`error\s+(G\d{4})`) does not match this format, so it correctly falls through to the `insufficient_evidence` classification today — not a bug, but a documented gap: this catalog's schema assumes a `G####` code, and some real GAUSS failures do not have one. Recorded in `docs/gauss-error-catalog.md` and `KNOWN_LIMITATIONS.md` rather than silently ignored or forced into the existing schema.
- **Startup/licensing scenarios** — not attempted this milestone. Constructing a genuine license-manager failure safely (without touching this machine's real license state) was judged out of scope for a bounded, low-risk probe; `STARTUP_OR_LICENSING` remains uncataloged, same as before this milestone.

## Interpreter and Diagnostic-Engine Changes

None to control flow. Both `gauss_execution_interpreter.interpret_execution(...)` and `gauss_execution_diagnostics.diagnose_execution(...)` only look codes up in the catalog; adding entries required zero code changes to either module, confirming the design goal stated in `docs/gauss-error-catalog.md`'s "Adding a New Entry" section holds under a real, non-trivial expansion.

One intentional classification change: `interpret_execution`'s output for `G0290` now reports `verification_status=("real_runtime", "official_documentation")` instead of `("official_documentation",)`, and `diagnose_execution`'s output for `G0290` now reports `real_runtime` in `knowledge_verification` and no longer includes the "not yet reproduced against a real GAUSS runtime" limitation string. Both pre-existing tests (`test_17_g0290_library_not_found_interpreted` in `test_gauss_execution_interpreter.py`, `test_07_g0290_bounded_diagnosis` in `test_gauss_execution_diagnostics.py`) were updated in place, with an inline comment explaining the change is intentional and evidence-driven, not a regression.

## Confidence Model

Unchanged. Every catalog-derived cause for all six new codes is assigned `low` confidence by the same uniform rule `_causes_from_entry` already applied to the five pre-existing codes — no code change was needed in `gauss_execution_diagnostics.py` to enforce this; it falls out of the existing design. Verified directly by dedicated tests for each new code (`test_32` through `test_37` in `scripts/test_gauss_execution_diagnostics.py`) and a general assertion (`test_38`) that none of the six new entries' diagnosis output contains repair-shaped language.

## CLI

No new command. `interpret` and `diagnose` were exercised against all six new codes via a helper (`_failed_run_with_stderr`) that drives the real `request --fake-failure` / `plan` / `confirm` / `execute` sequence and then overrides only the captured stderr text — proving the CLI's actual evidence-assembly path (`_build_execution_evidence`) passes new codes through correctly, without adding a dedicated fake-runner mode per code.

## Testing

- New `scripts/test_gauss_error_catalog.py`: 18 tests — catalog size, verification-metadata presence, duplicate/empty-status rejection (raises `ValueError`), documentation-discrepancy retention, documentation-only vs. dual-sourced vs. real-runtime-only labeling, code lookup/normalization, category population (new categories populated, still-unused categories honestly empty), no-repair-instruction checks, and the `G0036`/`G0047` two-distinct-codes-one-category check.
- `scripts/test_gauss_execution_interpreter.py`: 8 new tests (one per new code, plus a `G0290`-upgrade-aware update to the pre-existing test, a 4-code regression check for the original entries, and a case-insensitivity check for a new code).
- `scripts/test_gauss_execution_diagnostics.py`: 9 new tests (one bounded-diagnosis test per new code, a repair-shaped-output sweep across all six, a `G0290`-upgrade regression test, a pre-existing-five-codes regression test, and an unknown-code-after-expansion test), plus an in-place update to the pre-existing `G0290` test.
- `scripts/test_gauss_code_assistant_cli.py`: 2 new tests (`interpret`/`diagnose` pass-through for all six new codes in one parametrized test, and an uncataloged-code-remains-generic check).
- Full existing regression suite (11 required suites plus the optional real-runner smoke test) re-run and passing, including the two intentionally-updated `G0290` assertions.

## Real GAUSS Executions Performed

Fifteen real GAUSS invocations via `tgauss.exe -b`, all in this milestone's own bounded probe (see "Evidence-Gathering Method" above), plus the optional `test_gauss_code_assistant_real_runner.py --run-gauss` smoke test for validation completeness. No package install/removal, no license/environment change, and confirmed zero lingering `gauss`/`tgauss` processes after the full probe and after validation.

## Out of Scope (unchanged from the authorizing task)

None implemented.

## Readiness Classification

Ready for continued structured alpha testing, now with substantially broader verified diagnostic coverage. Not ready for assisted debugging, repair planning, or repair application — unchanged and structurally impossible for this module to drift into.

**Recommended next milestone:** durable execution sessions or evidence-aware repair planning are the two named candidates in this project's own roadmap; a further diagnostic-coverage expansion remains available but is now lower-priority evidence-wise, since this milestone's own bounded probe already found and cataloged every cleanly-reproducible error from its candidate list, leaving mostly harder-to-safely-reproduce categories (startup/licensing) or documentation cross-checks as the remaining low-risk work in that direction.
