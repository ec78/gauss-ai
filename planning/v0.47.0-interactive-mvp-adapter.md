# v0.47.0 Interactive MVP Adapter

## Release Goal

Create the smallest terminal-based adapter that lets a human manually test the real GAUSS Code Assistant MVP workflow without writing Python glue.

This milestone addresses the P0 product gap surfaced after `v0.46.0`: the repository had a composed, tested Python facade, but no honest user-facing entry point. The adapter is an alpha harness, not a production chat interface.

## Scope

Implemented:

- `scripts/gauss_code_assistant_cli.py`, a local terminal adapter and testable command handler.
- Workspace bootstrap beneath an approved local parent directory.
- Request, plan, confirmation, fake execution, output metadata, explicit file reading, provenance, status, reset, and exit commands.
- Deterministic fake runner by default, visibly disclosed on every execution.
- Trace identifiers for adapter session, workspace, request, orchestration instance, and execution provenance.
- `scripts/test_gauss_code_assistant_cli.py`, a direct command-handler and transcript-style test suite.

Explicitly not implemented:

- Durable `gauss_execution_session.ExecutionSession` integration.
- `begin_analysis()` wiring.
- Real GAUSS execution from the adapter.
- Uploads, cloud services, persistent sessions, multi-user ownership/ACLs, binary/PDF/image/spreadsheet readers, autonomous execution, autonomous file reading, or a natural-language agent framework.

## Architecture

The CLI depends on the existing MVP facade and workflow modules:

```text
terminal command
  -> InteractiveMvpAdapter.handle_line(...)
  -> GaussCodeAssistantWorkflow
  -> ExecutionWorkflow / WorkspaceRegistry / WorkspaceFileReader
  -> deterministic fake runner (execute only)
```

The adapter translates terminal input into existing structured objects. It does not duplicate or reimplement:

- execution eligibility;
- confirmation validation;
- workspace containment;
- file path/type/size validation;
- explicit-read enforcement;
- output registration;
- provenance creation.

Those remain owned by `scripts/gauss_execution_workflow.py`, `scripts/gauss_workspace.py`, and `scripts/gauss_workspace_file_reader.py`.

## Safety Model

Execution cannot occur until:

1. a workspace has been created and readied;
2. a request has been stored;
3. `plan` has called `GaussCodeAssistantWorkflow.propose(...)`;
4. the user supplies `confirm <request_hash>`.

The adapter deliberately requires the displayed `request_hash` as confirmation input. If an old or mismatched hash is supplied after the proposal changes, `ExecutionWorkflow.confirm_execution(...)` rejects it through the existing `WorkflowConfirmationEvent` validation path.

`outputs` reports `WorkflowResult.files_produced` metadata only. It never opens files. `read <relative-path>` is the only command that asks for content, and it routes through `GaussCodeAssistantWorkflow.read_file(...)`.

## Fake Runner

The default runner is deterministic and local:

- success mode writes `fake-output.txt` inside the active workspace and returns metadata for that file;
- failure mode returns a deterministic GAUSS-like runtime-error-shaped result;
- both modes disclose that GAUSS was not invoked;
- no files are written outside the active workspace.

## Known Limitations

- The adapter is one-process and one-session only.
- Workspaces and durable store files are process-local alpha harness state and are discarded when temporary parents are used.
- Request interpretation is intentionally limited and adapter-driven. This is not a natural-language agent runtime.
- `execution_session_reference` is displayed with an explicit caveat: it is still the orchestration instance ID, not a durable `ExecutionSession` ID.
- The workspace lifecycle remains single-shot for execution. A completed workspace should be replaced with `workspace create` before another execution.

## Acceptance Criteria

- A tester can launch the adapter with one documented command.
- A tester can create a workspace without writing Python.
- A tester can complete `request -> plan -> confirm -> fake execute -> outputs -> explicit read`.
- The existing workflow facade is invoked at each applicable stage.
- Execution cannot occur without valid confirmation.
- File content cannot be read without an explicit read command.
- Output metadata can be viewed without reading content.
- The adapter clearly labels fake execution.
- Trace identifiers are visible.
- No existing safety contract is duplicated or weakened.
- No GAUSS process is started.

## Tests

`scripts/test_gauss_code_assistant_cli.py` covers:

- startup/help/exit;
- workspace bootstrap;
- request and proposal;
- explicit confirmation;
- decline path;
- execute blocked before confirmation;
- stale/mismatched confirmation;
- deterministic fake success;
- deterministic fake failure;
- output metadata without reading;
- explicit file read;
- path traversal rejection;
- cross-workspace mismatch;
- reset behavior;
- trace disclosure;
- confirmation required again after proposal-changing input;
- no real GAUSS import;
- complete transcript-style integration.
