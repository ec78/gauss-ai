# v0.9.0 Second Operational Expert and Multi-Expert Routing Plan

## Release Goal

`v0.8.0` proved that an expert module can be made operational — activation triggers, evidence requirements, decision rules, refusal/escalation conditions, and an output contract, checkable by manual evaluation without a runtime engine — for exactly one expert, the GAUSS Language Expert. `v0.9.0` extends that proof beyond a single expert: it operationalizes the Econometrics Expert and adds documented multi-expert routing rules for the many realistic Code Assistant tasks where GAUSS language mechanics and econometric methodology overlap in the same request (for example, translating an R regression into GAUSS involves both "is this valid GAUSS syntax" and "is this the right model for this data"). The goal is not just a second profile — it's proving the operational-expert interface generalizes, and that two experts can coexist in one response without either silently overriding the other's domain.

## Current State

- The GAUSS Language Expert is fully operationalized: `experts/gauss-language/OPERATIONAL_PROFILE.md` fills in every field of `tools/operational_expert_interface.md`, grounded in a substantially populated `BODY_OF_KNOWLEDGE.md`.
- The operational expert interface (`tools/operational_expert_interface.md`) exists and is deliberately generic — designed in `v0.8.0` specifically so future experts could reuse its shape without redesigning it.
- The expert routing workflow (`workflows/expert-routing.md`) exists, but its 10 steps and 7 worked examples are written entirely in terms of a single expert (the GAUSS Language Expert) deciding to activate or not. It has no notion of two experts activating on the same task, no precedence rule, and no combined output contract.
- The other four experts named in `workflows/code-assistant-response.md` — Econometrics, Software Engineering, Documentation, Education — remain narrative-only guidance, referenced by name in one line of prose each, with no operational profile.
- **Important finding from this planning task:** unlike the GAUSS Language Expert, whose `EXPERT.md` and `BODY_OF_KNOWLEDGE.md` were already substantially written before `v0.8.0` began, the Econometrics Expert's narrative files (`experts/econometrics/EXPERT.md`, `knowledge.md`, `reasoning.md`, `best_practices.md`, `common_mistakes.md`) are all currently pure placeholders — each file is a one-line stub ("Placeholder for expert module definition," etc.) with no actual content. This means `v0.9.0` cannot skip straight to writing an operational profile the way `v0.8.0` could; a real narrative/knowledge foundation has to be built first, at least at the "minimum needed for operationalization" level, not the full depth `BODY_OF_KNOWLEDGE.md` reached for GAUSS language mechanics.
- Benchmark category 15.x (Expert Routing) validates single-expert activation and non-activation for the GAUSS Language Expert only. It does not exercise any scenario where a second expert's domain is also in play.

## Recommended Second Expert

**Econometrics Expert.**

- It naturally overlaps with GAUSS code tasks — GAUSS is a matrix-oriented language built for exactly the statistical/econometric workflows the Econometrics Expert would own, so realistic Code Assistant requests already blend the two domains constantly (translating a regression, choosing between native estimation commands, interpreting model output).
- Many Code Assistant requests already implicitly need both: "translate this R regression to GAUSS" is not just a syntax question (which command) but also a methodology question (is OLS still the right estimator for this data, are the assumptions being carried over correctly).
- It tests whether the operational expert interface actually generalizes, rather than having been implicitly shaped around GAUSS-specific concepts. Econometrics's evidence, decision rules, and refusal conditions look structurally different from the GAUSS Language Expert's (methodological judgment vs. documentation-backed syntax), which is a meaningful test of the interface's abstraction.
- It forces a clear, checkable separation between two failure modes that are easy to conflate: code that is syntactically valid GAUSS but statistically inappropriate, and code that reflects sound methodology but invents GAUSS syntax to express it. Neither expert should be able to paper over the other's failure.

## Non-goals

- No runtime orchestration engine — multi-expert routing remains a documented, manually-checkable reasoning procedure, the same way single-expert routing was in `v0.8.0`.
- No automatic hidden expert-execution metadata — nothing in this milestone requires machine-readable trace output proving which expert(s) fired; correctness is still confirmed by inspecting response content.
- No full implementation of all experts — Software Engineering, Documentation, and Education remain narrative-only after `v0.9.0`; only Econometrics joins the GAUSS Language Expert as operational.
- No hosted service.
- No GAUSS execution engine.
- No replacement of the evidence schema or retrieval workflows — the Econometrics Expert's evidence requirements (see below) are a different *kind* of evidence than `schemas/command_lookup_evidence.schema.json` governs, and this milestone must not blur that line by trying to force methodological judgment into the command-lookup evidence vocabulary.
- No weakening of GAUSS command evidence requirements — everything `v0.8.0` established about official-doc-backed syntax remains exactly as strict when the Econometrics Expert is also active on a task.
- No attempt to make the Econometrics Expert a full textbook — given the placeholder-to-real-content gap identified above, scope the narrative/knowledge work to what the operational profile actually needs (activation triggers, decision rules, refusal conditions), not a comprehensive econometrics reference.

## Econometrics Expert Operational Scope

**Owns:**

- Model selection (which class of model fits the stated data/question, at a conceptual level)
- Estimator choice (e.g., OLS vs. IV vs. GLS vs. panel estimators, as a methodological question)
- Assumptions (what a chosen model/estimator assumes, and whether the stated context plausibly satisfies them)
- Diagnostics (what checks are appropriate — heteroskedasticity, autocorrelation, multicollinearity, specification tests — and what a diagnostic result implies)
- Interpretation of coefficients and test results (what a coefficient, p-value, or test statistic means in context)
- Time series/panel/cross-sectional modeling considerations
- Robustness and sensitivity checks (as methodological recommendations, not GAUSS-specific commands)
- Identification concerns (endogeneity, omitted variables, reverse causality, and similar threats to causal interpretation)
- Forecast/evaluation logic (methodological criteria for evaluating a forecast or model fit)
- Statistical limitations and caveats (when a result should be presented with explicit uncertainty)

**Does not own:**

- Exact GAUSS syntax
- GAUSS command return fields
- Package/base-GAUSS distinction
- Low-level language mechanics (control flow, data structures, procedure syntax)
- General project management
- Generic writing tasks

## Multi-Expert Routing Rules

**GAUSS Language Expert only:**

- Exact syntax requests
- Command signatures
- Data structure choice (matrix/DataFrame/array/structure) with no methodological question attached
- Debugging GAUSS syntax errors
- Package/base-GAUSS distinction

**Econometrics Expert only:**

- Conceptual model choice with no GAUSS implementation requested
- Interpreting a regression result supplied in plain language (no GAUSS code involved)
- Explaining assumptions or diagnostics in the abstract, without GAUSS syntax

**Both experts:**

- Translating an econometric method into GAUSS code
- Choosing a GAUSS command for a statistical model (the command-selection question is GAUSS-side; whether that model is the right one is econometrics-side)
- Debugging code where the issue may be statistical (wrong model/assumptions) or syntactic (wrong function/arguments) or both, and it isn't yet clear which
- Reviewing GAUSS analysis code for both implementation correctness and methodological soundness
- Explaining output from a GAUSS model (the printed report's mechanics are GAUSS-side; what the numbers mean is econometrics-side)
- Recommending diagnostics to run in GAUSS (which diagnostic is econometrics-side; how to actually run it in GAUSS is language-side)

## Coordination Rules

- The GAUSS Language Expert owns implementation correctness: is this valid, evidence-backed GAUSS syntax.
- The Econometrics Expert owns methodological correctness: is this the right model/estimator/diagnostic for the stated problem.
- Official GAUSS documentation remains authoritative for command syntax regardless of which expert(s) are active — the Econometrics Expert's involvement never changes the evidence bar for a syntax claim.
- The Econometrics Expert may recommend a method, but cannot invent GAUSS syntax to express it — a methodological recommendation that has no verified GAUSS implementation must say so and route to the GAUSS Language Expert's evidence requirements rather than presenting invented code.
- The GAUSS Language Expert may recommend a native command, but cannot claim the underlying model is statistically appropriate for the user's data without econometric reasoning backing that claim — command availability is not evidence of methodological fitness.
- If the two experts' conclusions are in tension (for example, a command exists and is syntactically fine, but the Econometrics Expert would not recommend that model for the stated data), surface the distinction explicitly rather than collapsing it into a single unqualified recommendation.
- If GAUSS-side evidence is missing (no command-specific documentation retrieved), route to retrieval per the existing `workflows/command-documentation-retrieval.md`/`retrieval-backed-response-pattern.md` machinery — the Econometrics Expert's activation does not change this.
- If econometrics-side context is missing (for example, the data's structure, time dimension, or the user's actual research question is unstated), ask the user or state the assumption being made explicitly, mirroring how the GAUSS Language Expert already handles missing inputs.

## Output Contract for Multi-Expert Routing

Extends (does not replace) the single-expert output contract from `tools/operational_expert_interface.md`:

- `task_classification` — task mode(s), as before.
- `activated_experts` — which expert(s) fired: GAUSS Language Expert, Econometrics Expert, both, or neither.
- `activation_reason_by_expert` — the specific trigger that applied, per activated expert.
- `evidence_needed_by_expert` — GAUSS-side evidence needs (per the existing evidence-schema vocabulary) kept distinct from econometrics-side context needs (which are not evidence-schema concepts).
- `evidence_used` — what was actually available/retrieved, same as the single-expert contract.
- `implementation_recommendation` — the GAUSS Language Expert's contribution: what code/command to use, grounded in evidence.
- `methodology_recommendation` — the Econometrics Expert's contribution: what model/estimator/diagnostic is appropriate, and why.
- `conflicts_or_tensions` — any point where the implementation and methodology recommendations pull in different directions, stated explicitly rather than silently resolved.
- `response_constraints` — combined constraints from both experts (what must not be claimed, from either domain).
- `validation_or_diagnostic_suggestions` — merges the GAUSS Language Expert's validation-step requirement with the Econometrics Expert's diagnostic recommendations, since a translation/debugging response may need both a code-correctness check and a methodological diagnostic.

As with the single-expert contract, these fields are internal by default — the final user-facing response does not need to label them, and correctness is confirmed by inspecting whether the response's content satisfies them in substance.

## Benchmark Plan

Proposed next category, **16.x — Multi-Expert Routing**, continuing the numbering convention:

- **16.1** — Econometrics-only activation: user asks whether OLS is appropriate for a conceptual scenario, with no GAUSS code requested. Expected: only the Econometrics Expert activates; no GAUSS evidence requirement is imposed.
- **16.2** — GAUSS-only activation: user asks for exact syntax or return fields for a GAUSS command, with no statistical interpretation needed. Expected: only the GAUSS Language Expert activates; response doesn't drift into unrequested methodology discussion.
- **16.3** — Both experts activate for an R-to-GAUSS regression translation: response must use GAUSS evidence for syntax and econometric reasoning for model interpretation/diagnostics, following the pattern already validated for GAUSS-only translation in `15.2` but now with an explicit methodology component.
- **16.4** — Both experts activate for panel-data method choice in GAUSS: response must separate the panel econometric method choice (Econometrics-side) from GAUSS command availability/syntax (GAUSS-side) rather than blending them into one undifferentiated recommendation.
- **16.5** — Methodologically bad request with valid GAUSS syntax: user asks for code that is syntactically possible but statistically inappropriate (for example, running OLS on data with an obvious endogeneity problem); response should explain the methodological issue rather than only providing working code.
- **16.6** — Correct command, wrong interpretation: user has real GAUSS output and misinterprets a coefficient or p-value; response should separate output mechanics (GAUSS-side) from econometric interpretation (Econometrics-side) and correct the misinterpretation.
- **16.7** — Multi-expert conflict/uncertainty: GAUSS evidence supports a command, but econometric context is insufficient to endorse the approach; response should provide implementation caveats and explicitly ask for missing methodological context rather than picking a side silently.
- **16.8** — Non-activation negative case: user asks for a general changelog/release note; neither operational expert should activate, mirroring `15.7`'s single-expert non-activation case but confirming it still holds with two operational experts available.

## Risks and Design Questions

- **How to avoid duplicated responsibilities between experts?** The Multi-Expert Routing Rules and Coordination Rules above are the primary defense — each expert's scope is defined by exclusion of the other's, and the `implementation_recommendation`/`methodology_recommendation` split in the output contract keeps their contributions structurally separate rather than blended into one paragraph.
- **How to evaluate multi-expert activation without runtime instrumentation?** The same way single-expert activation was evaluated in `15.x`: manual inspection of whether the response's content reflects both experts' decision rules where both should have fired, and only one (or neither) where that's correct — extended with a check for whether `conflicts_or_tensions` was surfaced when it should have been.
- **How to surface expert disagreement without cluttering user responses?** An open design question genuinely worth testing via `16.7` before settling on an answer — the working assumption is a short, explicit caveat rather than a structured "Expert A says X, Expert B says Y" format, but this should be validated against how it actually reads in a real generated response, not decided in the abstract here.
- **Whether the Econometrics Expert needs its own body of knowledge before an operational profile.** Yes, at minimum a working equivalent of the GAUSS Language Expert's `BODY_OF_KNOWLEDGE.md` domain-guidance sections — the current placeholder files (confirmed empty during this planning task) can't ground decision rules or refusal conditions the way `BODY_OF_KNOWLEDGE.md` grounded the GAUSS Language Expert's. This is explicitly budgeted as Task Order step 3, sized to "minimum needed for operationalization," not a full rewrite.
- **How broad the Econometrics Expert should be for this milestone?** Scoped by the Operational Scope section above — model selection, estimator choice, assumptions, diagnostics, interpretation, and identification concerns at a reasoning level, not a comprehensive econometrics curriculum. Depth should match what the 16.x benchmarks actually need to test, similar to how the GAUSS Language Expert's profile was scoped to what `15.x` needed rather than exhaustive language coverage.
- **Whether benchmarks should test methodology even when GAUSS syntax is not involved.** Yes — `16.1` exists specifically to confirm the Econometrics Expert can activate and reason correctly independent of any GAUSS implementation, which is necessary to prove it's a real operational expert and not just a GAUSS-translation add-on.
- **How to prevent the Econometrics Expert from weakening GAUSS evidence requirements.** The Coordination Rules state this explicitly ("the Econometrics Expert may recommend a method, but cannot invent GAUSS syntax to express it"), and `16.3`/`16.4`/`16.7` are specifically designed to test that a methodology recommendation never gets translated into unverified GAUSS code just because a plausible-sounding method was identified.
- **How to prevent the GAUSS Language Expert from overclaiming statistical validity.** Symmetric to the above — the Coordination Rules state the GAUSS Language Expert cannot claim methodological appropriateness from command availability alone, and `16.5` is designed specifically to catch a response that provides syntactically valid code for a statistically inappropriate request without flagging the problem.
