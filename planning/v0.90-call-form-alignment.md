# v0.90.0 — Call-Form Alignment: Design

Status: **approved** (2026-10-23, with every §8 recommendation: 1a, 2 yes, 3 (b) defer with (c) in parallel, 4-6 yes). Implementation in progress. Baseline for every probe and comparison: HEAD `7513151` (`v0.89.2` plus the publication record), with the published docs copy fetched on 2026-10-23 (1,826 pages).

This is the first milestone under v0.89's decision 10 = **B**: widen deterministic coverage within the existing constraint, so that more valid code reaches `handoff_candidate` and none reaches it wrongly. It takes up live evaluation 80.x's finding 2 (`planning/v0.89-release-readiness.md` §11.6), which investigation showed to be one of three related defects in how documented call forms are parsed and applied.

## 1. Why

`extract_documented_signature` reads every documented call form of a function, then keeps only two summaries of them: a set of `(min, max)` argument-count ranges, and **one merged parameter list** in first-seen order. Every downstream check works from those summaries:
- `validate_call` asks whether the call's argument count falls in any range;
- `check_parameter_roles` compares argument *i* with entry *i* of the merged list.

That loses the structure GAUSS's own documentation states. Three defects follow:

| # | Defect | Effect | Measured |
|---|---|---|---|
| A | Roles are checked against the **merged** list of all forms | `olsmt("", y, x, ctl)` checks `y` against `formula`; `plotScatter(x, y)` checks `x` against the optional `myPlot`. False gaps (`review_required`), and with literal arguments a false **not_ready** whose stated reason is untrue | 58 symbols; 80.10, 80.11 |
| B | An optional group that is not trailing (`plotScatter([myPlot, ]x, y)`) makes **every** parameter optional | `plotScatter();` and `plotACF();` are count-compatible and reach **handoff_candidate**; GAUSS rejects both (`G0159`, `G0274`) | 41 symbols (40 `plot*`) |
| C | A named default (`arimaFit(y, p=p, d=d, q=q)`) is counted as a required positional parameter | `bvarFit(y, p=2)` is not_ready: "documented form(s) accept 1 or 9 argument(s); this call passed 2" | 26 `timeseries` symbols |

A and C err in the safe direction: they block valid code, with a reason that is false. **B is the only defect in v0.89 known to put code GAUSS rejects at `handoff_candidate`.** It is not a safety breach: the code computes in memory, and the handoff reports GAUSS's error. But it is a wrong claim of a compatible signature, made to a user who is about to approve a run.

Goals:
- a call is checked against the documented form it can actually be, never against a list merged from several;
- an optional group is optional where the documentation puts it: leading, middle or trailing;
- `not_ready` for a role mismatch means no documented form fits, and its reason names the form;
- nothing reaches `handoff_candidate` that did not before, except calls that a documented form fits exactly. Each one is reviewed individually and spot-checked in GAUSS.

Constraints (all from `CLAUDE.md`):
- deterministic: no model, no score; a call either fits a documented form or it does not;
- stdlib only;
- the system-statement registry, the readiness state machine, the generation gate and grounding are unchanged;
- **this changes signature parsing**, so it needs the all-pages before/after signature diff and a verdict diff against HEAD on the real docs (§6).

Out of scope:
- argument **type** inference (an expression-built argument stays untraced; that is a later B item);
- the `&` parameter gap (v0.83.0, `plotSetTitle(&myPlot, …)`);
- the analysis-workspace milestone;
- class C's semantics, unless decision 3 says otherwise.

## 2. Investigation findings

All probes ran on 2026-10-23 at HEAD `7513151`, against the 2026-10-23 docs copy. Spot checks used `tgauss.exe -b` (GAUSS 26.1.4), each from its own new empty directory. The scratchpad scripts are not committed.

### 2.1 The parsing, as it is

- `_parse_signature_occurrence(raw_args)` splits at the **first** `[`. Everything before it is required; everything after it, with brackets removed, is optional. Correct for `f(a, b[, c[, d]])`; wrong for any group that is not at the end.
- `extract_documented_signature` collects one range per distinct form, and one merged name list. Its docstring states the simplification: "it does not track per-overload parameter metadata separately".
- `check_parameter_roles` is positional over that merged list (v0.83.0 added special cases around a documented `...`).
- These three are the only consumers of `arg_ranges`, `parameter_names` and `parameters`. Preconditions use fixed argument positions per symbol, and none of the six precondition symbols (`inv`, `invpd`, `solpd`, `chol`, `eigh`, `eighv`) has more than one form or a non-trailing group.

### 2.4 Class C: named defaults

- 26 `timeseries` pages document forms such as `arimaFit(y, p=p, d=d, q=q, sp=P, sd=D, sq=Q, period=s)` and `bvarFit(y, p=1, prior="minnesota", n_draws=5000, …)`. The parser counts each `name=default` as a required positional argument, so `bvarFit`'s ranges are exactly 1 and 9.
- The docs' own examples pass named arguments **out of documented order and as subsets**: `arimaFit(y, period=12, p=-1, d=1, q=-1)`, `bvarFit(data, p=4, ar=0)`.
- **Every one of these examples starts `library timeseries;`**, a system-touching statement, so any program using them is `not_ready` regardless. Class C can change a reason, never a state.
- **Not spot-checked.** On this machine `library timeseries;` raises no error, but `arimaFit` stays an undefined symbol (`G0025`) under `tgauss -b`, and the named-argument calls fail to parse before that (`G0029 Missing left parenthesis`), as GAUSS does for any unknown name. So the named-argument semantics (any order? positional allowed for a named default?) have no evidence here. Aptech offered to help test (v0.89 §9.3).
- **Evidence after approval (2026-10-23).** The user stated the rule: named arguments work in any order, after the required ones, with the defaults given in the `proc` definition. That needs no `timeseries` package to test, only a `proc` with defaults. Spot checks nd01-nd09 (`tgauss.exe -b`, GAUSS 26.1.4; `proc (1) = f(a, b=2, c=3); retp(a*100 + b*10 + c); endp;`):

### 2.5 What the design must decide

- **Which form a call is.** GAUSS itself selects by argument count and, for `[myPlot, ]`, by the first argument's type. The validator cannot evaluate types in general, but it can enumerate the alignments a form allows and use the evidence it has.
- **How to combine several viable alignments.** The safe reading: a role **mismatch** blocks only if every viable alignment mismatches; a role **match** counts only if some alignment matches completely; anything in between is unknown.

## 3. Proposed design

### 3.1 Per-form signatures

`DocumentedSignature` gains `forms: tuple[CallForm, ...]`, one per distinct documented form, in document order. A `CallForm` is an ordered list of **slots**, each one of:
- a required parameter;
- an optional group: one or more parameters (or nested groups) present or absent together, wherever the documentation puts the brackets;
- a variadic `...` (any number, including zero);
- (decision 3) a named default `name=default`: optional, matched by name.

A new parser, `_parse_call_form(raw_args)`, reads the bracket structure as written: a `[` opens a group, the matching `]` closes it, groups nest, and the leading comma inside a group (`[, ctl]`, `[myPlot, ]`) is a separator, not a parameter. It shares `_split_top_level_args` and `_normalize_parameter_name` with the current code, and is unit-tested on every form shape found in §2.2.

`arg_ranges` is then derived from the forms: a form's minimum counts only its required slots, so `plotScatter`'s range becomes `(2, 3)` (both forms) instead of `(0, 3)`. The merged `parameter_names` and `parameters` stay, built as today, for anything that only lists names. They are no longer used to check roles.

### 3.2 Alignments

For a call with *n* arguments, each form yields its **alignments**: every way of including or omitting its optional groups (respecting nesting) and sizing its variadic so the slots number *n*. Each alignment maps argument *i* to one documented parameter.
- `plotScatter(x, y)`: form 1 gives one alignment (`x`, `y`, without `myPlot`); form 2 gives (`df`, `formula`).
- `olsmt("", y, x, ctl)`: only form 2 has a four-slot alignment (`data`, `depvar`, `indvars`, `ctl`).
- `plotScatter()`: no alignment in any form.

The enumeration is deterministic: forms in document order, and within a form, fewer included groups first. It is bounded at `MAX_CALL_ALIGNMENTS = 64` per call. Past the bound, roles are `UNKNOWN` with a new cause, `call_form_unresolved`, never guessed. No documented form measured in §2.2 comes near it.

### 3.3 Argument count (fixes B)

A call is count-compatible exactly when at least one alignment exists. `plotScatter();` and `plotACF();` become `INCOMPATIBLE`, with the existing message, now right: "documented form(s) accept 2-3 argument(s); this call passed 0". This moves verdicts toward not_ready only.

### 3.4 Roles (fixes A)

Each argument's category is resolved once, as today (`resolve_argument_category_with_cause`: literals, traced assignments, documented return types). Then each alignment is checked against its own parameters:
1. **Some alignment matches at every position:** the role check reports that alignment (all `MATCH`), and its parameter names appear in any explanation.
2. **Otherwise, if every alignment has at least one `MISMATCH`:** `MISMATCH`, reported for the first such alignment in enumeration order. The reason names the form ("does not match the documented type for parameter 'x' (matrix) in `plotScatter([myPlot, ]x, y)`, or any other documented form").
3. **Otherwise:** the first alignment with no mismatch is reported, and its unknown positions stay `UNKNOWN` with their usual causes. Where the viable alignments disagree about which parameter a position is, the cause is `call_form_ambiguous`.

So a mismatch blocks only if no documented form can fit, and a match counts only if one form fits completely. Today a single misaligned slot decides both. The rule reads only categories the validator already computes, and it is order-independent in outcome: the reported alignment changes only which explanation is shown.

### 3.5 What a user sees

- `coverage_gaps` and role explanations name the parameter of the reported alignment (`depvar`, not `formula`).
- A new gap cause, `call_form_ambiguous`, gets its own explanation text, as every cause does, and appears in the MCP output unchanged in shape.
- `docs/pre-execution-validation.md` gets a short section on call forms. `KNOWN_LIMITATIONS.md`'s 80.x-2 line is replaced by what remains (§5).

### 3.6 What does not change

- grounding (`resolve_concepts`, `ground_multi`, aliases), the generation gate and `command_doc_lookup.py`'s extraction of `syntax_blocks`: the new parser reads the same `syntax_blocks` strings;
- `resolve_argument_category_with_cause`, the precondition registry and checkers, the syntax rules and the system-statement registry;
- the readiness state machine and `compute_eligibility`;
- the MCP tool surface and the execution handoff.

## 4. Scope boundary

In scope: §3.1-§3.5, tests, the §6 diffs, `docs/pre-execution-validation.md`, `KNOWN_LIMITATIONS.md`, the release records and live evaluation 81.x.

Out of scope:
- argument type inference beyond today's tracing (an expression-built argument stays untraced);
- the `&` parameter gap;
- class C's named-argument matching, unless decision 3 chooses (a);
- choosing between same-arity forms by an argument's runtime type (GAUSS does this; the validator can only use the categories it already has);
- the analysis-workspace milestone.

## 5. Known limitations this design accepts

- **A form is chosen only by the evidence the validator has.** Where two forms accept the same count and the arguments' categories are unknown (`plotScatter(x, y)` with `rndn` arguments: `x, y` or `df, formula`), the roles stay `UNKNOWN` (`call_form_ambiguous`), so such code stays `review_required`. That is honest, but it means 80.11's exact snippet does not move.
- **A role match under one alignment is evidence for that form only.** It says the arguments fit a documented form, not that GAUSS will choose that form at run time. GAUSS chooses by the same count and, for `[myPlot, ]`, by the first argument's type, so the two agree for every form measured in §2.2.
- **Named defaults (class C) stay counted as positional** unless decision 3 says otherwise. All 26 symbols need `library timeseries;`, which keeps their code `not_ready` anyway; the false count reason remains next to the true one.
- **`switchFit(y[, x], num_states, …)`** is the one mid-list group; it is parsed correctly but has no live evidence.

## 8. Decisions needed

1. **Combine alignments as §3.4** (a mismatch blocks only if every alignment mismatches; a match counts only if one alignment matches completely; otherwise unknown).
   - (a) as proposed;
   - (b) stricter: any mismatching viable alignment blocks;
   - (c) choose one alignment by a fixed preference (for example, without leading optionals first) and check only it.

   *Recommend (a).* It is the only rule that blocks when no documented form can fit and never blocks a call that one form fits. (b) keeps false blocks such as cf03 whenever a second form also counts. (c) is a guess dressed as a rule.
2. **Fix B's count in this milestone** (§3.3). *Recommend yes.* It is the one known path to a wrong handoff_candidate, and it falls out of the same parser.
3. **Class C (named defaults).**
   - (a) parse `name=default` as an optional slot matched by name, in any order, after spot checks prove the semantics;
   - (b) defer, and disclose;
   - (c) ask Aptech (Jason) for the rules and a working `timeseries` setup, then decide.

   *Recommend (b) with (c) in parallel.* Every class-C program is already `not_ready` through `library timeseries;`, so (a) changes reasons, never states. And there is no GAUSS evidence on this machine for the semantics (§2.4), which this project never guesses.
4. **`MAX_CALL_ALIGNMENTS = 64`** (§3.2). *Recommend yes;* no measured form needs more than a handful.
5. **Keep the merged `parameter_names`/`parameters` fields** for listing, unused by the role check. *Recommend yes.* Removing them touches tests and callers for no verdict change.
6. **81.x in an empty folder outside the repository,** as 80.x. *Recommend yes.*
7. **Dataset-file arguments (§2.6), raised during implementation.**
   - (a) add an argument-dependent rule to the system-statement registry: a curated list of `(function, parameter)` pairs, each with its page's quoted "name of dataset" evidence, where any argument other than the empty string `""`, `0`, or a value traced to in-memory data (a matrix literal, a dataframe or matrix from a documented call) is `file_read`, so `not_ready`. Ship it in v0.90.0, before §3 can widen anything;
