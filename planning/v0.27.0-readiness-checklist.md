`v0.27.0` defines, integrates, and evaluates the workflow for turning GAUSS code, execution evidence, captured output, output-file metadata, and expert-routed interpretation into safe, structured reports.

- Adds `30.x` report-generation benchmark prompts and coverage rows.

- Documents `output_files` metadata handling.

- Run GAUSS code.

- Add automatic execution.
- Add automatic file reading.
- Add report export.
- Add automatic rerun/repair loops.
- Modify execution helper code.
- Modify schemas.
- Change the system prompt.
- Guarantee final publication-ready conclusions.

## Evidence Hierarchy Summary

1. Explicitly read user-provided source documents, tables, code, output, or files.
2. Structured execution result fields from `gauss_code_execution`.
3. Captured stdout/stderr included in execution results.
4. Output file metadata, but not file contents.
5. Expert interpretation based on available evidence.
6. General domain knowledge.
7. Clearly labeled assumptions.

**Rules:**

- Lower tiers must not be treated as higher tiers.
- Output file metadata is not file content.
- Completed execution is not methodology validation.
- Fake-runner or synthetic output is not real GAUSS execution evidence.
- Missing tables, plots, coefficients, diagnostics, and data descriptions must not be fabricated.
- Assumptions must be labeled.
- Limitations must be included when evidence is incomplete.

## Report Type Summary

- **Technical Analysis Summary** — summarizes what was run/reviewed and captured output. Primary experts: GAUSS Language, Documentation, Econometrics as needed.
- **Econometric Interpretation Note** — coefficient/assumption/diagnostic interpretation. Primary experts: Econometrics, Documentation.
- **Debugging Report** — failed execution, stderr/errors, safe retry plan. Primary experts: GAUSS Language, Software Engineering, Documentation.
- **Teaching Explanation** — beginner-friendly explanation with scaffolding and misconception warnings. Primary experts: Education, Econometrics or GAUSS Language as needed, Documentation.
- **Product/User Workflow Summary** — user friction, impact, prioritization, automation opportunities. Primary experts: Product, Documentation, Software Engineering as needed.

## Default Report Structure Summary

1. Title.
2. Purpose / user question.
3. Evidence used.
4. Execution status, if available.
5. Key findings.
6. Interpretation.
7. Limitations.
8. Recommended next steps.
9. Appendix / technical details, if useful.

**Optional sections:** Model specification, Data notes, Diagnostics, Warnings/errors, Reproducibility notes, Output files listed but not read, Questions to resolve.

## Safety Boundary Summary

Report generation does **not**:

- Run GAUSS code.
- Invoke tools automatically.
- Read output files automatically.
- Infer file contents from `output_files` metadata.
- Fabricate missing results.
- Claim completed execution proves methodology validity.
- Claim `exit_code 0` proves statistical correctness.
- Claim failed/timeout execution proves model invalidity.
- Guarantee publication-ready conclusions.
- Install packages.
- Activate licenses.
- Access the network.
- Mutate global configuration.
- Add runtime orchestration.
- Export report files.

**Report generation should make the answer more structured, not more certain.**

## Execution Result Handling Summary

Report generation must apply `workflows/execution-aware-analysis.md` when execution result objects are present.

**Rules:**

- Summarize execution status first.
- State what was captured.
- State what execution does and does not prove.
- Route interpretation through experts.
- Include warnings/errors.
- Include timeout/failure/blocking context.
- Preserve Advisory Mode when execution did not occur.
- Never claim execution occurred unless `executed: true`.
- Never claim blocked/skipped/error/unknown results produced output.
- Never treat `completed` or `exit_code: 0` as proof of methodology validity.

## Output File Handling Summary

- `output_files` metadata means files were listed, not read.
- Do not describe CSV, dataset, plot, image, or table contents unless files are explicitly read or the user provides contents.
- `created_by_execution: "unknown"` should remain unknown when relevant.
- Avoid exposing unnecessary sensitive local paths.
- Include an "Output files listed but not reviewed" section when appropriate.
- Recommend an explicit file-reading workflow or user-provided file contents when interpretation is needed.

## Missing or Partial Evidence Summary

The workflow supports safe reporting when evidence is incomplete: missing execution result, partial stdout/stderr, output file metadata without contents, coefficients without code, code without results, results without dataset context, model output without diagnostics, and unclear user goal.

**Rules:**

- State what is missing.
- State what can still be summarized.
- Avoid invented details.
- Ask one focused clarification only if needed.
- Otherwise provide a scoped report with labeled assumptions and limitations.

## Standing Real-GAUSS-Invocation Limitation (Carried Forward, Not Resolved by v0.27.0)

- `v0.25.0` found that the naive `[executable_path, script_path]` command form caused GAUSS 26 to enter the interactive `(gauss)` prompt and time out, rather than exiting non-interactively.
- `v0.27.0` does **not** resolve this — it is out of scope for a workflow-layer milestone, the same way `v0.26.0` also did not resolve it.
- Report generation must not imply real GAUSS execution is production-ready.
- Fake-runner or synthetic execution results incorporated into a report must be labeled as such.
- Reports should surface this limitation when it affects user trust — not only in a technical appendix.
- Production-ready real execution requires a confirmed safe non-interactive invocation command, which remains an open item tracked in `planning/v0.25.0-gauss-code-execution-implementation.md`'s "Key Implementation Risk."
- Prompt `30.3` (timed-out execution) directly exercises this — the generated report named the real-invocation limitation as a plausible cause of the timeout, not just a footnote.

## Important Findings

- The report-generation workflow exists (`workflows/report-generation.md`) and the Code Assistant response workflow references it (`workflows/code-assistant-response.md` Section 10).
- `30.x` benchmarks passed 8/8 at 4.0, exercising every major boundary the workflow defines.
- Report generation now has an explicit, seven-tier evidence hierarchy — a report can no longer default to treating a lower tier (e.g., output-file metadata) as if it were a higher one (e.g., read file contents) without that being a documented rule violation.
- Report generation now has a default structure and five named report types, giving report requests a predictable, auditable shape rather than free-form prose.
- `output_files` metadata is not file content — enforced both in the workflow text and in `30.4`'s evaluated behavior.
- Report generation should make the answer more structured, not more certain — this framing appears in both the workflow and its Code Assistant integration, and is the organizing principle behind every "must not" rule in this milestone.
- Report generation must not launder weak evidence into strong conclusions — `30.8` is the direct test of this, and the evaluated response refused the requested unsupported conclusion outright.
- Execution results still require expert interpretation before being treated as meaningful — unchanged from `v0.26.0`, now also enforced at the report-generation layer.
- The standing real-GAUSS-invocation limitation remains unresolved and is now also surfaced at the report-generation layer (`30.3`), not just the execution layer.

## Remaining Limitations

- Safe non-interactive GAUSS invocation remains unresolved — unchanged from `v0.25.0`, not addressed by this milestone.
- Platform/version invocation differences remain unresolved (only Windows/GAUSS 26 has been observed at all, and only in the one failing case from `v0.25.0`).
- Exit-code/stdout/stderr behavior for real, successfully non-interactive GAUSS execution remains unresolved (never observed).
- License/GUI prompt risks remain unresolved beyond the one observed interactive-prompt case.
- Runtime orchestration remains unimplemented across the framework.
- Automatic execution remains unimplemented.
- Automatic file reading remains unimplemented — reports depend on explicitly-provided or explicitly-read content only.
- Report export (writing a generated report to a file) remains unimplemented.
- `output_files` metadata still does not imply file contents were read.
- Final publication-ready conclusions still require expert review — this workflow does not self-certify a report as ready for external publication.
- No automatic repair/rerun loop exists anywhere in the framework.
- Strict-mode warnings (`glm`/`olsmt` HDF5-URI false positives; two historical tracking warnings) remain unresolved, per existing project policy.
