# v0.74.0 — Deterministic Pre-Execution Validation & Grounding Coverage Expansion

## 1. Repository state

Starting commit: `b1c1988` (`v0.73.0`, tagged, pushed, released). Branch: `main`. Working tree was clean at the start of this milestone. This document is written as the milestone's own capstone design/readiness record, mirroring `planning/v0.73.0-grounding-gated-generation.md`'s structure and the milestone brief's own required final-report sections.

## 2. v0.73.0 gap analysis

**Why symbol checking alone was insufficient**: `v0.73.0`'s `check_generated_symbols(...)` only asked whether a call-shaped identifier *appeared* supported (a grounded/resolved topic, a common builtin, or plausibly user-defined). It never checked argument count, argument order, argument type/shape, or any documented precondition. A generated call using only real, documented symbols could still be structurally or semantically wrong.

**The `tscsmtControl` finding**: in `v0.73.0`'s own live evaluation (`63.5`), a `FULL`-gated request correctly used the real, documented `tscsFit` function — but also called `tscsmtControl()`, which does not exist as a callable at all. `tscsFit`'s own documentation mentions "an instance of a `tscsmtControl` structure" in plain prose — `tscsmtControl` is a struct *type name*, not a function; the real constructor is `tscsmtControlCreate()`. The post-generation checker correctly flagged `tscsmtControl` as unknown, but had no way to relate it to its real companion.

**The `invpd` finding**: a real, generated `invpd(...)` example executed successfully against real GAUSS, but the input matrix was not actually verified to be symmetric and positive definite — `invpd`'s own documentation states plainly that a non-symmetric input can "erroneously appear to operate successfully." Execution success and documented-precondition satisfaction are independent facts; `v0.73.0` had no mechanism to check the latter at all.

**The limited alias-index issue**: `v0.73.0`'s natural-language resolution depended entirely on a 5-entry, hand-curated table (`meanc`, `stdc`, `vec`, `inv`, `tscsfit`). Any real GAUSS operation not in that table, and not literally named, could not resolve — a structural coverage ceiling that does not improve as the table's authors' attention moves elsewhere.

## 3. Grounding coverage expansion

`scripts/gauss_doc_concept_index.py` (new module) builds a `DocumentationConceptIndex` by scanning every `.rst` file under the caller's own `docs_root` (bounded to `MAX_INDEXED_DOC_FILES = 4000`; the real checkout used in this milestone's own development has 2,063 files, scanned in ~1.4s and cached in-process per docs_root/mtime). For each file it extracts:

- The real callable symbol name(s), preferring documented call syntax (`.. function:: y = meanc(x)` or a plain `y = f(x);` Format-heading line) over the file's own stem, since a single page can document more than one symbol (`invinvpd.rst` documents both `inv` and `invpd`).
- A small set of keywords derived from the page's own heading and "Purpose" section text (filtered against a fixed generic-word list — `_GENERIC_DOC_WORDS` — and, for a large enough corpus, a deterministic document-frequency filter; see Section 8).
- Companion symbol names referenced via `:func:`/backtick markup.

`resolve_derived_concepts(phrase, index)` scores every entry by keyword overlap with the whole phrase, proposing only entries meeting `MIN_KEYWORD_OVERLAP = 2` (a lone shared word is not enough signal), ranked/tied deterministically. `gauss_conversation_engine.resolve_concepts(...)` runs this as a supplemental pass after the existing literal-token and curated-alias passes: a single top-scoring candidate is independently re-verified via a real `command_doc_lookup.lookup(...)` call before being trusted (exactly the curated table's own discipline); more than one equally-scored candidate is reported as genuine `AMBIGUOUS`, never guessed. `GroundingSource.origin` gained a new `"derived_from_docs"` value so provenance always distinguishes `literal` / `resolved_concept` (curated) / `derived_from_docs` / `recent_topic`.

**Curated-alias role after expansion**: unchanged and fully preserved — the 5-entry table is checked first (so a curated match is never displaced by a coincidentally-scoring derived one) and remains valuable for high-value phrases the derived index's keyword-overlap heuristic cannot reliably reconstruct (short/idiomatic phrasing, or phrasing whose vocabulary doesn't literally overlap the target page's own prose).

**Resolution coverage evaluation** (Section 9's `64.1` scenario and this milestone's own module-level exploration against the real corpus): the derived index successfully proposed real, on-topic candidates for phrases with no curated coverage at all (e.g. "sum each column of my matrix" → `sumc`, tied with two other genuinely similar real functions, `cumsumc`/`matndup`, correctly triggering `CLARIFY` rather than a guess). It also has a real, disclosed limitation: bag-of-words overlap has no synonym awareness — a query for "the maximum value in each column" (the real function is `maxc`, whose purpose text says "largest element") instead proposed `maxindc` (purpose text literally says "maximum element"), a real, differently-scoped function (index of the max, not the value). This is not a fabrication — both are real, existing functions — but it is a genuine precision limitation, disclosed here rather than hidden.

## 4. Signature extraction

`scripts/gauss_pre_execution_validation.extract_documented_signature(symbol, best_match)` re-parses `command_doc_lookup`'s own already-extracted `syntax_blocks` for the exact documented call form(s) of `symbol`. Supported documentation patterns, both confirmed present in the real checkout used in this milestone's development:

- The `.. function::` directive style, one or more overload lines (`meanc`, `invpd`, `tscsFit`'s two overloads).
- The older plain Format-heading style with a bare `name = f(...);` line and no directive (`tscsmtControlCreate`).

A `[...]`-bracketed trailing argument group is parsed as optional (confirmed against the real, documented `tscsFit(y, x, grp[, tsc])` form); multiple overloads produce multiple `(min, max)` ranges, and a generated call is compatible if its argument count falls in *any* documented range. If `symbol` cannot be found call-shaped in any syntax block, `extraction_status = UNKNOWN` — never a fabricated signature.

**Fallback behavior**: `UNKNOWN` signatures never block eligibility (Section 7) — they are a disclosed gap, not a violation. **Known limitations**: extraction is argument-COUNT only; it does not parse or check parameter types, shapes, or documented default-value semantics.

## 5. Generated-call validation

`extract_generated_calls(code)` extracts call-shaped expressions (`name(`) with their own raw, top-level-split argument text and line number, skipping any line beginning with a known control-flow/declaration keyword (the same discipline `v0.73.0`'s `check_generated_symbols` already established) — not a GAUSS parser, no type inference. `validate_call(...)` compares a call's argument count against its `DocumentedSignature`, returning `COMPATIBLE` / `INCOMPATIBLE` / `UNKNOWN`. It explicitly never claims order, type, or semantic correctness merely because the count matches.

**Unknown behavior**: a symbol not among this turn's documented/resolved topics is `documented=False`, `UNKNOWN` — distinct from a documented symbol whose signature simply couldn't be extracted (`documented=True`, `UNKNOWN`).

**False-positive risk found and fixed live**: GAUSS `//`/`/* */` comments containing a parenthetical remark (e.g. `// Set the method (optional, default is 0)`) were initially mistaken for call-shaped expressions by both this new extractor and `v0.73.0`'s own `check_generated_symbols` — fixed by a new `_strip_comments_for_analysis(...)` helper applied before any symbol/call/precondition scanning (see Section 8).

## 6. Preconditions

`DocumentedPrecondition` (`symbol`, `description`, `kind`, `source`, `machine_checkable`) is a small, hand-curated, doc-verified table (`_PRECONDITION_INDEX`), exactly mirroring `_CONCEPT_ALIAS_INDEX`'s own discipline. Two entries exist: `invpd` (`machine_checkable=True`) and `inv` (`machine_checkable=False` — squareness is checkable but general invertibility is not attempted deterministically in this version).

**Machine-checkable constraint implemented**: for a *literal* matrix argument (a `{...}` literal directly, or traced through a single preceding `identifier = {...}` assignment in the same code, tolerating a trailing transpose quote on the identifier), `check_invpd_precondition(...)` deterministically checks squareness, symmetry (exact/tolerance float comparison), and positive-definiteness (Sylvester's criterion via real leading-principal-minor computation — no eigendecomposition, no external numeric library, bounded to `MAX_CHECKED_MATRIX_DIM = 6`).

**Unverified constraints**: any argument that is a bare runtime variable with no traceable literal assignment, or any more complex expression (the real documented `invpd(x'x)` OLS example is a matrix-product expression, deliberately never partially evaluated), reports `UNVERIFIED`. `inv`'s own precondition always reports `UNVERIFIED` in this version (no validator implemented). **`SATISFIED` is never returned without deterministic literal evidence — proven by test (`test_28`, `test_gauss_pre_execution_validation.py`) that no non-literal input can ever produce `SATISFIED`.**

**Exact `invpd` handling**: see Section 8's hard regression.

## 7. Execution eligibility

Three states (`ExecutionEligibility`): `INELIGIBLE`, `REQUIRES_CLARIFICATION`, `ELIGIBLE_FOR_VALIDATION`. `compute_eligibility(...)` is a pure function of already-computed evidence (generation policy, unknown symbols, ambiguous topics, call validations, precondition checks, code-extraction success) — no model call, no I/O.

**Exact deterministic rule**: `REQUIRES_CLARIFICATION` if genuine ambiguity remains (priority, mirroring `v0.73.0`'s own `CLARIFY` priority). Otherwise `INELIGIBLE` if ANY of: code extraction failed; the generation policy didn't permit generation at all; any call-shaped symbol remains unknown/unsupported; any call's documented signature is known-`INCOMPATIBLE`; any documented precondition is known-`VIOLATED`. Otherwise `ELIGIBLE_FOR_VALIDATION`.

**What `ELIGIBLE_FOR_VALIDATION` means**: exactly what Phase 12 of the brief specifies — "this code has enough deterministic support to be considered for a future controlled execution-validation workflow." **What it explicitly does NOT mean**: correct, safe, methodologically appropriate, approved for execution, or user-approved. An `UNKNOWN` signature or `UNVERIFIED` precondition does NOT block eligibility (both are disclosed gaps, not violations) — the rendered report always names any `UNVERIFIED` precondition explicitly so a reader is not misled into thinking "eligible" means "fully checked."

If this rule proves too permissive as more preconditions/signatures are added in a future milestone, it should be tightened then, informed by real evidence at that time — not preemptively guessed at now.

## 8. Exact regressions

### tscsmtControl

- **Was it detected?** Yes — reproduced live, unprompted, again in this milestone's own `64.7` evaluation (the real model made the identical mistake `v0.73.0`'s `63.5` found), and via automated test (`test_90`, `test_gauss_conversation_engine.py`).
- **Was companion evidence surfaced?** Yes, but only after a real gap was found and fixed: the real `tscsFit` documentation references `tscsmtControl` only in unmarked prose, with no cross-reference to `tscsmtControlCreate` at all — the same-page `related_links` mechanism alone found nothing. Fixed by adding a bounded fallback: a direct `command_doc_lookup.lookup(unknown_symbol, docs_root, max_results=3)` call, whose own substring-based file-name scoring found `tscsmtcontrolcreate.rst` directly. Confirmed live post-fix (`64.7`) and by test (`test_18`, `test_90`, `test_97`... see `test_gauss_pre_execution_validation.py`/`test_gauss_conversation_engine.py`).
- **Was it prevented from being eligible?** Yes — `eligibility=ineligible` in every case, live and automated. No silent correction was ever applied; the hallucinated symbol is never rewritten.

### invpd

- **Was valid SPD input recognized?** Yes — `SATISFIED`, confirmed live (`64.4`) and by real `tgauss.exe -b` execution (both the module's own test suite and a real spot check: `{2 1, 1 2}` inverted successfully).
- **Was invalid input detected?** Yes — `VIOLATED`, confirmed live (`64.5`) and by real `tgauss.exe -b` execution of the identical input, which independently raised `error G0121: Matrix not positive definite`.
- **Could runtime success override the violation?** **No.** The precondition check is computed entirely from the generated code's own literal text — it has no dependency on, and is computed before, any real execution. This was proven directly: the real GAUSS version used in this milestone's own development actually *rejected* the non-symmetric input with a clear error (rather than the "erroneously appears to succeed" case `invinvpd.rst`'s own text warns is possible) — strong convergent evidence the deterministic check predicts real failures correctly, and structural proof (by construction, not merely by this one outcome) that a hypothetical future case where GAUSS *did* silently "succeed" on bad input would still not change this module's own `VIOLATED` verdict.

### alias coverage

Across the ten `64.x` live scenarios, resolutions came from: **literal** token match (`invpd`, `inv`, `tscsFit`, `meanc` when named directly — most scenarios), **curated alias** (`meanc` via "column means" in `64.2`/`64.10`, `inv` via "invert this matrix" in `64.4`/`64.5`/`64.8`), and **derived-from-docs** (the `64.1` tie among `cumsumc`/`matndup`/`sumc`, correctly triggering `CLARIFY`). No live scenario in this bounded set happened to produce a single, unambiguous, previously-uncovered derived resolution — but the module's own automated tests (`test_06`/`test_09`, `test_gauss_doc_concept_index.py`) and a direct exploration against the real corpus (Section 3) confirm the mechanism works correctly on its own, including honestly surfacing ambiguity rather than guessing when real, similar functions exist. The curated table remains necessary for the small set of high-value phrases (e.g. "panel regression" → `tscsfit`) whose vocabulary doesn't literally overlap the target page's own prose closely enough for the derived index's bag-of-words scoring to find on its own.

## 11. Safety

Can conversational code:
- **execute GAUSS? NO.**
- **invoke shell? NO.**
- **write files? NO.**
- **apply repairs? NO.**
- **bypass approval? NO.**
- **self-declare eligibility through the model? NO** — `compute_eligibility(...)` takes no provider/model-shaped argument at all (structurally confirmed: `test_40`), is computed entirely within `gauss_pre_execution_validation.py`/`gauss_conversation_engine.py`, and no code path allows a provider's own response text to alter its result.

All six answers are NO, confirmed both structurally (`test_39`/`test_93`/`test_94`/`test_35` scan for banned imports/tokens — `subprocess`, `os.system`, `eval`, `exec`, file-write calls, and every `gauss_execution_*`/`gauss_repair_*`/`gauss_verification_*` module name) and behaviorally (every live scenario in Section 9).

## 14. Product impact

**Yes, pre-execution validation materially improved the ability to distinguish plausible GAUSS code from code actually supported by authoritative evidence**, with direct, observed evidence:

- The `tscsmtControl` hallucination — real, reproduced live twice now (`63.5`, `64.7`) — is caught both times, and as of this milestone is paired with a genuinely useful diagnostic (the real companion, `tscsmtControlCreate`) that `v0.73.0` could not surface.
- The `invpd` precondition regression is now a hard, tested, deterministic guarantee rather than an unhandled gap: a syntactically perfect, symbol-correct, even successfully-*executing* call can still be correctly marked `INELIGIBLE` when its own documented precondition is violated — proven by real, convergent GAUSS execution (`error G0121`) matching the deterministic prediction exactly.
- A genuinely new, previously-unobserved distinction surfaced live: real execution can validate that code *runs* while a model's own separate prose claim about the result is still wrong (`64.4`) — this milestone's own architecture doesn't (and can't) fix that, but it does keep it clearly separate from the precondition/eligibility verdict, which is exactly the "methodological validity stays separate" discipline Phase 15 of the brief calls for.

## 15. Remaining limitations

- **Incomplete signature extraction**: argument count only; no order, type, or shape checking. Two documentation formats are supported; an unanticipated third format would fail closed to `UNKNOWN`, not silently guess.
- **Incomplete concept indexing**: the derived index found a real, on-topic candidate for a real query with no curated coverage (`sumc`), but demonstrated a real synonym-matching miss (`maxc` vs. `maxindc`) — bag-of-words overlap has no semantic understanding.
- **Limited static semantics**: no dimension/conformability checking, no type checking, no data-flow analysis beyond simple same-code literal-assignment tracing.
- **Runtime-dependent values are always `UNVERIFIED`, by design** — this module will never evaluate a real GAUSS expression itself.
- **Unverified preconditions remain common** — only one function family (`invpd`) has an implemented deterministic validator; every other documented precondition anywhere in the real corpus is `UNVERIFIED` if referenced at all (most aren't referenced, since no curated precondition entry exists for them).
- **Model dependence remains real** — `qwen2.5-coder:7b` still hallucinates when ungrounded or under-grounded; this milestone makes that harder to act on undetected, not impossible to attempt.
- **`docs-root` dependency, local hardware/Ollama dependence, no execution, no autonomous debugging, no file editing** — all unchanged from `v0.71.0`-`v0.73.0`.
- **QA-intent gap** (Section 13): the new eligibility computation does not yet run for code-shaped answers to QA-classified questions, unlike `v0.73.0`'s own intent-independent symbol check.
- **Anthropic remains not live-network-tested**, unchanged.

## 16. Recommendation

The project is ready for **human alpha testing of deterministic pre-execution validation** — the architecture demonstrably improves, with direct live and real-GAUSS evidence, the exact reliability gaps `v0.73.0`'s own evaluation disclosed, while preserving every existing safety boundary unchanged (zero diff on core pipeline modules; all six safety questions answered NO).

The project is **not** ready for **controlled execution handoff** as the next milestone. The evidence gathered here (Sections 9-10, 14-15) shows real, useful, but still narrow and incomplete validation coverage: one precondition family implemented, argument-count-only signature checking, a QA-intent gap in the eligibility computation itself, and a documented synonym-matching limitation in the newly-expanded resolution layer. **Do not begin the next milestone automatically** — a future milestone's scope (e.g. broader precondition coverage, closing the QA-intent gap, or an explicit, approval-gated execution handoff) should be a deliberate decision informed by this report and the real transcripts in `evaluations/runs/2026-09-12-code-assistant-pre-execution-validation-run-*.md`, not an automatic continuation.
