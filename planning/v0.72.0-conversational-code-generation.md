# v0.72.0 — Conversational GAUSS Code Generation and Multi-Source Grounding

## 1. Objective

Turn `gauss-ai` from a conversational Q&A assistant into a conversational GAUSS coding assistant: a user can ask for GAUSS code and receive it, grounded where possible, honestly labeled where not, never executed, never written to a file, never treated as an approved repair. Not autonomous execution; not controlled tool orchestration.

## 2. What this milestone is not

Not autonomous conversational execution, not model-controlled subprocess execution, not direct shell tools, not file writes from chat, not conversational source-file editing, not automatic repair application, not autonomous retry/debug loops, not multi-file autonomous changes, not IDE integration, not durable conversation persistence, not a database/cloud session, not telemetry, not model fine-tuning, not bundled model weights, not auto-install of Ollama, not automatic model pulls, not arbitrary web retrieval, and not a vector-database/full-RAG rewrite.

## 3. Repository state at the start of this milestone

`v0.71.0` (Local Ollama Provider & Live Conversational Validation) was the current released state: three interchangeable providers (`fake`/`ollama`/`anthropic`), real live Ollama validation, an execution/repair-intent keyword boundary, and an effectively single-token documentation-grounding design (`ground(...)` returns the *first* matching topic, never more than one). `61.4`'s own live evaluation had already disclosed the resulting gap: a comparison question naming two real, documented topics could only ever ground on one of them.

## 5. Intent classification

`classify_intent(question) -> Intent` is deterministic, bounded phrase matching — not a language model. Order matters and is safety-relevant: `_RUN_KEYWORDS` and `_REPAIR_KEYWORDS` are checked first, so a phrase that also contains words like "code" or "this" is never misclassified as a mere code-generation request. `Intent.CLI_INVOCATION` exists on the enum for completeness but is never produced by this module — that interception remains entirely upstream in `gauss_ai_chat.py`, unchanged from `v0.71.0`.

## 6. Multi-source grounding

`ground_multi(...)` looks up every distinct candidate token in a question (not just the first that hits), bounded to `MAX_GROUNDING_SOURCES = 4`, deduplicated, with an error code (if present) always checked first exactly as the legacy `ground(...)` did. `GroundingStatus` (`GROUNDED`/`PARTIALLY_GROUNDED`/`UNGROUNDED`) is a derived property of `GroundingBundle`, computed purely from whether sources exist and whether any referenced topic went unmatched — it can never be constructed in an internally inconsistent state, and is never trusted from, or reported by, the model. A bounded `recent_topics` list (`MAX_RECENT_TOPICS = 5`) on `ConversationState` generalizes the old single-`last_topic` fallback so a multi-turn conversation can resolve context against more than the single most recent topic.

**Example, verified live**: "What is the difference between reshape and vec in GAUSS?" now grounds on both `reshape` and `vec` together (`GROUNDED`, two sources) — the exact gap `v0.71.0`'s own `61.4` disclosed as not yet fixed.

## 7. Code generation

Prompted via `CODE_GENERATION_SYSTEM_PROMPT_ADDENDUM`, added as an extra system message only for `Intent.CODE_GENERATION` turns: prefer documented syntax, never invent a function name (say so instead), distinguish predicted output from execution evidence, keep methodological appropriateness separate from syntax correctness, and ask a clarifying question only when necessary. `extract_code_blocks(...)` conservatively extracts fenced code blocks (```` ``` ```` or ```` ```gauss ````) from the model's response text — structural, never interprets prose as code, never executes anything, never writes anything to disk (verified by test). `AnswerResult.generated_code`/`.executed`/`.methodologically_validated` make status explicit and machine-readable; the last two are always `False` — there is no code path anywhere in this module capable of setting either to `True`.

## 8. Safety

Can conversational code generation:
- **execute GAUSS? NO** — no import of any execution module anywhere in `gauss_conversation_engine.py`/`gauss_chat_provider.py` (structurally verified by tests scanning the modules' own import lines).
- **invoke shell commands? NO** — no `subprocess`/`os.system` reference anywhere in either module (structurally verified).
- **write files? NO** — no `open(`/`write_text`/`write_bytes` call anywhere in `extract_code_blocks(...)` or any code-generation code path (structurally verified).
- **approve repairs? NO** — no import of any approval/gate module.
- **apply repairs? NO** — no import of any repair-application module.
- **bypass execution confirmation? NO** — `classify_intent(...)` checks execution/repair phrasing before code-generation classification, and this holds even immediately after a code-generation turn (verified live against a real, reachable model in `62.8`/`62.9`, and deterministically in `test_46`-`test_48`).

All six answers are NO. Two real gaps in the *interception* keyword coverage (not the safety guarantee itself) were found live and fixed within this milestone — see Section 10.

## 9. Live Ollama validation

**Model**: `qwen2.5-coder:7b`. **Environment**: the same real, locally running Ollama installation validated in `v0.71.0`, unchanged. **Scenario count**: ten (`62.1`-`62.10`), each run through the installed `gauss-ai` CLI, real transcripts in `evaluations/runs/2026-09-09-code-assistant-conversational-code-generation-run-*.md`.

**Results**: 8 of 10 scenarios passed cleanly (`62.1`, `62.3`, `62.4`, `62.5`, `62.6`, `62.8`, `62.9`-after-fix, `62.10`). One scenario (`62.2`) passed on architecture/disclosure but exposed a real model hallucination. One scenario (`62.7`) is recorded as a genuine **Fail** — the model fabricated an entire nonexistent panel-regression syntax pattern with zero disclosed uncertainty.

**Syntax failures / hallucinations**: `62.2`'s `colmean` (real function: `meanc`) and `62.7`'s entire `panel`/struct-field-assignment pattern, both confirmed nonexistent via real GAUSS execution.

**Grounding failures**: none in the architecture itself — every disclosed gap (`62.2`'s "means" stopword, `62.10`'s "data" false positive) was found and either fixed or explicitly disclosed as a known limitation, never silently hidden.

**Latency observations**: consistent with `v0.71.0`'s own findings — genuinely-answered turns took several seconds to tens of seconds; deterministic execution/repair-boundary redirects returned near-instantly, corroborating that the provider was not invoked for those turns.

## 10. Real GAUSS spot validation

Examples executed via `tgauss.exe -b` on real GAUSS 26.1.4:
- `reshape(x, 2, -1)` (from `62.1`/`62.6`-turn-2 style code) — **matches** the official documentation's own worked example exactly.
- `colmean(y)` (the model's `62.2` invention) — **fails**: `error G0025 : Undefined symbol: 'colmean'`, confirming the hallucination.
- `ones(2, 3)` + `print` (`62.5`) — **matches**: predicted values and shape correct; only a cosmetic floating-point display difference from the model's simplified prediction.
- `reshape` + `meanc` combined (`62.6`'s final turn) — **matches**: real column means computed correctly.

Predicted behavior matched actual behavior in every case except the confirmed hallucination (`colmean`), which the architecture had already flagged as ungrounded before the model invented it.

## 11. Model suitability

**SUITABLE WITH LIMITATIONS.**

`qwen2.5-coder:7b` reliably produces correct, minimal, documented GAUSS syntax when the relevant documentation is actually retrieved and provided as grounding evidence (`62.1`, `62.3`, `62.5`, `62.6`), and sometimes explicitly discloses uncertainty about an invented name (`62.4`). It also, at least twice in this small ten-scenario sample, confidently fabricated syntax with no disclosed uncertainty at all when grounding evidence was absent or incomplete (`62.2`, and severely in `62.7`) — directly contrary to its own explicit system-prompt instructions. This inconsistency, not any single failure, is the reason for "WITH LIMITATIONS" rather than an unconditional "SUITABLE": the model cannot be trusted to reliably self-disclose when it is guessing. **What needs improvement**: either a more reliable model for uncertainty disclosure, or an architectural mitigation such as declining to generate code at all (rather than falling back to general-knowledge generation) when grounding evidence for the request is entirely absent — explicitly recommended for a future milestone, not implemented here.

## 15. Real defects found live and fixed within this milestone

1. **`"means"` stopworded, hiding a real `meanc` lookup** (`62.2`): a comparison-question-era stopword from `v0.70.0` silently prevented `ground_multi(...)` from ever attempting to resolve "column means" to `meanc`, so the disclosure claimed complete grounding on `reshape` alone while the real model went on to invent `colmean`. Fixed by removing `"means"` from `_STOPWORDS` (documented inline with this exact finding); re-verified live. This did not eliminate the model's own hallucination — it made the underlying gap honestly visible instead of silently hidden.
2. **"apply that code to my file" not recognized as a repair/application request** (`62.9`): the existing `_REPAIR_KEYWORDS` list (already extended once, in `v0.71.0`, for a `fix`/`repair`/`apply`-`change`-shaped phrase family) did not cover "apply ... code ... to a file" phrasing. Fixed by extending `_REPAIR_KEYWORDS` with an "apply/add/insert/put/write/save ... code" phrase family, covered by `test_47b_...`; re-verified live against the same real model.

## 16. Remaining limitations (not fixed in this milestone)

- **Model hallucination risk remains real and unmitigated at the architecture level** (Section 11) — the primary reason conversational execution remains out of scope.
- **Natural-language phrasing does not map to function names.** No synonym map exists by design; "column means" will not resolve to `meanc` unless the function is actually named.
- **Retrieval-precision false positives remain possible** on generic English words (`62.10`'s "data").
- **Anthropic provider still not live-network-tested** — unchanged from `v0.70.0`/`v0.71.0`.
- Every item in Section 2 remains not implemented, by design.

## 17. Recommendation

All planned phases for this milestone are complete: intent classification, multi-source grounding, code generation with explicit machine-readable status, live validation (ten real scenarios, two real defects found and fixed, one real model-quality Fail honestly recorded), real-GAUSS spot validation, comprehensive automated testing, a new evaluation category, and documentation updates. The project is ready for **human alpha testing of conversational code generation**, with the explicit, disclosed caveat that generated code must be treated as unverified until checked — this is stated to testers directly in updated documentation. **Do not begin the next milestone automatically** — in particular, do not treat this milestone's real, disclosed model-hallucination findings as solved; a future milestone's scope (e.g. grounding-gated generation, or intent routing and controlled tool orchestration) should be a deliberate decision informed by this report and the real transcripts in `evaluations/runs/2026-09-09-code-assistant-conversational-code-generation-run-*.md`, not an automatic continuation.
