# v0.76.0 — GAUSS Syntax Validation & Validation-Coverage Hardening

## 1. Starting state

- HEAD at milestone start: `eb21658` (`v0.75.0` tag, package version `0.75.0`), branch `main`, working tree clean.
- `scripts/gauss_pre_execution_validation.py` (1541 lines) is the deterministic validation layer: documented-signature extraction, argument-count/parameter-role checking, four documented preconditions (`invpd`/`inv`/`solpd`/`chol`), predicted-output claim detection/verification, a 3-state `ExecutionEligibility`, and a `ValidationCoverage` summary (symbol/signature/parameter-role/precondition/predicted-output, each `COMPLETE`/`PARTIAL`/`NOT_APPLICABLE`/`UNKNOWN`).
- `scripts/gauss_conversation_engine.py` wires this module in unconditionally (`v0.75.0`'s own universal-routing fix): any code-shaped answer, regardless of intent, gets a `PreExecutionValidationResult`. `gauss_ai_chat.py._render_answer` renders it via `validation_mod.render_validation_report(...)`.
- Neither module has any syntax-shape checker at all today: a matrix literal is only ever inspected by `_parse_literal_matrix`/`_find_literal_matrix_for_argument`, which is a best-effort extractor for precondition/predicted-output checking, not a validator — a literal it cannot parse is reported `UNVERIFIED`/absent, never `INVALID`.

## 2. Gap analysis (Phase 1)

**The exact `chol` finding** (`evaluations/runs/2026-09-12-code-assistant-universal-code-validation-run-008.md`, scenario `65.8b`): asked for `chol` on `{-1 0, 0 -1}` (a real, invalid, non-positive-definite input), the live `qwen2.5-coder:7b` model wrote `x = {-1 0; 0 -1};` — a semicolon row separator, not GAUSS's real comma convention. `_find_literal_matrix_for_argument` correctly declined to guess and reported the `chol` precondition `UNVERIFIED` — safe, but uninformative: the code was never flagged as having a syntax problem at all, and `pre_execution_eligibility` stayed `eligible_for_validation`.

**Real-GAUSS confirmation performed for this milestone** (`tgauss.exe -b`, this session):

```
x = {-1 0; 0 -1};       ->  -1.0000000  0.0000000  +DEN  0.0000000  -1.0000000   (ONE row, 5 elements, exit 0, no error)
x = {-1 0, 0 -1};       ->  -1.0000000  0.0000000
                             0.0000000  -1.0000000                              (correct 2x2, exit 0)
x = ;                   ->  error G0105: Bad expression or missing arguments (exit 0, stderr text)
```

This is worse than an outright parse error: GAUSS silently accepts the `;`-separated form and folds it into a single malformed row containing a `+DEN` (denormal/garbage) placeholder element — a silent semantic corruption, not a loud failure. `UNVERIFIED` is the honest response for "I can't check this precondition," but it is the wrong response for "this input is not well-formed GAUSS syntax at all." That distinction is the missing layer this milestone adds.

**Documented provenance for the row-separator rule**: `let.rst` (official docs, `docs-root` checkout), Format/Examples section: `let x = { 1 2 3, 4 5 6, 7 8 9 };` — rows separated by `,`, elements within a row separated by whitespace; "If curly braces are used, the `let` is optional," so the same literal syntax applies to a bare `x = {...}` assignment.

**Validation-coverage gap**: `ValidationCoverage` (`v0.75.0`) already tracks which checks ran, but nothing consumes it as a hard gate — `ExecutionEligibility` is computed independently of coverage breadth, so a code block with mostly `UNKNOWN` evidence and a code block with fully `COMPLETE` evidence can both be `ELIGIBLE_FOR_VALIDATION` with no way for a caller (or a future execution-handoff milestone) to tell them apart.

## 3. Design (Phases 2–17) — all added to `gauss_pre_execution_validation.py`

Extending the existing module, not a parallel one, per `CLAUDE.md` convention and this module's own existing docstring style (dated/attributed narrative comments, explicit provenance).

### 3.1 `SyntaxValidationResult` (Phase 2)

```
class SyntaxStatus(str, Enum): VALIDATED, INVALID, PARTIAL, UNKNOWN
@dataclass(frozen=True)
class SyntaxIssue: rule, message, line_number, construct
@dataclass(frozen=True)
class SyntaxValidationResult: status, issues, validated_constructs, unknown_constructs
```

`VALIDATED` means only "no syntax violation was found within this version's implemented deterministic coverage" — documented explicitly in the class docstring, never "fully correct GAUSS."

### 3.2 Bounded scope (Phase 3)

No parser, no grammar. Operates on already-comment-stripped code (the same `_strip_comments_for_analysis` convention every existing check in this module already follows). Checks, each independently sourced:

| Check | Rule source |
|---|---|
| Matrix-literal row separator (`,` not `;`) | `let.rst` (documented) + real `tgauss.exe -b` execution (this session) |
| Matrix-literal ragged/empty rows | `let.rst` (documented — a literal's rows are meant to be conformable) |
| Balanced `{}`/`()`/`[]` | GAUSS is a bracket-delimited language throughout its own docs; verified against every real syntax example already in this repo's own curated precondition/signature fixtures |
| Dangling assignment (`x = ;`) | Real `tgauss.exe -b` execution (this session): `error G0105: Bad expression or missing arguments` |
| Incomplete call (`meanc(` unterminated) | Falls out of the balanced-parenthesis rule above |
| Malformed call argument separators (stray/leading/trailing comma) | Narrow, repository-convention rule: a GAUSS argument list is comma-separated values, never an empty slot |
| Unterminated double-quoted string | `let.rst`'s own `"dog""cat"` example (double quotes are the unambiguous string delimiter — single quote is reserved for the transpose operator in generated code and is deliberately NOT treated as a string delimiter here, to avoid false positives on `x'`) |

A small `_SYNTAX_RULE_REGISTRY: dict[str, SyntaxRule]` records `name`/`description`/`source`/`applies_to` for each rule above, referenced by name from every `SyntaxIssue.rule`.

Explicitly NOT attempted: `do/while/for`, `if/endif`, `proc/endp` block validation, string concatenation (`$+`), complex/scientific-notation literal validation, character-element matrix literals beyond the two structural rules above. Any of these found in code is recorded in `unknown_constructs` (e.g. `"control_flow_block"`), never silently ignored and never guessed at.

### 3.3 Call-expression parsing (Phase 6)

`extract_generated_calls` already extracts nested calls as independent flat entries with correctly-bounded top-level argument splitting (`meanc(reshape(x, 2, 3))` already yields two `GeneratedCall`s: `meanc` with 1 argument `"reshape(x, 2, 3)"`, and `reshape` with 3 arguments) — confirmed by reading the existing `_find_matching_paren`/`_split_top_level_args` implementation before writing new code, per this milestone's "extend, don't duplicate" instruction. No representation change needed; this milestone adds a regression test proving it and a `check_call_delimiters` pass (stray-comma detection) that reuses `_split_top_level_args` output.

### 3.4 Coverage hardening (Phase 8)

`ValidationCoverage` gains `syntax_check: str` (same four-state vocabulary). A new `EvidenceProfile` enum (`MINIMAL` / `PARTIAL` / `BROAD`) is computed from the five non-orthogonal dimensions (symbol/signature/parameter-role/precondition/syntax — **not** predicted-output, which stays orthogonal per Phase 17): `BROAD` requires symbol/syntax `COMPLETE` and every other dimension `COMPLETE` or `NOT_APPLICABLE`; `MINIMAL` when syntax is `UNKNOWN` or two-plus dimensions are `UNKNOWN`; `PARTIAL` otherwise. No numeric score.

### 3.5 Handoff readiness (Phases 9–11, 16, 17)

```
class HandoffReadiness(str, Enum): NOT_READY, REVIEW_REQUIRED, HANDOFF_CANDIDATE
@dataclass(frozen=True)
class ReadinessResult: state, reasons
```

`compute_handoff_readiness(...)` is pure/deterministic (no model input), computed from: `ExecutionEligibility`, `SyntaxValidationResult`, `call_validations`, `preconditions`, `EvidenceProfile`. Rules:

1. `eligibility != ELIGIBLE_FOR_VALIDATION` → `NOT_READY` (both `INELIGIBLE` and `REQUIRES_CLARIFICATION` — a future handoff workflow has nothing to consider until eligibility itself is clean).
2. `syntax.status == INVALID` → `NOT_READY`, reasons quote the syntax issues directly.
3. Otherwise, collect review reasons: `syntax.status in (PARTIAL, UNKNOWN)`; any documented call with an unknown signature (`signature_known == False`); any `UNVERIFIED` (runtime-dependent) precondition; `evidence_profile != BROAD`. Any one of these → `REVIEW_REQUIRED`.
4. No review reasons and no violation → `HANDOFF_CANDIDATE`, reasons list the positive evidence (grounded, symbols supported, signatures compatible, syntax validated, no known precondition violations, coverage broad).

This directly encodes the milestone's own default policy: an **unknown** signature or an **unverified** runtime-dependent precondition never silently becomes `HANDOFF_CANDIDATE` — they force human review — while a **known violation** (invalid syntax, incompatible signature, violated precondition, mismatched parameter role, unknown symbol) is `NOT_READY`, never merely "needs review."

`HANDOFF_CANDIDATE` explicitly does not mean correct, safe, approved, or executed — documented on the enum itself, mirroring `ExecutionEligibility`'s own existing docstring discipline.

### 3.6 Predicted output stays orthogonal (Phase 17)

No change to `compute_eligibility`'s signature; `compute_handoff_readiness` also never takes a predicted-output argument, by construction (cannot even accidentally consume it).

### 3.7 Wiring (`gauss_conversation_engine.py`, `gauss_ai_chat.py`)

`_validate_pre_execution` gains: `syntax = validate_syntax(...)` per code block (merged conservatively — `INVALID` if any block invalid, else worst-of across blocks), passed into `compute_validation_coverage` and a new `compute_handoff_readiness` call. `PreExecutionValidationResult`/`AnswerResult` each gain `syntax: SyntaxValidationResult | None` and `readiness: ReadinessResult | None` fields (defaulted, so every existing construction site stays valid). `render_validation_report` gains syntax/readiness lines. No new import edges into any execution/repair/verification module — verified by extending the existing structural safety test.

## 4. Scope exclusions (Phase 25)

No conversational execution, no execution handoff, no subprocess/shell/file-write path, no autonomous retry, no full GAUSS parser. This milestone only adds deterministic advisory evidence and a readiness *label* — it executes nothing and approves nothing.
