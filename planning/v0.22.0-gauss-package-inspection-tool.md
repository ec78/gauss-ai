# v0.22.0 - GAUSS Package Inspection Tool

## Release Goal

`v0.22.0` plans the second read-only GAUSS tooling capability: package inspection. Environment detection (`v0.21.0`) answers "is GAUSS installed, and which executable/version would we use?" Package inspection answers a distinct, narrower question: "given that GAUSS environment, which GAUSS packages/application modules appear available?"

The goal is to define how the assistant can inspect or infer which GAUSS packages are available in a detected GAUSS environment.

`v0.22.0` should plan a tool that can:

- Use the selected GAUSS executable/environment from environment detection.
- Identify likely installed GAUSS packages.
- Distinguish base GAUSS availability from package availability where possible.
- Return structured package availability results.
- Support package-aware assistant responses.
- Preserve Advisory Mode fallback.
- Avoid running user GAUSS code.
- Avoid executing statistical analysis.
- Avoid activating Execution Mode.
- Avoid runtime orchestration.

This is package inspection planning only. It is not code execution.

## Current State

- Environment detection is implemented in `v0.21.0` (`scripts/gauss_environment_check.py`).
- The helper can select the newest GAUSS version by default when multiple installations are found.
- It can honor a user-provided executable path and a user-specified preferred version, both overriding the newest-version default.
- No package inspection exists yet — there is no `tools/gauss_package_inspection.md`, `schemas/gauss_package_inspection.schema.json`, or `scripts/gauss_package_inspection.py`.
- No GAUSS code execution exists yet.
- Code Assistant behavior remains advisory/verified-knowledge unless future tools are explicitly invoked — this milestone does not change that.

## Why Package Inspection Matters

- Some GAUSS commands are base commands, available in every installation.
- Some capabilities may live in GAUSS application modules or packages that require separate installation or licensing (for example, `tscsFit` from the commercial TSMT package, per `KNOWN_LIMITATIONS.md`).
- The assistant should not suggest package-dependent workflows as if they are always available.
- Package inspection helps the assistant distinguish:
  - "GAUSS is installed."
  - "This package is installed."
  - "This package status is unknown."
  - "This package is required but missing."
- Package inspection is prerequisite context for safer future execution — knowing what's installed before attempting to run anything that depends on it.

**Examples:**

- If a command belongs to a separately installed module, the assistant should say that package availability must be checked, rather than assuming it.
- If package status is unknown, the assistant should avoid overclaiming either way.
- If a package is missing, the assistant should provide fallback/advisory guidance rather than failing or refusing to help.

## Relationship to Environment Detection

Package inspection depends on environment detection, but environment detection alone is not package inspection.

Package inspection should use:

- Selected executable path.
- Selected GAUSS version.
- Platform.
- Detection status.
- Candidate details if needed.

But:

- GAUSS found does not mean packages are installed.
- GAUSS version known does not mean package availability is known.
- `execution_candidate` does not mean package inspection has occurred.
- Package inspection should gracefully return unknown or unavailable when environment detection is `not_found`, `ambiguous`, `inaccessible`, `error`, or `unknown`.

## Proposed Tool

**Possible file:** `tools/gauss_package_inspection.md`

**Possible implementation file later:** `scripts/gauss_package_inspection.py`

**Tool name:** `gauss_package_inspection`

**Purpose:**

- Inspect or infer installed GAUSS packages.
- Identify whether requested packages appear available.
- Report package availability as installed, missing, unknown, or inaccessible.
- Distinguish base GAUSS from package-dependent functionality where possible.
- Return structured output suitable for assistant reasoning.

**Tool permission level:**

- Read-only environment/package inspection.
- No user GAUSS code execution.
- No statistical analysis.
- No package installation.
- No license activation.
- No environment mutation.
- No runtime orchestration.

This tool is classified as read-only per `TOOL_SPEC.md`'s Permission Model, the same category as `gauss_environment_check` — in contrast to the future GAUSS Code Execution Tool, which remains high-risk.

## Package Inspection Strategy

Plan possible approaches without implementing them.

### Environment-based inspection

Use output from `gauss_environment_check`:

- Selected executable path.
- Version.
- Platform.
- `detection_status`.

If environment detection is not `found`, package inspection should usually return `unavailable` or `unknown` with Advisory Mode fallback.

### Filesystem-based inspection

Explore package/application directories where GAUSS stores installed modules, if known.

Important:

- Do not overclaim exact directories until verified.
- Use read-only checks only.
- Handle platform differences.
- Handle user-installed vs. system-installed packages.
- Handle multiple GAUSS versions with separate package sets.

### Configuration/path inspection

Consider whether GAUSS uses:

- Library paths.
- Package directories.
- Application directories.
- Configuration files.
- Startup files.

Do not assume final structure without verification.

### Minimal GAUSS metadata query

Discuss but do not commit:

- A future package-inspection implementation may need a minimal GAUSS query to list packages.
- If such a query requires invoking GAUSS, classify it separately and treat it as higher risk than filesystem inspection.
- It must not run user GAUSS code.
- It must use a timeout.
- It must not mutate state.
- It must clearly report that GAUSS was invoked for package metadata only, if implemented later.

For `v0.22.0` planning, prefer filesystem/read-only inspection first — this mirrors `v0.21.0`'s own precedent, where `--allow-version-query` was accepted into the input contract but deliberately left as a documented no-op until a safe flag is confirmed.

## Proposed Input Contract

Future inputs:

- `environment_check_result` — optional object.
- `executable_path` — optional string.
- `gauss_version` — optional string.
- `platform_hint` — optional string.
- `requested_packages` — optional array of strings.
- `package_search_paths` — optional array of strings.
- `allow_metadata_query` — optional boolean.
- `inspection_timeout_seconds` — optional integer.
- `strict` — optional boolean.

Input rules:

- If `environment_check_result` is provided and valid, use it as primary context.
- If `executable_path` is provided directly, use it cautiously.
- `requested_packages` narrows inspection to named packages.
- `package_search_paths` should be read-only.
- `allow_metadata_query` should default to `false` or implementation-defined until safety is established.
- `strict` should avoid guessing outside supplied paths/context.
- Inputs must not cause file mutation.

## Package Status Semantics

### complete

Use when inspection was performed and package availability is considered sufficiently determined for the requested scope.

### partial

Use when some packages or paths were inspected but uncertainty remains.

### unavailable

Use when package inspection cannot be performed because the GAUSS environment is not found, ambiguous, inaccessible, or unsupported.

### error

Use when inspection fails unexpectedly.

### unknown

Use when the tool cannot determine status.

## Default Behavior with Multiple GAUSS Versions

Ties directly to `v0.21.0`'s newest-version default rule:

- Package inspection should use the selected GAUSS environment from environment detection.
- If GAUSS 24, 25, and 26 are installed and environment detection selects GAUSS 26, package inspection should inspect the GAUSS 26 package context by default.
- If the user explicitly selects GAUSS 25, inspect the GAUSS 25 package context.
- Do not mix package results across versions unless explicitly requested.
- Report the GAUSS version/environment being inspected.
- Package availability may differ by GAUSS version — a package available under GAUSS 25 is not guaranteed available under GAUSS 26, or vice versa.

## Assistant Response Behavior

**If package installed:**

- State the package appears available.
- Still avoid claiming code execution.
- Still verify command syntax via the GAUSS Language Expert/evidence.
- Mention package/version if known.

**If package missing:**

- State the package was not detected.
- Do not claim GAUSS is missing.
- Provide advisory fallback.
- Suggest installing/enabling the package only at a high level, unless installation guidance is verified.

**If package unknown:**

- State status is unknown.
- Avoid overclaiming.
- Provide options: continue in Advisory Mode, provide a path, inspect manually later.

**If inspection is unavailable:**

- Explain package inspection could not be performed.
- Continue in Advisory or Verified Knowledge Mode.

**If package inspection errors:**

- Report a structured error.
- Do not break the assistant.
- Continue advisory reasoning where possible.

## Expert Boundary Rules

- Package inspection supports the GAUSS Language Expert but does not replace command evidence.
- Package availability does not validate syntax.
- Package availability does not validate statistical methodology.
- Package availability does not validate maintainability.
- Package availability does not validate documentation quality.
- Package availability does not validate education/learning design.
- Package availability does not validate product value.
- Package availability does not imply execution occurred.
- A missing package should not be treated as proof that a method is invalid.
- An installed package should not be treated as proof that a method is appropriate.

## Safety Requirements

- Read-only inspection.
- No user GAUSS code execution.
- No analysis execution.
- No package installation.
- No license modification.
- No environment mutation.
- No file modification.
- No deletion.
- No hidden invocation unless explicitly allowed later.
- Timeouts for any metadata query, if implemented.
- Structured errors.
- Advisory fallback after any failure.
