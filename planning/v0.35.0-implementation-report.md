# v0.35.0 Implementation Report: Real Execution Reliability and Output Verification

## Milestone Purpose

`v0.35.0` broadens confidence in the real controller execution path `v0.34.0` established, by verifying — across five bounded, individually authorized real GAUSS invocations, driven through the complete orchestration controller — that the path behaves reliably across repeated independent requests, and that it correctly handles output-file creation, declared expected outputs, and output-file metadata (never content). Real testing surfaced and led to the fix of a genuine controller bug in expected-output comparison. **This does not constitute production readiness** — see `planning/v0.35.0-readiness-checklist.md`.

See also `planning/v0.35.0-real-execution-reliability-and-output-verification.md` for this milestone's upfront scope/plan.

## Explicit Authorization Received

Up to **five** real GAUSS invocations were authorized, subject to preflight/safety requirements, limited to: the verified Windows environment, GAUSS 26.1.1.5516, `C:\gauss26\tgauss.exe`, inline code only, contained disposable working/output directories, minimal non-destructive code, no network, no credentials/secrets, no arbitrary user-file access, no GUI execution. No automatic retry was authorized. Every invocation had to use a new canonical request, a new orchestration instance, fresh request-bound confirmation, a stated purpose, and be recorded individually.

### Invocation 3 — `output-created`

```
... --working-directory "...\gauss-ai-reliability-v035-output-created" \
  --output-directory "...\gauss-ai-reliability-v035-output-created" \
  --session-id "v035-session-output-created" --scenario output-created --invocation-number 3
```

`request_hash: 40204e90...`, `expected_output_files: ['gauss_output.txt']`. `execution_status: completed`, `exit_code: 0`, `stdout: 'hello output test\n'`. `output_file_count: 1` — `path='C:\...\gauss-ai-reliability-v035-output-created\gauss_output.txt' size_bytes=19 file_type='text/plain' created_by_execution='unknown'`. Post-run: exactly two files (the generated script and `gauss_output.txt`, 19 bytes — metadata size confirmed via directory listing only, content never read), no lingering process.

**Bug found:** `failure_category` was reported as `FailureCategory.MISSING_EXPECTED_OUTPUT`, despite the file genuinely having been created and correctly discovered. Root cause: `_missing_expected_outputs(...)` in `scripts/gauss_runtime_orchestration.py` compared the declared expected filename (`"gauss_output.txt"`) against `result.output_files[].path` (always an absolute path, per `_discover_output_files` in `scripts/gauss_code_execution.py`) using exact string equality — a bare declared filename can never equal an absolute path. The canonical request contract (`planning/v0.31.0-canonical-execution-request-contract.md`, field 9) documents `expected_output_files` as "descriptive, not paths the helper validates" — a free-form filename, not something the caller can be expected to predict as an exact absolute path — confirming this was a genuine implementation bug, not a caller error.

**Fix applied (controller-only, narrowly scoped):** `_missing_expected_outputs(...)` now compares by basename (`Path(f.path).name`) instead of exact string equality. `scripts/gauss_code_execution.py` and `schemas/gauss_code_execution.schema.json` were not touched. Full regression suite re-run immediately: 69/69 pre-existing controller tests still passed.

**Decision not to re-run invocation 3 live:** re-verifying the fix via a sixth real invocation would have exceeded the five-invocation budget. Instead, the fix is verified via a real-shaped fake regression test (`test_74`, Stage 4) reproducing this exact scenario's real evidence (declared filename, absolute discovered path, size) and asserting `failure_category is None` post-fix.

## Stage 4 — Test Strengthening

`scripts/gauss_runtime_orchestration.py`: one narrowly scoped fix (`_missing_expected_outputs`, basename comparison instead of exact-string equality). No other controller or adapter code changed. `scripts/gauss_code_execution.py` and `schemas/gauss_code_execution.schema.json` untouched.

`scripts/test_gauss_runtime_orchestration.py` grew from 69 to 85 passing tests — 16 new tests (`test_71`-`test_86`) covering: two independent requests each executing once; no stale state across instances; fresh confirmation required per instance; the output-created bug fix regression (real-shaped fixture); the output-missing correctness regression (real-shaped fixture); output-file metadata field retention; output metadata never carrying content; a `blocked` execution status being disclosed as a failure rather than silently accepted (locking in pre-existing, not new, routing behavior); distinct result records across instances; prior-result immutability; runtime-error vs. missing-output distinctness; missing-output still reaching `execution_completed`; duplicate request-identity refusal via a deliberately reused adapter; identical code with new request identity being permitted and isolated; safe summaries omitting output-file content; and no automatic rerun after a missing-output classification. The file's final test was renumbered `test_70` → `test_87` (identical "never imports the real helper" logic) to remain last.

**Verified live:** `python scripts/test_gauss_runtime_orchestration.py` → `85 test function(s) run, 0 check failure(s). ALL CHECKS PASSED.` `python scripts/test_gauss_execution_adapter.py` → unchanged, `31 test function(s) run, 0 check failure(s).`

Two test-writing corrections were made and fixed during Stage 4 before the suite passed cleanly (documented for full transparency): `test_71`/`test_84` initially assumed distinct `request_id` alone produces a distinct `request_hash` — incorrect, since `request_hash` is a pure 12-field content fingerprint that deliberately excludes `request_id` (confirmed by direct inspection of `_HASH_INCLUDED_FIELD_ORDER`); tests were corrected to either vary a hash-included field (`working_directory`, mirroring the real invocations) or to explicitly assert and test the same-hash case correctly. `test_73`/`test_86` initially expected the wrong exception type (`GuardFailedError`) for a state-adjacency refusal that actually raises `InvalidTransitionError`; corrected to match the controller's actual, existing behavior (verified against `test_19`'s own established pattern).

## Non-Goals, Restated

`v0.35.0` does not: implement user-facing or conversational execution; modify the execution helper or its schema; enable script-path execution; establish cross-process, crash-safe, or concurrent exactly-once guarantees (the five invocations ran sequentially, in separate processes, never concurrently); implement cooperative cancellation; verify cross-platform or cross-version behavior; make any methodological-validity claim from any real result (none of the five scripts involve statistical methodology); read output-file contents (only path/size/type/discovery-provenance metadata was ever captured or disclosed); or claim production readiness.
