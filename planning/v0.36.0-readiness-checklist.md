# v0.36.0 Readiness Checklist

## Release Goal

`v0.36.0` replaced the orchestration controller's in-memory-only safeguards with an optional, standard-library SQLite-backed durable state layer, establishing that a confirmed canonical request already authorized or attempted must never be silently invoked again — across process restarts and across cooperating local processes. **No GAUSS was run at any point in this milestone's implementation, testing, or evaluation work.**

`v0.36.0`:

- Designed and documented the full data model, transaction boundaries, locking model, crash-recovery model, confirmation-expiry policy, migration/retention/redaction rules, and corruption behavior before writing implementation code.
- Implemented `scripts/gauss_orchestration_state_store.py`, a standalone, dependency-free (standard-library `sqlite3` only) durable store.
- Integrated it into the controller narrowly and additively — `state_store` defaults to `None`, preserving all 85 pre-existing controller tests unmodified.
- Verified genuine cross-process duplicate-invocation protection with real, separate OS processes (not simulated).
- Modeled and verified four distinct crash points, honestly disclosing the one genuine, permanent gap (scenarios 2 and 3 are indistinguishable without a helper/schema change).
- Verified seven corruption scenarios and one unsupported-schema-version case all fail closed.
- Added read-only recovery/inspection tooling with no automatic repair, retry, or rerun capability.
- Added and evaluated `37.x` benchmarks (24/24 passed at 4.0).
- Updated project documentation and tracking.

`v0.36.0` does **not**:

- Claim distributed exactly-once execution or multi-machine coordination.
- Claim protection across different database file paths or against manual database tampering.
- Claim crash-safe knowledge of whether GAUSS actually launched near the invocation boundary.
- Implement automatic repair, retry, or rerun of any kind.
- Enable script-path execution.
- Read output-file contents.
- Store raw code, secrets, credentials, environment-variable values, or raw conversation text.
- Use pickle.
- Wire anything into `workflows/code-assistant-response.md` or any agent.
- Modify `scripts/gauss_code_execution.py`, `schemas/gauss_code_execution.schema.json`, or `scripts/gauss_execution_adapter.py`.
- Run GAUSS at any point.

## Important Findings

- The durable authorization transaction is genuinely, verifiably atomic under real cross-process contention — not merely designed to be, but demonstrated with real, separate OS processes racing for the SQLite write lock, twice run for stability with identical results both times.
- Two self-identified issues were found and fixed during this milestone's own test development, both disclosed rather than glossed over: (1) the initial corruption-detection logic for a deleted transition-history row was insufficient (an empty history trivially "looked" gap-free) and was strengthened to compare history length against the record's own sequence counter; (2) several new controller tests initially made incorrect assumptions about existing behavior (that `request_id` alone determines `request_hash`, and that a past-`confirmed` authorization failure must specifically be `DuplicateInvocationError`) — both were corrected in the tests, not the implementation, since the underlying behavior was already correct.
- The crash-recovery model's central honesty commitment — that scenarios 2 and 3 are genuinely indistinguishable without a helper/schema change — was upheld throughout implementation, testing, documentation, and evaluation; no artifact in this milestone claims otherwise.
- No stop condition, from this milestone's own list, was encountered.

## Remaining Limitations

- Distributed exactly-once execution and multi-machine coordination remain unimplemented and unclaimed.
- Protection across cooperating processes configured with different database file paths is not provided.
- Protection against manual, out-of-band database tampering is not provided.
- Crash-safe knowledge of whether a real GAUSS process actually launched near the invocation-authorization boundary is not provided — this is a permanent, disclosed limitation, not a temporary gap.
- No automatic repair, retry, or rerun exists for corrupt or ambiguous records — a human must decide.
- No user-facing wiring exists between this milestone's work and `workflows/code-assistant-response.md` or any agent.
- No cross-platform or cross-version verification was performed (this milestone touches no GAUSS-invocation code at all, so this is inherited from prior milestones, not newly introduced or newly resolved).
- Retention is indefinite by default — no automatic deletion or archival of durable records exists yet.

## Explicit Readiness-Level Distinction

- **Local, durable, genuinely cross-process invocation-authorization safety: YES, demonstrated.** Real, separate OS processes racing to authorize the same durable record produce exactly one success, every time; confirmation, execution results, and terminal state all survive a real process exit and a fresh reopen.
- **Distributed / multi-machine readiness: NO, and not attempted.** SQLite is a local, single-file technology; nothing here implements or claims network coordination, replication, or multi-host locking.
- **Production readiness: NO.** This milestone provides a durability and cross-process-safety primitive, not a production deployment — no automatic repair, no retention policy beyond "keep everything," no migration tooling beyond a single fail-closed version check, and no verification beyond fake helpers (correctly so, since no GAUSS was run).
- **Readiness for future user-facing workflow integration: NOT YET, AND NOT ATTEMPTED HERE.** Nothing in this milestone wires the durable store or the controller into `workflows/code-assistant-response.md` or any agent.

## Blockers

**No blocker for tagging `v0.36.0` as scoped.** All required deliverables are complete: the durable store is implemented, tested (52 single-process + 15 genuine cross-process/crash tests), and integrated narrowly without breaking any of the 85 pre-existing controller tests; `37.x` evaluations passed 24/24 at 4.0; self-tests, tracking, and release-readiness all pass by default; project docs are consistent and current; no GAUSS was run.

**Separate blockers for future milestones** (not this milestone's scope to resolve):

- Multi-machine/distributed coordination, if ever required — a genuinely different technology choice, not an extension of SQLite.
- Retention/archival policy, if durable records are ever expected to accumulate indefinitely in a real deployment.
- User-facing wiring, if and when explicitly scoped as its own milestone.
- Resolving the scenario-2/scenario-3 crash ambiguity, if ever required — would need a helper/schema change explicitly out of this milestone's scope.

## Readiness Recommendation

**Ready to tag `v0.36.0` as a bounded, local, durable-state and cross-process-safety milestone.** The central invariant — a confirmed request already authorized or attempted is never silently invoked again — is now durable and genuinely verified across real, separate OS processes, not merely designed on paper. Every corruption and crash scenario this milestone models fails closed and is honestly disclosed, including the one permanent gap (crash-point ambiguity) that cannot be resolved without touching the helper or schema, which this milestone correctly declined to do. `37.x` evaluations passed 24/24 at 4.0.
