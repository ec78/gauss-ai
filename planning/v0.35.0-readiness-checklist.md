# v0.35.0 Readiness Checklist

## Release Goal

`v0.35.0` broadened confidence in the real controller execution path `v0.34.0` established, by performing five real, authorized GAUSS invocations through the complete orchestration controller: two independent successful executions proving state isolation between requests, one contained output-file creation, one declared-but-unmet expected output, and one further real GAUSS runtime error. Real testing surfaced and led to the fix of a genuine controller bug in expected-output comparison.

`v0.35.0`:

- Performed preflight verification (adapter/controller test baselines, tracking, release readiness, import boundaries, helper self-test, exact GAUSS version, output-directory containment semantics) before any real invocation.
- Extended the real controller harness with five named, individually selected scenarios and a caller-declared invocation-number audit trail.
- Performed five real GAUSS invocations, all individually justified and recorded, all within the authorized five-invocation budget.
- Found a genuine controller bug during real testing (expected-output filename comparison) and fixed it narrowly, in the controller only.
- Strengthened `scripts/test_gauss_runtime_orchestration.py` with 16 new tests (69 to 85 passing).
- Added and evaluated `36.x` benchmarks (20/20 passed at 4.0).
- Updated project documentation and tracking.

`v0.35.0` does **not**:

- Establish production readiness.
- Claim reliability beyond the five verified script/environment combinations.
- Enable script-path execution.
- Add automatic retries or reruns.
- Claim cross-process, crash-safe, concurrent, or distributed exactly-once behavior.
- Claim cooperative cancellation.
- Claim cross-platform or cross-version support.
- Read output-file contents.
- Wire anything into `workflows/code-assistant-response.md` or any agent.
- Modify `scripts/gauss_code_execution.py`, `schemas/gauss_code_execution.schema.json`, `scripts/gauss_execution_adapter.py`, `scripts/gauss_environment_check.py`, or `scripts/gauss_package_inspection.py`.
- Exceed the five-invocation real-execution budget (five were used, none repeated automatically).

## Important Findings

- The complete controller confirmation/state-machine path was exercised against real GAUSS five more times, bringing the running total to seven real controller-path invocations across `v0.34.0`/`v0.35.0`, all successful in being correctly classified.
- Two independent, identically-coded requests were structurally proven isolated — distinct instance IDs, invocation IDs, and (since working directories differed) request hashes.
- Real output-file creation and metadata-only discovery were confirmed working correctly, inside approved containment.
- **A genuine controller bug was found by real testing, not by inspection** — `_missing_expected_outputs` always misclassified genuinely-created files as missing due to a basename-vs-absolute-path mismatch. This is exactly the kind of finding this milestone existed to surface, and it was fixed narrowly, disclosed honestly (in the implementation report, the evaluation responses, and here), and regression-tested without spending a real invocation to re-verify.
- The `exit_code: 0` non-authoritative finding was reconfirmed for the runtime-error scenario, consistent with every prior milestone.
- No stop condition, from this milestone's own list, was encountered.

## Remaining Limitations

- Reliability beyond the five verified script/environment combinations remains unestablished.
- Cross-platform (macOS/Linux) and cross-version (GAUSS 24/25) behavior remain unverified.
- Cross-process, crash-safe, concurrent, and distributed exactly-once behavior remain unimplemented and unclaimed — all five real invocations ran sequentially, never concurrently.
- True cooperative cancellation remains unimplemented.
- Output-file content reading remains unimplemented — only metadata (path/size/type/discovery-provenance) is ever captured.
- Script-path execution remains blocked.
- No user-facing wiring exists between this milestone's work and `workflows/code-assistant-response.md` or any agent.
- Durable invocation-record persistence and crash recovery remain unaddressed.
- `output_directory`'s actual effect (discovery scope only, not subprocess `cwd`) remains a subtle, easy-to-misunderstand behavior, now explicitly documented but not changed.

## Explicit Readiness-Level Distinction

- **Operational, controller-verified real-execution path with demonstrated reliability: YES.** Five further real invocations, on top of `v0.34.0`'s two, all correctly classified; state isolation between independent requests structurally demonstrated; output-file creation and expected-output handling verified working correctly (after a real bug was found and fixed).
- **Production-ready system: NO.** Five (or seven, cumulatively) successful, manually-supervised, narrowly-scoped invocations are not production readiness. Production readiness would require, at minimum: broader reliability testing across many more scripts and repeated runs; cross-platform and cross-version verification; durable state and cross-process/concurrent safety beyond the current single-process-only guarantee; and a demonstrated absence of further undiscovered bugs of the kind this milestone found.
- **Readiness for future user-facing workflow integration: NOT YET, AND NOT ATTEMPTED HERE.** Nothing in this milestone wires the real path into `workflows/code-assistant-response.md` or any agent.

## Blockers

**No blocker for tagging `v0.35.0` as scoped.** All required deliverables are complete: all five authorized real invocations succeeded in being correctly classified; the real bug found during testing was fixed and regression-tested; `36.x` evaluations passed 20/20 at 4.0; self-tests, tracking, and release-readiness all pass by default; project docs are consistent and current.

**Separate blockers for the next real-execution milestone** (not this milestone's scope to resolve):

- Broader reliability testing (more scripts, more repeated runs, including divide-by-zero and other edge cases) under explicit authorization.
- Cross-platform/cross-version verification, if and when other environments become available.
- Durable persistence and cross-process locking, if a stronger exactly-once guarantee is ever required.
- User-facing wiring, if and when explicitly scoped as its own milestone.

## Non-blocking Follow-ups

- Consider a broader, still-bounded real-execution test matrix (more scripts, a timeout scenario if a safe deterministic one is ever verified) under a future explicit authorization.
- Scope cross-platform/cross-version verification once other environments become available.
- Scope durable invocation-record persistence if cross-process guarantees are ever required.
- Consider whether `expected_output_files`' basename-matching could ever collide for two files with the same name in different subdirectories under `output_directory` — not observed in this milestone's testing, but worth a future edge-case test if output-directory subdirectory usage is ever added.

## Readiness Recommendation

**Ready to tag `v0.35.0` as a Real Execution Reliability and Output Verification milestone.** All five authorized real GAUSS invocations succeeded in being correctly classified (two independent successes, one output-creation, one missing-output, one runtime error), were fully preflighted and documented, and stayed within every stated constraint. A genuine controller bug was found through real testing, fixed narrowly, and honestly disclosed rather than glossed over. `36.x` evaluations passed 20/20 at 4.0. This milestone should **not** be described anywhere as establishing production readiness, cross-platform/cross-version support, cross-process/concurrent exactly-once behavior, cooperative cancellation, output-file content reading, or user-facing automatic execution — all remain explicitly future work.
