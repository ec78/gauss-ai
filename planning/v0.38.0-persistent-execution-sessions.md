# v0.38.0 Persistent Execution Sessions and Agent Handoff Design — Planning

## Release Goal

Design how confirmed execution requests can safely persist across:

- processes
- agent turns
- worker boundaries
- future deployment environments

`v0.38.0` defines, without implementing:

- execution session identity
- persistent request representation
- confirmation persistence
- expiration rules
- ownership boundaries
- safe resumption rules
- cancellation behavior
- execution history boundaries
- audit requirements

`v0.38.0` does **not**:

- implement a database
- implement distributed workers
- implement background jobs
- add autonomous execution
- weaken confirmation requirements
- persist sensitive data unnecessarily

This is a design-only milestone. No code, schema, benchmark, or system-prompt change is authorized. No GAUSS is run.

## Current State

**Already exists** (`v0.31.0`-`v0.37.0`):

- The user-facing execution workflow (`scripts/gauss_execution_workflow.py`) — intent classification, plan proposal, confirmation validation, response composition.
- The durable orchestration object (`scripts/gauss_runtime_orchestration.py`'s `MockOrchestrationInstance`, `CanonicalExecutionRequest`, 13-state machine).
- Confirmation-bound execution — `confirmation_scope == request_hash`, independently re-validated at two layers.
- Request hashing — a deterministic `request_hash` fingerprint over 12 canonical fields, excluding `request_id`.
- The execution controller — `MockOrchestrationInstance.invoke(...)`, atomic durable authorization (`v0.36.0`).
- The Helper Adapter (`scripts/gauss_execution_adapter.py`) — the one controlled route to the execution helper.
- A durable, SQLite-backed state store (`scripts/gauss_orchestration_state_store.py`, `v0.36.0`) — but it stores only a `code_digest`, never raw code, and `confirmation_scope`/plan content are not fully reconstructable from it.

**Missing:**

- A durable persistence layer for the full, resumable execution *plan* (not just its hash/digest and status).
- Cross-process handoff — a second process cannot currently reconstruct enough of a confirmed request to invoke it.
- Session recovery — no concept of "resume this confirmed session in a new process" exists.
- Cancellation across workers — cancellation today is scoped to one in-memory instance in one process.
- An ownership model — no concept of who created, who may resume, who may cancel, or who may view a session's results.

## Core Design Question

**How can a confirmed execution request safely move from one conversational context/process to another without weakening consent or safety?**

Every design decision below is evaluated against this question first. A design that answers it by weakening confirmation binding, widening replay risk, or persisting more than necessary is rejected regardless of convenience.

## Execution Session Model

A conceptual session object (design only — no implementation, no schema, no class defined in code by this milestone):

Example fields:

- `execution_session_id` — a stable identity distinct from `orchestration_instance_id`, `request_id`, and `request_hash`; see "Session vs. Instance vs. Request Identity" below for why a fourth identifier is likely needed rather than reusing an existing one.
- `request_hash` — unchanged meaning from `v0.31.0`: the 12-field content fingerprint.
- `plan_digest` — the exact digest the user's confirmation was bound to (today, identical to `request_hash`; kept as a separate conceptual field so a future plan-versioning change would not silently conflate the two).
- `execution_status` — mirrors the controller's existing execution-status vocabulary; not a new taxonomy.
- `confirmation_status` — mirrors the controller's existing `ConfirmationStatus` vocabulary.
- `created_at` / `expires_at` — session-level timestamps, distinct from (and no looser than) the existing `confirmation_expires_at` policy from `v0.36.0`.
- `owner/context identifier` — an opaque identifier for "who/what created this session" (see Ownership and Permissions — conceptual only, not implemented).
- `execution environment summary` — the same `EnvironmentSummary` shape already defined in `gauss_runtime_orchestration.py`; not redefined.
- `helper result reference` — a pointer to a result record, never the result content itself.
- `cancellation state` — mirrors the controller's existing `CancellationStatus` vocabulary.

Clearly separate three categories, since conflating them is the most likely way this design could accidentally widen the current safety boundary:

- **Persisted state**: identity fields, hashes/digests, statuses, timestamps, ownership identifiers, environment summary, result *references*. Everything already durably stored by `v0.36.0`'s state store, plus whatever new fields a future session layer adds — all non-sensitive, all safe to read back after a restart.
- **Transient runtime state**: the actual `CanonicalExecutionRequest` object (including inline code), the live `MockOrchestrationInstance`, the injected `runner`/adapter/helper callables. These exist only in the process that built them, exactly as today, and this milestone does not propose changing that.
- **Sensitive data**: raw inline code, `stdout`/`stderr` content, output-file content, credentials, environment-variable values, raw conversation text. Already excluded from persistence by `v0.36.0`'s design; this milestone does not propose including any of it in a session record either.

### Session vs. Instance vs. Request Identity

A likely-necessary distinction a future implementation phase will need to resolve, flagged here rather than decided: `orchestration_instance_id` today identifies one in-memory (optionally durable) controller instance, scoped to the process that created it. A "session" as described in this document is a *durable, cross-process-referenceable* concept, which may or may not be the same identifier. Two options exist for a future phase to choose between, not decided here:

1. `execution_session_id == orchestration_instance_id` — the durable record itself becomes the session; simplest, but conflates "the controller's own bookkeeping key" with "the externally-referenceable handle a conversational agent hands across a boundary."
2. `execution_session_id` is a new, separate identifier that maps to one `orchestration_instance_id` — cleaner separation of concerns, but adds a mapping table and a second identifier space to reason about.

This document does not resolve which option a future phase should take; it only names the question so Phase 1 (Session Model) has to answer it explicitly rather than by accident.

## Confirmation Persistence

**What must be stored to prove confirmation:** the exact `request_hash` the user confirmed, the `session_id` the confirmation was issued in, a store-computed expiry timestamp (never the caller-supplied audit timestamp, per `v0.36.0`'s existing policy), and a monotonic consumed/not-consumed flag. This is exactly what `v0.36.0`'s `record_confirmation(...)` already persists — this milestone does not propose storing anything additional to "prove" confirmation happened.

**How confirmation binds to a request:** `confirmation_scope` must equal `request_hash` exactly (unchanged from `v0.31.0`). A session-level design must preserve this unchanged: a session cannot be "confirmed" independently of the exact request it was confirmed against.

**What invalidates confirmation:** any change to a hash-included field (code, working directory, output directory, executable, timeout, expected outputs, required packages, environment summary, safety review) — because any such change produces a new `request_hash`, which no prior confirmation's `plan_digest` can match. This is unchanged, structural behavior from `v0.31.0` through `v0.37.0`, not a new rule.

**Expiration rules:** unchanged from `v0.36.0`'s existing 30-minute wall-clock TTL, computed at confirmation time from the store's own clock, never extended by a restart. A session-level design must not introduce a second, looser expiration mechanism that could outlive or override this one.

**Replay prevention:** a consumed confirmation never becomes reusable (monotonic consumption, unchanged from `v0.31.0`/`v0.36.0`). A session-level design that allowed "resuming" a session by re-consuming an already-consumed confirmation would violate this and is explicitly rejected.

**Examples:**

Valid — same exact request resumes:

> User confirms: "Run `model.gss` in `/tmp/job1`."
> Later, in a different process, the *exact same* confirmed request (same code, same working directory, same every hash-included field) is what gets resumed. `request_hash` is unchanged; the persisted confirmation still matches it.

Invalid — requires a new confirmation:

> User confirms: "Run `model.gss`."
> Later: the code changes, or the directory changes, or output behavior changes.
> Any of these changes `request_hash`. The old confirmation's `plan_digest` no longer matches. A new proposal and a new, explicit confirmation are required — there is no partial-match or "close enough" resumption path, by design.

## Session State Machine

States (a superset of the controller's existing 13-state machine, adding session-level states that do not yet exist in `gauss_runtime_orchestration.py`):

- `created`
- `awaiting_confirmation`
- `confirmed`
- `queued` *(new — a confirmed session waiting for a worker/process to pick it up; does not exist in the current single-process controller)*
- `running`
- `completed`
- `failed`
- `cancelled`
- `expired`

Valid transitions mirror the existing controller's adjacency rules (`created → awaiting_confirmation → confirmed → queued → running → completed|failed`, plus cancellation from any non-terminal state) — a future implementation phase must reconcile this against `gauss_runtime_orchestration.VALID_TRANSITIONS` rather than inventing a parallel, potentially inconsistent table. `queued` is the one genuinely new state this document introduces, since it represents time between "confirmed in process A" and "picked up by process B," which has no analog in the current single-process `invoke()` call.

**Prohibited transitions** (explicitly, matching the task's own list):

- `expired → running` — an expired confirmation can never be consumed; this already fails closed today (`v0.36.0`'s `authorize_invocation`).
- `cancelled → running` — a cancelled session is terminal, exactly like the controller's existing `CANCELLED` terminal state.
- **changed request → old confirmation** — a request that changed (new `request_hash`) can never be authorized by a confirmation scoped to the old hash; this is not a state-machine transition so much as a standing invariant that must hold at every state.
- `failed → automatic retry` — no automatic retry exists today and none is proposed; a retry is always a brand-new session from a brand-new proposal, exactly as `v0.37.0`'s `request_rerun(...)` already enforces by always raising.

## Agent Handoff Model

```text
Conversation Agent
  creates request
        |
        v
Persistent Session Store
        |
        v
Execution Controller
        |
        v
Worker/Process
        |
        v
Result Store
        |
        v
Conversation Agent
```

**What crosses boundaries:** `execution_session_id`, `request_hash`/`plan_digest`, `code_digest` (never raw code), status fields, timestamps, environment summary, an opaque owner/context identifier, and (after completion) a *reference* to a result record — never the result's raw stdout/stderr/output-file content itself, mirroring the existing metadata-only boundary.

**What does not cross boundaries:** raw inline code, raw stdout/stderr, raw output-file content, credentials, environment-variable values, raw conversation text. This is the same exclusion list `v0.36.0` already established for durable storage; a cross-process handoff must not become a backdoor that reintroduces any of it.

**How confirmation is preserved:** the confirmed status and its binding to `request_hash` travel with the session record itself (already durable as of `v0.36.0`); a worker process picking up a `queued` session re-validates `confirmation_scope == request_hash` and non-expiry independently, exactly as `authorize_invocation(...)` already does today for the single-process case — a future phase extends this check, it does not relax it.

**How results are returned:** the executing process persists a result *reference* (status, exit code, output-file count/metadata, failure category — the same fields `v0.36.0`'s `record_execution_result(...)` already persists) to the Result Store; the conversation agent's process reads that reference back via the session store, never by receiving raw execution output directly from the worker process.

**The open problem this milestone does not solve:** today, a worker process cannot actually *invoke* a confirmed session, because `reload_orchestration_instance(...)` never reconstructs `request` (raw code is never persisted — see Current Limitation). This diagram describes the shape a future implementation would need, not a mechanism for closing that gap; closing it is explicitly out of scope here (see Non-goals and Risks).

## Ownership and Permissions

Future concepts only — **not implemented, not designed in detail, by this milestone**:

- **User ownership** — which human/account a session belongs to.
- **Workspace ownership** — which project/workspace a session's working directory belongs to.
- **Session ownership** — which conversation/agent-context created a session.
- **Execution authorization** — whether the entity attempting to resume/cancel/view a session is actually allowed to.

Open questions for a future phase to answer (not answered here):

- Who can resume execution?
- Who can cancel execution?
- Who can view outputs?
- Who owns generated files?

Today, `session_id` is accepted as an opaque, caller-supplied string with no ownership semantics beyond exact-match session-mismatch rejection (`SessionMismatchError`). Any future ownership model must be at least as strict as this — never looser.

## Cancellation Model

- **Cancellation request** — an explicit, caller-initiated action; never inferred, never automatic.
- **Cancellation states** — mirrors the controller's existing `CancellationStatus` vocabulary (`not_cancelled`, `cancel_requested_during_invocation`, `cancellation_acknowledged`); a session layer should reuse this, not invent a parallel one.
- **Cancellation timing** — pre-invocation cancellation (clean, terminal, unchanged from today); mid-invocation cancellation (records intent only, does not and cannot interrupt an already-running synchronous call — an honestly disclosed limitation inherited unchanged, not solved by a session layer); post-invocation cancellation (a no-op on the execution itself, only affects downstream analysis/reporting, unchanged).
- **Behavior while GAUSS is running** — a session layer does not change this: this repository has never claimed cooperative cancellation of a real, running GAUSS process, and this milestone does not propose acquiring that capability. A future worker-based design would need a genuinely new mechanism (e.g., process-group termination) that is explicitly out of scope here.
- **Cleanup requirements** — a cancelled session's working/output directories are never automatically deleted (matching the existing "no automatic cleanup of user-owned files" non-goal, carried forward unchanged); cleanup remains a human or separately-scoped, explicitly-authorized action.

## Expiration Model

- **Confirmation expiration** — unchanged, 30-minute wall-clock TTL from `v0.36.0`.
- **Session expiration** — a broader, session-level expiration (e.g., a `queued` session that no worker ever picks up) is a genuinely new concept this milestone only names, not designs in detail; a future phase must decide whether it reuses the same 30-minute constant or needs its own, and must justify any divergence rather than picking an arbitrary new number.
- **Cleanup policies** — expired sessions are not automatically deleted; they remain available for audit/inspection, mirroring `v0.36.0`'s "no automatic deletion of durable records" retention policy.
- **Stale execution prevention** — an expired session can never transition to `running` (see Session State Machine's prohibited transitions); this is the same fail-closed guarantee `v0.36.0` already established for confirmation expiry, extended conceptually to the session level.

## Auditability

What should be recorded (a session-level extension of the transition-event log `v0.36.0` already implements, not a new mechanism):

- request creation
- confirmation event
- execution start
- execution completion
- cancellation
- failure
- result delivery (the act of a conversation agent's process reading back a result reference — new relative to `v0.36.0`, since today there is only one process to "deliver" to)

**Do not store unnecessary sensitive content.** Every audit entry follows the same redaction rules already established: identifiers, hashes, statuses, and timestamps only — never raw code, never stdout/stderr, never output-file content, never credentials.

## File and Artifact Boundaries

- **Where execution files live** — unchanged: the confirmed `working_directory`/`output_directory`, never a session-store-managed location. A session record never becomes a copy of, or a substitute for, the actual filesystem location.
- **How outputs are referenced** — by path/size/type/created-by metadata only (unchanged `OutputFileMeta`/`OutputFileSummary` shape from `v0.31.0`/`v0.37.0`), never by embedding content in the session or result record.
- **Whether files persist** — yes, exactly as long as the filesystem keeps them; a session layer neither extends nor shortens their lifetime.
- **Cleanup policy** — no automatic cleanup, unchanged non-goal.
- **Artifact ownership** — an open question deferred to the Ownership and Permissions section above; not designed in detail here.
- **`output_files` metadata boundary** — preserved without exception.

**metadata ≠ file content** — restated as a hard boundary this entire design is built around, not a implementation detail: nothing proposed in this document introduces any code path capable of carrying file content across a process/session boundary.

## Security Boundaries

- **No replay attacks** — a consumed confirmation is never reusable; a session's confirmation binding is exactly as strict cross-process as it is today single-process.
- **No stale confirmation reuse** — expiry and hash-binding are preserved, not loosened, by any handoff mechanism.
- **No arbitrary process execution** — a session never carries an executable command line beyond the already-validated `executable_path`/inline-code shape; no new "run this shell command" capability is proposed anywhere in this document.
- **No unsafe path changes** — `working_directory`/`output_directory` remain part of the hashed request; changing either invalidates confirmation exactly as today.
- **No privilege escalation** — a worker process resuming a session must never gain broader filesystem/network/credential access than the process that originally proposed and confirmed it would have had.
- **No hidden execution** — a `queued` session is always the result of an explicit, already-confirmed request; nothing in this design proposes a path from "unconfirmed" to "queued."
- **No silent request mutation** — a session's persisted `request_hash`/`plan_digest` are immutable once set, exactly like the existing frozen `CanonicalExecutionRequest`.

## Evaluation Strategy

Proposed future `39.x` benchmark examples (**not added by this milestone** — naming them here only to inform Phase 6 of a future implementation milestone):

1. Confirmed request resumes safely.
2. Modified code invalidates confirmation.
3. Expired confirmation requires renewal.
4. Cancelled execution cannot restart.
5. Wrong user cannot resume session.
6. Output artifact ownership preserved.
7. Duplicate execution prevented.
8. Worker failure handled safely.

## Implementation Phases

(Design sequencing for a future, separately authorized implementation milestone — not started by `v0.38.0`.)

- **Phase 1** — session model: resolve the session/instance/request identity question; finalize the session field list.
- **Phase 2** — persistence abstraction: decide how (and whether) session records extend `v0.36.0`'s existing durable store versus a new, separate mechanism.
- **Phase 3** — controller integration: wire session lifecycle into `gauss_runtime_orchestration.py` without weakening any existing guard.
- **Phase 4** — handoff testing: fake-only, multi-process tests proving safe handoff (or proving it is still correctly refused, per the current limitation).
- **Phase 5** — cancellation/expiration: implement the session-level expiration and cross-process cancellation behavior designed above.
- **Phase 6** — evaluation: add the `39.x` benchmark category.

## Risks

- Stale confirmation being treated as valid after a handoff.
- Replay of an already-consumed confirmation.
- Unauthorized resumption by a process/user that did not create or was not granted the session.
- Accidental duplicate execution across two processes racing on the same session.
- Sensitive data (raw code, stdout/stderr, credentials) being persisted "for convenience" during a future implementation phase.
- File/artifact ownership confusion once multiple processes can reference the same working directory.
- Worker failure leaving a session ambiguously `queued`/`running` with no resolution path (an extension of `v0.36.0`'s already-disclosed ambiguous-crash limitation, now across an additional handoff boundary).
- State corruption if a future persistence layer does not reuse `v0.36.0`'s existing atomic-transaction discipline.
- Session cleanup being skipped or over-aggressive, either leaking stale sessions indefinitely or deleting audit evidence prematurely.

## Non-goals

- Autonomous execution.
- Distributed computing.
- Cloud deployment.
- A multi-user production system.
- Persistent storage implementation (this milestone designs, does not build).
- Background workers.
- Job queues.
- Long-running execution management.
