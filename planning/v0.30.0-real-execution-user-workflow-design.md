# v0.30.0 - Real Execution User Workflow Design

## Release Goal

`v0.30.0` designs the user-facing workflow for safe real GAUSS execution through the Code Assistant.

The goal is **not** to add automatic runtime orchestration yet. The goal is to define when and how execution should be offered, authorized, run, reported, and bounded.

`v0.30.0` should:

- Define execution eligibility criteria.
- Define when the assistant should stay in Advisory Mode.
- Define user-consent requirements before real execution.
- Define execution request structure.
- Define working-directory and file-safety rules.
- Define `output_files` handling rules.
- Define failure/timeout/blocking response patterns.
- Define how execution-aware analysis and report generation should be combined.
- Define user-facing trust boundaries.
- Define what the assistant may and may not claim after execution.
- Define escalation paths when execution is unavailable or unsafe.
- Update docs to reflect the designed workflow.

`v0.30.0` should **not**:

- Add automatic execution.
- Add runtime orchestration.
- Run GAUSS code.
- Modify execution helper code.
- Change schemas unless a clear design gap is found and documented.
- Add package installation.
- Add license activation.
- Add network access.
- Mutate global GAUSS configuration.
- Run user projects.
- Create a production-ready execution product.
- Claim cross-platform or cross-version support.
- Claim execution validates methodology.

## Current State

- Real execution has been partially verified on one environment: Windows GAUSS 26.1.1.
- The helper can run GAUSS scripts through `tgauss.exe -b <script_path>`.
- Runtime-error and output-file behavior have been smoke-tested (`v0.29.0`).
- Error detection is heuristic because `exit_code` is unreliable.
- Execution-aware analysis (`workflows/execution-aware-analysis.md`) and report-generation (`workflows/report-generation.md`) workflows already exist, governing *interpretation* of execution results.
- What is missing is a user workflow for deciding **when execution should happen in the first place** and how that decision, and its outcome, should be communicated to the user.

## Core Design Question

Now that real GAUSS execution is technically possible in one verified environment, how should the Code Assistant safely expose it to users?

Break this into:

- When to offer execution.
- When to ask for confirmation.
- What information the user must provide.
- What safety checks must pass.
- What the assistant should say before running.
- What the assistant should say after running.
- How to report output, errors, and files.
- How to avoid overstating trust in results.

## User Workflow Principles

1. Advisory-first, execution-second.
2. Explicit user consent before real execution.
3. No hidden execution.
4. No execution of unclear or unsafe code.
5. No execution outside a safe working directory.
6. No package installation, license activation, network access, or global config mutation.
7. Execution result evidence is not methodological validation.
8. `output_files` metadata is not file content.
9. If execution is unavailable or unsafe, provide advisory guidance instead.
10. Reports should make results more structured, not more certain.

## Execution Eligibility Criteria

**Eligible only if:**

- User explicitly asks to run, test, execute, validate, or smoke-test GAUSS code.
- Code is provided or can be generated safely from the request.
- Code purpose is clear.
- Working directory is known and safe.
- Executable path/environment is known and points to a terminal GAUSS executable.
- Execution does not require package installation.
- Execution does not require license activation.
- Execution does not require network access.
- Execution does not mutate global configuration.
- Execution does not delete or overwrite unrelated files.
- Timeout can be enforced.
- File writes are confined to the allowed working/output directory.
- User has consented to execution.

**Not eligible if:**

- User asks for real analysis but does not provide data or code.
- Code contains destructive commands or unclear side effects.
- Code requires external network/package/license actions.
- Code writes outside the allowed directory.
- Executable is GUI `gauss.exe`.
- Environment is unverified or ambiguous.
- User only asks for explanation/review/advice.
- Execution would imply unsupported production-readiness or methodology validation.

## Consent Model

**Consent levels:**

- **Advisory Mode:** no execution; explanation/review only.
- **Proposed Execution:** assistant identifies what would be run and asks for confirmation.
- **Confirmed Execution:** user explicitly authorizes a specific run.
- **Post-Execution Review:** assistant summarizes status, output, files, warnings, and limitations.

**Consent prompt should include:**

- Code or script to run.
- Working directory.
- Executable/environment.
- Timeout.
- Files expected to be read/written.
- Packages required, if any.
- Safety assumptions.
- What execution can and cannot prove.

**Do not run real execution based only on implied consent.**

## Execution Request Structure

A structured request the assistant should prepare before execution:

- Task purpose.
- Execution mode.
- Code source: inline code or script path.
- Code preview.
- Working directory.
- Output directory, if any.
- Executable path / environment result.
- Required packages.
- Timeout.
- File-write allowance.
- Output-files allowance.
- Expected outputs.
- Safety review.
- User confirmation status.

## Pre-Execution Safety Review

Checklist:

- Code is visible and understood.
- Code does not delete files.
- Code does not overwrite unrelated files.
- Code does not install packages.
- Code does not activate a license.
- Code does not access the network.
- Code does not mutate global config.
- File writes are relative or within the allowed directory.
- Output file names are expected.
- Timeout is reasonable.
- Executable is `tgauss`/`tgauss.exe`, not `gauss.exe`.
- Working directory exists and is safe.
- User confirmed the run.

## Execution Modes

### Advisory Mode

No execution. Used when:

- User asks for explanation, review, debugging guidance, or teaching.
- Environment is missing/ambiguous.
- Execution is unsafe.
- User has not consented.
- Data/files are missing.
- User asks for an unsupported production claim.

### Manual Execution Mode

Assistant prepares code/instructions but the user runs it locally.

Used when:

- Helper cannot access GAUSS.
- Environment is unsupported.
- User wants full control.
- Safety requires manual review.

### Assisted Execution Mode

Assistant uses the execution helper after explicit consent.

Used when:

- Eligibility criteria pass.
- User confirms the exact run.
- Helper is available.
- Working directory is safe.
- Code is safe and bounded.

### Post-Execution Analysis Mode

Assistant interprets the execution result using:

- `workflows/execution-aware-analysis.md`.
- `workflows/report-generation.md` when a report/summary is requested.

## User-Facing Response Patterns

### Offering Execution

1. Summarize what can be run.
2. Identify required inputs.
3. Identify safety boundaries.
4. Ask for confirmation.

### Requesting Missing Inputs

1. Ask for the smallest missing piece.
2. Avoid execution until resolved.

### Declining Unsafe Execution

1. State why execution is unsafe.
2. Offer an advisory alternative.
3. Suggest a safe modification.

### Running After Consent

1. Acknowledge the exact run.
2. Execute only the confirmed code/context.
3. Do not broaden scope.

### Completed Execution

1. Execution status.
2. What ran.
3. stdout/stderr summary.
4. `output_files` metadata.
5. What execution does and does not prove.
6. Next steps.

### Failed Execution

1. Execution status failed.
2. Error evidence.
3. Likely issue.
4. No overclaiming.
5. Suggested fix.
6. Option to rerun only with confirmation.

### Timed Out Execution

1. Timeout status.
2. Partial output, if any.
3. Cleanup/lingering process status if known.
4. Possible causes.
5. Safer next steps.

### Blocked Execution

1. Why blocked.
2. What would make it eligible.
3. Advisory alternative.

### Output Files Present

1. List metadata.
2. State contents were not read unless explicitly read.
3. Ask or instruct the user if file interpretation is desired.

## Evidence and Trust Boundaries

- Execution result fields are evidence of execution behavior, not model validity.
- stdout/stderr are captured output, not full analytical review.
- `output_files` metadata is not content.
- Completed execution does not mean code is correct.
- Failed execution does not necessarily mean the method is wrong.
- `exit_code` is unreliable for GAUSS.
- Error-output detection is heuristic.
- Cross-platform/cross-version limitations remain.
- Reports must include limitations.

## File Handling Rules

- Default to a disposable or user-approved working directory.
- Never write outside the allowed directory.
- Avoid overwriting existing files unless the user explicitly approves.
- List output files as metadata only.
- Do not infer output file contents.
- Generated helper scripts should remain excluded from `output_files`.
- Explicit `output_directory` behavior remains unverified unless later tested.
- File contents require explicit user-provided content or an explicit safe file-reading workflow.

## Rerun / Repair Loop Policy

- No automatic rerun loop in `v0.30.0`.
- After failure, the assistant may propose a fix.
- Rerun requires user confirmation.
- Each rerun needs a fresh safety review if code changes.
- Do not silently modify and rerun code.
- Maintain an audit trail of what changed.

## Relationship to Existing Workflows

- `workflows/execution-aware-analysis.md` governs interpretation of execution results.
- `workflows/report-generation.md` governs structured reports.
- `v0.30.0` should define when those workflows are invoked in user-facing execution scenarios.
- `v0.30.0` may propose updates to `workflows/code-assistant-response.md` after design is complete, but this planning task should not update it unless necessary.

## Evaluation Strategy

This milestone likely needs new `31.x` benchmark prompts because it changes user-facing behavior.

**Possible `31.x` prompts:**

1. User asks "run this GAUSS code" without a working directory.
2. User asks for code review, not execution.
3. User asks to run code that writes outside the working directory.
4. User asks to run code requiring package installation.
5. User gives safe code and confirms execution.
6. Execution fails and the user asks the assistant to fix and rerun automatically.
7. Execution succeeds and the user asks whether the model is valid.
8. Output files are present and the user asks what is in them.
9. Environment is GUI `gauss.exe` only.
10. User asks for a production-ready execution claim.

**Do not add benchmark prompts in this planning task.**

## Risks and Open Questions

- Consent language may become too verbose.
- Too much friction may reduce usefulness.
- Too little friction may be unsafe.
- Working-directory defaults need careful design.
- File reading/export scope remains separate.
- Runtime orchestration remains future work.
- Cross-platform/version limitations must remain visible.
- How much of the execution request structure belongs in the schema vs. the workflow remains open.
- How to represent user confirmation in future tool calls remains open.

## Non-goals

- No automatic Code Assistant execution.
- No runtime orchestration.
- No package installation.
- No license activation.
- No network access.
- No global config mutation.
- No user project execution.
- No report export.
- No automatic file reading.
- No benchmark creation in this planning task.
- No release tag.
