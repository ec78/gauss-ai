# v0.25.0 Readiness Checklist

## Release Goal

`v0.25.0` implements the first controlled GAUSS code execution helper based on the `v0.24.0` execution contract (`tools/gauss_code_execution.md`, `schemas/gauss_code_execution.schema.json`).

`v0.25.0`:

- Implements `scripts/gauss_code_execution.py`.
- Provides a CLI.
- Provides an importable `execute_gauss_code(...)` API.
- Returns schema-shaped output matching `schemas/gauss_code_execution.schema.json`.
- Uses a runner abstraction.
- Includes fake-runner self-tests.
- Validates safe working-directory containment.
- Enforces timeouts.
- Captures stdout, stderr, exit code, and elapsed time.
- Supports output-file metadata discovery limited to the working directory.
- Blocks unsafe, missing, or ambiguous execution contexts.
- Blocks execution when package inspection reports required missing packages.
- Warns on unknown package status.
- Accepts `allow_network` but does not enable network access.
- Does not install packages or activate licenses.

`v0.25.0` does **not**:

- Provide confirmed production-ready real GAUSS execution.
- Resolve non-interactive GAUSS invocation syntax.
- Install packages.
- Activate licenses.
- Access the network.
- Mutate global GAUSS configuration.
- Implement automatic repair/rerun loops.
- Implement report generation.
- Integrate into the Code Assistant workflow.
- Implement full runtime orchestration.
- Prove methodology validity from execution.

## Confirmed Real-GAUSS Invocation Finding

A manual smoke test during implementation accidentally invoked the real local GAUSS 26 installation on this development machine.

**Command form used:** `[executable_path, script_path]` (the helper's default, best-effort command builder).

**Test code:** `print "hello";` (deliberately trivial and harmless).

**Outcome:**

- GAUSS launched, printed its startup banner and the script's `print` output, then entered its interactive `(gauss)` prompt instead of exiting non-interactively.
- The process ran for the full 30-second default timeout before the helper's timeout guard terminated it.
- No lingering `tgauss.exe` remained afterward (confirmed via `tasklist`).
- No packages were installed.
- No license was activated.
- No network access occurred.
- No files were touched outside the disposable temporary working directory used for the test.

**Interpretation:**

- The helper architecture and timeout controls worked exactly as designed — a real, uncontrolled GAUSS invocation was safely contained and terminated.
- The naive command form `[executable_path, script_path]` is **not sufficient for confirmed non-interactive execution**.
- Real non-interactive GAUSS invocation remains the primary open issue for this milestone.
- Real execution through this helper should be treated as experimental/limited until a safe, confirmed non-interactive command form is found. This is a genuine, load-bearing finding — not a defect in the helper's safety design, but direct evidence that the one deliberately-isolated unresolved risk named in `planning/v0.24.0-gauss-code-execution-prototype.md`'s "Key Implementation Risk" was real.

### Result Schema

**Path:** `schemas/gauss_code_execution.schema.json`

**Purpose:** Validates execution result shape.

- Draft 2020-12.
- 19 required top-level fields plus optional `raw_execution_details`.
- `execution_status` enum: `completed`, `failed`, `timed_out`, `skipped`, `blocked`, `error`, `unknown`.
- `operating_mode` enum: `advisory`, `verified_knowledge`, `execution`.
- `code_source` enum: `inline`, `script_path`, `none`, `unknown`.
- `output_file` object schema (`path`, `size_bytes`, `file_type`, `created_by_execution` tri-state, `notes`).
- Ten `allOf`/`if`/`then` consistency constraints, most notably: `executed: false` cannot coexist with `execution_status: completed`; `executed: true` requires `operating_mode: execution`; `blocked` requires `executed: false` and `operating_mode: advisory`; `error` requires at least one error.
- Unchanged since `v0.24.0` — the implementation conforms to it rather than requiring changes.

## Importable API Summary

**Function:** `execute_gauss_code(...)`

**Supported inputs:** `environment_check_result`, `package_inspection_result`, `executable_path`, `gauss_version`, `code`, `script_path`, `working_directory`, `input_files`, `output_directory`, `timeout_seconds`, `allow_file_write`, `allow_output_files`, `allow_network`, `strict`, `capture_stdout`, `capture_stderr`, `validate_schema`.

**Return value:** a dictionary shaped for `schemas/gauss_code_execution.schema.json`.

## Runner Abstraction Summary

- The default runner uses `subprocess.run` without `shell=True`.
- A fake runner is used for all self-test cases.
- Command construction is isolated in an injectable `command_builder`.
- The runner returns a structured result: `executed`, `timed_out`, `exit_code`, `stdout`, `stderr`, `elapsed_seconds`, `raw_details`.
- The runner abstraction isolates unresolved GAUSS CLI invocation behavior to one narrow, overridable component.
- Real GAUSS invocation remains platform/version dependent and unconfirmed — calling `execute_gauss_code(...)`/the CLI without an injected `runner` and with a `found` environment context **will** attempt real GAUSS invocation.

## Environment and Package Context Summary

**Environment precedence:**

1. Explicit executable/version.
2. `environment_check_result`.
3. Automatic environment detection when not `strict`.
4. Blocked/advisory fallback.

**Package behavior:**

- Missing packages (`missing_packages` non-empty in `package_inspection_result`) block execution.
- Unknown packages (`unknown_packages` non-empty) warn but do not block.
- Package installed does not prove syntax or methodology validity.
- No auto-installation.
- No license activation.

## Input Validation and Safety Summary

- Exactly one of `code` or `script_path` is required.
- Both `code` and `script_path` supplied together blocks.
- Neither `code` nor `script_path` supplied skips (not blocks — treated as no execution requested).
- `working_directory` is required.
- `working_directory` must exist and be a directory.
- `script_path`/`output_directory`/`input_files` must resolve inside `working_directory`.
- Path traversal is rejected.
- Symlink handling is conservative.
- No process-CWD fallback.
- No writes outside `working_directory`.
- Network access is unsupported (accepted as an input, never enabled).

## Working Directory and Timeout Summary

- Inline code is written only to a helper-created subdirectory (`.gauss_code_execution_generated`) inside `working_directory`.
- The generated inline-code path is kept out of the schema's `script_path` field when `code_source` is `inline` (recorded only in `raw_execution_details`), per schema constraint.
- Timeout default (`DEFAULT_TIMEOUT_SECONDS = 30.0`) and maximum (`MAX_TIMEOUT_SECONDS = 300.0`) are documented constants.
- `timeout_seconds <= 0` blocks.
- A timeout exceeding the maximum is capped with a warning, not silently accepted or rejected.
- Timeout terminates the process (Python's `subprocess.run` kills the child on `TimeoutExpired`).
- stdout/stderr capture is size-limited (`MAX_CAPTURE_CHARS = 20000`).
- Truncation creates a recorded warning, never a silent drop.

## Output and Status Mapping Summary

- Output file discovery is read-only (`Path.iterdir()`/`Path.stat()` only).
- Output discovery is limited to `output_directory` (or `working_directory` if not supplied), always inside `working_directory`.
- The internal generated-script directory (`.gauss_code_execution_generated`) is excluded from discovered output files.
- File contents are never read.
- `created_by_execution` is currently always `"unknown"` (no before/after comparison is implemented).

**Status mapping:**

- `exit_code == 0` → `completed`.
- Nonzero exit → `failed`.
- Runner-reported timeout → `timed_out`.
- Safety-policy refusal → `blocked`.
- No code/script → `skipped`.
- Unexpected helper/runner failure → `error`.

## Safety Boundary

The helper does **not**:

- Install packages.
- Activate licenses.
- Enable network access.
- Mutate global GAUSS configuration.
- Run automatic repair/rerun loops.
- Implement runtime orchestration.
- Integrate into the Code Assistant workflow.
- Generate reports from output.

Even if execution completes, it does not prove:

- Syntax is generally valid.
- Methodology is valid.
- The model is correct.
- Estimates are meaningful.
- Diagnostics are adequate.
- Code is maintainable.
- Documentation is clear.
- Learning design is effective.
- Product value is proven.

## Self-Test Summary

- Missing executable → `blocked`.
- Ambiguous environment → `blocked`.
- No code/script → `skipped`.
- Both code and script → `blocked`.
- Missing working directory → `blocked` (both `None` and a nonexistent path).
- Successful fake execution → `completed`.
- Failed fake execution → `failed`.
- Timeout fake execution → `timed_out`.
- stdout/stderr capture.
- Output-truncation warning.
- Output-file listing limited to `working_directory`.
- Path traversal rejected.
- `--allow-network` warning/no-op.
- Schema validation for representative outputs (`blocked`, `skipped`, `completed`, `failed`, `timed_out`).
- `executed: false` never reports `completed`.
- Nonzero exit maps to `failed`.
- `exit_code 0` maps to `completed`.
- Package missing blocks without auto-install.
- Bonus case: unknown package warns without blocking.

## Important Findings

- GAUSS code execution helper implementation exists (`scripts/gauss_code_execution.py`).
- Fake-runner self-tests pass (18 cases + 1 bonus case, both with and without `--validate-schema`).
- Schema validation support works, mirroring both prior helpers' pattern exactly.
- The runner abstraction successfully isolates real-invocation uncertainty to one narrow, overridable component (`command_builder`), so implementation-logic correctness and real-GAUSS-invocation correctness can be verified independently.
- Safety controls exist and are self-tested for working-directory containment, timeout enforcement, output capture/truncation, and path containment.
- Missing packages block execution; unknown packages only warn — both self-tested.
- The naive real GAUSS command form `[executable_path, script_path]` is not confirmed for non-interactive use and caused GAUSS 26 to enter its interactive prompt in a real manual smoke test.

## Remaining Limitations

- Safe non-interactive GAUSS invocation remains unresolved.
- The naive `[executable_path, script_path]` form is known **not** to exit non-interactively, based on the observed GAUSS 26 smoke test on this development machine.
- Platform/version invocation differences remain unresolved (only Windows/GAUSS 26 has been observed at all, and only in the one failing case above).
- Exit-code/stdout/stderr behavior for real, successfully-non-interactive GAUSS execution remains unresolved (never observed, since the one real test never reached that state).
- License/GUI prompt risks remain unresolved beyond the one observed interactive-prompt case.
- Destructive-code detection remains limited to a best-effort, non-guaranteed heuristic (path-containment checks only; no code-content analysis).
- Code Assistant workflow integration remains unimplemented.
- Runtime orchestration remains unimplemented.
- Report generation from actual execution output remains unimplemented.
- No automatic repair/rerun loop exists.
- No formal CI integration for the execution helper's self-tests exists yet, unless added separately.
- Real execution should be considered experimental/limited, not production-ready.
