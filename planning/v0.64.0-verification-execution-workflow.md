# v0.64.0 - Verification Execution Workflow

## Release Goal

Implement a Verification Execution workflow that executes an already-applied repair's resulting source through the **existing, unmodified** execution pipeline and collects evidence. It is not automatic repair validation, automatic acceptance, autonomous retry, autonomous repair, or autonomous planning — it simply proposes an ordinary execution whose code happens to be the repaired file's current content, then produces a structured, evidence-only comparison against the original execution's own interpretation.

## Repository State Verified

Starting commit `248deef` (`v0.63.0`, tagged, pushed, released). Clean working tree. No repair module, and no execution module, is modified by this milestone.

## The Architectural Requirement, Restated

**Repair knows nothing about execution. Execution knows nothing about repair. Verification is only an adapter between them.**

- `scripts/gauss_repair_application.py` is not imported by `scripts/gauss_execution_workflow.py`, and never will be as a result of this milestone.
- `scripts/gauss_execution_workflow.py` is not modified at all — zero diff.
- `scripts/gauss_verification_execution.py` (new) is the only module that imports both `gauss_repair_application` (for `ApplicationResult`) and `gauss_execution_workflow` (for `ExecutionWorkflow`/`ExecutionProposal`/etc.) — and it does so only to translate one into inputs for the other. It contains no execution logic of its own (no runner, no invocation, no confirmation logic) and no repair logic of its own (no draft, no approval, no transaction).

## VerificationExecutionRequest

Immutable, frozen. Fields: `verification_execution_id`, `repair_application_id`, `application_result_id`, `workspace_id`, `relative_path`, `expected_post_repair_hash`, `reason`, `created_at`.

`repair_application_id` and `application_result_id` are deliberately the same value (`ApplicationResult.application_id`) — this repository has no separate, independently-identified "RepairApplication" record distinct from the transaction's own `ApplicationResult`; both suggested field names are kept, pointing at the one real identifier that exists, rather than inventing a second, redundant ID.

**The request references only an `ApplicationResult` — never a `RepairDraft`.** `build_verification_execution_request(application_result, ...)` reads `workspace_id`, `relative_path`, and `expected_post_repair_hash` directly off the `ApplicationResult` (`workspace_id`, `relative_path`, `post_application_content_hash`) — fields that already exist on that type specifically so no caller ever needs to reach past it to the draft that produced it. `application_result.outcome` must be `"applied"`; any other outcome raises `RepairNotAppliedError` immediately, since there is nothing to verify for a blocked or failed transaction.

## Workflow: Reuse, Not Reimplementation

```
ApplicationResult (already exists, real, on disk)
    -> build_verification_execution_request(...)  [this module]
    -> VerificationExecutionRequest
    -> propose_verification_execution(...)  [this module -- one function]
        1. execution_workflow.read_workspace_file(...)   <- gauss_workspace_file_reader, reused
        2. compare checksum to expected_post_repair_hash <- fail closed if stale
        3. execution_workflow.propose_execution(code=..., working_directory=...)
                                                          <- THE SAME METHOD ordinary execution uses
    -> ProposalOutcome                                   <- THE SAME TYPE ordinary execution returns
    -> (caller uses the ALREADY-EXISTING confirm_execution(...)/execute(...) -- untouched)
    -> ResponseReadyResult                               <- THE SAME TYPE ordinary execution returns
    -> compare_execution_outcomes(original, verification) [this module -- pure, no I/O]
    -> ComparisonSummary
```

`propose_verification_execution(...)` is the only function in this module that touches `ExecutionWorkflow`, and it calls exactly one of its methods (`propose_execution`) plus the pre-existing `read_workspace_file`. Confirmation and execution are **not wrapped by this module at all** — the CLI (and any future caller) uses `ExecutionWorkflow.confirm_execution(...)`/`execute(...)` (or the MVP facade's own `confirm(...)`/`execute(...)`) exactly as it already does for an ordinary execution, because a verification proposal produces an ordinary `ProposalOutcome` indistinguishable in type, and largely in content, from any other.

### Why the proposal is not workspace-lifecycle-bound

The workspace containing the repaired file already completed its one-shot lifecycle (`created → populated → ready → executing → completed`) during the *original* failing execution — `propose_execution`'s own existing workspace-completed check would unconditionally block a second workspace-bound proposal against it (this is `v0.52.0`'s own, deliberate one-attempt-per-workspace guarantee, unmodified and unchanged here). Verification's proposal therefore omits `workspace_id=` and instead passes `working_directory=<the workspace's own real root_path>` directly — an already-supported, pre-`v0.43.0` code path (workspace-unaware execution), not a new capability. The repaired file's real, on-disk content is still what gets executed, at its real location; only the workspace's own single-shot lifecycle bookkeeping is not re-entered for this second attempt, which is the correct behavior given that bookkeeping's own documented purpose (one execution attempt per workspace) was never meant to forbid verification as a concept — a fresh proposal targeting the same real directory is not "reusing" the completed workspace's own attempt, it is a new, independent one.

## Comparison Summary

`compare_execution_outcomes(original: ExecutionInterpretation, verification: ExecutionInterpretation) -> ComparisonSummary` is a pure function — no I/O, no re-execution, no re-interpretation of raw evidence (it consumes two already-computed `gauss_execution_interpreter.ExecutionInterpretation` objects, reusing that module's own classification rather than re-deriving it). It reports, deterministically, one of five evidence-only observations based on `completion_status`/`error_code`:

1. Original failed, verification succeeded → *"The repaired code executed successfully whereas the original execution failed with {code}."*
2. Original failed, verification failed with a different code → *"The repair changed execution behavior, but a different runtime error occurred."*
3. Original failed, verification failed with the same code → *"The repair did not change the observed execution outcome."*
4. Original succeeded, verification failed → *"The verification execution failed with {code} even though the original execution succeeded."*
5. Both succeeded / both failed identically in a way not covered above → a generic, honest same/different statement.

**`ComparisonSummary` has no `repair_correct`/`success_probability`/`confidence_score` field of any kind.** It reports `original_outcome`, `verification_outcome`, `same_outcome: bool`, and `observation: str` only — never a verdict.

## CLI

`verify-repair [--fake-success|--fake-failure|--fake-timeout|--fake-unknown-error]` builds the request, snapshots the original execution's own interpretation (before any state is overwritten), reads the repaired file, and calls `self.workflow.propose(...)` — the exact same facade method `plan` already calls — populating the exact same `self.mvp_session`/`self.pending_request` fields the pre-existing, **completely unmodified** `confirm`/`execute` commands already consume. `show-verification-request` displays the request and, once the verification execution has completed, the comparison summary.

## Testing

`scripts/test_gauss_verification_execution.py` covers request construction (including the not-applied rejection), stale-hash rejection, proposal reuse (asserting the returned object is a genuine `wf.ProposalOutcome`/`wf.ExecutionProposal`), full confirm/execute reuse through unmodified `ExecutionWorkflow` methods, and all five comparison-summary cases. CLI tests cover `verify-repair`/`show-verification-request` end to end with a real repaired file, plus a full regression check that ordinary `plan`/`confirm`/`execute` behavior is unaffected.

## 54.x Benchmarks — Evaluated, Not Placeholder

Ten `54.x` prompts created and genuinely evaluated against real, executed evidence (a real repaired file, real proposals, real fake-runner executions, real comparisons).

## Out of Scope (unchanged from the authorizing task)

Automatic retries, automatic repair acceptance, automatic rollback, automatic planning, automatic code editing, repair scoring, LLM repair loops, repair ranking, autonomous execution. No repair-specific execution engine, runner, proposal type, confirmation type, or session type was created.
