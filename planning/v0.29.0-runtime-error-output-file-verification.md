# v0.29.0 - GAUSS Runtime Error and Output File Verification

## Release Goal

`v0.29.0` verifies real GAUSS behavior beyond the `v0.28.0` hello-world and syntax-error cases.

`v0.29.0` should:

- Test runtime-error behavior under `tgauss.exe -b <script_path>`.
- Determine whether runtime errors produce detectable stdout/stderr patterns.
- Determine whether runtime errors return `exit_code` 0 or nonzero.
- Update GAUSS error detection only if new observed patterns justify it.
- Test safe output-file creation inside a disposable working directory.
- Verify whether `output_files` metadata detection works with real GAUSS-created files.
- Verify that no files are written outside the allowed working/output directory.
- Document stdout/stderr/exit-code/file behavior.
- Update tool docs and known limitations.
- Preserve all `v0.28.0` safety boundaries.

`v0.29.0` should **not**:

- Add runtime orchestration.
- Add automatic Code Assistant execution.
- Run user project code.
- Run real analyses.
- Install packages.
- Activate licenses.
- Access the network.
- Mutate global GAUSS configuration.
- Run destructive code.
- Claim cross-platform or cross-version support.
- Claim execution proves methodology validity.

## Current State

- `v0.28.0` verified `tgauss.exe -b <script_path>` on Windows GAUSS 26.1.1.
- The helper now uses the verified `-b` form for `tgauss`/`tgauss.exe`.
- GUI executable invocation is blocked.
- Syntax-error detection works for the observed failure pattern (`"Program execute failed"` in stdout; `error G####` in stderr).
- Exit code is unreliable because the syntax-error case returned `exit_code: 0`.
- Runtime-error behavior remains unknown — no runtime error (as opposed to a syntax error) has been smoke-tested.
- Output-file-writing behavior remains unknown — no test has confirmed real GAUSS-created files are correctly discovered.

## Candidate Runtime-Error Tests

Design conservative runtime-error smoke tests. Use only harmless examples. **Do not assume which error is best — research GAUSS-safe examples before proposing a live test**, the same discipline `v0.28.0` applied to invocation candidates.

## Runtime-Error Syntax Research Notes

**Files/docs/examples inspected:**

- Repository-wide grep search for `Undefined symbols`, `error G0`, `error G1`, `conformable`, `nonconformable` across all `.md`/`.json`/`.py` files (excluding this milestone's own planning docs).
- `experts/gauss-language/COMMAND_CATEGORIES.md` — the "Program Control" category (confirms `print`, `error`, `output`, `run`, `call` as real command names) and the matrix/array-creation category (confirms `ones`, `rows`, `cols`, `zeros`, `eye` as real command names).
- `experts/gauss-language/BODY_OF_KNOWLEDGE.md` — no mention of exact GAUSS runtime-error message wording found.
- `scripts/gauss_code_execution.py`'s `_detect_gauss_error` and its docstring — the only two GAUSS error messages actually observed anywhere in this project: `"Program execute failed"` (stdout) and `error G0105`/`error G0014` (stderr), both from the `v0.28.0` syntax-error and inline-expression smoke tests.
- No command-specific evidence file (`examples/retrieval/schema-aligned/*.evidence.json`) exists for any error-related or undefined-symbol-related command — the current seven/nine-command pilot evidence set (`olsmt`, `strindx`, `strsplit`, `dstatmt`, `qnewtonmt`, `pdsummary`, `minimize`, `glm`, `tscsfit`) does not cover this area.

**Candidate 1 — Undefined symbol / undefined variable**

- **Proposed script contents:** `print undefinedvar;`
- **Source/rationale:** `print` is a confirmed real command (Program Control category; already used successfully in `v0.28.0`'s completed-case smoke test). Referencing an unassigned identifier is core GAUSS language semantics, not a named command requiring its own evidence file — the risk being tested is language-level (undefined-symbol resolution), not command-specific syntax.
- **Expected behavior:** GAUSS reports an undefined-symbol error and exits non-interactively (consistent with `v0.28.0`'s finding that `-b` causes clean exits even on error).
- **Expected stdout/stderr pattern, if known:** Not confirmed. The two error messages actually observed so far (`"Program execute failed"` in stdout; `error G0105`/`error G0014` in stderr) both follow a `Program execute failed` + `error G####` shape. It is *plausible* an undefined-symbol error follows the same shape (a different `G` code), but this is an informed expectation based on two data points, not a repo-verified fact.
- **Safety notes:** No side effects — no file writes, no data operations, no computation beyond a single failed `print`.
- **Status:** **Recommended for smoke test** — safest possible runtime-error candidate; uses only already-verified `print` plus an intentionally-undefined identifier.

**Candidate 2 — Dimension mismatch / nonconformable matrix operation**

- **Proposed script contents:** `x = ones(2,2); y = ones(3,3); z = x + y;`
- **Source/rationale:** `ones` is a confirmed real command name (`experts/gauss-language/COMMAND_CATEGORIES.md`'s matrix/array-creation category). Matrix addition (`+`) is core GAUSS operator syntax. This candidate was already proposed (as a "Test 4" runtime-error design) in `v0.28.0`'s original planning doc, but was never actually run — only the syntax-error variant (`x = ;`) was executed during the `v0.28.0` smoke-test task.
- **Expected behavior:** GAUSS reports a conformability/dimension error when attempting to add two differently-shaped matrices, and exits non-interactively.
- **Expected stdout/stderr pattern, if known:** Not confirmed — same caveat as Candidate 1; the `error G####` shape is plausible but not verified for this specific error type.
- **Safety notes:** No side effects — matrices are trivially constructed in-memory via `ones`, no file I/O, no external data.
- **Status:** **Recommended for smoke test** — second-safest candidate; exercises a genuinely different failure category (numerical/shape error) than Candidate 1 (symbol-resolution error) or the already-tested syntax error.

**Candidate 3 — Divide by zero**

- **Proposed script contents:** `x = 1/0; print x;`
- **Source/rationale:** Core arithmetic operator syntax; no command evidence needed.
- **Expected behavior:** Genuinely uncertain. IEEE 754 floating-point division by zero commonly produces `Inf` rather than raising a runtime error in many numerical languages; GAUSS's specific behavior here is not documented anywhere in this repository.
- **Expected stdout/stderr pattern, if known:** Unknown. If GAUSS errors, an arithmetic-error message would be expected; if GAUSS instead prints `Inf`/`nan` and continues, the result would be `execution_status: completed` with no error — a legitimate, informative outcome, not a test failure, but also not useful for expanding `_detect_gauss_error`.
- **Safety notes:** No side effects.
- **Status:** **Possible but uncertain** — worth trying only if Candidates 1-2 leave time/need; low priority since the outcome may not even be a failure case.

**Candidate 4 — Invalid file read (nonexistent file)**

- **Proposed script contents:** Not finalized — a `load`-style statement was originally proposed in the `v0.29.0` planning doc, but no verified `load`/read syntax was found in this repository's evidence during this research pass.
- **Source/rationale:** None found. `COMMAND_CATEGORIES.md`'s "Data Import and Export" category lists real command names (`csvreadm`, `dataopen`, `loadd`, `readr`, etc.) that could plausibly read a nonexistent file and fail, but none has a command-specific evidence file confirming exact argument syntax in this repository.
- **Status:** **Rejected for this milestone / not evidenced** — do not run with guessed syntax. If pursued later, a specific read command's syntax should first be verified through this project's normal command-documentation-retrieval workflow (official docs or a command-specific evidence file), not assumed from a category listing alone.

## Candidate Output-File Tests

**Goal:** create a tiny text or CSV-like output file inside the disposable working directory, then confirm the helper's `output_files` discovery lists it correctly as metadata only.

**Requirements:**

- File path must be relative or explicitly inside the disposable working directory — never an absolute path outside it.
- Script must not overwrite unrelated files — the disposable directory must be freshly created or otherwise known-empty before the test.
- Output content must be harmless (e.g., a trivial numeric or string value).
- `output_files` metadata should record the created file (path, size, discovered) after execution.
- File contents must not be interpreted by this milestone's test procedure beyond confirming the file exists and has a plausible size — reading and asserting on file *contents* is out of scope for the helper's own metadata-only discovery contract (per `workflows/execution-aware-analysis.md` and `workflows/report-generation.md`'s existing "metadata, not contents" rule).

**Research required before any live test:** see "Output-File Syntax Research Notes" immediately below — verified syntax was found, so this test is no longer blocked on an uncertain command form. (Note: an earlier draft of this section conflated the `-l logfile` CLI flag from `v0.28.0`'s smoke tests — confirmed to write job-metadata only, not arbitrary content — with the separate, in-script `output file = ...` statement researched below; these are two different mechanisms, and only the latter is relevant to writing arbitrary content to a file.)

## Output-File Syntax Research Notes

**Files/docs/examples inspected:**

- `C:\gauss26\README.txt` — re-inspected; no file-writing syntax documented (it documents `tgauss` command-line flags and interactive commands only, not in-script GAUSS statements).
- `experts/gauss-language/COMMAND_CATEGORIES.md` — confirms `output` as a real command name (Program Control category) and `csvwritem`, `writer`, `fopen`, `fputs`, `saved` as real command names (Data Import and Export category) — category membership only, no argument syntax.
- `C:\gauss26\examples\` directory — searched for example files mentioning `output file`, `csvwritem`, `fopen`, or `fputs` (read-only `grep`, plain-text `.e` files only, no execution). Matches found in `circular.e`, `eqsolve1.e`, `eqsolvemt2.e`, `eqsolvemt3.e`, `eqsolvemt4.e`, `ols.e`, `qnewtonmt2.e`, `qnewtonmt3.e`, `sqpfact.e`, `sqpsolvemt1.e`, `sqpsolvemt_frontier.e`, `sqpsolvemt_nlls.e`, `sqptest.e`, `time.e`.
- Four of these were read directly (`ols.e` in full; `circular.e`, `time.e`, `eqsolve1.e` for the relevant lines) — all real, official example scripts shipped with this development machine's GAUSS 26 installation, not written by this project.

**Verified finding:** all four inspected examples use the same idiom, confirming it is genuine, real, official GAUSS syntax:

```
output file = <relative_filename> reset;
<statements that produce console output, e.g. print, or a call that prints results>
output off;
```

`ols.e` (read in full) demonstrates this most clearly and directly confirms the working-directory-relative behavior this milestone requires:

```gauss
rndseed 345346;
x = rndn(100, 5);
y = rndu(100, 1);

output file = ols_output.txt reset;
call ols("", y, x);

output off;

print;
print "Results of this run stored in ols_output.txt file";
print "The file will be found in your working directory";
```

`time.e` uses `output file = time_results.txt on;` (`on` rather than `reset`) — suggesting `reset` (start fresh, presumably truncating/overwriting) and `on` (presumably append/resume) are both real, distinct options, though the exact difference is inferred from usage rather than independently confirmed by a documentation source.

**Candidate — `output file` redirection**

- **Proposed script contents:** `output file = gauss_output.txt reset; print "hello output test"; output off;`
- **Source/rationale:** Directly modeled on the confirmed real usage in `ols.e`/`circular.e`/`eqsolve1.e`/`time.e` — not invented. Reuses `print`, already verified safe and working in `v0.28.0`'s completed-case smoke test.
- **Expected created file name:** `gauss_output.txt` (or any chosen relative filename).
- **Expected output location:** Inside the working directory the script is invoked from — `ols.e`'s own comment ("The file will be found in your working directory") directly confirms this.
- **Relative path only:** Yes — every inspected example uses a bare relative filename, never an absolute path.
- **Overwrite risk:** `reset` is used in three of the four examples and is presumably the safer, non-appending choice for a fresh disposable working directory; `on` (as seen in `time.e`) is avoided for this candidate to minimize any ambiguity about append-vs-overwrite semantics.
- **Verified by docs/examples:** Yes — by real, official, shipped GAUSS example files (not by this repository's own retrieval-evidence pipeline, and not by official online documentation directly, since neither was consulted in this task).
- **Status:** **Recommended for smoke test** — the strongest-evidenced candidate in this entire research pass, directly sourced from multiple real official examples rather than inferred or guessed.

**If no safe syntax had been found:** it was not necessary to fall back to this contingency, since verified syntax was found. Had it not been, the recommendation would have been to defer the output-file live test and consult official GAUSS documentation (the `output` command's reference page) or the local Qt Compressed Help files (`C:\gauss26\help\gauss.qch`/`.qhc`, still unread as of this research pass — see `v0.28.0`'s "Research Notes" for why) before proceeding.
