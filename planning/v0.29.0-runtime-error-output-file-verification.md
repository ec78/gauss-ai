# v0.29.0 - GAUSS Runtime Error and Output File Verification

## Release Goal

`v0.29.0` verifies real GAUSS behavior beyond the `v0.28.0` hello-world and syntax-error cases.

`v0.29.0` should:

- Test runtime-error behavior under `tgauss.exe -b <script_path>`.
- Determine whether runtime errors produce detectable stdout/stderr patterns.
- Determine whether runtime errors return `exit_code` 0 or nonzero.
- Update GAUSS error detection only if new observed patterns justify it.
- Test safe output-file creation inside a disposable working directory.
- Verify whether `output_files` metadata detection works with real GAUSS-created files.
- Verify that no files are written outside the allowed working/output directory.
- Document stdout/stderr/exit-code/file behavior.
- Update tool docs and known limitations.
- Preserve all `v0.28.0` safety boundaries.

`v0.29.0` should **not**:

- Add runtime orchestration.
- Add automatic Code Assistant execution.
- Run user project code.
- Run real analyses.
- Install packages.
- Activate licenses.
- Access the network.
- Mutate global GAUSS configuration.
- Run destructive code.
- Claim cross-platform or cross-version support.
- Claim execution proves methodology validity.

## Current State

- `v0.28.0` verified `tgauss.exe -b <script_path>` on Windows GAUSS 26.1.1.
- The helper now uses the verified `-b` form for `tgauss`/`tgauss.exe`.
- GUI executable invocation is blocked.
- Syntax-error detection works for the observed failure pattern (`"Program execute failed"` in stdout; `error G####` in stderr).
- Exit code is unreliable because the syntax-error case returned `exit_code: 0`.
- Runtime-error behavior remains unknown — no runtime error (as opposed to a syntax error) has been smoke-tested.
- Output-file-writing behavior remains unknown — no test has confirmed real GAUSS-created files are correctly discovered.

## Candidate Runtime-Error Tests

Design conservative runtime-error smoke tests. Use only harmless examples. **Do not assume which error is best — research GAUSS-safe examples before proposing a live test**, the same discipline `v0.28.0` applied to invocation candidates.

| Candidate | Script contents | Expected behavior | Risk level | Run in this milestone? | Detectable-failure signal |
|---|---|---|---|---|---|
| Undefined variable/symbol | `print undefinedvar;` | GAUSS reports an undefined-symbol error and exits | Low — no side effects, no data operations | Yes, primary candidate | An undefined-symbol error message in stdout/stderr, distinct wording from the `v0.28.0` syntax-error case |
| Dimension mismatch | `x = ones(2,2); y = ones(3,3); z = x + y;` | GAUSS reports a conformability/dimension error and exits | Low — no side effects, matrices are trivially constructed in-memory | Yes, secondary candidate | A dimension/conformability error message in stdout/stderr |
| Divide by zero | `x = 1/0;` | Uncertain — GAUSS may return `Inf`/`Nan` silently rather than erroring, since IEEE floating-point division by zero is often not a runtime error at all | Medium — behavior unknown, could silently "succeed" rather than fail, which is itself useful information but not a reliable error-detection test case | TBD — only if the first two candidates leave time/need, since the expected behavior is genuinely uncertain rather than a clean error case | If it errors: an arithmetic error message. If it does not error: `Inf`/`Nan` printed, `execution_status: completed` — a legitimate, informative negative result, not a test failure |
| Invalid file read (nonexistent file) | `load x = nonexistent_file.dat;` (syntax to be confirmed against real docs before use, not assumed) | GAUSS reports a file-not-found or load error and exits | Low, provided the load syntax is confirmed read-only and does not create a placeholder file as a side effect | Only if safe load syntax is confirmed first — do not run with guessed syntax | A file-not-found or load-error message in stdout/stderr |

## Candidate Output-File Tests

**Goal:** create a tiny text or CSV-like output file inside the disposable working directory, then confirm the helper's `output_files` discovery lists it correctly as metadata only.

**Requirements:**

- File path must be relative or explicitly inside the disposable working directory — never an absolute path outside it.
- Script must not overwrite unrelated files — the disposable directory must be freshly created or otherwise known-empty before the test.
- Output content must be harmless (e.g., a trivial numeric or string value).
- `output_files` metadata should record the created file (path, size, discovered) after execution.
- File contents must not be interpreted by this milestone's test procedure beyond confirming the file exists and has a plausible size — reading and asserting on file *contents* is out of scope for the helper's own metadata-only discovery contract (per `workflows/execution-aware-analysis.md` and `workflows/report-generation.md`'s existing "metadata, not contents" rule).

**Research required before any live test:** `v0.28.0`'s research already found GAUSS's `output file = <path> reset;` / `output off;` construct is real (it was used to generate the local `smoke.log`-style job header in a `-l` test, and appears in official-style GAUSS idioms), but its exact behavior for writing arbitrary user-controlled content (as opposed to redirecting the console log) has not been directly verified as a "write a CSV" idiom. **If safe syntax is uncertain when this milestone's research step actually runs, the output-file test must wait for verified syntax** — it must not proceed on a guessed `output file`/`fopen`/`csvWrite`-style call without confirming the exact command against local or official GAUSS documentation first, mirroring `v0.28.0`'s "do not assume flags" discipline applied to invocation research.

## Safe Smoke-Test Policy

- Use only disposable working directories.
- Use short timeouts (15 seconds, consistent with `v0.28.0`'s smoke-test timeout).
- Use `C:\gauss26\tgauss.exe` only if still available.
- Do not run user project code.
- Do not install packages.
- Do not activate licenses.
- Do not access network.
- Do not mutate global GAUSS configuration.
- Do not delete unrelated files.
- Do not write outside the disposable working/output directory.
- Check for lingering `tgauss.exe`/`gauss.exe` processes after each real test.
- Record exact command, script, cwd, timeout, stdout, stderr, exit code, elapsed time, files created, and process cleanup result — the same recording discipline `v0.28.0`'s "Smoke-Test Log" established.

## Expected Helper Updates

Helper code should be updated **only if real observed output justifies it** — the same discipline `v0.28.0` applied (research and verify first, then integrate).

**Possible updates:**

- Expand `_detect_gauss_error` with new runtime-error patterns, if a runtime error produces stdout/stderr text distinct from the existing `"Program execute failed"`/`error G####` patterns.
- Improve the warning message when `exit_code == 0` conflicts with detected error output, if a runtime error surfaces a case the current wording doesn't cover well.
- Adjust `output_files` listing only if real GAUSS-created files expose a bug in `_discover_output_files` (for example, an unexpected file type, an unexpected path shape, or a `created_by_execution` inference opportunity not previously possible without a real file to test against).
- Add self-tests for any new observed runtime-error pattern, mirroring `v0.28.0`'s fake-runner self-test additions.
- Add self-tests for `output_files` metadata behavior if real-file testing reveals a gap not already covered by the existing fake-runner "output files limited to working_directory" self-test.

**Do not change schemas unless absolutely required** — no schema gap is currently known; this milestone should only touch `schemas/gauss_code_execution.schema.json` if a genuinely new field or constraint is discovered to be necessary, not preemptively.

## Risks and Open Questions

- Runtime-error patterns may differ from syntax-error patterns.
- `exit_code` may remain unreliable for runtime errors, the same way it was for the syntax-error case.
- Output-file syntax may require GAUSS commands not yet verified.
- GAUSS may create auxiliary files (logs, temp files) beyond the intended output file.
- Output-file paths may behave differently relative to cwd than assumed.
- The helper's `output_files` listing may need refinement once tested against a real file.
- Output-file contents must not be confused with metadata — the existing "listed, not read" boundary must hold even for real files.
- A test could accidentally overwrite files if paths are not carefully controlled — disposable, freshly-created directories are required for every test.
- Cross-platform and cross-version behavior remain unverified — unchanged from `v0.28.0`, not this milestone's scope to resolve.
