# v0.45.0 GAUSS Code Assistant MVP Workflow

## Release Goal

Integrate the execution architecture built across `v0.37.0`-`v0.44.0` — conversational execution workflow, execution sessions, workspace abstraction, workspace-integrated execution, safe workspace file reading, output provenance — into one coherent, orchestrated user journey: from an initial coding request, through planning, through execution (only when authorized), through result inspection, to a final assistant response. **This milestone emphasizes orchestration and user experience, not new infrastructure.** It creates one new, thin facade module that *coordinates* existing modules; it does not reimplement, duplicate, or bypass any of their own guarantees.

**Explicit non-goals, restated from the authorizing task:** uploads; persistent storage; cloud execution; multi-user support; binary file readers; PDF/image parsing; autonomous execution; autonomous file reading; execution helper changes.

## Inspected Sources

- `scripts/gauss_execution_workflow.py` — `ExecutionWorkflow` (`propose_execution`/`confirm_execution`/`execute`/`cancel`/`inspect`/`read_workspace_file`/`request_rerun`), `classify_interaction_mode(...)`, `InteractionMode`, `ExecutionProposal`, `ResponseReadyResult`, `WorkspaceProvenance`.
- `scripts/gauss_execution_session.py` — `ExecutionSession`/`create_session`/`confirm_session`/etc. Confirmed still unwired to `ExecutionWorkflow` (per `KNOWN_LIMITATIONS.md`'s own `v0.40.0` entry) — this milestone does not change that; "execution session reference" in this document's Workflow Result Model means `orchestration_instance_id` (the identifier `WorkspaceProvenance.execution_session_id` already uses for exactly this concept), not a `gauss_execution_session.ExecutionSession` object.
- `scripts/gauss_workspace.py` — `WorkspaceRegistry` (`create_workspace`/`get_workspace`/`validate_workspace`/`get_workspace_manifest`/etc.), `WorkspaceStatus`.
- `scripts/gauss_workspace_file_reader.py` — `WorkspaceFileReadRequest`/`WorkspaceFileReadResult`/`read_workspace_file(...)`.
- `agents/code-assistant/AGENT.md`, `workflows/real-execution-user-workflow.md`, `workflows/code-assistant-response.md`, `workflows/execution-aware-analysis.md`, `workflows/report-generation.md` — the existing consent model, evidence/interpretation boundary, and expert-routing conventions this facade's user-facing summaries must remain consistent with, never redefine.
- `planning/v0.37.0`-`v0.44.0` — the full chain of design decisions this milestone composes rather than revisits: durable confirmation, workspace lifecycle, output provenance, explicit-only file reading.

## The Complete User Journey

1. **User request.** Raw conversational input, already turned into structured, pre-classified facts by the agent layer (never parsed as natural language by this facade, mirroring `classify_interaction_mode`'s own existing contract).
2. **Intent classification.** `GaussCodeAssistantWorkflow.classify_intent(signal)` — a direct pass-through to `gauss_execution_workflow.classify_interaction_mode(...)`; this facade adds no second classifier and no natural-language inference of its own.
3. **Workspace selection.** `select_workspace(workspace_id)` — validates (via `WorkspaceRegistry.validate_workspace(...)`) that the named workspace exists, is not deleted, and passes containment/ownership checks. This facade never creates a workspace implicitly; a workspace must already exist (created via `gauss_workspace.WorkspaceRegistry.create_workspace(...)`, outside this facade's own responsibility) before a session can select it.
4. **Execution planning.** `propose(...)` — a thin wrapper over `ExecutionWorkflow.propose_execution(...)`, forwarding `workspace_id`. All eligibility/safety/workspace-containment logic remains exactly where `v0.37.0`-`v0.43.0` put it; this facade adds no new checks.
5. **Confirmation (when required).** `confirm(...)` — a thin wrapper over `ExecutionWorkflow.confirm_execution(...)`. Only reachable from a session already holding an unblocked proposal; a rejected or invalid confirmation is reported honestly, never silently retried.
6. **Execution.** `execute(...)` — a thin wrapper over `ExecutionWorkflow.execute(...)`. Only reachable from a confirmed session. The underlying workspace lifecycle (`ready → executing → completed`) and output-provenance registration already happen automatically inside `ExecutionWorkflow.execute(...)` when the proposal was workspace-bound — this facade does not re-implement either.
7. **Output registration.** Already complete by the time `execute(...)` returns (per `v0.43.0`); this facade only *captures* `ResponseReadyResult.workspace_provenance` into its own session state — it performs no registration of its own.
8. **Optional file reading.** `read_file(session, request)` — a thin wrapper over `ExecutionWorkflow.read_workspace_file(...)`, requiring an explicit `WorkspaceFileReadRequest` naming the session's own `workspace_id`. Never called automatically by `execute(...)` or `compose_response(...)`.
9. **Analysis.** A lightweight, deterministic, rule-based interpretation of the `ResponseReadyResult` (evidence vs. conclusion separation, methodology caveat) — **not** a call into `gauss_runtime_orchestration.py`'s own `begin_analysis()`/`AnalysisStatus` machinery (which would require injecting fake analysis/report hooks, a controller-level extension out of scope here). `WorkflowResult.analysis_status` remains an honest pass-through of the controller's own `analysis_status` field (`"not_started"` unless a future milestone wires real analysis) — never fabricated as `"completed"` by this facade.
10. **Final assistant response.** `compose_response(session) -> WorkflowResult` — assembles everything gathered above into one structured object with a consistent, honest `user_facing_summary` string.

## Decision Points and Failure Modes

- **Advisory/explain/review/revise intents never reach `propose(...)` at all.** `advisory_response(mode, note)` produces a `WorkflowResult` with `execution_status=None` directly, for exactly this case — consistent messaging without ever touching the execution stack.
- **A blocked proposal** (ineligible, unsafe, workspace invalid/deleted/archived, path outside workspace) ends the session at `DECLINED`; `compose_response(...)` still returns a structured, honest `WorkflowResult` explaining why, never a raw exception surfaced to the user.
- **A rejected confirmation** also ends at `DECLINED`.
- **An execution failure** (runtime error, timeout, missing output, malformed result) still reaches `EXECUTED` — a failure is a *result*, not a facade-level error; `WorkflowResult.user_facing_summary` distinguishes it clearly from a declined/blocked session.
- **A file-read failure** is reported on its own terms (a `WorkspaceFileReadResult` with a specific `error_code`) and never described as an execution failure — restated from `v0.44.0`.
- **Calling a stage out of order** (e.g. `execute(...)` before `confirm(...)`) raises `MvpWorkflowStageError` immediately — this facade's own session-stage tracking is a *reporting* convenience, not a second, independent enforcement layer that could drift out of sync with the controller's real 13-state machine or the workspace's real 7-state machine; every real guard still lives exactly where it already did.

## Workflow Result Model

`WorkflowResult` (frozen dataclass, `scripts/gauss_code_assistant_workflow.py`):

- `request_summary` — a short, caller-supplied description of what was asked (audit-only).
- `workspace_id` — `None` for a non-execution (advisory) response.
- `execution_status` — `None` until `execute(...)` has run; otherwise the controller's own `execution_status` string.
- `execution_session_reference` — the `orchestration_instance_id` (see "Inspected Sources" above for why this, not a `gauss_execution_session.ExecutionSession`, is what this field means today).
- `files_produced` — `ResponseReadyResult.output_files`, metadata only.
- `files_read` — every `WorkspaceFileReadResult` this session's `read_file(...)` calls have produced, in order.
- `provenance` — `ResponseReadyResult.workspace_provenance`, when present.
- `analysis_status` — the honest pass-through described above.
- `user_facing_summary` — a consistent, template-composed string (see User Experience below).

## User Experience

Consistent messaging templates for the six scenarios the authorizing task names, implemented as `_summarize_*` helper functions feeding `user_facing_summary`:

1. **Explain GAUSS code.** No execution stack involved at all. `advisory_response(InteractionMode.EXPLAIN_CODE, ...)`. Summary states plainly that this was an explanation, not a run.
2. **Debug GAUSS code.** Same shape as (1), `InteractionMode.REVIEW_CODE`/domain-specific debugging framing remains the agent's own responsibility (expert routing, unchanged) — this facade only guarantees the *non-execution* path stays clearly labeled as such.
3. **Execute GAUSS code (confirmation required).** `propose(...)` → summary names the exact plan and asks for confirmation; only after `confirm(...)` succeeds does `execute(...)` become reachable. The summary at the proposal stage explicitly states nothing has run yet.
4. **Read an output file.** Only ever the result of an explicit `read_file(...)` call; summary distinguishes "file content evidence" from "execution evidence" and states the fixed methodology caveat.
5. **Explain execution errors.** After `execute(...)` returns a failure, the summary surfaces `runtime_error_detected`/`timed_out`/`missing_expected_output` explicitly and states this is not a facade-level failure — restated from `v0.37.0`'s own execution-aware boundary.
6. **Decline unsafe requests.** A blocked proposal's summary names the specific blocking reason (from `ProposalOutcome.failure_reason`) and offers a safe next step, never a bare refusal.

Every summary, regardless of scenario, includes the same non-negotiable disclosures already established: execution/read evidence is not methodology validation; `exit_code` is never authoritative; `output_files`/read content is metadata/evidence, not proof; a rerun always needs a fresh proposal.

## Testing Strategy

`scripts/test_code_assistant_mvp_workflow.py`: representative end-to-end scenarios (advisory-only, full propose→confirm→execute→read→respond happy path, blocked proposal, rejected confirmation, execution runtime error, file-read failure, out-of-order-stage rejection, workspace isolation across two sessions), using fake runners, disposable `WorkspaceRegistry`/`OrchestrationStateStore` temp directories, and no GAUSS invocation. Every guarantee already covered by `test_gauss_execution_workflow.py`/`test_workspace_execution_integration.py`/`test_gauss_workspace_file_reader.py` is not re-tested here in detail — this file tests *orchestration* (the facade correctly sequences and reports on existing modules), not the modules' own internal correctness a second time.

## Non-Goals

Restated from the authorizing task: uploads; persistent storage; cloud execution; multi-user support; binary file readers; PDF/image parsing; autonomous execution; autonomous file reading; execution helper changes; moving existing logic out of `gauss_execution_workflow.py`/`gauss_workspace.py`/`gauss_workspace_file_reader.py` into this facade (composition only); real analysis-engine integration (`begin_analysis()`/`AnalysisStatus` remain untouched); wiring `gauss_execution_session.py` into this facade (a separate, still-open gap this milestone does not close).
