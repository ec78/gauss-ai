Status: **implemented** (2026-10-20), not yet committed or released. The plan (§1-§8) was approved on 2026-10-20 with every §8 recommendation. §9 records what changed during implementation and the diffs; §10 is testing. Live evaluation 78.x (§7) ran on 2026-10-20 and is recorded in §11 (16 pass; eight approved real-GAUSS runs, each byte-identical to direct GAUSS; the replacement path was confirmed over the real transport by a recording-session probe, not by the live client). ## 1. Why

Live evaluations 76.x and 77.x (v0.86 plan §11.6, §12.6) found six small, pre-existing defects in the execution handoff and the precondition registry. One of them concerns the consent contract itself.

| # | Finding | Seen in | Effect |
|---|---|---|---|
| 1 | 77.x f2: `gauss_execution_decide` is not bound to the prompt the user saw | 77.1, 77.9; probe P5 | `prepare` silently replaces the pending request, and `decide` takes no `request_id`. A "yes" approves whatever was prepared last, and the response does not say which request ran. |
| 2 | 76.x f3: a refused prepare spends its `validation_id` | 76.10, 76.11 | `real_gauss_not_allowed` and `validation_stale` both consume the id. A resubmission then says `unknown_or_used_validation_id`, which is false: the id was never used. |
| 3 | 76.x f2: `gauss_session_start` does not report the real-GAUSS opt-in | 76.1 | A client cannot tell that a run is impossible until a prepare fails. In 76.1 the client guessed from a config file and told the user something false. |
| 4 | 77.x f3: the prompt shows a "Workspace parent" that is never used | 77.9-77.17 | Every approved run executed in a deleted temp directory, not the directory the prompt named. |
| 5 | 77.x f1: operator forms skip the precondition registry | 77.17; P1/P2 | A literal singular matrix is not_ready through `inv(a)` but handoff_candidate through `eye(2) / a`. |
| 6 | 76.x f6: `eigh` has no symmetry precondition | 76.12, 77.11; e07 | A non-symmetric literal reaches handoff_candidate, runs without error, and prints the eigenvalues of a different matrix. |

Goals:
- `decide` acts only on the request whose `request_id` the client names, and refuses anything else without creating an approval (items 1-3 touch only `gauss_mcp_server.py`);
- the prompt describes what the run actually does (item 4);
- every new precondition rule comes from a `tgauss.exe -b` spot check (§2) and cites it;
- no verdict moves toward handoff_candidate. Every predicted verdict change is toward review_required or not_ready (§6.2).

Constraints (as in v0.86.0):
- no change to `command_doc_lookup.py`, signature/type extraction, grounding, `compute_generation_gate` or the concept index, so the `ask()` gate is unchanged (§6.4);
- the readiness state machine, `compute_eligibility`, `compute_evidence_profile`, `check_parameter_roles`, the syntax layer and the system-statement registry (216 entries) are unchanged;
- the execution core is unchanged except one rendering function (§3.4): no change to the digest, the approval store, `_prelaunch_check`, `execute_execution_handoff` or the adapter;
- all source is read through `lex_gauss_source` / `source_statements` (CLAUDE.md; `test_170`).

Out of scope: the search/grounding milestone (v0.88.0 if renumbered, including 76.x finding 5), upstream docs defects (76.x f4, 75.x f8), expression category inference, reserved words, and public release readiness (§4).

### 2.1 Item 1: `decide` is not bound to the prompt (77.x finding 2)

**Code:**
- `Session.pending_request` (`gauss_mcp_server.py:141`) is one slot;
- `gauss_execution_prepare` overwrites it without checking it (`:422`) and returns only `request_id`, `digest` and `rendered_prompt` (`:424-428`);
- `gauss_execution_decide(session_id, response_text)` (`:432`) reads whatever is in the slot (`:442`);
- its response (`:468-475`) has no `request_id` and no request digest (`result_digest` is a digest of the result).

**R1** (fake runner): validate A (`invpd({2 1, 1 2})`) and B (`invpd({4 1, 1 4})`), prepare A, then prepare B.
- B's prepare response has the same three keys as A's, with no sign that A was replaced.
- `decide(sid, "yes")` returns `success`. A spy helper shows that **B's code ran**.
- Neither A's nor B's `request_id` or digest appears anywhere in the decide response.
- The decide signature is `(session_id, response_text)`.

This confirms P5 (v0.86 §12.6).

**What already holds:**
- an `unrecognized` reply keeps the request pending (`:446-447`);
- a decide with nothing pending is `no_pending_request`;
- the approval is digest-bound to the request it was created from (`create_execution_handoff_approval`), so what runs is always exactly what was prepared last.

The gap is only which prompt the user's reply answers.

**Client constraints:**
- **Stale tool descriptions (KL v0.80.0, 70.x):** Claude Code kept v0.79.0's tool descriptions for tools whose names did not change, so a client did not know `validation_id` existed. The server accepted the argument anyway. A new `decide` parameter will likewise be invisible to some clients until they restart fully.
- **The client chooses what to send.** The prompt shows the request digest, not the `request_id` (`render_execution_handoff_prompt`, `gauss_execution_handoff.py:658`). Either way, the client copies the identifier from the prepare response. Binding cannot prove the user saw the prompt. It can force the client to say which prompt the reply answers, and refuse a reply aimed at a prompt that is no longer pending.

### 2.2 Item 2: a refused prepare spends its `validation_id` (76.x finding 3)

**Code:** `gauss_execution_prepare` pops the id first (`gauss_mcp_server.py:391`). Only then does it re-validate (`:396-398`, `validation_stale`), check the opt-in (`:405`, `real_gauss_not_allowed`) and build the request (`:415-421`, `request_rejected`).

**R2:**

| Session | First prepare | Same id again |
|---|---|---|
| runner `gauss`, no opt-in | `real_gauss_not_allowed` | `unknown_or_used_validation_id` |
| fake runner, docs page removed before prepare (R2b) | `validation_stale` | `unknown_or_used_validation_id`, even after the page was restored |

**What it actually costs:**
- **Within one server process, a refused id can never succeed later.** The opt-in is the process's own environment, and a session's runner and executable are fixed at `gauss_session_start`. So the spent id loses nothing that could have been used.
- **The defect is the false error.** A resubmission is told the id was "used", which sent 76.10's client to re-validate, without an explanation.
- `request_rejected` (for example, runner `gauss` with no executable configured) spends the id the same way.

### 2.3 Item 3: the opt-in is not reported (76.x finding 2)

**Code:** `gauss_session_start` (`gauss_mcp_server.py:266-297`) returns `session_id`, `runner`, `docs_root_configured` (and `hint`). `_real_gauss_allowed()` (`:95`) is computed only inside prepare and `gauss_repair_start` (`:498`).

**R3:** the response keys are identical with and without `GAUSS_AI_MCP_ALLOW_REAL_GAUSS=1`: `['docs_root_configured', 'runner', 'session_id']`.

**What a flag could and could not prove:** the opt-in only removes the server's refusal. A prepare with a nonexistent executable still succeeds, and the run fails in the adapter's environment probe (`test_18`). So no field can say that real execution "works". Only a run proves that.

**Code:**

- `execute_execution_handoff` always runs in `tempfile.TemporaryDirectory(prefix="gauss_ai_handoff_")` (`:586`) and never reads `request.workspace_parent`;
- the field is digest-bound (`_DIGEST_FIELD_ORDER`, `:93-101`);
- both callers pass the configured value: `gauss_mcp_server.py:418` and `gauss_ai_chat.py:250-253`.

**R4:** the prompt contains `Workspace parent: <tmp>`. The helper received `working_directory = C:\Users\Owner\AppData\Local\Temp\gauss_ai_handoff_57rsar7s`, which is not under it.

**The temp directory is the design, not the bug:**

### 2.5 Item 5: operator forms skip the precondition registry (77.x finding 1)

**Code:**
- `check_preconditions(call, code=…)` (`gauss_pre_execution_validation.py:1910`) runs only for extracted calls whose symbol is in `_PRECONDITION_CHECKERS` (`:1902`: `invpd`, `inv`, `solpd`, `chol`);
- the engine calls it once per extracted call (`gauss_conversation_engine.py:1768-1772`, in `validate_generated_code`, which `validate_code` and the `ask()` path share);
- an operator is never a call, so `/` is never checked.

**HEAD probes:**

| ID | Code (abridged) | HEAD |
|---|---|---|

**What GAUSS documents:**
- `user-guide/fundamentals/operators.rst`: "`A / B` is equivalent to `inv(B) * A`. If either operand is a scalar, performs element-wise division instead."
- `matrix-division.rst`: "Computes the least squares solution to a system of equations, or performs scalar division", and in Remarks: "computes the least squares solution using QR decomposition."

**Spot checks (the dv series):**

| ID | Program (abridged) | Result | Establishes |

## 3. Proposed design

Deterministic and stdlib-only. No new module and no `pyproject.toml` change beyond the version.

### 3.1 `decide` binds to a `request_id` (item 1)

**`gauss_execution_decide(session_id, response_text, request_id=None)`.** `request_id` comes last, so existing positional calls still parse. Checks run in this order, all **before** the reply is parsed or any approval is created:
1. unknown session → `unknown_session` (unchanged);
2. nothing pending → `no_pending_request` (unchanged);
3. **`request_id` omitted → `{"error": "request_id_required", "detail": …}`.** The detail says to pass the `request_id` that `gauss_execution_prepare` returned with the prompt the user answered. Nothing is recorded, and the request stays pending. The parameter is optional in the schema but required in effect (decision 2), so a client with a stale tool description gets this explanation rather than a schema error.
4. **`request_id` ≠ the pending request's:**
   - if a later prepare replaced it → `request_superseded`, with `pending_request_id`;
   - otherwise (unknown, or already decided) → `request_not_pending`.

   Either way, nothing is recorded or run.
5. otherwise, unchanged: parse; `unrecognized` keeps the request pending; then decline, or approve and execute once.

**Every decide response that refers to a request echoes it:** `request_id` and `request_digest` (the digest the prompt showed), on `unrecognized`, `declined` and every execution outcome.

**`gauss_execution_prepare` reports a replacement.**
- When a request was already pending, the response adds `replaced_request_id`, plus a fixed `notice`: "An earlier prompt (request …) was pending and is no longer valid. Show the user this prompt instead."
- The single slot stays (decision 3). A replaced id goes into a bounded per-session list (8 entries, like `MAX_VALIDATIONS_PER_SESSION`), only so step 4 can name `request_superseded`.
- A refused prepare (§3.2) never touches the pending request.

**Wording:**
- `gauss_execution_decide`'s docstring (the tool description) names `request_id`;
- the server `instructions` (`:252-261`) change "pass the user's own yes/no to gauss_execution_decide" to "… together with that prompt's request_id";
- `docs/mcp-server.md` (lines 37, 52) is updated to match.

**The CLI chat path is unchanged.** `gauss_ai_chat` prompts the human directly in the terminal, so there is no client in between.

### 3.2 A refused prepare does not spend its id (item 2)

`gauss_execution_prepare`'s order becomes:
1. session;
2. **the opt-in gate** (runner `gauss` without the opt-in → `real_gauss_not_allowed`), before any id is looked up;
3. `session.validated.get(validation_id)`: a **lookup, not a pop** (`unknown_or_used_validation_id` when absent);
4. re-validation (`validation_stale`);
5. request creation (`request_rejected`);
6. **only now, `pop` the id**, record the pending request (§3.1) and return the prompt.

The rule becomes: **an id is spent only by a prepare that returns a prompt** (decision 4). A refused id can be resubmitted and gets the same refusal again. It ages out under the existing 8-id cap. The chat path (no `validation_id`) is unaffected.

### 3.3 `gauss_session_start` reports the opt-in (item 3)

The response adds:
- `real_gauss_allowed`: `true`/`false`, exactly `_real_gauss_allowed()`, whatever the runner;
- `execution_hint`, only when `runner == "gauss"` and the flag is false: the same text as the prepare refusal.

The tool description says that the flag reflects the server operator's opt-in only, and that whether the executable launches is known only from a run (§2.3). No new capability: the server already computes the flag.

### 3.4 The prompt says where code runs (item 4)

**Fix the line, not the behavior** (decision 6):
- `render_execution_handoff_prompt` no longer prints `Workspace parent`. In its place it prints a fixed line: `Runs in: a new temporary directory, deleted after the run`.
- Both callers stop passing `workspace_parent` into `create_execution_handoff_request` (`gauss_mcp_server.py:418`, `gauss_ai_chat.py:253`), so the digest no longer binds a value that the user is not shown and the run does not use.
- The dataclass field and `_DIGEST_FIELD_ORDER` stay as they are, so the digest's structure and `test_gauss_execution_handoff`'s per-field mutation tests are unchanged. A request built with `workspace_parent=None` already digests exactly that way today.
- The session keeps `workspace_parent`; guided repair still uses it.

This is the only change in `gauss_execution_handoff.py`, and it affects one function (§6.4). `docs/controlled-execution-handoff.md`'s prompt description is checked and updated if it quotes the line.

### 3.5 A literal-divisor check for `/` (item 5)

**A new function, `check_operator_preconditions(code)`**, in `gauss_pre_execution_validation.py`, returning `PreconditionCheck`s. `validate_generated_code` adds one line beside the existing loop (`gauss_conversation_engine.py:1772`): `precondition_checks.extend(validation_mod.check_operator_preconditions(cleaned_block))`. Results flow through the existing violated/unverified handling (`:3524`, `:4280`, `:4370`), unchanged.

**Finding `/`:**
- it reads `lex_gauss_source(code).masked_view`, so `/` inside a string or comment is never seen;
- it skips `./` (a `.` immediately before `/`).

**The divisor** is the operand immediately right of `/`. It must be a whole operand, from dv15, dv16 and dv19:
- a `{…}` literal, or a name with an optional trailing `'`;
- followed by a boundary that binds after `/`: `;`, `)`, `,`, `]`, `+`, `-`, `*`, `/`, `~`, `|`, a relational or word operator, or the end.

A transposed name has its rows transposed. Anything else (`^`, `[`, `(`, a member `.`, a call, a parenthesized operand) is an expression, and gets no check (§5).

A name is resolved by the existing tracer, `_find_literal_matrix_for_argument` (`:1677`), at the `/` position: the most recent plain top-level assignment, refused on any other write. A divisor larger than `MAX_CHECKED_MATRIX_DIM` (6) is treated like a runtime value.

**The dividend** is the operand immediately left of `/`, when it is a whole operand (a name or a number preceded by `=`, `(`, `,`, `+`, `-`, `~`, `|` or the statement start):
- a number, or a name traced to a 1×1 literal: **scalar**;
- a name traced to a larger literal: **matrix**;
- anything else (a call such as `eye(2)`, a product, an untraced name): **unknown**.

**The divisor's classification** (exact, reusing `_determinant`):

| Divisor | Class | Evidence |
|---|---|---|
| 1×1 | scalar | dv05 |
| square, \|det\| ≤ `_SINGULAR_DETERMINANT_TOLERANCE` | fails (`G0048`) | dv02, dv03, dv12, dv19, dv22, dv23 |
| square, nonsingular | solves | dv01, dv16, dv24 |
| tall (M > K), \|det(X'X)\| ≤ tolerance | fails (`G0121`) | dv06, dv20, dv32 |
| tall, full rank | solves (least squares) | dv07 |
| wide (M < K) | fails (`G0121`) | dv08 |

**The result:**

| Divisor | Dividend scalar | Dividend matrix | Dividend unknown |
|---|---|---|---|
| runtime / expression / too large | no check | no check | no check |
| scalar | no check | no check | no check |
| solves | no check | **satisfied** | no check |
| fails | no check (element-wise: dv04, dv25) | **violated** → not_ready | **unverified** → review_required (decision 7) |

- The unverified explanation says: if the dividend is a matrix, GAUSS fails (`G0048`/`G0121`); if it is a scalar, GAUSS divides element-wise (dv26: `eye(1) / a`).
- The precondition is a `DocumentedPrecondition(symbol="/", source="user-guide/fundamentals/operators.rst; matrix-division.rst", machine_checkable=True)`. Its description quotes `operators.rst`'s equivalence with `inv`, records that GAUSS 26.1.4 fails rank-deficient divisors with `G0121` contrary to the QR remark, and cites the dv IDs.
- It lives in a new constant `_OPERATOR_PRECONDITIONS = {"/": …}`, not in the call-keyed `_PRECONDITION_INDEX`. So `documented_preconditions(...)` and `_PRECONDITION_CHECKERS` are unchanged.

**Runtime divisors are not checked, and this is disclosed** (decision 7, §5). This includes the finding's own 77.17 S19 (`eye(k) / xx`), which stays handoff_candidate, unlike `inv(xx)` (review_required). Giving every `/` with a runtime divisor the `inv` treatment would mark 496 docs occurrences unverified, including every `s / n`-style scalar division, because the validator cannot tell a scalar from a matrix.

### 3.6 An `eigh`/`eighv` symmetry precondition (item 6)

- **Two entries**, `_PRECONDITION_INDEX["eigh"]` and `["eighv"]` (decision 9):
  - each description quotes its page's Purpose sentence and type;
  - each records the lower-triangle behavior (eg01, eg02, eg05, eg08) and the `G0150` (eg07).
- **One checker, `check_symmetric_eigen_precondition`**, registered for both in `_PRECONDITION_CHECKERS`:
  - it uses the shared `_literal_matrix_for_precondition_argument`, then `_is_square` and `_is_symmetric`, the same functions `check_invpd_precondition` uses;
  - `check_invpd_precondition` itself is not touched.
- **Results:**
  - not square → violated (eg07);
  - not symmetric → violated, with a message saying that `eigh` reads only the lower triangle and would return the eigenvalues of a different matrix (eg01/eg06);
  - otherwise satisfied.
- **A runtime input is unverified**, exactly as for `invpd` (decision 8). `eigh(vcx(x))` therefore becomes review_required.
- A literal `x'` passes the tracer as today, and symmetry is unaffected by a transpose (eg10).

## 5. Known limitations this design accepts

- **The binding is client-mediated.** The server checks that the client names the pending prompt's `request_id`. It cannot check that the user saw that prompt, or that the client relays the reply faithfully. This is unchanged from today, but the server no longer runs a different request than the one the client names.
- **Only one request is pending per session.** A superseded prompt cannot be approved; the client must prepare again.
- **A client that never learns the parameter cannot run code.** Its `decide` calls fail with `request_id_required` until it passes the id, and the error explains how.
- **A refused `validation_id` lingers until evicted** (8 per session). A stale one keeps failing on resubmission, since re-validation is deterministic.
- **`real_gauss_allowed: true` does not mean the executable launches** (§2.3).
- **`/` is checked only for a literal divisor:**
  - a runtime divisor (77.17 S19, 74.5) is never checked, unlike `inv(x)`;
  - with an unknown dividend (`eye(2) / a`), a failing literal divisor is review_required, not not_ready, because a scalar dividend would divide element-wise (dv26);
  - parenthesized (dv27) and indexed (dv28) divisors are not checked;
  - row conformability (`G0036`) is not checked.
- **`trap 1` is not modelled** (dv13, dv14). Under it, a singular `/` or `inv` returns a missing value silently. This was already true for `inv`.
- **The singularity bound is an absolute 1e-9 on the determinant**, so `inv` and `/` report a violation for literal matrices that GAUSS inverts (dv10, dv11; decision 11).
- **`eigh(<runtime value>)` becomes review_required**, including `eigh(x'x)`, which is always symmetric, because expressions are never evaluated.
- **All behavior is from GAUSS 26.1.4 spot checks.** The docs describe `/` as a QR least-squares solve, which dv06/dv20/dv32 contradict.

## 8. Decisions needed

1. **Bind on `request_id`, not the digest.** *Recommend `request_id`.* It is unique per prepare and already returned. The digest is equal for two prepares of identical code and settings (by design, `request_id` is excluded from it), so it cannot tell two prompts apart. `decide` echoes both, so the client can show the user that the digest matches the prompt.
2. **How required is `request_id`?**
   - (a) optional in the schema, enforced by the server (`request_id_required`);
   - (b) required in the schema;
   - (c) optional, falling back to the last prepared request.

   *Recommend (a).* (b) gives a client with a stale description a generic validation error instead of an explanation (KL 70.x). (c) leaves the binding opt-in, which does not fix the finding. (a) is a breaking change for any client that omits the id. The only clients are local MCP clients of this private alpha, and the error says exactly what to do.
3. **A prepare while a request is pending: replace and report** (`replaced_request_id`, `notice`; the old id becomes `request_superseded`), rather than refuse, or keep several pending requests. *Recommend replace and report.* Refusing could strand a session whose user never answers. Several pending prompts widen the consent surface for no live need. After this change, CLAUDE.md's "must not prepare a second request while the user is still answering" rule can be relaxed to a recommendation.
4. **A refused prepare never spends its id, including `validation_stale`.** *Recommend yes (one rule: spent only by a prepare that returns a prompt).* The alternative, retiring stale ids with an explicit `validation_id_retired: true`, is also honest, but it adds a second rule for no safety gain, since re-validation runs on every prepare.
5. **`gauss_session_start` reports `real_gauss_allowed` for every runner, plus `execution_hint` when runner `gauss` lacks it.** *Recommend yes.* It is categorical, already computed, and adds no capability. The 78.x setup still confirms it with one prepare.
6. **Fix the "Workspace parent" line, not the behavior.** Remove the line, print a fixed `Runs in` line, and stop passing `workspace_parent` into handoff requests, so the digest binds only what is shown. *Recommend yes.* Running in `workspace_parent` would contradict the v0.78 design (ephemeral, never the user's directory), would change the execution core, and would leave or delete files in the user's (OneDrive-synced) workspace. Keeping the value digest-bound but hidden would bind something the user cannot see.
7. **`/`: a literal-divisor check, with runtime divisors disclosed** (§3.5).
   - (a) as designed: violated for a known matrix dividend, unverified for an unknown dividend, no check for runtime divisors;
   - (b) also treat every non-scalar-literal runtime divisor as unverified, for parity with `inv(x)`;
   - (c) disclosure only.

   *Recommend (a).* (b) would mark 496 docs occurrences unverified and cap every `s / n` mean, because scalars and matrices cannot be told apart. In the 406 snippets it moves 74.5 and S19 to review_required. (c) leaves P2's literal singular solve offered for execution.
8. **`eigh` with a runtime input: unverified (review_required), as for `invpd`.** The alternative is a literal-only check, which emits nothing for a runtime input. *Recommend unverified.*
   - It is the registry's existing rule.
   - The failure is silent (eg01 vs eg06), the case the registry exists for.
   - The measured reach is 3 docs blocks and 0 snippets.

   The cost is that `eigh(x'x)`-style code becomes review_required (§5).
9. **Include `eighv`.** *Recommend yes.* It has the same Purpose sentence and the same lower-triangle behavior (eg05).
10. **Severity of a non-symmetric `eigh` literal: violated (not_ready).** The alternative is unverified with an explanation. *Recommend violated.* GAUSS returns another matrix's eigenvalues without any error (eg01/eg06), the same class as `invpd`'s documented silent case, which the registry already treats as violated.
11. **The singularity bound (dv10/dv11): disclose, do not change.** *Recommend disclose in `KNOWN_LIMITATIONS.md`.* It is a pre-existing false not_ready (safe direction). GAUSS's threshold is not documented (dv29 fails at 1e-17, dv10 runs at 1e-10). A fix needs its own sweep and would move `inv` verdicts this milestone holds fixed. `/` reuses the same bound, so the two spellings agree.
12. **Renumber the search draft to v0.88.0.** Rename `planning/v0.87-search-and-grounding-recall.md` to `planning/v0.88-search-and-grounding-recall.md`, retitle it, renumber its §7 "Live evaluation 76.x" to the next free category at the time (79.x if 78.x is used here), and update `PROJECT_STATUS.md`'s references. *Recommend yes,* done when this plan is approved, as its own small change. It was not renamed in this session.
13. **After implementation, update CLAUDE.md:** remove the "until 77.x finding 2 is fixed" bullet and state the new `decide` contract, and add `real_gauss_allowed` to the opt-in check. *Recommend yes,* in the same release commit sequence.

1. **A client can keep several prompts open by using one session per prompt, so the replacement path never ran live (78.4, 78.5). Observation, consent clarity; safe direction; v0.87.0 design.**

But when several prompts are open, which prompt a bare "yes" answers is decided by the client alone. This client announced its mapping before each reply ("I'll treat your next yes or no as the answer to C"). `replaced_request_id`/`request_superseded` were never triggered live; B1 confirms them over the real transport.
   - **KL relation:** v0.87.0's entry says "only one request is pending per session". It doesn't say that sessions multiply that.

3. **The `eigh` runtime precondition holds back correct, common code (78.10). Observation; the disclosed cost of decision 8.** `eigh(vcx(x))` is always symmetric, but it is review_required and runs only outside the handoff. The validator now steers toward `eig` (P5 is a candidate), which gives the same eigenvalues for symmetric input but, unlike `eigh`, is not guaranteed to return them sorted or real. The client offered `eig` without using it. Reconsider if this recurs.
4. **The no-documented-call rule was met by an incidental call (78.12). Observation; pre-existing (v0.80.0 policy).** `ones(2, 2) ./ A` is a candidate because `ones` is documented, though nothing about the computation is checked. The client said so. The rule asks for documentation evidence; an incidental call supplies evidence about itself only. Not a safety issue: the code still needs the user's approval, and computes in memory.
