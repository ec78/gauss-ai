# v0.59.0 - Source Identity and Repair Draft Foundation

## Release Goal

Implement Phase 1 of `planning/v0.58.0-repair-application-safety-design.md`: immutable source-identity models, an immutable `RepairDraft` model, and deterministic structural validation — data only. This milestone does not generate a patch, edit a file, or apply a repair.

## Repository State Verified

Starting commit `8554ee2` (`v0.58.0`, tagged, pushed, released). Clean working tree. `scripts/gauss_repair_planner.py` and `scripts/gauss_repair_approval.py` unmodified throughout this milestone — confirmed by `git diff --stat` showing zero lines against either file at ship time.

## Architecture

```
RepairPlan (gauss_repair_planner.py, v0.56.0)
    -> repair_plan_digest(plan) -> str      (unchanged)
    -> [approval, gauss_repair_approval.py, v0.57.0 -- unrelated to this module]

SourceArtifact + SourceIdentity + EditScope
    -> RepairDraft (this milestone, gauss_repair_draft.py)
    -> repair_draft_digest(draft) -> str
    -> validate_repair_draft(draft, current_source_identity=None) -> DraftValidationResult
```

`scripts/gauss_repair_draft.py` imports nothing from `gauss_repair_planner.py` or `gauss_repair_approval.py` — a `RepairDraft` references `repair_plan_digest` as a plain string field, never a `RepairPlan` object. This keeps the new layer fully decoupled, mirroring how `gauss_repair_approval.py` itself stays decoupled from execution/workspace modules.

## SourceIdentity Model

Two classes, deliberately kept separate:

- **`SourceArtifact`** — a stable "which file" reference: `workspace_id`, `relative_path`, `file_type`. Independent of content; two artifacts with equal fields name the same file regardless of what it currently contains.
- **`SourceIdentity`** — a content-bound snapshot: `artifact: SourceArtifact`, `content_hash`, `size`, `encoding`, optional `line_range`, optional `observed_at`. This is "this file, in exactly this state" — the actual thing a draft binds to.

The split (rather than one merged class) is what makes hash-mismatch and workspace-mismatch independently testable: two `SourceIdentity` instances can share an artifact while differing only in `content_hash`, or share a hash while differing only in artifact. Both are exercised directly by dedicated tests (`test_16_hash_mismatch_fails_validation`, `test_17_workspace_mismatch_fails_validation`, `test_18_path_mismatch_fails_validation`).

Both classes are frozen dataclasses; equality and hashing are Python's automatic dataclass behavior, requiring no custom `__eq__`/`__hash__` — "identity equality should be deterministic" is satisfied by the language itself, not by bespoke logic (`test_01`/`test_02` confirm this directly).

**Zero I/O.** Every hash, size, and timestamp is caller-supplied. This mirrors two existing conventions exactly: `gauss_workspace.ManifestFileEntry.checksum`/`.size` are "caller-asserted, never computed here," and `gauss_repair_approval.ApprovalRecord.recorded_at` is a "caller-supplied clock value, never computed internally." No third convention was invented.

`SourceSnapshot`, named as a candidate concept in the authorizing prompt, was not implemented as a separate class — `SourceIdentity` already *is* the snapshot concept (an artifact plus a specific content state). Introducing a third, largely redundant class would have added indirection without adding a distinction Phase 1 actually needs; this consolidation is a deliberate scope decision, not an oversight.

## RepairDraft Model

```
RepairDraft
  repair_draft_id            opaque, caller-supplied, EXCLUDED from the digest
  repair_plan_digest         plain string; no RepairPlan import anywhere in this module
  source_identity: SourceIdentity
  edit_scope: EditScope
  proposed_change_description
  assumptions / risks / verification_steps    fixed, generic (no drafting intelligence exists)
  generated_at / generated_by
  approval_required           always True via the sanctioned constructor
  safe_to_prepare_draft        always False
  safe_to_apply                   always False
  draft_boundary
```

`EditScope` (`line_start`, `line_end`, `intended_operation`, optional `target_procedure`/`target_symbol`) represents only location and a short description of intent — never a unified diff, patch, replacement text, or generated code. The `no_generated_code` validation check actively guards this (rejecting `;`/`" = "`-shaped content), rather than relying on authors to remember the rule.

`build_repair_draft(...)` is the sanctioned constructor: it fills in the fixed generic `assumptions`/`risks`/`verification_steps`/`draft_boundary` and hardcodes `approval_required=True`, `safe_to_prepare_draft=False`, `safe_to_apply=False`. Direct `RepairDraft(...)` construction remains available (used by tests that deliberately want a differently-shaped draft, e.g. a blank description) — the same relationship `gauss_repair_planner.plan_repair(...)` has to direct `RepairPlan(...)` construction.

**Why `safe_to_prepare_draft` stays `False` on a `RepairDraft` object, even though a draft now exists:** the field's meaning is "is there a safe, implemented mechanism downstream of this object to act further" — not "does this object itself exist." No drafting-refinement or application mechanism exists downstream of a `RepairDraft` in this milestone, so the answer stays `False`, exactly as it stayed `False` on every `RepairPlan` before any drafting mechanism existed at all. The flag tracks capability, not object existence.

## Digest Model

`repair_draft_digest(draft) -> str` and `source_identity_digest(identity) -> str` both follow the exact convention `gauss_repair_planner.repair_plan_digest` established: a canonical dict over every field in fixed order, `json.dumps(..., sort_keys=False, ensure_ascii=True, separators=(",", ":"))`, then SHA-256.

**`repair_draft_id` is deliberately excluded** from `repair_draft_digest`'s canonicalization. The digest represents content identity, not instance identity — mirroring how `repair_plan_digest` has no plan-instance ID to exclude in the first place, because `RepairPlan` never had one. `test_11_draft_id_excluded_from_digest` proves this directly: two drafts built with different `repair_draft_id` values but otherwise identical content produce the same digest, while remaining distinguishable by their own ID field.

**Neither digest is stored as a field on the object it identifies**, despite the authorizing prompt's own suggested field list naming `draft_digest` as a `RepairDraft` field. This is a deliberate deviation, made for the same reason `RepairPlan` itself has no `plan_digest` field: storing the digest on the object would create a self-reference (the digest would need to be computed before the object exists, then passed into its own constructor, with special-casing to exclude itself from its own canonicalization). Keeping the digest external, computed on demand from a fully-constructed object, avoids that whole class of bug entirely and keeps `RepairDraft` consistent with the one existing precedent in this codebase for exactly this kind of object.

## Validation Model

`validate_repair_draft(draft, current_source_identity=None) -> DraftValidationResult` is pure, deterministic, and performs no I/O. Ten checks:

| Check | Semantics |
|---|---|
| `workspace_match` | If a current identity is supplied, its workspace/path match the draft's bound identity; trivially passes (with an explicit "skipped" detail) when no current identity is supplied |
| `hash_match` | Same comparison for content hash — the core stale-source signal from the v0.58.0 design's Section 7, modeled here without any I/O: the caller is responsible for freshly re-reading and re-hashing a real file through an authorized path and supplying the result |
| `valid_utf8_encoding` | Declared encoding is exactly `"utf-8"` |
| `valid_range` | Line range is well-formed, closed, and positive (1-based) |
| `bounded_scope` | Range does not exceed `MAX_EDIT_RANGE_LINES` (200) — a concrete numeric cap implementing the v0.58.0 threat table's own "a future implementation should also cap total changed lines" recommendation (Section 21, "large patch abuse") early, at the validation layer |
| `single_file` | Structurally guaranteed (the data model has no way to name more than one file); the check documents this guarantee rather than testing nothing |
| `immutable_identity` | The bound `SourceIdentity` is verified, via `dataclasses.is_dataclass`/`__dataclass_params__.frozen`, to actually be a frozen dataclass instance |
| `deterministic_digest` | The draft's digest is recomputed twice and compared |
| `reversible_representation` | A bounded range and a non-empty description together exist — the minimum structural precondition a future reversible-application step would need; true reversibility (recording original text) is out of scope for this foundation milestone, which never reads any file |
| `no_generated_code` | Neither the description nor the intended operation contains code-shaped tokens |

**Validation proves structural safety only.** It never proves the intended operation is a correct GAUSS fix, and it never proves a draft is safe to apply — consistent with `docs/gauss-repair-planning.md`'s own long-standing distinction between structural validation and correctness.

## CLI Changes

Two new commands: `repair-draft` (constructs a new draft from explicit flags — `--path`, `--content-hash`, `--size`, `--line-start`, `--line-end`, `--operation`, `--description`, and optional `--workspace-id`/`--encoding`/`--procedure`/`--symbol`) and `show-repair-draft` (re-displays `last_repair_draft` without recomputing anything). `repair-draft` requires an existing repair plan (`run 'repair-plan' first`); `--workspace-id` defaults only to the adapter's own already-established active workspace, never to anything inferred. Both commands render every field, the validation result, and five explicit disclosure lines. `reset` clears `last_repair_draft` alongside `last_repair_plan` and the approval store. Adapter version string bumped to `v0.59.0 alpha`.

## Safety Guarantees

- Zero I/O anywhere in `gauss_repair_draft.py` — checked structurally (`test_39_no_filesystem_mutation_in_module_source` greps the module's own source for `open(`/`write_text(`/`read_text(`/`os.remove`/`os.replace`/`shutil.`).
- No import of any execution/workspace/orchestration/session/state-store/repair-planner/repair-approval module, `subprocess`, `socket`, or `urllib` (`test_40_no_forbidden_imports`).
- `safe_to_apply`/`safe_to_prepare_draft` are `False` on every draft the sanctioned constructor produces, across every scenario the test suite exercises (`test_35`, `test_36`).
- No edit-content representation exists anywhere in the model — validated both structurally (the data model has no such field) and behaviorally (the `no_generated_code` check).
- The CLI never calls `execute`/`plan`/`confirm`, never mutates workspace state (`test_81_repair_draft_does_not_mutate_workspace_or_filesystem` diffs the real workspace directory tree before/after), and never adds an approval record (`test_83`).

## Recommendation for v0.60.0

This milestone's own authorizing task collapsed the `v0.58.0` design's Phase 1 ("source identity and draft model") and Phase 2 ("deterministic draft validation") into one implementation pass — both are delivered here (`RepairDraft`/`SourceIdentity` plus `validate_repair_draft`). The natural next increment is therefore the design's **Phase 3: a draft-review and approval workflow**, mirroring `gauss_repair_approval.py`'s own conflict/revoke discipline but keyed by `repair_draft_digest` instead of `repair_plan_digest`. This is the smallest coherent next step: it requires no new I/O (drafts are already fully constructed, in-memory objects, exactly like plans were when `v0.57.0` built approval for them), and it is the next unimplemented phase in the design document's own dependency order. Phase 4 (the local single-file application prototype) should not be attempted until draft approval exists, since the application gate depends on it.
