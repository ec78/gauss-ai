# v0.66.0 — Repair Session Summary

## Position in the reasoning pipeline

```
Execution -> Interpretation -> Diagnosis -> Repair Plan -> Strategy Approval
    -> Repair Draft -> Draft Approval -> Application Approval
    -> (Application Gate -- checked separately, not composed here)
    -> Repair Application -> Verification Execution -> Comparison
    -> Verification Review
    -> Repair Session Summary (this module, v0.66.0)
```

The summary sits strictly downstream of every other layer and is read by nothing. No module in this repository will import `gauss_repair_session_summary.py` except the CLI.

## Objective

A read-only composition of evidence already produced by every prior milestone. It introduces no new workflow, no new approval, no new repair capability, no execution, no planning, no rerun, no rollback, no persistence, no durable session, and no mutation of anything. It owns none of the objects it displays — it only holds references to them and presents them together, in one place, for a human to read.

## Why this module imports so much

Every other layer added since `v0.56.0` has followed a strict, minimal-dependency rule: a layer imports only the one layer immediately below it (draft approval imports draft; application approval imports draft; verification imports application; review imports verification). `gauss_repair_session_summary.py` deliberately breaks that pattern, and this is a conscious, singular exception: its entire purpose is composition *across* the full pipeline, so it needs type visibility into every stage that can appear in a session. It imports:

- `gauss_code_assistant_workflow` (`WorkflowResult`, for the original execution)
- `gauss_execution_interpreter` (`ExecutionInterpretation`)
- `gauss_execution_diagnostics` (`DiagnosticAssessment`)
- `gauss_repair_planner` (`RepairPlan`)
- `gauss_repair_approval` (`ApprovalRecord`, strategy-level)
- `gauss_repair_draft` (`RepairDraft`)
- `gauss_repair_draft_approval` (`DraftApprovalRecord`)
- `gauss_repair_application_approval` (`ApplicationApprovalRecord`)
- `gauss_repair_application` (`ApplicationResult`)
- `gauss_verification_execution` (`VerificationExecutionRequest`, `ComparisonSummary`)
- `gauss_verification_review` (`VerificationReview`)

Despite the wide import surface, the module contains **zero logic beyond composition**: no I/O, no clock access beyond a caller-supplied `generated_at`, no hashing, no re-derivation of any field already present on the objects it references, and no code path capable of constructing, mutating, or reconstructing any of the imported types itself (it only ever receives already-built instances as parameters).

## What is deliberately excluded

**The Application Gate is not part of the summary.** `evaluate_application_gate(...)` requires a freshly-supplied current source identity and workspace status — a genuine, external freshness check, not a cached record. Fabricating a gate result inside a read-only summary (or silently re-reading the file to produce one) would be new capability this milestone does not authorize. The summary is honest about this: it composes only objects that already exist as evidence, and gate freshness is not evidence, it is a live precondition check the tester must still run explicitly via `check-repair-application-gate`.

## Model

```python
@dataclass(frozen=True)
class TimelineEntry:
    stage: str
    timestamp: str
    description: str

@dataclass(frozen=True)
class RepairSessionSummary:
    original_execution: "mvp.WorkflowResult | None"
    interpretation: "interpreter_mod.ExecutionInterpretation | None"
    diagnosis: "diagnostics_mod.DiagnosticAssessment | None"
    repair_plan: "repair_planner_mod.RepairPlan | None"
    strategy_approval: "repair_approval_mod.ApprovalRecord | None"
    repair_draft: "repair_draft_mod.RepairDraft | None"
    draft_approval: "draft_approval_mod.DraftApprovalRecord | None"
    application_approval: "application_approval_mod.ApplicationApprovalRecord | None"
    application_result: "application_mod.ApplicationResult | None"
    verification_request: "verification_mod.VerificationExecutionRequest | None"
    comparison_summary: "verification_mod.ComparisonSummary | None"
    verification_review: "review_mod.VerificationReview | None"
    timeline: tuple[TimelineEntry, ...]
    current_status: str
    generated_at: str
    boundary: str
```

Every reference field is `Optional` and holds the *exact same object* the caller passed in — never a copy, never a re-derived value. `test_*_summary_holds_the_exact_same_object_not_a_copy` proves this with `is`, not `==`, for every populated field.

### Timeline

Built in **fixed pipeline order**, not sorted by timestamp value. Only stages whose object both exists and carries a genuine timestamp field contribute an entry: strategy approval (`recorded_at`), repair draft (`generated_at`), draft approval (`recorded_at`), application approval (`recorded_at`), application result (`applied_at`), verification request (`created_at`), verification review (`reviewed_at`). Execution, interpretation, diagnosis, and the repair plan carry no timestamp anywhere in this architecture — an existing, honest limitation this milestone does not invent and cannot fix by fabricating one. Timestamps are opaque, caller-supplied strings (frequently identical across stages under a fixed test clock); sorting by parsed value would be unstable and could misorder same-timestamp entries, so pipeline order is used unconditionally instead.

### Current status

A single string naming the furthest stage actually reached, computed by walking the pipeline from its end backward and returning the first populated stage found (`verification_reviewed`, `verification_completed`, `verification_requested`, `applied`/`application_blocked`/`application_failed`, `application_approved`/`application_declined`, `draft_approved`/`draft_declined`, `draft_created`, `strategy_approved`/`strategy_declined`, `planned`, `diagnosed`, `interpreted`, `executed`, or `no_execution`). Pure, deterministic, and reused nowhere else.

### Boundary

A fixed, always-present disclosure, matching this repository's convention:

```
This is a read-only summary of evidence already produced by prior stages. It creates no new
approval, executes nothing, plans nothing, repairs nothing, and mutates no prior state. Any
missing stage below reflects that stage genuinely has not occurred in this session.
```

## `build_repair_session_summary(...)`

The single sanctioned constructor. Every domain parameter defaults to `None` (a session need not have reached every stage); `generated_at` is required and caller-supplied, matching every other layer's own clock-injection convention. Builds `timeline` and `current_status` internally via two small, pure, private helpers — no other public surface.

## CLI

One new command: `show-repair-session`. The adapter's `_show_repair_session()` method gathers whichever objects the current session already has (recomputing `interpretation`/`diagnosis`/`comparison_summary` the exact same way `_interpret()`/`_diagnose()`/`_current_comparison_summary()` already do — no new recomputation logic, pure reuse of existing methods), calls `build_repair_session_summary(...)`, and renders every section. No new adapter state is added beyond what already exists; `show-repair-session` reads, it never writes.

## Testing dimensions

Summary reflects existing objects (identity-checked, not equality-checked); missing stages handled honestly (every field independently omittable, no stage assumed present because an earlier or later one is); ordering correct (timeline is always in fixed pipeline order regardless of call-argument order or timestamp values); timeline correct (only genuinely-timestamped stages appear; a session with zero completed stages produces an empty timeline, not a fabricated one); CLI output (a full real session end-to-end, plus every partial-session state); immutability (frozen dataclass, structural no-verdict/no-mutation-method checks); regression (every prior module the summary reads has zero diff).

## Not implemented

No new approval, execution, planning, repair, rerun, rollback, persistence, durable session, or mutation of any kind. No consumer of the summary beyond the CLI's own display. No gate re-evaluation. No aggregation across multiple sessions — this summarizes exactly one adapter session's own current state.
