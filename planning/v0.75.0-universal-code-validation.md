# v0.75.0 — Validation Coverage & Universal Code Eligibility

## 1. Repository state

Starting commit: `a52e7a8` (`v0.74.0`, tagged, pushed, released). Branch: `main`. Working tree was clean at the start of this milestone. This document mirrors `planning/v0.74.0-pre-execution-validation.md`'s structure and the milestone brief's own required final-report sections.

## 2. v0.74.0 gap analysis (Phase 1 findings)

**The QA-intent eligibility gap** (disclosed but not fixed in `v0.74.0`, `KNOWN_LIMITATIONS.md`/Section 15 of the prior planning doc): `ConversationEngine.ask(...)` only computed `gate = compute_generation_gate(bundle)` for `Intent.CODE_GENERATION`; every other intent left `gate = None`, and the pre-execution validation call site required `gate is not None and gate.policy in (FULL, SUPPORTED_ONLY)`. A `QA`-classified turn whose answer happened to contain code-shaped GAUSS (confirmed possible since `v0.72.0`/`v0.73.0`'s own `check_generated_symbols(...)` was already deliberately made intent-independent for exactly this reason) therefore NEVER reached `_validate_pre_execution(...)` — `pre_execution_eligibility` stayed `None` regardless of what the code contained, purely because of how the question was phrased.

**Signature validation** (`gauss_pre_execution_validation.extract_documented_signature`) was argument-count-only — no parameter name/role/type/shape metadata was extracted at all, even though the real, local documentation checkout's own `.. function::` directive blocks carry a machine-parseable `:type <name>: <text>` line for exactly this purpose (confirmed by direct inspection of `meanc.rst`, `invinvpd.rst`, `solpd.rst`, and a corpus-wide `grep` across the real docs root turning up a consistent, small vocabulary: `scalar`, `string`, `struct`/`struct pointer`, `NxK matrix`, `Nx1 vector`, `dataframe`, etc.).

**Precondition coverage** was exactly one family (`invpd`); `inv` was curated but explicitly marked `machine_checkable=False` in `v0.74.0` because no deterministic invertibility test existed.

**Predicted-output claims** were not modeled at all. The exact `v0.74.0` finding (`evaluations/runs/2026-09-12-code-assistant-pre-execution-validation-run-004.md`): a real, valid, `ELIGIBLE_FOR_VALIDATION` `invpd({2 1, 1 2})` example whose model-claimed "expected output" (`0.5 -0.5 / -0.5 0.5`) was wrong (real inverse, confirmed via `tgauss.exe -b`: `0.66666667 -0.33333333 / -0.33333333 0.66666667`) — disclosed in prose in that run's own notes, but with no structural representation anywhere in `AnswerResult`.

## 3. Universal validation routing (Goal 1 / Phases 2-3)

`compute_generation_gate(bundle)` is now called unconditionally for every intent that reaches past the execution/repair early return (previously only for `CODE_GENERATION`). It is still used to block/clarify the provider call ONLY for `CODE_GENERATION` — for every other intent the provider is always called, exactly as before (prose-only QA is unaffected).

The pre-execution validation entry condition changed from `if generated_code and gate is not None and gate.policy in (FULL, SUPPORTED_ONLY):` to `if generated_code:` — the single, structural fix. `_validate_pre_execution(...)` remains the ONE call site (no duplicate validation path was introduced); it now also receives the full answer text (`answer_text=text`) so it can run the new predicted-output analysis.

An ungrounded (`BLOCK`) or ambiguous (`CLARIFY`) bundle that still produced code (a QA-route hallucination with no real evidence) is validated too, and correctly comes out `INELIGIBLE`/`REQUIRES_CLARIFICATION` via `compute_eligibility(...)`'s own pre-existing `generation_policy`/`ambiguous_topics` checks — nothing new was added to make this work; it was already latent in `compute_eligibility(...)`'s design, just never reached for these intents.

Five new regression tests (`test_gauss_conversation_engine.py`, `test_99`-`test_103`) prove: a QA-classified turn with a real, correct code example now gets `ELIGIBLE_FOR_VALIDATION`; a QA-classified turn with a hallucinated symbol now gets `INELIGIBLE` (previously: unvalidated); prose-only QA is unaffected (`pre_execution_eligibility` stays `None`); an explicit `CODE_GENERATION` request is validated exactly once, not twice; a follow-up QA turn reusing an earlier grounded topic is validated too. Two new end-to-end tests (`test_gauss_ai_chat.py`, `test_36`-`test_37`) prove the same through the full rendered chat loop.

## 4. Signature coverage (Goal 2 / Phases 4-6)

New `DocumentedParameter` (`name`, `required`, `position`, `category`, `shape`, `source`) and `classify_documented_type(type_text)` parse a real `:type <name>: <text>` line (from the same `.. function::` directive block already used for argument-count extraction) into a coarse category set (`SCALAR`/`VECTOR`/`MATRIX`/`STRING`/`CONTROL`/`DATASET`/`UNKNOWN`) and shape (`SQUARE`/`COLUMN_VECTOR`/`ROW_VECTOR`/`UNKNOWN`). A genuinely documented enumeration (real corpus text: `"a: matrix, vector, or scalar"`) produces a real multi-category allowed set, not an arbitrarily-picked first match.

`infer_literal_category(argument)` (Phase 6) classifies a GENERATED call's own literal argument text — a bare number (`SCALAR`), a quoted string (`STRING`), or a `{...}` literal (`VECTOR`/`MATRIX`, with shape). A runtime variable or any other expression is always `UNKNOWN` — never partially evaluated, never guessed.

`check_parameter_roles(call, signature=...)` compares these positionally, producing `MATCH`/`MISMATCH`/`UNKNOWN` per argument. `MISMATCH` now blocks eligibility (`compute_eligibility(...)` gained a `parameter_role_checks` parameter); `UNKNOWN` — from either side — never does.

**What remains argument-count-only**: any symbol documented in the older plain Format-heading style (no `.. function::` directive, hence no `:type` lines at all) still gets no parameter metadata — `extract_documented_signature(...)` correctly falls back to an empty `parameters` tuple rather than guessing. **What remains UNKNOWN**: every runtime variable, every non-literal expression, and every parameter whose own documented `:type` text matched none of the small, fixed keyword vocabulary.

## 5. Parameter-role/type validation

Implemented categories: the 7-value `TypeClass` enum above. Literal inference: numeric scalar, quoted string, and `{...}` literal (scalar/column-vector/row-vector/square-matrix/non-square-matrix, per real dimension counting — no evaluation of matrix contents beyond counting rows/columns). Mismatch handling: a `MISMATCH` is produced only when BOTH sides are confidently known and genuinely disjoint (e.g. a string literal where the documentation names only `matrix`) — this is deliberately conservative; an ambiguous or partially-unknown comparison always yields `UNKNOWN`, never a guessed `MISMATCH`. Limitations: positional only (no keyword-argument matching, since GAUSS call syntax here is positional); no dimension/conformability cross-checking between two different parameters of the same call.

## 6. Preconditions (Goal 3 / Phase 7)

`invpd` (unchanged from `v0.74.0`). `inv` upgraded from `machine_checkable=False` to `True`: for a literal matrix, squareness and a nonzero determinant (`_matrix_inverse(...)`'s own exact cofactor/adjugate computation, reusing `_determinant(...)`) are both deterministically checkable — `VIOLATED` for non-square or singular, `SATISFIED` otherwise, `UNVERIFIED` for a runtime value or an oversized literal (bound: `MAX_CHECKED_MATRIX_DIM = 6`, unchanged). Two genuinely new families, selected because the real local docs checkout supports a deterministic literal check and each is authoritatively documented: `solpd` (`solpd.rst`; the SECOND argument, `A`, must be positive definite; the function's own documented "looks only at the upper half of the matrix including the principal diagonal" convention is mirrored exactly — via a new `_reflect_upper_triangle_to_symmetric(...)` helper — rather than reusing `invpd`'s stricter literal-symmetry requirement, which `solpd` itself does not impose) and `chol` (`chol.rst`; identical upper-triangle-only convention, on its one argument). `DocumentedPrecondition` gained an `argument_index` field (default `0`) so `solpd`'s second-argument target is represented explicitly, not hardcoded past the existing single-argument assumption.

**UNVERIFIED behavior**: unchanged discipline — any non-literal argument, or a literal exceeding the bound, is `UNVERIFIED`, never guessed as `SATISFIED`. New regression tests (`test_27` through `test_27j`, `test_gauss_pre_execution_validation.py`) cover valid/invalid/oversized/runtime cases for all three new/upgraded checkers, including a dedicated test proving `solpd` does NOT require literal symmetry (a deliberately non-symmetric literal whose upper triangle is positive definite is correctly `SATISFIED`).

**Superseded test**: `test_27` (formerly asserting `inv`'s precondition is always `UNVERIFIED`) was updated with an inline comment explaining the supersession, per this repository's own testing-expectations rule — the old expectation was genuinely obsolete now that a real deterministic validator exists, not silently weakened.

## 7. Predicted output (Goal 4 / Phases 9-11)

New `PredictedOutputClaim` (`present`, `raw_text`, `parseable`, `verification_status`, `expected_value`, `computed_value`, `issues`) and `OutputVerificationStatus` (`NOT_PRESENT`/`VERIFIED`/`MISMATCH`/`UNVERIFIED`/`UNPARSEABLE`). Detection (`detect_predicted_output_claim`) is marker-based — a small, explicit phrase list (`"Expected output:"`, `"This should print:"`, `"The expected output is:"`, etc., matching both `CODE_GENERATION_SYSTEM_PROMPT_ADDENDUM`'s own instructed phrasing and the real live phrasing observed in `run-004.md`) — never a general "any sentence about output" detector.

Verification (`verify_predicted_output`) is bounded to four recognized call patterns applied to a literal matrix: `meanc`, `sumc`, `inv`, `invpd` (the last two reusing `_matrix_inverse(...)`, the same exact adjugate computation the upgraded `inv` precondition check uses). Comparison (`_values_close`) is on FLATTENED values only (orientation-agnostic, since a model may transpose how it writes a result) within a small relative tolerance. Anything else is `UNVERIFIED`; non-numeric claimed text is `UNPARSEABLE`.

**The exact `v0.74.0` wrong-output regression, reconstructed** (`test_66`, `test_gauss_pre_execution_validation.py`; end-to-end in `test_37`, `test_gauss_ai_chat.py`): `invpd({2 1, 1 2})` claimed-output `"0.5 -0.5 / -0.5 0.5"` now deterministically computes the real inverse (`0.6667, -0.3333, -0.3333, 0.6667`) and reports `MISMATCH` — never `VERIFIED`, and the code's own `ELIGIBLE_FOR_VALIDATION` status is completely unaffected by the mismatch (verified directly: `compute_eligibility(...)` takes no predicted-output argument at all, structurally, per `test_70`).

## 8. Live Ollama evaluation

**Model**: `qwen2.5-coder:7b`, same as `v0.71.0`-`v0.74.0`. **Environment**: the same real, locally running Ollama installation and real local GAUSS documentation checkout (2,063 files). **Scenario count**: ten (`65.1`-`65.10`), all Pass after fixes (scores 3.86-4.0), real transcripts in `evaluations/runs/2026-09-12-code-assistant-universal-code-validation-run-*.md`.

**The core objective was proven live, twice, independently**: `65.1` ("What does invpd do, and can you show a quick example?") and `65.10` (a multi-turn conversation starting with "What does meanc do?") both show a `QA`-classified turn's own code receiving a real `ELIGIBLE_FOR_VALIDATION` verdict — something `v0.74.0` structurally could not produce for any `QA`-classified turn.

**Three real defects were found live and fixed within the milestone**:

1. (`65.1`, `65.10`) The `v0.74.0` documentation-derived concept index scored a whole QUESTION's own keyword overlap against every indexed page and tied two-to-three unrelated pages purely because they shared ordinary English words ("can"/"you") in their own Purpose text — rare enough (14/2,105, 2/2,105 entries) that the existing document-frequency safety net never caught them. This bug existed in `v0.74.0` too, but was INERT for `QA`-classified turns before this milestone's own routing fix made `ambiguous_topics` consequential for every intent. **Fixed** by extending `_GENERIC_DOC_WORDS` (`gauss_doc_concept_index.py`) with a small, corpus-frequency-independent English pronoun/modal-auxiliary list. Regression: `test_09b_pronoun_and_auxiliary_verb_overlap_never_produces_false_ambiguity`.
2. (`65.9`, `65.10`) The new predicted-output-claim detector stopped capturing at the FIRST fenced code block it saw — which was frequently the OPENING of the model's own separate output fence (often preceded by markdown bold, `"**Expected output:**\n\`\`\`\n..."`), not plain text before one. **Fixed** by rewriting detection (`_extract_claim_text(...)`) to explicitly prefer a fence's own content when one immediately follows the marker. Regression: `test_67b`.
3. (`65.9`) A real model response labeled its numeric block with a leading text line (`"Inverted Matrix:"`) inside the same fence; the parser rejected the whole block as non-numeric. **Fixed** by skipping leading lines with zero digit characters as a label/header before parsing. Regression: `test_67c` (using the exact real, wrong claimed value from this live run).

All three fixes were followed by a full test-suite re-run (clean) and a live re-run of the affected scenario, per this milestone's own defect-handling protocol.

**The exact `v0.74.0` wrong-prediction finding was reconstructed and correctly detected** (`65.9`): across three live attempts, the real model predicted correctly twice (`VERIFIED` both times, after the fixes) and incorrectly once (`0.4/-0.2/...` vs. the real `0.6667/-0.3333/...`, confirmed `MISMATCH` via the dedicated regression test using this exact value — re-eliciting an identical wrong prediction from a non-deterministic model on a later run is not guaranteed). `pre_execution_eligibility` stayed `eligible_for_validation` throughout, unaffected by the predicted-output verdict either way.

**Signature/parameter-role failures**: `65.4` (incompatible argument count) and `65.5` (parameter-role mismatch) both found the live model naturally avoiding the deliberately-wrong request (the same real-model-avoidance pattern `v0.74.0`'s own `64.6` observed) — both paths were instead proven via a forced-response check against the REAL local docs-root (not a synthetic fixture), confirming `meanc`'s own real `:type x: NxK matrix` line drives a genuine `MISMATCH`/`INCOMPATIBLE` verdict end to end.

**Precondition failures**: `65.7` (`invpd`, unchanged from `v0.74.0`'s `64.5`); `65.8`'s invalid `chol` case did not reach `VIOLATED` live because the model's own literal used non-standard `;` row separators (a real, disclosed cross-language syntax quirk, also seen in `65.1`) — the checker correctly, conservatively reported `UNVERIFIED` rather than guessing; `VIOLATED` was independently confirmed by unit test and real GAUSS execution using the correctly-formed literal.

**Eligibility results**: `ELIGIBLE_FOR_VALIDATION` in `65.2`/`65.3`/`65.4`/`65.6`/`65.8a`/`65.9`/`65.10`(turns 2-3); `INELIGIBLE` in `65.7`; `REQUIRES_CLARIFICATION` only in the pre-fix `65.1`/`65.10` runs (the defect itself), never after the fix.

**False positives found and fixed live**: the two concept-index false-ambiguity cases and the two predicted-output detection gaps, all listed above.

**False negatives**: none confirmed — every case the model got wrong (the `65.9` wrong prediction) was caught; no violated precondition or incompatible signature was ever missed.

## 9. Real GAUSS validation

Seven examples were executed via `tgauss.exe -b` (GAUSS 26.1.4), specifically targeting the three new/upgraded precondition families:

| Example | Deterministic verdict | Real execution result |
|---|---|---|
| `inv({1 2, 2 4})` (singular) | `VIOLATED` (zero determinant) | Real error code `50` (`scalerr`), matching `invinvpd.rst`'s own documented `inv`/`trap 1` error-code table exactly |
| `invpd({2 1, 1 2})` | `SATISFIED` | Success — real inverse `0.66666667 -0.33333333 / -0.33333333 0.66666667` (used to confirm the `65.9` MISMATCH/VERIFIED detection against both a wrong and a right model claim) |
| `solpd({1,1}, {2 1, 1 2})` | `SATISFIED` | Success — `[0.33333333, 0.33333333]` |
| `solpd({1,1}, {-1 0, 0 -1})` | `VIOLATED` | Real error `G0121: Matrix not positive definite` |
| `solpd({1,1}, {2 1, 999 2})` (non-symmetric, upper-triangle-only) | `SATISFIED` (upper triangle only) | Success — **identical** result to the symmetric case above (`[0.33333333, 0.33333333]`), empirically confirming `solpd` genuinely ignores its lower triangle exactly as this module's own convention assumes |
| `chol({2 1, 1 2})` | `SATISFIED` | Success — correct upper-triangular factor |
| `chol({-1 0, 0 -1})` | `VIOLATED` | Real error `G0121: Matrix not positive definite` |

**Any eligible/satisfied example that failed?** No — every `SATISFIED` example executed successfully; every `VIOLATED` example failed with the exact real GAUSS error this module's own precondition descriptions predict. **Any mismatch between static validation and real behavior?** No — all seven examples converge exactly. This is the strongest evidence yet in this repository's history for the two new/upgraded precondition families: not just documentation-text agreement, but direct empirical confirmation, including the specific, non-obvious "upper-triangle-only" convention `solpd`/`chol` document.

## 10. Eligibility (Goal 5 / Phase 12)

`compute_eligibility(...)` gained one new input, `parameter_role_checks` (default `()`, so every pre-`v0.75.0` call site remains valid): a `MISMATCH` anywhere now adds an `INELIGIBLE` issue, exactly like an `INCOMPATIBLE` signature or a `VIOLATED` precondition already did. It deliberately does NOT gain a predicted-output input of any kind — verified structurally by `test_70` (no parameter name containing "output"/"predicted"). Every other rule is unchanged from `v0.74.0` (see that milestone's own Section 7).

**Phase 14 decision, made explicitly**: `ExecutionEligibility` remains a 3-state enum. A fourth "eligible with caveats" tier was considered and rejected — the new `ValidationCoverage` (Section 11, Phase 13) already gives a caller everything such a tier would have provided (which specific passes ran to completion vs. left gaps), without proliferating eligibility states. Documented in this module's own top-of-file docstring, not just here.

## 11. Validation coverage metadata (Phase 13)

New `ValidationCoverage` (`symbol_check`, `signature_check`, `parameter_role_check`, `precondition_check`, `predicted_output_check`), each `COMPLETE`/`PARTIAL`/`NOT_APPLICABLE`/`UNKNOWN`, computed by `compute_validation_coverage(...)` from the same evidence `_validate_pre_execution(...)` already produces. `symbol_check` is `COMPLETE` whenever code is present (that check has no partial state); the other four reflect how much of THIS turn's own evidence was actually resolved vs. left `UNKNOWN`/`UNVERIFIED`/absent. Rendered as one additional line in `render_validation_report(...)`, only when `coverage` is supplied.

## 14. Product impact

**Yes — the universal-validation gap is genuinely closed, with direct, observed live evidence, and the broadened evidence quality is real, not merely additive test coverage:**

- Two independent live scenarios (`65.1`, `65.10`) prove a `QA`-classified turn's own code now receives the identical eligibility verdict a `CODE_GENERATION` turn would get — the exact, specific gap `v0.74.0` disclosed and this milestone was chartered to close.
- The new signature/parameter-role layer is proven correct against REAL documentation (not just synthetic fixtures) via two forced-response checks (`65.4`, `65.5`), confirming `meanc.rst`'s own `:type x: NxK matrix` line drives a real `MISMATCH`/`INCOMPATIBLE` verdict end to end.
- The three new/upgraded precondition families (`inv`, `solpd`, `chol`) are not just documentation-text-verified but EMPIRICALLY confirmed against real GAUSS 26.1.4 across seven spot checks, all converging exactly — including the specific, non-obvious "ignores the lower triangle" convention `solpd`/`chol` document, which this milestone's own checker design predicted correctly before the empirical check was run.
- The predicted-output-claim model reconstructed the exact `v0.74.0` wrong-prediction finding and correctly discriminated a genuinely wrong live prediction from a genuinely correct one across three real attempts, never conflating either with execution evidence or with the code's own structural eligibility.
- A genuinely valuable second-order effect: universal routing didn't just add new capability, it also SURFACED a real, pre-existing `v0.74.0` defect (the concept-index false-ambiguity bug) that was previously invisible precisely because it could never affect a `QA`-classified turn. This is direct evidence that broadening validation coverage finds real problems, not just theoretical ones — exactly the kind of result that justifies continuing to broaden it in a future milestone.

## 15. Remaining limitations

- **Incomplete signature/parameter-role semantics**: only a `.. function::`-directive-style `:type` line is parsed; the older plain Format-heading style still gets argument-count-only checking. Parameter-role checking is positional and literal-only — any runtime variable is `UNKNOWN`, by design, never inferred.
- **Precondition coverage remains narrow in absolute terms**: four function families (`invpd`, `inv`, `solpd`, `chol`) out of GAUSS's full command surface, and only for literal-matrix arguments.
- **Predicted-output verification is limited to a handful of literal patterns** (`meanc`/`sumc`/`inv`/`invpd` on a literal matrix) — this milestone's own live evaluation also showed detection ITSELF (not just verification) needs continued hardening against real model output shapes (markdown-fenced blocks, labeled blocks); further shapes not yet observed live may still slip through to `UNVERIFIED`/`UNPARSEABLE` rather than being checked.
- **The documentation-derived concept index's false-ambiguity risk is mitigated, not eliminated** — this milestone fixed the SPECIFIC pronoun/auxiliary-word class found live; a different, not-yet-observed generic-word class could still produce a future false `CLARIFY`. `MIN_KEYWORD_OVERLAP = 2` remains a low bar for topically-empty shared words in general.
- **Runtime-dependent values are always `UNVERIFIED`/`UNKNOWN`, by design** — no module in this milestone evaluates a real GAUSS expression itself.
- **Model dependence remains real** — `qwen2.5-coder:7b` still occasionally uses non-standard syntax (the `;`-vs-`,` row-separator quirk observed twice live, `65.1`/`65.8`) and still sometimes predicts wrong numeric output (`65.9`) — this milestone makes both harder to act on undetected, not impossible to produce.
- **`docs-root` dependency, local hardware/Ollama dependence, no execution, no autonomous debugging, no file editing** — all unchanged from `v0.71.0`-`v0.74.0`.
- **Anthropic remains not live-network-tested**, unchanged.

## 16. Recommendation

The project is ready for **human alpha testing of universal code validation** — the exact, disclosed `v0.74.0` QA-intent eligibility gap is demonstrably closed, with direct live evidence on two independent scenarios, and the broadened validation evidence (signature/parameter-role, three precondition families, predicted-output claims) is proven correct against both real documentation and real GAUSS execution, not merely unit-tested in isolation. Three real, live-found defects were fixed within the milestone and are now covered by regression tests, following this repository's own established discipline.

The project is **not** ready for the next milestone, **controlled execution handoff**, per this repository's own explicit workflow rule and this milestone's own honest limitations (Section 15): precondition coverage remains narrow in absolute terms, signature/parameter-role checking is still positional-literal-only, and predicted-output detection itself needed two live-found fixes within this very milestone — direct evidence that even the DETECTION layer for new evidence types is not yet mature enough to treat as a settled foundation for execution eligibility. **Do not begin `v0.76` automatically** — a future milestone's scope should be a deliberate decision informed by this report and the real transcripts in `evaluations/runs/2026-09-12-code-assistant-universal-code-validation-run-*.md`.
