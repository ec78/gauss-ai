# v0.35.0 Real Execution Reliability and Output Verification — Planning

## Scope

`v0.35.0` broadens confidence in the real controller execution path `v0.34.0` established, by verifying — across several bounded, independently authorized real GAUSS invocations — that the path behaves reliably when used repeatedly with separate requests, and that it correctly handles output-file creation, expected-output declaration, and output-file metadata (never content). This milestone does not add new production capability; it adds evidence, tests, and narrow harness extensions.

**In scope:** a named-scenario extension to the real controller-path harness; up to five real GAUSS invocations covering repeated success, state isolation, contained output-file creation, missing-expected-output detection, and a real GAUSS runtime error; fake-based regression tests locking in the resulting evidence; a new evaluation category; documentation updates; a readiness review.

**Out of scope (explicit non-goals):** any user-facing or conversational wiring; any change to `scripts/gauss_code_execution.py` or `schemas/gauss_code_execution.schema.json`; script-path execution; cross-process, crash-safe, or concurrent exactly-once guarantees; cooperative cancellation; cross-platform or cross-version verification; any methodological-validity claim; reading output-file contents; automatic retry.

## Invocation Budget

Up to **5** real GAUSS invocations are authorized, one per named scenario above, each individually justified and recorded. Using fewer than five is acceptable if a scenario's objective is already met by an earlier one — but the five scenarios above are individually distinct in what they verify (repeated success, state isolation, output creation, missing output, runtime error), so the default expectation is that all five will be used unless a stop condition is hit. No automatic retry is authorized: if any single invocation fails to complete due to a harness/environment problem (not a GAUSS runtime error, which is itself a valid, expected outcome for the `runtime-error` scenario), the failure is recorded and the next scenario proceeds only after re-verifying preflight, not by silently re-attempting the same request.

## Containment Policy

Every real invocation uses its own freshly created, disposable working directory, confirmed empty immediately before use. The `output-created` scenario additionally uses an explicit `output_directory`, either the same working directory or a disposable subdirectory of it — never a path outside the approved working-directory tree. `gauss_execution_adapter.py`'s existing `_resolve_inside`-equivalent containment check (enforced inside `scripts/gauss_code_execution.py`, unmodified by this milestone) already blocks any `output_directory` that resolves outside `working_directory` — this milestone relies on that existing, previously-verified (`v0.29.0`) enforcement rather than re-implementing it. After every invocation, the working/output directory tree is listed and checked for exactly the expected file(s), and a process check confirms no lingering `tgauss`-named process.

## Expected-Output Policy

`expected_output_files` is declared per-request as a tuple of relative filenames the caller expects the script to produce. The controller's existing `_missing_expected_outputs(...)` (unmodified by this milestone) compares declared names against the `path` values in the helper's returned `output_files` metadata. A mismatch sets `FailureCategory.MISSING_EXPECTED_OUTPUT` on an otherwise-`EXECUTION_COMPLETED` result — execution success and expected-output verification are and remain two independently tracked outcomes, never conflated. This milestone reads only `output_files` metadata (`path`, `size_bytes`, `file_type`, `created_by_execution`, `notes`) — never file content — consistent with every prior milestone's boundary.

## Result Evidence to Retain

For each real invocation: scenario name; request ID; request hash; confirmation scope; session ID; full state-transition sequence; helper invocation ID; executable identity; environment summary; working directory; output directory (if any); start/end evidence; helper invocation status; execution status; runtime-error evidence (stdout/stderr); exit code (with the standing non-authoritative caveat); declared expected output files; discovered output-file metadata; missing expected outputs (if any); unexpected-file check result; final controller state; analysis status; report status. All of this is recorded in `planning/v0.35.0-implementation-report.md`.

## Stop Conditions

As specified in the authorizing task, verbatim in effect: environment/version mismatch; executable identity uncertain; GUI `gauss.exe` risk; helper/schema change appears necessary; script-path execution would need enabling; output containment cannot be guaranteed; output files appear outside approved directories; an unexpected file would be overwritten; output-file metadata cannot be distinguished from content; confirmation bypass/reuse; duplicate execution for one request; state leakage between instances; unexplained side effects; network/credentials/secrets/arbitrary execution needed; a malformed/ambiguous result; workflow/agent/system-prompt changes needed; budget exceedance. None of these were encountered during Stage 1 preflight (see the implementation report for the live-verified preflight record).

## Acceptance Criteria

- Up to 5 real invocations performed, each individually justified, none exceeding the budget, no automatic retry.
- Repeated successful executions demonstrated using separate requests, with structural evidence of state isolation (distinct request hashes, distinct invocation IDs, distinct adapter/controller instances, no result overwrite).
- Output-file creation verified inside approved containment, with accurate metadata and no content read.
- Missing expected-output detection verified, distinct from execution failure, with no fabricated metadata.
- Runtime-error classification verified stable and distinct from missing-output classification.
- Adapter and controller test suites pass in full, strengthened with fake-based regression coverage for every new scenario type.
- A new evaluation category (`36.x`) is added and passes.
- Documentation is updated consistently; readiness review completed.

## Non-Goals, Restated

This milestone does not: implement user-facing or conversational execution; modify the execution helper or its schema; enable script-path execution; establish cross-process, crash-safe, or concurrent exactly-once guarantees; implement cooperative cancellation; verify cross-platform or cross-version behavior; make any methodological-validity claim from any real result; read output-file contents; or claim production readiness.
