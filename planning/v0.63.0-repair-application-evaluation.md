## Defects Found and Fixed

Two genuine defects were discovered. Both are narrowly-scoped, evaluation-driven fixes — no capability was broadened, no rerun/rollback/durable-session logic was added.

### Defect 1: Empty or whitespace-only `replacement_text` silently deleted the edit range

**Found via:** Prompt 53.2's evaluation (empty replacement text).

**Behavior before the fix:** `replacement_text=""` (or whitespace-only) produced zero replacement lines when spliced into the file, which is indistinguishable from *deleting* the entire edit range — and the transaction applied this without any distinct signal, since the existing `CANDIDATE_NON_EMPTY` check only verified the *whole resulting file* wasn't blank, not that the *replacement itself* carried real content. This silently performed a line deletion, which this milestone's own absolute scope (and `v0.62.0`'s before it) explicitly excludes ("no deletes").

**Fix:** A new check, `REPLACEMENT_TEXT_NON_EMPTY`, blocks with reason `replacement_text_empty` whenever `replacement_text.strip()` is empty — evaluated immediately after backup creation, before candidate construction ever runs, so the deletion never happens. `scripts/test_gauss_repair_application.py` gained `test_28`, and `test_09` was updated to reflect the new, more specific blocking reason.

### Defect 2: An uncaught `UnicodeEncodeError` for non-UTF-8-encodable replacement text

**Found via:** Prompt 53.3's evaluation (malformed replacement text — a lone UTF-16 surrogate).

**Behavior before the fix:** `candidate_content.encode("utf-8")` was called with no exception handling. A `replacement_text` containing a lone surrogate (or any other content not representable in UTF-8) raised an uncaught `UnicodeEncodeError` straight out of `apply_repair(...)`, crashing the caller — a direct violation of this module's own fail-closed design principle: every other malformed-input scenario returns a clean `blocked` result, never an exception.

**Fix:** The encode call is now wrapped; a `UnicodeEncodeError` is caught and converted into a `blocked` result with reason `candidate_not_utf8_encodable`, recorded via a new `CANDIDATE_ENCODABLE` check. `scripts/test_gauss_repair_application.py` gained `test_29`.

**Net effect on the check list:** a successful application now reports 18 named checks (previously 16) — `REPLACEMENT_TEXT_NON_EMPTY` and `CANDIDATE_ENCODABLE` are the two additions, both purely additive and evaluated only in the already-existing candidate-validation phase. No existing check's name, ordering relative to itself, or semantics changed. Historical `v0.62.0` records (`CHANGELOG.md`'s `v0.62.0` entry, `release-notes-v0.62.0.md`, the `52.x` benchmark prompt text and run files) are left untouched, since "16 checks" was accurate at the time those were written — this repository's own established policy is to never rewrite historical evaluation records, and the same principle extends to historical release notes and changelog entries.
