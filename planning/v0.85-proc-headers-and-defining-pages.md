# v0.85.0 — Procedure Headers, Defining Pages and Code-Loading Statements: Design

Status: **approved** (2026-10-15) with every §8 recommendation. Not yet implemented.

## 1. Why

Live evaluation 74.x (`planning/v0.84-lexical-statement-stream.md` §11.5) found two real validator defects and raised one registry question. Every one predates v0.84.0 and fails in the safe direction, but they hit ordinary code:

| Finding (74.x) | Seen in | Effect |
|---|---|---|
| 1. A `proc` header is checked as a call | 74.18 | `proc (1) = myFunc(struct PV p);` is a false syntax INVALID (`call_argument_missing_separator`), so every structure-based optimizer objective (`sqpSolveMT`, `optmt`, `QNewtonmt`, `cmlmt`, `PV`/`DS` code) is not_ready with a misleading reason. `tgauss.exe -b` shows the code is valid and converges. |
| 2. The validator and grounding can use different pages for one symbol | 74.19 | For `miss`, grounding resolves `missmissrv.rst` but the validator's signature lookup and the grounding excerpt use `ismiss.rst`. `miss` loses its signature, its documented return type (three false `return_type_undocumented` gaps follow), and its search excerpt carries the wrong page's text. |
| 7. `library` is not a system statement | 74.17 | `library tspdlib;` loads package code from disk but produces no `system_statements` entry, unlike `run`, `#include`, `use` and `includedir`. **The user decided (2026-10-15) to add it.** |

**Correction to the 74.x record.** 74.x finding 3 (`&`-prefixed parameters never get their `:type`) is **not new**:
- v0.83.0 found it in its verdict diff (§9.2 item 5 there), and `KNOWN_LIMITATIONS.md` discloses it.
- It was deliberately left unfixed. Matching the names would let a literal `5` "match" a function pointer documented as `scalar`, which widens candidacy in the unsafe direction.
- 74.16 rediscovered it live.

§2.3 re-measures it, and §8 decision 5 recommends keeping v0.83.0's decision. The 74.x run file `-016`, `INDEX.md`, `benchmark-coverage.md`, v0.84 §11 and `PROJECT_STATUS.md` are corrected alongside this plan.

Goals:
- a `proc`/`keyword` header is checked by its own evidence-backed grammar, never as a call;
- every per-symbol documentation lookup in the validation path uses the page grounding already resolved, so citation, excerpt and signature always come from one page;
- code-loading statements (`library`, and, if decision 4 agrees, `dlibrary`/`dllcall`) are always not_ready.

Constraints (as in v0.84.0):
- no change to `command_doc_lookup.py` (`score_file`, `lookup`, `extract_match`) or to signature/type extraction (`extract_documented_signature`, `_parse_signature_occurrence`, `_PARAM_TYPE_LINE_RE`);
- the readiness state machine, `compute_eligibility` and `compute_evidence_profile` are unchanged;
- `resolve_concepts`, `compute_generation_gate` and the concept index are unchanged, so each question's grounding status, policy and topics are unchanged (§6.4).

Out of scope: the search/grounding milestone items (74.x findings 4-6), expression category inference (72.3 finding 1), and public release readiness.

## 2. Investigation findings

All probes ran at HEAD `48664c8` (v0.84.0 + the 74.x records) against the published docs copy (`C:/Users/Owner/.gauss-ai/docs`). Real-GAUSS spot checks used `tgauss.exe -b` (GAUSS 26.1.4) from a scratch directory, with `print`-only programs. The scratchpad scripts are not committed.

### 2.1 Finding 1: the header grammar, from real GAUSS

`_check_call_argument_missing_separator` (`gauss_pre_execution_validation.py:2457`) runs `_CALL_SHAPED_RE` over the masked text and skips only `_BLOCK_CONSTRUCT_KEYWORDS`. In `proc (1) = myFunc(struct PV p);` the name `myFunc(` is call-shaped and not a keyword, so the parameter list is checked as call arguments, and `struct PV p` trips `_ADJACENT_BARE_TOKENS_RE`. The same happens on v0.83.0 (74.x §11.5); the rule dates from v0.77.0 (`D-007`).

Spot checks (2026-10-15). s1/s2 are from 74.18 (run file `-018`); h1-h12 are new.

| ID | Header (abridged) | Result | Establishes |
|---|---|---|---|
| s1 | `proc (1) = myFunc(struct PV p);` | prints `10.000000` | a typed `struct` parameter is valid |
| s2 | the full 74.18 `sqpSolveMT` program | converges, `retcode 0` | the idiomatic objective runs end to end |
| h1 | `proc (1) = f(struct PV p, struct DS d);` | `6.0000000` | several struct parameters |
| h2 | `proc (1) = g(x, struct PV p, y);` | `113.00000` | struct and plain parameters mixed |
| h4b | `proc (0) = setb(struct box *pp);` | `7.0000000` | struct pointer parameter, `*` attached to the name |
| h7 | `proc k(struct PV p);` (no `(n) =`) | `9.0000000` | the short header form |
| h12 | `proc (1) = apply(&g, x);` | `42.000000` | a function-pointer parameter `&name` |
| h6 | `keyword kw(str);` | prints | a `keyword` header |
| h3 | `proc (1) = h(a b);` | `G0008 Syntax error 'a b)'` | adjacent bare names in a header are an error |
| h8 | `proc (1) = f(struct PV);` | `G0008 'struct PV)'` | a struct type with no parameter name is an error |
| h9 | `proc (1) = f(string s);` | `G0008 'string s)'` | only `struct` may type a parameter |
| h11 | `proc (0) = setb(struct box * pp);` | `G0008 'struct box * pp)'` | `*` must be attached to the name |
| h10 | `proc (1) = f(x,);` | **runs** | a trailing comma is accepted (surprising; see decision 2) |
| h5 | `y = f(struct PV p);` (a call, not a header) | `G0008 'struct'` | the existing call rule must keep firing on calls |

**The evidence-backed header parameter grammar:** each comma-separated item is `name`, `&name`, `struct Type name` or `struct Type *name` (no whitespace after `*`). h3, h8, h9 and h11 are the observed violations.

### 2.2 Finding 2: hidden ties at `max_results=1`

`command_doc_lookup.lookup(...)` sorts by score, truncates to `max_results` (`selected = candidates[:max_results]`), and only then checks `best_score - second_score < 25` for `"ambiguous"`. With `max_results=1` there is never a second score, so **a tie is always reported `"found"` and broken alphabetically**:
- `ismiss.rst` and `missmissrv.rst` both score 120 for `miss` (`command_in_file_name`, `command_in_heading`, `command_call_text`, `command_reference_text`);
- `ismiss` sorts first.

Grounding does not have this problem. `resolve_concepts` (`gauss_conversation_engine.py:837`) calls `lookup(token, max_results=3)` and v0.81.0's `_resolve_ambiguous_by_definition`, which picks the one page whose syntax block defines `token(`. But three later sites re-look the symbol up with `max_results=1`:

| Site | What it reads | Effect for `miss` |
|---|---|---|
| `ground_multi` `:1054` | the grounding source's **content** (its citation comes from the resolution) | citation `missmissrv.rst`, content `ismiss.rst` (74.19's mislabelled excerpt) |
| `validate_generated_code` `:1694` | the signature of each grounded topic | `extract_documented_signature("miss", ismiss)` → `unknown`, no return categories |
| `validate_generated_code` `:1724` | the signature of extra documented calls | the same |

**Measured over every documented symbol.** 1,418 symbols are named in a `.. function::` line anywhere in the published docs. For each, today's validator page (`lookup(..., 1)`) was compared with the resolver's page (`lookup(..., 3)` + `_resolve_ambiguous_by_definition`):
- **The page differs for exactly one symbol: `miss`.** Its signature goes from `unknown` to `extracted`.
- The resolver leaves **8** symbols `"ambiguous"`: `arimaFit`, `dotfgtme`, `func`, `KPSS_2breaks`, `newfoo`, `plotIrf`, `plotIRF` and `svarControlCreate`.
  - For each, today's page is the same top-ranked page, and 7 of the 8 have an extracted signature today.
  - So a helper that *required* `"found"` would wrongly drop 7 signatures. The design therefore falls back to today's page when the resolver cannot decide (§3.2).
- One other symbol's page does not define it (`func`, on `cc/mathematical-functions.rst`), and it is unchanged by this design.

`_lookup_command` (`:499`, used by legacy `ground()` and the recent-topic fallback at `:1075`) and `resolve_concepts`' alias paths (`:866`, `:891`) also use `max_results=1`. They feed grounding status, so they are left unchanged (§3.5, §6.4).

### 2.3 74.x finding 3 (`&` parameters), re-measured: keep v0.83.0's decision

Across the 1,418 symbols, 119 have an `&`-prefixed parameter. If names were matched consistently:
- 67 would become `control` (`struct pointer` / `struct`);
- 24 would become `scalar` (for example `eqSolve(&F)`, whose `:type &F:` is `scalar`);
- 23 stay `unknown` (`function pointer`, `pointer`);
- 5 have no `:type` line.

`infer_literal_category("&objfun")` is `unknown`, so a real `&name` argument would still be UNKNOWN: no verdict improves. But a non-`&` literal passed where the docs say `scalar` would start to MATCH. That is exactly the widening v0.83.0 refused. **Recommendation: no change** (decision 5). The existing disclosure in `KNOWN_LIMITATIONS.md` stands; only the 74.x record needs correcting.

### 2.4 Code-loading statements

`_SYSTEM_STATEMENT_REGISTRY` (213 entries) lists `run`, `#include`, `use` and `includedir` under `source_inclusion`.

- **Not listed:** `library` (`library.rst`: "Sets up the list of active libraries"; `library pgraph, cmlmt;` makes GAUSS read `.lcg` index files and autoload package code from disk).
- **Also not listed:**
  - `dlibrary` (`dlibrary.rst`: "Dynamically links and unlinks shared libraries");
  - `dllcall` (`dllcall.rst`: "Calls functions located in dynamic libraries").

  These two load and run **native code** in-process, which is further outside GAUSS's memory than anything currently registered.
- **No collisions:** none of the three names appears in any test fixture, Appendix A snippet (v0.84) or 74.x snippet other than 74.17's `library tspdlib;`.

`check_system_statements`' anchors need no change. `library`, `dlibrary` and `dllcall` are statement-leading words, so `_SYSTEM_STATEMENT_RE` matches them, and `library = 5;` stays excluded by the existing assignment look-ahead.

## 3. Proposed design

Deterministic and stdlib-only. No new module and no `pyproject.toml` change.

### 3.1 Procedure headers (finding 1)

In `gauss_pre_execution_validation.py`:
- **`_check_call_argument_missing_separator` skips header names.** It skips the procedure name in any statement whose leading word is `proc` or `keyword`. It reads `source_statements(...)` (v0.84.0), so "leading" means first in a `;`-terminated statement, never a line start. Concretely, call-shaped matches whose offset falls inside such a statement, before the statement's first `(`, are skipped. All other calls are checked exactly as today (h5 stays INVALID).
- **A new INVALID rule, `proc_header_parameter`,** checks each header's parameter list against §2.1's grammar, after splitting on top-level commas. Its `_SYNTAX_RULE_REGISTRY` entry carries the h3, h8, h9 and h11 provenance.
  - An item that is one of the four legal shapes passes.
  - An item that matches an observed violation shape is INVALID: adjacent bare names (h3), `struct Type` with no name (h8), a non-`struct` type word before a name (h9), and `*` separated from its name (h11).
  - Anything else adds no issue. The `proc` block is already an unknown `control_flow_block`, so the verdict is review_required at best regardless.
- **An empty item** (h10's trailing comma): decision 2.

### 3.2 One defining page per symbol (finding 2)

In `gauss_conversation_engine.py`, a new private helper, `_lookup_defining_page(symbol, docs_root) -> dict`:
1. `result = _resolve_ambiguous_by_definition(symbol, doc_lookup_mod.lookup(symbol, docs_root, max_results=3))`. This is the same resolution `resolve_concepts` performs for an exact-symbol token.
2. If `result["status"] == "found"`, return it.
3. Otherwise return `doc_lookup_mod.lookup(symbol, docs_root, max_results=1)` unchanged. This is today's behavior, so the 8 still-ambiguous symbols keep their current page and signature.

It is used at the three §2.2 sites (`:1054`, `:1694`, `:1724`), each keeping its own status and confidence checks exactly as written. `command_doc_lookup.py` is not touched.

### 3.3 Code-loading statements (registry)

- `library` is added under `SystemStatementCategory.SOURCE_INCLUSION` (`library.rst`).
- Decision 4: `dlibrary` and `dllcall` under a new category `native_code` (`dlibrary.rst`, `dllcall.rst`).
- The registry grows to 214 (or 216) entries. `check_system_statements`' anchors and logic are unchanged.

### 3.4 Wording

- The `call_argument_missing_separator` registry text gains one sentence: `proc`/`keyword` headers are checked by `proc_header_parameter`.
- The `DOCUMENTED_TYPE_MISSING` comment already describes the `&` exception, so it is unchanged.

### 3.5 What does not change

- `command_doc_lookup.py` in full, and every extraction function (§6.3).
- `resolve_concepts`, `_lookup_command`, `compute_generation_gate`, `GroundingBundle`, `_CONCEPT_ALIAS_INDEX`, `search_candidates` and the concept index.
- `ground_multi` changes only at `:1054` (excerpt content). Grounding status, policy, matched, unmatched and ambiguous topics are unchanged by construction (§6.4).
- The readiness state machine, `compute_eligibility`, `compute_evidence_profile` and `RoleUnknownCause`.
- `_PARAM_TYPE_LINE_RE` and the `&` disclosure (decision 5).
- No expression is ever evaluated.

## 4. Scope boundary

In scope: §3.1-§3.4; the 74.x record correction (§1); `KNOWN_LIMITATIONS.md` gains the 74.x findings that remain (search items 4-6, the header grammar's unknown shapes, the 8 still-ambiguous symbols).

Out of scope:
- **The search/grounding milestone:**
  - `sortc` / percentile recall;
  - the `setColDateFormats` false full grounding;
  - `for` as a stopword;
  - hyphenated candidates;
  - excerpt truncation before Outputs.
- **`command_doc_lookup.lookup`'s truncate-then-tie-check order.** Fixing it inside `lookup` would change every `max_results=1` caller, including grounding paths. §3.2 fixes the validation path only, and this is recorded for the search milestone.
- **`fn` one-line function headers** (`fn area(r) = …;`). They are not in the 74.x evidence.
- **`&` parameter matching** (decision 5).
- **Expression category inference** and **public release readiness**.

## 5. Known limitations this design accepts

- The header grammar comes from 13 spot checks, not from a published grammar: the docs show examples but no formal rule. Shapes outside the four legal and four violating forms add no issue, and are capped at review_required by the `proc` block.
- 8 symbols still resolve ambiguously, and keep today's top-ranked page (§2.2).
- `library` with no arguments (which only prints the library list) is also not_ready. Like every registry entry, it fails closed.

## 7. Live evaluation 75.x

After implementation:
1. Run the full suite.
2. Stop any `gauss-ai-mcp.exe`, then reinstall (`pip install -e ".[mcp]"`).
3. Reload the window.

Then, in a **fresh** conversation, the user asks plain-language tasks one at a time. The client writes all code and searches itself, and doesn't read this document or `PROJECT_STATUS.md` until the tasks are done. Useful shapes from 74.x:

## 8. Decisions needed

1. **Header scope: `proc` and `keyword` only.** *Recommend yes.* Both are evidenced (s1-h12). `fn` headers have no live evidence and a different shape (`fn name(args) = expr;`).
2. **h10, the trailing comma (`proc (1) = f(x,);` runs in real GAUSS).**
   - Option (a): accept it silently.
   - Option (b): an unknown construct, `proc_header_empty_parameter`.
   - Option (c): INVALID.

   *Recommend (a).* GAUSS accepts it, (c) would claim a violation GAUSS does not have, and the `proc` block already caps the verdict at review_required, so (b) adds nothing.
3. **Fix the content site `:1054` too**, not only the two validator sites. *Recommend yes.* Otherwise grounding keeps citing one page while showing another (74.19), and `documented_symbols` is read from the wrong page's text. The cost is that `ground_multi` is no longer byte-identical, so §6.4 item 2 pins its outputs instead.
4. **Register `dlibrary` and `dllcall`**, under a new category `native_code`. *Recommend yes.* They load and call native code, beyond anything registered today. CLAUDE.md asks that I/O the registry does not yet list be caught. A new category name keeps reasons honest ("native_code", not "source_inclusion").
5. **`&` parameters: keep v0.83.0's decision** (no matching change; the disclosure stays). *Recommend yes* (§2.3). Revisit only together with argument-side inference of `&name` as a pointer, which is its own design.
6. **Correct the 74.x record now**, as a separate commit, before implementation: 74.16's `&fct` finding was a known, disclosed limitation, rediscovered live. *Recommend yes.*
