# v0.24.0 - GAUSS Code Execution Prototype

## Release Goal

`v0.24.0` plans the first narrow prototype for executing GAUSS code in a controlled, explicit, read/write-limited way. It is the third tool-enabled capability after environment detection (`v0.21.0`) and package inspection (`v0.23.0`), and the first to actually run GAUSS code rather than only inspect the local environment.

The goal is to define a future execution helper that can:

- Consume selected GAUSS environment context from environment detection (`scripts/gauss_environment_check.py`).
- Optionally consume package inspection context (`scripts/gauss_package_inspection.py`).
- Run explicitly provided GAUSS code or a specified GAUSS script file.
- Use a safe working directory.
- Capture stdout, stderr, exit status, elapsed time, and generated output files if allowed.
- Return structured execution results.
- Distinguish actual execution output from interpretation.
- Preserve expert boundaries.

`v0.24.0` planning should **not** implement:

- Execution code yet.
- Runtime orchestration.
- Code Assistant workflow integration.
- Package installation.
- Dependency installation.
- License activation.
- Automatic repair loops.
- Report generation from output.
- Statistical validation.

## Current State

- `v0.21.0` implemented environment detection (`scripts/gauss_environment_check.py`, `detect_environment(...)`) — read-only, CLI-usable, importable.
- `v0.23.0` implemented package inspection (`scripts/gauss_package_inspection.py`, `inspect_packages(...)`) — read-only, CLI-usable, importable, consumes environment-detection context.
- Both helpers are read-only: neither runs user GAUSS code, neither mutates the environment, neither installs anything.
- No GAUSS code execution exists yet anywhere in this framework.
- Execution Mode (defined in `planning/v0.19.0-gauss-tooling-strategy-and-execution-modes.md`) remains inactive — no execution tool exists to make it a real candidate.
- Runtime orchestration does not exist.
- Code Assistant workflow integration with any of the three tools (environment detection, package inspection, or the future execution tool) does not exist yet — `workflows/code-assistant-response.md` still ends every response at Step 8's failure-mode check without a tool-output-consumption step.
- The assistant can provide Advisory Mode and Verified Knowledge Mode guidance (write GAUSS code, explain it, cite verified command evidence) but cannot yet claim GAUSS code has actually run, and must not imply otherwise.

## Proposed Tool

- **Helper module:** `scripts/gauss_code_execution.py`
- **Tool spec:** `tools/gauss_code_execution.md`
- **Result schema:** `schemas/gauss_code_execution.schema.json`

The helper should be CLI-usable and importable, following the same pattern already established by `scripts/gauss_environment_check.py` and `scripts/gauss_package_inspection.py`.

**Preferred importable API name: `execute_gauss_code(...)`.**

Rationale: `run_gauss_code(...)` is also a reasonable name, but `execute_gauss_code(...)` is chosen for two reasons — it matches this framework's existing vocabulary (`operating_mode_recommendation: execution_candidate`, "Execution Mode," `can_execute_gauss_code`), and it reads unambiguously as an action with consequences ("execute") rather than something that could be misread as a lightweight, side-effect-free check ("run" is used more loosely elsewhere, e.g. "run a self-test"). This name should be treated as decided for `v0.24.0`'s eventual implementation task, not re-litigated per-task.

## Execution Scope

Define the first prototype narrowly.

**Allowed:**

- Execute an explicitly supplied GAUSS code string.
- Execute an explicitly supplied `.gss` or GAUSS script file path.
- Use an explicitly selected GAUSS executable path from environment detection or a direct argument.
- Run inside a safe working directory.
- Enforce a timeout.
- Capture stdout/stderr/exit code.
- Record whether execution completed, failed, timed out, or was skipped.
- Optionally list generated output files, limited to inside the safe working directory.

**Not allowed:**

- Execute arbitrary discovered files.
- Execute code without an explicit user/tool request.
- Install packages.
- Activate licenses.
- Modify global GAUSS configuration.
- Modify environment variables permanently.
- Write outside the safe working directory.
- Delete user files.
- Access the network.
- Infer statistical validity from successful execution.
- Automatically rerun corrected code, unless a later milestone explicitly allows it.

## Permission and Safety Model

Execution must require explicit intent. This is the most consequential capability the framework has planned so far — the first that can affect real files and real processes — so this section governs every other design decision below.

**Rules:**

- No silent execution.
- No execution from ambiguous prompts.
- No execution if environment detection is unavailable or ambiguous.
- No execution if the executable path is missing, inaccessible, or untrusted.
- No execution without a safe working directory.
- No execution without a timeout.
- No execution of code that appears to modify files outside the working directory, unless explicitly allowed in a future design.
- No package installation.
- No license activation.
- No network access.
- No hidden metadata or dependency commands beyond the requested execution.

The helper should treat execution as a tool operation, not a reasoning shortcut: the assistant does not execute code to "check its own work" implicitly, and a request to write code does not by itself authorize running it. Every one of these rules restates and narrows the Graceful Fallback Principle and Execution Mode definition from `planning/v0.19.0-gauss-tooling-strategy-and-execution-modes.md` for this specific, higher-risk capability.

## Relationship to Environment Detection

The execution helper should use the selected GAUSS environment from `scripts/gauss_environment_check.py`.

**Rules:**

- If environment detection selected GAUSS 26, execution should use GAUSS 26 by default.
- If the user explicitly selected GAUSS 25, execution should use GAUSS 25.
- If the user provided an executable path directly, that path controls.
- Do not silently switch GAUSS versions.
- Do not run if the environment is `not_found`, `ambiguous`, `inaccessible`, or `error`.
- If version is `unknown` but the executable is accessible (`detection_status: found`, `version_known: false`), execution may be allowed only if explicitly permitted by the prototype's rules — this is an open design decision, not resolved by this planning task (see "Risks and Open Questions").

This mirrors the version-context inheritance rule already established for package inspection (`v0.23.0`'s "Version-Specific Package Context Rule") — execution is a third capability that inherits the selected environment rather than re-deciding it.

## Relationship to Package Inspection

Package inspection can provide feasibility context but should not be required for all code execution.

**Rules:**

- Package inspection can warn when requested packages appear missing or unknown.
- A missing package should not be confused with GAUSS itself being missing.
- Unknown package status should not automatically block execution, unless the code depends on that package and policy requires confirmation.
- An installed package does not prove syntax validity.
- An installed package does not prove methodology validity.
- An installed package does not prove execution success.
- Execution failure may reveal missing dependencies, but should not trigger automatic installation — a failure surfaces as a structured result and an explanation, not a repair action.

## Proposed Input Contract

**Possible inputs:**

- `environment_check_result`
- `package_inspection_result`
- `executable_path`
- `gauss_version`
- `code`
- `script_path`
- `working_directory`
- `input_files`
- `output_directory`
- `timeout_seconds`
- `allow_file_write`
- `allow_output_files`
- `allow_network`
- `strict`
- `capture_stdout`
- `capture_stderr`
- `validate_schema`

**Important:**

- Exactly one of `code` or `script_path` should usually be required — supplying both, or neither, is a blocked/invalid request in the first prototype.
- `working_directory` should be required for execution; there is no default "current directory" fallback given the stakes involved.
- `allow_network` should default to `false` and probably remain entirely unsupported in the first prototype (accepted as an input for forward-compatibility with the contract, rejected or ignored-with-warning in behavior — mirroring the `--allow-version-query`/`--allow-metadata-query` no-op precedent from `v0.21.0`/`v0.23.0`).
- `allow_file_write` should default to `false`, or when `true`, be strictly limited to the working directory.
- `timeout_seconds` should have a safe default and a hard maximum that cannot be overridden upward by the caller.
- `input_files` should be explicit — no implicit discovery of "nearby" files to feed into execution.

## Proposed Output Contract

**Suggested top-level fields:**

`checked`, `executed`, `execution_status`, `operating_mode`, `executable_path`, `gauss_version`, `working_directory`, `command`, `code_source`, `script_path`, `timeout_seconds`, `elapsed_seconds`, `exit_code`, `stdout`, `stderr`, `output_files`, `warnings`, `errors`, `next_steps`, `raw_execution_details`.

**Suggested `execution_status` enum:** `completed`, `failed`, `timed_out`, `skipped`, `blocked`, `error`, `unknown`.

**Suggested `operating_mode` enum:** `advisory`, `verified_knowledge`, `execution`.

**Important:**

- `executed: true` only when GAUSS was actually invoked as a subprocess — never set based on intent, request validity, or a successful pre-flight check alone.
- `execution_status: completed` does not mean statistically valid, correct, or meaningful — only that the process ran to completion.
- `exit_code: 0` does not mean statistically valid — a script can exit cleanly while producing a nonsensical or methodologically inappropriate result.
- `output_files` should be limited to paths inside the safe working directory; nothing outside it should ever be listed or read.
- `stdout`/`stderr` may need a truncation policy for very large output — see "Timeout and Resource Policy."

## Planned Schema

Plan `schemas/gauss_code_execution.schema.json`. It should:

- Use the repository's existing JSON Schema convention (Draft 2020-12, `additionalProperties: false`, a `$defs` section for shared enums/tri-states, `allOf`/`if`/`then` consistency constraints), matching `schemas/gauss_environment_check.schema.json` and `schemas/gauss_package_inspection.schema.json`.
- Include strict top-level required fields (the full output-contract list above).
- Define the `execution_status` enum.
- Define an output-file object schema (at minimum a path and a note that it was discovered inside the working directory only).
- Define `warnings`/`errors` arrays.
- Prevent ambiguous claims around executed vs. skipped: `executed: false` must never coexist with `execution_status: completed`.
- Enforce that `timed_out` carries at least one warning or error explaining the timeout.
- Enforce that `blocked` carries at least one error or next step explaining why execution did not proceed.
- Allow an optional `raw_execution_details` object for implementation-specific diagnostics, mirroring `raw_detection_details`/`raw_inspection_details` in the two existing schemas.

**This task does not create this schema.** It is scoped to a future task in the Suggested Task Order below, following the same spec-before-schema-before-implementation sequencing already used for both prior tools.

## Working Directory Policy

- Execution must happen in an explicit, caller-supplied safe working directory — there is no implicit default.
- The helper may create a temporary subdirectory only if a future design explicitly specifies this; it is not assumed by this plan.
- No writes outside the working directory, regardless of `allow_file_write`.
- Output file discovery is limited to the working directory.
- Path traversal (e.g. `../` segments resolving outside the working directory) should be rejected.
- Symlink handling should be conservative — a symlink inside the working directory that resolves outside it should not be treated as a legitimate output path.
- Relative paths (for `script_path`, `input_files`, `output_directory`) should resolve under the working directory, not the process's current directory.
- Destructive operations should be blocked or warned where detectable (for example, code that appears to reference paths outside the working directory before execution even begins) — this is a best-effort, pre-flight heuristic, not a guarantee, and should be documented as such rather than oversold.

## Timeout and Resource Policy

- A timeout is required for every execution attempt — there is no untimed mode.
- A safe default timeout should be defined by the eventual implementation task (not fixed by this plan).
- A maximum timeout should be enforced that the caller cannot override upward.
- The process should be forcibly terminated on timeout, not merely flagged.
- Captured stdout/stderr should be size-limited.
- Truncation, if it occurs, should be recorded explicitly in `warnings` rather than silently dropping output.
- No long-running background processes.
- No detached processes — the helper should own the full lifecycle of any process it starts and ensure it is terminated before returning.

## Result Interpretation Policy

Execution output is evidence that code ran, not evidence that:

- Syntax is generally valid beyond this specific run/context.
- The model is statistically valid.
- The method is appropriate.
- Estimates are meaningful.
- Diagnostics are adequate.
- Code is maintainable.
- Documentation is sufficient.
- Learning design is effective.
- Product value is proven.

Successful execution should route interpretation to relevant experts, not be treated as self-certifying:

- **GAUSS Language Expert** — implementation/syntax context (did the code use correct GAUSS syntax and idioms, independent of whether it happened to run).
- **Econometrics Expert** — methodology/diagnostics/interpretation (is the estimator, specification, and interpretation of output sound).
- **Software Engineering Expert** — maintainability (is the executed code well-structured, independent of its output).
- **Documentation Expert** — explanation clarity (is the output/result explained clearly to the user).
- **Education Expert** — learning scaffolding (if the execution is part of a teaching interaction).
- **Product Expert** — user-value implications (if the execution's result bears on a product/feature decision).

This restates `experts/EXPERT_BOUNDARY_MATRIX.md`'s independence principles for the specific, narrower case of code execution output, exactly as `v0.20.0`/`v0.21.0` did for environment detection and `v0.22.0`/`v0.23.0` did for package inspection.

## Failure and Fallback Policy

- If execution is blocked, return a structured `blocked`/advisory output — never a silent no-op or an unstructured error.
- If the GAUSS executable is unavailable, do not execute.
- If a package dependency appears missing, warn or block depending on explicit policy (not yet decided by this plan — see "Risks and Open Questions").
- If execution fails, do not fabricate results — report the real failure, real stdout/stderr, and real exit code.
- If execution times out, return `timed_out` with partial stdout/stderr if any was captured before termination.
- If code produces no output, state clearly that execution completed but no output was captured, rather than implying something went wrong.
- If output cannot be interpreted, provide next steps rather than guessing at what it means.
- Advisory Mode remains available after any failure — an execution failure must never break the assistant's ability to keep helping with code, explanation, review, documentation, education, or product reasoning.

## Security and Risk Considerations

**Risks:**

- Arbitrary code execution.
- File modification/deletion.
- Path traversal.
- Environment leakage (secrets, credentials, or sensitive local state exposed via `stdout`/`stderr`/output files).
- Large output capture (memory/disk exhaustion).
- Long-running processes.
- Hidden package-installation commands triggered indirectly by executed GAUSS code.
- License prompts (interactive prompts that hang a supposedly non-interactive execution).
- GUI popups (GAUSS's interactive/graphical behavior blocking a scripted invocation).
- Network access.
- Sensitive local paths leaking into captured output.
- Execution logs containing private data.

**Mitigations:**

- Explicit execution request (never inferred).
- Safe working directory (no writes/reads outside it).
- No network access.
- No package installation.
- No global config mutation.
- Timeouts (with a hard maximum).
- Structured errors (never a raw traceback surfaced to the user).
- Output truncation (with the truncation itself recorded).
- Path validation (traversal/symlink rejection).
- No automatic rerun loops (a failure is reported, not silently retried).

## Testing Strategy

Self-tests should not require real GAUSS, following the precedent set by both `scripts/gauss_environment_check.py --self-test` and `scripts/gauss_package_inspection.py --self-test`.

**Synthetic/self-test cases:**

- Missing executable → `blocked`/`skipped`.
- Ambiguous environment → `blocked`/`skipped`.
- No code or script supplied → `blocked`/`skipped`.
- Both code and script supplied → `blocked`/`skipped`.
- Missing working directory → `blocked`/`skipped`.
- Timeout mapping using a fake runner (a process stand-in that simulates hanging).
- Successful execution using a fake runner.
- Failed execution using a fake runner (nonzero exit code).
- stdout/stderr capture from a fake runner.
- Output-truncation warning when captured output exceeds a size threshold.
- Output-file listing limited strictly to the working directory.
- Path traversal rejected (an output/input path resolving outside the working directory).
- `--allow-network` rejected or ignored with a warning.
- Execution result validates against the schema once it exists.
- `executed: false` never reports `execution_status: completed` (a structural invariant check).

If a real GAUSS installation exists, optional manual verification can be documented separately (the same split `v0.21.0` used for manual verification against real GAUSS 24/25/26 installations) — but real GAUSS should never be required for `--self-test` or for CI.

## Risks and Open Questions

- Exact GAUSS command-line invocation syntax for non-interactive script execution, across GAUSS versions and platforms.
- Whether the GAUSS CLI supports non-interactive, scriptable execution consistently (vs. requiring an interactive session or GUI).
- Exit-code behavior — what GAUSS actually returns on success/failure/syntax error.
- stdout/stderr behavior — where GAUSS writes program output, errors, and diagnostic messages.
- License prompts or GUI behavior that could hang a supposedly non-interactive invocation.
- Working-directory behavior — how GAUSS resolves relative paths and where it looks for included files by default.
- Package path behavior during execution — whether GAUSS needs additional path configuration to find installed packages, and whether that configuration is itself a form of environment mutation.
- Output file conventions — where GAUSS writes generated files by default, and whether that can be redirected without global configuration changes.
- Safe detection of destructive GAUSS code — how far a pre-flight heuristic can reasonably go before it becomes either useless (too permissive) or a source of false confidence (too aggressive without being a real sandbox).
- Windows/macOS/Linux differences in process invocation, termination, and timeout enforcement.
- Whether CI can ever run execution tests without a real GAUSS installation (likely not — CI would need `--self-test`'s fake-runner coverage only, mirroring `v0.21.0`/`v0.23.0`'s CI posture).
- Whether this capability belongs in a local-only helper, an MCP server, or a different connector architecture — not decided by this plan, and potentially a bigger decision than any single milestone.
- Whether the version-unknown-but-accessible case (environment `found`, `version_known: false`) should ever be allowed to execute, or should always be blocked pending a confirmed version.
- Whether a missing/unknown package dependency should warn or block by default, and whether that default should be configurable.
