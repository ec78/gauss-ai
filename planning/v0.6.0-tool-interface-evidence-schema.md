# v0.6.0 Tool Interface and Evidence Schema Plan

## 1. Release Goal

`v0.4.0` proved a local script could find and extract command-specific documentation. `v0.5.0` proved the Code Assistant can respond consistently once that evidence exists, across four retrieval states (found/complete, found/incomplete, not found, ambiguous) and a source-conflict state, with a required validation step for translation and debugging.

`v0.6.0` should prove a different, more structural claim: **retrieval evidence can be represented in a consistent, inspectable, and testable format** — not just produced by one script and consumed by manual judgment. Concretely:

- Every field a response might cite (syntax, defaults, return structure, status, source, confidence, unresolved questions) has a defined name, type, and meaning, instead of being whatever shape `scripts/command_doc_lookup.py`'s current JSON output happens to be.
- The eight retrieval/response states already defined qualitatively in `workflows/retrieval-backed-response-pattern.md` (found-complete, found-incomplete, not-found, ambiguous, category-only, curated-only, conflict, stale) have a matching, checkable representation in the evidence object itself — not just in prose guidance.
- Evidence quality (missing fields, missing provenance, unredacted paths, unflagged conflicts) becomes something that can be checked mechanically, at least for the cases that are cheap to check, rather than relying solely on an evaluator reading the JSON by eye.

This is still a prototype-stage milestone. It formalizes the *shape* of evidence so future tools and evaluations can rely on it — it does not build a new retrieval engine, a live agent runtime, or an enforcement layer that blocks bad responses automatically.

## 2. Scope

- **Evidence object/schema design.** Define the fields, types, and required/optional status for a "command lookup evidence" object (Section 4).
- **Command lookup output schema.** Align the schema with what `scripts/command_doc_lookup.py` already produces where possible, so adopting it is a mapping exercise, not a rewrite (see Constraints — no rewriting existing lookup JSON yet).
- **Required vs. optional fields.** Distinguish fields that must always be present (e.g., `command_name`, `retrieval_status`) from fields that are only meaningful in certain states (e.g., `conflicts` only when `retrieval_status` is `conflict`).
- **Confidence and status values.** Define an explicit status enum (Section 4) that maps onto the states already in `workflows/retrieval-backed-response-pattern.md`, plus a numeric or categorical confidence indicator.
- **Source provenance.** Every verified fact should be traceable to a specific source (file, curated note, category list) and an authority level (Section 5).
- **Freshness/staleness indicators.** A way to say "this evidence was generated at time X and has not been re-verified since," addressing the `strindx` keyword-quoting incident from `v0.4.0` where a stale/incorrect committed file looked authoritative until someone re-ran the lookup.
- **Ambiguity handling.** A structured way to list multiple candidate matches (file names, headings, scores) instead of only prose describing that ambiguity exists.
- **Incomplete extraction handling.** A structured way to say which fields were extracted and which were truncated or missing, rather than only a free-text `unresolved_questions` list.
- **Conflict handling between official docs and curated notes.** A structured way to represent that two sources disagree on a specific field, and which one wins.
- **Error/failure representation.** A defined shape for "lookup failed" (docs root missing, no matching file, tool error) distinct from "lookup succeeded but found nothing relevant."
- **How the Code Assistant should consume evidence objects.** Concrete consumption rules (Section 6) tying schema fields back to the response behavior already defined in `workflows/retrieval-backed-response-pattern.md`.
- **Evaluation cases for schema quality.** New benchmark prompts (Section 9) that test whether the assistant behaves correctly when handed evidence with specific schema properties (missing fields, stale timestamps, conflict markers), not just "well-formed JSON."

## 3. Non-Goals

- Full semantic search over documentation.
- A hosted or shared retrieval service.
- Full GAUSS runtime execution or code validation by actually running GAUSS.
- Replacing official GAUSS documentation as the authoritative source.
- Indexing every GAUSS command.
- Building a full agent runtime (tool-calling loop, live retrieval invocation, memory). This milestone defines the evidence *shape*; wiring it into an autonomous loop is a separate, later concern.
- Automatically enforcing all response behavior. A validator can check that an evidence object is well-formed and that certain dangerous patterns are absent (e.g., an unredacted path), but it cannot and should not be asked to verify that a Code Assistant response's prose correctly reflects the evidence — that remains a manual evaluation concern per `workflows/manual-evaluation.md`.

## 4. Proposed Evidence Schema

A candidate schema for a single command's lookup evidence object. Field names are chosen to align closely with `scripts/command_doc_lookup.py`'s existing output (`command_name`, `confidence`, `status`, `unresolved_questions`, `extraction_warnings`, `keyword_hits`, `related_links`, `raw_section_headings`) so that adoption is mostly renaming/regrouping, not a rewrite.

| Field | Type | Required? | Notes |
|---|---|---|---|
| `command_name` | string | Required | The command name as requested. |
| `source_type` | enum | Required | `official_local_rst`, `curated_note`, `category_only`, `none`. |
| `source_path` | string or null | Required when `source_type` is `official_local_rst` or `curated_note` | Redacted relative to `docs_root`; never an absolute local path. |
| `source_authority` | enum | Required | One of the levels in Section 5 (`official_docs`, `official_package_docs`, `official_source`, `curated_note`, `example_or_blog`, `category_list`, `general_knowledge`). |
| `retrieval_status` | enum | Required | `found_complete`, `found_incomplete`, `not_found`, `ambiguous`, `conflict`, `stale`, `error`. See status definitions below. |
| `confidence` | number (0-1) | Required | Carried over from the existing scoring approach in `scripts/command_doc_lookup.py`. |
| `matched_heading` | string or null | Optional | The document heading actually matched, if any. |
| `match_reasons` | array of strings | Optional | E.g., `exact_file_name`, `exact_heading`, as already produced today. |
| `verified_syntax` | array of strings | Optional | Only populated when actually extracted; empty, not guessed, otherwise. |
| `verified_inputs` | object or null | Optional | Structured parameter info when extracted. |
| `verified_outputs` | object or null | Optional | Structured return-field info when extracted; see `unresolved_questions` for what's missing. |
| `verified_defaults` | object or null | Optional | Control/default values actually documented (e.g., `ctl.con` default). |
| `verified_examples` | array of strings | Optional | Only literal extracted examples, not generated ones. |
| `keyword_hits` | object | Optional | Keyword → snippet list, as already produced today. |
| `related_links` | array of strings | Optional | Cross-referenced commands/sections, as already produced today. |
| `unresolved_questions` | array of strings | Required (may be empty) | Explicit list of what's not verified; empty array, not omitted, when nothing is unresolved. |
| `extraction_warnings` | array of strings | Required (may be empty) | Tool-level warnings distinct from content-level unresolved questions. |
| `ambiguity` | object or null | Required when `retrieval_status` is `ambiguous` | `{ "candidates": [ { "source_path": ..., "confidence": ..., "match_reasons": [...] }, ... ] }`. |
| `conflicts` | array of objects or null | Required when `retrieval_status` is `conflict` | `{ "field": ..., "official_value": ..., "curated_value": ..., "curated_source_path": ..., "resolution": "official_docs_used" }`. |
| `generated_at` | string (ISO 8601 timestamp) or null | Recommended, not yet required (see Open Questions) | When this evidence object was produced. |
| `docs_root_redacted` | boolean | Required | `true` when `source_path`/`docs_root` fields have been redacted for sharing, matching today's `--redact-docs-root` behavior. |
| `tool_version` | string or null | Recommended, not yet required | Identifies which version/commit of `scripts/command_doc_lookup.py` produced this evidence, to help detect drift as the script changes. |

**Status value definitions:**

- `found_complete` — a confident match with no relevant unresolved fields (state A).
- `found_incomplete` — a confident match, but extraction stopped short of covering the full section (state B).
- `not_found` — no matching official documentation found (state C).
- `ambiguous` — multiple plausible candidates, none clearly best (state D).
- `conflict` — official docs and a curated note both exist and disagree on at least one field (state G).
- `stale` — evidence exists but its freshness relative to current official docs has not been confirmed this session (state H).
- `error` — the lookup process itself failed (e.g., docs root missing/unreadable), distinct from a clean "not found."

This schema is a planning proposal, not a final specification — it should be reviewed against a second real command's lookup output (Section 10 risk: "whether JSON Schema is enough") before being locked in.

## 5. Source Authority Model

Authority levels, highest to lowest:

1. **Official docs** — the command-specific `.rst` (or equivalent) page in the local official documentation checkout. Highest authority for syntax, arguments, defaults, and return values.
2. **Official package docs** — documentation for a package-specific command, when the command is not part of base GAUSS. Same authority as official docs, but scoped to that package's version/compatibility.
3. **Official source code** — `.src`/`.e` implementation files, used only when documentation is unavailable or ambiguous and source inspection is possible; lower confidence than documented behavior because it requires interpretation rather than reading a stated contract.
4. **Curated command notes** (`experts/gauss-language/commands/*.md`) — convenience summaries citing an official source and a last-verified date. Never overrides official docs; used alone only when official docs are unavailable this session, with a freshness caveat.
5. **Examples/blogs** — applied usage patterns; supporting evidence for realistic workflows, not a full API specification. Useful for illustrating a call pattern, not for asserting an argument is optional or a default value.
6. **Category lists** (`experts/gauss-language/COMMAND_CATEGORIES.md`) — discovery only. Confirms a command is real and roughly what area it belongs to; confirms nothing about syntax, arguments, or return values.
7. **General model knowledge** — lowest authority; cannot verify command-specific syntax, arguments, defaults, or return values under any circumstances. May be used for stable, non-command-specific conceptual explanation only (e.g., what a moment matrix is, not what `olsmt` calls a specific field).

Clarifications carried into the schema and consumption rules:

- Official docs (levels 1-2) override curated notes (level 4) whenever both exist and disagree — this is `retrieval_status: conflict` handling.
- Category lists (level 6) never populate `verified_syntax`, `verified_inputs`, `verified_outputs`, or `verified_defaults` — only `source_type: category_only` with those fields empty.
- Examples (level 5) may populate `verified_examples` but should not be used to infer `verified_inputs`/`verified_defaults` that aren't independently documented (an example passing 3 arguments doesn't confirm a 4th is unsupported).
- General model knowledge (level 7) never appears as a `source_authority` value for a specific command's verified fields; it is not a retrievable source.

## 6. Evidence Consumption Rules

- **When evidence is complete (`found_complete`).** The assistant may state `verified_syntax`, `verified_inputs`, `verified_outputs`, and `verified_defaults` as fact, citing `source_path`, and should still include the validation-step requirement from `workflows/retrieval-backed-response-pattern.md` for translation/debugging responses.
- **When evidence is incomplete (`found_incomplete`).** The assistant must present only the fields actually populated and must surface every entry in `unresolved_questions` verbatim or in close paraphrase — it must not fill a gap using a field name's apparent meaning.
- **When docs are missing (`not_found` or `error`).** The assistant must refuse to populate `verified_syntax`/`verified_inputs`/`verified_outputs`/`verified_defaults` from any other source and must say verification could not be performed, per Prompt 12.2's established behavior.
- **When evidence is ambiguous (`ambiguous`).** The assistant must present the `ambiguity.candidates` list (or a summary of it) instead of silently using the highest-confidence candidate, per Prompt 12.3's established behavior, even if one candidate's `confidence` is numerically higher than the others.
- **When lookup JSON may be stale (`stale`).** The assistant must state the evidence has not been freshly re-verified this session (using `generated_at`/`tool_version` if present) before relying on it for a high-stakes answer, and should recommend re-running the lookup for production use.
- **How to cite or summarize evidence.** Prefer naming `source_path` and `source_authority` explicitly ("verified from official local documentation, `olsmt.rst`") over vague phrases like "the docs say," consistent with the wording patterns already defined in `workflows/retrieval-backed-response-pattern.md` Section 5.
- **How to preserve unresolved questions.** `unresolved_questions` and `extraction_warnings` should be treated as required reading before finalizing a response — if either is non-empty, the response must acknowledge at least the entries relevant to the user's question, per Prompt 12.1's established behavior.

## 7. Validation and Quality Checks

Checks a lightweight validator (Section 8, Stage 3) could plausibly run against an evidence object:

- Required fields are present (`command_name`, `source_type`, `source_authority`, `retrieval_status`, `confidence`, `unresolved_questions`, `extraction_warnings`, `docs_root_redacted`).
- `retrieval_status` is a valid enum value from Section 4.
- `source_path` is present and non-null whenever `retrieval_status` is `found_complete`, `found_incomplete`, `conflict`, or `stale`, and `source_type` is `official_local_rst`.
- No unredacted local absolute filesystem path appears in a committed artifact (`docs_root_redacted` is `true`, and `source_path` contains no drive letters or `/Users/`, `/home/`, `C:\` style prefixes) — this is a direct check the `v0.4.0`/`v0.5.0` readiness checklists already performed by hand.
- No `verified_*` field is populated without a corresponding `source_path` and `source_authority` — i.e., no verified fact without provenance.
- `verified_examples` entries are only accepted when `source_type` is `official_local_rst` or `curated_note` — never fabricated to fill the field.
- `extraction_warnings` are surfaced, not silently dropped, whenever `retrieval_status` is `found_incomplete`.
- `conflicts` is present and non-empty whenever `retrieval_status` is `conflict`, and each conflict entry names both the official and curated value.
- `ambiguity.candidates` has at least two entries whenever `retrieval_status` is `ambiguous`.

These are validation rules for the **evidence object's shape and internal consistency**, not for whether a Code Assistant response correctly reflects that evidence in prose — that remains a manual evaluation concern.

## 8. Candidate Implementation Deliverables

Per the constraints on this planning pass (schema design first, implementation only where trivial and isolated), likely files for later stages:

- `schemas/command_lookup_evidence.schema.json` — a JSON Schema expression of Section 4's field table.
- `schemas/README.md` — explains the schema's purpose, versioning approach, and relationship to `scripts/command_doc_lookup.py`'s current output.
- `tools/evidence_schema.md` — narrative documentation of the schema and the Section 5 authority model, in the same style as `tools/command_doc_lookup.md`.
- `scripts/validate_lookup_evidence.py` — a small, isolated validator implementing the Section 7 checks against a given JSON file; explicitly out of scope to build in this planning pass unless it turns out to be trivial (see Constraints).
- `examples/retrieval/README.md` updates — note that committed lookup JSON is expected to (eventually) validate against the schema, once the script is updated to emit it.
- `workflows/retrieval-backed-response-pattern.md` updates — cross-reference the schema's field names in the response-state table (Section 3 of that document) once the schema is finalized.
- `evaluations/benchmark-prompts.md` additions — the new "Evidence Schema" category (Section 9 below).
- `evaluations/benchmark-coverage.md` updates — once the new prompts are evaluated.

This plan does **not** propose rewriting `examples/retrieval/olsmt.lookup.json` or `strindx.lookup.json` to match the schema yet; that's an explicit later stage (Section 11, Stage 4), done deliberately rather than as a side effect of planning.

## 9. Candidate Benchmark Prompts

These test schema-aware behavior, which is different from the response-quality behavior `v0.5.0`'s 12.x prompts already cover — so this plan proposes a new category, **"Evidence Schema" (category 13)**, rather than continuing 12.x. Draft prompts:

- **13.1 — Evidence object missing required fields.** Present the assistant with a lookup evidence object missing a required field (e.g., no `retrieval_status`). Expected behavior: the assistant treats the evidence as untrustworthy/incomplete at the tooling level and says so, rather than guessing what the missing field would have said.
- **13.2 — Stale lookup JSON presented as current.** Present evidence with a `retrieval_status: stale` (or an old `generated_at`) being used for a production-code question. Expected behavior: the assistant flags the staleness and recommends re-verification before giving production-ready syntax.
- **13.3 — Conflict represented in schema fields.** Present evidence with a populated `conflicts` array showing a specific field disagreement (e.g., a `ctl.con` default mismatch). Expected behavior: the assistant uses the official value, states the conflict, and recommends fixing the curated note — extending Prompt 12.4's prose-only conflict test to a schema-driven one.
- **13.4 — Ambiguous lookup represented in schema.** Present evidence with a populated `ambiguity.candidates` array (two or more real-shaped candidates). Expected behavior: the assistant lists the actual candidates from the array rather than describing that ambiguity exists in the abstract — extending Prompt 12.3 to a schema-driven case with concrete candidate data.
- **13.5 — Extraction warning present but easy to miss.** Present evidence where `extraction_warnings` is non-empty but `retrieval_status` is `found_complete` (a genuinely partial signal, not a full incomplete state). Expected behavior: the assistant still surfaces the warning rather than treating `found_complete` as a green light to ignore it.
- **13.6 — Verified syntax present but outputs incomplete.** Present evidence with populated `verified_syntax` and `verified_inputs` but a null/partial `verified_outputs` plus non-empty `unresolved_questions` about return fields. Expected behavior: the assistant gives verified syntax confidently while keeping the return-field gap explicit — a schema-driven version of Prompt 12.1.
- **13.7 — Committed artifact contains an unredacted local path.** Present a (hypothetical, described) evidence file where `docs_root_redacted` is `false` or `source_path` contains an absolute local path. Expected behavior: the assistant flags this as a problem to fix before committing/sharing the artifact, rather than treating it as normal.

## 10. Risks and Open Questions

- **Is JSON Schema enough?** JSON Schema can check shape (types, required fields, enums) but not semantic correctness (e.g., that `conflicts[].official_value` actually matches what's in `source_path`). This plan assumes JSON Schema covers the mechanical checks in Section 7 and that semantic correctness stays a manual evaluation concern — worth revisiting once a validator exists.
- **Should existing lookup JSON be validated retroactively?** `examples/retrieval/olsmt.lookup.json` and `strindx.lookup.json` predate this schema and use different field names/shapes. Retrofitting them is a judgment call between "prove the schema works on real data now" and "avoid unnecessary churn on files that already passed evaluation" — this plan defers the decision to Stage 4.
- **How should evidence schemas be versioned?** If the schema changes after `v0.6.0`, old committed evidence objects will not match the new schema. A `schema_version` field (not yet in Section 4's table) may be needed — flagged here rather than added speculatively before the first version is even used.
- **How should staleness actually be detected**, not just represented? `generated_at` alone doesn't know if official docs have since changed. This plan proposes representing staleness (the `stale` status and `generated_at`/`tool_version` fields) without yet solving automatic staleness *detection*, which likely needs either a docs-checkout fingerprint or manual re-verification triggers.
- **Should `generated_at` be required?** Making it required strengthens staleness tracking but would immediately invalidate the two existing committed lookup files, which don't have it. This plan proposes "recommended, not required" for now, revisited once retroactive validation (above) is decided.
- **Should source snippets be stored, or only references/line numbers?** Storing full snippets (as `keyword_hits` already does) is more self-contained but risks copying more of the official docs into this repository than intended (`workflows/command-documentation-retrieval.md`'s "do not mirror full documentation pages" principle). Line-number references are more compact but require the docs checkout to be present to verify anything after the fact.
- **How much provenance is actually needed for trust?** The schema in Section 4 requires `source_path` and `source_authority` for every verified field, which may be more bookkeeping than is proportionate for a small local prototype. Worth revisiting after the first real schema-based benchmark run (13.x) shows whether the overhead is worth it in practice.

## 11. Suggested Implementation Stages

1. **Planning and schema design.** This document. Review the Section 4 schema against at least one more real lookup (not just `olsmt`/`strindx`) before treating field names as settled.
2. **Schema file and documentation.** Write `schemas/command_lookup_evidence.schema.json` and `schemas/README.md`/`tools/evidence_schema.md` from the finalized version of Section 4.
3. **Validator script.** Implement `scripts/validate_lookup_evidence.py` covering the Section 7 checks, kept small and isolated.
4. **Update lookup JSON generation to match schema.** Decide the retroactive-validation open question above, then update `scripts/command_doc_lookup.py`'s output shape (and, if warranted, regenerate `olsmt.lookup.json`/`strindx.lookup.json`) to match.
5. **Update response workflows to consume schema fields.** Revise `workflows/retrieval-backed-response-pattern.md` Section 3's state table to reference actual schema field names/values instead of prose-only descriptions.
6. **Add and run schema-focused evaluations.** Add Prompts 13.1-13.7 to `evaluations/benchmark-prompts.md`, then run and record manual evaluations, following the `v0.5.0` precedent of evaluating each new state individually.
7. **Readiness checklist.** Draft a `v0.6.0` readiness checklist modeled on the `v0.4.0`/`v0.5.0` precedents, including a check that `ROADMAP.md` and `KNOWN_LIMITATIONS.md` reflect the schema's actual scope and that no unredacted paths exist in any updated example files.
