# v0.15.0 Readiness Checklist

## Release Goal

`v0.15.0` operationalizes the Documentation Expert as the fourth operational expert, adding documentation clarity, reference structure, examples, comments/docstrings, usage guidance, troubleshooting, caveat placement, and user-facing explanation quality to the Code Assistant. The Code Assistant now has four separately-owned, non-substitutable correctness dimensions:

- **GAUSS Language Expert** — implementation correctness (GAUSS syntax, command/procedure selection, data structures, package/base distinction).
- **Econometrics Expert** — methodological correctness (model/estimator choice, assumptions, diagnostics, causal/predictive framing).
- **Software Engineering Expert** — maintainability/design correctness (code organization, modularity, refactoring, testability, error handling, safe change management).
- **Documentation Expert** — documentation/explanation correctness (clarity, reference structure, examples, comments/docstrings, usage guidance, warnings/caveats, troubleshooting, audience awareness).

As with every operational expert before it, this remains **documented, manual-evaluation-driven expert routing, not runtime orchestration**. No code parses, executes, or enforces `workflows/expert-routing.md` or any `OPERATIONAL_PROFILE.md` at runtime; a response is checked against them manually. Adding a fourth expert changed the *shape* of routing (a compact activation matrix plus worked patterns replacing the prior eight-type enumeration) but not its *mechanism*.

## Documentation Expert Summary

**Purpose:** guide agents on documentation quality and user-facing clarity — reference structure, task-oriented guides, examples, comments, docstrings, warnings/caveats, and troubleshooting notes. Owns whether an explanation is clear, complete, well-structured, and matched to its reader, not whether the underlying GAUSS code is syntactically valid, the underlying method is statistically appropriate, or the underlying code is well-designed.

**Scope (owns):** documentation clarity, reference structure, task-oriented usage guidance, examples and usage snippets, comments and docstrings, parameter/return-value explanation, input/output explanation, prerequisites and setup notes, assumptions and caveats, warnings and caution notes, troubleshooting notes, terminology consistency, audience awareness, reducing ambiguity, documentation completeness checks, transforming technical notes or code into user-facing documentation.

**Non-scope (does not own):** exact GAUSS syntax, verified GAUSS command signatures, the GAUSS package/base distinction, econometric model appropriateness, causal interpretation, statistical diagnostics, code maintainability/design as its primary domain, instructional sequencing over time as its primary domain, curriculum design, product strategy, release management, official GAUSS documentation authority.

**Activation triggers:** writing or improving documentation, explaining code for users, writing examples, writing comments/docstrings, documenting procedures/functions/inputs/outputs, explaining parameters/return values, creating usage notes, turning technical notes into user-facing docs, improving reference pages, writing troubleshooting guidance, reducing ambiguity, making documentation beginner-friendly without creating a full lesson plan, adding warnings/caveats/prerequisites, documenting assumptions, improving help text/README sections, reviewing docs for clarity/completeness.

**Non-activation cases:** simple GAUSS syntax lookup only, exact command documentation retrieval only (unless rewrite/explanation is requested), pure econometric interpretation without documentation intent, pure code refactoring without documentation intent, pure education/lesson planning, curriculum design, product strategy, general prose editing unrelated to technical/product documentation, non-technical release-note writing, CI guard questions without a clarity angle, unrelated factual questions.

**Boundary rules:**
- The Documentation Expert may improve wording, structure, examples, comments/docstrings, troubleshooting guidance, and user-facing usage notes.
- It may **not** invent GAUSS syntax.
- It may **not** certify statistical validity.
- It may **not** certify code maintainability or design quality.
- It may **not** claim code or tests were executed unless they actually were.
- **Clear documentation is not evidence of syntax correctness, statistical validity, or maintainability** — documentation clarity is an independent claim from all three.
- **Documentation supports task completion and reference use; Education supports learning over time** through sequencing, scaffolding, exercises, and pedagogy — making a single piece of documentation beginner-friendly is not curriculum design.

**Relationship to GAUSS Language Expert:** GAUSS Language Expert owns implementation correctness; Documentation Expert owns explanation clarity. Examples must use verified syntax or be labeled pseudocode/unverified.

**Relationship to Econometrics Expert:** Econometrics Expert owns methodological correctness; Documentation Expert owns clarity, caveat placement, and reader-facing structure for methodological content. A clearly worded caveat is never confirmation the underlying assumption holds.

**Relationship to Software Engineering Expert:** Software Engineering Expert owns maintainability/design; Documentation Expert owns comment/docstring clarity and structure. Good documentation never proves code is well-designed, and well-designed code may still need better documentation.

**Relationship to future Education Expert:** Documentation helps a reader complete a task or understand a reference right now; Education (not yet operationalized) would help a reader learn over time through sequencing, scaffolding, exercises, and pedagogy. Curriculum design remains out of scope for this expert.

## Four-Expert Routing Summary

Four classification axes now drive routing (`workflows/expert-routing.md` Step 1):

1. GAUSS implementation
2. Econometric methodology
3. Software engineering/code quality
4. Documentation/explanation quality

**Routing-pattern approach:** any subset of the four operational experts may activate. Rather than enumerating all 2⁴ = 16 mathematically possible combinations, `expert-routing.md` Step 4 gives a **compact 12-row activation matrix** plus a general coordination rule for any combination without its own named row — deliberately not a full 16-combination routing engine. Implementation, methodology, maintainability, and documentation claims must remain separate when more than one expert activates; the strictest applicable evidence/context requirement wins; routing remains documented/manual-evaluation-driven, not runtime orchestration.

Common patterns documented with worked examples:

- Documentation-only
- GAUSS + Documentation
- Econometrics + Documentation
- Software Engineering + Documentation
- GAUSS + Software Engineering + Documentation
- GAUSS + Econometrics + Documentation
- All four
- Neither

(Two pre-existing non-documentation combinations — GAUSS + Econometrics, and Econometrics + Software Engineering — are kept as prose-only worked examples from `v0.14.0` rather than duplicated as matrix rows, since they don't involve the new fourth axis.)

- `agents/code-assistant/task_modes.md` — all ten task modes now state whether and why the Documentation Expert activates for that mode (strong activation for Documentation and Code Explanation modes; conditional for the rest); the Cross-Mode Validation checklist was extended for the four-expert routing pattern.
- `prompts/code_assistant_system.md` — "Identify the relevant expertise" now names all four operational experts and the activation-matrix pattern; the "Cross-Expert Guardrails" section gained documentation-specific bullets.

Summary of what changed in Code Assistant behavior:

- The Code Assistant now considers the Documentation Expert for documentation clarity, examples, comments/docstrings, reference structure, usage guidance, troubleshooting notes, warnings/caveats, parameter/return explanations, README/help text, and audience clarity.
- GAUSS syntax remains owned exclusively by the GAUSS Language Expert.
- Statistical/methodological claims remain owned exclusively by the Econometrics Expert.
- Maintainability/design claims remain owned exclusively by the Software Engineering Expert.
- Pseudocode or unverified examples must be labeled clearly rather than presented as confirmed GAUSS.
- Tests or checks must never be presented as already run.
- The Documentation Expert remains explicitly distinct from the future (not-yet-operationalized) Education Expert.

## Important Findings

- The Code Assistant now has four separable correctness dimensions — implementation correctness (GAUSS Language Expert), methodological correctness (Econometrics Expert), maintainability/design correctness (Software Engineering Expert), and documentation/explanation correctness (Documentation Expert) — each independently checkable and none substitutable for another.
- The Documentation Expert improves examples, comments, usage guidance, and reference clarity without weakening any existing GAUSS evidence requirement; every `22.x` run that touched GAUSS syntax either used verified evidence (`meanc`/`stdc` treated as baseline-known, `glm` grounded in real local evidence) or explicitly caveated unverified details (missing-value handling, `packr`'s exact signature, `glmParameters`' internal fields).
- Four-expert routing remains readable when expressed as axes, a compact activation matrix, and worked common patterns rather than a full 16-case enumeration — the discipline held throughout the actual benchmark evaluations.
- All-four routing (`22.5`) is viable in practice: a single response organized into four labeled sections kept implementation, methodology, maintainability, and documentation recommendations independently identifiable, with an explicit closing statement that none of the four validates any of the others.
- The Documentation Expert was confirmed distinct from the future Education Expert in practice (`22.6`): the Code Assistant gave a genuinely useful curriculum outline while explicitly flagging that sequencing/pedagogy is not backed by an operationalized expert, and correctly scoped the Documentation Expert to individual reference-material clarity only.
- Neither-expert routing (`22.8`) remains important and still holds correctly with four experts available — a benchmark category's own name ("Documentation Expert Foundation") was not itself an activation trigger for a plain marketing-writing task.

## Remaining Limitations

- No runtime orchestration exists for any expert or routing combination — all routing remains a documented reasoning procedure checked by manual evaluation.
- Education and Product experts remain narrative-only/placeholder perspectives, not operationalized with their own profiles.
- The Documentation Expert does not validate GAUSS syntax independently — exact syntax claims still require the GAUSS Language Expert and official-doc-backed evidence.
- The Documentation Expert does not validate statistical methodology independently — model/estimator appropriateness still requires the Econometrics Expert.
- The Documentation Expert does not validate maintainability/design independently — that still requires the Software Engineering Expert.
- Documentation clarity is not correctness evidence — a well-written page can still describe invalid syntax, unsupported methodology, or poorly designed code.
- Testing advice from any expert is not execution — no run in this milestone claimed a test was actually run.
- Evidence validation is structural, not semantic or execution validation — a schema-valid evidence object is not proof of correct GAUSS behavior.
- GAUSS code is not executed anywhere in this framework as of this milestone.
- Strict-mode evidence validation and tracking guards still have the same documented warning-promoted-to-failure cases (`glm`/`olsmt` HDF5-URI path warnings; two historical tracking warnings) as every prior milestone.
