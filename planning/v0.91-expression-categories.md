## 1. Why

81.x passed 12 of 12 tasks, but the thing that most often kept valid code from running was a rule gauss-ai applies by design: **expressions are never evaluated.** An argument written as an expression (`ones(rows(x), 1)`, `meanc(x ~ y)`, `asdf(y ~ x1 ~ x2, …)`) leaves that parameter's role `UNKNOWN`, so the code stays `review_required`, and the client rewrote working code with literals to get a run (81.5, 81.8).

Expressions do not need to be *evaluated* to know their *category*. `rows(x)` is a scalar because `rows.rst` documents a scalar return; `ones(5, 1) ~ x1 ~ x2` of numeric operands is a numeric matrix; `x'x`, `s2 * invpd(x'x)` and `(x .< 2) .or (x .> 8)` are numeric. The role check asks only "can this argument be the documented type?", which a category answers.

| # | Item | Effect today | Measured |
|---|---|---|---|
| A | Expression arguments have no category | valid code stays `review_required` (81.5, 81.7, 81.8) | 89 expression gaps in 79 review_required programs; 19 programs have no other gap |

Goals:
- an argument expression gets a **category** (never a value) whenever every operand's category is known, so a documented type can be confirmed without evaluating anything;
- such a category can confirm a role (`MATCH`) but never refute one (`MISMATCH`), so it can only remove false gaps, never add a false block;
- nothing reaches `handoff_candidate` that is I/O, and every program that moves there is spot-checked in GAUSS.

Constraints (all from `CLAUDE.md`):
- deterministic: categories come from literals, traced assignments, documented return types and fixed operator rules; no model, no score, no evaluation;
- every scan reads `lex_gauss_source(...)`'s masked view and `source_statements(...)` (the lexical-discipline rule); no regex over raw text;
- preconditions stay exactly as they are: `invpd(x'x)` remains `unverified`, so its code stays `review_required` (a category says nothing about symmetry or definiteness);
- the system-statement and dataset-argument registries (including `library`, until v0.92.0), the generation gate and grounding are unchanged.

Out of scope:
- evaluating any value, shape or dimension;
- prose-typed parameters (`olsmt.rst`'s `depvar`, `asdf.rst`'s names) and the Inputs cut (`ctl` of `olsmt`): documentation-extraction changes for a later milestone (81.x findings 1, 4);
- named default arguments (v0.90 class C);
- string expressions (`$+`): unchanged, never a numeric category;
- package functions and `library` (v0.92.0);
- the analysis-workspace milestone.

### 2.3 How categories are resolved today

`resolve_argument_category_with_cause(...)` classifies:
- a **literal** (`{1 2}`, `2`, `"a"`);
- a **simple identifier**, traced to its governing assignment: a literal there is `TRACED_LITERAL`, and a single documented call there is `DOCUMENTED_RETURN`, using the call's documented `:rtype`.

Anything else is `argument_expression`, and an identifier assigned from anything else is `argument_assigned_from_expression`. A `DOCUMENTED_RETURN` category can `MATCH` but never `MISMATCH` (v0.81.0: a documented "matrix" return may be 1x1 at run time). This milestone reuses exactly that guard for expressions.

## 3. Proposed design

### 3.1 Expression categories

A new `infer_expression_category(text, *, code, line_number, column, signatures)` reads the argument (or the governing right-hand side) as tokens from the masked view and returns a category, or `UNKNOWN`:
- **Operands:** a numeric literal or brace literal (its existing category); a traced identifier (the existing tracing, recursively bounded); a documented call (its documented `:rtype`, as `DOCUMENTED_RETURN`); a parenthesized sub-expression; an indexed operand (`x[., 2]`) of a numeric operand, which is numeric.
- **Operators, all numeric in and numeric out:** `+ - * / ^ %`, the element-wise `.* ./ .^`, transpose `'` and `.'`, the concatenations `~` and `|`, the comparisons (`< <= > >= == !=`, with or without the `.`) and the word operators (`and or not xor eqv`, with or without the `.`), using the existing `_WORD_OPERATORS` list, and unary minus.
- **Result:** if every operand is numeric (`scalar`, `vector` or `matrix`), the expression is **`matrix`**: the most general numeric category, since shapes are never computed. Otherwise (a string operand, a `$` operator, an unknown or undocumented call, an untraced name, anything unparsed) it is `UNKNOWN`, with the existing cause.
- **Origin:** a new `ArgumentOrigin.EXPRESSION_CATEGORY`, which, like `DOCUMENTED_RETURN`, can `MATCH` but never `MISMATCH`. So against a documented `matrix` (which accepts vector and scalar) an expression confirms the role. Against a documented `scalar`, `string` or `control` it stays `UNKNOWN` with a new cause, `expression_category_imprecise`, never a mismatch.
- **Bounds:** at most 64 tokens of nesting and 3 levels of identifier tracing per argument; past either bound, `UNKNOWN`.
- **What it changes:** only `resolve_argument_category_with_cause(...)`'s answer for an expression or an expression-assigned identifier, so only role checks, and so only the `parameter_role_check` coverage dimension. Preconditions, syntax, symbols and the registries never read it.

`rows(x)` (documented `scalar`) passed to `ones(r, c)` (documented `scalar`) is the one place a direct documented scalar return matters. A single call is `DOCUMENTED_RETURN` with its exact documented category, as for a traced variable today, so `ones(rows(x), 1)` confirms.

### 3.2 What does not change

The generation gate and grounding; preconditions and their checkers; the syntax rules; the system-statement and dataset-argument registries; the execution handoff and the MCP tool surface.

## 5. Known limitations this design accepts

- **A category is not a shape.** `ones(n, 1) ~ x1 ~ x2` is "a numeric matrix", not "an n×3 matrix", so dimension errors are still found only by GAUSS (31 of v0.90's 61 upward probes failed on values).
- **Only `matrix`-accepting parameters are confirmed by an expression.** A documented `scalar` parameter given `n - 1` stays `UNKNOWN` (`expression_category_imprecise`), because "numeric" is not "scalar".
- **Preconditions still need literals.** `invpd(x'x)` stays `unverified`, so OLS written with `invpd` stays `review_required` (expected: `runtime_dependent`, 14 gaps in §2.1).
- **Package code is unchanged** until v0.92.0 (§2.4).

## 9. Implementation and deviations from the approved plan

Implemented on 2026-10-29, on top of `v0.90.0` plus its records (HEAD `37acfd2`). Baseline for every comparison below: a `git archive` of `37acfd2`'s `scripts/` (`607c6ea` and `37acfd2` differ only in records). The docs copy is the one fetched on 2026-10-23. ### 9.1 As planned, and the deviations

- **§3.1 as planned:** `infer_expression_category(...)`, which returns an `ExpressionCategory` and reads the argument through `lex_gauss_source(...)`'s masked view (`_ExpressionReader`). Also as planned: `ArgumentOrigin.EXPRESSION_CATEGORY`, `RoleUnknownCause.EXPRESSION_CATEGORY_IMPRECISE`, the bounds `MAX_EXPRESSION_TOKENS = 64` and `MAX_EXPRESSION_TRACE_DEPTH = 3`, and the never-MISMATCH guard in `_positional_role_checks(...)`, next to `DOCUMENTED_RETURN`'s.
- **Deviation 1: `resolve_argument_category_with_cause(...)` is unchanged; a new role-only wrapper adds the categories.** §3.1 said only that function's answer would change. But the `v0.89.3` dataset-argument registry (`_computes_in_memory(...)`) also calls it, so changing it would have changed an I/O decision: `olsmt(x ~ y, y, x)` would have become in-memory. The categories therefore live in a new `resolve_role_argument_category(...)`, which only `_positional_role_checks(...)` calls. The registry and the precondition tracer are provably untouched (§9.5; invariance test 198).
- **Deviation 2: operands are traced at their own statement.** For a variable assigned from an expression, the operands are traced where that assignment is, not at the call. Otherwise `a = "s"; x = a ~ 2; a = 1; meanc(x)` would read `a` as the later number. `_governing_assignment(...)` returns only text and is shared with the precondition tracer, so it is left unchanged. A new `_governing_statement_start(...)` only locates the statement it chose, and refuses unless that statement's right-hand side is the same text.
- **Deviation 3: how the bounds are read.** 64 tokens count every operand, operator and postfix at every parenthesis level. A call's argument list, an index `[...]` and a `{...}` literal each count as one token, because their contents never decide the category. "3 levels of tracing" means at most three assignments are followed from the argument to an operand's own expression.
- **Deviation 4: the operator set, made exact.** As §3.1, plus unary `not`/`.not` (a word operator that is only unary). Not accepted, so they give `UNKNOWN`: `^` as a prefix (GAUSS's string dereference, `operators.rst`), `&`, `:` outside an index, `!`, `.*.` (Kronecker, not in §3.1's list), unary `+`, and member access. The implicit product `x'x` is read only with no space (`x' x` is `UNKNOWN`). An index that holds a string (`df[., "col"]`) refuses.
- **Deviation 5: gap texts name the reason.** `argument_expression` and `argument_assigned_from_expression` no longer say that expressions are never evaluated. They name the operand or construct that stopped the inference ("operand `w` has no single traceable assignment earlier in this code", "it uses a string operator (`$`)"). The cause values are unchanged.
- **Deviation 6: the measured set is larger than §2.1's.** It has 581 programs. That is the 398 the v0.90 corpus script now finds (more run files exist), plus every distinct `gauss_validate_code` input recorded in this machine's Claude Code transcripts, the empty-folder 80.x and 81.x sessions among them. The gate set has 951 questions (927 at v0.90; more transcript queries since).
- **Finding 1: real OLS with standard errors passes the trace bound.** In `X = ones(rows(x), 1) ~ x; b = invpd(X'X) * X'y; e = y - X * b; s2 = e'e / (rows(X) - cols(X)); se = sqrt(diag(s2 * invpd(X'X)));`, `diag`'s argument is four assignments from `X` (`s2 → e → b → X`). So it is `argument_expression` ("traced through more than 3 assignments"). The verdict is the same either way, `review_required`, because `invpd`'s precondition is unverified. §7's expectation is corrected, and the bound is kept as approved. Raising it (to 5 or 6) is cheap and would only remove that gap; it is a candidate for 82.x's recommendation.
- **Finding 2: an expression can now confirm a structure-function argument whose code then fails on the structure.** p436 (`par1 = pvCreate(); par1 = pvPack(par1, 1 | 2, "b");` with no `struct PV par1;`) reaches `handoff_candidate`, and GAUSS 26.1.4 stops with `G0181 Illegal assignment - type mismatch`. At v0.90 its only gap was `1 | 2`. The category is right: GAUSS needs the declaration, which is the disclosed "structure types are not modelled" class (`KNOWN_LIMITATIONS.md`, v0.86.0). With the declaration (p437) it runs.

### 12.4 Findings

1. **The 3-assignment trace bound now drives rewrites** (§9.1 finding 1, live). In 82.2, `sqrt(diag(vcv))` and `sqrt(s2 .* d)` stayed unknown at the bound. The client replaced `sqrt(...)` with `(...) .^ 0.5`, because operator operands are never role-checked. So the bound makes the function form weaker than the equivalent operator form. The recording session measured the bound each version needs (by patching `MAX_EXPRESSION_TRACE_DEPTH` in memory on the archive): the client's second version (`c04`, `sqrt(s2 .* d)`) reaches handoff_candidate at 5, and its first (`c03`, `sqrt(diag(vcv))`, whose longest chain is `vcv → s2 → u → b_hat → Xty → y → X`) at 7. So §9.1's suggested 5 or 6 covers the shortened program but not the client's natural first draft; a follow-up should take its bound from this kind of evidence and the usual verdict diff.
2. **`vector`-typed parameters cannot be confirmed by an expression** (by design, decision 1a; undisclosed for `vector`). `selif(x, (x .>= 3) .and (x .<= 7))` and `indexcat(x, v)` stayed unknown because `e` and `x` are documented as `vector`; the client fell back on a sort-and-slice workaround that is fragile when the range is empty (e01). Same class as decision 1(c)'s scalars; `KNOWN_LIMITATIONS.md` named only `scalar` and now names `vector` too.
3. **A typed declaration is never a traced assignment** (pre-existing, safe-direction, undisclosed until now). `string names = { "y", "X1", "X2", "X3" };` gave "`names` has no single traceable assignment" (82.6); so do `string s = "a";` and `matrix y = x;` at `v0.90.0` and `v0.91.0`. Spot checks td01-td07 show GAUSS reads the initializer as a literal: `x = 4; matrix y = x;` makes `y` the character constant "X" (prints `+DEN`), and `s = "a"; string t = s;` prints `S`, in GAUSS 26.1.4 and 27.0.0. So a later rule could trace a typed declaration with a literal initializer, and could flag a name initializer as almost certainly a mistake. Added to `KNOWN_LIMITATIONS.md`.
4. **"Validation coverage is broad" can be reached by moving work into unchecked operators** (client's opinion; known). 82.1's `invpd` → `/` uses the disclosed v0.87.0 limitation (a runtime divisor is never checked); 82.2's `sqrt` → `.^ 0.5` is finding 1. Neither produced a wrong result. The wording says what was checked, not that the code is correct, and the prompt says execution success does not establish validity; no change recommended beyond finding 1.
5. **`gmmfit.rst` documents wrong output member names** (upstream documentation). It lists `gOut.parEst` and `gOut.numParms`; GAUSS 26.1.4 rejects both (`G0504`) and accepts `gmmFitIV`'s `paramEst` and `numParams` (gm01-gm04). For Aptech, with the `dotor` issue.
6. **Package code is the next wall** (planned, v0.92.0). 82.13's lasso program is correct and runs, but `library gml;` keeps it not_ready. The client used the shell to confirm GML is installed (82.12), which gauss-ai cannot report.
