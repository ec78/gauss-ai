# v0.57.0 - Repair Approval Mechanism (Design Phase)

## Release Goal

Define and implement the approval mechanism `requires_explicit_approval` has only documented since `v0.56.0`, without implementing repair application. Chosen over the alternative candidate (durable execution sessions) — see "Rationale" below, carried forward from the planning memo that authorized this milestone.

## Rationale (from the authorizing planning memo)

Durable execution sessions (`scripts/gauss_execution_session.py`, `v0.40.0`) are real, previously-scoped work with a complete design already written (`planning/v0.47.0-session-integration-readiness.md`), but nothing in this repository currently needs them — the CLI adapter is single-process/single-turn, and repair planning is already a pure function needing no session state. They were correctly deferred in `v0.47.0` for exactly this reason, and nothing new since then created a consumer for them.

The approval mechanism, by contrast, directly extends the pipeline stage `v0.56.0` just shipped: `requires_explicit_approval` was a computed-but-unread field. Defining what an approval *is* — hash-bound to a specific plan, explicit, single-use, revocable — needed no durable-session prerequisite: it could reuse the same process-local, hash-bound discipline `gauss_execution_workflow.WorkflowConfirmationEvent` already established for execution confirmation. That is exactly what this milestone did.

## Architecture

```
RepairPlan (from gauss_repair_planner.py, v0.56.0)
    -> repair_plan_digest(plan) -> str        (new in v0.56.0's own module, this milestone)
    -> explicit ApprovalDecision (approve/decline), hash-bound to that digest
    -> ApprovalRecord (single-use, process-local, revocable)
```

`scripts/gauss_repair_approval.py`'s `RepairApprovalStore` is the single stateful component this milestone adds — an ordinary in-memory `dict[str, ApprovalRecord]`. It is pure and deterministic except for that one piece of state, and has zero import of `gauss_code_execution`, `gauss_workspace`, `gauss_runtime_orchestration`, `gauss_execution_adapter`, `gauss_execution_workflow`, `gauss_execution_session`, or `gauss_orchestration_state_store` — verified structurally, not merely by convention (`test_09_approval_module_has_no_forbidden_imports`).

`repair_plan_digest(plan) -> str` lives in `gauss_repair_planner.py` itself (the plan's own identity is that module's responsibility, not the approval layer's) and follows `gauss_runtime_orchestration.compute_request_hash`'s existing convention exactly: a canonical dict over every field in fixed order, `json.dumps(..., sort_keys=False, ensure_ascii=True, separators=(",", ":"))`, then SHA-256. No new hashing scheme was invented.

## Approval Model

`ApprovalDecision` (enum): `approved`, `declined`.

`ApprovalRecord` (frozen dataclass): `decision`, `plan_digest`, `recorded_at` (caller-supplied, e.g. the adapter's injectable `clock()` — never computed internally, keeping the module pure), `source_error_code`, `source_error_category`, `repair_status`, `safe_to_apply` (always `False`), `safe_to_prepare_draft` (always `False`), `approval_boundary` (fixed disclosure string).

`RepairApprovalStore`: `approve(plan, recorded_at)`, `decline(plan, recorded_at)`, `get_decision(plan)`, `get_decision_for_digest(plan_digest)`, `revoke(plan)`, `__len__`.

## Hash-Binding and Staleness

Any change to any field of a `RepairPlan` — a different strategy, a different piece of supporting evidence, a different piece of supplied source context — produces a different digest. There is no separate "invalidate this approval" step: `get_decision(plan)` looks up by the plan's *current* digest, so a decision recorded against a since-changed plan is simply not found. This mirrors how a stale `request_hash` already fails to match a changed execution proposal elsewhere in this repository, rather than inventing a new staleness concept.

## Single-Use, Non-Overwriting, Revocable

`approve`/`decline` raise `ApprovalConflictError` if a decision already exists for that digest — a decision is never silently overwritten. `revoke(plan)` is the only sanctioned way to replace one (returns `True`/`False` depending on whether a record existed). Tested explicitly: `test_07_re_approval_or_overwrite_behavior` covers approve-then-approve, approve-then-decline, revoke, and re-record after revoke.

## Safety Boundary

- `safe_to_apply`/`safe_to_prepare_draft` are `False` on every `ApprovalRecord` — the same critical, structurally-tested invariant `v0.56.0` established for `RepairPlan` itself, now proven independently for the approval layer.
- The module never reads or writes a file, never launches GAUSS, never mutates workspace state, never creates a new execution proposal — same verification method as `gauss_repair_planner.py` (source-inspection tests, not convention).
- `APPROVAL_BOUNDARY_STATEMENT` is a fixed, always-present disclosure identical on every record: *"This records an explicit human decision about a specific repair plan. It does not apply, patch, or prepare a draft of any change. No code was modified. No file was written. GAUSS was not rerun."*
- No LLM-based approval reasoning, no auto-approval, no inference from plan confidence.

## CLI Integration

`approve-repair <plan_digest>` / `decline-repair <plan_digest>`. Both operate against `InteractiveMvpAdapter.last_repair_plan` — the exact `RepairPlan` object the adapter's most recent `repair-plan` call produced, never a freshly recomputed one (source-context CLI flags are not remembered between calls, so recomputation could silently diverge from what the user actually saw and is deciding about). `repair-plan`'s own output now shows `plan_digest` and, whenever `requires_explicit_approval` is `True`, a `next_step` line naming both commands. Supplying a digest that does not match `last_repair_plan`'s own current digest is rejected with `ERROR stale_or_incorrect_digest` plus the correct current digest. `reset` clears `last_repair_plan` and creates a fresh `RepairApprovalStore`.

## Testing

- `scripts/test_gauss_repair_approval.py`: 14 tests — digest determinism/stability/sensitivity (3, cross-checked against the dedicated digest tests in `test_gauss_repair_planner.py`), core store scenarios (matching-digest approval, stale-digest rejection, decline, conflict/revoke/re-record, multiple independent plans, unknown-error plans), boundary/purity (forbidden imports, no file I/O), and process-locality.
- `scripts/test_gauss_repair_planner.py`: 5 new tests for `repair_plan_digest` itself (determinism, cross-computation stability, sensitivity to source context and to error code, SHA-256 format).
- `scripts/test_gauss_code_assistant_cli.py`: 9 new tests — `approve-repair` before/after a plan exists, stale digest (including the specific case where a second `repair-plan` call with different source context supersedes the first), decline path, conflict-without-revoke, missing-argument usage error, `reset` clearing both plan and approval state, and a regression check that ordinary `repair-plan` output (including for `successful_execution_no_repair_needed`) is unaffected by the new layer.
- Full existing regression suite (16 required suites, 550+ pre-existing test functions) re-run and passing unchanged.

## Out of Scope (unchanged from the authorizing task)

Patch application, file editing, source rewriting, replacement-code generation, automatic code correction, draft preparation, automatic source-context collection, autonomous retry, autonomous execution, durable or cross-process approval persistence, session integration, conversational memory, chat adapters, LLM-based approval reasoning, repair execution. None implemented.

## Readiness Classification

Ready for continued structured alpha testing, now with a real, tested mechanism for recording repair-plan decisions. Not ready for repair application in any form — unchanged, explicitly out of scope, and structurally impossible for this module to drift into (no code path sets `safe_to_apply` to `True`, and nothing in the repository reads an `ApprovalRecord` toward any change).

**Recommended next milestone:** durable execution sessions remain a real, previously-scoped candidate, now closer to relevant since a future repair-application workflow would need to correlate an approval decision with the exact execution/plan it was derived from across turns — but no such workflow is authorized yet, so building session durability speculatively would repeat the exact pattern `v0.47.0` already correctly avoided. The more evidence-grounded next step is either (a) a genuinely scoped, explicitly-authorized Repair Application design (not implementation) that defines how an `ApprovalRecord` would gate a future patch-construction step, or (b) durable sessions, authorized specifically because Repair Application's own design turns out to need them. This milestone's own evaluation found zero defects, so refinement is not the forcing function either way.
