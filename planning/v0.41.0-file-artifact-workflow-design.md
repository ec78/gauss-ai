# v0.41.0 GAUSS File and Artifact Workflow Design

## Release Goal

`v0.41.0` defines the file and artifact architecture required for a user-facing GAUSS assistant that can move from:

> User provides code

to:

> User provides a GAUSS project workspace.

Define support for:

- project workspaces
- input files
- scripts
- datasets
- configuration files
- execution artifacts
- output metadata
- safe file interpretation workflows

**This milestone is design-only.** It does not: implement file handling; implement uploads; implement artifact storage; read user files; interpret output files automatically; change execution behavior. It does not modify the execution helper, create workspace code, create artifact storage, run GAUSS, add automatic execution, add runtime orchestration, change schemas, add benchmarks, change the system prompt, or create a release tag.

## Current State

**Already exists:**

- The execution helper (`scripts/gauss_code_execution.py`), verified `tgauss.exe -b <script_path>` invocation, Windows/GAUSS 26.1.1 only.
- The conversational execution workflow (`scripts/gauss_execution_workflow.py`) and in-memory execution sessions (`scripts/gauss_execution_session.py`).
- `output_files` metadata: path, size, type, `created_by_execution` tri-state, notes — never content.
- Generated-script exclusion: the helper's own inline-code script is excluded from `output_files`.
- Execution-aware analysis (`workflows/execution-aware-analysis.md`) — evidence/interpretation separation, expert routing, explicit deferral of file reading to a future workflow.
- Report generation (`workflows/report-generation.md`) — an evidence hierarchy that already ranks "explicitly read" above "metadata only."

**Missing:**

- A workspace abstraction — today, `working_directory`/`output_directory` are bare strings on a request; there is no tracked, identified, lifecycle-managed container.
- A file manifest — nothing enumerates what files exist in a workspace before or after execution beyond the helper's own post-execution `output_files` discovery.
- Artifact ownership — no concept of who created, who may read, or who may delete a file distinct from the underlying filesystem's own permissions.
- A safe file-reading workflow — `workflows/execution-aware-analysis.md` names this gap explicitly; it does not close it.
- A reproducibility model — no structured way to answer "what exactly produced this result," linking a workspace, its files, a confirmed request, a session, an instance, and any resulting report.
- A project lifecycle — today's model is one script per confirmed request; there is no concept of an ongoing, multi-file, multi-run project.

## Core Design Question

**How can the assistant safely move from executing isolated GAUSS scripts to handling complete GAUSS projects without weakening file security, user control, or evidence boundaries?**

Every section below is evaluated against this question first, exactly as `v0.38.0`/`v0.39.0` evaluated their own designs against their respective core questions. A design that answers it by widening filesystem access, blurring metadata/content, or reading files without a distinct, later, explicit step is rejected regardless of convenience.

## Workspace Model

### Execution Workspace

A bounded environment containing: user inputs, GAUSS scripts, datasets, configuration files, generated scripts, execution outputs, and metadata.

**Workspace identity:**

- `workspace_id` — a new identifier, distinct from `execution_session_id`/`orchestration_instance_id`/`request_hash` (see "Relationship to Execution Sessions" below for why a fourth-ish identifier space is warranted, mirroring `v0.39.0`'s own resolution of the session/instance/request question).
- `owner/reference` — an opaque identifier, matching `ExecutionSession.owner`'s deliberately-unvalidated shape (ownership *rules* remain undesigned here too — see Artifact Ownership).
- `creation time`.
- `lifecycle state` — one of the seven states below.
- `allowed paths` — the bounded root(s) a workspace may ever read or write within; never a bare, unbounded filesystem root, and never expanded implicitly once set.

A workspace corresponds most closely to today's `working_directory`/`output_directory` pair, but is a tracked, identified object rather than two bare path strings — the same kind of upgrade `v0.36.0` gave the controller's in-memory-only state (tracked, identified, inspectable) without yet promising persistence or cross-process sharing (this document proposes neither).

## Workspace Lifecycle

States:

- `created`
- `populated`
- `ready`
- `executing`
- `completed`
- `archived`
- `deleted`

**Prohibited transitions** (explicit, matching the task's own examples and extended to the full lifecycle):

- `deleted → executing` — a deleted workspace can never be resurrected into an executable state.
- `unknown workspace → execution` — an execution attempt against a `workspace_id` with no tracked record must fail closed, exactly as `gauss_orchestration_state_store.RecordNotFoundError` already fails closed for an unknown `orchestration_instance_id`.
- `unauthorized workspace → access` — restated from Artifact Ownership: an access attempt without a passing ownership check must fail closed, once ownership rules exist (they do not yet — see Non-goals).
- `archived → executing` — an archived workspace is dormant, not resumable in place; a genuinely new run requires a new workspace (or an explicit, separately designed "reactivate" operation this document does not propose).
- `completed → populated` — files cannot be silently re-added to a workspace whose execution has already concluded; this would let a post-hoc file change retroactively alter what "produced" a completed result, violating the Reproducibility Model below.

**Where each state applies:** `created` (workspace identity allocated, empty); `populated` (input files/scripts/datasets/configuration present, not yet execution-eligible); `ready` (a workspace passes whatever validation a future eligibility layer defines — this document does not redefine `workflows/real-execution-user-workflow.md`'s own Execution Eligibility Decision, only notes that a `ready` workspace is a precondition input to it); `executing` (an Execution Instance, per `v0.39.0`'s vocabulary, is in flight against this workspace); `completed` (the instance reached a terminal outcome); `archived` (retained for audit/reproducibility but no longer active); `deleted` (workspace metadata retained per audit rules — see Auditability — but files are gone; a terminal, permanent state).

## File Manifest Model

A manifest tracks the files known to belong to a workspace:

```json
{
  "workspace_id": "ws_3f9c1a...",
  "files": [
    {
      "name": "model.gss",
      "type": "script",
      "source": "user",
      "size": 1234,
      "checksum": "sha256:...",
      "creation_state": "populated"
    },
    {
      "name": "data.csv",
      "type": "dataset",
      "source": "user",
      "size": 50000,
      "checksum": "sha256:...",
      "creation_state": "populated"
    },
    {
      "name": "gauss_output.txt",
      "type": "output",
      "source": "execution",
      "size": 19,
      "checksum": "sha256:...",
      "creation_state": "completed"
    }
  ]
}
```

**File metadata may include:** `name`, `type`, `size`, `checksum`/reference, `source`, `creation_state`. This deliberately mirrors — and does not replace — the existing `output_file` schema shape (`path`/`size_bytes`/`file_type`/`created_by_execution`/`notes`) for anything execution-produced; the manifest is a superset view across a whole workspace's lifetime, not a competing schema for one execution's own outputs.

**Do not automatically store:** secrets, credentials, unnecessary copies of files. A `checksum` reference is preferred over a stored copy wherever possible, mirroring `gauss_orchestration_state_store.digest_code(...)`'s existing "digest, not content" precedent — a manifest entry proves a file's identity without duplicating its bytes.

## Artifact Model

Three artifact categories, kept separate exactly as Execution Request/Session/Instance are kept separate in `v0.39.0`:

### Input Artifacts

Examples: GAUSS scripts, datasets, configuration files. **Source:** user-provided.

### Execution Artifacts

Examples: generated output files, logs, tables, figures. **Source:** execution — these are what `output_files` metadata already describes today; this model gives them a durable, workspace-scoped identity beyond one execution result object's lifetime.

### Derived Artifacts

Examples: reports, summaries, interpretations. **Source:** analysis workflow (`workflows/execution-aware-analysis.md`, `workflows/report-generation.md`) — never execution itself. A derived artifact is evidence of what an expert-routed interpretation *concluded*, not new execution evidence.

**Every artifact needs:** identity (a stable reference, workspace-scoped), ownership (see below), lifecycle (created → available → archived/deleted, a narrower version of the workspace lifecycle scoped to one file), metadata (per the File Manifest Model), and provenance (which of the three categories it belongs to, and — for execution/derived artifacts — a reference back to the Execution Instance or analysis step that produced it).

## File Security Boundaries

The assistant must:

- never access arbitrary user directories
- use bounded workspaces
- reject path traversal
- avoid writing outside the workspace
- avoid overwriting unrelated files
- validate file paths
- separate metadata from contents

**Preserve:** `output_files` metadata ≠ file contents — restated, not weakened, from every prior milestone back to `v0.25.0`.

These restate, at the workspace/artifact layer, exactly the boundaries `workflows/real-execution-user-workflow.md`'s Working Directory and File Rules and Pre-Execution Safety Review already establish for a single confirmed request. A workspace is a longer-lived container for the same bounded-directory concept, not a new, looser one — `allowed paths` (Workspace Model) is this design's name for what a single request's `working_directory`/`output_directory` pair already enforces today, generalized to persist across multiple files and (eventually) multiple execution attempts.

## Input File Handling

**How users might provide files** (design questions, not implemented):

- Are files uploaded? A future implementation would need a defined transport and size/type limits — not designed here.
- Are paths referenced? Referencing an existing on-disk path raises the same unresolved script-identity-fingerprinting gap `v0.31.0`/`v0.32.0` already left open for script-path execution — a future design must either resolve that gap or continue refusing path-reference mode, not silently reintroduce it through the workspace door.
- Are files copied into the workspace? Copying (versus referencing in place) is the safer default consistent with "bounded workspace" containment, but doubles storage and raises its own cleanup questions (see Risks).
- How is ownership tracked? Deferred to Artifact Ownership below — not resolved here.

**Do not implement.** This section names the open questions a future implementation milestone must answer; it does not answer them.

## Output File Handling

After execution, capture: filename, size, type, timestamp, provenance — extending, not replacing, the existing `output_file` schema fields.

**Do not automatically:** read contents, summarize contents, infer results. This restates `workflows/execution-aware-analysis.md`'s existing Handling Output Files rule verbatim.

**Require a separate workflow:** when the user asks "Explain this output file," the safe file-reading workflow (below) begins — output-file *metadata* capture and output-file *content interpretation* remain two distinct steps, never fused.

## Safe File Reading Workflow (Design for a Future Milestone)

**Before reading:**

- identify the requested file (by workspace-scoped manifest entry, never a bare, re-typed path)
- confirm permission/context (ties into Artifact Ownership's undesigned "who can view outputs" question — this workflow's own gate, not a bypass of it)
- validate the path (must resolve inside the owning workspace's `allowed paths`; reject traversal exactly as the existing safety review already requires for execution)
- identify the file type (to decide whether safe, structured reading is even possible — see binary-format risk below)
- avoid secrets (a file that appears to contain credentials/secrets should be flagged, not silently read and repeated back)
- avoid unsupported binary formats (a future implementation must refuse, not guess, when it cannot safely interpret a format)

**After reading:**

- distinguish contents from metadata (a read file's content is now genuine evidence, at the Evidence Hierarchy's top tier per `workflows/report-generation.md`; this must be visibly distinct from a metadata-only reference in any response)
- preserve evidence boundaries (a read file's content proves what that file contains, not code correctness or methodological validity — the same non-overclaim discipline as execution evidence)
- do not overclaim (reading a `.csv` header row is not the same as understanding a dataset's full content or quality; this workflow must not conflate the two)

This section names requirements for a future, separately authorized workflow document and implementation; `v0.41.0` implements none of it.

## Reproducibility Model

A future execution record should connect: workspace → files → execution request → execution session → execution instance → outputs → reports, so that "What exactly produced this result?" is answerable by following one reference chain rather than reconstructing it from memory or from scattered evidence.

This is additive to, not a replacement for, `v0.39.0`'s own model: a session's `reference_metadata` field (already present on `ExecutionSession`, currently an unstructured `dict[str, Any]`) is the natural place a future implementation would record a `workspace_id` reference — no change to `ExecutionSession`'s own field list is proposed here, since `reference_metadata` already accommodates this without modification.

## Relationship to Execution Sessions

- **Execution sessions** answer: "When and under what confirmation was this allowed to run?"
- **Workspaces** answer: "What files and artifacts were involved?"
- **Execution instances** answer: "What happened during this attempt?"

These remain separate, mirroring exactly the rationale `v0.39.0` gave for keeping Request/Session/Instance separate (differing cardinality, mutability, lifetime, and safety boundary — see that document's "Why these must remain separate"). A workspace may outlive any single session (a project reused across several confirmed runs); a session's own six-state lifecycle (`v0.39.0`) is not extended or modified by this document.

## Artifact Ownership

Future concepts only — **not designed in detail, not implemented, by this milestone** (mirroring `v0.38.0`'s own explicit deferral of ownership):

- workspace owner
- artifact owner
- generated artifact ownership
- cleanup responsibility

Open questions for a future phase: who can access outputs? who can delete artifacts? how long are artifacts retained?

Today, `ExecutionSession.owner` is an opaque, unvalidated string with no enforced rules (per `v0.39.0`/`v0.40.0`'s own disclosed limitation). A future workspace-level `owner`/`reference` field should be held to the same honesty: present, but not yet a real access-control mechanism, and never represented as one.

## Report Generation Integration

Report generation (`workflows/report-generation.md`) may consume: execution results, artifact metadata, and explicitly read files (once the Safe File Reading Workflow exists). **Metadata alone does not authorize content claims** — restated directly from that workflow's own Evidence Hierarchy, which already ranks "output file metadata, but not file contents" below "explicitly read." This document does not change that ranking; it gives the "explicitly read" tier a concrete future workflow to be produced by.

Proposed future `42.x` "File and Artifact Workflow" benchmark examples (**not added by this milestone**):

7. User asks to reproduce a prior result.
8. User asks whether an output file proves model validity.

## Risks

- Accidental file exposure.
- Path traversal.
- Sensitive data persistence.
- Artifact ownership confusion.
- Output interpretation overreach (treating metadata, or a partial read, as a full content claim).
- Large files (no size-limit policy is designed here).
- Binary formats (no safe-parsing policy is designed here).
- Cleanup failures (a deleted workspace whose files were not actually removed).
- Workspace leakage (files from one workspace becoming visible to another).
- Stale artifacts (an archived workspace's files outliving their usefulness with no retention policy).

## Non-Goals

- Automatic file reading.
- Arbitrary filesystem access.
- Cloud storage.
- Production artifact management.
- Multi-user permissions.
- Report publishing.
- A data governance system.
- Autonomous project execution.
