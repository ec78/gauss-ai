# v0.17.0 Readiness Checklist

## Release Goal

`v0.17.0` operationalizes the Product Expert as the sixth operational expert the Code Assistant explicitly routes through. It adds user problem framing, workflow fit, first-use experience, activation, time-to-value, adoption barriers, value proposition, positioning, prioritization, scope tradeoffs, discovery questions, product assumptions, and product risk reasoning as a distinct, checkable correctness dimension — independent of whether the underlying GAUSS code is syntactically valid, the underlying method is methodologically sound, the underlying code is well-designed, a single piece of content is clearly documented, or a learning experience is well-sequenced.

The Code Assistant now routes through six operational experts:

- **GAUSS Language Expert** — implementation correctness.
- **Econometrics Expert** — methodological correctness.
- **Software Engineering Expert** — maintainability/design correctness.
- **Documentation Expert** — documentation/explanation correctness.
- **Education Expert** — education/learning-design correctness.
- **Product Expert** — product/user-value correctness.

Routing remains documented and manually evaluated, not runtime orchestration. No code parses or enforces `workflows/expert-routing.md`, any `OPERATIONAL_PROFILE.md`, `workflows/code-assistant-response.md`, `agents/code-assistant/task_modes.md`, or `prompts/code_assistant_system.md` at runtime; a response is checked against them manually, the same way task-mode fit is checked today.

## Product Expert Summary

**Purpose:** guide agents on product reasoning and user-value framing — whether a feature or capability actually solves a real user problem, fits a real workflow, and has a credible path to adoption.

**Scope (owns):** user problem framing, customer/job-to-be-done framing, workflow fit, user journey, first-use experience, activation and time-to-value, adoption barriers, value proposition, positioning, product requirements framing, prioritization tradeoffs, scope tradeoffs, feature usefulness, customer segment fit, persona/use-case alignment, user success criteria, product assumptions, product risk identification, feedback loop design, product discovery questions, MVP/scope reasoning, adoption and retention considerations, go-to-market handoff considerations at a high level.

**Non-scope:** exact GAUSS syntax, verified GAUSS command signatures, the GAUSS package/base distinction, econometric model appropriateness, causal interpretation, statistical diagnostics, code maintainability/design as a primary domain, documentation/reference clarity as a primary domain, learning-design correctness as a primary domain, instructional sequencing, release management, official GAUSS documentation authority, guaranteed market outcomes, pricing/legal/security decisions as final authority.

**Activation triggers:** product strategy, product positioning, user problem framing, customer problems, jobs to be done, workflow fit, user journey, onboarding-as-product-experience, first-use experience, activation, time-to-value, adoption barriers, feature prioritization, feature usefulness, value proposition, customer segment fit, product requirements, product scope, MVP framing, product tradeoffs, user feedback interpretation, product discovery questions, user success criteria, release impact framing, roadmap tradeoffs, product risk assessment.

**Non-activation cases:** simple GAUSS syntax lookup only, exact command documentation retrieval only, pure econometric interpretation without product/user-value intent, pure code refactoring without product/user-value intent, pure documentation/reference writing without product/user-value intent, pure education/lesson planning without product/user-value intent, general prose editing unrelated to product strategy or user value, release-note writing unless product positioning or user-impact framing is requested, CI guard questions unless product risk or user impact is involved, simple factual questions unrelated to product reasoning.

**Boundary rules:**

- May frame user problems, jobs to be done, workflow fit, adoption risks, time-to-value, value propositions, positioning, discovery questions, prioritization tradeoffs, scope recommendations, product assumptions, and product risks.
- May not invent GAUSS syntax.
- May not certify statistical validity.
- May not certify code maintainability or design quality.
- May not certify documentation/reference clarity.
- May not certify learning-design quality.
- May not guarantee market outcomes, adoption, retention, willingness to pay, product-market fit, or prioritization certainty without evidence.
- May not claim execution.
- Product value is not evidence of syntax correctness, statistical validity, maintainability, documentation quality, or education quality.
- User demand is not evidence of statistical validity.
- Product urgency is not evidence that design risk is acceptable.
- Good documentation or training is not proof of product value.
- Product hypotheses must be labeled as hypotheses when evidence is missing.

**Relationship to GAUSS Language Expert:** implementation correctness stays with the GAUSS Language Expert; Product may frame whether a GAUSS-related feature appears useful but never invents or approves GAUSS syntax.

**Relationship to Econometrics Expert:** methodological correctness stays with the Econometrics Expert; Product may reason about the user value of an analysis feature but never certifies statistical validity.

**Relationship to Software Engineering Expert:** maintainability/design correctness stays with the Software Engineering Expert; Product may treat technical debt as a product-risk input to a tradeoff but never certifies code design.

**Relationship to Documentation Expert:** documentation/reference clarity stays with the Documentation Expert; Product owns positioning and value proposition, and may recommend documentation as an adoption support, but never certifies documentation quality.

**Relationship to Education Expert:** learning-design correctness stays with the Education Expert; Product owns whether a feature is worth building/teaching/documenting and how onboarding fits the overall product experience, but never certifies learning-design quality — good training may support adoption but never proves a feature is valuable or should be prioritized.

## Six-Expert Routing Summary

Six classification axes (`workflows/expert-routing.md` Step 1):

1. GAUSS implementation
2. Econometric methodology
3. Software engineering/code quality
4. Documentation/explanation quality
5. Education/learning-design quality
6. Product/user-value quality

Any subset of the six experts may activate. Rather than enumerating all 64 mathematically possible combinations, Step 4 documents a compact 16-row activation matrix plus 36 worked routing examples, governed by coordination principles (claims stay separable; the strictest applicable evidence/context requirement wins) for any combination without its own named row. This is the same "readable at N combinations, not a combinatorial engine" discipline `v0.14.0` committed to at eight, `v0.15.0` extended to twelve, and `v0.16.0` extended to fourteen, now extended to sixteen.

Common patterns documented: Product-only, Product + Documentation, Product + Education, Product + GAUSS, Product + Econometrics, Product + Software Engineering, Documentation + Education + Product, GAUSS + Documentation + Education + Product, GAUSS + Econometrics + Product, all six, and Neither. Pre-existing five-expert-era combinations without a product dimension (GAUSS + Education, Econometrics + Education, Documentation + Education, Software Engineering + Education, GAUSS + Documentation + Education, Econometrics + Documentation + Education, GAUSS + Econometrics + Documentation + Education, all five) and older four-expert-era combinations remain covered as prose Routing Examples rather than duplicated matrix rows.

Implementation, methodology, maintainability, documentation, education, and product claims must remain separate and separately attributable, even within one coherent response. Routing is documented/manual-evaluation-driven, not runtime orchestration — no engine executes `workflows/expert-routing.md`.

## Important Findings

- The Code Assistant now has six separable correctness dimensions: implementation correctness, methodological correctness, maintainability/design correctness, documentation/explanation correctness, education/learning-design correctness, and product/user-value correctness.
- The Product Expert adds user-value reasoning (problem framing, workflow fit, adoption, positioning, prioritization) without weakening any GAUSS evidence requirement, econometric context requirement, maintainability context requirement, documentation context requirement, or learning-design context requirement.
- The Product Expert adds product framing without replacing the Documentation Expert or the Education Expert — both boundaries are directly benchmark-tested (`24.2`, `24.3`, `24.7`) and all three passed.
- The Product Expert helps identify adoption risks, workflow fit, assumptions, and discovery questions, but never proves product-market fit or market demand — every run that touched a product-value claim explicitly labeled it as a hypothesis or named the evidence gap rather than asserting it as settled.
- Six-expert routing remains readable when expressed as axes, a compact activation matrix, and worked common patterns rather than a full 64-case combinatorial engine.
- All-six routing is viable when implementation, methodology, maintainability, documentation, education, and product claims remain separately attributable.
- Neither-expert routing (`24.8`) remains important to avoid over-applying expert machinery to ordinary writing tasks — this held even though the prompt's own benchmark category name ("Product Expert Foundation") could tempt an evaluator to look for product content that should not be there.
- A significant pre-existing documentation-hygiene gap was discovered and fixed during this readiness task: `experts/software-engineering/OPERATIONAL_PROFILE.md` and `experts/econometrics/OPERATIONAL_PROFILE.md` had never been updated since `v0.14.0` and `v0.9.0` respectively, and still described "three-expert routing"/"four routing types (GAUSS-only, Econometrics-only, both experts, neither)" and multiple "future Documentation/Education/Product Expert, once operationalized" escalation references. `experts/documentation/OPERATIONAL_PROFILE.md` also still said "five-expert routing" and had two lingering "future Education/Product Expert" escalation lines. All were corrected in this task — see "Stale Wording Fixed" below.

## Remaining Limitations

- No runtime orchestration exists for any of the six experts or for routing between them.
- No narrative-only expert placeholder remains as of `v0.17.0`, but routing itself remains a documentation/manual-evaluation-driven contract, not a runtime instrumentation layer.
- The Product Expert does not validate GAUSS syntax independently — that remains the GAUSS Language Expert's evidence-backed claim.
- The Product Expert does not validate statistical methodology independently — that remains the Econometrics Expert's claim.
- The Product Expert does not validate maintainability/design independently — that remains the Software Engineering Expert's claim.
- The Product Expert does not validate documentation/reference clarity independently — that remains the Documentation Expert's claim.
- The Product Expert does not validate learning-design quality independently — that remains the Education Expert's claim.
- The Product Expert does not guarantee market outcomes, adoption, retention, willingness to pay, or product-market fit — these require actual user/customer evidence, never asserted from an internally plausible narrative alone.
- Product value is never correctness evidence for any of the other five domains.
- User demand is never evidence of statistical validity.
- Product urgency is never evidence that a design risk is acceptable.
- Good documentation or training is never proof of product value.
- Product hypotheses require evidence before being presented as settled.
- Testing/validation advice from any expert is not a claim of execution.
- Evidence validation (`validate_all_evidence.py`) checks structure, not GAUSS semantic correctness or execution.
- GAUSS code is not executed anywhere in this framework as of `v0.17.0`.
- Strict-mode validation and tracking checks still have documented warning-promoted-to-failure cases (2 evidence-validation warnings on `glm`/`olsmt`; 2 tracking warnings, historical).
