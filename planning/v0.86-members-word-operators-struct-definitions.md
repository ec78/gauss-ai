# v0.86.0 — Structure Members, Word Operators and Structure Definitions: Design

Status: **implemented** (2026-10-16), not yet committed or released. The plan (§1–§8) was approved on 2026-10-16 with every §8 recommendation. §9 records what changed during implementation and the diffs; §10 is testing. Live evaluation `76.x` (§7) ran on 2026-10-19 and is recorded in §11 (19 pass, 1 fail on a client error; the real-GAUSS opt-in never reached the server, so no code executed through MCP). The drafted search milestone is now v0.87.0 (`planning/v0.87-search-and-grounding-recall.md`, renamed, otherwise unchanged).

## 1. Why

Live evaluation 75.x (`planning/v0.85-proc-headers-and-defining-pages.md` §11.5) had four fails, all caused by three validator defects. All three are pre-existing and fail in the safe direction, and each one blocks ordinary, valid GAUSS with a reason that states something false about GAUSS:

| Finding (75.x) | Seen in | Effect |
|---|---|---|
| 1. `let_statement_shape` rejects a brace literal assigned to a structure member | 75.8, 75.18 | `ctl.bStart = {0, 0};` is a false syntax INVALID ("target must be a plain name"). The client relayed the false rule to the user twice and rewrote correct code. |
| 2. GAUSS's word operators are read as calls | 75.19 | `(x .< 2) .or (x .> 8)` makes `or` an unknown call (false not_ready). Inside a call argument it is also a false INVALID (`call_argument_missing_separator`). |
| 3. A structure definition is read as a matrix literal | 75.20 | `struct regResults { matrix b; … };` is a false INVALID (`matrix_literal_row_separator`) for every snippet that defines its own structure type. |

The investigation (§2) also found one pre-existing defect in the **unsafe** direction, in the same rule as finding 1. `pp->x = {3 4};` (a brace literal through a structure pointer) is handoff_candidate at HEAD, but real GAUSS rejects it (§2.1, m24/m25). Decision 2 covers it.

Goals:
- every rule shape this milestone adds or changes comes from a `tgauss.exe -b` spot check (§2), and its `_SYNTAX_RULE_REGISTRY` entry cites it;
- the three false verdicts become the verdict the evidence supports, and every snippet that newly leaves not_ready is checked against CLAUDE.md's I/O rule;
- the rule's real violations stay INVALID: indexed targets, text after the literal, malformed definitions, and adjacent operands.

Constraints (as in v0.85.0):
- no change to `command_doc_lookup.py` or to signature/type extraction (`extract_documented_signature`, `_parse_signature_occurrence`, `_PARAM_TYPE_LINE_RE`);
- `resolve_concepts`, `ground_multi`, `compute_generation_gate`, `GroundingBundle` and the concept index are unchanged, so the `ask()` gate is unchanged (§6.4);
- the readiness state machine, `compute_eligibility`, `compute_evidence_profile`, `check_parameter_roles` and the system-statement registry (216 entries) are unchanged;
- all source is read through `lex_gauss_source` / `source_statements` (CLAUDE.md; `test_170`).

Out of scope: the search/grounding items (v0.87 draft, 75.x finding 7), upstream doc/library defects (finding 8), expression category inference, and public release readiness. Findings 4-6 are §8 decisions 7-9.

### 2.1 Finding 1: brace literals and structure-member targets

**Cause.** `_check_let_statements` (`gauss_pre_execution_validation.py:2959`) matches `_LET_STATEMENT_RE`, whose target may be indexed or a member (`\s*\.\s*name`). It flags any target containing `[` **or** `.`. The rule's provenance (v0.82.0) cites only plain and indexed targets, and the member branch has no evidence.

**Spot checks.** `struct pt { matrix x; }; struct pt s;` precedes each m-program unless noted.

| ID | Statement | Result | Establishes |
|---|---|---|---|
| m01 | `s.x = {1 2};` | `1 2` | a member target takes a brace literal |
| m02 | `s.x = { 1 2,`⏎`3 4 };` | the 2×2 | the same, multi-line |
| m03 | `s.a.b = {1};` (nested structures) | `1` | a nested member path |
| m08 | `let s.x = {1 2};` | `1 2` | the explicit `let` form |
| m11 | `s.sa = {"a" "b"};` (`string array` member) | `a b` | a string literal list |
| m15 | `d.dataMatrix = {1 ., 3 4};` (`dsCreate`) | prints | missing-value elements |
| m10 | `s.x = ({1, 2})';` | `1 2` | a parenthesized literal may be followed by an operator |
| m06 | `s.x = {1, 2}';` | `G0008 '''` | **nothing may follow the literal, as for plain names** |
| m07 / m13 / m31 | `s.x = {1, 2} + 1;` / `s.x = {1 2} ~ {3 4};` / `let s.x = {1 2} + 1;` | `G0008` | the same |
| m04, m22 | `s.x = {1 2 3}; s.x[1] = {5};` | prints `5`, **1×1** | **silent misparse: the whole member becomes the literal** |
| m16 | `s.x = {1 2 3}; s.x[1] = 5;` | `5 2 3` | (control: without braces the element is set) |
| m18 | `v = {1 2 3}; v[1] = {5};` (plain name) | prints `5` | the same silent misparse for plain indexed targets |
| m17, m19, m21 | `…[2] = {5};` (member and plain) | `G0047 Rows don't match` | |
| m20 | `s.x[1, 2] = {9};` | `G0046 Columns don't match` | |
| m05 | `s.x[1:2] = {7 8};` | `G0008` | |
| m09, m28, m29 | `s . x = {1 2};` / `s .x = …` / `s. x = …` | errors (`redefinition of structure 's'`, `G0504`) | whitespace around `.` is not a member access |
| m30 | `s . x = 3;` (no literal) | `G0174 '.' and ' ' operators must be inside [] brackets` | the same without a literal |
| m24, m25 | `struct pt *pp; pp = &s; pp->x = {3 4};` / `{3}` | error (`redefinition of unknown 'pp'`) | **a pointer-member target rejects a brace literal** |
| m26, m23, m27 | `pp->x = ({3 4});` / `pp->x = 3;` / `pp->x = v;` | run | (controls) |
| m12 | `struct sc { scalar z; }; …; s.z = {3};` | `G0071 Type mismatch` | a `scalar` member rejects any literal (a type rule, not syntax; m32's `s.z = 3;` runs) |

So the rule's evidence-backed shape is:
- a brace literal may be assigned to a plain name **or a member path written without whitespace** (`a.b`, `a.b.c`);
- an indexed target (plain or member) is always wrong. It is either an error (`G0046`/`G0047`/`G0008`) or, for a 1×1 index on a row, a silent replacement of the whole variable (m04, m18), the same class of hazard as the kept `matrix_literal_row_separator`;
- nothing may follow the literal, whatever the target;
- a whitespace member target and a `->` pointer-member target with a literal are errors.

**HEAD verdicts** (probes, each followed by `x = {1, 2}; m = meanc(x);`):
- m03, m04, m06, m08 and sc01 all give `let_statement_shape` (not_ready), the correct and the wrong ones alike;
- `pp->x = {3 4};` gives **handoff_candidate**, because `_LET_STATEMENT_RE` does not match `->`, so a program real GAUSS rejects is offered for execution (the unsafe-direction finding, decision 2);
- `s . x = 3;` (m30) is also handoff_candidate (decision 3).

**Reach.** Of the 5,891 code blocks in the published docs, **60 blocks on 43 pages** assign a brace literal to a member (mostly control structures: `ctl.A = { 1.5, 2.1 };`, `ctl.active = {…}`), and all 60 get `let_statement_shape` at HEAD. No docs block assigns a literal to an indexed member or through `->`.

### 2.2 Finding 2: word operators

**Cause.**
- `_CALL_SHAPED_RE` (`:197`) matches `or(` after the `.` of `.or (`. `extract_generated_calls` (`:932`) and `gauss_conversation_engine.check_generated_symbols` (`:1307`) both scan `call_scan_view(...)` (`:490`), and neither skips these words.
- `_check_call_argument_missing_separator` (`:2486`) treats `or` as a token, so in `(x .< 2) .or (x .> 8)` the `or (` pair is "adjacent tokens".

**What GAUSS documents.**
- `user-guide/fundamentals/operators.rst` ("Logical Operators") and `cc/operators.rst` document five logical operators, each in an element-wise (`.and`) and a matrix (`and`) form: `and`, `or`, `not`, `xor`, `eqv`. Each has its own page (`logical-and.rst` … `logical-xor.rst`).
- The relational words `eq`, `ne`, `lt`, `le`, `gt`, `ge` (and `.lt` …) are not in either operator table. They appear only in examples (`recode.rst`, `delif.rst`: `(20 .lt x) .and (x .le 30)`).
- `selif.rst`'s own example uses `(…) .and (…)` inside a call.

**Spot checks** (`a = {1, 0, 1}; b = {1, 1, 0};` for dot forms, `s = 1; t = 0;` for matrix forms):

| Shape | Words | Result |
|---|---|---|
| `(a) .OP (b)`, `(a).OP(b)`, `a .OP b`, `sumc((a) .OP (b))`, `sumc(a .OP b)` | `and`, `or`, `xor`, `eqv` | all run (20 programs) |
| `(s) OP (t)`, `(s)OP(t)`, `maxc((s) OP (t))`, `maxc(s OP t)` | the same | all run (16) |
| `.not (a)`, `.not(a)`, `sumc(.not (a))`, `sumc(.not a)`, `not (s)`, `not(s)`, `e = not(s);`, `maxc(not (s))`, `maxc(not s)` | `not` | all run (9) |
| `if (s) or (t);`, `if not(t);` | | run |
| `a .OP 1`, `(a) .OP (1)`, `sumc((a) .OP (1))`, `s OP 1`, `(s) OP (1)`, `maxc((s) OP (1))` | `eq`, `ne`, `lt`, `le`, `gt`, `ge` | all run (36) |
| `.OR`, `OR`, `.NOT`, `Or` | | run (case-insensitive) |
| `OP = 1;` and `proc (1) = OP(x);` | all 11 | **`G0276 Illegal use of reserved word`** (22 programs) |
| `sumc(a .or b a)` | | `G0063 Operator expected` (control: real adjacency) |
| `y = maxc(s not t);`, `y = sumc((a) .not (b));` | | `G0136` (control: `not` is unary only) |
| `y = sumc((a) (b));`, `y = sumc((a) (b) .or (a));` | | `G0136` (control) |
| `sumc(.or a)` / `sumc(a .or)` | | `G0064` / `G0105` (a binary operator with a missing operand) |
| `y = selif(x, (x .> 1) .and (x .< 9));` | | runs (`selif.rst`'s idiom) |

So all eleven words are operators in every position, and none can ever name a variable or a procedure (G0276). A word operator followed by `(` is never a call.

**HEAD verdicts** (probes):
- `.or (`, `.not (`, `.xor (`, `.eqv (`, `.eq (`, `.lt (` and the plain `or (`, `not (` all give an unknown call (`call_undocumented`), so not_ready;
- `.and (` grounds on `logical-and.rst` by accident (`signature_not_extracted`, review_required);
- every in-call form above is a false `call_argument_missing_separator` INVALID, **including `selif.rst`'s own example**;
- `a .or b` without parentheses at top level is not affected.

**Reach.** 12 docs code blocks (11 pages) extract a word operator as a call. A simulation masked the word operators as in §3.2, on every docs block that contains one. It cleared `call_argument_missing_separator` from 11 blocks (`delif`, `recode`, `selif`-style examples, `missex`, `create`, `filesa`, the MATLAB/Python intro pages). It left the other 10, which are prose or SQL text in literal blocks unrelated to operators. `create` and `filesa` are registered system statements, so those examples stay not_ready.

### 2.3 Finding 3: structure definitions

**Cause.** `_check_matrix_literals` (`:2322`) reads every top-level `{…}` in the masked code as a matrix literal, so the member declarations' `;` trip `matrix_literal_row_separator`.

`source_statements(...)` splits a definition at its inner `;` (`struct pt { matrix x` / `}`), which no other rule misreads. The `}` statement has no leading word, the member statements have no `=` or call, and `call_scan_view` sees nothing call-shaped.

**What GAUSS documents.** `user-guide/advanced/structures.rst` ("Defining Structures", "Member types") lists six member types: `scalar`, `matrix`, `array`, `string`, `string array` and `struct T`. `declare.rst`'s example adds `sparse matrix`. The 8 definitions in the docs (5 pages) all use these forms.

**The evidence-backed member grammar.** Each `;`-separated item in the body is one of seven type phrases followed by exactly one name:
- type phrases: `scalar`, `matrix`, `array`, `string`, `string array`, `sparse matrix`, `struct Name`;
- the item is case-insensitive, and any whitespace, including a newline, may separate its words;
- an empty item is ignored, so a body may be empty (d10) and the final `;` may be missing (d12);
- the name may itself be a type word (d37).

All 15 observed failing member items (d05-d09, d15-d17, d20, d25-d28, d30, d40) deviate from this one shape, each in a different way: a missing or unknown type, a missing name, an extra name, or `*`, `,`, `=`, `[`, `{` or a statement.

**HEAD verdicts.** sc04, d01, d02, d13 and every legal form above give `matrix_literal_row_separator` (not_ready). A definition with a `print` inside it (d30) gets the same issue, which is right only by accident.

**Reach.** All 8 docs definitions (5 pages) give `matrix_literal_row_separator` at HEAD.

## 3. Proposed design

Deterministic and stdlib-only, all in `gauss_pre_execution_validation.py`. No new module and no `pyproject.toml` change.

### 3.1 Structure-member targets (finding 1)

`_check_let_statements` keeps its statement loop. Its target is now classified as follows:

| Target | Example | v0.86.0 | Evidence |
|---|---|---|---|
| plain name | `x = {…}` | unchanged: valid; trailing text INVALID | v0.82.0 |
| member path, no whitespace around `.` | `s.x`, `s.a.b`, `let s.x` | **valid**; trailing text INVALID | m01-m03, m08, m10, m11, m15, sc01-sc03; m06, m07, m13, m31 |
| indexed, plain or member | `v[1]`, `s.x[1]`, `s.x[1:2]` | INVALID (unchanged) | v0.82.0; m04, m05, m17-m22 |
| member with whitespace around `.` | `s . x`, `s .x`, `s. x` | INVALID (unchanged), with a message that names the whitespace | m09, m28, m29 |
| pointer member | `pp->x = {…}` | **INVALID** (new, decision 2) | m24, m25 (m26 is the control) |

- `_LET_STATEMENT_RE`'s target gains an optional `->name` step, so the pointer form is matched; nothing else about the statement match changes.
- Messages name the real cause, for example "a `{…}` literal cannot be assigned to an indexed target", or "GAUSS reads `s . x` as … (whitespace around `.`)".
- The registry entry's description and provenance gain the m-series.

### 3.2 Word operators (finding 2)

- A new constant `_WORD_OPERATORS` holds the eleven words `and`, `or`, `not`, `xor`, `eqv`, `eq`, `ne`, `lt`, `le`, `gt`, `ge` (decision 4). Its comment cites operators.rst/cc/operators.rst, the examples, and the spot checks (every position runs; all 11 are reserved, G0276).
- **`call_scan_view(...)` blanks each word-operator token.** A token is a whole identifier, matched case-insensitively on the masked view, with or without a leading `.`. `call_scan_view` is already the ONE text both `extract_generated_calls` and `check_generated_symbols` scan (v0.80.0), so the two consumers cannot disagree. Argument text is still sliced from the code view, so an argument such as `(x .< 2) .or (x .> 8)` keeps its full text and is still an `argument_expression` for role checks. The duplicated `_LANGUAGE_CONSTRUCT_KEYWORDS` sets are not touched.
- **`_check_call_argument_missing_separator`:**
  - skips a call-shaped match whose name is a word operator;
  - before the adjacency regex, replaces word operators inside each argument with a same-length mask. A binary operator becomes `+`, an operator, so `a .or b` is never "adjacent". `not`/`.not` becomes `(`, which can start an operand but cannot end one. So the observed `G0136` misuse `s not t` / `(a) .not (b)` stays INVALID, and `.not (a)` / `a .and .not b` pass;
  - reports the message with the original argument text;
  - keeps every other adjacency exactly as today (`sumc(a .or b a)`, G0063).
- No rule reads raw text: both changes operate on the masked view, so a word inside a string or comment is never touched (`test_170`).

### 3.3 Structure definitions (finding 3)

- **`_struct_definitions(masked)`** is a new private helper, modelled on v0.85.0's `_proc_headers`:
  - it reads `source_statements(...)`, and a definition starts at a statement whose leading word is `struct` and that matches `struct\s*(Name)?\s*\{`;
  - the body's closing brace is `_find_matching_brace` on the masked view (strings masked, so a `{` in a string never counts);
  - it records the name, the brace offsets, the line, and what follows the `}` up to the next `;`.
- **`_check_matrix_literals`** skips a `{` that opens a definition body and resumes after its `}`. Every other literal is checked exactly as today, including a literal right after a definition (d24) and a `;`-separated literal anywhere else.
- **A new INVALID rule, `struct_definition_shape`:**
  - the body is split on `;` (masked), empty items are dropped, and each item's whitespace is collapsed;
  - an item that matches §2.3's grammar passes;
  - any other item is INVALID (decision 5), with a message that names the item, and the issue is reported on the item's line;
  - a definition with no type name (d39) is INVALID too;
  - its `_SYNTAX_RULE_REGISTRY` entry carries the d-series and sc04.
- **After the `}`:** `;` (sc04) or a single name and `;` (d13, d35) is legal. Anything else, including d11's missing `;`, adds the unknown construct `struct_definition`, so the verdict is review_required at best. There is only one failing observation (d11), so no INVALID claim is made.
- **A checked definition with no issue adds `struct_definition` to `validated_constructs`** (decision 6). A snippet that defines its own structure can therefore reach handoff_candidate when everything else checks out.
- **The I/O rule.** The legal grammar admits only a type phrase and a name, so no statement can hide inside a passing definition. `struct d { dos dir; };` is INVALID (`dos` is not a type), as GAUSS's own `d30` shape shows. Every statement after the definition is scanned by `check_system_statements` as before.

## 5. Known limitations this design accepts

- **Structure types are not modelled.** The following are compile or run-time errors in real GAUSS that the validator does not see. Each can now reach review_required or handoff_candidate, and the handoff reports the failure honestly:
  - a literal assigned to a `scalar` member (m12, `G0071`);
  - an undefined member type, or a declaration before its definition (d21, d41, `G0507`);
  - a different redefinition (d19, `G0467`).

  A definition inside a `proc` (d18, `G0468`) is already capped at review_required by the `proc` block.
- **After `}`, anything but `;` or `name;` is unknown, not INVALID** (d11 is the only failing observation).
- **A whitespace member target without a literal (m30, `G0174`) stays unchecked** (decision 3). It is handoff_candidate at HEAD and fails at compile time.
- **A binary word operator with a missing operand inside an argument is not flagged.** `sumc(.or a)` (`G0064`) is INVALID at HEAD only by accident, because `or a` reads as adjacent names. It no longer is. `sumc(a .or)` (`G0105`) was never flagged. Both fail at compile or run time.
- **Reserved words stay unchecked** (finding 5, decision 8), including the eleven word operators used as names (`or = 1;`, G0276).
- **The spot checks are GAUSS 26.1.4 behavior**, and the docs give the member types and operator tables but no formal grammar.
- **Removing a fake call can lower a verdict.** A snippet whose only "documented call" was `.and (` (grounded by accident on `logical-and.rst`) now has no documented call. Under the v0.80.0 policy it is not_ready with that reason (§6.2, the 75.19 `.and` probe). This is the true reason, not a regression.

## 8. Decisions needed

1. **Member targets: allow `a.b(.c)*` with a literal; keep every indexed target (plain or member) INVALID; apply the trailing-text rule to members.** *Recommend yes.* It follows §2.1 exactly. The indexed case is worse than an error: m04/m18 silently replace the whole variable.
2. **Flag `p->m = {…}` (new INVALID branch).** *Recommend yes.* HEAD offers it for execution although GAUSS rejects it (m24, m25), so this is the one change here in the unsafe-to-safe direction. No docs example has the shape, so nothing valid is affected, and the parenthesized form (m26) stays valid.
3. **Whitespace member targets without a literal (`s . x = 3;`, m30) are out of scope.** *Recommend yes (record in `KNOWN_LIMITATIONS.md`).* It would be a new rule outside the three findings, and it fails at compile time, which the handoff reports honestly. The literal form stays INVALID through the let rule.
4. **The word-operator list is all eleven words**, including the relational `eq`/`ne`/`lt`/`le`/`gt`/`ge` that appear only in docs examples. *Recommend yes.* All eleven are spot-checked as operators in every position and as reserved words (G0276), so none can ever be a call. `not`/`.not` is masked as an operand start so its binary misuse stays INVALID.
5. **A definition member that does not match the seven-type-phrase grammar is INVALID.**
   - Option (a), INVALID for any non-matching item.
   - Option (b), INVALID only for the observed failure shapes, and an unknown construct otherwise.

   *Recommend (a).* All 15 observed failures deviate in different ways, and together they cover every way an item can deviate from "type phrase + one name". (b) would add a classification layer that, on the evidence, never fires.
6. **A valid definition is a validated construct**, so a snippet with a user-defined structure can reach handoff_candidate. *Recommend yes.* The alternative (an unknown `struct_definition`, review_required at best) would turn 75.20's false INVALID into a permanent cap on ordinary code. The type-level errors this cannot see (§5) fail at compile time and are reported honestly, as other unmodelled errors already are.
7. **Finding 4 (`dftype(x, "category")`, a false INCOMPATIBLE against "vector").** *Recommend: not in v0.86.0; it needs its own design.* Which documented "vector" parameters accept a string list cannot be read from the type text alone, and any fix moves verdicts in both directions, through the role checks that every other milestone holds fixed. Record it in `KNOWN_LIMITATIONS.md`.
8. **Finding 5 (reserved words, `lower`/`upper` → G0276).** *Recommend: not in v0.86.0; a separate milestone.* GAUSS 26's changelog says assignment to any built-in function name is a reserved-word error (`eig = 5`), and the docs do not mark which documented symbols are built-ins. A sound rule therefore needs a one-time `tgauss.exe -b` sweep of the 1,418 documented names, recorded as a provenance table. The eleven word operators (already spot-checked) could be added now, but on their own they would cover almost none of the real risk.
9. **Finding 6 (multi-form signatures label role gaps with the wrong parameter, `gmmFitIV`).** *Recommend: not in v0.86.0.* The cause is not located, it affects only the labels of unknown gaps (never a state), and the fix belongs to signature alignment, which this milestone holds fixed. Record it in `KNOWN_LIMITATIONS.md`.

The client's programs: S00-S02, S04-S14, S16-S19 and S21 print what the client said or predicted. S03 fails (`G0507`, 77.4). S20 fails with `G0071`, as intended for a question about that error. S15 was not run (a file write).

1. **An operator form of an inversion skips the precondition registry (77.17). Minor, validator coverage; safe at run time. Not in `KNOWN_LIMITATIONS.md`.**
   - **Cause:** `check_preconditions(...)` runs only for calls of `invpd`, `inv`, `solpd` and `chol` (`_PRECONDITION_CHECKERS`, `gauss_pre_execution_validation.py`). GAUSS's `/` operator inverts or solves the same matrices (`eye(k) / xx`, `y / X`) and is never checked.
   - **Effect:** the verdict depends on spelling. 77.17's regression was review_required with `invpd(X'X)` and with `inv(xx)` (unverifiable runtime precondition) and handoff_candidate with `/`; the client disclosed this before the user approved. With a literal singular matrix, `inv(a)` is not_ready (`violated`) but `eye(2) / a` is handoff_candidate (P1/P2).
   - **Severity:** GAUSS fails both forms loudly (`G0048`, `G0121`; x02-x05), so no silently wrong output was found; the gap costs pre-run detection, not correctness. It is the same class as KL v0.78.0's disclosed `print f(...)` gap ("less deterministic scrutiny").
   - **KL relation:** KL lines 56 and 63 disclose that expressions are never evaluated (so `invpd(x'x)` stays review_required); they do not say that operators bypass preconditions a call would get.
   - **Candidate:** treat a `/` whose divisor is a literal square matrix like `inv` for the existing literal check, or disclose the gap in `KNOWN_LIMITATIONS.md`.
2. **A reply is not bound to the prompt the user read (77.1, 77.9; P5). Minor-Moderate, consent binding, pre-existing (v0.79.0). Not disclosed.**
   - **Cause:** `gauss_execution_prepare` stores its request in the single slot `session.pending_request`, silently replacing any pending one, and `gauss_execution_decide(session_id, response_text)` takes no `request_id` or digest. Its response does not echo which request ran.
   - **Effect:** the approval is digest-bound to whatever was prepared last, not to the prompt the user answered. Live, the 77.1 `det` request was replaced by 77.9's prepare without notice; it was harmless because the client showed and passed replies only for the latest prompt. P5 shows that a "yes" given after two prepares executes the second request.
   - **Mitigation today:** the client is responsible for showing only the latest prompt; the same client could also misreport the reply, so the binding is client-mediated either way.
   - **Candidate:** `gauss_execution_decide` takes the `request_id` (or digest) the user saw and refuses a mismatch; `prepare` reports when it replaced a pending request; `decide` echoes the request_id and digest it acted on.
3. **The prompt shows a "Workspace parent" the handoff never uses (77.9-77.17). Minor, display, pre-existing (v0.78.0); partly disclosed.**
   - **Cause:** `execute_execution_handoff(...)` always runs in `tempfile.TemporaryDirectory(prefix="gauss_ai_handoff_")`, deleted afterwards; `request.workspace_parent` is only digest-bound and rendered (`render_execution_handoff_prompt`).
   - **Effect:** every approved run executed in a different directory from the one the user approved; `workspace_state`/`provenance` are `null`, and no on-disk trace of an approved or declined run remains.
   - **KL relation:** KL v0.78.0 says code "runs as an ephemeral inline snippet in a fresh temp directory"; the prompt line contradicts that to a user who reads only the prompt.
   - **Candidate:** for the handoff, replace the line with "Runs in: a temporary directory, deleted afterwards", or omit it.
4. **Known items reproduced live, not new:**
   - the `&` and `...` gaps (KL v0.83.0; 77.3, 77.4);
   - the `.` literal (KL v0.85.0; 77.7);
   - the `scalar` member `G0071` (KL v0.86.0, §5 m12; 77.18);
   - `gmmFitControl` (75.x finding 8; 77.4);

   - `eigh`'s missing symmetry precondition (76.x finding 6; 77.11);

   - `proc` blocks unmodelled (v0.82.0 scope);
