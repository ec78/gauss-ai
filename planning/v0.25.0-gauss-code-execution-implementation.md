# v0.25.0 - GAUSS Code Execution Implementation

## Release Goal

`v0.25.0` implements the first narrow GAUSS code execution helper based on the `v0.24.0` execution contract (`tools/gauss_code_execution.md`, `schemas/gauss_code_execution.schema.json`), moving code execution from specification to real code — the same spec-then-implement split already used for environment detection (`v0.20.0` spec / `v0.21.0` implementation) and package inspection (`v0.22.0` spec / `v0.23.0` implementation).

The goal is to implement a helper that can:

- Consume environment-detection output from `scripts/gauss_environment_check.py`.
- Optionally consume package-inspection output from `scripts/gauss_package_inspection.py`.
- Execute explicitly supplied GAUSS code or an explicitly supplied GAUSS script file.
- Require a safe working directory.
- Enforce timeouts.
- Capture stdout, stderr, exit code, elapsed time, and limited output-file metadata.
- Return schema-valid output matching `schemas/gauss_code_execution.schema.json`.
- Block unsafe or ambiguous execution requests.
- Preserve Advisory Mode fallback when execution cannot proceed.

`v0.25.0` should **not**:

- Install packages.
- Activate licenses.
- Access the network.
- Mutate global GAUSS configuration.
- Write outside the safe working directory.
- Implement automatic debugging/rerun loops.
- Implement report generation.
- Claim statistical validity from execution.
- Implement full runtime orchestration.
- Integrate into the Code Assistant workflow unless separately scoped.

## Current State

- `v0.23.0` implemented package inspection (`scripts/gauss_package_inspection.py`, `inspect_packages(...)`).

## Key Implementation Risk

The major unresolved risk is **GAUSS non-interactive invocation**.

**Open questions:**

- What command-line form runs a `.gss` script non-interactively?
- Does invocation differ by GAUSS version?
- Does invocation differ on Windows, macOS, and Linux?
- Does GAUSS return meaningful exit codes?
- Does GAUSS write to stdout/stderr consistently?
- Can license or GUI prompts hang the process?
- Does GAUSS respect the process working directory?
- How are output files written relative to the working directory?

`v0.25.0` should implement the helper architecture using a runner abstraction so self-tests can use a fake runner even if real GAUSS invocation remains platform-specific and partially unresolved. This mirrors how `scripts/gauss_environment_check.py` and `scripts/gauss_package_inspection.py` both used dependency-injectable internals (`path_exists_fn`, `accessibility_fn`, `discovery_fn`/`list_dir_fn`, `env_detect_fn`) so their `--self-test` suites never depended on a real GAUSS installation — a runner abstraction extends that same discipline to a component that, unlike its predecessors, must eventually launch a real subprocess.

**Confirmed finding (implementation task, manual smoke test against this development machine's real GAUSS 26 installation):** the naive, best-effort command form `[executable_path, script_path]` does **not** run non-interactively. GAUSS launched, printed its startup banner and the script's `print` output to stdout, then sat at an interactive `(gauss)` prompt awaiting further input rather than exiting on its own — the process only terminated because the helper's timeout killed it after 30 seconds. This confirms the risk named above was real, not hypothetical: real non-interactive invocation remains genuinely unresolved, not merely "unverified." The manual smoke test itself was an unintended real invocation (triggered by omitting `--environment-result` during CLI testing, which let automatic environment detection find and use the real local GAUSS 26 installation) — harmless in this case (`print "hello";`), but a concrete reminder that any call to `execute_gauss_code(...)`/the CLI without an injected fake `runner` and with a `found` environment context will attempt a real GAUSS invocation. Future testing and any documentation examples should make this explicit rather than assume it away.

## Runner Abstraction

**Suggested design:**

- An internal function or class that receives the command, working directory, timeout, and capture settings.
- The default runner uses `subprocess` with a timeout.
- Self-tests use a fake runner.
- The runner returns: `executed`, `timed_out`, `exit_code`, `stdout`, `stderr`, `elapsed_seconds`, and raw details.

**Benefits:**

- No real GAUSS required for self-tests.
- Future platform-specific GAUSS invocation can be isolated to one narrow component.
- Safer testing of timeout/failure/success cases without ever spawning a real process during `--self-test`.

## Environment Context Handling

**Support:**

- `environment_check_result` object.
- Environment result JSON file path through the CLI.
- Direct executable path.
- Direct GAUSS version.

**Rules:**

- Explicit executable path controls when provided.
- The environment result's selected executable/version is used when direct input is absent.
- Do not silently switch GAUSS versions.
- Do not execute when environment status is `not_found`, `ambiguous`, `inaccessible`, or `error`.
- If version is unknown but the executable is accessible, decide a conservative policy; recommended: allow execution only with an explicit executable path and a warning, never as an automatic fallback from environment detection alone.
- If no usable executable context exists, return `blocked`/advisory.

This mirrors the input-precedence pattern both prior helpers already use: explicit direct arguments → supplied result object → automatic detection fallback (unless `strict`) → unavailable/advisory. `execute_gauss_code(...)` should follow the same precedence for consistency across all three tools.

## Package Context Handling

**Support:**

- `package_inspection_result` object.
- Package inspection JSON file path through the CLI.

**Rules:**

- Package inspection is advisory/feasibility context, not a hard gate for every execution.
- A missing package may block only if the requested execution depends on that package and policy is explicit about it.
- Unknown package status should warn, not be treated as installed.
- Never auto-install packages.
- Never activate licenses.
- Package installed does not prove syntax validity.
- Package installed does not prove methodology validity.
- Package installed does not prove execution success.

## Input Validation

**Require:**

- Exactly one of `code` or `script_path`.
- `working_directory`.
- A selected executable context.
- `timeout_seconds` or a safe default.
- Safe paths.

**Rules:**

- `code` and `script_path` supplied together should block.
- Neither `code` nor `script_path` supplied should skip/block (not silently proceed).
- `working_directory` must exist and be accessible.
- `script_path` must be inside `working_directory` unless a future policy explicitly allows external read-only scripts.
- `output_directory` must resolve inside `working_directory`.
- `input_files` must be explicit and inside `working_directory`, or copied safely in a later design.
- Path traversal must be rejected.
- Symlink handling should be conservative.
- `allow_network` should be rejected or ignored with a warning.
- `allow_file_write` should never permit writes outside `working_directory`.

## Code Handling Policy

**For inline code:**

- Write the code to a temporary `.gss` file inside the safe working directory or a helper-created subdirectory under it.
- Do not write outside `working_directory`.
- Document the generated script path in `raw_execution_details` if needed.
- Avoid exposing unnecessary paths in normal output.

**For `script_path`:**

- Only execute the explicit script path supplied.
- Require safe path validation.
- Do not execute arbitrary discovered files.
- Do not modify the script file.

## Command Construction

Because exact GAUSS invocation may be uncertain, command construction should be planned as a narrow, isolated concern:

- Create a narrow function responsible for building the command.
- Document current assumptions explicitly in code comments.
- Allow command construction to be overridden/injected in tests (`command_builder`).
- Do not hide uncertainty — if invocation syntax is unknown, the implementation should say so rather than guess silently.
- If invocation syntax is unknown, the implementation may support a conservative placeholder/fake-runner self-test and block real execution unless an executable command policy is confirmed.

**Decision needed before implementation:**

- Whether `v0.25.0` should execute real GAUSS on a development machine if a command form is known, or
- Whether `v0.25.0` should implement the helper with fake-runner tests and a guarded real-runner path, deferring confirmed real-invocation support.

**Recommendation:** implement the helper with the runner abstraction and fake-runner self-tests first. Add real GAUSS manual verification only if a safe command form is confirmed — the same order `v0.21.0` used (self-test suite first, then manual verification against real GAUSS 24/25/26 installations once the logic was already proven synthetically).

**Outcome:** this recommendation was followed — the fake-runner self-test suite (18 cases) passes without any real GAUSS involvement. A real-GAUSS check was also performed (see "Key Implementation Risk" above) and confirmed the default command form does not achieve non-interactive execution; the `command_builder` injection point exists specifically so this can be revised later without touching the rest of the helper.

## Working Directory Policy

- `working_directory` is required.
- The path must exist and be a directory.
- No implicit process-CWD fallback.
- Resolve all paths.
- Reject path traversal outside `working_directory`.
- Output file discovery is limited to `working_directory`.
- No cleanup outside helper-created temporary files.
- No deletion of user files.
- Avoid following unsafe symlinks.

## Timeout and Resource Policy

- A safe default timeout.
- A hard maximum timeout.
- Subprocess-level timeout enforcement.
- Terminate the process on timeout.
- No detached/background process.
- Capture stdout/stderr.
- Truncate stdout/stderr above a size limit.
- Record truncation warnings.
- Record elapsed time.
- Avoid crashing on large output.

**Suggested constants** (exact values are an implementation decision, not fixed by this plan):

- `DEFAULT_TIMEOUT_SECONDS`
- `MAX_TIMEOUT_SECONDS`
- `MAX_CAPTURE_CHARS`

Use conservative values and document them in code comments, the same way `scripts/gauss_environment_check.py` documents `PLAUSIBLE_EXECUTABLE_NAMES`/`COMMON_LOCATION_TEMPLATES` as a conservative, non-exhaustive starting set rather than a claimed-final answer.

## Output File Discovery

- Optional output file listing if `allow_output_files` is true.
- Only list files under `working_directory` or an `output_directory` inside it.
- Record `path`, `size_bytes`, `file_type`, and `created_by_execution` if knowable.
- If `created_by_execution` cannot be determined, use `"unknown"` (the schema's `output_file.created_by_execution` field is already tri-state for exactly this reason).
- Do not read arbitrary file contents.
- Do not include files outside `working_directory`.
- Avoid exposing unnecessary sensitive paths.

## Status Mapping

- **`completed`** — GAUSS invoked and process completed without timeout. `exit_code` may be `0`, or tool policy may classify nonzero as `failed`. Recommended: `exit_code 0` → `completed`, nonzero → `failed`.
- **`failed`** — GAUSS invoked and returned a nonzero exit, or the runner reports a runtime failure.
- **`timed_out`** — GAUSS invoked and exceeded the timeout.
- **`skipped`** — no explicit code/script, or execution not requested.
- **`blocked`** — safety policy prevented execution before invocation.
- **`error`** — unexpected helper error.
- **`unknown`** — execution state could not be determined.

**Important:**

- `executed: true` only if the GAUSS subprocess was actually invoked.
- `blocked`/`skipped` means `executed: false`.
- `completed` does not mean statistically valid.
- `failed`/`timed_out` does not mean the method is invalid.

These mapping rules are already encoded as hard constraints in `schemas/gauss_code_execution.schema.json`'s `allOf`/`if`/`then` blocks — the implementation must satisfy them, not just describe them.

## CLI Design

**Options:** `--environment-result`, `--package-inspection-result`, `--executable-path`, `--gauss-version`, `--code`, `--script-path`, `--working-directory`, `--input-file`, `--output-directory`, `--timeout-seconds`, `--allow-file-write`, `--allow-output-files`, `--allow-network`, `--strict`, `--json`, `--validate-schema`, `--self-test`.

**Behavior:**

- JSON output under `--json`, human-readable summary by default — consistent with `scripts/gauss_environment_check.py` and `scripts/gauss_package_inspection.py`.
- `--self-test` uses the fake runner and does not require real GAUSS.
- `--validate-schema` validates against `schemas/gauss_code_execution.schema.json`, degrading to a warning (not a crash) if `jsonschema` is unavailable — the same graceful pattern both prior helpers already use.

## Self-Test Strategy

Self-tests use the fake runner exclusively and should cover:

1. Missing executable → `blocked`.
2. Ambiguous environment → `blocked`.
3. No code or script → `skipped` or `blocked`.
4. Both code and script → `blocked`.
5. Missing working directory → `blocked`.
6. Successful fake execution → `completed`.
7. Failed fake execution → `failed`.
8. Timeout fake execution → `timed_out`.
9. stdout/stderr capture.
10. Output-truncation warning.
11. Output-file listing limited to `working_directory`.
12. Path traversal rejected.
13. `--allow-network` rejected or ignored with a warning.
14. Schema validation for representative outputs.
15. `executed: false` never reports `completed`.
16. Nonzero exit maps to `failed`.
17. `exit_code 0` maps to `completed`.
18. Package missing can block when policy says so, but no auto-install occurs.

**No self-test should require real GAUSS.**

## Manual Verification Strategy

If real GAUSS is available:

- Test only a simple, harmless script — for example, printing a string or scalar.
- Use a disposable safe working directory.
- Use a short timeout.
- No network.
- No package installation.
- Capture stdout/stderr/exit code.
- Document whether invocation works, and exactly what command form was used.

Manual real-GAUSS verification is optional and should not be required for release readiness unless the milestone explicitly claims real execution support.

## Benchmark Strategy

Reuse `28.x` as the response-behavior benchmark suite.

Do not add a new manual benchmark category unless:

- Workflow integration changes assistant behavior.

Implementation-level behavior should be tested by self-tests/fake runner, not new manual benchmark prompts — the same split `v0.21.0` and `v0.23.0` both used (`--self-test` for implementation correctness, the existing `26.x`/`27.x` categories for response-behavior correctness).
