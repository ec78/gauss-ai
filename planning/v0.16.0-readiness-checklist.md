# v0.16.0 Readiness Checklist

## Release Goal

`v0.16.0` operationalizes the Education Expert as the fifth operational expert the Code Assistant explicitly routes through. It adds learning objectives, instructional sequencing, scaffolding, practice design, feedback, assessment, misconception handling, prerequisite mapping, and learner progression as a distinct, checkable correctness dimension — independent of whether the underlying GAUSS code is syntactically valid, the underlying method is methodologically sound, the underlying code is well-designed, or a single piece of content is clearly documented.

The Code Assistant now routes through five operational experts:

- **GAUSS Language Expert** — implementation correctness.
- **Econometrics Expert** — methodological correctness.
- **Software Engineering Expert** — maintainability/design correctness.
- **Documentation Expert** — documentation/explanation correctness.
- **Education Expert** — education/learning-design correctness.

Routing remains documented and manually evaluated, not runtime orchestration. No code parses or enforces `workflows/expert-routing.md`, any `OPERATIONAL_PROFILE.md`, `workflows/code-assistant-response.md`, `agents/code-assistant/task_modes.md`, or `prompts/code_assistant_system.md` at runtime; a response is checked against them manually, the same way task-mode fit is checked today.

## Education Expert Summary

**Purpose:** guide agents on learning design and learner progression — whether a learning experience is well-sequenced, appropriately scaffolded, and likely to produce durable understanding.

**Scope (owns):** learning objectives, instructional sequencing, scaffolding, practice exercises, feedback design, assessment design, learner progression, beginner-to-advanced pathways, misconception handling, prerequisite mapping, concept sequencing, cognitive load management, guided/worked examples, formative checks, remediation, workshop/session structure, training plan structure, learning path design, onboarding learning flow, exercise difficulty progression.

**Non-scope:** exact GAUSS syntax, verified GAUSS command signatures, the GAUSS package/base distinction, econometric model appropriateness, causal interpretation, statistical diagnostics, code maintainability/design as a primary domain, documentation/reference clarity as a primary domain, product strategy, product positioning, feature prioritization, release management, official GAUSS documentation authority.

**Activation triggers:** lesson plans, curriculum design, learning paths, training plans, onboarding sequences, workshop outlines, learning objectives, practice exercises, quizzes/assessments, feedback prompts, scaffolding, concept sequencing, beginner-to-advanced progression, misconception correction, prerequisite mapping, guided practice, worked examples for learning, remediation activities, teaching GAUSS/econometric/coding concepts, turning a topic into a learning experience over time.

**Non-activation cases:** simple GAUSS syntax lookup only, exact command documentation retrieval only, pure econometric interpretation without teaching intent, pure code refactoring without teaching intent, pure documentation/reference writing without learning progression, product strategy, general prose editing unrelated to learning design, release-note writing, CI guard questions unless learning/evaluation design is involved, simple factual questions unrelated to learning design, a one-off explanation with no request for sequence/practice/scaffolding/progression.

**Boundary rules:**

- May design learning objectives, sequences, scaffolds, practice exercises, feedback, assessments, and remediation paths.
- May not invent GAUSS syntax.
- May not certify statistical validity.
- May not certify code maintainability or design quality.
- May not certify documentation/reference clarity.
- May not certify product value, adoption, positioning, or prioritization.
- May not claim execution.
- Lesson quality is not evidence of syntax correctness, statistical validity, maintainability, documentation quality, or product value.

**Relationship to GAUSS Language Expert:** implementation correctness stays with the GAUSS Language Expert; Education may sequence/scaffold GAUSS concepts but never invents syntax — any example must use verified syntax or be labeled pseudocode.

**Relationship to Econometrics Expert:** methodological correctness stays with the Econometrics Expert; Education may design learning exercises around statistical concepts but never certifies methodology.

**Relationship to Software Engineering Expert:** maintainability/design correctness stays with the Software Engineering Expert; Education may build practice around code-quality concepts but never certifies maintainability.

**Relationship to Documentation Expert:** documentation supports task completion and reference use right now; education supports learning over time through sequencing, scaffolding, practice, feedback, and pedagogy. Documentation is supporting material within a lesson, not a competing authority on pedagogy; a single piece of beginner-friendly documentation is not by itself a curriculum.

**Relationship to future Product Expert:** a good training curriculum is never evidence a feature is valuable, that product-market fit exists, or that a feature should be prioritized. Education supports learner development; a future Product Expert would support user problem framing, workflow fit, adoption, positioning, and prioritization. Product-strategy-adjacent requests are flagged as out of scope rather than answered with unfounded confidence.

## Five-Expert Routing Summary

Five classification axes (`workflows/expert-routing.md` Step 1):

1. GAUSS implementation
2. Econometric methodology
3. Software engineering/code quality
4. Documentation/explanation quality
5. Education/learning-design quality

Any subset of the five experts may activate. Rather than enumerating all 32 mathematically possible combinations, Step 4 documents a compact 14-row activation matrix plus 26 worked routing examples, governed by coordination principles (claims stay separable; the strictest applicable evidence/context requirement wins) for any combination without its own named row. This is the same "readable at N combinations, not a combinatorial engine" discipline `v0.14.0` committed to at eight and `v0.15.0` extended to twelve, now extended to fourteen.

Common patterns documented: Education-only, GAUSS + Education, Econometrics + Education, Documentation + Education, Software Engineering + Education, GAUSS + Documentation + Education, Econometrics + Documentation + Education, GAUSS + Econometrics + Documentation + Education, all five, and Neither. Pre-existing four-expert-era combinations without an education dimension (GAUSS + Econometrics, GAUSS + Software Engineering, Econometrics + Software Engineering, GAUSS + Software Engineering + Documentation, GAUSS + Econometrics + Documentation, GAUSS + Econometrics + Software Engineering, and the four-expert case) remain covered as prose Routing Examples rather than duplicated matrix rows.

Implementation, methodology, maintainability, documentation, and education claims must remain separate and separately attributable, even within one coherent response. Routing is documented/manual-evaluation-driven, not runtime orchestration — no engine executes `workflows/expert-routing.md`.

- Pseudocode or unverified examples must be labeled.

## Important Findings

- The Code Assistant now has five separable correctness dimensions: implementation correctness, methodological correctness, maintainability/design correctness, documentation/explanation correctness, and education/learning-design correctness.
- The Education Expert improves tutorials, learning paths, practice exercises, assessments, feedback, and learner progression without weakening any GAUSS evidence requirement, econometric context requirement, maintainability context requirement, or documentation context requirement.
- Five-expert routing remains readable when expressed as axes, a compact activation matrix, and worked common patterns rather than a full 32-case combinatorial engine.
- The Education Expert must remain distinct from the Documentation Expert (task-completion/reference clarity now vs. learning over time) and from the future Product Expert (learner development vs. problem framing/adoption/positioning/prioritization) — both boundaries are directly benchmark-tested (`23.4`, `23.7`) and both passed.
- All-five routing is viable when implementation, methodology, maintainability, documentation, and education claims remain separately attributable.
- Neither-expert routing (`23.8`) remains important to avoid over-applying expert machinery to ordinary writing tasks — this held even though the prompt's own benchmark category name ("Education Expert Foundation") could tempt an evaluator to look for education content that should not be there.
- A latent gap discovered and fixed during the prior integration task (not new to this task, but confirmed still correctly fixed here): `workflows/expert-routing.md` referenced a Product Expert narrative line in `workflows/code-assistant-response.md` before one actually existed; both that file and `prompts/code_assistant_system.md` now correctly name the Product Expert in their narrative-only lists.

## Remaining Limitations

- No runtime orchestration exists for any of the five experts or for routing between them.
- The Product Expert remains fully narrative-only/placeholder; no operational profile exists for it.
- The Education Expert does not validate GAUSS syntax independently — that remains the GAUSS Language Expert's evidence-backed claim.
- The Education Expert does not validate statistical methodology independently — that remains the Econometrics Expert's claim.
- The Education Expert does not validate maintainability/design independently — that remains the Software Engineering Expert's claim.
- The Education Expert does not validate documentation/reference clarity independently — that remains the Documentation Expert's claim.
- The Education Expert does not validate product value, adoption, positioning, or prioritization — that remains future Product Expert territory.
- Lesson/learning-design quality is never correctness evidence for any of the other four domains.
- Testing/validation advice from any expert is not a claim of execution.
- Evidence validation (`validate_all_evidence.py`) checks structure, not GAUSS semantic correctness or execution.
- GAUSS code is not executed anywhere in this framework as of `v0.16.0`.
- Strict-mode validation and tracking checks still have documented warning-promoted-to-failure cases (2 evidence-validation warnings on `glm`/`olsmt`; 2 tracking warnings, historical).
