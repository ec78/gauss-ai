`v0.28.0` researches, verifies, and integrates a real GAUSS non-interactive batch invocation path for the observed Windows GAUSS 26.1.1 environment.

`v0.28.0`:

- Researches candidate GAUSS invocation forms.
- Inspects local GAUSS installation documentation without initially invoking GAUSS.
- Identifies `tgauss.exe -b <script_path>` as the documented candidate.
- Runs controlled smoke tests in disposable working directories.
- Verifies `tgauss.exe -b <script_path>` exits non-interactively on the observed machine.

- Discovers that GAUSS returns exit code 0 even for a syntax-error case.

- Prove cross-platform behavior.

- Add runtime orchestration.
- Add automatic execution by the Code Assistant.
- Install packages.
- Activate licenses.
- Access the network.
- Mutate global GAUSS configuration.
- Change schemas.
- Add benchmarks.
- Change the system prompt.
- Make execution production-ready across all environments.

## Verified Invocation Summary

- **Verified command form:** `tgauss.exe -b <script_path>`.
- **Verified environment:** Windows, GAUSS 26.1.1, `C:\gauss26\tgauss.exe`.
- **Prior known-bad form:** `[executable_path, script_path]` (no `-b`).
- **Why the prior form failed:** GAUSS entered its interactive `(gauss)` prompt after printing the banner and script output, rather than exiting, and only terminated when the helper's 30-second timeout guard killed it (confirmed during `v0.25.0` implementation).
- **Why `-b` matters:** `C:\gauss26\README.txt`'s "Release Notes for GAUSS Terminal Version" → "Command line syntax" documents `-b` as "Execute in batch mode and exit" — the one flag directly targeting the observed failure mode.
- **Verification scope:** the observed machine only (Windows, GAUSS 26.1.1). No other platform or GAUSS version was tested.
- **Production-readiness caveat:** cross-platform and cross-version behavior remain unverified; real execution through this helper should still be treated as experimental outside this one tested combination.

- No test hit its timeout.
- No lingering `tgauss.exe`/`gauss.exe` process remained after any test, including a final comprehensive system-wide check.
- No packages were installed, no license was activated, no network access occurred, during any test.

## Exit-Code Caveat and Error Detection

GAUSS returned exit code `0` for both the successful smoke tests and the deliberate syntax-error smoke test.

**Therefore:**

- `exit_code` alone cannot classify success/failure.
- `completed` cannot be inferred from `exit_code: 0` alone.
- The helper now checks observed GAUSS error output patterns in addition to exit code.
- Detected error output overrides `exit_code: 0` — the result is classified `failed`, with an explanatory warning.
- stderr containing only banner/job-header text (no error indicators) does not, by itself, cause a `failed` classification.

**Current heuristic (`_detect_gauss_error`):**

- `"program execute failed"` present in stdout (case-insensitive substring match).
- A regex matching the observed GAUSS error-code pattern, `error\s+G\d{4}` (case-insensitive), present in stderr — matches the two codes actually observed (`error G0105`, `error G0014`).

**Limitations:**

- The heuristic is intentionally narrow — it is not a general-purpose GAUSS error parser.
- Runtime errors (as opposed to the one observed syntax-error shape) remain untested; the heuristic's coverage of that failure mode is unconfirmed.
- Future versions may require additional patterns as new GAUSS failure shapes are observed.
- False positives and false negatives remain possible for error shapes not yet seen — this is documented in the function's own docstring, not hidden.
