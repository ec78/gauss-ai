# v0.7.0 Broader Command Coverage and Automated Evidence Tests Plan

## Release Goal

`v0.6.0` proved that command lookup evidence can be represented in a structured, validated schema: a formal JSON Schema, a validator with pass/fail/warning semantics, opt-in schema-aligned output from the retrieval prototype, and manual evaluation coverage across every realistic evidence state (valid, incomplete, not found, ambiguous, conflicting, stale, and structurally invalid).

`v0.7.0` should move from **"the evidence system works"** to **"the evidence system is harder to regress."** Concretely:

- Real schema-aligned evidence exists for more than the current two pilot commands (`olsmt`, `strindx`), covering a deliberately varied set of documentation shapes.
- Every committed schema-aligned example and fixture can be checked in one pass, so a broken fixture or a schema drift is caught immediately instead of discovered the next time someone happens to run the validator by hand on that one file.
- Validator warning quality improves where the fix is low-risk, without weakening the schema or accepting more false positives than necessary.
- `scripts/command_doc_lookup.py`'s extraction completeness improves in narrow, low-risk ways (for example, capturing more of a truncated struct field list) without a rewrite.
- None of this breaks the legacy (non-`--schema-output`) lookup format, which remains the default and must stay byte-for-byte compatible.

This is still a prototype-stage milestone. It does not execute GAUSS code, does not stand up a hosted or shared retrieval service, and does not attempt to index all of GAUSS's documentation — it makes the existing small, local-first system more trustworthy to extend.

## Scope

- Add more real schema-aligned command examples, generated by actually running `scripts/command_doc_lookup.py --schema-output` against a local official docs checkout (never hand-authored to look real).
- Add a script or test entry point that validates all schema-aligned examples and schema fixtures in one pass, rather than requiring someone to remember to run the validator against each file individually.
- Add documentation for running these validation checks, including what a clean run looks like and what a regression looks like.
- Improve validator warning quality where possible — specifically the known path-detection false-positive on official documentation examples (e.g., the `olsmt` HDF5-URI case) — without loosening the schema itself.
- Improve `scripts/command_doc_lookup.py` extraction completeness where low-risk, such as reducing truncation on large output-structure sections (the `olsmtOut` field list gap identified back in `v0.5.0`/`v0.6.0` evaluations is the clearest concrete target).
- Add benchmarks for automated evidence validation if appropriate, distinct from the response-quality benchmarks (`12.x`) and the schema-state benchmarks (`13.x`) already covered.

## Non-goals

- No GAUSS code execution engine.
- No hosted retrieval service.
- No full MCP server implementation.
- No automatic indexing of all GAUSS documentation.
- No breaking changes to legacy lookup output — `scripts/command_doc_lookup.py` without `--schema-output` must remain byte-for-byte compatible with today's behavior.
- No release of machine-local paths in any newly committed example or fixture.

## Candidate Commands for Expanded Coverage

All names below are real, category-verified commands from `experts/gauss-language/COMMAND_CATEGORIES.md`. None of their syntax, arguments, defaults, or return values are asserted here — they are candidates for future `scripts/command_doc_lookup.py --schema-output` runs and evaluation only, exactly like `olsmt` and `strindx` were before `v0.4.0`.

| Command | Category | Why it's useful | Likely schema fields exercised | Priority |
|---|---|---|---|---|
| `strsplit` | String Handling | Different return shape than `strindx` (likely an array/multiple-piece result instead of a scalar index), broadening string-command coverage beyond the not-found/`idx == 0` pattern already well-tested. | `verified_syntax`/`syntax_blocks`, `returns_section` with a non-scalar return description, `examples`. | High |
| `dstatmt` | Descriptive Statistics and Computation | Likely has a paired control-structure/output-structure pattern similar to `olsmt`, making it a good second data point for whether the schema and extraction generalize to another struct-heavy command. | `controls_section`, `outputs_section` (possibly another large struct prone to truncation), `unresolved_questions`/`extraction_warnings` if truncated. | High |
| `qnewtonmt` | Optimization and Solution | Already flagged as a strong candidate in the `v0.5.0` plan: its category has a sibling `minimizecontrolcreate`-style pattern, suggesting a control-structure/output-structure pair from a domain (optimization) with zero current coverage. | `controls_section`, `formula_section` (unlikely to apply), `outputs_section`, possibly a second file for a paired control-creation command — good test of the "docs split across multiple files" open question from `v0.5.0`. | High |
| `pdsummary` | Panel Data | Panel/time-series domain has zero current schema-aligned coverage; likely exercises DataFrame-oriented documentation structure distinct from `olsmt`'s matrix-oriented one. | `inputs_section` describing DataFrame/panel-index inputs, `examples`, possibly `related_links` to other panel commands. | High |
| `loadd` | Data Import and Export | Extremely commonly used (already referenced in nearly every existing example's setup comments); foundational for DataFrame-based workflows; likely a simpler, shorter doc page — useful as a low-complexity contrast to `olsmt`. | `verified_syntax`, `inputs_section` (file path/format arguments), `returns_section` (DataFrame return). | Medium |
| `glm` | Estimation Methods | Complements `olsmt` in the same category with a different model family; likely has its own control-structure pattern, useful for testing whether response guidance generalizes across two modeling commands rather than just one. | `controls_section`, `outputs_section`, `formula_section` if formula-string input is supported. | Medium |
| `xlsreadm` | Data Import and Export | Alternate file-format import (Excel vs. `loadd`'s more general path), useful for checking whether the extractor handles a differently-structured "Format"/"Remarks" page reasonably. | `verified_syntax`, `inputs_section`, `examples`. | Low |
| `csvreadm` | Data Import and Export | Another alternate import path; lower priority than `xlsreadm` since it's likely to have a similar doc shape to other import commands already covered. | `verified_syntax`, `inputs_section`. | Low |
| `minimize` | Optimization and Solution | A newer GAUSS 26 optimization command (L-BFGS-B, bound-constrained), publicly documented at `docs.aptech.com/gauss/minimize.html`. Complements `qnewtonmt` with current-version optimization coverage and a bound-constrained (vs. unconstrained) algorithm; likely has its own control-structure pattern (`minimizecontrolcreate`) similar in shape to `qnewtonmt`'s. Only add as a real schema-aligned example if `minimize.rst` exists in the local docs checkout — do not hand-write evidence from the public web page. | `verified_syntax` (function-pointer call, multiple optional-argument formats), `controls_section`, `outputs_section`, `formula_section` (unlikely to apply). | High if local docs available, otherwise a documented follow-up |

Recommended `v0.7.0` scope: the four original **High** priority commands (`strsplit`, `dstatmt`, `qnewtonmt`, `pdsummary`) give the best category spread (string, statistics, optimization, panel/DataFrame) for the least effort and are now all complete. `minimize` is an added High-priority candidate specifically for *current-version* optimization coverage, contingent on local docs availability (see below). The **Medium** and **Low** candidates remain reasonable stretch goals or `v0.8.0` carryover.

**`qnewtonmt` vs. `minimize`.** These are not redundant: `qnewtonmt` provides established, already-verified optimization-command coverage (unconstrained quasi-Newton optimization, already exercised in `examples/retrieval/schema-aligned/qnewtonmt.evidence.json`). `minimize` provides current-GAUSS-26 optimization-command coverage (bound-constrained L-BFGS-B) and should be added alongside `qnewtonmt`, not in place of it — `qnewtonmt`'s example should not be removed or treated as superseded.

## Automated Validation Plan

Design (not implemented in this planning pass) for `scripts/validate_all_evidence.py`:

- **Inputs to validate:**
  - Every file under `examples/retrieval/schema-aligned/*.json` — expected to pass.
  - Every file under `examples/retrieval/schema-fixtures/*.json` matching a "valid" naming convention (e.g., not `invalid-*`) — expected to pass.
  - `examples/retrieval/schema-fixtures/invalid-missing-required-fields.json` (and any future `invalid-*` fixtures) — expected to **fail**, and the script should treat that expected failure as a pass for its own purposes.
- **Behavior:**
  - Reuse `scripts/validate_lookup_evidence.py`'s validation logic (import it, not reimplement it) so there is one source of truth for schema/warning checks.
  - Support `--strict` to propagate strict-mode warning-as-failure behavior into the aggregate run.
  - Support `--json` to emit a machine-readable summary (per-file results plus an overall pass/fail).
  - Print a concise human-readable summary by default: file count checked, pass count, expected-fail count, unexpected-fail count, and total warnings.
  - Return exit code 0 only when every "should pass" file passes (under the current strictness setting) and every "should fail" file fails; return nonzero if any file behaves unexpectedly in either direction (a "should pass" file failing, or a "should fail" file unexpectedly passing).
- **Distinguishing expected-invalid fixtures from real regressions:** rather than hardcoding file names, use a simple, documented naming convention (files under `schema-fixtures/` prefixed `invalid-` are expected to fail; everything else under `schema-aligned/` and `schema-fixtures/` is expected to pass) so adding a new fixture later doesn't require editing the validator-runner's logic.

This design is deliberately conservative: it composes the existing validator rather than duplicating its rules, so schema or warning-check changes only need to happen in one place.

## Benchmark Plan

Proposed new category, **"Automated Evidence Validation" (category 14)**, continuing the existing per-category numbering convention (Retrieval = 11, Retrieval Integration = 12, Evidence Schema = 13, Automated Evidence Validation = 14):

- **14.1 — All valid examples and fixtures pass validation.** Run (or ask the assistant to reason about running) `scripts/validate_all_evidence.py` and confirm every schema-aligned example and valid fixture reports a pass. Expected behavior: the assistant reports the aggregate result accurately and does not claim success without citing the actual run.
- **14.2 — Intentionally invalid fixture still fails as expected.** After the automated runner exists, confirm `invalid-missing-required-fields.json` (or a newly added `invalid-*` fixture) is still correctly reported as an expected failure, not silently passed due to a runner bug. Expected behavior: the assistant distinguishes "this failed, as designed" from "this failed unexpectedly."
- **14.3 — Real command evidence with warnings is handled correctly.** Present a newly generated real schema-aligned example (from the `v0.7.0` command list) that has at least one validator warning, and ask whether it's safe to use. Expected behavior: mirrors the `13.7`/`13.1` discipline — inspect the actual warning, distinguish pass-with-warnings from failure, and don't overstate the evidence as warning-free.
- **14.4 — Expanded command examples do not regress prior examples.** After adding new schema-aligned examples, confirm the original `olsmt.evidence.json`/`strindx.evidence.json` still validate identically to before. Expected behavior: the assistant (or the automated runner) catches any accidental schema or script change that would have altered previously-passing evidence.
- **14.5 — Legacy lookup output remains backward compatible.** After any `scripts/command_doc_lookup.py` extraction improvements, confirm legacy (non-`--schema-output`) output for `olsmt` and `strindx` is still byte-for-byte identical to the currently committed `.lookup.json` files. Expected behavior: the assistant treats any diff here as a blocking regression, not a minor detail.

## Risks and Design Questions

- **How many real commands are enough for `v0.7.0`?** This plan recommends 4 (the High-priority set) as the primary target, with Medium/Low as stretch goals, to keep the milestone reviewable rather than turning into an open-ended indexing project.
- **Should warning false positives fail CI?** Not by default — `scripts/validate_all_evidence.py`'s baseline behavior should treat warnings as non-blocking (matching `scripts/validate_lookup_evidence.py`'s existing non-strict default), with `--strict` available for anyone who wants a stricter gate. Automatically failing on the known `olsmt` HDF5-path false positive would be actively counterproductive.
- **How to handle local docs availability?** New schema-aligned examples can only be generated on a machine with a local official GAUSS docs checkout, same constraint as `v0.4.0`-`v0.6.0`. If a docs root isn't available when this milestone is implemented, this plan's Task Order explicitly allows generating fewer examples rather than fabricating output.
- **Should generated evidence be committed or regenerated on demand?** This plan assumes committed (matching `v0.4.0`-`v0.6.0` precedent for `olsmt`/`strindx`), since committed evidence is what benchmarks and the automated validator actually check against. Regenerate-on-demand would require a docs checkout at evaluation time, which isn't guaranteed.
- **How to keep examples path-safe?** Continue the existing pattern: `--redact-docs-root` for `docs_root`, relative `file_path` values (already produced automatically by `scripts/command_doc_lookup.py`), and a final grep-for-absolute-paths check before committing, exactly as performed in the `v0.6.0` readiness audits. Known false-positive path-shaped official-docs examples (like `olsmt`'s HDF5 URI) are not local leaks and should not be stripped.
- **How to avoid treating schema validity as GAUSS semantic correctness?** Keep restating it explicitly in every new example's surrounding documentation and in any new benchmark expectations — this has been a recurring theme since `v0.6.0` and should not be allowed to fade as more examples are added.

## Suggested Task Order

1. **Planning** — this document.
2. **Choose pilot commands** — confirm the final `v0.7.0` command list (starting from the High-priority four) against actual local docs availability before committing to specific commands.
3. **Generate additional schema-aligned examples** — run `scripts/command_doc_lookup.py --schema-output --redact-docs-root` for each chosen command and commit the real output, following the same honesty practices established for `olsmt`/`strindx` (no hand-editing, warnings documented not suppressed).
4. **Add the validate-all script** — implement `scripts/validate_all_evidence.py` per the design above.
5. **Add tests or benchmark prompts** — add 14.1-14.5 to `evaluations/benchmark-prompts.md`.
6. **Run manual evaluations** — evaluate the new benchmarks plus a regression check against the `13.x` evaluations to confirm nothing broke.
7. **Tracking/readiness** — update `INDEX.md`, `benchmark-coverage.md`, `CHANGELOG.md`, `ROADMAP.md`, `KNOWN_LIMITATIONS.md`, and draft a `v0.7.0` readiness checklist following the `v0.4.0`-`v0.6.0` precedent.
8. **Release** — tag only after the readiness checklist reports no blockers, as a separate explicit action.

## Readiness Criteria

Before tagging `v0.7.0`:

- At least the four High-priority commands (or a documented, justified subset if local docs access was limited) have real, committed schema-aligned examples.
- `scripts/validate_all_evidence.py` exists, runs successfully against the full current set of examples and fixtures, and correctly distinguishes expected-pass from expected-fail files.
- All new benchmark prompts (14.1-14.5) have been manually evaluated and pass, or any failures have a documented follow-up.
- Legacy lookup output for `olsmt` and `strindx` is confirmed byte-for-byte unchanged from the `v0.6.0` baseline.
- No newly committed example or fixture contains an unredacted local absolute path (verified by the same grep-based check used in prior readiness audits).
- `CHANGELOG.md`, `ROADMAP.md`, and `KNOWN_LIMITATIONS.md` accurately reflect what was actually delivered, not just what was planned.
- A `v0.7.0` readiness checklist has been produced and reports no blockers.
