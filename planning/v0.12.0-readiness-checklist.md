## Cleanup and Guard Summary

### GAUSS Language knowledge.md disposition

`experts/gauss-language/knowledge.md` is now a compatibility placeholder, replacing its prior unexplained one-line stub ("Placeholder for domain knowledge notes."). It states plainly that `experts/gauss-language/BODY_OF_KNOWLEDGE.md` is the active, authoritative knowledge source, and that `knowledge.md` is not a separate or competing source. No behavior change is implied: nothing in the Code Assistant's workflows, prompts, or task modes ever read `knowledge.md`'s content directly, so replacing the placeholder text changes nothing about how the GAUSS Language Expert actually operates. This mirrors the disposition already applied to `experts/econometrics/knowledge.md` in `v0.11.0`, closing a follow-up that `v0.11.0`'s own readiness checklist explicitly deferred.

### Release-readiness check

`scripts/check_release_readiness.py` was added. Default mode runs exactly two checks — `validate_all_evidence.py` and `check_evaluation_tracking.py`, both in default (non-strict) mode — and exits nonzero only if either default check fails; confirmed directly from the script's own logic (`return 0 if default_pass else 1`). `--json` reports `overall_pass` based on the default checks only, in every case, including when `--strict` is also passed. `--strict` additionally runs both underlying scripts' strict mode, but reports that result in a clearly separate, labeled "informational" section — it never redefines what counts as default release readiness and never affects the script's own exit code. No warnings are suppressed anywhere in this: the script prints each underlying command's real stdout/stderr verbatim.

### Strict-mode CI expectations

Default checks (`validate_all_evidence.py`, `check_evaluation_tracking.py`, or `check_release_readiness.py` with no flags) are the current release-health gates. Strict checks (`--strict`) are warning-free gates and are currently expected to fail, for specific, named, reviewed reasons:
- Evidence strict fails on exactly `glm.evidence.json` and `olsmt.evidence.json`, both reviewed HDF5-URI path-warning false positives from official documentation examples.
- Tracking strict fails on exactly two documented historical warnings: the `2.2`/`2.3` Prompt ID mismatch, and the unindexed `v0.3.0` smoke-test file.

If CI is added in the future, it should start with default checks only (`scripts/check_release_readiness.py`, no flags) — running `--strict` in CI today would make every run fail on the same already-reviewed warnings, training reviewers to ignore CI failures. Warnings must never be hidden or suppressed just to make CI (or this script) report green; a future warning should be resolved at its source or explicitly documented as a reviewed exception by name, never silenced by weakening a validator.

### PACKAGE_DOC_DIRECTORIES refresh process

`PACKAGE_DOC_DIRECTORIES` (`scripts/command_doc_lookup.py`, added `v0.11.0`) is a hardcoded snapshot derived from the official GAUSS Applications index (`docs_root/applications.rst`), not live parsing — the tool does not read that file at lookup time. The refresh process is now documented as concrete steps in `scripts/README.md`: inspect `applications.rst`'s `:link:` targets, compare against the current set, update only directories actually present in the index, regenerate/validate only affected evidence if needed, and re-run `validate_all_evidence.py` to confirm no new unexpected result. This is source classification only, not licensing verification — the Code Assistant must still state a package's actual licensing/version dependency explicitly whenever it recommends a package-sourced command.

## Final Validation and Guard State

- `python scripts/validate_all_evidence.py --json`: confirms the same (`"overall_pass": true`, `"unexpected_count": 0`, `"total_warnings": 6`).
- `python scripts/validate_all_evidence.py --strict`: `Overall: FAIL`, exactly 2 unexpected files (`glm.evidence.json`, `olsmt.evidence.json`).
- `python scripts/check_evaluation_tracking.py` (default, re-run for this audit): `76` prompt IDs, `76` coverage rows, `63` run files referenced, `68` index entries checked, `0` errors, `2` warnings, `Overall: PASS`.
- `python scripts/check_evaluation_tracking.py --json`: confirms the same structured result.
- `python scripts/check_evaluation_tracking.py --strict`: `Overall: FAIL` (exit 1), the same 2 documented historical warnings promoted.
- `python scripts/check_release_readiness.py` (default, re-run for this audit): `Default checks overall: PASS`, exit `0`.
- `python scripts/check_release_readiness.py --json`: `{"default_pass": true, "overall_pass": true, ...}`.
- `python scripts/check_release_readiness.py --strict`: default checks section still reports `PASS`; the separate, labeled "Strict Checks (informational; failure is expected)" section reports `FAIL` for both underlying scripts, with an explicit note that this does not affect the overall release-readiness result; script exit code remains `0`.

To be explicit about what these results mean: a default **PASS does not mean zero warnings** — it means zero errors/unexpected results, with the 2 (tracking) and 6 (evidence, across two files) warnings present and accounted for. **Release readiness is based on default gates only** — `check_release_readiness.py`'s pass/fail and its `--json` `overall_pass` field never incorporate strict-mode results, by design. Both **`--strict` failures are expected** and limited strictly to previously documented, reviewed, warning-promoted-to-failure cases — no new or unexplained strict-mode failure exists anywhere in the current repository state. Evidence validation checks structure only: it **does not prove GAUSS semantic correctness or that any GAUSS code was executed**.

## Important Findings

- Local release readiness is now easier to run consistently — one command (`scripts/check_release_readiness.py`) instead of remembering to run two separate scripts and combine their results by hand.
- Strict checks are now explicitly documented as informational, pre-CI, warning-free gates — not a second release-readiness bar a contributor might mistakenly think must also pass.
- Future CI can start with default checks without hiding any strict warning: the policy explicitly names every current strict failure rather than leaving CI's eventual scope ambiguous.
- Compatibility placeholders (now present for both `experts/econometrics/knowledge.md` and `experts/gauss-language/knowledge.md`) prevent an expert-knowledge file from reading as an unexplained gap or a competing, out-of-date source.
- The `PACKAGE_DOC_DIRECTORIES` refresh guidance reduces risk from a maintained snapshot by making the refresh steps concrete and repeatable, and by keeping the snapshot's failure mode bounded (under-classification only, never mis-classification) explicit.
