# v0.80.0 — Hybrid MCP Validation, Docs Fetch, and Validation Hardening: Design

## 1. Why

v0.79.0's MCP server wrapped `ConversationEngine.ask()` whole, including its own provider call. When the MCP client is itself a capable model (Claude, ChatGPT), that is a redundant second model hop, and it forces every user to configure a provider just to get grounded answers. Public distribution also needed documentation without asking users to clone a git repository.

The user approved four decisions:

- a **hybrid** design: the client model writes code, and gauss-ai validates it deterministically;
- keeping `gauss_chat_ask` as an explicit opt-in **strict mode**;
- a one-time, user-invoked documentation download from the published site;
- a narrow `CLAUDE.md` network exception for that download, with documentation fetched per user and never redistributed.

## 2. Gaps found during planning (fixed first, as prerequisites)

1. **Keyword-prefix call skipping.** Both `extract_generated_calls` and the engine's unknown-symbol checker skipped every line that `startswith` a construct keyword, with no word boundary. Effects:
   - Calls on `print`, `retp`, `if` and `while` lines were never extracted.
   - `printfm(...)`, `format = ...` and `forecast = arima(...)` lines were dropped entirely.
   - A hallucinated `print colmean(x);` was never flagged.
   - `print invpd({2 1, 3 2});` escaped its precondition check. The same gap let live evaluation 69.1 reach `HANDOFF_CANDIDATE` with nothing checked.

   **Fix:** a single shared `gauss_pre_execution_validation.call_scan_text(line)` used by both scanners. It skips only declaration lines (`proc`, `endp`, `local`, with word boundaries), masks string literals, and blanks a `for` header's loop variable. It returns text of the same length, so argument text is still sliced from the original line. A drift-guard test proves the two scanners see identical call symbols.
2. **No check for system-touching statements.** `y = invpd(...); dos "...";` could reach `HANDOFF_CANDIDATE`, and the execution helper does not sandbox GAUSS code (`allow_file_write` is accepted, then discarded).

   **Fix:** a doc-verified `_SYSTEM_STATEMENT_REGISTRY` with 50 names. Every entry was checked against a real page in the official docs; `export` was dropped because no page exists. It covers:
   - OS commands, process launch and process control;
   - `run` and `#include`;
   - directory changes;
   - file deletes, writes and reads.

   Matching handles both statement position and call shape, ignores string literals and same-named assignments, and fails closed. Any finding forces `NOT_READY` (the user's decision), checked first in `compute_handoff_readiness`. Principle: the handoff runs only self-contained snippets that compute in memory.

## 3. Shared validation chain

`ConversationEngine._validate_pre_execution` and `ask()`'s inline unknown-symbol pass became one module-level function, `validate_generated_code(generated_code, *, bundle, gate, docs_root_str, recent_topics, answer_text)`.

The refactor was proven behavior-preserving by snapshot: `repr(AnswerResult)` across 12 scenarios was byte-identical before and after. The scenarios included a multi-turn case where `recent_topics` matters.

## 4. `validate_code(code, *, docs_root)`

Grounding comes from the code's own called symbols, not from `ground_multi`, which is built for natural-language questions.

1. Extract calls with the fixed extractor.
2. Drop names that are `proc`-defined or assigned in the same code.
3. Look up each remaining name exactly as `resolve_concepts` looks up a literal token (`max_results=3`, `MIN_DOC_CONFIDENCE`).
4. Build a `GroundingBundle` directly and run `validate_generated_code`.

Checked against the real docs, the lookups accept real symbols (`invpd` at 0.6 via its combined page) and reject `colmean`, `matmean`, `invertmatrix`, `olsfit` and `meancol`.

Fail-closed rejections, with `rejected_reason`, never exceptions:

- empty code;
- a Markdown fence;
- more than 20,000 characters;
- more than 24 distinct calls;
- no configured documentation.

Code with no documented calls is `NOT_READY`, with an explanatory note. That is the same conservative outcome as `ask()`.

## 5. MCP tool surface

**Base tools (9):** `gauss_session_start`/`close` (renamed from `gauss_chat_start`/`close`), `gauss_search_docs`, `gauss_validate_code`, `gauss_execution_prepare(validation_id?)`, `gauss_execution_decide`, and the three repair tools.

**Opt-in tools (2):** `gauss_chat_ask`/`gauss_chat_reset`. `main()` registers them only when `chat-provider` resolves to something other than `fake`.

`validation_id` rules:

- issued only for `HANDOFF_CANDIDATE`;
- per session, capped at 8, oldest evicted;
- single-use;
- **re-validated at prepare time**, refused as `validation_stale` if the docs changed;
- `prepare` never accepts code directly.

Pending-request source is tracked, so a hybrid execution never clears a pending chat offer.

## 6. `gauss-ai docs fetch`

New module `gauss_docs_fetch.py` (stdlib `urllib`):

1. Read the page list from the published `searchindex.js`, excluding `_`-prefixed internal pages: 1,826 pages.
2. Download each page's `_sources/<file>.txt` and save it as `.rst` in the same layout.

Safety and robustness:

- Remote names are untrusted: absolute paths, `..` and escapes are rejected before any download.
- Downloads go to a staging directory, which is then atomically swapped in. Any failure aborts and keeps the previous cache, because the concept index's document-frequency filter needs the full corpus.
- `docs_root` is set only if unset; a path the user chose is never overridden.
- A manifest records the source and time.
- CLI: `gauss-ai docs fetch [--yes]` and `gauss-ai docs status`.
- `gauss-ai doctor` gained a local-only `docs_root` check: PASS, WARN when unset, FAIL when missing or empty.

**Real-fetch findings.** The first real run hit HTTP 403 partway through, while the same URL returned 200 a moment later: the site rate-limits. Retry behavior became:

- concurrency 2;
- backoff of 2s/5s/15s on 403, 429, 5xx and network errors;
- immediate failure on 404.

The second run fetched all 1,826 pages in 272 seconds, using the backoff 134 times.

A parity check against the local clone found that clone on `develop`, last updated 2026-06-02:

- 146 published pages missing from it (e.g. `dfaddcol`, `diagmat`, the "coming to GAUSS" guides);
- 383 unpublished draft pages present in it;
- about 26% of shared pages differing.

The published download is more current than the clone every prior evaluation was grounded against.

## 7. Deviations from the approved plan

- **`gauss-ai init` got a "next step" pointer instead of an interactive download prompt.** Every existing init test scripts its prompts exactly, so an extra prompt would have broken all of them, and keeping `init` offline is arguably better anyway.
- **System-statement matching masks string literals** instead of accepting string false positives. This was cheap and strictly more accurate.

## 8. Testing

New and updated tests:

- extraction (4) and the system gate (4) in `test_gauss_pre_execution_validation.py`;
- the engine: shared scanner, drift guard, end-to-end `ask()`, `validate_code` (9);
- `test_gauss_docs_fetch.py` (11, injected transport and sleep, network-free);
- doctor (2, plus test_17 updated with justification);
- `test_gauss_mcp_server.py` rewritten (21).

The full suite passes. No existing expectation changed except test_17 (justified inline) and the MCP tool-set test (justified inline).

## 9. Known limitations

- The hybrid path cannot *prevent* ungrounded code from being written, only from being validated or executed. Strict mode exists for that.
- Code with no documented calls is never executable.
- The fetch takes minutes because of rate limiting.
- There is no idle-session eviction.
- The MCP surface for v0.80.0 has not yet been exercised live against a real client (planned as evaluation 70.x).
