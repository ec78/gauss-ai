# v0.10.0 Evidence Coverage and Routing Regression Guards Plan

## Release Goal

`v0.9.0` proved that two operational experts can coexist and route correctly across GAUSS-only, Econometrics-only, Both, and Neither cases — but its own evaluations surfaced two real gaps in the evidence layer underneath that routing, plus a manual-tracking risk that has held so far only because every prior milestone was careful about it by hand. `v0.10.0` converts those findings into durable repository improvements rather than leaving them as evaluation-run footnotes: it adds local schema-aligned evidence for `glm` (closing the live-documentation dependency found in `16.7`), audits whether a real GAUSS panel-estimation command exists (closing the open question from `16.4`), and adds a lightweight, local, non-CI check that keeps benchmark prompts, run files, the run index, and the coverage table consistent with each other going forward — so a tracking drift is caught mechanically instead of only by an evaluator's diligence.

## Current State

- The evidence schema (`schemas/command_lookup_evidence.schema.json`) and aggregate validator (`scripts/validate_all_evidence.py`) exist and are exercised by real schema-aligned examples for seven commands plus five fixtures.
- Multi-expert routing exists (`workflows/expert-routing.md`, both operational profiles) and is fully integrated into the Code Assistant's response workflow, task modes, and system prompt.
- Benchmark category `16.x` (Multi-Expert Routing) is complete: all eight prompts evaluated and passed at 4.0.
- `glm` was verified during the `16.7` evaluation, but only via a live fetch of `docs.aptech.com/gauss/glm.html` — there is no local schema-aligned `glm.evidence.json`, so every future task needing `glm` evidence would have to re-fetch it live rather than inspecting a committed file.
- Panel-estimation coverage is unresolved: the `16.4` evaluation checked `experts/gauss-language/COMMAND_CATEGORIES.md`'s Panel Data category and found only data-management/descriptive utilities (`pdSummary`, `pdBalance`, `pdLag`, etc.), with no verified fixed/random-effects estimation command. This was correctly disclosed rather than papered over, but it remains an open question, not a documented conclusion.
- Tracking consistency (every benchmark prompt has a coverage row; every coverage row's run-file link actually exists; the run index and coverage table agree) has been maintained by hand across eleven benchmark categories (`1.x`-`16.x`) so far. This has worked, but nothing mechanically prevents a future task from adding a benchmark prompt without a matching coverage row, or a coverage row pointing at a run file that was never created.

## Scope

- Add schema-aligned command evidence for `glm`.
- Add or update a curated command note for `glm` only if it would add real value beyond the schema-aligned evidence, and only ever as a subordinate convenience reference per `workflows/command-documentation-retrieval.md`'s existing curated-cache policy.
- Audit official/local docs for panel-estimation commands (fixed effects, random effects, or an equivalent general-purpose panel regression estimator), building on the preliminary check already done in this planning task (see Deliverable 2).
- Document what is verified, unresolved, or not found for panel estimation, without inventing a command name to fill the gap either way.
- Add a lightweight tracking-consistency script or documented check for evaluations, covering benchmark prompt IDs, run files, run index entries, and coverage-table entries.
- Add benchmark prompts `17.1`-`17.6` for evidence coverage and tracking guards.
- Run `17.x` evaluations.

## Non-goals

- No runtime expert orchestration.
- No new operational expert.
- No full command index (this milestone adds targeted coverage for two specific gaps, not a comprehensive command catalog).
- No GAUSS execution engine.
- No weakening of evidence requirements.
- No treating command-category membership as exact syntax evidence.
- No inventing panel-estimation support if official evidence is missing — an honest "not found" is an acceptable, documented outcome for this milestone.
- No rewriting the whole evaluation framework — the tracking guard is additive tooling, not a redesign of `evaluations/scoring.md`, `workflows/manual-evaluation.md`, or the existing run-file format.

## Deliverable 1 — glm Evidence Coverage

**Preliminary finding from this planning task:** a local `glm.rst` file exists in the docs checkout used throughout this project (confirmed by direct inspection, not assumed). Spot-checking it confirms the same facts already verified live during the `16.7` evaluation: three call formats (`glm(y, x, family[, var_names[, categoryIdx[, link]]])`, `glm(y, x, family[, ctl])`, `glm(dataset_name, formula, family[, ctl])`), a `family` parameter with `"binomial"` among its documented options, `"logit"` as the default Binomial link, and the same worked logistic-regression example (`call glm(data, "admit ~ rank + gre + gpa", "binomial");`) that the live fetch returned. This means Deliverable 1 is a normal real-evidence-generation task like the `v0.7.0` pilot commands, not a documentation gap that requires falling back to online-only sourcing.

Plan:

- Generate schema-aligned evidence for `glm` from the official local docs using `scripts/command_doc_lookup.py glm --docs-root <path> --schema-output --redact-docs-root`, the same process used for every other real example in `examples/retrieval/schema-aligned/`.
- If a future regeneration ever finds the local docs missing `glm.rst` (environment-dependent), document the source and provenance clearly in the evidence file's `notes` and in `examples/retrieval/README.md` before falling back to any other sourcing — do not silently mix live-fetched and locally-generated evidence without saying so.
- Verify, from the extraction itself (not assumed from this planning task's preliminary check):
  - All supported call formats.
  - The `family` options list, including `"binomial"`.
  - The default Binomial link (`logit`).
  - The logistic-regression example.
  - Key output fields, only if actually documented and captured by extraction — if the extraction truncates before reaching the output structure (as happened with `olsmt` and `qnewtonmt`), disclose that rather than filling in unconfirmed fields.
- Validate with `scripts/validate_lookup_evidence.py` (single-file) and `scripts/validate_all_evidence.py` (aggregate) — both should pass in non-strict mode, consistent with the `v0.7.0` release-health bar.
- Add `glm` to the real-examples list in `examples/retrieval/README.md`, `scripts/README.md`, and `schemas/README.md` wherever the other seven commands are already listed, following the existing pattern rather than introducing a new one.
- Add a curated note (`experts/gauss-language/commands/glm.md`) only if evaluation reveals a specific, repeated need for one (per `commands/README.md`'s "only for high-value, failure-prone, or frequently evaluated commands" policy) — `glm`'s `16.7` benchmark result didn't identify a specific extraction gap a curated note would fix, so this is optional, not assumed necessary.

## Deliverable 2 — Panel Estimation Coverage Audit

**Preliminary finding from this planning task:** a first-pass search of the local docs checkout for panel-estimation-sounding files found three categories of near-misses, none of which is a general-purpose fixed/random-effects panel regression estimator:

1. `cc/panel-data.rst` — the category index already reflected in `COMMAND_CATEGORIES.md`'s Panel Data section (data-management/descriptive utilities only).
2. `tspdlib/docs/panel_fisher.rst`, `panel_surwald.rst`, `panel_zhnc.rst` — from the `tspdlib` package (later confirmed by direct inspection to be panel *Granger-causality* tests, not unit-root tests as their filenames initially suggested). These test a statistical property of panel data; they do not estimate a fixed/random-effects regression model.
3. `bhatlib/archived/gcmlpanel.rst` — an **archived**, package-specific gradient-computation helper for composite marginal likelihood estimation (confirmed by direct inspection: it returns four gradient-component matrices, not model estimates, and lives under an `archived/` path). Not a general-purpose panel estimator, and its archived status is itself worth noting.

This is a planning-stage spot-check, not the full audit — Deliverable 2's actual implementation should still systematically check package-level documentation (not just the core `cc/` category index) before concluding one way or the other, since GAUSS's panel-estimation support (if any) may live in a specific econometrics-focused package not yet searched.

Plan:

- Inspect local official docs and command categories for panel-estimation commands systematically — core `cc/panel-data.rst`, plus package-level docs (`tspdlib` and any other econometrics-oriented package directories) rather than the category index alone.
- Distinguish, in the audit's findings:
  - Panel data-management utilities already verified (`pdLag`, `pdBalance`, `pdSort`, etc.).
  - Panel descriptive/summary utilities already verified (`pdSummary`).
  - Panel time-series/stationarity tests, if found (e.g., the `tspdlib` panel unit-root tests noted above) — a real capability, but not an estimation command, and worth naming as a distinct category so it isn't mistaken for one.
  - Actual panel-estimation commands (fixed effects, random effects, or equivalent), if found.
  - Unresolved or not-found estimation coverage, if none is found after the systematic check.
- If a panel-estimation command is found: generate schema-aligned evidence for it, validate it the same way as `glm`, and document its exact verified scope (which effects structure, which standard-error options, etc.) rather than overstating it as general-purpose if it's actually narrow.
- If none is found: add a clear, specific limitation note (not a vague "coverage is incomplete") stating exactly what was checked and what wasn't found, consistent with how `KNOWN_LIMITATIONS.md` already states this finding provisionally. Do not invent a command name to fill the gap. Preserve the methodology/implementation separation established in `v0.9.0` — the Econometrics Expert can still give full fixed-effects-vs-random-effects methodological guidance regardless of what this audit finds; only the GAUSS-side "here's the verified command" claim depends on the audit's outcome.

**Status: Done — a verified panel-estimation command was found, correcting the preliminary spot-check above.** Full audit: `examples/retrieval/panel-estimation-coverage-audit.md`. Systematically searching package-level docs (not just `cc/panel-data.rst`) found `tscsFit` in the `tsmt/` (TSMT) package directory — a genuine pooled time-series-cross-section regression estimator returning both fixed-effects and random-effects coefficient estimates. Schema-aligned evidence was generated and validated: `examples/retrieval/schema-aligned/tscsfit.evidence.json` (single-file `PASS`; `validate_all_evidence.py` default `PASS`, 14 files checked, 0 unexpected, 6 total warnings, unchanged from before — `tscsFit` introduced zero new warnings; `--strict` still fails only on the same two previously known files, `olsmt` and `glm` — `tscsfit` passes strict cleanly). Critical caveat documented in the audit: TSMT is a separately licensed commercial package (not base GAUSS, requires GAUSS/GAUSS Engine v25+), which the Code Assistant must state whenever `tscsFit` is recommended. The audit also corrected this planning task's own preliminary misclassification of the `tspdlib` panel tests (they test Granger causality, not unit roots/stationarity, per direct inspection) and found a real tooling gap worth tracking: `command_doc_lookup.py` does not yet distinguish `official_docs` from `official_package_docs` for package-located files — documented as a follow-up, not fixed in this task per the constraint against modifying the script without a clear bug.

## Deliverable 3 — Evaluation Tracking Guard

A lightweight, local script — `scripts/check_evaluation_tracking.py` — checking, at minimum:

- Every benchmark prompt ID in `evaluations/benchmark-prompts.md` has a corresponding row in `evaluations/benchmark-coverage.md`.
- Every `Passed`/`Failed` (or equivalent non-`Not Run`) coverage row has a run-file link.
- Every run file referenced by the coverage table actually exists under `evaluations/runs/`.
- Every existing run file has, at minimum, a Prompt ID, an Overall Score, and a Decision field (per `workflows/manual-evaluation.md`'s result template).
- `evaluations/runs/INDEX.md` includes every completed run file (no orphaned run file missing from the index).
- Duplicate Prompt IDs across coverage rows are flagged (a signal something was miscopied or double-added).
- `Not Run` coverage rows are not required to have a run-file link (this is the expected, healthy state for an unevaluated prompt, not a gap to report).

Design intent: mirror `scripts/validate_all_evidence.py`'s shape — a single-purpose aggregator with a clear pass/fail summary and per-item detail, reusing the existing markdown files as its only inputs (no new metadata format to maintain). Keep it simple and local; no CI setup is required for `v0.10.0`, though adding one later is a natural non-blocking follow-up once this script exists and has been exercised manually.

**Status: Done.** `scripts/check_evaluation_tracking.py` created and run against the real, current tracking state in all three modes:

- **Default:** `Benchmark prompt IDs found: 59`, `Coverage rows found: 59` (exact 1:1 match), `Run files referenced: 46`, `Run index entries checked: 51`. **0 errors**, 2 warnings, `Overall: PASS` (exit 0).
- **`--json`:** confirms the same counts and `"overall_pass": true`.
- **`--strict`:** the same 2 warnings are promoted to failures, `Overall: FAIL` (exit 1) — expected, per the same strict-mode-has-a-higher-bar convention already established for `validate_all_evidence.py`.

**The 2 warnings, both genuine and correctly left as warnings, not fixed:**
1. `benchmark-coverage.md` links Prompt `2.2` to `2026-06-30-code-assistant-manual-run-001.md`, but that run file's own `Prompt ID:` field says `2.3` — this is the exact documented historical mismatch `benchmark-coverage.md`'s own notes already explain (the run predates stable Prompt ID assignment); the guard correctly surfaces it without failing the default run.
2. `2026-07-01-code-assistant-smoke-test-v0.3.0.md` exists under `evaluations/runs/` but is referenced by neither `benchmark-coverage.md` nor `runs/INDEX.md` — a genuine, newly-surfaced finding: a legacy `v0.3.0`-era smoke test that predates the Prompt-ID-based tracking system entirely (confirmed by inspecting the file: it's a broader onboarding/quickstart smoke test, not a single-Prompt-ID benchmark run, so it doesn't fit the coverage/index schema and was correctly never force-fit into it). Documented here as an accepted, known warning rather than retrofitted into a schema it predates.

**One real bug was found and fixed during Task 3 testing (in the newly-written script itself, not in tracking files):** the initial version's "orphaned run file" check globbed every `*.md` under `evaluations/runs/` including `README.md` (a documentation file describing the directory, not an evaluation run), producing a false-positive warning. Fixed by excluding `README.md` alongside the already-excluded `INDEX.md`.

## Risks and Design Questions

- **What if local official docs do not include `glm`?** Not applicable in practice — confirmed present during this planning task — but the contingency plan (documented sourcing, no silent live/local mixing) is stated in Deliverable 1 regardless, since this repository's docs checkout path is environment-dependent and shouldn't be assumed identical in every future session.
- **Should online-official docs be represented differently from local-official docs?** Yes, in principle — the schema's `source_type` enum already has room for this distinction (e.g., `official_local_rst` is used today; a hypothetical `official_online` type doesn't currently exist). This milestone doesn't need to resolve it since local docs are available for both `glm` and the panel audit, but it's worth flagging as a schema question for whenever a command genuinely has no local documentation available.
- **How much panel coverage should be included before the milestone becomes too large?** Scoped deliberately narrow: audit and document, generate real evidence *only if* a genuine estimation command is found, and explicitly accept "not found, clearly documented" as a valid, complete outcome — this milestone is not committed to shipping panel-estimation evidence, only to resolving the open question honestly.
- **Should the tracking guard be a script or checklist first?** A script, per the task's own naming (`scripts/check_evaluation_tracking.py`) and Deliverable 3 above — a checklist alone wouldn't actually catch a mismatch the next time someone forgets to update `benchmark-coverage.md`, which is the whole point of adding this now rather than continuing to rely on manual diligence.
- **How strict should the guard be with older benchmark categories?** It should report what it finds, not silently special-case old categories — but `17.6`'s evaluation explicitly plans to cross-check any reported gap against `benchmark-coverage.md`'s own "Completed Runs Not Directly Covered By Current Stable Prompts" section, which already documents several intentional historical mismatches (`2.1`/`4.1` runs predating stable Prompt IDs). The guard should surface these as known, not as new failures.
- **How to avoid turning this into a full CI project?** By stopping at a local, manually-run script with clear output, per Deliverable 3's explicit "no CI setup required yet" — CI integration is listed only as a future non-blocking follow-up, not part of this milestone's scope.
