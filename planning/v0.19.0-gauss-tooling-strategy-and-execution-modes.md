# v0.19.0 - GAUSS Tooling Strategy and Execution Modes

## Release Goal

`v0.19.0` begins the transition from a documentation/evaluation-driven Code Assistant toward a tool-enabled GAUSS assistant that can optionally inspect the local GAUSS environment, identify installed GAUSS packages, run GAUSS code, capture results, and help users generate reports.

The goal of this milestone is not to implement execution yet, but to define the strategy and boundaries for:

- Checking whether GAUSS is installed.
- Identifying GAUSS version.
- Identifying installed GAUSS packages.
- Running GAUSS code when available.
- Capturing output and generated artifacts.
- Helping users interpret results.
- Helping users generate reports.
- Preserving advisory-mode behavior when GAUSS is not installed.

State clearly:

- Execution is an optional capability, not a requirement for the assistant to function.
- Advisory mode — the assistant's entire current behavior — remains fully supported regardless of whether execution is ever added.
- No runtime orchestration is implemented by this planning task.
- No GAUSS code is executed by this planning task.

## Current State

- The six-expert system (`experts/EXPERT_REGISTRY.md`) is complete and consolidated as of `v0.18.0` — GAUSS Language, Econometrics, Software Engineering, Documentation, Education, and Product experts all operational, with a registry, boundary matrix, routing cheat sheet, evaluation dashboard, and maintenance guide in place.
- The Code Assistant can write, explain, review, document, teach, and product-frame GAUSS-related work, per `agents/code-assistant/AGENT.md` and `workflows/code-assistant-response.md`.
- The system has verified command evidence (`examples/retrieval/schema-aligned/*.evidence.json`, `schemas/command_lookup_evidence.schema.json`) and retrieval-backed response patterns (`workflows/retrieval-backed-response-pattern.md`).
- The system has evaluation, tracking, and release-readiness guards (`scripts/validate_all_evidence.py`, `scripts/check_evaluation_tracking.py`, `scripts/check_release_readiness.py`, `.github/workflows/release-readiness.yml`).
- The system does not currently inspect a local GAUSS installation.
- The system does not currently list installed packages.
- The system does not currently run GAUSS code.
- The system must not claim execution unless an execution tool actually runs code — this constraint already exists today (`agents/code-assistant/AGENT.md`'s Limitations and Failure Modes sections, every `OPERATIONAL_PROFILE.md`'s refusal conditions) and `v0.19.0` does not weaken it; it only plans how a future execution tool would satisfy it.

## Target Operating Modes

### Advisory Mode

**Use when:**

- GAUSS is not installed.
- GAUSS availability is unknown.
- Execution tools are unavailable.
- The user does not request execution.
- Execution is unsafe or out of scope.

**Capabilities:**

- Write GAUSS code.
- Explain GAUSS code.
- Review code.
- Suggest diagnostics.
- Design analyses.
- Use verified command evidence.
- Create docs, tutorials, and reports as drafts.
- Identify what should be run later.

**Required constraints:**

- Do not claim execution.
- Label code as unexecuted.
- Distinguish verified syntax from unverified syntax.
- Distinguish advice from results.
- Provide next steps for running locally if useful.

This is the assistant's entire current mode of operation as of `v0.18.0`. Nothing about `v0.19.0` changes this mode's behavior or requirements.

### Verified Knowledge Mode

**Use when:**

- GAUSS may or may not be installed.
- Exact GAUSS command claims are backed by verified evidence.
- Execution has not occurred.

**Capabilities:**

- State verified command signatures or known usage patterns.
- Cite or reference evidence artifacts.
- Distinguish native commands from custom/manual fallbacks.
- Recommend package requirements when known.

**Required constraints:**

- Verified command evidence is not execution.
- Command availability does not prove methodological correctness.
- Evidence validation is structural, not semantic execution.

Verified Knowledge Mode already exists in substance today — it is what the GAUSS Language Expert's evidence-backed responses already do. `v0.19.0` names it explicitly as a distinct mode so that a future execution tool's outputs can be clearly distinguished from evidence-backed-but-unexecuted claims, rather than the two blurring together once execution becomes possible.

### Execution Mode

**Use when:**

- GAUSS is installed and detected.
- Required tools are available.
- The user permits or requests execution.
- The execution context is safe and scoped.

**Capabilities:**

- Inspect GAUSS version.
- Inspect installed packages.
- Run GAUSS code.
- Capture stdout/stderr/logs.
- Inspect generated output files.
- Summarize results.
- Diagnose runtime errors.
- Compare expected vs. actual behavior.
- Help generate reports from actual output.

**Required constraints:**

- Report the execution environment.
- Report package availability.
- Separate runtime errors from methodology errors.
- Do not overclaim statistical validity from successful execution.
- Do not overclaim product value from successful execution.
- Preserve the six expert boundaries (`experts/EXPERT_BOUNDARY_MATRIX.md`).
- Gracefully fall back if execution fails or GAUSS is unavailable.

Execution Mode does not exist today. It is the subject of future milestones (`v0.20.0`-`v0.22.0` below) and is not implemented by this planning task.

## Graceful Fallback Principle

- The assistant must not break if GAUSS is not installed.
- GAUSS availability should change capabilities, not core assistant identity — the Code Assistant remains the same assistant, with or without execution available.
- If GAUSS is unavailable, the assistant should continue in Advisory or Verified Knowledge Mode.
- If a user asks to run code but GAUSS is unavailable, the assistant should:
  - State that execution is unavailable.
  - Provide the code.
  - Explain how to run it locally.
  - Identify expected outputs where appropriate.
  - Avoid pretending results exist.
  - Offer troubleshooting steps for installing/configuring GAUSS only if appropriate.

This principle generalizes the existing rule already stated in `agents/code-assistant/AGENT.md` ("Claim code has been executed unless it has actually been run by an available tool") to a whole-system design constraint: every future execution-related tool must have a documented, non-breaking degraded state, not just a documented success state.

## Proposed Tool Capabilities

Plan future tools, but do not implement them yet. Each tool below follows `TOOL_SPEC.md`'s structure (Purpose, Tool Role, Inputs, Outputs, Permission Model, Invocation Rules, Failure Modes, Evaluation Criteria) — a real future tool spec should fill in that full template, not just this summary.

### GAUSS Environment Detection Tool

**Possible file:** `tools/gauss_environment_check.md`

**Purpose:**

- Determine whether GAUSS is installed or discoverable.
- Identify OS/platform assumptions.
- Locate executable path if possible.
- Identify GAUSS version if available.
- Report unavailable/unknown states cleanly.

**Inputs:**

- Optional preferred GAUSS executable path.
- Optional working directory.
- Optional environment variables.

**Outputs:**

- `installed`: true/false/unknown
- `executable_path`
- `version`
- `platform`
- `detection_method`
- `warnings`
- `errors`
- `fallback_mode_recommendation`

**Failure behavior:**

- Return a structured unavailable/unknown state.
- Do not throw an unhandled failure.
- Recommend advisory mode.

This is a read-only tool per `TOOL_SPEC.md`'s "Read-Only Tools" category — it inspects, it does not modify.

### GAUSS Package Inspection Tool

**Possible file:** `tools/gauss_package_inspection.md`

**Purpose:**

- Identify installed GAUSS packages/libraries where possible.
- Distinguish base GAUSS capabilities from installed packages.
- Report package availability before code execution.
- Support package-aware response guidance.

**Inputs:**

- GAUSS executable path or environment handle.
- Optional package names to check.
- Optional working directory.

**Outputs:**

- `packages_detected`
- `package_name`
- `package_version` if available
- `installed`: true/false/unknown
- `detection_method`
- `warnings`
- `errors`

**Failure behavior:**

- Return an unknown state if inspection cannot be performed.
- Do not block advisory mode.

This is also a read-only tool. It depends on the Environment Detection Tool having already established that GAUSS is installed and where.

### GAUSS Code Execution Tool

**Possible file:** `tools/gauss_code_execution.md`

**Purpose:**

- Run scoped GAUSS code when GAUSS is installed.
- Capture output, errors, logs, and generated files.
- Support execution-aware debugging and analysis.

**Inputs:**

- Code or script path.
- Working directory.
- Execution timeout.
- Package requirements.
- Expected output files.
- Execution mode/safety constraints.

**Outputs:**

- `executed`: true/false
- `exit_status`
- `stdout`
- `stderr`
- `logs`
- `generated_files`
- `runtime_errors`
- `warnings`
- `environment_summary`
- `package_summary`

**Failure behavior:**

- Return a structured failure.
- Preserve code and diagnostic context.
- Recommend advisory-mode fallback when appropriate.

Per `TOOL_SPEC.md`'s "High-Risk Tools" category, this is the only proposed tool that runs code rather than only inspecting state — a real future spec should classify it as high-risk and define the extra controls (timeouts, scoped working directory, explicit user permission) that category requires.

### Result Reporting Workflow

**Possible file:** `workflows/analysis-result-reporting.md`

**Purpose:**

- Convert GAUSS execution output into user-facing summaries and reports.
- Separate actual results from interpretation.
- Distinguish runtime success from methodological validity.
- Support reproducible report drafts.

This is a workflow, not a tool — it consumes the Execution Tool's structured output and the relevant experts' interpretation, rather than performing inspection or execution itself.

## Tool Safety and Scope Rules

- Never claim code ran unless the execution tool reports `executed: true`.
- Never hide runtime errors.
- Never treat successful execution as statistical validity.
- Never treat successful execution as maintainability.
- Never treat successful execution as product value.
- Do not run code outside a scoped working directory.
- Use timeouts.
- Report generated files explicitly.
- Preserve user data privacy assumptions.
- Do not modify user files unless explicitly requested.
- Prefer read-only inspection for environment/package checks.
- Execution tools should return structured results rather than freeform-only output.
- Advisory mode must remain available after any tool failure.

These rules are the `v0.19.0`-specific application of `TOOL_SPEC.md`'s general permission model (Read-Only, Write-Capable, High-Risk) and `REASONING_FRAMEWORK.md`'s validation principles ("Validate tool outputs before relying on them," "Validate that risky actions were avoided or explicitly authorized") to the specific case of GAUSS execution.

## Relationship to Six Experts

- **GAUSS Language Expert** uses environment/package/execution evidence for implementation correctness — a successful run is stronger evidence than unexecuted verified syntax, but it is still bounded by the same evidence rules in `experts/gauss-language/OPERATIONAL_PROFILE.md`; it does not grant the GAUSS Language Expert authority over any other dimension.
- **Econometrics Expert** uses execution output as data but still owns methodology and interpretation — a regression that runs successfully is not evidence the model specification is appropriate; per `experts/EXPERT_BOUNDARY_MATRIX.md`, "clean code proves statistical validity" is already a named false equivalence, and "successful execution proves statistical validity" is the same trap in a new form.
- **Software Engineering Expert** uses runtime errors and structure but still owns maintainability/design — a runtime error can reveal a design flaw, but a clean run does not certify good design.
- **Documentation Expert** may document actual executed behavior but must not invent results — documenting real output is stronger grounding than documenting assumed output, but the Documentation Expert still does not independently verify GAUSS syntax, statistical validity, or execution; it reports what the execution tool actually returned.
- **Education Expert** may turn executed examples into lessons but must not treat execution as learning effectiveness — a runnable example is a better teaching artifact than an unverified one, but running successfully does not prove the lesson taught anything.
- **Product Expert** may reason about the workflow impact of execution capability (e.g., "does execution reduce time-to-value for a given user workflow?") but must not treat tool success as product validation — a working execution tool is not evidence that users want it, adopt it, or that it solves a real problem; per `experts/EXPERT_BOUNDARY_MATRIX.md`'s escalation matrix, product value still requires actual user/customer evidence, not internal capability alone.

No expert's boundaries from `experts/EXPERT_BOUNDARY_MATRIX.md` change as a result of tools becoming available. Execution changes what evidence is available to an expert; it does not change which expert owns which correctness dimension, and it does not let one dimension substitute for another.

## Risks and Design Questions

- How will GAUSS be invoked across platforms (Windows, macOS, Linux)?
- How will the GAUSS executable path be discovered — environment variables, known install locations, user-provided configuration, or all three?
- How will package lists be detected reliably, given GAUSS packages are directory-based rather than centrally registered?
- Can GAUSS package versions be inspected consistently across packages, or only for some?
- What working directory and file permissions are safe for a code-execution tool to use by default?
- How should timeouts work — a fixed default, a user-configurable value, or task-dependent?
- What output files should be captured — only files explicitly named by the user/script, or anything written to the working directory during the run?
- How should generated files be linked or summarized in a response without dumping raw binary or oversized content?
- How should execution errors be represented — as a single `runtime_errors` field, or structured by error type (syntax, dimension, missing package, I/O, other)?
- How should user-provided data files be handled with respect to privacy and scope — should the tool ever read files outside the declared working directory?
- How should execution mode work in environments where GAUSS licensing is unavailable (e.g., a package requiring a separate license, as `tscsFit`/TSMT already does today per `KNOWN_LIMITATIONS.md`)?
- How should the assistant distinguish "not installed" from "not accessible" (e.g., installed but not on `PATH`, or installed but the license file is missing)?
- How should the assistant keep advisory mode useful when execution is unavailable, rather than treating it as a degraded fallback?
- What claims can be made from successful execution alone (the code ran, produced this output) versus what still requires expert interpretation (the output means X, the model is appropriate, the design is good, the feature is valuable)?
- Should execution tools be local-only, connector-based, MCP-based, or all of these later? This is explicitly not decided by this planning task.
