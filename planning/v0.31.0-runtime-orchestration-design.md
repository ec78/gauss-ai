# v0.31.0 Runtime Orchestration Design

## Milestone Goal

`v0.31.0` designs the architecture that connects:

- user execution request
- execution intent recognition
- workflow mode selection
- eligibility review
- safety review
- execution-plan presentation
- explicit user confirmation
- helper invocation
- structured result capture
- execution-aware analysis
- report generation
- final response

State clearly:

- This milestone begins as design-only. No orchestration code is written in `v0.31.0`'s first task.
- Implementation should not start until interfaces and state transitions are agreed — the Suggested Task Order below treats interface/contract definition as prerequisite work, not a parallel track.
- Runtime orchestration must preserve every `v0.30.0` consent and safety requirement without exception: advisory-first behavior, explicit and non-implied consent, the four execution modes, the pre-execution safety-review checklist, working-directory/file-handling boundaries, the rerun/repair policy, and the evidence/trust boundaries already defined in `workflows/real-execution-user-workflow.md`. Orchestration is a *mechanism* for enforcing those rules consistently across turns — it is not a license to relax any of them.

## Current State

- `scripts/gauss_code_execution.py` exists and can execute a verified terminal GAUSS batch invocation (`tgauss.exe -b <script_path>`), confirmed on Windows/GAUSS 26.1.1 for completed, failed (two runtime-error types), and output-file-writing cases.
- `workflows/real-execution-user-workflow.md` exists, defining execution eligibility, consent, safety review, and response patterns — but as **documentation the assistant follows manually**, not as code any controller enforces.
- `workflows/code-assistant-response.md` routes to the real-execution workflow (Section 9), execution-aware analysis (Section 10), and report generation (Section 11) — but this routing is a documented decision sequence, not a state machine with enforced transitions.
- `workflows/execution-aware-analysis.md` exists, governing interpretation of a structured execution result once one exists.
- `workflows/report-generation.md` exists, governing turning that evidence into a structured report when requested.
- Current transitions between these components are manual: a human (or an LLM following the documented workflows) reads the applicable workflow file at each step and decides what to do next. Nothing programmatically enforces that eligibility passed before a safety review ran, or that a safety review passed before confirmation was requested.
- There is no runtime orchestration controller — no code owns "what state is this execution request in."
- There is no automatic tool invocation — `execute_gauss_code(...)` is called only when a human/evaluation harness calls it directly; nothing in the assistant's response pipeline calls it based on a state transition.
- There is no persisted execution-session state — nothing tracks, across turns, what code was shown, what plan was confirmed, or whether a given confirmation is still valid for the current request.

## Desired End-to-End Flow

1. **User request received** — assistant reasoning (Step 1 of `workflows/code-assistant-response.md`, task classification).
2. **Execution intent classified** — assistant reasoning, informed by `workflows/real-execution-user-workflow.md`'s trigger-case list; distinguishes review/explanation/debugging from an actual run/test/execute/smoke-test/rerun request.
3. **Execution mode selected** — workflow state; one of Advisory, Proposed Execution, Assisted Execution, Post-Execution Analysis, per the Real-Execution Decision Checkpoint.
4. **Required execution inputs collected** — assistant reasoning + workflow state; code/script, working directory, executable, timeout, expected writes. Pattern C ("Request Missing Inputs") applies here.
5. **Eligibility decision completed** — workflow state, evaluated against `workflows/real-execution-user-workflow.md`'s Execution Eligibility Decision criteria.
6. **Safety review completed** — workflow state, evaluated against the Pre-Execution Safety Review checklist.
7. **Exact execution plan shown** — assistant reasoning producing a user-facing artifact (Pattern B, "Offer Execution").
8. **Explicit user confirmation obtained** — a genuine turn boundary; consent is a fact about what the user said, not something the assistant infers.
9. **Execution request frozen** — workflow state; the confirmed plan becomes immutable and is what gets executed, not a paraphrase of it.
10. **Helper invoked** — tool action; the one place `execute_gauss_code(...)` is actually called, through a single controlled adapter.
11. **Structured result validated** — tool action + workflow state; the raw helper result is schema-validated and classified.
12. **Result routed to execution-aware analysis** — assistant reasoning, per `workflows/execution-aware-analysis.md`.
13. **Report-generation workflow invoked when appropriate** — assistant reasoning, per `workflows/report-generation.md`, only when a report/summary was actually requested.
14. **Final response produced** — assistant reasoning, per Step 7/Steps 12+ of `workflows/code-assistant-response.md`.
15. **Execution record retained only within defined boundaries** — workflow state, bounded by the Conversation and Session Boundaries section below; no unbounded persistence.

Steps 2, 4 (the collection dialogue), 7, 12, 13, and 14 are **assistant reasoning** — they require judgment, natural-language generation, and workflow-file-grounded decision-making that a state machine does not itself perform. Steps 3, 5, 6, 9, and 15 are **workflow state** — deterministic classifications and transitions a controller can and should own so they are not re-derived inconsistently turn to turn. Steps 8, 10, and 11 are the only genuine **tool/system actions** in this flow: step 8 is an external fact (what the user typed), and steps 10-11 are the one real boundary crossing into a subprocess and back.

## Architectural Principles

- Advisory-first.
- Explicit consent.
- No hidden execution.
- No implied consent.
- Deterministic execution request — the same confirmed inputs always produce the same request object; no reinterpretation at invocation time.
- Frozen confirmed plan — once confirmed, the request that gets executed is exactly what was shown, not a re-derived version of it.
- Least privilege.
- Bounded filesystem access.
- Terminal GAUSS only (`tgauss`/`tgauss.exe`; GUI `gauss.exe` remains refused).
- No package installation.
- No license activation.
- No network access.
- No global configuration mutation.
- No silent retries.
- No automatic repair loop.
- Structured outputs.
- Evidence-aware interpretation.
- Methodology validity remains separate from execution status.
- Honest capability disclosure — the orchestration layer must be able to say "I can't actually invoke the tool right now" rather than fabricate a result, mirroring the discipline already demonstrated in `31.5`'s evaluation.
- Fail closed on ambiguity — an orchestration controller that cannot confidently classify a state defaults to `blocked`/Advisory rather than guessing forward.

## Proposed Components

### Execution Intent Classifier

- Distinguishes review, explanation, debugging, generation, and execution requests.
- Distinguishes an explicit run request from implied interest ("this looks like it would run fine" is not a request to run it).
- Identifies post-execution interpretation requests (a structured result is already present).
- Avoids treating code presence alone as consent — code being shown or generated is never itself a request to execute it.

### Execution State Machine

- Tracks mode and current state for a given execution request.
- Prohibits invalid transitions (see "State Machine" below).
- Preserves consent boundaries as a first-class invariant, not an incidental check.
- Requires renewed confirmation after any meaningful change to the frozen request.

### Execution Request Builder

- Collects code or script path (mutually exclusive, mirroring the existing tool contract's `code_source` field).
- Collects working directory.
- Collects executable path (or accepts environment-detection output).
- Collects timeout.
- Identifies expected writes.
- Identifies expected input/output files.
- Produces a canonical execution request (see "Execution Request Contract" below) — the single artifact that eligibility, safety review, confirmation, and invocation all operate on.

### Eligibility Evaluator

- Determines whether the request is eligible for real execution, per `workflows/real-execution-user-workflow.md`'s Execution Eligibility Decision.
- Rejects the GUI executable.
- Rejects an unknown working directory.
- Rejects writes outside the allowed directory.
- Rejects package/license/network/global-configuration requirements.
- Rejects destructive or unclear-side-effect behavior.
- Rejects requests that would imply unsupported production-readiness or cross-platform/cross-version certainty.

### Safety Review

- Inspects filesystem impact (writes, deletions, overwrites).
- Inspects the timeout value.
- Inspects the executable.
- Inspects input/output scope.
- Inspects destructive or persistent effects.
- Produces a user-visible safety summary — the same content the Offer Execution response pattern already shows the user, generated once and reused rather than re-derived per response.

### Consent Manager

- Binds consent to the exact frozen execution request (by fingerprint — see "Execution Request Contract").
- Records what the user actually confirmed, not what the assistant intended to run.
- Invalidates consent the moment the request changes in any material way.
- Prevents reuse of stale consent for a materially different request.
- Distinguishes a specific confirmation ("yes, run exactly that") from general approval ("sounds good," "sure," a compliment about the plan) — only the former counts.

### Helper Adapter

- Converts the canonical execution request into a single `execute_gauss_code(...)` invocation.
- Validates helper inputs before calling.
- Invokes the helper exactly once per confirmed request.
- Captures the structured result unmodified.
- Never constructs a shell command directly — all invocation goes through the helper's existing `command_builder`/`runner` abstractions; the adapter does not duplicate or bypass that logic.
- Never retries automatically.

### Result Validator

- Validates the result against `schemas/gauss_code_execution.schema.json`.
- Distinguishes helper/tool failure, GAUSS runtime error, timeout, and successful completion, using the result's own `execution_status`/`executed`/`operating_mode` fields rather than re-deriving classification logic.
- Preserves raw stdout/stderr as evidence, unmodified.
- Preserves the `output_files` metadata boundary — metadata in, metadata out, never inferred content.
- Flags incomplete or malformed results rather than passing them downstream silently.

### Analysis Router

- Routes completed (or failed/timed-out/blocked) results into `workflows/execution-aware-analysis.md`.
- Routes methodology questions to expert reasoning (principally the Econometrics Expert), never answering them from execution status alone.
- Routes report requests into `workflows/report-generation.md`.
- Never treats execution success as analytical or statistical validity — this is the same boundary already enforced in every `29.x`/`30.x`/`31.x` evaluation, made structural here rather than only convention.

### Response Composer

- Produces the user-facing summary.
- Discloses plainly whether execution occurred.
- Reports errors honestly, using captured evidence rather than invented detail.
- Lists output metadata without inferring contents.
- Distinguishes execution findings from methodology findings in the same response.
- Presents safe next actions (rerun with confirmation, provide missing input, review output files explicitly, etc.).

### Execution Record

A minimal execution record, containing only:

- `request_id` — an opaque identifier for this specific execution request.
- `state` — current state-machine value (see "State Machine").
- `confirmed_request_snapshot` — the exact frozen request the user confirmed (see "Execution Request Contract").
- `consent_reference` — a timestamp or turn reference marking when/how consent was given; not the raw conversation text.
- `helper_result` — the structured result returned by the helper, once invoked.
- `output_metadata` — the `output_files` array from the result (metadata only, never content).
- `analysis_status` — whether execution-aware analysis has been applied.
- `report_status` — whether report generation has been applied, and to what report type.
- `rerun_eligible` — whether a rerun could be proposed from this state, and under what conditions.

Do not include: raw user-provided secrets, full conversation transcripts, file contents, or any data not required to reconstruct what was requested, confirmed, and returned. The record exists to support consent validation and auditability (see "Observability and Auditability"), not to be a general-purpose conversation log.

## State Machine

**States:**

- `advisory` — no execution request is active; the default state.
- `collecting_inputs` — an execution intent was recognized but required inputs are incomplete.
- `proposed` — a complete execution plan has been built and shown to the user, awaiting confirmation.
- `awaiting_confirmation` — equivalent to `proposed` from the controller's perspective; kept as a distinct name because some designs may want to distinguish "plan just shown" from "plan shown, prompt issued, actively waiting."
- `confirmed` — the user has explicitly confirmed the exact displayed plan; the request is now frozen.
- `executing` — the helper adapter has been invoked and has not yet returned.
- `execution_completed` — the helper returned a result with `execution_status: completed`.
- `execution_failed` — the helper returned a result with `execution_status` in `{failed, timed_out, error}`.
- `analyzing` — the result is being routed through execution-aware analysis.
- `report_generating` — the report-generation workflow is being applied.
- `completed` — the full flow (execution + analysis + optional report) has concluded and a final response was produced.
- `cancelled` — the user withdrew the request before execution, or explicitly declined to proceed.
- `blocked` — eligibility or safety review failed; execution cannot proceed without a materially different request.

**Valid transitions (non-exhaustive, illustrative):**

`advisory → collecting_inputs` (intent recognized, inputs incomplete)
`advisory → proposed` (intent recognized, inputs already complete)
`collecting_inputs → proposed` (inputs completed)
`collecting_inputs → blocked` (an input reveals an ineligible request)
`collecting_inputs → cancelled` (user withdraws)
`proposed → awaiting_confirmation` (prompt issued)
`awaiting_confirmation → confirmed` (explicit confirmation received, tied to the exact displayed plan)
`awaiting_confirmation → cancelled` (user declines)
`awaiting_confirmation → collecting_inputs` (user changes something — new request, fresh input collection)
`confirmed → executing` (helper adapter invoked)
`executing → execution_completed`
`executing → execution_failed`
`execution_completed → analyzing`
`execution_failed → analyzing` (failure is still evidence to be interpreted, per `workflows/execution-aware-analysis.md`'s `failed`/`timed_out` handling)
`analyzing → report_generating` (a report was requested)
`analyzing → completed` (no report requested)
`report_generating → completed`
`execution_failed → collecting_inputs` (user wants to propose a fix — this re-enters input collection for a *new* request, never `executing` directly)
`blocked → collecting_inputs` (the blocking condition is resolved with new/changed inputs)
`cancelled → collecting_inputs` (user re-initiates after cancelling — a wholly new request, no reuse of the cancelled one's `request_hash`/consent)

**Compact transition table** (entry condition and valid exits for every non-terminal state; `—` marks terminal/resumable-only states with no further forward exit of their own):

| State | Entry condition | Valid exits | Terminal? |
|---|---|---|---|
| `advisory` | Default; or any terminal/blocked state once its request is abandoned | `collecting_inputs`, `proposed` | No (resumable default) |
| `collecting_inputs` | Execution intent recognized; required inputs incomplete | `proposed`, `blocked`, `cancelled` | No |
| `proposed` | All required-before-confirmation fields populated; safety review passed | `awaiting_confirmation` | No |
| `awaiting_confirmation` | Plan shown; confirmation prompt issued | `confirmed`, `cancelled`, `collecting_inputs` | No |
| `confirmed` | Explicit confirmation received, tied to the exact displayed `request_hash` | `executing` | No |
| `executing` | Helper adapter invoked; synchronous call in flight | `execution_completed`, `execution_failed` | No |
| `execution_completed` | Helper returned `execution_status: completed` | `analyzing` | No |
| `execution_failed` | Helper returned `execution_status` in `{failed, timed_out, error}`, or the request was blocked/errored before invocation completed | `analyzing`, `collecting_inputs` (new rerun request only) | No |
| `analyzing` | A result (completed or failed) is being interpreted | `report_generating`, `completed` | No |
| `report_generating` | A report was requested and analysis finished | `completed` | No |
| `completed` | Final response produced | `advisory` (new, unrelated request), `collecting_inputs` (rerun) | Yes (for this request) |
| `cancelled` | User withdrew before or during execution | `collecting_inputs` (wholly new request) | Yes (for this request) |
| `blocked` | Eligibility or safety review failed | `collecting_inputs` (after the blocking condition changes) | Yes (for this request; resumable only via a new/changed request) |

`completed`, `cancelled`, and `blocked` are terminal **for the request that reached them** — the state machine does not resurrect a completed/cancelled/blocked request into a live one; any further action creates a new `request_id`. This is a deliberate consistency point with the Consent Model's "no reuse of stale consent" and the Rerun and Repair Policy's "always a new request" rule.

**Prohibited transitions:**

- `advisory → executing` (must pass through proposal and explicit confirmation).
- `collecting_inputs → executing` (incomplete inputs can never reach invocation).
- `awaiting_confirmation → executing` without an explicit `confirmed` transition in between — confirmation is a distinct, logged event, not something inferred from silence or a vague reply.
- `execution_failed → executing` directly (any rerun must pass back through `collecting_inputs → proposed → confirmed`, per the Rerun and Repair Policy — no shortcut, even for a trivial-looking fix).
- Reusing a `confirmed` state whose underlying request has changed — any change invalidates the `confirmed` state and forces a return to `collecting_inputs`/`proposed`.
- `blocked → executing` without first leaving `blocked` via a resolved, re-evaluated request.

## Execution Request Contract

**Authoritative source:** `planning/v0.31.0-canonical-execution-request-contract.md` is now the single, authoritative specification of the Canonical Execution Request — its full 18-field inventory, lifecycle, path/environment/confirmation contracts, canonicalization procedure, hash-inclusion matrix, validation sequence, Helper Adapter projection, persistence/logging rules, examples, and open decisions. This section is retained only as a high-level summary; where anything here and the authoritative document ever appear to disagree, the authoritative document governs.

**Summary:** the request is a canonical, internal design contract for this milestone — **not** a change to `schemas/gauss_code_execution.schema.json` (which remains the unmodified *result* schema) and **not** a formal JSON Schema of its own (see Open Questions). It has 18 fields: `request_id`, `code`, `script_path`, `working_directory`, `output_directory`, `executable_path`, `timeout_seconds`, `expected_input_files`, `expected_output_files`, `required_packages`, `allow_output_files`, `execution_purpose`, `user_confirmed`, `confirmation_scope`, `confirmation_timestamp`, `environment_summary`, `safety_review`, and `request_hash`. Three fields were renamed from an earlier draft of this document to align exactly with the verified helper parameter names and the canonical contract's own naming (`allowed_write_directory` → `output_directory`; `confirmation_timestamp_or_turn_reference` → `confirmation_timestamp`) — the rationale for each rename is documented in the authoritative document's field inventory, not repeated here.

Thirteen of the 18 fields contribute to `request_hash` and invalidate confirmation when changed (`code`, `script_path`, `working_directory`, `output_directory`, `executable_path`, `timeout_seconds`, `expected_input_files`, `expected_output_files`, `required_packages`, `allow_output_files`, `environment_summary`, `safety_review`) — note that `allow_output_files` was reclassified as hash-included during the canonical-contract work, reversing this document's own earlier, looser treatment of it; the reversal and its rationale are recorded in the authoritative document, not silently applied here. The remaining five (`request_id`, `execution_purpose`, `user_confirmed`, `confirmation_scope`, `confirmation_timestamp`) do not contribute to the hash, for reasons specific to each (identity, descriptive-only, or self-referential — see the authoritative document's hash-inclusion matrix).

**Helper-parameter clarifications, summarized** (full detail and the complete field-by-field Helper Adapter projection now live in the authoritative document's own sections): `allow_file_write`, `capture_stdout`, `capture_stderr`, and `validate_schema` are all documented no-ops on `execute_gauss_code(...)` itself; real schema validation is a separate call, `validate_against_schema(...)`, that the Result Validator must invoke explicitly after a result returns; `output_directory` already exists as a real, validated helper parameter (not a future one); and the Helper Adapter must always supply explicit environment context plus `strict=True` so the helper never silently re-detects a different environment at invocation time than was shown pre-confirmation.

## Consent Model for Orchestration

- **What qualifies as explicit consent:** an unambiguous, affirmative statement that is clearly and specifically about the exact plan just displayed — e.g., "yes, run that," "confirmed, go ahead with that plan." A reply must be interpretable as referring to the specific displayed `request_hash`, not to the conversation in general.
- **When consent is requested:** only after the full plan has been built (all required-before-confirmation fields populated) and the safety review has passed. Consent is never requested for a partial or unreviewed plan.
- **What exact information is shown before consent:** every field listed as "must be user-visible before confirmation" above, in the same shape as `workflows/real-execution-user-workflow.md`'s Consent Prompt.
- **How the confirmed request is frozen:** `request_hash` is computed once the plan is finalized and shown; `confirmation_scope` records that same hash at the moment of confirmation. The frozen request that reaches the helper adapter is the object matching that hash, never a re-derived or re-summarized version.
- **When consent expires or becomes invalid:** immediately upon any change to a fingerprinted field (see above), or if execution does not occur within the same logical turn/session the plan was confirmed in and the user later asks to proceed after enough time/context has passed that re-confirmation is the safer default — this milestone does not attempt to define a precise timeout for "how long is confirmation valid," and leaves it as an Open Question below.
- **How rerun consent works:** a rerun is always a *new* execution request with its own `request_id` and `request_hash`; it never reuses the prior request's `confirmation_scope`, even if the code is byte-for-byte identical, because the Rerun and Repair Policy requires a fresh safety review and fresh confirmation regardless.
- **How changed code invalidates consent:** any difference in `code`/`script_path` content changes `request_hash`, resetting `user_confirmed` to `false` and returning the state machine to `collecting_inputs`/`proposed`.
- **How changed paths invalidate consent:** any difference in `working_directory`, `executable_path`, or `output_directory` changes `request_hash` identically to a code change.
- **How changed timeout or file writes invalidate consent:** any difference in `timeout_seconds` or `expected_output_files` (or a newly-introduced write that wasn't previously expected) changes `request_hash` identically.
- **Why "go ahead" is only valid when immediately tied to a displayed plan:** an unqualified "go ahead" said minutes/turns after a plan was shown, or said about a different topic entirely, cannot be reliably matched to a specific `request_hash` — the Consent Manager should require the confirmation to occur in direct response to the still-current proposal, not treat any affirmative-sounding phrase anywhere in the conversation as consent. This is the direct enforcement mechanism for `workflows/real-execution-user-workflow.md`'s "Do not run based on implied consent" rule.
- **Not reusable across reruns:** already stated above — every rerun is a new request/hash/confirmation, with no exception for "the code is identical to last time."
- **Not reusable across sessions:** a `confirmation_scope` recorded in one session must never be treated as valid in a different session, even for what looks like the identical request — because this design assumes no durable cross-session persistence (see Conversation and Session Boundaries), a confirmation from a prior session simply does not exist for the Consent Manager to find; the request must be rebuilt and reconfirmed from scratch.
- **Not reusable after expiry:** this design does not fix a precise timeout for confirmation validity (left as an Open Question), but establishes the default posture: if there is genuine doubt about whether a displayed plan is still the one the user is responding to (a long gap, an intervening unrelated topic, a resumed conversation), the safer default is to fail closed and re-present the plan for fresh confirmation rather than assume it still applies.
- **Minimum evidence for a genuine `confirmed` transition** (platform-agnostic — this does not prescribe a chat UI, a button, or a specific phrase): (1) a plan was displayed with every user-visible field populated and a passed safety review; (2) the user's very next contribution is affirmative and specifically responsive to that plan (not a general affirmative statement elsewhere in the conversation); (3) the plan the user is responding to is still the current one — no edit has occurred between display and confirmation. All three must hold; any one missing means no `confirmed` transition occurs.
- **Distinguishing confirmation from general interest in execution:** "that would be interesting to run," "I bet that works," or "you could execute this" are expressions of interest, not confirmation of a specific displayed plan, and must not trigger a `confirmed` transition — this mirrors the Execution Intent Classifier's "avoid treating code presence as consent" responsibility, extended to avoid treating enthusiasm as consent.

## Tool Invocation Boundary

- Orchestration must call the execution helper through exactly one controlled adapter (the Helper Adapter component above).
- No arbitrary shell execution anywhere in the orchestration layer.
- No direct invocation of GAUSS outside the helper — the adapter is the only caller of `execute_gauss_code(...)`.
- No GUI invocation — the adapter must reject (not silently substitute) a request whose `executable_path` resolves to `gauss.exe`.
- No automatic package installation.
- No environment mutation.
- No retry loop — a failed or timed-out invocation ends that request's `executing` state; any subsequent attempt is a new, separately confirmed request.
- Helper output must be schema-validated against `schemas/gauss_code_execution.schema.json` before being passed to the Result Validator's classification logic.
- Raw tool evidence (`stdout`, `stderr`, `exit_code`, `output_files`) must be preserved unmodified through the adapter — no summarization or filtering at this layer; that belongs to the Response Composer, downstream.
- Orchestration must not fabricate an execution result when the tool/adapter is unavailable — it must disclose that plainly (as `31.5`'s evaluation already demonstrated is the correct behavior) rather than presenting a synthetic result as real.

**Helper-boundary findings from direct inspection of `scripts/gauss_code_execution.py` (this review's verification pass; no invented behavior):**

- `execute_gauss_code(...)` never raises — every internal step (environment resolution, input validation, code preparation, runner invocation) is wrapped so that an unexpected exception still returns a structured `execution_status: error` result rather than crashing the caller. The Helper Adapter can rely on always receiving a dict-shaped result, never an exception, from a well-formed call.
- Command construction is genuinely structured, not shell-string-based: `_default_command_builder` returns a `list[str]` (`[executable_path, "-b", script_path]` for terminal executables), and the default runner calls `subprocess.run(command, ..., shell=False)` with that list directly. A human-readable `command` string is joined only for display/result purposes (`" ".join(command_list)`), never re-parsed or re-executed as a shell string. This confirms the "no shell injection surface" claim rather than merely asserting it.
- `output_directory` is a **real, already-implemented** helper parameter — it is validated via the same path-containment logic as `script_path`/`input_files` (must resolve inside `working_directory`, path traversal is rejected) and defaults to `working_directory` when omitted. This corrects an inaccuracy in an earlier draft, which described this field (then named `allowed_write_directory`) as supporting "a future" design; the parameter and its structural enforcement already exist, and the field has since been renamed to `output_directory` to match the helper's own parameter name exactly (see `planning/v0.31.0-canonical-execution-request-contract.md`). What remains genuinely unverified (per `KNOWN_LIMITATIONS.md`) is only *real GAUSS execution behavior* when an explicit, non-default `output_directory` is supplied — not the parameter's existence.
- `allow_file_write` is accepted but is a documented no-op in the current implementation (see Execution Request Contract's "Helper-parameter clarifications"); orchestration must not describe it as a control that changes helper behavior.
- **Determinism gap identified and closed by this review:** without an explicit `environment_check_result`/`executable_path`+`gauss_version` and `strict=True`, the helper will silently call `gauss_environment_check`'s auto-detection at invocation time. If orchestration built the displayed plan from one environment snapshot but the helper then re-detects a *different* environment at `executing` time (for example, a newly available GAUSS version), the executed request could diverge from the confirmed one. The Tool Invocation Boundary therefore requires the Helper Adapter to always pass explicit environment context and `strict=True`, so environment resolution happens once (during Eligibility Evaluation, before the plan is shown) and never silently again at invocation.
- The helper's own failure/status vocabulary, confirmed directly in code, is the vocabulary orchestration's Result Validator must reuse rather than reinvent: `execution_status` ∈ `{completed, failed, timed_out, skipped, blocked, error, unknown}`, with `executed: true` only for `completed`/`failed`/`timed_out`. A `blocked`/`skipped` result never reaches `executing` in the state machine — it corresponds to the Eligibility Evaluator/Safety Review/Execution Request Builder rejecting the request *before* invocation, and the state machine should never represent it as having entered `executing` at all.
- `validate_against_schema(result, schema_path)` is a separate function from `execute_gauss_code(...)`; the `validate_schema` parameter on the latter is a no-op. The Result Validator component must call `validate_against_schema(...)` itself after receiving a result — this was underspecified in the original draft's phrasing ("helper output must be schema-validated") without naming which call performs it.

## Failure Taxonomy

Refined against the helper's actual status vocabulary (`execution_status` ∈ `{completed, failed, timed_out, skipped, blocked, error, unknown}`; `executed` boolean) confirmed directly in `scripts/gauss_code_execution.py`. Categories are grouped by the stage at which they are first detected — several categories never reach the helper at all, and the table makes that explicit rather than implying every row is a helper outcome.

| Category | Stage detected | Helper status (if reached) | Execution occurred? | Confirmation consumed? | Result retained? | Analysis allowed? | Rerun eligible? | New confirmation required? | Blocking? | Required disclosure |
|---|---|---|---|---|---|---|---|---|---|---|
| Missing inputs | Execution Request Builder | N/A — never reached | No | No | No | No | N/A | N/A (never confirmed) | No — resolvable | Ask for the smallest missing input (Pattern C) |
| Ineligible request | Eligibility Evaluator | N/A — never reached | No | No | No | No | N/A | N/A | Yes, until request changes | Explain why, per eligibility criteria |
| Unsafe request | Safety Review | N/A — never reached | No | No | No | No | N/A | N/A | Yes, until request changes | Decline, explain, propose safe alternative (Pattern D) |
| Confirmation rejected | Consent Manager (`awaiting_confirmation → cancelled`) | N/A — never reached | No | No (explicitly declined) | No | No | N/A | Yes, if user later wants to proceed | No — user-directed | Acknowledge, no further action unless the user restarts |
| Consent missing | Consent Manager (`proposed`/`awaiting_confirmation`) | N/A — never reached | No | No | No | No | N/A | N/A (first request) | No — resolvable | Present plan, request confirmation (Pattern B) |
| Consent stale | Consent Manager (request changed after display, before confirmation) | N/A — never reached | No | No (prior confirmation, if any, discarded) | No | No | N/A | Yes | No — resolvable | Re-present the (possibly changed) plan, request fresh confirmation |

| Output metadata present, content unread | Result Validator / Response Composer | `completed` (or `failed`, if files were written before failure) | Yes | Yes | Yes | Yes | N/A | N/A | No | List metadata, state contents unread (Pattern I) |
| Duplicate execution attempt | Consent Manager / Helper Adapter (a second invocation is attempted for a `request_hash` already in `executing`/`execution_completed`/`execution_failed`) | N/A — rejected before a second helper call | No (for the duplicate attempt) | N/A (the original confirmation already applies to the original attempt only) | The original result is retained; the duplicate attempt is refused | N/A | N/A | A genuinely new run requires a new request | Yes, for the duplicate attempt | Report that this request already ran; show the existing result instead of invoking again |
| User cancellation before execution | Any pre-`executing` state | N/A — never reached | No | No | No | No | N/A | N/A | No | Acknowledge, no further action |
| User cancellation during execution | `executing` | Whatever the synchronous helper call returns once it returns (see File Lifecycle Design's synchronous-call caveat — genuine mid-call cancellation is not available) | Ambiguous — the call is synchronous and cannot be cooperatively interrupted; "cancellation" here can only mean the user withdrew interest while waiting, not that the process was actually killed | Yes | Yes, whatever result the call returns | Depends on what returned | N/A, unless a result exists | Yes, with fresh confirmation | No | Disclose the synchronous-call limitation plainly: the call could not be interrupted, so the result (if any) reflects what actually ran |

**Explicit design guarantee, restated from the components above:** analysis failure never rewrites `execution_status`, and report-generation failure never erases or reinterprets a validated execution result — both failure modes are downstream-only and must never be allowed to retroactively change what the Result Validator already determined.

## Rerun and Repair Design

- No automatic reruns, under any failure category.
- The assistant may diagnose a failure and propose revised code, per `workflows/real-execution-user-workflow.md`'s Rerun and Repair Policy.
- Revised code must be shown to the user in full, not summarized as "fixed."
- A new execution request (`request_id`, `request_hash`) must be created for any rerun — never a mutation of the prior request.
- The safety review must run again against the new request, even if the change looks trivial.
- The user must confirm again, tied to the new `request_hash`.
- The prior execution result remains a distinct record — it is not overwritten or merged with the new attempt.
- Any comparison between runs (e.g., "did the fix work?") must clearly attribute each piece of evidence to its own request/result, never blending stdout/stderr from two different runs into one narrative.

## File Lifecycle Design

- Working directory validation happens once, during Execution Request Builder, and is re-validated if the working directory changes (which invalidates consent, per the Consent Model).
- `output_directory` enforcement is the Helper Adapter's responsibility, delegating to the helper's existing working-directory-containment logic rather than reimplementing it.
- Temporary/generated scripts (for inline `code`) follow the helper's existing behavior — generated exactly once per invocation, excluded from `output_files`, consistent with the `v0.28.0`/`v0.29.0`-verified exclusion behavior.
- Input files must be explicit (`expected_input_files`); no implicit discovery of "nearby" files, mirroring the helper's existing `input_files` contract.
- Output metadata collection is the Result Validator's responsibility — it passes through the helper's `output_files` array unmodified.
- File-reading (turning `output_files` metadata into actual content) remains a separate workflow, explicitly out of `v0.31.0`'s scope (see Non-Goals and Open Questions).
- Cleanup responsibility: this design does not assume the orchestration layer deletes anything. No file is ever deleted unless a future milestone explicitly designs and the user explicitly confirms a deletion action — absent that, generated artifacts remain in the working directory for the user to manage.
- No deletion unless explicitly designed and confirmed — this applies to the orchestration layer itself, not just the executed GAUSS code (which is already prohibited from destructive behavior by the eligibility criteria).
- Future artifact handoff (e.g., passing an output file into a later report-generation step) must go through an explicit, safe file-reading workflow — not an implicit assumption that "the file is there so it can be read."
- **File-name collisions:** the helper does not rename or version colliding output files — if a script writes to a filename that already exists, GAUSS's own overwrite behavior (not orchestration's) determines the outcome. Orchestration's Safety Review should flag a foreseeable collision against `expected_output_files` and existing directory contents *before* confirmation, since the Pre-Execution Safety Review already requires confirming "code does not overwrite unrelated files" — but this is a pre-flight check, not an enforcement mechanism inside the synchronous helper call itself.
- **Duplicate request handling:** two confirmed requests targeting the same `working_directory`/files are not merged or deduplicated by this design; each is its own `request_id` with its own safety review. It is the Safety Review's job to flag, not silently allow, an apparent collision between a new request and a still-open or recent one in the same directory.
- **Interruption or process-restart behavior:** because the Execution Record is not assumed durable (see Conversation and Session Boundaries), a process restart or interruption while `executing` leaves an ambiguous outcome — the helper's underlying `subprocess.run(..., timeout=...)` may still be running, may have completed, or may have been killed by the OS, and orchestration has no record to consult afterward. The safe design posture is to fail closed: after any interruption, treat the interrupted request as `unknown`/not confirmed, require the user to rebuild and reconfirm before any further attempt, and never assume the interrupted run's result (if any file changes are visible on disk) can be safely attributed without independent verification.
- **Cancellation limitations once a synchronous helper call begins:** `execute_gauss_code(...)`'s default runner is a blocking `subprocess.run(..., timeout=timeout_seconds)` call with no cooperative cancellation hook exposed by the helper today. Once `executing` begins, "cancellation" can only mean the user withdrawing interest while waiting for the call to return (or for its timeout to elapse) — it cannot mean actually interrupting the subprocess mid-run. This design does not promise true mid-execution cancellation; it only promises that the *result*, once the synchronous call returns, is handled honestly (see the Failure Taxonomy's "User cancellation during execution" row) and that no *new* invocation is started while one is already outstanding for the same request.

State clearly: output content interpretation remains out of scope for `v0.31.0`'s design unless contents are explicitly read through a safe workflow defined separately; this design does not create or imply any automatic file-reading capability.

## Conversation and Session Boundaries

- **May persist across turns (within a session):** the Execution Record (request state, confirmed snapshot, result, analysis/report status) for requests still in progress or recently completed.
- **Execution request drafts:** may persist while in `collecting_inputs`/`proposed`, but must be clearly re-shown (not silently assumed) if the conversation resumes after a gap.
- **Confirmed request snapshots:** persist only as long as needed to complete the flow (through `completed`); this design does not require indefinite retention.
- **Completed results:** persist for the remainder of the session so analysis/report generation and user follow-up questions can reference them, without needing to re-invoke the helper.
- **Stale-consent invalidation:** must be checked, not assumed, whenever a rerun or follow-up references a prior request — the Consent Manager owns this check.
- **User modifications:** any user-initiated change to a pending request returns it to `collecting_inputs`, discarding the stale `confirmed`/`request_hash` state.
- **Rerun history:** each rerun is its own Execution Record; a lightweight chain reference (this request's predecessor `request_id`) is reasonable for user-facing "here's what changed since last time" framing, but is not required for correctness.
- **Cancellation:** an explicit terminal state (`cancelled`); no further action is taken on a cancelled request, and it is not implicitly revivable — a new request must be built from scratch.
- **Session cleanup:** this design does not assume any durable storage; when a conversation/session ends, Execution Records are not assumed to survive it. Any durable audit trail beyond the current session is explicitly out of scope (see Non-Goals).

**Distinguish:**

- **Conversational memory** — what the user and assistant said; already exists as ordinary conversation context, not something this design adds.
- **Runtime state** — the Execution Record and state-machine position; new, in-memory-scoped to the current session, as this document defines it.
- **Filesystem state** — the actual working directory, scripts, and output files on disk; owned by the operating system and the helper's existing working-directory containment logic, not by orchestration.
- **Durable audit state** — a persistent, cross-session record; explicitly **not** assumed to exist by this design (see Non-Goals — "durable execution history").

Do not assume durable persistence exists. Every design element above should degrade gracefully to "this session's context only" unless a future milestone explicitly adds durable storage.

## Security and Trust Boundaries

- User-provided code is untrusted.
- User-provided paths are untrusted.
- Assistant-generated code must still be reviewed (by the safety review) before execution — generation is not self-certifying.
- The working directory must be constrained; path-traversal rejection (already implemented in the helper) remains the enforcement point, not duplicated logic in orchestration.
- Command construction must not allow shell injection — orchestration passes structured arguments to the helper's existing `command_builder`, never string-concatenated shell commands.
- The helper must receive structured arguments (already true of `execute_gauss_code(...)`'s signature); orchestration must not introduce a new, less-structured calling convention.
- No network access, anywhere in this design.
- No credentials or secrets are collected, stored, or logged by any orchestration component.
- No secrets in logs — the Execution Record and any observability output must avoid capturing anything beyond what's needed to reconstruct request/consent/result.
- No license mutation.
- No global environment mutation.
- No arbitrary subprocess use outside the one Helper Adapter boundary.
- Fail closed on unsupported behavior — an orchestration path that encounters a case it wasn't designed for should land in `blocked`/Advisory, never in `executing`.

## Observability and Auditability

A minimal, planning-only execution record — the fields below extend and make concrete the Execution Record already introduced under "Proposed Components." Each is marked **conceptual** (this document defines its meaning and role, but not its storage/implementation) or **implementation-required** (a later phase must decide the concrete representation before this is usable).

| Field | Purpose | Status |
|---|---|---|
| `request_identifier` | Distinguishes this request from any other, past or concurrent | Conceptual — the *concept* of a stable ID is settled here; the generation mechanism is an Open Question |
| `request_hash` | Supports duplicate-execution prevention (a second `executing` attempt for the same hash is rejected) and consent-scope verification | Conceptual — fingerprint *inputs* are settled (Execution Request Contract); the *hashing algorithm* is an Open Question |

State clearly: auditability must not expose secrets, full file contents, or unnecessary code beyond what was already user-visible in the displayed plan and the captured stdout/stderr evidence. An audit record should let someone reconstruct *what was decided and why*, not serve as a general-purpose transcript or a file-content archive.

## Implementation Phases

Each phase below states an objective, its prerequisites, its deliverables, what it explicitly does *not* attempt, what must pass before advancing to the next phase, and its rollback/fail-closed behavior if something goes wrong mid-phase.

### Phase 1 — Interfaces and State Definitions

- **Objective:** Turn this document's design into concrete, reviewable interfaces without writing any controller logic yet.
- **Prerequisites:** This design document reviewed and agreed (see Readiness Criteria); no prior phase.
- **Deliverables:** the canonical execution request finalized as an internal typed structure (dataclass/similar, not necessarily a JSON Schema — see Open Questions); the state machine's states/transitions finalized; the consent/fingerprinting representation finalized; confirmation that `schemas/gauss_code_execution.schema.json` needs no change (the result contract is reused, not replaced).
- **Explicit non-goals:** no orchestration controller code; no helper adapter code, mock or real; no invocation of any kind.
- **Tests/evaluations required before advancing:** a design walkthrough confirming every state/transition and every request-contract field maps to something in this document (no undefined behavior); no automated tests are possible yet since nothing executes.
- **Rollback/fail-closed behavior:** N/A — this phase produces documents/interfaces only; there is nothing to roll back.

### Phase 2 — Orchestration Controller Skeleton

- **Objective:** Prove the state machine and consent model are implementable and internally consistent, entirely without touching GAUSS.
- **Prerequisites:** Phase 1's interfaces finalized and reviewed.
- **Deliverables:** state-transition logic implementing every valid transition and rejecting every prohibited one from this document's tables; a mock/fake Helper Adapter (mirroring the real helper's own existing fake-runner self-test pattern) that never calls a real subprocess; deterministic unit tests covering every state/transition pair, every consent-invalidation rule, and the duplicate-execution-prevention check.
- **Explicit non-goals:** no real helper invocation of any kind; **this phase must not call GAUSS, `tgauss.exe`, or `gauss.exe`, directly or indirectly** — it is a hard constraint of the phase, not merely a default.
- **Tests/evaluations required before advancing:** 100% of the deterministic state-transition test suite passing; a manual review confirming no test or code path in this phase touches a real subprocess, file outside a disposable test directory, or network call.
- **Rollback/fail-closed behavior:** any failing transition test blocks advancing to Phase 3; the skeleton itself has no persistent side effects to roll back (it is pure in-memory logic against a mock adapter).

### Phase 3 — Helper Integration

- **Objective:** Connect the proven skeleton to the real, already-verified `execute_gauss_code(...)` helper, for the first time.
- **Prerequisites:** Phase 2's skeleton complete and its full test suite passing.
- **Deliverables:** a real Helper Adapter wrapping `execute_gauss_code(...)` with explicit environment context and `strict=True` (per the Determinism Gap finding above); a call to `validate_against_schema(...)` on every real result; enforcement of exactly one invocation per confirmed request; enforcement of no automatic retry.
- **Explicit non-goals:** no analysis/report-generation wiring yet (that's Phase 4); no file/session handling beyond what the helper already does itself (that's Phase 5).
- **Tests/evaluations required before advancing:** controlled real-invocation smoke tests (mirroring the `v0.28.0`/`v0.29.0` smoke-test discipline: disposable working directories, harmless trivial scripts, bounded timeouts, confirmed process cleanup) confirming completed/failed/timed-out results all classify correctly through the real adapter; confirmation that a second invocation attempt for an already-`executing`/completed `request_hash` is refused.
- **Rollback/fail-closed behavior:** if real-invocation smoke testing reveals the adapter's assumptions don't hold (for example, environment resolution behaves unexpectedly with `strict=True`), Phase 3 does not proceed to Phase 4 until the Helper Adapter is corrected and re-tested; the underlying helper itself is never modified as part of this phase — a helper-level gap found here would need its own separate, explicitly scoped milestone, consistent with the "do not modify execution helper code" boundary that governs every task in this project's execution-track work.

### Phase 4 — Analysis and Reporting Integration

- **Objective:** Route real Phase 3 results through the already-existing interpretation workflows, without inventing new interpretation logic.
- **Prerequisites:** Phase 3's real Helper Adapter complete and smoke-tested.
- **Deliverables:** execution-aware analysis routing (`workflows/execution-aware-analysis.md`) wired to real results; report-generation routing (`workflows/report-generation.md`) wired to real results, only when a report was actually requested; verification that the Failure Taxonomy's "analysis failure never rewrites execution status" and "report-generation failure never erases a validated result" guarantees hold against real (not just synthetic) results.
- **Explicit non-goals:** no new analysis/report logic beyond what these two workflows already define; no automatic report export.
- **Tests/evaluations required before advancing:** a walkthrough of real completed/failed/timed-out results from Phase 3 through both workflows, confirming methodology-boundary language (no validity claims from `completed`/`exit_code: 0`) survives intact.
- **Rollback/fail-closed behavior:** if analysis/report routing produces a methodology overclaim or misroutes a result, this phase does not advance until fixed; execution results themselves (Phase 3's output) are never modified by this phase's own failures.

### Phase 5 — File and Session Handling

- **Objective:** Fill in the remaining input/output/session mechanics the earlier phases deliberately deferred.
- **Prerequisites:** Phase 4's analysis/report routing complete.
- **Deliverables:** input-file handling consistent with the helper's existing `input_files` contract; output-metadata handling consistent with the helper's existing `output_files` contract; either a safe file-reading handoff design or an explicit, documented decision to defer it further (see Open Questions); cleanup and session-boundary behavior implementing "Conversation and Session Boundaries" and the File Lifecycle Design's collision/duplicate/interruption clarifications above.
- **Explicit non-goals:** no automatic file-content reading unless a safe workflow for it is explicitly designed and approved as part of this phase (not assumed); no deletion of user files.
- **Tests/evaluations required before advancing:** collision/duplicate-request/interruption scenarios exercised against disposable test directories, confirming fail-closed behavior in each case.
- **Rollback/fail-closed behavior:** an unresolved file-handling ambiguity blocks advancing rather than shipping an implicit assumption; interruption handling defaults to treating any ambiguous prior state as unusable, requiring rebuild-and-reconfirm.

### Phase 6 — Evaluation and Hardening

- **Objective:** Validate the fully integrated controller against the `32.x` scenario matrix and this document's safety boundaries, and prepare for a readiness review.
- **Prerequisites:** Phases 1-5 complete.
- **Deliverables:** `32.x` benchmark prompts and coverage rows authored (per this document's Evaluation Strategy matrix) and evaluated against the real controller; failure-path testing across every row of the Failure Taxonomy; a safety review re-verifying every item in "Security and Trust Boundaries" against actual controller behavior, not just design intent; documentation updated; a `v0.31.0`-successor readiness checklist.
- **Explicit non-goals:** no production deployment claim; no cross-platform/cross-version claim beyond what's actually been tested.
- **Tests/evaluations required before advancing (to a hypothetical release):** all `32.x` prompts passing; no unresolved Failure Taxonomy gap; no unresolved Security and Trust Boundary violation.
- **Rollback/fail-closed behavior:** any failing `32.x` scenario or safety-boundary violation blocks readiness; this phase does not relax any consent/safety/eligibility rule to make a test pass — a failing test means the controller needs fixing, not the requirement being weakened.

## Risks

- Stale consent (confirmation reused for a changed request).
- Duplicate execution (a request invoked more than once from a single confirmation).
- Hidden execution (any path that reaches `executing` without a genuine `confirmed` transition).
- Tool unavailability (the helper or its dependencies aren't reachable in a given environment).
- Malformed helper results (schema-invalid or internally inconsistent output).
- Unsafe file writes (a request that appears safe at proposal time but behaves differently at execution time).
- Shell injection (any path that bypasses the helper's structured-argument invocation).
- Accidental package/network actions (a regression that reintroduces a capability this design explicitly excludes).
- Unreliable `exit_code` (must not become a new dependency of orchestration's own classification logic).
- Heuristic error detection (`_detect_gauss_error` remains narrow; orchestration must not assume it is exhaustive).
- Output metadata misinterpretation (any component downstream of the Result Validator treating metadata as content).
- Methodology overclaiming (any component treating `completed`/`exit_code: 0` as validity evidence).
- State desynchronization (the Execution Record disagreeing with what actually happened).
- Conversation/runtime mismatch (the user's mental model of "what's about to run" diverging from the frozen request).
- Unintended persistence (Execution Records or logs outliving their intended session scope, or capturing more than needed).
- Cross-platform assumptions (any component silently assuming Windows/GAUSS 26.1.1-specific behavior generalizes).

## Non-Goals

- Production deployment.
- Automatic execution without confirmation.
- Autonomous repair loops.
- Package installation.
- License activation.
- Network access.
- Global configuration changes.
- Cross-platform support claims.
- Cross-version support claims.
- GUI GAUSS automation.
- Methodology validation from execution alone.
- Output-file content interpretation without reading files.
- Long-running job management.
- Streaming output.
- Parallel execution.
- Durable execution history (beyond the current session).
- Report export.

## Open Questions

**Resolved at the conceptual level by this review** (the *what* is settled; an implementation-level *how* may still need a decision in a later phase):

- How should helper unavailability be represented distinctly from helper *failure*? **Resolved conceptually** — the Failure Taxonomy now distinguishes "Executable/environment unavailable" (`blocked`, never reaches `executing`) from "Helper/tool invocation failure" (`error`, reaches `executing` but the process cannot launch) from "GAUSS runtime error" (`failed`, the process launched and GAUSS itself reported a problem). The exact code path implementing each distinction is a Phase 3 concern.
- How should analysis/report-generation failures be separated from execution failure? **Resolved conceptually** — the Failure Taxonomy states explicitly that analysis/report-generation failures never rewrite `execution_status` and never erase a validated execution result; the Observability record's `analysis_status`/`report_status` fields are tracked independently of `failure_category`. The concrete storage mechanism remains a Phase 1/4 implementation decision.
- How should duplicate execution be prevented, at least conceptually? **Resolved conceptually** — a second invocation attempt for a `request_hash` already `executing`/completed/failed is refused (Failure Taxonomy's "Duplicate execution attempt" row). **Still genuinely open:** the exact mechanism (an idempotency key check, a hard single-invocation lock, something else) is unspecified.

**Still open, unresolved by this review:**

- Should orchestration be a Python module, a workflow engine, or an agent tool? A plain Python module (mirroring `scripts/gauss_code_execution.py`'s own shape) is the leading candidate given this project's precedent, but this is not decided here.
- Should the canonical request use a formal JSON Schema (like the result schema) or an internal typed structure only? A formal schema adds validation rigor but also surface area; not decided here.
- Where should transient execution state live — in-process memory, a session-scoped file, something else? Not decided here; depends on how the orchestration layer is ultimately hosted.
- How should confirmation be represented across turns in whatever conversational/agent harness eventually calls this — a structured tool-call argument, a parsed natural-language match, something else? Not decided here.
- How should request fingerprints be generated — which hashing approach, over exactly which canonical serialization? This review specified *what* must be true of the serialization (fixed key order, explicit nulls, no whitespace sensitivity — see Execution Request Contract) but not the specific hash function/library.
- How should user cancellation be detected and handled robustly (versus simply not confirming) — particularly *during* execution, given the synchronous-call limitation this review identified (see File Lifecycle Design)?
- The exact duplicate-execution-prevention *mechanism* (idempotency key vs. lock vs. something else) — see above.
- How should file inputs be materialized safely, if a future design allows the assistant to stage input files rather than requiring the user to have them in place already?
- Should file reading (turning `output_files` metadata into interpreted content) be part of `v0.31.0`'s later phases, or a fully separate later milestone? This document's default position is **later milestone** (see Non-Goals), but it is flagged here as still open pending review.
- What is a reasonable confirmation-expiry policy — is "fail closed on any doubt" (this review's stated default posture) sufficient, or does a later phase need a precise timeout?
- What audit data should actually be retained, and for how long, once this moves beyond a single-session design?
- What is the minimum viable orchestration implementation — is Phase 2's mock controller alone enough to validate the design before any real helper integration, or does Phase 3 need to start sooner to surface real-world friction earlier?
