# v0.33.0 Controlled Real Execution Integration

## Milestone Purpose

`v0.33.0` establishes and verifies, for the first time, the complete real execution path:

`Canonical Execution Request` → `Runtime Orchestration Controller` → `GaussExecutionAdapter` → `execute_gauss_code(...)` → `tgauss.exe -b <script_path>` → structured result validation → orchestration result routing

This milestone performed exactly **one** real, minimal, non-destructive GAUSS smoke test through the doubly-gated harness built in `v0.32.0`, under explicit, narrowly-scoped user authorization, and — because that smoke test succeeded cleanly — integrated a narrow, explicit real-path factory into the orchestration controller. **This does not constitute production readiness or user-facing automatic execution** — see `planning/v0.33.0-readiness-checklist.md` for the full readiness assessment and the explicit distinction between an operational real-execution path, a production-ready system, and user-facing automatic execution.

## Explicit Authorization Received

The task that produced this milestone included an explicit, scoped authorization to perform one controlled real GAUSS smoke test, limited to: the verified Windows environment, GAUSS 26.1.1, `tgauss.exe`, inline GAUSS code, one minimal non-destructive smoke test, contained working/output directories, no network access, and no credentials/secrets. The authorization explicitly excluded: arbitrary GAUSS execution, GUI execution, script-path execution, automatic retries, destructive code, and user-facing automatic execution. Every constraint below documents how that scope was honored.

## Stage 4 — Controller Integration

A single, narrow, explicit factory was added to `scripts/gauss_runtime_orchestration.py`:

```python
def build_production_adapter_runner(
    *, request_identity: str, environment_probe: Callable[[str], bool] | None = None
) -> AdapterRunner:
    ...
```

This is the **only** function in the controller module whose explicit invocation, by name, can result in a real GAUSS call. It:

- Is never called by `MockOrchestrationInstance`'s own construction, by `invoke(...)`'s default behavior, or by any test in this repository's default suite — confirmed structurally (`"build_production_adapter_runner" not in MockOrchestrationInstance.__init__.__code__.co_names` / `.invoke.__code__.co_names`).
- Does not consult whether GAUSS is installed — it only constructs the object graph (`gauss_execution_adapter.load_real_helper()` + `GaussExecutionAdapter(...)` + `AdapterRunner(...)`); installed-ness is irrelevant to whether this function runs.
- Calls exactly two things, confirmed structurally via `__code__.co_names`: `gauss_execution_adapter` (module-qualified access) and nothing resembling `execute_gauss_code` or `subprocess` directly.
- Preserves every existing invariant unchanged: confirmation remains required and is consumed atomically at authorization (unchanged `invoke()` logic); exactly one invocation per request in the single-process scope (unchanged `HelperInvocationStatus` tracking, now also enforced independently by the adapter's own per-instance registry); script-path requests remain blocked (unchanged `submit_for_review()`); no automatic retry or rerun (unchanged — no loop exists anywhere); cancellation during execution remains non-cooperative and honestly disclosed (unchanged `cancel()`); structured results are preserved unmodified; output metadata remains metadata only; successful execution never establishes methodological validity (unchanged data model, re-verified structurally by `test_36`/`test_25` in the two test suites).

**No agent, workflow, or system-prompt file was touched.** This factory exists only inside `scripts/gauss_runtime_orchestration.py`; nothing calls it from outside this task's own verification.
