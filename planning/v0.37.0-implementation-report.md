## Stage 2 — Implementation

### `scripts/gauss_execution_workflow.py`

Core types and functions:

- `InteractionMode` — `ADVISORY`, `EXPLAIN_CODE`, `REVIEW_CODE`, `REVISE_CODE`, `PREPARE_EXECUTION_PLAN`, `EXECUTE_AFTER_CONFIRMATION`, `CANCEL_PENDING_EXECUTION`, `INSPECT_PRIOR_RESULT`, `REQUEST_RERUN`.
- `IntentSignal` / `classify_interaction_mode(...)` — a pure function over explicit booleans; precedence order: cancellation → rerun → inspect → confirmation-present → (`execution_explicitly_requested and code_present`) → non-executing hint passthrough → `ADVISORY`.
- `EligibilityDeclarations` / `evaluate_eligibility(draft, declarations)` — structurally encodes `workflows/real-execution-user-workflow.md`'s Execution Eligibility Decision checklist against the already-built `RequestDraft` plus a small set of caller-declared flags not derivable from the draft (package install, license activation, network access, global-config mutation, writes-outside-directory, missing data).
- `SafetyReviewInput` / `evaluate_safety_review(...)` — encodes 13 of the 14 Pre-Execution Safety Review items into the controller's own `SafetyReviewOutcome`/`SafetyReviewItem` types (reused, not reimplemented); the 14th item (user confirmation) is deliberately excluded since it cannot yet be true when `safety_review` is hashed into the request, and is enforced instead as `confirm_execution(...)`'s own later, independent gate.
- `ExecutionProposal`, `ProposalOutcome`, `WorkflowConfirmationEvent`, `ConfirmationOutcome`, `OutputFileSummary`, `ResponseReadyResult` — the response-ready projections described in the planning document.
- `ExecutionWorkflow` — `propose_execution`, `confirm_execution`, `execute`, `cancel`, `invalidate_for_session_boundary`, `inspect`, `request_rerun` (always raises `RerunRequiresNewRequestError`).

### Enforced dependency direction

`scripts/gauss_execution_workflow.py` imports only `gauss_runtime_orchestration` and `gauss_orchestration_state_store` — never `gauss_execution_adapter` or `gauss_code_execution`. Verified directly (`test_37`, `test_60`): `hasattr(wf, "gauss_execution_adapter")` and `hasattr(wf, "gauss_code_execution")` are both `False`.

Every orchestration instance the module creates is built via `gauss_runtime_orchestration.build_durable_orchestration_instance(...)` — never the bare `MockOrchestrationInstance(...)` constructor — so every proposal is durable from creation.

### A discovered architectural finding

While writing the cross-process test (`test_49`) and the restart test (`test_32`), both initially assumed a reloaded instance in a different process could complete an `execute()` call. Both failed with `GuardFailedError: No canonical request is attached to this instance; cannot invoke.` Root cause: `gauss_runtime_orchestration.reload_orchestration_instance(...)` always sets `instance.request = None` (raw code is never durably persisted, a deliberate `v0.36.0` design choice this module inherits unchanged), and `invoke()`'s pre-existing `self.request is None` guard (from `v0.31.0`) correctly refuses to proceed. This means cross-process invocation is not merely blocked by losing a race at the durable-store layer — it is **structurally impossible** for any process other than the one that built the original proposal. Both tests were corrected to assert this real, honest behavior instead of the originally assumed (incorrect) behavior. No code change was needed to enforce this; it falls out of the existing `v0.31.0`/`v0.36.0` design, exactly the way `v0.36.0`'s own `reload_orchestration_instance` docstring anticipated for `begin_analysis()`.

## Limitations (restated from KNOWN_LIMITATIONS.md)

- No automatic execution: intent classification never parses text; only an explicit, structured flag together with code reaches a plan, and only a fully validated confirmation reaches execution.
- A confirmed-but-not-yet-invoked request can only be invoked by the process that built it — genuinely discovered during this milestone's own testing, not merely assumed.
- Mid-execution cancellation records intent only; the synchronous helper call cannot be interrupted.
- `exit_code` remains non-authoritative; `output_files` remain metadata only.
- No cross-platform/cross-version claim; verified only on Windows/GAUSS 26.1.1.
- No production-readiness or general-purpose autonomy claim.
