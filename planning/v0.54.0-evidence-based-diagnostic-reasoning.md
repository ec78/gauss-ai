# v0.54.0 - Evidence-Based Diagnostic Reasoning

## Release Goal

Add a deterministic Diagnosis layer to the project's staged reasoning pipeline (Execution → Evidence Collection → Interpretation → Verified Knowledge → Diagnosis → Repair Planning), strictly separate from the not-yet-implemented Repair stage. Diagnosis answers *what verified causes may explain this result, what evidence is still missing, and what should be inspected next* — never *what exact code should replace the current code*.

## Architecture

```
Execution evidence + Interpretation + Verified error knowledge -> DiagnosticAssessment
```

`scripts/gauss_execution_diagnostics.py`'s `diagnose_execution(evidence: ExecutionEvidence) -> DiagnosticAssessment` is the single entry point. It calls `gauss_execution_interpreter.interpret_execution(evidence)` internally — the same pure classification `interpret` uses — rather than re-deriving `execution_phase`/`failure_type`/error-code extraction a second, possibly divergent way, per the explicit permission in this milestone's own scope ("It is acceptable for `diagnose` to call the pure interpreter function internally against already-captured evidence if that avoids duplicated classification logic and does not mutate state").

The module is pure and has zero import of `gauss_code_execution`, `gauss_workspace`, `gauss_runtime_orchestration`, or `gauss_execution_adapter` — verified structurally (`test_23_diagnosis_module_has_no_execution_or_workspace_imports` inspects the module's own source), not merely by convention. It never launches GAUSS, calls an execution helper, mutates workspace state, edits source code, reads output files, accesses the network, calls an LLM, retries, constructs a repair, or writes a new request/plan.

## Data Model

`DiagnosticAssessment` (frozen dataclass): `diagnostic_status`, `confidence`, `summary`, `possible_causes`, `supporting_evidence`, `contradicting_evidence`, `missing_evidence`, `questions_to_ask`, `recommended_diagnostic_steps`, `limitations`, `repair_boundary`, `safe_to_continue`, `requires_user_input`, `source_error_code`, `source_error_category`, `knowledge_verification`.

`DiagnosticCause` (frozen dataclass, nested): `cause_id`, `title`, `description`, `confidence`, `supporting_evidence`, `required_evidence`, `verification_source`, `is_catalog_verified`.

`DiagnosticStatus` (enum): `no_failure_detected`, `diagnosed`, `unknown_error`, `timeout`, `not_available`, `insufficient_evidence`.

`DiagnosticConfidence` (enum): `high`, `medium`, `low`, `insufficient_evidence`. Never "certain"/"guaranteed"/"proven".

`contradicting_evidence` is included as a real field but is honestly always empty in this version — nothing this engine currently consumes can detect an actual internal contradiction between two evidence fields. Included now (not omitted) so a future evidence source could populate it without a schema change; `test_13_contradictory_evidence` documents today's honest emptiness rather than leaving it silently unverified.

## Confidence Model and Cause Ranking

Deliberately simple and fully explainable, with no opaque or numeric scoring:

1. Look up the interpretation's `error_code` in the catalog.
2. If found, build one `DiagnosticCause` per `known_triggers` entry — a short, evidence-grounded description of a situation known to trigger this code.
3. Every catalog-derived cause is assigned `low` confidence, uniformly. `G0036` can support high confidence that incompatible matrix dimensions were reported (that's the interpretation's own classification, carried through as `knowledge_verification`/`supporting_evidence`); it does not automatically support high confidence that a specific cause (e.g. a missing transpose) explains it, since this engine has no source-code-content, variable-value, or matrix-shape evidence to distinguish between the several plausible triggers named in the catalog. `DiagnosticAssessment.confidence` mirrors this split: `low` whenever at least one catalog-derived cause exists, `high` only for a clean no-failure result, `insufficient_evidence` for timeout/blocked/uncataloged/genuinely-insufficient cases.
4. If no entry is found, or the entry has no `known_triggers`, `possible_causes` is empty and confidence becomes `insufficient_evidence` — never padded with a generic programming guess.

`test_17_confidence_ceiling_behavior` asserts this ceiling holds for every one of the five cataloged codes, not just one representative case.

## Catalog Changes

`GaussErrorCatalogEntry` gained three fields, all optional (default empty tuple), populated only from the same accepted evidence sources as each entry's own `verification_status` (real GAUSS runtime evidence recorded in this repository, official Aptech documentation, or existing repository evidence with clear provenance):

- `known_triggers: tuple[str, ...]`
- `diagnostic_questions: tuple[str, ...]`
- `required_evidence_for_diagnosis: tuple[str, ...]`

All five existing codes now carry this knowledge:

| Code | Known triggers (count) | Diagnostic knowledge basis |
|---|---:|---|
| `G0105` | 3 | Same real-runtime + official-documentation sources as the entry itself |
| `G0036` | 2 | Same real-runtime + official-documentation sources; causes never assert the specific documented-vs-runtime wording discrepancy as a cause, only the entry's own `title`/`generic_explanation` field carries that |
| `G0025` | 3 | Same real-runtime + official-documentation sources |
| `G0014` | 2 | Same real-runtime + official-documentation sources |
| `G0290` | 1 | Official documentation only, explicitly labeled as not yet runtime-confirmed — same as the entry's own verification status |

No speculative common-programming-error causes were added for any code. `Numerical`, `Startup or Licensing`, `User Interruption`, and `Timeout` remain without diagnostic knowledge, consistent with those categories having no cataloged error codes at all (see `docs/gauss-error-catalog.md`'s "Future Placeholders" section).

## CLI Integration

`diagnose`, alongside the existing `interpret`. Both operate on the same `ExecutionEvidence` snapshot, assembled once by a shared `_build_execution_evidence()` helper (assembly only, no classification logic duplicated). `diagnose` is available under the same rule as `interpret` (any time after `execute`; `reset` clears both); never calls `execute`/`plan`/`confirm`; never auto-displays stdout/stderr; never auto-reads output files; never mutates workspace state; deterministic across repeated calls (verified both at the pure-engine level and through real CLI transcripts).

## Interpretation/Diagnosis Boundary

| | `interpret` | `diagnose` |
|---|---|---|
| Answers | What happened? | What verified causes may explain it? What evidence is missing? What should be inspected next? |
| Never answers | — | What exact code should replace the current code? |
| Relationship | Called by `diagnose` internally (pure function reuse) | Never silently invoked from `interpret`; never invokes `interpret`'s own CLI command as a state-mutating side effect |

## Repair Boundary

`DiagnosticAssessment` has no field capable of holding replacement code, a proposed fix, or a corrected-code snippet — structurally, not just by convention (`test_21_no_code_repair_fields_or_repair_output` checks the dataclass's own field names). `repair_boundary` is a fixed, always-present string: `"Diagnosis does not modify or repair the program."` No cause description, summary, or recommended step anywhere in the module contains rewrite language (checked directly).

**Recommended next milestone:** this evaluation found zero unresolved defects at any severity, same as `v0.53.0`'s own evaluation. Given the project's staged pipeline explicitly names Repair Planning as the next conceptual stage, and given diagnosis itself is functioning cleanly with no gaps the evaluation surfaced, the strongest evidence-based case is to expand the *verified error catalog* further (more real-runtime-confirmed codes, and where possible upgrading `G0290` from documentation-only to dual-sourced) before attempting Repair Planning — Repair Planning's own quality will be bounded by how much verified knowledge Diagnosis has to draw on, so growing that knowledge base is the more evidence-grounded next step than beginning a substantially larger, higher-risk milestone.
