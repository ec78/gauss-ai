# v0.69.0 — Alpha Feedback Integration and AI-Assisted Repair Draft Generation

## Objective

Respond to five real observations from the first private alpha session (`v0.68.0`) with product-experience improvements, and implement the first, deliberately narrow version of AI-assisted repair draft generation — without redesigning the safety architecture and without weakening any existing approval, application, verification, or review guarantee.

## What this milestone is not

Not autonomous repair, not automatic application, not automatic reruns, not autonomous retries, not a rollback mechanism, not a conversational chatbot, not an IDE integration, not project-wide reasoning, and not an LLM API integration. It is also not a new pipeline stage: the existing architecture —

```
Execution -> Interpretation -> Diagnosis -> Strategy -> Draft -> Application -> Verification -> Review
```

— is unchanged. Candidate generation is assistive tooling that helps a human arrive at the exact same `RepairDraft` object and `apply-repair --replacement-text` argument the pipeline already required, faster and with less blank-prompt typing. It does not replace, skip, or pre-authorize any existing approval layer.

## Alpha findings addressed

1. **Workspace-parent configuration confusion on failure** (`gauss-ai init`) — the write-check failure warning now explicitly states the value was *not saved*, and a summary at the end of `init` re-states which settings failed to save, if any.
2. **Runner selection prompt lacks explanation** — `gauss-ai init` now prints a short explanation of what `fake` (safe, no real GAUSS) and `gauss` (runs your real, configured executable) mean immediately before asking.
3. **Line numbers requested before evidence is shown** — the guided workflow now always calls the new `suggest-repair-draft` step (which prints the detected error code, title, and diagnosis summary, and any generated candidate) *before* any line-number prompt, whether or not a candidate was generated.
4. **Users expect the assistant to propose drafts, not just strategy** — addressed by the AI-assisted candidate generator described below.
5. **Too many internal stages exposed** — addressed indirectly: when a candidate is available, the guided workflow collapses five free-text prompts (line start, line end, operation, description, replacement text) into a single accept/edit/reject decision. No approval step itself is removed, hidden, or merged — every one of execution confirmation, strategy approval, draft approval, application approval, the application gate, and verification review remains a separate, explicit, real answer.

## AI-assisted repair draft generation: design

New module `scripts/gauss_repair_draft_generation.py`. "AI-assisted" here means bounded, deterministic, catalog-and-pattern-driven generation — this repository has no LLM integration anywhere, and this module adds none. It is structured so a genuine LLM-backed generator could be substituted behind the same `RepairDraftCandidate` contract in a future, separately authorized milestone without changing anything downstream.

Inputs: the same `ExecutionEvidence` `diagnose`/`interpret`/`repair-plan` already consume, plus the affected source code text — supplied by the caller (the adapter's own already-authorized `pending_request.code`, i.e. the exact content the guided workflow already read from the named file), never read from disk by this new module itself.

Internally reuses `gauss_execution_interpreter.interpret_execution(...)`, `gauss_execution_diagnostics.diagnose_execution(...)`, and `gauss_error_catalog.lookup_error(...)` — never re-derives classification or diagnostic reasoning a second way.

**Pattern coverage is deliberately narrow in this first version**: exactly one safe, unambiguous source pattern is recognized — G0105's own verified "incomplete or malformed expression" trigger, an assignment with an empty right-hand side (`x = ;`), matching this repository's own catalog-verified reproduction trigger exactly. Every other cataloged error code, and every G0105 occurrence that does not match this exact pattern, returns an honest `no_candidate_available` result with a clear explanation — never a fabricated guess. This mirrors `gauss_repair_planner.py`'s own `BLOCKED_BY_MISSING_SOURCE` precedent (an entry can be matched with no authored strategy yet) applied one layer further, now to literal code instead of only inspection strategies.

Every candidate's `proposed_replacement_text` is an explicitly-flagged placeholder substitution (`x = 0;`), never a claim about the user's actual intent. `confidence` is capped at `medium` — never `high` — and `reasoning` always states the substituted value is a placeholder that must be reviewed, not a guess at what the user's code needs.

## Where a candidate plugs into the existing pipeline

`RepairDraft`'s own structural model (`gauss_repair_draft.py`) already bans literal code tokens (`;`, `" = "`) from `proposed_change_description`/`intended_operation`, and its fixed `DRAFT_BOUNDARY_STATEMENT` already reads "No code was generated." This milestone preserves that invariant exactly: a candidate's `suggested_operation`/`suggested_description` fields are code-token-free descriptive text (validated by a dedicated regression test against `gauss_repair_draft`'s own banned-token list), used only to pre-fill `repair-draft`'s existing `--operation`/`--description` arguments. The candidate's actual code (`proposed_replacement_text`) is surfaced separately and only ever reaches the pipeline as the same `apply-repair --replacement-text` argument a manual tester has always had to supply by hand — after strategy approval, draft construction, draft approval, application approval, and a freshly re-evaluated application gate, exactly as before. `gauss_repair_application.py`'s own "no content is generated, inferred, or reconstructed by this module" claim remains true unchanged: from that module's perspective, `replacement_text` is still an opaque, caller-supplied string, whether the human typed it from scratch or explicitly accepted a shown suggestion.

## New adapter command

`suggest-repair-draft` (no arguments) — requires an existing repair plan (`last_repair_plan`, from `repair-plan`) and the pending request's source code; returns a rendered result showing the detected error/title, diagnosis summary, zero or more candidates (each showing affected statement, proposed replacement, reasoning, and confidence), and an explicit disclosure that every candidate is a proposal only. Process-local state only (`last_repair_draft_candidates`), cleared by `reset`, exactly like every other stage's own state. Available identically through the lower-level REPL and the guided workflow (the guided workflow calls it via the same `handle_line("suggest-repair-draft")` path every other step uses — never a second implementation).

## Guided workflow UX change

Immediately after strategy approval, the guided workflow now always runs `suggest-repair-draft` (showing evidence before any line-number prompt — finding #3). If exactly one candidate is generated, the user is asked directly to accept, edit, or reject it; if more than one, the user first chooses which to review. Accepting fills in the draft's line range/operation/description and the eventual `apply-repair --replacement-text` from the candidate. Editing keeps the candidate's line range/operation/description but lets the user supply their own replacement text. Rejecting (or no candidate being available) falls back to exactly today's fully manual entry, unchanged. Immediately before the final "approve applying" question, the exact replacement text about to be applied is now printed again, regardless of its source — a small, additive safety-visibility improvement.

## Not implemented

Pattern coverage beyond G0105's empty-assignment case; any use of a real LLM or external model; automatic acceptance of a candidate; automatic application; automatic rerun/retry; multi-file candidates; any change to `gauss_repair_application.py`, `gauss_repair_application_gate.py`, `gauss_repair_application_approval.py`, `gauss_repair_draft_approval.py`, `gauss_verification_execution.py`, or `gauss_verification_review.py` — all have zero diff.
