# v0.56.0 - Evidence-Aware Repair Planning

## Release Goal

Add a deterministic Repair Planning layer to the project's staged reasoning pipeline (Execution → Evidence Collection → Interpretation → Verified Knowledge → Diagnosis → Repair Planning → Repair Application), strictly separate from the not-yet-implemented Repair Application stage. Repair planning answers *what bounded repair strategy should be considered, what evidence and approval are needed before drafting or applying a change, and how should a future repair be verified* — never *here is the exact code to apply*.

## Architecture

```
Execution evidence + Interpretation + Diagnosis + Verified error knowledge + Explicit source context (optional)
    -> RepairPlan
```

`scripts/gauss_repair_planner.py`'s `plan_repair(evidence, source_context=None) -> RepairPlan` is the single entry point. It calls `gauss_execution_interpreter.interpret_execution(evidence)` and `gauss_execution_diagnostics.diagnose_execution(evidence)` internally — the same pure functions `interpret`/`diagnose` already use — rather than re-deriving classification or diagnostic reasoning a second, possibly divergent way, per this milestone's own explicit permission ("It is acceptable for `repair-plan` to call pure interpretation and diagnosis functions internally against already-captured evidence").

The module is pure and has zero import of `gauss_code_execution`, `gauss_workspace`, `gauss_runtime_orchestration`, `gauss_execution_adapter`, or `gauss_execution_workflow` — verified structurally (`test_29_repair_planner_module_has_no_execution_or_workspace_imports` inspects the module's own source), not merely by convention. It never launches GAUSS, calls an execution helper, mutates workspace state, edits source code, reads or writes files, accesses the network, calls an LLM, retries, applies a patch, or constructs a new execution proposal.

## Data Model

`RepairPlan` (frozen dataclass): `repair_status`, `confidence`, `summary`, `repair_strategy` (short label for the top-ranked action), `proposed_actions` (ranked tuple of `RepairAction`), `target_scope`, `source_context_used`, `supporting_evidence`, `assumptions`, `missing_evidence`, `risks`, `verification_steps`, `questions_to_answer` (reused directly from `DiagnosticAssessment.questions_to_ask`), `requires_user_input`, `requires_explicit_approval`, `safe_to_prepare_draft`, `safe_to_apply`, `repair_boundary`, `source_error_code`, `source_error_category`, `knowledge_verification`.

`RepairAction` (frozen dataclass, nested): `action_id`, `action_type` (always `"inspect"` this milestone), `description`, `target`, `preconditions`, `evidence_basis`, `confidence`, `is_concrete_edit` (always `False`), `requires_source_context`, `requires_user_approval`.

`SourceContext` (frozen dataclass): `code_text`, `line_start`, `line_end`, `matrix_shapes`, `referenced_paths`, `procedure_name`, `argument_summary` — all optional, populated only from explicit caller input.

`RepairConfidence` is not a new enum — it is `gauss_execution_diagnostics.DiagnosticConfidence`, imported and reused directly, per this project's own convention against duplicating existing models.

## Repair-Status Model

Eight values — the seven this milestone's own spec named as a minimum, plus `TIMEOUT`:

`successful_execution_no_repair_needed`, `not_applicable`, `timeout`, `strategy_available`, `draft_possible_with_more_context`, `blocked_by_missing_source`, `unknown_error`, `insufficient_evidence`.

`TIMEOUT` was added for direct parity with `DiagnosticStatus.TIMEOUT` rather than overloading `STRATEGY_AVAILABLE`'s meaning for a case with no catalog entry at all (timeout is an interpreter-level classification, not a GAUSS error code). `blocked_by_missing_source` is structurally supported (fires when a matched catalog entry has empty `repair_strategies`) but does not fire for any of the 11 codes cataloged as of this milestone, since all 11 now author at least one strategy — mirrored by `test_38_unknown_codes_do_not_inherit_known_strategies` and the catalog's own `test_19_all_entries_have_repair_planning_knowledge_as_of_v0_56_0`.

`strategy_available` vs. `draft_possible_with_more_context` is decided by a single, deterministic check: does the caller's supplied `SourceContext` populate at least one field this entry's `GaussErrorCategory` considers relevant (a small lookup table, `_CATEGORY_RELEVANT_CONTEXT_FIELDS`, not opaque scoring)? If yes, `missing_evidence` is cleared for that entry's own preconditions and the status narrows to `draft_possible_with_more_context` — but confidence, `safe_to_apply`, and `safe_to_prepare_draft` are unaffected either way.

## Confidence Model

Deliberately conservative, same philosophy as diagnosis:

1. Every catalog-derived `RepairAction` is `low` confidence, uniformly — regardless of the underlying error classification's own confidence, and regardless of whether relevant source context was supplied. `test_20_conservative_confidence_ceiling` asserts this across all 11 cataloged codes.
2. `successful_execution_no_repair_needed` mirrors the interpretation's own confidence (nothing to be uncertain about).
3. Every other status is `insufficient_evidence`.

A high-confidence error classification never implies a high-confidence repair strategy — the same principle diagnosis established for cause confidence, carried one layer further and never automatically raised just because more catalog or context is available.

## Catalog Changes

`GaussErrorCatalogEntry` gained four fields, all optional (default empty tuple), populated only from the same accepted evidence sources as each entry's own `verification_status`, or from conservative generic inspection language when no code-specific evidence exists:

- `repair_strategies: tuple[str, ...]`
- `repair_preconditions: tuple[str, ...]`
- `repair_verification_steps: tuple[str, ...]`
- `repair_risks: tuple[str, ...]`

All 11 existing codes now carry this knowledge. Every strategy is phrased as an inspection/decision prompt (e.g. `G0036`: "Inspect the dimensions and intended roles of both operands before deciding whether the operation, operand construction, or orientation needs adjustment"), never a concrete edit (never "Transpose the left matrix"). `repair_preconditions` for every entry intentionally matches the same source context its `required_evidence_for_diagnosis` already names — this catalog does not maintain two separate context requirements per code.

## CLI Integration

`repair-plan`, alongside the existing `interpret`/`diagnose`. Operates on the same `ExecutionEvidence` snapshot via the existing shared `_build_execution_evidence()` helper. Accepts a small, bounded set of explicit flags parsed by a new `_parse_source_context(...)` method — `--source-text`, `--matrix-shape` (repeatable), `--path` (repeatable), `--procedure`, `--args`, `--line-start`, `--line-end` — never reading a file or fetching anything; every value comes directly from what the caller typed. An unrecognized flag returns an explicit `ERROR usage` message rather than silently ignoring it.

Available under the same rule as `interpret`/`diagnose` (any time after `execute`; `reset` clears all three); never calls `execute`/`plan`/`confirm`; never auto-displays stdout/stderr; never auto-reads output files; never mutates workspace state; deterministic across repeated calls with identical arguments (verified both at the pure-engine level and through real CLI transcripts).

## Interpretation / Diagnosis / Repair-Planning Boundaries

| | `interpret` | `diagnose` | `repair-plan` |
|---|---|---|---|
| Answers | What happened? | What verified causes may explain it? What evidence is missing? | What bounded strategy should be considered? What's needed before drafting or applying a change? How should a future repair be verified? |
| Never answers | — | What exact code should replace the current code? | What exact code should be applied? |
| Relationship | Called by `diagnose` and `repair-plan` internally | Called by `repair-plan` internally; never calls `repair-plan` | Calls both internally; never invoked by either |

None of the three commands edits code, applies a patch, retries GAUSS, or proves methodological correctness.

## Approval Boundary

`requires_explicit_approval` is `True` exactly when a plan has at least one proposed, code-specific `RepairAction` (`strategy_available` or `draft_possible_with_more_context`) — documenting that *if* this plan ever proceeded toward an applied change, approval would be required first. No approval mechanism, workflow, or persisted decision is implemented this milestone; the field is purely forward-looking (`test_22_explicit_approval_required_for_actionable_plans`).

## Application Boundary

`safe_to_apply` is **always `False`** — a critical, structurally-tested invariant (`test_21_safe_to_apply_always_false` checks every reachable status). `safe_to_prepare_draft` is likewise always `False`: no draft-generation capability exists yet, even for `draft_possible_with_more_context`. Every `RepairAction.is_concrete_edit` is always `False`, and no `action_type` is ever an edit/apply/patch/rewrite/replace verb (`test_33_no_edit_or_apply_action_types`). `repair_boundary` is a fixed, always-present string folding in every disclosure this milestone's own scope requires: *"This is a repair plan, not an applied repair. No code was modified. GAUSS was not rerun. User approval would be required before any future repair application."* The CLI additionally emits a dedicated `application_boundary` line on every call.

## Real GAUSS Executions Performed

None. This milestone's evaluation reasons over already-verified catalog knowledge and the pure repair-planning engine; no new GAUSS invocation was required to verify any repair-planning claim. The optional real-runner smoke test was run once for validation completeness only, per this milestone's own instruction not to run real GAUSS merely to repeat already-sufficient evidence.

## Out of Scope (unchanged from the authorizing task)

Patch application, file editing, source rewriting, replacement-code generation, automatic code correction, autonomous retry, autonomous execution, multi-attempt workspace behavior, durable execution sessions, conversational memory, uploads, cloud execution, chat adapters, statistical-method recommendations, methodological validation, LLM-based repair planning, repair execution. None implemented.

## Readiness Classification

Ready for continued structured alpha testing, now including bounded, evidence-aware repair-planning strategies alongside execution, interpretation, and diagnosis. Not ready for assisted debugging with an applied fix, repair application, or autonomous correction — unchanged, explicitly out of scope, and structurally impossible for this module to drift into (`safe_to_apply` has no code path that ever sets it `True`).

**Recommended next milestone:** this evaluation found zero unresolved defects at any severity, matching `v0.53.0` through `v0.55.0`'s own evaluations. Given the project's staged pipeline explicitly names Repair Application as the next conceptual stage, and given repair planning itself is functioning cleanly with no gaps the evaluation surfaced, the strongest evidence-based case is either durable execution sessions (needed before any future repair-application workflow could safely correlate a plan with the exact execution it was derived from across turns) or a scoped, explicitly-authorized approved-repair-application design phase — not implementation — that defines the approval mechanism `requires_explicit_approval` currently only documents. A further diagnostic/repair-strategy coverage expansion remains available but is lower-priority evidence-wise, since this milestone's own catalog already carries repair knowledge for all 11 existing codes.
