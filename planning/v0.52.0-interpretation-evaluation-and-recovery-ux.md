# v0.52.0 - Interpretation Evaluation and Recovery UX

## Release Goal

Two things, both grounded in evidence rather than speculative design work:

1. Formally evaluate all ten `43.x` Execution Interpretation benchmarks (added but left `Not Run` in `v0.51.0`) through the actual `InteractiveMvpAdapter` CLI / interpreter path, using real GAUSS evidence where it materially strengthens the evaluation and explicitly-disclosed deterministic fixtures elsewhere.
2. Fix the one Minor finding carried since `v0.50.0`: a completed, single-shot-exhausted workspace could still accept `request`/`plan` for a second attempt, only failing late and opaquely at `execute` with a raw `InvalidWorkspaceTransitionError`.

This is an evaluation and recovery-UX milestone. It is explicitly not an assisted-debugging or code-repair milestone — see "Out of Scope" below.

## Part 2: Interpreter Boundary Validation

Extended `scripts/test_gauss_code_assistant_cli.py` (tests 23-31) to prove, through the actual adapter rather than only the pre-existing direct-module unit tests in `scripts/test_gauss_execution_interpreter.py`:

- `interpret` never calls `execute`, never creates a new orchestration instance, never advances the session stage, and never mutates workspace status (`test_30`).
- `interpret` never auto-displays stdout/stderr content and never triggers a file read (`test_31` — checked via absence of `stdout_begin`/`stderr_begin`/`content_begin` markers and `len(mvp_session.file_reads) == 0`).
- `interpret` is deterministic and non-destructive: calling it (or `stdout`/`stderr`/`provenance`) twice in a row on the same result produces identical output both times (`test_27`).
- `interpret` before any execution reports unavailability rather than fabricating a result (`test_20`, pre-existing; re-confirmed unaffected by this milestone's changes).
- The new `--fake-timeout`/`--fake-unknown-error` evidence paths are exercised through the CLI end to end (`test_28`, `test_29`).

No production architecture was weakened to make these provable — all assertions read existing, already-public state (`mvp_session.stage`, `mvp_session.orchestration_instance_id`, `mvp_session.file_reads`, `registry.get_workspace(...).status`) rather than adding test-only hooks.

## Part 3: Completed-Workspace Planning Fix

### Reproduction (before the fix)

```
workspace create → request → plan → confirm → execute   (workspace reaches 'completed')
request → plan → confirm   (all silently succeed)
execute → ERROR InvalidWorkspaceTransitionError: completed -> executing is not a valid workspace transition.
```

The user could get all the way through a second `request`/`plan`/`confirm` cycle before discovering, from a raw internal exception, that the workspace could never have supported it.

### Root cause

`ExecutionWorkflow.propose_execution(...)` (`scripts/gauss_execution_workflow.py`) already special-cased `WorkspaceStatus.ARCHIVED` to reject a new proposal before it examined `working_directory`/other eligibility fields — but had no equivalent check for `WorkspaceStatus.COMPLETED` (or `EXECUTING`). The rejection that *did* exist lived only at `execute(...)` time, inside `WorkspaceRegistry.update_workspace_status(...)`'s own `VALID_TRANSITIONS` enforcement (`gauss_workspace.py`) — correct, but far too late in the user journey.

### Fix

Added two more branches to the same `elif` chain in `propose_execution(...)`, exactly mirroring the existing `ARCHIVED` pattern:

- `WorkspaceStatus.COMPLETED` → blocked, with a message naming the single-shot exhaustion and directing the caller to create a fresh workspace.
- `WorkspaceStatus.EXECUTING` → blocked, with a message noting the in-flight attempt.

This is the authoritative workspace-lifecycle boundary, not a CLI-only text check — a caller that bypassed the CLI entirely and called `ExecutionWorkflow.propose_execution(...)` directly would get the same rejection. No `ExecutionProposal` object is ever built for the blocked case (`ProposalOutcome.proposal is None`), matching "no new plan was created." The workspace's own status and manifest are left untouched by the rejection (verified in `test_workspace_execution_integration.py::test_18`). The pre-existing `execute(...)`-time guard (`update_workspace_status`'s `VALID_TRANSITIONS` check) remains fully intact as defense in depth — proven by a dedicated test (`test_20_lower_level_transition_still_blocked_if_propose_is_bypassed`) that forces a workspace to `COMPLETED` after confirmation and confirms `execute(...)` still raises `InvalidWorkspaceTransitionError` rather than silently succeeding.

`InteractiveMvpAdapter._plan()` translates the authoritative rejection into explicit user-facing guidance (`workspace_single_shot_exhausted: true`, a plain-language explanation, and an explicit `workspace create` instruction) rather than just relaying the raw `failure_reason` string.

No workspace lifecycle states, transitions, or edges were added, removed, or redesigned — `VALID_TRANSITIONS` in `gauss_workspace.py` is unchanged. This remains a strictly single-shot workspace model; the fix only moves an already-inevitable rejection earlier and makes it legible.

## Part 4: Recovery UX Improvements

Every change below is tied to a concrete observation, not speculative polish:

1. **Completed-workspace `plan` guidance** (tied directly to the Part 3 defect) — see above.
2. **`fake_runner_mode` no longer printed for the real GAUSS backend** — observed directly in the 43.1/43.2/43.3 real-evaluation transcripts: `request`'s response always echoed `fake_runner_mode: success` even under `--runner gauss`, where the field is meaningless (there is no "fake mode" for a real run). Now only shown for the fake backend.
3. **`--fake-timeout`/`--fake-unknown-error` request modes** — added because Part 1 required a way to exercise 43.4 and 43.9 through the real CLI/interpreter path, not just via direct interpreter unit tests; these are reusable testing/evaluation infrastructure, documented in `docs/real-gauss-debugging-alpha-guide.md`.
4. **`reset` vs. `workspace create` guidance clarified in the completed-workspace block message and in `docs/real-gauss-debugging-alpha-guide.md`** — tied to a real ambiguity: `reset` only clears adapter-local request/plan/result state; it does not change the underlying workspace's own `completed` status, so `reset` alone does not recover from this specific block. This was not previously stated explicitly anywhere.

No other cosmetic changes were made to the `execute`/`interpret`/`stdout`/`stderr`/`outputs`/`read`/`provenance`/`reset` sequence — the 43.x evaluation did not surface confusion in those specific commands beyond the two items above.

## Out of Scope (unchanged from the authorizing task)

Autonomous debugging, autonomous code correction, suggested code rewrites, automatic retries, multi-attempt workspaces, durable execution sessions, chat adapters, uploads, cloud execution, LLM calls inside interpretation, broad architecture redesign. None of these were implemented, and no interpreter classification logic changed as a result of this milestone (only a CLI-adapter-level cosmetic fix and the new fake-evidence request modes).
