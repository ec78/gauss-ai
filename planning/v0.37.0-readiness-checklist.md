## Interaction Contract Assessment

- Interaction modes are a fixed, closed enum (`InteractionMode`, 9 members) matching the task's own supported-modes list.
- `classify_interaction_mode(...)` is a pure function with an explicit, documented precedence order; no branch reaches an executing mode without both `execution_explicitly_requested=True` and `code_present=True`, or a pre-validated confirmation event.
- `ExecutionProposal`/`ResponseReadyResult` carry no field capable of holding raw file content — `OutputFileSummary` has no `content` field at all (verified by dataclass field inspection, `test_54`).
- Confirmation is bound to `request_hash` via `plan_digest`, independently re-checked by `confirm_execution(...)` before the controller is consulted, and again by the controller's own `attach_confirmation(...)`/`record_confirmation(...)` checks — two independent layers, not one.

## Important Findings

1. **A genuine, discovered architectural fact, not a bug**: cross-process invocation of a confirmed-but-not-yet-executed request is structurally impossible via this module, not merely blocked by a race. `reload_orchestration_instance(...)` always leaves `request=None`; `invoke()`'s pre-existing `v0.31.0` guard refuses to proceed on it. Verified with three real, separate racing OS processes (`test_49`), all refused, none corrupting the durable record, the original process still able to complete the invocation afterward.
2. **Two independent layers of confirmation validation.** `confirm_execution(...)`'s own `plan_digest == request_hash` check runs before the controller is ever consulted; the controller's own `attach_confirmation(...)` check (`confirmation_scope == request_hash`) and durable `record_confirmation(...)` check run again, independently. Neither layer trusts the other's absence.
3. **The 14th safety-review checklist item (user confirmation) is deliberately excluded from the hashed `SafetyReviewOutcome`** to avoid circularity (confirmation cannot be true before the hash it depends on is computed) — enforced instead as `confirm_execution(...)`'s own separate, later, independently validated gate. This is a documented design decision, not an oversight.

## Remaining Limitations

- No automatic execution of any kind; every run requires an explicit, structured request and an explicit, independently validated confirmation.
- Cross-process resumption of a confirmed-but-not-yet-invoked request is not supported — only the process that built the proposal can invoke it (see Finding 1).
- Mid-execution cancellation records intent only; the synchronous helper call cannot be interrupted (inherited, unchanged).
- `exit_code` remains non-authoritative; `output_files` remain metadata only, never content.
- Verified only on the observed Windows/GAUSS 26.1.1 environment; no cross-platform or cross-version claim.
- No distributed or multi-machine claim (inherited from `v0.36.0`, unchanged).
- No methodological-validity claim from execution alone.

## Explicit Readiness-Level Distinction

- **Ready**: as a controlled conversational workflow-integration milestone — one dedicated, tested, narrowly-documented boundary module connecting the existing user-facing workflow to the existing durable controller, with no automatic execution and no bypass of any existing safeguard.
- **Not ready, and not claimed**: as a generally autonomous assistant; as a production deployment; as a distributed or multi-machine system; as a system supporting cross-process handoff of an in-flight confirmed request.

## Non-blocking Follow-ups

- Consider a future milestone that explicitly scopes a genuine conversational-agent wiring (structured intent/confirmation events actually produced by a live agent turn, not just accepted as typed inputs) — out of scope here, since this milestone's own boundary is deliberately agent-agnostic.
- Consider a future milestone addressing cross-process resumption of a confirmed-but-not-invoked request, if a real deployment need arises — this would require a deliberate, separately-reviewed decision about durably persisting (or re-deriving) code, which both this milestone and `v0.36.0` were correctly barred from doing informally.
