# v0.14.0 Readiness Checklist

## Release Goal

`v0.14.0` operationalizes the Software Engineering Expert as the third operational expert, adding maintainability, refactoring, testability, code review, and safe change-management reasoning to the Code Assistant. The Code Assistant now has three separately-owned, non-substitutable correctness dimensions:

- **GAUSS Language Expert** — implementation correctness (GAUSS syntax, command/procedure selection, data structures, package/base distinction).
- **Econometrics Expert** — methodological correctness (model/estimator choice, assumptions, diagnostics, causal/predictive framing).
- **Software Engineering Expert** — maintainability/design correctness (code organization, modularity, refactoring, testability, error handling, safe change management).

As with `v0.8.0` and `v0.9.0` before it, this remains **documented, manual-evaluation-driven expert routing, not runtime orchestration**. No code parses, executes, or enforces `workflows/expert-routing.md` or any `OPERATIONAL_PROFILE.md` at runtime; a response is checked against them manually, the same way task-mode fit is checked today. Adding a third expert changed the *shape* of routing (four routing types grew to eight) but not its *mechanism*.

## Software Engineering Expert Summary

**Purpose:** guide agents on code quality and maintainability — structure, modularity, naming, refactoring, testability, error handling, and safe change management. Owns whether code is well-organized, readable, and safe to change, not whether a line of GAUSS is syntactically valid or a modeling choice is statistically appropriate.

**Scope (owns):** code organization, modularity, decomposition, naming clarity, readability, maintainability, refactoring strategy, testability, edge-case thinking, error-handling strategy, code review patterns, reducing duplication, safe change management, separation of concerns, complexity management, lightweight design guidance, migration/refactor planning.

**Non-scope (does not own):** exact GAUSS syntax, verified GAUSS command signatures, the GAUSS package/base distinction, econometric model appropriateness, causal interpretation, statistical diagnostics, official GAUSS documentation authority, product strategy, instructional sequencing, user-facing documentation quality as a primary domain.

**Activation triggers:** refactoring requests, code review requests, maintainability/readability/modularity concerns, duplicated logic, procedure/function design, test strategy, error handling, edge cases, project/code organization, safe incremental changes, complexity concerns, reviewing generated code for design weaknesses, cleaning up messy code, making code easier to maintain/test/extend.

**Non-activation cases:** simple GAUSS syntax lookup only, exact GAUSS command documentation retrieval only, pure econometric interpretation without code/design concerns, pure documentation writing, pure education/lesson planning, product strategy, general prose editing, release-note writing, CI guard questions unless code/design quality is involved, factual questions unrelated to software design.

**Boundary rules:**
- The Software Engineering Expert may recommend structure, refactoring, and tests.
- It may **not** invent GAUSS syntax to fit a recommended structure.
- It may **not** claim statistical or causal validity from clean code alone.
- It may **not** claim code or tests were executed unless they actually were.
- **Clean code is not evidence of causal/statistical validity** — code quality and methodological soundness are independent claims.
- **Valid GAUSS syntax is not evidence of good design** — syntactic validity and maintainability are independent claims.

**Relationship to GAUSS Language Expert:** the GAUSS Language Expert owns implementation correctness (is this valid, evidence-backed GAUSS syntax); the Software Engineering Expert owns maintainability (is this code well-organized, readable, and safe to change). It may recommend a refactor's structural goal but defers exact GAUSS syntax to the GAUSS Language Expert and its evidence requirements.

**Relationship to Econometrics Expert:** the Econometrics Expert owns methodological correctness (is this the right model/estimator/diagnostic); the Software Engineering Expert owns code/workflow quality (is the analysis organized, decomposed, testable). When both are in play, methodological and maintainability claims are kept separate and separately attributable, the same way implementation and methodology claims already stay separate for the other two experts.

## Three-Expert Routing Summary

`workflows/expert-routing.md` documents eight routing types, replacing the four (`v0.9.0`-`v0.13.0`) that existed before this milestone:

1. GAUSS-only
2. Econometrics-only
3. Software-engineering-only
4. GAUSS + Econometrics
5. GAUSS + Software Engineering
6. Econometrics + Software Engineering
7. GAUSS + Econometrics + Software Engineering
8. Neither

Each type has a documented when-it-applies statement, a worked example, an evidence/context pattern, and a response rule — this is a documented set of combinations to check a response against, not a combinatorial routing engine.

Coordination principles carried through from `v0.9.0` and extended to three experts:

- Implementation, methodology, and maintainability claims must remain separate and separately attributable when more than one expert activates, even within one coherent response.
- The strictest applicable evidence/context requirement wins — if a task touches multiple domains, meeting only one expert's bar is not sufficient to answer the whole question.
- Command availability is not methodological validity; clean structure is not statistical validity; syntax validity is not maintainability.
- Routing remains documented and manually evaluated — no runtime orchestration engine executes these rules, and expert activation is internal by default (not a required "expert activated" label).

## Code Assistant Integration Summary

Software Engineering Expert references were integrated into all three Code Assistant surfaces:

- `workflows/code-assistant-response.md` — Step 2 ("Identify Relevant Experts") now names the Software Engineering Expert alongside the other two and references the eight routing types.
- `agents/code-assistant/task_modes.md` — all ten task modes (Code Generation, Debugging, Code Explanation, Code Translation, Code Review, Refactoring, Optimization, Documentation, Test Generation, Design Guidance) now state whether and why the Software Engineering Expert activates for that mode; the Cross-Mode Validation checklist checks the eight routing types and the expert's boundary rules.
- `prompts/code_assistant_system.md` — "Identify the relevant expertise" now names all three operational experts and the eight routing types; a new "Cross-Expert Guardrails" section states the syntax-validity/design and code-quality/statistical-validity boundaries explicitly.

Summary of what changed in Code Assistant behavior:

- The Code Assistant now considers the Software Engineering Expert for refactoring, code review, maintainability, modularity, readability, testability, error handling, edge cases, duplicated logic, and safe change management.
- GAUSS syntax remains owned exclusively by the GAUSS Language Expert.
- Statistical/methodological claims remain owned exclusively by the Econometrics Expert.
- Pseudocode or unverified syntax must be labeled clearly rather than presented as confirmed GAUSS.
- Tests or checks recommended by the Software Engineering Expert must never be presented as already run.

## Important Findings

- The Code Assistant now has three separable correctness dimensions — implementation correctness (GAUSS Language Expert), methodological correctness (Econometrics Expert), and maintainability/design correctness (Software Engineering Expert) — each independently checkable and none substitutable for another.
- The Software Engineering Expert improves code review, refactoring, and testing guidance without weakening any existing GAUSS evidence requirement; every `21.x` run that touched GAUSS syntax either used verified local evidence or explicitly caveated unverified functions (e.g., `packr` in `21.2`, `21.4`) rather than asserting them.
- Three-expert routing remains readable at eight combinations because each combination is documented as one sentence plus one worked example — the discipline established in the `v0.14.0` planning doc held throughout the actual benchmark evaluations.
- All-three routing (`21.4`) is viable in practice: a single response kept implementation, methodology, and maintainability recommendations independently identifiable without needing three separately labeled sections.
- Neither-expert routing (`21.8`) remains important and still holds correctly with three experts available — a benchmark category's own name ("Software Engineering Expert Foundation") was not itself an activation trigger for a plain writing task.

## Remaining Limitations

- No runtime orchestration exists for any expert or routing combination — all routing remains a documented reasoning procedure checked by manual evaluation.
- Documentation, Education, and Product experts remain narrative-only/placeholder perspectives, not operationalized with their own profiles.
- The Software Engineering Expert does not validate GAUSS syntax independently — exact syntax claims still require the GAUSS Language Expert and official-doc-backed evidence.
- The Software Engineering Expert does not validate statistical methodology independently — model/estimator appropriateness still requires the Econometrics Expert.
- Testing advice from any expert is not execution — no run in this milestone claimed a test was actually run.
- Evidence validation is structural, not semantic or execution validation — a schema-valid evidence object is not proof of correct GAUSS behavior.
- GAUSS code is not executed anywhere in this framework as of this milestone.
- Strict-mode evidence validation and tracking guards still have the same documented warning-promoted-to-failure cases (`glm`/`olsmt` HDF5-URI path warnings; two historical tracking warnings) as every prior milestone.
