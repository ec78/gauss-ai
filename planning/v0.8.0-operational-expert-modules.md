# v0.8.0 Operational Expert Modules Plan

## Release Goal

`v0.7.0` proved that command lookup evidence can be represented, validated, and checked in aggregate with growing real command coverage. Expert modules, meanwhile, have existed since early milestones only as narrative documentation and specification assets (`experts/gauss-language/*.md`) that the Code Assistant's prompts *reference by name* but never *route through* in any structured way.

`v0.8.0` operationalizes expert modules, starting with the GAUSS Language Expert, so the Code Assistant can route tasks through expert-specific decision rules — explicit activation triggers, required inputs/evidence, decision rules, and an output contract — rather than relying only on general prompt guidance that happens to mention the expert's name. This is a reasoning-structure milestone, not a runtime-engine milestone: "operational" here means the expert has a defined interface the Code Assistant's documented workflow can be checked against, not that a program executes the expert as code.

Distinguishing the four states explicitly:

- **Expert concept implemented:** Yes — the idea of routing different task types through different expert reasoning is already named in three separate prompt/workflow files.
- **Expert documentation partially implemented:** Yes — `EXPERT.md` is an intentionally incomplete framework; `BODY_OF_KNOWLEDGE.md` and `COMMAND_CATEGORIES.md` are substantially populated reference material.
- **Expert runtime behavior not yet implemented:** Confirmed gap — no file defines activation triggers, required/optional inputs, required evidence by task type, an output contract, or refusal/escalation conditions in a checkable form. "Identify Relevant Experts" today is one line of prose, not a decision procedure.
- **Expert evaluations not yet implemented:** Confirmed gap — no benchmark category tests whether the Code Assistant actually consulted expert-specific decision rules versus arriving at the same answer through general prompt guidance alone. The 13.x/14.x categories test evidence-schema and validator mechanics, not expert activation.

## Scope

- Define an operational expert interface (a lightweight, reusable schema for any expert module, not just this one).
- Create a GAUSS Language Expert operational profile that fills in that interface with real, checkable content.
- Add expert routing rules for Code Assistant task modes (tying the existing 10 task modes to explicit expert activation).
- Define expert input and output contracts (what the Code Assistant hands the expert reasoning step, and what it gets back).
- Define expert evidence requirements (how this connects to, and does not duplicate or weaken, the existing evidence schema and retrieval-backed response pattern).
- Define expert refusal/escalation behavior (when the expert should say "not enough evidence" or "not my domain" rather than answer anyway).
- Add workflow updates so the Code Assistant consults the GAUSS Language Expert for GAUSS-specific tasks, replacing the current one-line "Identify Relevant Experts" step with a real procedure.
- Add benchmark prompts (15.x) for expert routing and expert-grounded responses, following the same manual-evaluation discipline used for 11.x-14.x.

## Non-goals

- No full agent runtime engine.
- No hosted service.
- No MCP server implementation.
- No GAUSS execution engine.
- No automatic multi-expert orchestration beyond documented routing behavior (single-expert routing to the GAUSS Language Expert is in scope; a general orchestration layer across all five experts named in `code-assistant-response.md` is not).
- No replacement of evidence schema or retrieval workflows — the operational expert interface consumes and cites `schemas/command_lookup_evidence.schema.json` output and `workflows/retrieval-backed-response-pattern.md` states; it does not define a competing evidence format.
- No weakening of evidence requirements — an expert profile can add stricter requirements for when exact syntax may be given, never looser ones.

## Operational Expert Interface

A lightweight, markdown-first interface any expert module (GAUSS Language Expert first, others later) should define. No runtime engine is required to check a response against this interface by hand, the same way `evaluations/scoring.md` is checked by hand today.

```yaml
expert_id: string                 # stable identifier, e.g. "gauss-language-expert"
expert_name: string                # display name
expert_scope: string                # one-paragraph statement of what this expert owns
activation_triggers:                # conditions under which the Code Assistant must consult this expert
  - trigger description
required_inputs:                    # information the expert reasoning step needs to proceed
  - input description
optional_inputs:                    # information that improves the answer but is not blocking
  - input description
required_evidence:                  # by task type, what evidence class is required before exact claims are made
  task_type: evidence requirement
decision_rules:                     # ordered, checkable rules the expert applies
  - rule
output_contract:                    # required fields in the expert's contribution to the final response
  - field: description
refusal_conditions:                 # when the expert must decline to give exact syntax/claims
  - condition
escalation_conditions:              # when the task should route to a different expert or back to the user
  - condition
evaluation_criteria:                # how a response can be checked against this profile
  - criterion
```

Design notes:

- This is intentionally close in shape to the existing `retrieval-backed-response-pattern.md` (which already has states A-H and a response structure) — the operational expert interface generalizes that pattern one level up, from "how retrieval evidence shapes a response" to "how an expert's domain rules shape a response," and an expert profile should cite retrieval states rather than redefine them.
- `required_evidence` should reference `retrieval_status` / `source_authority` values from `schemas/command_lookup_evidence.schema.json` where applicable (for example, "exact syntax requires `source_authority: official_docs` or `official_package_docs`"), not invent a parallel evidence vocabulary.
- The interface is descriptive/checkable, not executable. Nothing in `v0.8.0` requires code that parses this YAML at runtime; it is a documentation contract the Code Assistant's response is expected to satisfy, verified today by manual evaluation the same way task-mode fit is verified today.

## GAUSS Language Expert Operational Profile

To live in a new file (`experts/gauss-language/OPERATIONAL_PROFILE.md`), filling in the interface above:

**Purpose:** Ground every GAUSS-specific claim the Code Assistant makes — syntax, procedure/API usage, data structure choice, package vs. base-GAUSS distinction — in verified evidence or explicit uncertainty, rather than general model knowledge.

**Scope:** GAUSS language mechanics: syntax, procedures, data structures (matrix, DataFrame, array, string, scalar, structure), control flow, native command selection, package/base-GAUSS distinction, and known AI failure modes specific to GAUSS. Explicitly not econometric/statistical methodology, product decisions, or general software-engineering process (those remain the Econometrics, Software Engineering, Documentation, and Education experts' domains, per `workflows/code-assistant-response.md`).

**Activation triggers:** any task mode from `agents/code-assistant/task_modes.md` where the answer includes GAUSS code, GAUSS syntax claims, GAUSS command/procedure selection, or a GAUSS data-structure recommendation (see Expert Routing Rules below for the concrete list).

**Relevant task modes:** Code Generation, Debugging, Code Translation, Code Review, Refactoring, Optimization, Test Generation, Design Guidance, and the GAUSS-specific portions of Code Explanation and Documentation.

**Knowledge domains:** `experts/gauss-language/BODY_OF_KNOWLEDGE.md`'s domain structure (language fundamentals and beyond), `COMMAND_CATEGORIES.md` for discovery, `commands/*.md` for curated notes, and `schemas/command_lookup_evidence.schema.json`-shaped evidence for verified command-specific facts.

**Required evidence by task type:**

| Task type | Evidence requirement |
|---|---|
| Exact command syntax, defaults, return values | `retrieval_status: found_complete` or `found_incomplete` evidence with `source_authority: official_docs` or `official_package_docs`; if unavailable, state that verification is needed rather than inventing syntax. |
| Command selection ("which procedure should I use") | `COMMAND_CATEGORIES.md` for candidate discovery is sufficient; exact usage still requires the row above before presenting production-ready syntax. |
| General language mechanics (control flow, scoping, procedure structure) | `BODY_OF_KNOWLEDGE.md` domain content is sufficient; no per-call retrieval needed unless a specific function's behavior is in question. |
| Data-structure choice (matrix/DataFrame/array/structure) | `BODY_OF_KNOWLEDGE.md` decision guidance is sufficient; cite the tradeoff, not a specific unverified function signature. |
| Package-specific behavior | Same bar as command syntax — package source, official package docs, or curated note; state the package dependency explicitly regardless of evidence source. |

**Decision rules** (extending `EXPERT.md`'s existing six general rules with checkable, task-type-specific ones):

1. Do not invent GAUSS syntax, packages, procedures, or APIs.
2. Prefer official-doc-backed command evidence for exact syntax, defaults, and return values.
3. Use curated notes (`experts/gauss-language/commands/*.md`) only as convenience references when official evidence is unavailable or already consistent with it — never as a substitute source when official evidence conflicts.
4. Prefer native GAUSS procedures when verified and appropriate for the task.
5. Use manual matrix implementations only for teaching, customization, cases where no suitable native command exists, or intentionally transparent worked examples.
6. Distinguish DataFrame, matrix, array, string, scalar, and structure usage explicitly; never treat them as interchangeable.
7. Treat package-specific functions differently from base GAUSS functions, and state the dependency whenever a package-specific function is used.
8. Do not claim GAUSS code was executed unless it was actually run by an available tool.
9. Preserve uncertainty when evidence is incomplete, stale, ambiguous, or conflicting — surface it rather than resolving it silently in either direction.

**Failure modes:** the same list already in `EXPERT.md`'s "Common AI Failure Modes" section (hallucinated procedures/keywords, cross-language assumption import, version-behavior blindness, plausible-but-non-idiomatic code, overgeneralization from one example, confusing language mechanics with econometric methodology, failing to retrieve for source-dependent questions) — carried into the operational profile as `refusal_conditions`/`escalation_conditions` rather than left as prose.

**Response obligations:** every GAUSS-specific claim in the final response must be traceable to one of: (a) cited retrieval evidence, (b) `BODY_OF_KNOWLEDGE.md` general language mechanics, (c) explicitly stated uncertainty. No fourth category ("just seemed right") is permitted.

## Expert Routing Rules

**Activate the GAUSS Language Expert when the task involves:**

- GAUSS code generation
- GAUSS debugging
- GAUSS code translation (from Python, R, MATLAB, Stata, or pseudocode)
- GAUSS code review
- Native command/procedure selection
- Procedure or package API usage questions
- Data structure choice (matrix vs. DataFrame vs. array vs. structure vs. string)
- Package-specific vs. base-GAUSS distinction
- Syntax verification of user-provided or assistant-generated GAUSS code
- Any point where hallucination risk is elevated (unfamiliar command name, cross-language idiom present, version-sensitive behavior)

**Do not activate (or activate only incidentally) when the task is:**

- Non-GAUSS general writing (for example, drafting a project announcement)
- Purely project-management tasks (for example, updating a tracking file, drafting a commit message)
- Release tracking and readiness-checklist bookkeeping (the kind of work this repository's own `planning/*-readiness-checklist.md` files represent)
- Generic non-GAUSS explanations, unless they have a GAUSS implication (for example, explaining what OLS is conceptually does not require the expert; showing OLS in GAUSS via `olsmt` does)

This list operationalizes the existing "Identify Relevant Experts" step in `workflows/code-assistant-response.md` and `prompts/code_assistant_system.md`, which currently gives only one general-purpose line per expert.

## Expert Output Contract

What the GAUSS Language Expert's reasoning step contributes to the Code Assistant's final response (as an internal reasoning structure — not necessarily a literally labeled section in every user-facing answer, see Risks and Design Questions below):

- `task_classification`: which task mode(s) this is, and why the expert activated.
- `activated_knowledge_domains`: which `BODY_OF_KNOWLEDGE.md` domains and/or `COMMAND_CATEGORIES.md` entries are relevant.
- `evidence_needed`: what evidence class this task requires, per the Required Evidence table above.
- `evidence_used`: what evidence was actually retrieved or already available (citing a real evidence file/lookup, not asserting evidence exists).
- `verified_facts`: claims backed by evidence_used, stated as verified.
- `decision_recommendation`: the expert's recommended approach (for example, "use `olsmt`, not a manual matrix OLS implementation, because verified evidence exists and it is the native GAUSS procedure for this workflow").
- `risks_or_uncertainties`: anything incomplete, stale, ambiguous, or conflicting that the user should know about.
- `response_constraints`: what the final response must NOT claim (for example, "must not state `strindx`'s not-found return value unless retrieved" if evidence is missing).
- `validation_suggestions`: a concrete way for the user to check the result, per existing retrieval-backed-response-pattern requirements for translation/debugging.

## Benchmark Plan

Proposed next category, **15.x — Expert Routing**, following the 11.x-14.x numbering convention in `evaluations/benchmark-prompts.md`:

- **15.1** — GAUSS code generation request; expected behavior confirms the response reflects GAUSS Language Expert activation (decision rules 1, 2, 4, 6 above visibly applied) rather than generic code-assistant boilerplate.
- **15.2** — R-to-GAUSS translation request; expected behavior confirms the response routes through the expert, retrieves command evidence for the native procedure recommended, and does not silently substitute a manual implementation when a verified native command exists.
- **15.3** — Debugging a hallucinated Python-style string function call (for example, a `.find()`-style method invented on a GAUSS string); expected behavior confirms the expert identifies the cross-language contamination and corrects to real GAUSS behavior (`strindx`, `0`-based not-found).
- **15.4** — Choosing between `qnewtonmt` and `minimize` for an optimization task; expected behavior confirms the expert surfaces both as valid native options, distinguishes them by capability/recency (per `examples/retrieval/schema-aligned/qnewtonmt.evidence.json` and `minimize.evidence.json`) rather than picking one without justification, and does not claim one deprecates the other without evidence.
- **15.5** — DataFrame vs. matrix design-guidance request; expected behavior confirms the expert's decision rules on data-structure distinction are applied, not just general reasoning.
- **15.6** — Ambiguous command evidence (reusing the `ambiguous-command-match.json` fixture pattern from `v0.6.0`); expected behavior confirms the expert escalates the ambiguity to the user rather than inventing syntax to resolve it unilaterally.
- **15.7** — A clearly non-GAUSS task (for example, drafting a changelog entry); expected behavior confirms the GAUSS Language Expert does *not* unnecessarily activate, as a negative-case check on the routing rules.

## Risks and Design Questions

- **How explicit should expert activation be in final responses?** A fully internal reasoning step keeps responses terse but makes routing failures hard to catch in evaluation; a fully visible "Expert: GAUSS Language Expert activated" preamble is checkable but adds boilerplate the user did not ask for. Likely resolution: internal by default, but evaluation runs should still be able to identify *evidence* of correct routing (decision rules visibly applied, correct evidence class required) without requiring a literal label — similar to how 13.x/14.x evaluations already infer correct behavior from response content rather than requiring an explicit self-report.
- **Should expert routing be visible or internal?** Related to the above; leaning toward internal/implicit unless a future multi-expert conflict makes visibility valuable.
- **How to keep expert modules from becoming duplicated prompt text?** The operational profile should *reference* `BODY_OF_KNOWLEDGE.md`, `COMMAND_CATEGORIES.md`, and the retrieval workflows rather than restate their content — this plan already tries to model that by pointing at existing files instead of re-deriving their content inline.
- **How to avoid experts bypassing evidence requirements?** The interface's `required_evidence` and `refusal_conditions` fields are the enforcement mechanism; the Non-goals section explicitly forbids loosening evidence requirements via an expert profile. Evaluation should specifically test that an expert profile never becomes a way to skip retrieval that would otherwise be required (see 15.2, which tests exactly this).
- **How to evaluate expert activation without a runtime?** The same way task-mode fit and retrieval-backed-response-pattern compliance are evaluated today: manual inspection of whether the response's content is consistent with the profile's decision rules, scored against `evaluations/scoring.md`'s existing dimensions (particularly Task Mode Fit and Assumptions and Dependencies) plus new expert-specific benchmark expectations.
- **How to handle multiple future experts?** The interface is deliberately generic (`expert_id`, `expert_scope`, etc.) so the Econometrics, Software Engineering, Documentation, and Education experts named in `workflows/code-assistant-response.md` can eventually get their own operational profiles using the same shape, without redesigning the interface. Multi-expert *orchestration* (what happens when two experts' domains overlap on one task) is explicitly out of scope for `v0.8.0` — see Non-goals.
- **How to keep expert docs maintainable?** Keep `EXPERT.md` (narrative/spec) and `OPERATIONAL_PROFILE.md` (interface-filled, checkable) as separate files with distinct purposes, the same separation this repository already uses between `schemas/command_lookup_evidence.schema.json` (formal) and `tools/evidence_schema.md` (narrative).
