## Newest-Version Default Rule

When multiple GAUSS versions are detected, the helper defaults to the newest/highest version unless the user provides a preferred executable path or preferred version.

**Example:** GAUSS 24, GAUSS 25, GAUSS 26 detected → default selection: GAUSS 26.

**Selection priority:**

1. User-provided executable path.
2. User-specified preferred version.
3. Highest detected GAUSS version.
4. `ambiguous` if versions cannot be determined safely.

- A user path overrides the newest-version rule.
- A preferred version overrides the newest-version rule.
- A newest-inaccessible-plus-older-accessible situation does not silently downgrade — it returns `ambiguous` with an explicit warning.
- Multiple unknown-version candidates remain `ambiguous`.

## Detection and Fallback Behavior

- User-provided path is checked first and never silently substituted on failure.
- Preferred version is matched against discovered candidates and never silently overridden by a newer detected version.
- `PATH` lookup uses `shutil.which` against a conservative, documented-as-non-exhaustive set of plausible executable names.
- Common-location scan checks read-only, category-based paths (Windows Program Files-style, macOS Applications-style, Linux `/opt`/`/usr/local`); WSL and unsupported platforms return no candidates rather than guess.
- Candidate accessibility checks existence, file type, and (on POSIX) the executable bit; Windows treats existence as sufficient.
- Version is inferred from the path/directory name (e.g., `GAUSS26` → `26`); an optional version query is accepted but does not currently invoke anything.
- Every code path returns schema-valid output, including a caught-exception `error` path so detection never crashes the caller.
- Advisory Mode (`operating_mode_recommendation: advisory`) is the fallback for `not_found`, `ambiguous`, `inaccessible`, `error`, and `unknown` states — only `found` recommends `execution_candidate`.
