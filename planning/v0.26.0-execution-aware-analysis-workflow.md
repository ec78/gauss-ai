# v0.26.0 - Execution-Aware Analysis Workflow

## Release Goal

`v0.26.0` defines how the Code Assistant should interpret and respond to structured execution-result objects from `gauss_code_execution` — the workflow layer that sits on top of `v0.25.0`'s implemented helper, the same way `workflows/expert-routing.md` sits on top of the six operationalized experts rather than being part of any single expert's own profile.

The goal is to formalize a workflow for:

- Consuming execution result objects (shaped by `schemas/gauss_code_execution.schema.json`).
- Identifying execution status.
- Distinguishing actual execution output from interpretation.
- Routing interpretation to the correct expert dimensions.
- Producing safe user-facing summaries.
- Preserving Advisory Mode fallback after failure, timeout, skipped, blocked, or unknown results.
- Avoiding overclaims from completed execution.

`v0.26.0` should **not**:

- Improve real GAUSS invocation syntax.
- Claim production-ready real execution.
- Add runtime orchestration.
- Run GAUSS code.
- Install packages.
- Activate licenses.
- Automatically rerun or repair code.
- Generate polished reports from execution output.
- Replace econometric/statistical review.

## Current State

- Environment detection exists (`scripts/gauss_environment_check.py`, `v0.21.0`).
- Package inspection exists (`scripts/gauss_package_inspection.py`, `v0.23.0`).
- Code execution helper architecture exists (`scripts/gauss_code_execution.py`, `v0.25.0`).
- The execution helper has fake-runner self-tests (18 cases + 1 bonus case); real non-interactive GAUSS invocation remains unresolved — a manual smoke test confirmed the default command form causes GAUSS to enter an interactive session rather than exit non-interactively.
- No Code Assistant workflow integration exists yet for execution-result interpretation — `workflows/code-assistant-response.md` still ends every response at Step 8's failure-mode check without a tool-output-consumption step.
- `28.x` benchmarks validate response behavior around execution *boundaries* (refusal, no false claims, package-missing handling), but no dedicated execution-*aware analysis* workflow exists yet that defines how to interpret a result object once one is actually supplied.

## Execution Result Inputs

The workflow should expect execution result objects shaped by `schemas/gauss_code_execution.schema.json`.

**Important fields:** `checked`, `executed`, `execution_status`, `operating_mode`, `executable_path`, `gauss_version`, `working_directory`, `command`, `code_source`, `script_path`, `timeout_seconds`, `elapsed_seconds`, `exit_code`, `stdout`, `stderr`, `output_files`, `warnings`, `errors`, `next_steps`, `raw_execution_details`.

The workflow may also use environment/package context if present (a supplied `environment_check_result` or `package_inspection_result`), but the execution result object is primary — it is the one artifact that actually reflects what happened for this specific request.

## Execution Status Handling

### completed

**Assistant may say:** code ran in the reported environment/context; the process completed; an exit code was captured; stdout/stderr/output files were captured if present.

**Assistant must not say:** the model is statistically valid; estimates are trustworthy; syntax is generally valid across versions; the analysis is correct; diagnostics are adequate; report conclusions are supported without review.

**Required next step:** route interpretation to the relevant expert dimension, often the Econometrics Expert for models.

### failed

**Assistant may say:** code was invoked but failed; stderr/errors are debugging evidence; a runtime failure can help diagnose syntax, dependency, or runtime issues.

**Assistant must not say:** the model is methodologically invalid solely because execution failed; results exist if they were not produced; code has been fixed unless actually re-executed.

**Required next step:** use the GAUSS Language Expert for implementation/runtime debugging; use package/environment context if dependency-related; preserve Advisory Mode fallback.

### timed_out

**Assistant may say:** the process exceeded its timeout; partial stdout/stderr may exist; runtime/convergence/data-size issues may be involved.

**Assistant must not say:** the model is wrong; the code is invalid; results are available if not captured; increasing the timeout is always safe.

**Required next step:** suggest debugging loops, data size, convergence, or timeout settings, or a smaller test case; use the Software Engineering Expert for performance/code structure where relevant; use the Econometrics Expert for convergence/model diagnostics where relevant.

### blocked

**Assistant may say:** execution did not occur; safety policy blocked the request; the blocking reason and a safe next step.

**Assistant must not say:** code ran; output exists; the block proves the code or method invalid.

**Required next step:** explain safe remediation — choose an environment, provide a working directory, resolve a path, address a missing package, etc.

### skipped

**Assistant may say:** execution did not run because a required execution input was absent or no explicit execution was requested.

**Assistant must not say:** code ran; output was produced.

**Required next step:** ask for explicit code/script and a working directory, or offer advisory review.

### error

**Assistant may say:** the helper/tool encountered an unexpected error; execution state may be unreliable.

**Assistant must not say:** execution succeeded; the model is invalid; outputs are complete.

**Required next step:** explain the tool error and a safe retry/diagnostic path.

### unknown

**Assistant may say:** execution state could not be determined.

**Assistant must not say:** code ran successfully; code failed definitively; results are reliable.

**Required next step:** recommend a rerun with clearer environment/tool context, or continue in Advisory Mode.

## Expert Routing Rules

- **GAUSS Language Expert:** syntax/runtime errors, command usage, GAUSS data structures, implementation correctness, stdout/stderr debugging.
- **Econometrics Expert:** model assumptions, identification, diagnostics, statistical validity, estimates and interpretation, forecast/model evaluation.
- **Software Engineering Expert:** code organization, maintainability, performance, long-running/timeouts, testability, safe refactoring.
- **Documentation Expert:** explaining outputs, documenting code/results, usage notes, troubleshooting text.
- **Education Expert:** teaching interpretation, learner scaffolding, exercises, conceptual explanation.
- **Product Expert:** user workflow impact, time-to-value, product/user value, prioritization of next steps.

Execution status is not itself an expert conclusion. It is evidence routed through the expert system, the same way a package-inspection result or an evidence-schema lookup result is evidence routed through the expert system rather than a conclusion in its own right.

## Interpretation Boundaries

Execution result can support claims about:

- Whether the helper reports execution happened.
- Execution status.
- Exit code.
- Elapsed time.
- Captured stdout/stderr.
- Captured output-file metadata.
- Warnings/errors reported by the helper.

Execution result cannot prove:

- Methodology validity.
- Statistical correctness.
- Estimate reliability.
- Causal identification.
- Model assumptions.
- Diagnostic adequacy.
- Code maintainability.
- Documentation quality.
- Learner understanding.
- Product value.
- Production readiness.

Even `completed` with `exit_code: 0` is execution evidence only.

## Response Pattern

**Suggested structure:**

1. Execution status summary.
2. What was captured.
3. What this does and does not prove.
4. Expert-routed interpretation.
5. Safe next steps.

**Example template:**

- "The code [completed/failed/timed out/was blocked] in the reported execution context."
- "Captured output: ..."
- "This means the process [ran/did not run], but it does not by itself prove..."
- "From a [GAUSS/econometrics/software/documentation/education/product] perspective..."
- "Next step: ..."

## Handling stdout/stderr

- Summarize stdout/stderr; do not overquote long output.
- Preserve warnings/errors materially — do not paraphrase away a specific error message.
- Do not hide stderr just because `exit_code` is `0`.
- Do not invent missing output.
- Clearly separate stdout from interpretation (label captured output as captured output, not as the assistant's own analysis).
- Mention truncation warnings when present.
- If output is too long, summarize and recommend inspecting the full artifact if available.

## Handling Output Files

- `output_files` metadata means files were listed, not necessarily read.
- Do not claim file contents unless they were actually provided or read.
- Distinguish generated (`created_by_execution: true`) from unknown (`created_by_execution: "unknown"`) — the current implementation always reports `"unknown"`, since no before/after comparison is implemented yet.
- Do not expose unnecessary sensitive local paths.
- Recommend reading output files only through a later, explicit file-reading workflow/tool — this workflow does not itself read file contents.

## Handling Warnings and Errors

- Surface execution warnings.
- Surface errors that affected execution.
- Do not treat warnings as fatal unless indicated (a `completed` result with warnings is still `completed`).
- Do not ignore helper warnings about non-interactive invocation, timeout, truncation, package status, unsafe paths, or missing environment — these are exactly the warnings `scripts/gauss_code_execution.py` is designed to surface, and dropping them silently would defeat the point of generating them.

## Handling Package Context in Execution Results

- A missing package before execution may block execution.
- Unknown package status may warn.
- An installed package does not prove syntax validity.
- An installed package does not prove methodology validity.
- An installed package does not prove execution success.
- A missing package does not mean GAUSS is missing.
- No auto-installation — this restates `tools/gauss_code_execution.md`'s Relationship to Package Inspection and `scripts/gauss_code_execution.py`'s implemented conservative default (block on `missing_packages`, warn on `unknown_packages`) rather than inventing new policy.

## Handling Real Invocation Limitation

- A real GAUSS 26 smoke test during `v0.25.0` implementation showed the naive default command form (`[executable_path, script_path]`) entered the interactive GAUSS prompt and timed out, rather than exiting non-interactively.
- Execution-aware responses must not overstate real execution reliability while this remains unresolved.
- If a user asks whether GAUSS execution is production-ready, the answer is no — not yet confirmed.
- Fake-runner self-test success is not proof of real GAUSS invocation success; the two are independently verified (implementation-logic correctness vs. real-invocation correctness) and must not be conflated in a response.

## Failure and Fallback Patterns

- `failed` → debug using stderr/errors.
- `timed_out` → performance/convergence/runtime investigation.
- `blocked` → resolve the safety/input issue.
- `skipped` → provide the missing explicit input.
- `error` → tool diagnostic/retry path.
- `unknown` → rerun or advisory interpretation.

Advisory Mode remains available in all cases — an execution-result interpretation failure must never break the assistant's ability to keep helping with code, explanation, review, documentation, education, or product reasoning, the same Graceful Fallback Principle `planning/v0.19.0-gauss-tooling-strategy-and-execution-modes.md` established for every tool in this framework.

## Risks and Open Questions

- How to present long stdout/stderr safely without either truncating meaningfully or overwhelming the user.
- When to ask for more context vs. offer interpretation with stated assumptions.
- How to cite/link output files if they are later materialized into an actual review artifact.
- Whether this workflow should change the Code Assistant system prompt, or remain a referenced workflow file like `workflows/expert-routing.md`.
- How to integrate with future runtime orchestration, if that is ever planned.
- Whether execution-result interpretation should require a dedicated "execution evidence" block in the response, similar to how retrieval-backed responses cite evidence.
- How to handle partial outputs (e.g., a `timed_out` result with meaningful partial stdout).
- How to handle conflicting stdout/stderr/exit_code signals (e.g., `exit_code: 0` but stderr contains warning-shaped text).
- How to handle a successful execution with obvious statistical red flags visible in the captured output (e.g., a wildly implausible coefficient) — does the workflow require flagging this proactively, or only on request?
- How to handle the real-invocation limitation in user-facing wording without either alarming users unnecessarily or understating the risk.
