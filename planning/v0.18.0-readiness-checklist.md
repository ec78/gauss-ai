# v0.18.0 Readiness Checklist

## Release Goal

`v0.18.0` consolidates the six-expert system completed at `v0.17.0`. It does not add a new expert. It adds cross-system reference and maintenance artifacts that make the existing expert system easier to maintain, audit, evaluate, and extend — closing the gap between "the system works" and "the system is easy to keep working correctly as it keeps growing."

The six operational experts:

- GAUSS Language Expert
- Econometrics Expert
- Software Engineering Expert
- Documentation Expert
- Education Expert
- Product Expert

The six correctness dimensions these experts separately own:

- Implementation correctness
- Methodological correctness
- Maintainability/design correctness
- Documentation/explanation correctness
- Education/learning-design correctness
- Product/user-value correctness

State clearly:

- Routing remains documented/manual-evaluation-driven — `workflows/expert-routing.md` was not modified this milestone.
- No runtime orchestration is implemented anywhere in the framework.
- No expert behavior changed. No `EXPERT.md`, `BODY_OF_KNOWLEDGE.md`, or `OPERATIONAL_PROFILE.md` decision rule, activation trigger, or output contract changed in substance — the `v0.18.0` profile audit's 12 fixes were all narrow textual/cross-reference corrections.
- No benchmark behavior changed — `evaluations/benchmark-prompts.md`, `evaluations/benchmark-coverage.md`, and `evaluations/runs/INDEX.md` were not modified this milestone.
- No schema behavior changed — `schemas/command_lookup_evidence.schema.json` was not touched.

## Consolidation Artifacts Summary

### Expert Registry

**Path:** `experts/EXPERT_REGISTRY.md`

**Purpose:** Summarizes all six operational experts, correctness dimensions, ownership, non-ownership, activation summaries, related files, and maintenance notes — one page to find any expert's identity without reading every operational profile in full.

### Expert Boundary Matrix

**Path:** `experts/EXPERT_BOUNDARY_MATRIX.md`

**Purpose:** Summarizes expert ownership boundaries, false equivalences, escalation paths, and what each expert must avoid overclaiming — consolidates ~30 scattered independence bullets from `workflows/expert-routing.md` into one scannable matrix.

### Expert Routing Cheat Sheet

**Path:** `workflows/expert-routing-cheatsheet.md`

**Purpose:** Provides a compact quick-reference for six-axis routing, 25 common routing patterns, evidence/context rules, escalation rules, and an anti-overclaiming checklist — a summary, not a replacement, for `workflows/expert-routing.md`.

### Operational Profile Consistency Audit

**Path:** `planning/v0.18.0-operational-profile-audit.md`

**Purpose:** Audits all six `OPERATIONAL_PROFILE.md` files for structure, stale wording, related-file accuracy, escalation completeness, runtime disclaimers, and cross-profile consistency.

**Audit result:**

- All six profiles audited, read fresh in full.
- 12 textual inconsistencies found and fixed across four profiles (GAUSS Language: 4; Documentation: 2; Education: 5; Product: 1). Econometrics and Software Engineering were already clean from the `v0.17.0` readiness audit.
- No expert behavior changed.
- No routing behavior changed.
- No runtime orchestration implied.

### Evaluation Dashboard

**Path:** `evaluations/EVALUATION_DASHBOARD.md`

**Purpose:** Summarizes benchmark categories, evaluation state, guard counts, known warnings, historical exceptions, and guard command expectations, in one consolidation snapshot pointing back to `evaluations/benchmark-coverage.md` and `evaluations/runs/INDEX.md` as the sources of truth.

### Expert-System Maintenance Guide

**Path:** `workflows/expert-system-maintenance.md`

**Purpose:** Documents how to maintain the expert system when experts, routing, benchmarks, evaluations, release docs, or readiness checks change — including a checklist for adding a new expert, a routing-update checklist, a stale-wording search checklist, a benchmark-maintenance checklist, and a release-hygiene checklist.

## Six-Expert System Summary

- GAUSS Language Expert owns implementation correctness.
- Econometrics Expert owns methodological correctness.
- Software Engineering Expert owns maintainability/design correctness.
- Documentation Expert owns documentation/explanation correctness.
- Education Expert owns education/learning-design correctness.

State:

- Each correctness dimension remains separate. One dimension cannot prove another.
- The strictest applicable evidence/context requirement wins.
- Pseudocode or unverified syntax must be labeled.
- Product hypotheses must be labeled when evidence is missing.
- Testing recommendations are not execution claims.
- Evidence validation is structural, not semantic or execution validation.

## 25.x Benchmark Decision

`25.x` consolidation benchmarks were considered and intentionally deferred for `v0.18.0`.

**Reason:** the `v0.18.0` artifacts (`experts/EXPERT_REGISTRY.md`, `experts/EXPERT_BOUNDARY_MATRIX.md`, `workflows/expert-routing-cheatsheet.md`, `evaluations/EVALUATION_DASHBOARD.md`, `workflows/expert-system-maintenance.md`) are read-only consolidation references. They summarize already-tested behavior from `21.x`-`24.x` rather than introducing new expert behavior, new routing behavior, or new runtime behavior. The proposed `25.x` prompts in `planning/v0.18.0-expert-system-consolidation.md`'s "Benchmark Plan" section would mostly re-test known-good expert-boundary behavior already covered by the Software Engineering, Documentation, Education, and Product benchmark categories.

Future `25.x` benchmarks may still be useful if the consolidation artifacts become part of a user-facing retrieval/evaluation workflow, or if an automated routing layer is introduced later — at that point the artifacts would stop being purely read-only summaries and would exercise genuinely new behavior worth testing directly.

State:

- No benchmark prompts were added in `v0.18.0`.
- No benchmark coverage rows were added in `v0.18.0`.
- No run files were created in `v0.18.0`.
- `evaluations/EVALUATION_DASHBOARD.md` was updated to show `25.x` as "Not added" / optional, not as a pending or planned category.

## Important Findings

- The six-expert system is now operationally complete, and this milestone did not need to change that — it only made the existing system easier to maintain and audit.
- Consolidation artifacts (registry, boundary matrix, cheat sheet, dashboard, maintenance guide) reduce drift risk but do not change any expert's behavior, activation trigger, or output contract.
- Stale wording has been a recurring maintenance risk across `v0.16.0`, `v0.17.0`, and this milestone's own profile audit (which found a prior task's own remediation note had overclaimed what it fixed) — this is now addressed with the profile audit's findings and the maintenance guide's stale-wording checklist.
- The registry, boundary matrix, cheat sheet, profile audit, dashboard, and maintenance guide together provide a clearer system-of-record structure than the prior state, where this information was implicit or scattered across `workflows/expert-routing.md` and six separate operational profiles.
- Evaluation state is now easier to inspect through `evaluations/EVALUATION_DASHBOARD.md` instead of reconstructing it from three separate files or live guard output.
- Skipping `25.x` avoids redundant evaluation of unchanged behavior — the consolidation artifacts do not introduce anything `21.x`-`24.x` didn't already test.

- No automated stale-wording guard — `workflows/expert-system-maintenance.md`'s Stale Wording Search Checklist is a manual process, not a script.
- No automated evaluation dashboard generation — `evaluations/EVALUATION_DASHBOARD.md` is a manually maintained snapshot, explicitly labeled as such.
- No strict-mode enforcement change — strict checks remain informational, consistent with `v0.12.0`/`v0.13.0` policy.
- Strict validation/tracking still have documented warning-promoted-to-failure cases (`glm`/`olsmt` HDF5-URI warnings; the two historical tracking warnings).
- Evidence validation remains structural, not semantic or execution validation.
- GAUSS code is not executed by any guard or validation check in this framework.
- Tracking validation checks prompt/coverage/run/index consistency, not response quality.
- Consolidation docs can still become stale if not maintained — the maintenance guide reduces but does not eliminate this risk.
