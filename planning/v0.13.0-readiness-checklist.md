# v0.13.0 Readiness Checklist

## Release Goal

`v0.13.0` moves the local default release-readiness gate into CI by adding a minimal GitHub Actions workflow that runs default checks automatically on `push` and `pull_request`. It:

- Runs the default release-readiness check (`python scripts/check_release_readiness.py`) in CI.
- Does not enforce strict mode — the workflow never passes `--strict`.
- Does not suppress any warning — the workflow's output is the underlying scripts' real output, unmodified.
- Preserves the existing policy that strict checks remain documented informational/future warning-free gates, not current release blockers.
- Validates all of the above with the `20.x` Default CI Guard Integration benchmark category.

- **Strict mode:** not run by CI — confirmed directly, `--strict` does not appear anywhere in the workflow file.
- **Warnings:** not redirected or suppressed — confirmed directly, the single `run:` step has no output redirection, filtering, or `continue-on-error` masking; whatever `check_release_readiness.py` prints locally is exactly what appears in the CI log.
- **Code path:** CI uses the same local release-readiness entrypoint rather than a separate code path — the workflow does not reimplement any check logic; its pass/fail is entirely `check_release_readiness.py`'s own exit code.

## Default vs Strict Behavior

- Default release-readiness checks (`validate_all_evidence.py` + `check_evaluation_tracking.py`, both non-strict, or `check_release_readiness.py` which runs both) are the current release-health gates — passing with exit code `0` is what "release-ready" means today, locally and in CI.
- Strict checks (`--strict`) are informational/future warning-free gates, not current release blockers.
- CI currently runs default checks only; it does not run `--strict` for either underlying script.
- Strict evidence validation still fails for `glm.evidence.json` and `olsmt.evidence.json` — reviewed HDF5-URI path-warning false positives, not real path leaks.
- Strict tracking still fails for the two documented historical warnings: the `2.2`/`2.3` Prompt ID mismatch, and the unindexed `v0.3.0` smoke-test file.
- CI passes if default release-readiness passes — confirmed directly, both locally and via `check_release_readiness.py`'s own default-only exit-code logic.
- Strict warnings must not be hidden to make CI pass — no workflow step, script change, or documentation change in this milestone does or recommends that.

## Final Validation and Guard State

- `python scripts/validate_all_evidence.py` (default, re-run for this audit): `Checked 14 file(s): 14 as expected, 0 unexpected`, `Total warnings across all files: 6`, `Overall: PASS`.
- `python scripts/validate_all_evidence.py --json`: confirms the same (`"overall_pass": true`, `"unexpected_count": 0`, `"total_warnings": 6`).
- `python scripts/validate_all_evidence.py --strict`: `Overall: FAIL`, exactly 2 unexpected files (`glm.evidence.json`, `olsmt.evidence.json`).
- `python scripts/check_evaluation_tracking.py` (default, re-run for this audit): `81` prompt IDs, `81` coverage rows, `68` run files referenced, `73` index entries checked, `0` errors, `2` warnings, `Overall: PASS`.
- `python scripts/check_evaluation_tracking.py --json`: confirms the same structured result.
- `python scripts/check_evaluation_tracking.py --strict`: `Overall: FAIL` (exit 1), the same 2 documented historical warnings promoted.
- `python scripts/check_release_readiness.py` (default, re-run for this audit): `Default checks overall: PASS`, exit `0`.
- `python scripts/check_release_readiness.py --json`: `{"default_pass": true, "overall_pass": true, ...}`.
- `python scripts/check_release_readiness.py --strict`: default checks section still reports `PASS`; the separate, labeled "Strict Checks (informational; failure is expected)" section reports `FAIL` for both underlying scripts, with an explicit note that this does not affect the overall release-readiness result; script exit code remains `0`.

To be explicit about what these results mean: a default **PASS does not mean zero warnings** — it means zero errors/unexpected results, with the 2 (tracking) and 6 (evidence, across two files) warnings present and accounted for. **Release readiness is based on default gates only**, and this is now enforced automatically by CI as well as locally. Both **`--strict` failures are expected** and limited strictly to previously documented, reviewed, warning-promoted-to-failure cases — no new or unexplained strict-mode failure exists anywhere in the current repository state. Evidence validation checks structure only: it **does not prove GAUSS semantic correctness or that any GAUSS code was executed**.

## Important Findings

- CI now exercises the exact same default release-readiness entrypoint used locally — `check_release_readiness.py` — with no separate CI-only validation path, confirmed directly from the workflow file's single check step.
- CI adds automation without changing validator behavior: `scripts/check_release_readiness.py`, `validate_all_evidence.py`, and `check_evaluation_tracking.py` were not modified as part of adding CI.
- Strict checks remain visible but non-blocking, both locally and now in CI — this is a continuation of `v0.12.0`'s documented policy, not a new decision made under time pressure while wiring up CI.
- Warning visibility is preserved end-to-end: no redirection, filtering, or suppression exists anywhere in the workflow file or in `check_release_readiness.py`'s subprocess-output handling.
- No new separate CI-only validation path was introduced — confirmed by the fact that the exact command run in CI (`python scripts/check_release_readiness.py`) is identical to, and produces identical output to, the command a contributor runs locally.

## Remaining Limitations

- Strict checks are not enforced by CI yet — this is a deliberate `v0.13.0` scope boundary, not an oversight.
- No non-blocking strict CI job exists yet (for example, a `continue-on-error: true` job that runs `--strict` and reports without failing the workflow).
- No strict-warning allowlist/config file exists yet; the two current exceptions remain docs-only (`scripts/README.md`, `evaluations/benchmark-coverage.md`'s "Historical Tracking Exceptions" section).
- Evidence validation remains structural, not semantic or execution validation — a schema-valid file is not proof of correct or current GAUSS behavior, nor that any code ran.
- No GAUSS execution engine exists; nothing in this milestone changes that.
- Multi-expert routing remains documentation/manual-evaluation-driven, not runtime orchestration.
- Only the GAUSS Language Expert and the Econometrics Expert are operationalized; the Software Engineering, Documentation, and Education experts remain narrative-only.

## Non-blocking Follow-ups

- Consider adding a non-blocking strict CI job later (informational only, not a required gate).
- Consider a strict-warning allowlist/config file only if the number of documented exceptions grows enough to make manual policy-reading unwieldy — two exceptions does not currently justify it.
- Consider pinning dependencies in a `requirements.txt` if the dependency set grows beyond the single `jsonschema` package.
- Consider adding a CI status badge to `README.md` after the workflow's naming/path has stabilized through at least one more milestone (deliberately not added yet, per `v0.13.0`'s own implementation task, since the repo doesn't otherwise use badges).
- Continue operationalizing the remaining narrative-only experts (Software Engineering, Documentation, Education) in a future capability milestone.
- Revisit panel-estimation coverage if official or package docs are found to include a verified estimator beyond `tscsFit`.
- Add more package-specific econometric benchmarks.
