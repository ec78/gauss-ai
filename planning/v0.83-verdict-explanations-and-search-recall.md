# v0.83.0 — Verdict Explanations and Search Recall: Design

Status: **implemented** (2026-10-10). The plan (§1–§8) was approved with every recommendation in §8. §9 records what changed during implementation and both required diffs; §10 is testing. §11: the live evaluation `73.x` was not run before release; it was run after release on 2026-10-12 (§11).

## 1. Why

Live evaluation 72.x (`planning/v0.82-bounded-control-flow-syntax-coverage.md` §11.3) passed all sixteen tasks with no wrong verdict. It did leave four findings where the verdict was right but the client could not tell *why*, or could not find what it needed:

| Finding | Seen in | What the client saw |
|---|---|---|
| F1. Wrong reason for code with no documented calls | 72.6, 72.8 | not_ready, reason "generation policy does not permit code generation (block)". Nothing was generated. |
| F2. A partial verdict doesn't name its cause | 72.3, 72.15 | review_required, reason "validation coverage is partial". The client guessed the cause wrong both times. |
| F3. `sprintf`'s variadic arguments never get a documented type | 72.15 | Every `sprintf` with an argument after the format string is review_required. |
| F4. `gauss_search_docs` fails a plain question | 72.16 | "compute a covariance matrix" → `ungrounded`, no sources. |

Goals:
- every reason states the real, deterministic cause;
- F3 reaches the verdict its documentation supports;
- a plain search returns clearly labeled **candidate** pages.

Constraints:
- no verdict changes except F3's intended one and the variadic-alignment correction in §3.3, each of which will show in the §6.3 verdict diff;
- `ground_multi`, `resolve_concepts` and `compute_generation_gate` stay byte-for-byte unchanged;
- no change to `_SYSTEM_STATEMENT_REGISTRY`, `compute_eligibility`'s verdict logic, `compute_evidence_profile` or the readiness state machine.

Deferred (unchanged from `PROJECT_STATUS.md`): category inference for elementwise expressions (72.3 finding 1), and public release readiness.

## 2. Investigation findings

All probes ran through the real `validate_code` / `ground_multi` at HEAD (`d6167b0`, v0.82.0) against the published docs copy (`C:/Users/Owner/.gauss-ai/docs`).

### 2.1 F1: where the "generation policy" reason comes from

`validate_code` (`gauss_conversation_engine.py:1875`) builds a `GroundingBundle` from the code's own called symbols and then calls `compute_generation_gate(bundle)`. That gate is the `ask()` path's gate, reused so `validate_generated_code` can be shared between the two paths. When no called symbol is documented, the bundle has no sources, so the policy is `block`. `compute_eligibility` (`gauss_pre_execution_validation.py:2570`) then adds the issue `generation policy does not permit code generation (block)`, and `compute_handoff_readiness` returns it as the not_ready reason. `NO_DOCUMENTED_CALLS_NOTE` is attached separately in `CodeValidationResult.notes`.

| Probe | Verdict | Reasons today |
|---|---|---|
| 72.6 accumulator loop (no calls) | not_ready | `generation policy does not permit code generation (block)` |
| 72.8 loop with `if`/`break` (no calls) | not_ready | same; syntax `partial` is never mentioned |
| `x = colmedian({1,2,3});` (only an unknown call) | not_ready | the `block` text **and** `unresolved/unsupported call symbol(s): colmedian` |
| `x = meanc({1,2,3}); y = foo(x);` | not_ready | `unresolved/unsupported call symbol(s): foo` (policy `supported_only`, no misleading text) |

On the `validate_code` path, `block` happens exactly when no called symbol was matched (an ambiguous match gives `clarify` → REQUIRES_CLARIFICATION, which has its own accurate reason). That is the same condition that attaches the note, so the note's wording can replace the gate's wording with no change in when it fires.

### 2.2 F2: what "validation coverage is partial" hides

`compute_handoff_readiness` (`:3207`) adds that reason whenever `compute_evidence_profile(coverage) != BROAD`. It never receives the coverage itself or the role checks, so it cannot say which dimension fell short. The MCP response (`_validation_to_dict`, `gauss_mcp_server.py:216`) carries neither `coverage` nor `parameter_role_checks`. A client therefore **cannot** diagnose a partial verdict at all. The CLAUDE.md procedure ("call `validate_code(...)` directly and inspect `pre_execution.coverage`") exists because the MCP response leaves this out.

| Probe | Coverage | The unknown role check | Reason today |
|---|---|---|---|
| 72.15 `s = sprintf("%d and %d", 3, 4);` | role `partial` | `sprintf` arg 2, parameter `...`, documented category unknown | "validation coverage is partial…" |
| 72.3 `v = 1 ./ seqa(1, 1, 10); mu = meanc(v);` | role `partial` | `meanc` arg 1, parameter `x`, argument `v` unresolved (assigned from an expression) | same |

Every `UNKNOWN` role check today carries the same explanation, "the documented parameter type or this argument's own literal category could not be confidently determined". That doesn't even say which *side* is unknown. The information exists inside `check_parameter_roles` / `resolve_argument_category` (`:808`, `:872`); it is thrown away.

The syntax gap has the same problem in a smaller form: "syntax validation coverage is partial" doesn't name the construct, although `SyntaxValidationResult.unknown_constructs` has it (e.g. `control_flow_block`).

### 2.3 F3: why variadic arguments never get a type

Two separate defects, plus a pre-existing misalignment:

1. **No `...` type ever attaches, not just `sprintf`'s.** `_PARAM_TYPE_LINE_RE` (`:413`) only accepts identifier names. In the published docs, 23 pages document `:param ...:`, two more spell it `:param ....:` (`sprintf.rst`, `eqsolvemt.rst`), and one escapes it (`gmmfit.rst`: `:param \.\.\.:`). None of the 23 `:type` lines for these parameters attaches. All but one say `various` or `any` (which classify as unknown anyway). The exception is `sprintf.rst`'s `:type ....: NxK numeric or string vectors`.
2. **A four-dot variadic in a signature is not variadic.** `mlmt/maxlikmtprofilelimits.rst`: `maxlikmtProfileLimits(&logl, out0 [, ...., c1])` parses as `(2, 4, ('&logl', 'out0', '....', 'c1'))`, a maximum of 4 arguments, although `...` means no upper bound since v0.82.0. It is the only signature with this spelling.
3. **Arguments after a variadic slot are checked against the wrong parameter (pre-existing).** `check_parameter_roles` is purely positional. For `eqSolvemt(&fct, par, ..., c)` called with two extra arguments, argument 4 is compared against `c`. About twenty published signatures have parameters after `...` (a regex sweep finds 24 names, a few of them from prose; the §6.2 diff will give the exact list): `eqSolvemt`, `gmmFit`, `QNewtonmt`, `integrate1d`, `chibarsq`, `minimize`, `optim`, `cmlmt*`, `maxlikmt*`, `fred_set`, `dbnomics_set`, …. Arguments *beyond* the parameter list are skipped (`:898`). That is why 72.15's third argument (`4`) has no role check at all.

**The trap in the obvious fix.** Attaching `sprintf`'s type text as-is makes things worse. `classify_documented_type("NxK numeric or string vectors")` returns `('string',)`. `_TYPE_KEYWORDS` (`:344`) has no `numeric` entry and doesn't match the plural `vectors`. So the scalars in 72.15 would become a **MISMATCH**, and 72.15 a false not_ready.

**Real `tgauss.exe -b` spot checks (GAUSS 26.1.4, 2026-10-10), the open "does a scalar count" question:**

| Snippet | Result |
|---|---|
| `sprintf("%d and %d", 3, 4)` (scalars) | runs: `3 and 4` |
| `sprintf("%d", {1 2, 3 4})` (2x2 matrix) | runs |
| `sprintf("%d %d", {1, 2}, {3, 4})` (column vectors) | runs |
| `sprintf("%d", {1 2 3})` (row vector) | runs |
| `sprintf("%s=%d", "a" $\| "b", {1, 2})` (string array + vector) | runs |
| `sprintf("%s", "hello")` | runs |
| `sprintf("%d and %d", 3)` (format wants more than given) | runtime `G0159 Wrong number of parameters` |
| `sprintf("%d")` (no argument after the format) | `'sprintf' requires 2-1000 arguments, got 1` |

`sprintf.rst`'s own example passes a scalar (`sprintf(fmt, 3.1415926536)`). So the documented type accepts scalars, vectors, matrices and strings: a scalar is a 1x1 matrix (the v0.81.0 `_CATEGORY_ACCEPTS` rationale). The word that carries this is **"numeric"**. A bare `numeric` (no `matrix`/`vector`/`scalar`/`integer`/`array` in the same type text) appears on exactly **one** `:type` line in the published docs (`sprintf`'s) and on **zero** `:rtype` lines. Every other "numeric" line already names `vector` or `matrix` and would be unchanged.

The last two rows are pre-existing gaps, outside this milestone's scope: `sprintf("hello");` is **already** handoff_candidate in v0.82.0 and fails at run time, and format strings are never parsed. Both fail honestly at run time; see §5.

### 2.4 F4: why search returns nothing

`gauss_search_docs` is `ground_multi(query)`, serialized. `ground_multi`'s only other caller is `ConversationEngine.ask()` (`:1465`), whose bundle feeds `compute_generation_gate` (`:1493`). Probes:

| Query | Status / gate | What `resolve_concepts` found | What search returns |
|---|---|---|---|
| compute a covariance matrix | ungrounded / block | `covariance` unresolved; derived index: nothing (1 keyword < `MIN_KEYWORD_OVERLAP` 2) | nothing |
| correlation matrix | ungrounded / block | same shape (1 keyword) | nothing |
| ordinary least squares regression | ungrounded / block | derived index ties at 3 keywords: `fgls`, `ols`, `olsmt`, … but **all four words** also unresolved | nothing |
| variance-covariance matrix | ungrounded / clarify | ambiguous: `robustse`, `varcovm`, `varcovx`, `vcm`, `vcx`, … | only the phrase in `ambiguous_topics`, **no candidate names** |
| cholesky decomposition | ungrounded / clarify | ambiguous: `bandchol`, `chol`, … | phrase only |
| eigenvalues of a symmetric matrix | ungrounded / clarify | ambiguous: `eigh`, `eighv`, `lapeigh*` | phrase only |
| read a csv file | ungrounded / clarify | ambiguous: `csvreadm`, `csvreadsa` | phrase only |
| how do I sort a matrix by a column | ungrounded / clarify | ambiguous: `sortmc`, `sortr`, `sortrc`, `setcoldateformats` | phrase only |
| column means / meanc / transpose | grounded / full | resolved | the page |

(For "ordinary least squares regression" the derived ties are reported as ambiguous only when they come from 2+ distinct symbols, which they do. The table's "nothing" is because, at `MAX_RESOLUTIONS = 4`, the four unresolved single-word entries fill the cap before the derived-index entry is appended.)

So there are two failure modes:
- **A. Ambiguous:** the candidates were found and then thrown away by the MCP serializer. That is the common case.
- **B. Below threshold:** one meaningful keyword, by design not enough to *resolve*.

For B, how wide is a one-keyword match? `covariance` matches 17 index entries and `correlation` 7. Every one has the keyword in its own Purpose text. The noise is from add-on packages and guides (`tsmt/`, `sslib/`, `bhatlib/`, `textbook-examples/`). Restricted to core reference pages (no subdirectory) and de-duplicated by page, `covariance` gives 9 pages, `vcmvcx.rst` among them. A broad word like `random` (50 entries) is already exact-resolved, so the fallback never runs for it.

## 3. Proposed design

Deterministic and stdlib-only throughout.

### 3.1 F1: the real reason on `validate_code`

- `compute_eligibility` gains an optional keyword, `no_evidence_issue: str | None = None`. When the policy is `block` and it is given, that text replaces `generation policy does not permit code generation (block)`. The eligibility value (`INELIGIBLE`) is unchanged.
- `validate_generated_code` passes it through. `validate_code` supplies a reason derived from `NO_DOCUMENTED_CALLS_NOTE`: "no documented GAUSS function call was found to ground this code against -- code with no documented calls is never eligible for controlled execution".
- `ask()` passes nothing, so its wording is unchanged (there, generation really was gated).
- The note stays in `notes` (no response-shape break).

For 72.8: the reason now states the real blocker. The syntax gap becomes visible through the coverage summary added in §3.2. Reasons on a not_ready verdict stay limited to blockers.

### 3.2 F2: name the gap, deterministically

**(a) Categorical unknown causes on role checks.** `ParameterRoleCheck` gains `unknown_cause: str | None = None` (defaulted; set only when `status == UNKNOWN`). It takes values from a new enum, `RoleUnknownCause`:

| Value | Meaning | Determined by |
|---|---|---|
| `documented_type_missing` | the docs have no `:type` line for this parameter | `param.source is None` |
| `documented_type_unclassified` | there is a `:type` line, but its text names no known category (e.g. `various`) | `UNKNOWN in param.category`, source present |
| `variadic_position` | the argument falls at or after a `...` that is followed by other parameters (§3.3) | position arithmetic |
| `argument_expression` | the argument is an expression (`x'x`, `1 ./ v`), never evaluated | not a literal, not a simple identifier |
| `argument_untraced` | a variable with no single traceable governing assignment in this snippet | `_governing_assignment` returned `None` on both passes |
| `argument_assigned_from_expression` | the variable's governing assignment is an expression | right-hand side found, but not a literal or a single call |
| `return_type_undocumented` | the variable is assigned from `f(...)` whose docs give no classifiable `:rtype` | single-call right-hand side, no `return_categories` |
| `return_type_imprecise` | a documented return category disagrees with the parameter; a gap, not a mismatch (existing rule) | the existing `DOCUMENTED_RETURN` branch |

`resolve_argument_category` gets a sibling, `resolve_argument_category_with_cause(...)`, which returns the cause alongside the result. The existing function keeps its signature and delegates to it, so no caller changes. The `explanation` text becomes specific: "argument 1 of `meanc` (parameter `x`): `v` is assigned from an expression (`1 ./ seqa(1, 1, 10)`), which is never evaluated". It is a fixed template filled with the argument text and the cause; nothing is model-written.

**(b) Specific readiness reasons.** `compute_handoff_readiness` gains optional `coverage` and `parameter_role_checks` keywords. The state logic is untouched: the same conditions produce the same state. Only the review reasons change:
- the syntax reason names its constructs: "syntax validation coverage is partial -- unmodelled construct(s): control_flow_block";
- in place of the bare "validation coverage is partial…", one reason per non-complete dimension. For the role check, each unknown is listed as `symbol` argument N (parameter `p`): cause. The list is capped at 5, then "and N more". If a dimension is unknown for a reason not listed above, the generic text remains as a fallback; there is never a blank reason.

Both callers (`validate_generated_code`, so both paths) pass the new keywords. The CLI chat therefore gets the same, better wording.

**(c) MCP response.** `_validation_to_dict` adds:
- `coverage`: the six `ValidationCoverage` fields;
- `coverage_gaps`: a list of structured entries `{check, symbol, argument, parameter, cause, detail}` for role checks with status unknown, unverified preconditions, unknown signatures and unknown syntax constructs. Only gaps are listed, not every passing check, so the response stays small.

Existing keys are unchanged.

### 3.3 F3: variadic parameters

1. **Normalize the name.** A parameter name that is three or four dots, optionally backslash-escaped (`...`, `....`, `\.\.\.`), becomes `...`. This applies in two places: when splitting a signature (`_parse_signature_occurrence`), so `maxlikmtProfileLimits` becomes unbounded like every other `...`; and in `_PARAM_TYPE_LINE_RE` / `_extract_documented_parameter_types`, so `:type ...:` / `:type ....:` attach to the `...` parameter.
2. **Bare `numeric` means matrix.** In `classify_documented_type`, a type text containing `numeric` and none of `matrix`/`array`/`vector`/`scalar`/`integer` gets the `matrix` category. Evidence: GAUSS numeric values are matrices (the v0.81.0 `_CATEGORY_ACCEPTS` citations), plus the §2.3 spot checks. Measured effect: exactly one `:type` line (`sprintf`'s) and no `:rtype` line. `sprintf`'s `...` then classifies as `('string', 'matrix')`, which accepts scalar, vector, matrix and string, matching every row real GAUSS ran. Plural forms (`vectors`, `matrices`) are **not** added: they would also change `:type A: One or more matrices`, and nothing here needs them.
3. **Align arguments with a variadic slot.** Let `k` be the position of `...` in the parameter list.
   - Arguments before `k` are checked as today.
   - If `...` is the **last** parameter (`sprintf(fmt, ...)`), every argument at position ≥ `k` is checked against the `...` parameter. That fixes the uncovered third argument in 72.15.
   - If parameters **follow** `...` (`eqSolvemt(&fct, par, ..., c)`, `gmmFit(&fct, y[, ...[, gCtl]])`), arguments at position ≥ `k` are `UNKNOWN` with cause `variadic_position`. Which one is `c` can only be inferred by right-aligning, and the flattened `required` flags after `...` are off by one (min counts exclude `...`; positions include it). So this stays a disclosed gap, not a guess.

   This is the one place where a pre-existing check moves from MATCH/MISMATCH to UNKNOWN. A wrong MATCH could only flip candidate → review_required, and a wrong MISMATCH not_ready → review_required. The verdict diff (§6.3) will list every such case.

Expected verdict effect: 72.15's `sprintf("%d and %d", 3, 4)` goes from review_required to **handoff_candidate**. Every other variadic page's `...` type is `various`/`any`/absent, so it stays unknown.

### 3.4 F4: labeled candidates in search, gate untouched

A new function, `search_candidates(query, bundle, *, docs_root_str)`, lives in `gauss_conversation_engine.py`. It is **called only by `gauss_mcp_server.gauss_search_docs`**, after `ground_multi` has returned. It reads the finished bundle and the concept index and returns candidate entries. It never modifies or wraps the bundle.

1. **From ambiguity (mode A):** every `AMBIGUOUS` resolution's `candidates` (already computed), in their existing order.
2. **From a one-keyword fallback (mode B):** used only when the bundle has **no sources and no ambiguous candidates**. Index entries sharing at least one keyword with the query are ranked by categorical tiers:
   1. keyword-overlap count, descending;
   2. core reference page (no subdirectory) before package pages, before guide and example pages;
   3. page stem, alphabetically.

   No numeric score is exposed. Results are de-duplicated by page and capped at `MAX_SEARCH_CANDIDATES = 8`, with `candidates_truncated: true` and the total count when cut.
3. Each candidate is `{symbols, citation, purpose, status: "candidate"}`, where `purpose` is the page's own Purpose sentence from the index. **No full page content**: to read a candidate, the client searches its name, which resolves exactly and returns a real `grounded` source. Every candidate symbol is re-verified with `command_doc_lookup.lookup(...)` against the caller's docs root before it is listed, matching the alias-index discipline.
4. The response adds `candidates`, `candidates_truncated` and a fixed `candidate_note`: "Candidate pages are keyword matches, not grounded answers. Search a candidate's name to read its documentation." `grounding_status`, `sources`, `unmatched_topics` and `ambiguous_topics` are computed exactly as today and never change because of candidates. A search that finds only candidates still reports `ungrounded`.

**Why the `ask()` generation gate cannot change:**
- **Code:** `ground_multi`, `resolve_concepts`, `GroundingBundle`, `compute_generation_gate` and `gauss_doc_concept_index.resolve_derived_concepts` are not edited. The release check is an empty `git diff` over those function bodies. `MIN_KEYWORD_OVERLAP` stays 2; the fallback uses its own constant inside `search_candidates`.
- **Data flow:** candidates are never a field of `GroundingBundle` (which the gate reads), so the gate has no path to them. `ask()` never calls `search_candidates`.
- **Tests:**
  1. a structural test that `ConversationEngine.ask`'s source does not reference `search_candidates`, in the style of the existing no-import-path tests;
  2. a gate-equivalence test that pins `(status, policy, matched, unmatched, ambiguous)` for a fixed question set on a synthetic fixture (including the §2.4 shapes), computed at HEAD before the change and asserted after;
  3. a provider-raises test: `ask()` on a mode-B question still returns the `block` message without calling the provider.

## 4. Scope boundary

In scope: §3.1–§3.4.

Out of scope:
- **Expression category inference** (72.3 finding 1; deferred by `PROJECT_STATUS.md`). F2 makes that gap *visible*; it doesn't close it.
- **Format-string parsing** for `sprintf`/`printf` (G0159), and `sprintf`'s real minimum of 2 arguments. The first changes what "compatible" means. The second would read `:param` prose ("One or more"). Both fail honestly at run time; see §5.
- **Right-aligning arguments after a variadic slot** (§3.3 step 3).
- **Plural type keywords** (§3.3 step 2).
- **Changing `MIN_KEYWORD_OVERLAP` or the resolution rules** that feed grounding.
- **Search ranking beyond categorical tiers.** No embeddings, no TF-IDF scores shown as fact.

## 5. Known limitations this design accepts

To be disclosed in `KNOWN_LIMITATIONS.md`:
- `sprintf` with fewer arguments than its format string consumes (`sprintf("%d and %d", 3)`) moves from review_required to handoff_candidate. It fails at run time with `G0159`, which the handoff reports. `sprintf("hello")` (one argument; real GAUSS requires 2) is already a candidate in v0.82.0 for the same reason. Readiness is not correctness: the same class as 72.14.
- One-keyword candidates can include pages that merely *use* the concept (e.g. `rndMVn` "given a covariance matrix" for a covariance question). They are labeled as candidates with their Purpose sentence, so the client can tell.
- The coverage-gap list is capped at 5 role-check entries per response.

## 8. Decisions needed

1. **F1 wording.** Replace the gate text with the note's own cause on `validate_code` only, keeping `ask()`'s wording and the existing `notes` entry. *Recommend yes.*
2. **F2 response shape.** Add `coverage` and `coverage_gaps` (gaps only) to `gauss_validate_code`, rather than the full `parameter_role_checks` list. *Recommend gaps only:* smaller, and it answers the question clients actually got wrong.
3. **F3 open question: should a documented "NxK numeric or string vectors" accept a scalar?** *Recommend yes*, through the bare-`numeric` → `matrix` rule. Evidence: real GAUSS runs scalar, vector, matrix and string arguments; the page's own example passes a scalar; and the rule changes one `:type` line in the whole doc set. The alternative, reading `vectors` as `vector`, would make a matrix argument a false not_ready.
4. **F3 alignment.** Make arguments after a mid-list `...` `UNKNOWN` (`variadic_position`) instead of checking them against the wrong parameter. *Recommend yes.* It fixes a pre-existing defect in the safe direction; the verdict diff will show every affected case.
5. **F4 mode B (the one-keyword fallback).** Include it, or ship only mode A (exposing the ambiguous candidates already computed)? *Recommend including it,* with the core-before-packages tier and a cap of 8. Without it, 72.16 itself still returns nothing. Mode A alone fixes cholesky/eigen/csv/sort but not covariance or correlation.

### 11.5 Findings

1. **String contents are scanned as code (73.14). Real defect; Major, unsafe direction.** `validate_code` collects user-defined names with `_ASSIGNMENT_TARGET_RE` over code with comments stripped but strings not masked (`gauss_conversation_engine.py:1909-1911`). Any name followed by `=` inside a string is treated as assigned, and it is then dropped from `called_symbols` (`:1915`).
   - `print "det = " d;` makes `det(x)` a variable call: a false not_ready, with a misleading reason.
   - With `print "fakeinverse = " f;`, a hallucinated `fakeinverse(x)` is **not reported unknown**, `symbol_check` claims `complete`, and the verdict softens from not_ready (correct without the label) to review_required. Only signature coverage, which still counts the undocumented call, holds it there.
   - Probes: `dos` (system registry) and a violated `invpd` precondition still give not_ready behind a label, the latter with the wrong first reason.

   Labels like `"name = "` are ordinary GAUSS `print` style, so this is likely to occur in real use. Not observed to reach handoff_candidate.
2. **Multi-line statements are cut at newlines (73.10). Real defect; Moderate.** `_masked_statements` (`gauss_pre_execution_validation.py:1264`) iterates `splitlines()` before splitting on `;`. So `_governing_assignment` reads `x = { 2 1 0,` as the whole assignment, and a multi-line matrix literal is never traced. That is the layout of the GAUSS docs' own examples. Effects:
   - `eigh` on such a literal: a false review_required.
   - A known `invpd` SPD violation written over two lines softens from not_ready to review_required (precondition UNVERIFIED).

   Not execution-reachable: review_required issues no `validation_id`. The client already worked around it once (73.12, one-line literal on purpose), which is the steering cost 72.3 showed.
3. **`coverage_gaps` is silent for undocumented calls (73.14).** When `signature_check` is partial because a call is undocumented, the gap list is empty. Normally that call would be in `unknown_symbols` (a not_ready blocker), so the omission only shows when finding 1 has hidden it. It is still a hole in F2's "every partial verdict names its cause".
4. **Search recall gaps that F4 does not reach (73.12, 73.13). Minor.**
   - `sortc`'s derived keywords are `sortc, sort, dataframe`. For "sort a matrix by a column", `sortmc` and `sortr` tie at two keywords and form the ambiguous resolution. Mode B never runs when ambiguous candidates exist, so the standard function is never offered.
   - "percentile" appears in no index entry (`quantile`: `quantile, probabilitie`). The plain sentence then partially grounds on the dataloop `vector` page through the generic word "vector". Because a source exists, no candidate is offered.
5. **Cosmetic: the loop counter in `user_defined_symbols`.** `i` is listed for the `if`/`break` loop (73.8) but not for the plain loop (73.7). No verdict effect.

### 11.6 Recommendation

v0.83.0's own changes all held live: F1, F2, F3 and F4 each behaved as §3 designed, and the client's explanations of partial verdicts are now right. It stays released. **The two defects found live (findings 1 and 2) should be the next milestone's first scope, ahead of the deferred work.**
- Both come from text scanning that ignores GAUSS's lexical structure: strings are not masked, and statements end at newlines instead of `;`.
- Both are bounded and share one fix shape: a single masked, `;`-terminated statement stream used by the assignment scan and both tracers.
- Finding 1 weakens the hallucination guard, which is the validator's core job.

Finding 3 belongs in the same change. Per CLAUDE.md, the fix needs:
- regression tests for every 73.10/73.14 probe;
- a verdict diff against HEAD on the real docs (expected changes are in both directions: false not_ready → candidate, and the softened verdicts back to not_ready).

Finding 4 is a separate, smaller search-side item (curated aliases or a rule letting an exact-token page compete with ambiguous ties); it must keep the §3.4 gate-equivalence guarantees. Per `CLAUDE.md`, the next milestone is not started until the user chooses it.
