# v0.20.0 - GAUSS Environment Detection Tool

## Release Goal

`v0.20.0` plans the first read-only tool capability for the GAUSS Code Assistant, following the strategy laid out in `planning/v0.19.0-gauss-tooling-strategy-and-execution-modes.md`.

The goal is to define a tool that can:

- Check whether GAUSS is installed or discoverable.
- Identify the GAUSS executable path when possible.
- Identify the GAUSS version when possible.
- Identify the platform and detection method.
- Report unavailable, unknown, or ambiguous states without failing.
- Recommend the correct assistant operating mode.

State clearly:

- This milestone is for planning the environment detection tool, not building it.
- The tool is read-only.
- No GAUSS code execution is implemented.
- Package inspection is not implemented.
- Advisory mode remains fully supported.
- The assistant must not break if GAUSS is missing or inaccessible.

## Relationship to v0.19.0 Operating Modes

`planning/v0.19.0-gauss-tooling-strategy-and-execution-modes.md` defined three operating modes. Environment detection is the mechanism that lets the assistant choose among them safely.

### Advisory Mode

**Use when:**

- GAUSS is not installed.
- GAUSS cannot be found.
- GAUSS access is denied.
- Detection fails.
- The executable path is ambiguous.
- The user has not requested execution.
- Execution tools are unavailable.

A detection result should recommend Advisory Mode whenever `installed` is `false`, `unknown`, `inaccessible`, or `ambiguous`.

### Verified Knowledge Mode

**Use when:**

- GAUSS installation is unknown or irrelevant to the task.
- Exact GAUSS claims are supported by verified docs/evidence.
- No execution is requested or performed.

Environment detection is not required for Verified Knowledge Mode — a response can cite verified command evidence regardless of whether GAUSS is installed locally.

### Future Execution Mode

**Use only when:**

- GAUSS is installed and the executable is detected.
- Version is available, or not required for the task.
- Future execution tools exist.
- The user requests or permits execution.
- Execution is safe and scoped.

Environment detection is necessary but not sufficient for Execution Mode — a positive detection result only makes Execution Mode a *candidate*, per the `can_execute_gauss_code` output field below; it does not activate Execution Mode by itself, since no execution tool exists yet and, once one does, further checks (package availability, user permission, scoping) still apply.

## Current State

- No GAUSS environment detection tool exists yet.
- The Code Assistant currently operates in Advisory Mode and Verified Knowledge Mode only, per `planning/v0.19.0-gauss-tooling-strategy-and-execution-modes.md`.
- The assistant must not claim execution — this constraint already exists today (`agents/code-assistant/AGENT.md`'s Limitations and Failure Modes, every `OPERATIONAL_PROFILE.md`'s refusal conditions) and is not weakened by this planning task.
- The repository has tool specifications (`TOOL_SPEC.md`) but no GAUSS executable detection implementation, and `agents/code-assistant/AGENT.md`'s Tools section already anticipates this: "Running GAUSS code, if a runtime tool becomes available... Until tools are implemented, the agent should clearly distinguish between verified code, inferred patterns, and code that should be checked against documentation."
- `v0.20.0` should define the tool contract before implementation, the same way `v0.19.0` defined the operating-mode strategy before any tool existed.

## Proposed Tool

**Possible file:** `tools/gauss_environment_check.md`

**Tool name:** `gauss_environment_check`

**Tool purpose:**

- Detect whether GAUSS is installed or discoverable.
- Identify executable path.
- Identify version where possible.
- Identify platform.
- Identify detection method.
- Return structured unavailable or unknown states.
- Recommend fallback mode.

**Tool permission level** (per `TOOL_SPEC.md`'s Permission Model):

## Detection Strategy

Plan detection strategies without implementing them.

### User-provided path

If the user provides a GAUSS executable path:

- Check whether the path exists.
- Check whether it appears executable.
- Optionally attempt a version query in a future implementation.
- Return a path-specific result.

### PATH lookup

If no path is provided:

- Search `PATH` for expected GAUSS executable names.
- Record matching candidates.
- Handle multiple candidates explicitly.
- Do not silently choose among ambiguous candidates unless a deterministic rule is defined during implementation.

### Common installation locations

Consider platform-specific common paths, without overcommitting to exact final paths:

**Windows:**

- Program Files locations.
- GAUSS installation directories.
- User-specified paths.
- `PATH` lookup.

**macOS:**

- Applications directory.
- Command-line path if installed.
- User-specified paths.
- `PATH` lookup.

**Linux:**

- `PATH` lookup.
- Common local/`bin` or `opt` locations.
- User-specified paths.

**Important:** do not overcommit to exact path names unless verified during implementation. This planning doc lists categories of locations rather than exact final paths, since the exact paths should be verified against real installations at implementation time rather than assumed now.

### Version query

A future implementation may attempt a minimal version check if safe.

This planning doc defines:

- Version query is optional.
- Failure to get a version should not make `installed` false.
- Version-unknown should be represented separately from `installed: false`.
- A version query must not run user code.

### Ambiguous candidates

If multiple GAUSS executables are found:

- Return an ambiguous state.
- Include candidate paths.
- Recommend user selection.
- Do not silently run code.

### Inaccessible executable

If an executable exists but cannot be run:

- Return `installed: unknown` or an inaccessible status.
- Include permission/error notes.
- Recommend Advisory Mode.

## Proposed Input Contract

Future inputs (all optional):

- `preferred_executable_path` — optional string
- `working_directory` — optional string
- `platform_hint` — optional string
- `allow_version_query` — optional boolean
- `detection_timeout_seconds` — optional integer
- `environment_overrides` — optional object
- `strict` — optional boolean

State:

- Inputs are optional.
- The tool should work with no inputs.
- A user-provided path should take precedence over discovery.
- Environment overrides should be handled cautiously — they change what the tool sees, not what is actually installed, and a future implementation should not let an override silently produce a misleading `installed: true`.
- No input should cause file mutation.

## Proposed Output Contract

Structured output fields:

- `checked` — true/false
- `installed` — true/false/unknown
- `accessible` — true/false/unknown
- `executable_path` — string/null
- `executable_candidates` — list
- `version` — string/null
- `version_known` — true/false
- `platform` — string/null
- `detection_method` — string
- `detection_status` — `found`/`not_found`/`ambiguous`/`inaccessible`/`error`/`unknown`
- `operating_mode_recommendation` — `advisory`/`verified_knowledge`/`execution_candidate`
- `can_execute_gauss_code` — true/false/unknown
- `warnings` — list
- `errors` — list
- `next_steps` — list
- `raw_detection_details` — optional object

**Field meanings:**

- `installed: true` does not mean code has been run.
- `execution_candidate` does not mean Execution Mode is active.
- `can_execute_gauss_code: true` means future execution *may* be possible, not that execution occurred.
- Version unknown is not the same as `installed: false`.
- Ambiguous candidates require user clarification or a deterministic policy before execution.

## Failure and Fallback Behavior

- Tool failure should return structured error output.
- Tool failure should not break the assistant.
- If detection fails, recommend Advisory Mode.
- If GAUSS is missing, recommend Advisory Mode.
- If GAUSS is inaccessible, recommend Advisory Mode.
- If multiple candidates are found, recommend Advisory Mode or user clarification.
- If a version query fails but the executable exists, report the executable found with version unknown — do not downgrade this to `installed: false`.
- Do not claim GAUSS execution.
- Do not claim package availability.
- Do not claim syntax correctness from environment detection.

## Assistant Response Behavior

**If found:**

- State GAUSS appears available.
- Report executable path if appropriate.
- Report version if known.
- Explain that this only confirms environment availability.
- Do not claim code execution.
- Explain that future package inspection or execution may still be needed.

**If not found:**

- State GAUSS was not detected.
- Continue in Advisory Mode.
- Provide code or guidance as normal.
- Explain that execution was not performed.
- Offer user path-based detection if appropriate.

**If unknown/inaccessible:**

- State what could not be determined.
- Provide warnings/errors.
- Continue in Advisory Mode.
- Ask for an executable path only if needed.

**If ambiguous:**

- List candidates.
- Ask the user to choose or provide a preferred path.
- Do not execute.

## Relationship to Six Experts

- **GAUSS Language Expert** may use environment detection to determine whether execution might be possible, but still requires command evidence for syntax claims — a detected installation is not a substitute for `required_evidence` in `experts/gauss-language/OPERATIONAL_PROFILE.md`.
- **Econometrics Expert** should not treat GAUSS availability as statistical validity — an installed GAUSS environment says nothing about whether a given estimator or model is appropriate.
- **Software Engineering Expert** should not treat GAUSS availability as maintainability — environment detection reports what is installed, not whether code is well-organized.
- **Documentation Expert** may document environment setup (e.g., install locations, `PATH` configuration) but should not claim execution occurred from a detection result alone.
- **Education Expert** may teach how to check the environment but should not claim learning effectiveness from a successful detection.
- **Product Expert** may reason about the user value of environment detection (e.g., reduced setup friction, clearer next steps) but should not treat a working detection tool as product validation — per `experts/EXPERT_BOUNDARY_MATRIX.md`, product value still requires actual user/customer evidence, not internal capability alone.

This extends `planning/v0.19.0-gauss-tooling-strategy-and-execution-modes.md`'s "Relationship to Six Experts" section to the specific, narrower case of environment detection rather than execution generally: no expert's boundary changes, and detection changes what evidence is available, not which expert owns which correctness dimension.

## Risks and Design Questions

- What are reliable executable names across platforms?
- What common installation locations should be checked?
- Is a version query safe and available across GAUSS versions?
- Does a version query require license availability?
- How should the tool distinguish "not installed," "not accessible," and "not licensed"?
- Should multiple candidates be considered ambiguous, or should the newest version win by default?
- Should detection be purely read-only filesystem/path inspection, or allow a minimal executable call (e.g., a version flag)?
- How should environment variables be handled?
- How should platform-specific paths be tested without all platforms available to the implementer?
- How should detection work in WSL, Windows, macOS, Linux, and container environments?
- How should this interact with future MCP or local connector tools?
- What should happen if GAUSS is installed but no license is available?
- How should logs avoid exposing sensitive paths unnecessarily?
