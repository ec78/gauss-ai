# v0.94.0 — Data Import and Export: Design

Status: **draft, awaiting decisions** (§8). Baseline for every probe and comparison: HEAD `99cdfc9` (`v0.93.1` plus its publication record), with the docs copy fetched on 2026-10-23 and this machine's GAUSS 26.1.4 installation.

The first of the three milestones toward a complete analysis workflow, agreed on 2026-11-14: v0.94 import and export, v0.95 state across steps, v0.96 the next coverage candidates (v0.93 plan §13.6). On 2026-11-14 the user signed off on relaxing `CLAUDE.md`'s file-I/O constraint in the shape proposed that day: one project folder; reads only from its `input/` folder, writes only to its `output/` folder; file names written literally in the code; GAUSS never touches the real folders; every file named in the run prompt. This plan turns that into a rule. Everything else that reaches outside GAUSS's memory stays `not_ready`.

## 1. Why

Code that reads or writes a file is always `not_ready`: the 76 `file_read` and 53 `file_write` names in `_SYSTEM_STATEMENT_REGISTRY`, and the 38 estimators in `_DATASET_ARGUMENT_REGISTRY` whose data argument may name a file (v0.89.3). So no analysis can start from the user's data, and none can keep a table or a figure:
- In the 1,410-program corpus, 618 of the 1,021 `not_ready` programs are blocked for file I/O (§2.4).
- In 84.x, 84.9 (`loadd` of a CSV) was `not_ready`; in 80.11 and 81.2 a plot could not be seen or kept (`plotSave` is a file write).
- The coverage milestones since v0.90 (decision 10 = B) cannot change this; they only widen what in-memory code can run.

Goals:
- code that loads the user's data from the input folder, or writes tables, datasets and figures to the output folder, can reach `handoff_candidate` and run;
- the run prompt names every file read (with its size and content digest) and every file kept;
- figures come back to the client as images;
- with no analysis folder configured, **every verdict is unchanged** (the default for everyone who does not opt in).

Constraints (from `CLAUDE.md`, unchanged except the relaxed rule):
- deterministic: which calls touch which files is decided by a curated, cited registry and the masked statement stream (`lex_gauss_source(...)`, `source_statements(...)`), never a model;
- the handoff stays human-approved, digest-bound and single-use; the client never answers a run prompt;
- the analysis folder is set by the user in the config, never by the client;
- no network, no telemetry; zero runtime dependencies for the base CLI.

Out of scope:
- state across steps (v0.95): each run still starts empty, so a later step re-loads its data;
- file handles and record I/O (`open`, `readr`, `writer`, `fopen`, `fgets`, `dataopen`, `seekr`), GAUSS's `load`/`save` statements, HDF5, `gda*`, databases, network sources (`fred_load`, URLs);
- deleting, renaming or appending to the user's files;
- the guided repair pipeline (`gauss_repair_*`), which keeps its own workspace rules.

## 2. Investigation findings

All probes ran on 2026-11-14 with `tgauss.exe -b` (GAUSS 26.1.4), each from its own new scratch directory, with the script in a `gen/` subfolder and the working directory one level up, as the handoff runs it (`gauss_code_execution.py`: `cwd=working_directory`, the script in `working_directory/<generated dir>/`).

### 2.1 Where GAUSS resolves a bare file name

- **Against the working directory, not the script's folder.** `csvReadM("d.csv")`, `loadd("d.csv")`, `loadd("d.csv", "y + x")`, `olsmt("d.csv", "y ~ x")` and `dstatmt("o.dat")` all read the file placed in the working directory (sp94a, sp94b); `cdir(0)` printed the working directory.
- **No fallback search.** In an empty working directory, `loadd("auto2.dat")`, `csvReadM("beef_prices.csv")`, `loadd("beef_prices.csv")` and `dstatmt("beef_prices.csv")` all stopped with "not found" or "Could not open file", although `C:\gauss26\examples\beef_prices.csv` exists (sp94c). A bare name therefore reaches only what the server put in the working directory.
- **A missing file is a GAUSS error,** not a silent empty result: `csvRead error: file 'missing.csv' not found`, then "Program terminated" (sp94b).

### 2.2 Where GAUSS writes

- `csvWriteM(a * 2, "o.csv")`, `saved(a, "o.dat", "y" $| "x")`, `xlsWrite(a, "o.xlsx", "A1", 1, "")` and `plotSave("p.png", 640|480)` each created their file in the working directory (sp94a). No file appeared anywhere else in the scratch tree.
- **`plotSave` works in batch mode.** `plotXY(...)` followed by `plotSave("p.png", 640|480)` wrote an 11 KB, 640x480 PNG of the expected line plot, with no window.
- **Side files.** `xlsWrite` also created `xls.log` in the working directory. A run can create files the code never names.
- `xlsReadM("o.xlsx", "A1", 1, "")` read back the 4 rows just written.

### 2.3 What the documentation says

The candidate functions' pages give each one exactly one file argument, typed `string` where a `:type` exists:

| Function | File argument | Notes |
|---|---|---|
| `loadd` | 1 `dataset` | "filepath to the dataset on disk, URL, or existing dataframe": a URL is a network read |
| `csvReadM`, `csvReadSA` | 1 `file` | |
| `xlsReadM`, `xlsReadSA`, `spreadSheetReadM`, `spreadSheetReadSA` | 1 `file` | `.xls`, `.xlsx` |
| `getHeaders` | 1 `fname` | |
| `csvWriteM` | 2 `filename` | optional `append` |
| `xlsWrite`, `xlsWriteM`, `xlsWriteSA`, `spreadSheetWrite` | 2 `file` | |
| `saved` | 2 `dataset` | type from the extension: CSV, GDAT, DAT, XLS, XLSX |
| `plotSave` | 1 `filename` | `.jpg`, `.plot`, `.png`, `.pdf`, `.svg`, `.tiff` |

The 38 dataset-argument estimators keep their v0.89.3 registry positions.

### 2.4 How code names files today

Over the 618 corpus programs blocked for I/O (a rough regex classification of the file-name argument of the common read, write and estimator calls; scratch script, not committed):

| Form | Count | Example |
|---|---:|---|
| `getGAUSSHome(...)` (GAUSS's bundled example data) | 216 | `loadd(getGAUSSHome("examples/auto2.dat"))` |
| a variable or expression | 193 | `olsmt(data, formula)` |
| a bare literal | 191 | `csvReadM("prices.csv")` (overcounts: includes some formula strings) |
| `__FILE_DIR $+ "..."` | 14 | `loadd(__FILE_DIR $+ "gbs_ato.gdat")` |
| an absolute path literal | 4 | `olsmt("C:/data/auto2.dat", ...)` |

So a bare-literal rule covers how a client writes code for the user's own files, but **about a third of the blocked code is the documentation's own idiom of loading GAUSS's example datasets** (decision 2).

## 3. Proposed design

### 3.1 The analysis folder

A new config key, `analysis_folder` (`gauss-ai config set analysis-folder <path>`), set by the user only. It holds two subfolders, created on first use: `input/` (the user puts data here; gauss-ai never writes to it) and `output/` (gauss-ai creates one new subfolder per run). `gauss-ai doctor` and `gauss_session_start` report it. **Unset, nothing in this plan applies** and every verdict is byte-for-byte what `v0.93.1` gives (§6.3 proves it).

### 3.2 Which file accesses are allowed

A curated `_FILE_ACCESS_REGISTRY`, like the dataset-argument registry: each entry is a function, its file argument's position, the direction (`read` or `write`), the extensions it accepts, and the doc page that types the argument (§2.3). A call is an **allowed file access** only when, in the masked statement stream:
- the function is in the registry (or is a v0.89.3 dataset-argument estimator, as a read);
- its file argument is **one string literal and nothing else** (no `$+`, no variable, no `getGAUSSHome`, no `__FILE_DIR`);
- the literal is a **bare file name**: letters, digits, `_`, `-`, `.` and spaces only; no `/`, `\`, `:` or `..` (which also excludes drive letters, UNC paths and URLs); and an extension on the read or write list (decision 3);
- for a read, the file exists directly in `input/` (decision 4).

Every other use of a `file_read`/`file_write` name stays `not_ready` with today's reason, and the reason now says why the exception did not apply: "the file name is not a single quoted name", "the file name contains a path", "no analysis folder is configured", "`d.csv` is not in the input folder".

The validator reports allowed accesses as a new `file_accesses` list (line, function, direction, name) instead of a `system_statements` entry, so they no longer force `not_ready`. Nothing else about the verdict changes: the code still has to meet every other check to reach `handoff_candidate`.

### 3.3 The run: copy in, copy out

`execute_execution_handoff` keeps its fresh temporary directory. With file accesses:
1. **At prepare,** the server resolves each read name in `input/`, records its size and SHA-256, and binds the folder path, each `(name, size, sha256)` and each write name into the request digest. The prompt gains:
   ```
   Reads (copied from C:\...\analysis\input; the originals are not changed):
     prices.csv (12,480 bytes, sha256 3f2a…)
   Keeps (copied to a new folder under C:\...\analysis\output):
     summary.csv, fit.png
   ```
2. **At decide (after "yes"),** the server copies the read files into the temporary directory, re-checking each SHA-256 (a file changed since the prompt refuses the run, nothing launched); runs GAUSS; then copies **only the files the code names as writes** into a new `output/<UTC timestamp>-<request id prefix>/` folder. Nothing is ever overwritten. Other new files (`xls.log`) are listed as "created, not kept"; a named write that GAUSS did not create is listed as "not created".
3. GAUSS never sees the real folders: its working directory is still the temporary one, deleted afterwards (§2.1: no fallback search, so a bare name reaches only the copies).

### 3.4 Results back to the client

`gauss_execution_decide` adds `files_kept` (name, full path, size) and `files_not_kept`. Each kept `.png`, `.jpg` or `.svg` up to a size cap is also returned as image content (MCP 2.3's `Image`), so a client can show the figure (decision 5). Tables stay files; the client reads them with its own tools if it has any.

### 3.5 What the user changes in `CLAUDE.md`

The project-wide constraint becomes: code that reaches outside GAUSS's own memory is `not_ready`, **except** an allowed file access (§3.2) into a user-configured analysis folder, run by copy-in/copy-out (§3.3), with every file named in the prompt. Every other system-touching statement and every other file form stays `not_ready`.

### 3.6 What does not change

Grounding, the generation gate, signature, precondition, syntax and role checks; the library rule; the handoff's approval, single-use and binding rules; the CLI chat's own offer (it passes no analysis folder, decision 6); the repair pipeline.

## 4. Scope boundary

In scope: §3, its tests, the §6 diffs, `CLAUDE.md` (§3.5), `docs/mcp-server.md`, `docs/pre-execution-validation.md`, the README quickstart's data section, `KNOWN_LIMITATIONS.md`, the release records and live evaluation 85.x.

Out of scope: §1's list.

## 5. Known limitations this design accepts

- **No state across steps** (v0.95). A three-step analysis loads its input file three times.
- **A package procedure could still write a file of its own choosing** into the temporary directory (v0.92's disclosed residual risk); it is now listed as "created, not kept" instead of vanishing silently.
- **Bare names only:** no subfolders inside `input/`, and code copied from the docs (`getGAUSSHome(...)`, `__FILE_DIR $+ ...`) needs editing to a bare name unless decision 2 allows the example data.
- **The registry, not the docs, says which argument is the file;** a function Aptech adds or changes needs an entry.
- **Large files:** the copy-in has size caps (decision 3); a dataset larger than the cap must be reduced first.
- **Formula strings and sheet arguments are not checked** beyond what the signature check already does.

## 6. Testing plan

### 6.1 Automated tests (synthetic fixtures, temp dirs, network-free)

- **Validator:** each registry entry allowed with a bare literal and an existing input; refused with a variable, `$+`, `getGAUSSHome`, `__FILE_DIR`, a `/`, `\`, `:`, `..`, a URL, a disallowed extension, a missing input, no analysis folder; a file name inside a comment or another string is never read (lexical discipline); every other system statement in the same code still blocks.
- **Handoff:** the digest binds the folder, the inputs' SHA-256 and the write names; a changed input refuses at decide without launching; the fake runner sees copies only; only named writes are kept; nothing is overwritten (two runs, two folders); side files are listed; a decline copies and creates nothing.
- **MCP server:** the session reports the folder; the prompt lists reads and keeps; `files_kept`, images within the cap; the test module pins an empty config, so no test reads a real analysis folder.
- **Config and doctor:** the new key, folder creation, a missing or unwritable folder.
- **Full suite** (49 files and the new ones), `check_release_readiness.py`, the CI matrix.

### 6.2 GAUSS spot checks

Each allowed function once, from its own scratch directory through the real copy-in/copy-out path, recording what was read and written. Each refused form once, to confirm the refusal reason.

### 6.3 Verdict diff

The 1,410-program corpus and the 84.x snippets, at HEAD and on the working tree, each in its own process:
- **with no analysis folder:** no field changes anywhere (the invariance proof);
- **with a synthetic analysis folder** holding every bare-named input the corpus reads: every move listed, every move to `handoff_candidate` run in GAUSS through copy-in/copy-out.

### 6.4 Gate

No grounding change; the gate questions are re-run once to confirm.

## 7. Live evaluation 85.x

A fresh client conversation in a new empty folder, with the local-scope registration under both drive-letter spellings, the real-GAUSS opt-in proved by one prepare, and an analysis folder whose `input/` holds one realistic CSV (for example a small panel of prices or a cross-section). Plain-language tasks, one at a time:
- load the file and summarize it;
- run a regression on it and save the coefficient table;
- plot two columns and show the figure;
- a task that needs a file outside the folder or a URL (expected: `not_ready`, with a reason the client can explain);
- one run the user declines (confirm nothing was copied or kept), and one input changed between prompt and answer (confirm the run is refused).

Record the exact prompt, the user's reply and the result for every run, and re-run each approved program with `tgauss.exe -b` on a copy of the input.

## 8. Decisions needed

1. **Folder layout:** one `analysis_folder` with `input/` and `output/` subfolders (recommended: one setting, and the user can see at a glance what gauss-ai may read), or two separate settings?
2. **GAUSS's own example data:** also allow reads of the literal forms `getGAUSSHome("examples/<name>")` and `getGAUSSHome("pkgs/<package>/examples/<name>")`, read in place from the configured GAUSS installation, listed in the prompt like other reads (recommended yes: it is about a third of the blocked corpus, it is the documentation's own idiom, and it reads only Aptech's shipped files), or keep this milestone to the analysis folder?
3. **Extensions and size caps:** reads `.csv`, `.txt`, `.xls`, `.xlsx`, `.dat`, `.gdat`, `.dta`, `.sas7bdat`; writes `.csv`, `.xls`, `.xlsx`, `.dat`, `.gdat`, `.png`, `.jpg`, `.svg`, `.pdf`; at most 200 MB per input file and 500 MB per run (recommended), or different lists or caps?
4. **Check that inputs exist at validation time,** so a client learns about a wrong name before asking for a run (recommended), or only at prepare?
5. **Return figures as images** in `gauss_execution_decide` (recommended, at most 4 images of at most 2 MB each), or file paths only?
6. **CLI chat (`gauss-ai` with no subcommand):** keep its execution offer in-memory only in this milestone (recommended: the MCP path is where analyses happen, and it keeps the change to one caller), or give it the same file access?
7. **A read-only input listing:** add the input files' names and sizes to `gauss_session_start`'s response, so a client can see what data exists without shell access (recommended yes; names and sizes only, never contents)?
