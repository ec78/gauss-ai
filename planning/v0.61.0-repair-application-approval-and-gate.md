# v0.61.0 - Repair Application Approval and Gate Validation

## Release Goal

Implement the fourth and final approval layer from `planning/v0.58.0-repair-application-safety-design.md` §4.C (Application Approval) and the pure, re-verifying precondition check from §13 (Application Gate) — as pure logic only. This milestone authorizes *checking whether an application would be allowed to proceed* and *recording a human decision about that exact authorization* — it does not write a file, construct a patch, or perform any repair application. `apply-repair` and every part of §14 (Application Transaction) remain future, separately-authorized work.

Clean working tree. `scripts/gauss_repair_planner.py`, `scripts/gauss_repair_approval.py`, `scripts/gauss_repair_draft.py`, and `scripts/gauss_repair_draft_approval.py` unmodified throughout this milestone — confirmed by `git diff --stat` showing zero lines against any of the four at ship time.

## Architecture

```
RepairDraft (gauss_repair_draft.py, v0.59.0)
    -> repair_draft_digest(draft) -> str                          (unchanged)
    -> DraftApprovalStore (gauss_repair_draft_approval.py, v0.60.0)
        .get_decision(draft) -> DraftApprovalRecord | None

ApplicationApprovalStore (this milestone, gauss_repair_application_approval.py)
    .approve(draft, recorded_at) -> ApplicationApprovalRecord
    .decline(draft, recorded_at) -> ApplicationApprovalRecord
    .revoke(draft, recorded_at) -> bool                            (transitions in place)
    .get_decision(draft) -> ApplicationApprovalRecord | None

evaluate_application_gate(..., inputs) -> ApplicationGateResult    (this milestone, gauss_repair_application_gate.py)
    -- pure function; consumes a RepairPlan, a RepairApprovalStore decision,
       a RepairDraft, a DraftApprovalStore decision, an ApplicationApprovalStore
       decision, and a caller-supplied "current source identity" -- never reads
       a file, never computes a hash of its own.
```

`scripts/gauss_repair_application_approval.py` follows the exact architectural discipline `gauss_repair_draft_approval.py` established one layer up: it imports only `gauss_repair_draft` (for `RepairDraft` and `repair_draft_digest`), never `gauss_repair_planner.py`, `gauss_repair_approval.py`, or `gauss_repair_draft_approval.py`, and never any execution/workspace/orchestration module. It performs zero I/O and holds exactly one piece of state — an in-memory `dict[str, ApplicationApprovalRecord]` keyed by digest.

`scripts/gauss_repair_application_gate.py` is new in kind: it is the first module in this pipeline whose entire purpose is to *combine* several upstream layers' state into one pass/fail verdict, rather than adding a new layer of its own content. It imports `gauss_repair_planner`, `gauss_repair_approval`, `gauss_repair_draft`, `gauss_repair_draft_approval`, and `gauss_repair_application_approval` — but calls only the pure, already-exported functions/methods each already provides (`repair_plan_digest`, `repair_draft_digest`, `.get_decision(...)`, `source_identity_digest`) rather than re-deriving any of their logic a second way. It never imports `gauss_workspace.py`, `gauss_workspace_file_reader.py`, or any execution/orchestration module, and performs zero I/O of its own — a "current source identity" is always a caller-supplied `SourceIdentity` value (the same zero-I/O contract `gauss_repair_draft.py` itself established for `SourceIdentity`), never something this module reads itself.

## Application Approval Model

`ApplicationApprovalDecision`: `approved`, `declined`, `revoked` — mirrors `DraftApprovalDecision`'s three-value shape exactly, for the same reason: this milestone's own task specification lists `revoked` as a first-class decision value, not merely a delete operation.

`ApplicationApprovalRecord` (frozen): `decision`, `draft_digest` (the sole binding key — see "Binding" below), `recorded_at` (caller-supplied clock value, never computed internally), `repair_draft_id` (informational only, mirroring `DraftApprovalRecord`'s own precedent), `safe_to_apply` (always `False`), `safe_to_prepare_draft` (always `False`), `approval_boundary` (one of two fixed strings).

**Binding.** Application approval binds to `repair_draft_digest(draft)` — the same digest draft-approval itself binds to, not a new, independently-computed "application digest." This is a deliberate choice, directly following §5 of the design document, which defines `repair_application_id` as an opaque per-attempt identifier (not a content digest) and treats the approved draft's own content identity as the thing being authorized for application — there is no separate "application content" to fingerprint independently of the draft it applies. `ApplicationApprovalRecord` therefore carries no separate `application_digest` field; a future `repair_application_id` (assigned at the actual application-transaction step, not this milestone) is the opaque per-attempt identifier the design anticipates, and is out of scope here since no transaction exists yet to assign one to.

## Revoke: Consistent With the v0.60.0 Precedent

`ApplicationApprovalStore.revoke(...)` transitions an existing active (approved or declined) record to `REVOKED` in place, exactly as `DraftApprovalStore.revoke(...)` (`v0.60.0`) already does — not a new design decision, but a direct continuation of the precedent `v0.60.0`'s own revoke-transitions-in-place choice set, since this milestone's task specification lists `revoked` as a first-class decision value here too. A `REVOKED` record does not block a fresh `approve`/`decline` call for the same digest; only an active record does. Duplicate and conflicting decisions both raise `ApplicationApprovalConflictError`, mirroring `DraftApprovalConflictError` exactly.

## The Application Gate

`evaluate_application_gate(...)` is a pure function taking every value the design's §13 lists as a precondition, explicitly as parameters — never fetched, read, or re-derived internally:

- `repair_plan` and `repair_approval_store` (or an already-looked-up `ApprovalRecord | None`) — strategy approval.
- `repair_draft` and `draft_approval_store` (or an already-looked-up `DraftApprovalRecord | None`) — draft approval.
- `application_approval_store` (or an already-looked-up `ApplicationApprovalRecord | None`) — application approval.
- `current_source_identity: SourceIdentity | None` — the caller's freshly-observed source state, exactly the same zero-I/O, caller-supplied contract `validate_repair_draft`'s own `current_source_identity` parameter already established in `v0.59.0`. This module never reads a file to obtain it.
- `workspace_status: str | None` — an optional, caller-supplied workspace-eligibility signal (e.g., the `WorkspaceStatus` value the caller already has from its own `WorkspaceRegistry`), since this module does not import `gauss_workspace.py` and cannot check eligibility itself.

Preconditions checked (each is a named, independently reported `ApplicationGateCheck`, mirroring `DraftValidationCheck`'s own per-check-result shape):

1. `STRATEGY_APPROVAL_EXISTS` — a strategy-level `ApprovalRecord` exists for the current plan digest and its decision is `approved`.
2. `DRAFT_APPROVAL_EXISTS` — a `DraftApprovalRecord` exists for the current draft digest and its decision is `approved`.
3. `APPLICATION_APPROVAL_EXISTS` — an `ApplicationApprovalRecord` exists for the current draft digest and its decision is `approved`.
4. `SOURCE_HASH_MATCHES` — `current_source_identity` (if supplied) has a `content_hash` equal to the draft's own bound `source_identity.content_hash`. If `current_source_identity` is not supplied, this check fails closed (`passed=False`) rather than being skipped — unlike `validate_repair_draft`'s own permissive "skip if absent" convention, the gate's job is specifically to prove freshness, so an absent re-verification is itself a failure here, not a no-op.
5. `WORKSPACE_ELIGIBLE` — `workspace_status`, if supplied, is not one of the terminal/ineligible values (`deleted`); if not supplied, this check fails closed identically to #4, for the same reason.
6. `PATH_UNCHANGED` — `current_source_identity`'s artifact (`workspace_id`, `relative_path`) matches the draft's own bound artifact exactly (this is a restatement of part of the draft's own digest binding, checked independently here as a defense-in-depth precondition, per the design's explicit "all of the following must hold... any single failure blocks" instruction rather than relying on the digest match alone).
7. `EDIT_SCOPE_UNCHANGED` — structurally guaranteed true: `RepairDraft` is immutable and `edit_scope` is part of what `repair_draft_digest` hashes, so any scope change already changes the digest every other check re-verifies against. Reported as a real, checked (not assumed) result the same way `validate_repair_draft`'s own `SINGLE_FILE` check documents a structural guarantee explicitly rather than silently.
8. `NO_REVOCATION` — none of the three approval records (strategy, draft, application) currently has decision `revoked`.
9. `DRAFT_DIGEST_MATCHES_APPROVED` — the application-approval record's own `draft_digest` field equals the draft's current digest (guards against a caller passing a stale `ApplicationApprovalRecord` alongside a since-changed draft).
10. `VALIDATION_PASSED` — `gauss_repair_draft.validate_repair_draft(draft, current_source_identity)` reports `all_passed=True`, reusing Phase 2's own validation rather than re-deriving structural safety checks a second way.

`safe_to_apply` is **not** a field this module ever produces as `True`. `ApplicationGateResult.all_passed` reports whether every precondition holds — a caller could, in a future, separately-authorized milestone, choose to treat an all-`True` gate result as *a* necessary condition for an actual application, but this module itself never claims application is now safe or authorized in any actionable sense: `ApplicationGateResult` has no `safe_to_apply` field at all, deliberately, so no code path anywhere can even superficially resemble flipping the invariant every upstream layer already enforces structurally. §13's remaining preconditions (backup prepared, rollback path verified, application consumer authorized, audit record initialized) are explicitly **not** checked by this module, because no backup mechanism, rollback mechanism, application consumer, or audit mechanism exists anywhere in this repository yet — checking for their presence would be checking for something structurally impossible to satisfy, not a meaningful gate. This is disclosed directly in the result (`not_applicable_checks`), not silently omitted.

## CLI Changes

Four new commands: `approve-repair-application <draft_digest>`, `decline-repair-application <draft_digest>`, `show-repair-application-approval`, `check-repair-application-gate`. The first three mirror `approve-repair-draft`/`decline-repair-draft`/`show-repair-draft-approval` exactly (same digest-binding, same stale-digest-rejection pattern). `check-repair-application-gate` takes no required arguments — it re-evaluates the gate against the adapter's own current in-memory state (`last_repair_plan`, its approval store's decision, `last_repair_draft`, its draft-approval decision, its application-approval decision) and, since the adapter has no real second "current file state" to re-read (no application-layer file target exists in this repository), reports `SOURCE_HASH_MATCHES`/`WORKSPACE_ELIGIBLE` honestly as failing-closed (no current source identity is ever fabricated) unless the tester explicitly supplies fresh values via `--current-content-hash`/`--current-workspace-status` flags — mirroring `repair-draft`'s own "every value is explicit, never invented" convention. No `revoke-repair-application` CLI command is added, consistent with `v0.57.0`/`v0.60.0`'s own precedent of leaving `revoke` at the module/API level only for a layer's first implementation. `reset` clears `last_repair_plan`... through a fresh `ApplicationApprovalStore`. Adapter version string bumped to `v0.61.0 alpha`.

## Disclosures

Every application-approval CLI response includes a fixed boundary string distinct from every prior layer's own boundary text, so "approved" never implies application occurred: for an approval, *"The repair application has been approved. No files have been modified. No repair has been applied. No execution has occurred. The application transaction itself remains unimplemented — approving this authorization records a decision only."* `check-repair-application-gate`'s own output includes an unconditional line stating that a passing gate result does not itself apply anything, since no application transaction exists to invoke.

## Recommendation for the Next Milestone

With all four approval layers now implemented (strategy, draft, application, and — separately, already existing — rerun via the ordinary execution-confirmation path) plus a pure gate check re-verifying every checkable precondition, the pipeline has everything the design's §23 Phase 4 (a local single-file application prototype) depends on except the transaction itself. That transaction is also the first code in this repository's history capable of writing to a user's file, so it needs its own explicit, separately-scoped authorization — this milestone deliberately does not request or imply that authorization.
