# v0.36.0 Durable Execution State and Cross-Process Safety — Planning

## Scope

`v0.36.0` replaces the orchestration controller's current in-memory-only safeguards with an optional, explicit, SQLite-backed durable state layer. It does not add real execution capability, does not run GAUSS, and does not touch the execution helper, the result schema, workflows, or agents. It exists to establish one invariant durably, across process restarts and across cooperating local processes:

> A confirmed canonical request that has already been authorized or attempted must never be silently invoked again.

**In scope:** a standalone durable-state-store module (`scripts/gauss_orchestration_state_store.py`); a narrow, additive integration point in `scripts/gauss_runtime_orchestration.py` (optional `state_store` parameter; unchanged default in-memory behavior when omitted); an explicit "production construction" factory requiring a store; atomic, transactional invocation authorization; crash-simulation and multiprocessing cross-process tests, all against fake helpers; read-only recovery/inspection tooling; a new evaluation category; documentation updates; a readiness review.

**Out of scope (explicit non-goals):** conversational workflow integration; agent or prompt changes; automatic execution; automatic retry or rerun; distributed workers; multi-host coordination; cloud databases; network services; cooperative GAUSS cancellation; script-path execution; output-file content reading; automatic file cleanup; cross-platform execution claims; cross-version GAUSS claims; methodology validation. **No GAUSS is run during this milestone.**

## Support Claim

This milestone's durability and cross-process guarantees are scoped exactly to:

- One local machine.
- Multiple cooperating Python processes on that machine, using the standard-library `sqlite3` module.
- One shared SQLite database file as the single source of truth.
- Transactional duplicate-invocation protection scoped to one orchestration instance (one canonical request submission) — never a cross-instance, content-based (`request_hash`) uniqueness constraint, since `v0.35.0`'s own `test_84` already established that two independent, identically-coded requests legitimately share a `request_hash` and must both be permitted to execute once each.

**Not claimed:** distributed exactly-once execution; multi-machine coordination; protection when cooperating processes are configured to use different database files or paths; protection against manual, out-of-band tampering with the database file; a guarantee that the underlying `tgauss.exe` process is actually terminated if the *controlling* Python process crashes near the helper-invocation boundary (this milestone tracks *ambiguity*, not guaranteed termination — GAUSS process lifecycle remains outside this layer's control, unchanged from every prior milestone).

## Durable Record Model

One row per orchestration instance in `orchestration_records`, keyed by `orchestration_instance_id` (primary key). Persisted fields, matching the task's required minimum list exactly, plus one addition (`code_digest`) explicitly recommended in lieu of raw code:

`orchestration_instance_id`, `session_id`, `canonical_request_id`, `request_hash`, `code_digest` (SHA-256 hex of inline code — never the code itself), `current_state`, `previous_state`, `confirmation_status`, `confirmation_scope`, `confirmation_timestamp` (an opaque caller-supplied audit label, never parsed as a real clock value — see Confirmation Expiry below), `confirmation_consumed` (boolean), `confirmation_expires_at` (a store-computed real wall-clock epoch value, independent of the opaque `confirmation_timestamp` label), `invocation_status`, `invocation_id`, `execution_status`, `exit_code`, `output_file_count`, `validation_ok`, `validation_problems` (a bounded JSON list of short structural-validation strings — never file content), `failure_category`, `cancellation_status`, `analysis_status`, `report_status`, `transition_sequence_number`, `created_at`, `last_transition_at`, `schema_version`.

A second table, `transition_events`, records the ordered transition history (`sequence_number`, `from_state`, `to_state`, `at`, `note`) per instance, `UNIQUE(orchestration_instance_id, sequence_number)`.

A third table, `invocation_attempts`, records at most one row per `orchestration_instance_id` (`UNIQUE` constraint — defense in depth alongside the atomic conditional `UPDATE` described below), recording `invocation_id`, `request_hash`, and `authorized_at`.

**Explicitly never persisted:** raw inline `code` text; `stdout`/`stderr` text; raw output-file content; secrets or credentials; environment-variable values; raw conversation text. This mirrors, rather than weakens, the codebase's two existing "safe summary" precedents — `OrchestrationRecord.to_safe_summary()` and `gauss_execution_adapter.safe_summary(...)` — neither of which has ever included `stdout`/`stderr` text or code. Durable storage is held to the same bar, not a looser one.

## Transaction Boundaries

Every durable state mutation is one SQLite transaction, committed or fully rolled back — no partial writes are ever visible to a second reader. The single highest-stakes transaction is invocation authorization (see Stage 2's Transaction Requirement below): it verifies every precondition (state, hash, confirmation validity/scope/expiry, no prior invocation) and, only if every precondition holds, atomically marks confirmation consumed, allocates/accepts an invocation ID, transitions the record to `executing`, and appends the transition event — all in one commit, using a single conditional `UPDATE ... WHERE <every precondition>` statement whose `rowcount` determines success. This is the standard, correct SQLite pattern for "check-then-act" under concurrent writers: SQLite's own file-level write serialization guarantees that a second concurrent writer's conditional `UPDATE` will see the first writer's already-committed change (or block behind `busy_timeout` until it can), so its own `WHERE` clause will no longer match once the first writer has succeeded — no explicit application-level lock is required for correctness, only correct precondition encoding in the `WHERE` clause. A `busy_timeout` is set on every connection so lock contention degrades to a bounded wait, not to `SQLITE_BUSY` failures under ordinary contention (tested in Stage 4).

## Locking Model

Default SQLite rollback-journal mode (not WAL) is used deliberately, to keep the durable store to exactly one file on disk with no auxiliary `-wal`/`-shm` side files to account for in containment/cleanup checks. `PRAGMA busy_timeout` is set on every connection (default 5000ms, configurable) so concurrent writers wait rather than fail immediately under ordinary contention. No process-level file lock, no external lock manager, and no advisory locking beyond SQLite's own built-in transaction serialization is used — introducing one would add complexity without adding correctness beyond what a single, precondition-complete conditional `UPDATE` already provides.

## Crash-Recovery Model

Four crash points are modeled and tested (Stage 4), matching the task's exact specification:

1. **Crash before the authorization commit.** No visible change: confirmation remains unconsumed, no invocation ID exists. A retry (a *new*, explicit authorization call, never automatic) may still succeed normally.
2. **Crash after the authorization commit but before the injected helper is called.** The durable record shows `invocation_status: in_progress` with an `invocation_id` set, but no execution result. On reload, this is reported as **ambiguous** — the system cannot know whether the (hypothetical) real helper was ever launched — and is surfaced by the read-only inspection tooling as "requires manual review." No automatic retry occurs; a human (or an explicitly authorized future action, out of scope here) must decide the outcome.
3. **Crash after the helper call returns but before the result is durably persisted.** Same durable signature as (2) — `in_progress`, no result — because this layer has no way to distinguish "the call never returned" from "the call returned but persistence didn't happen" without a change to the helper/adapter boundary, which this milestone does not make (a stop condition explicitly forbids helper/schema modification). This is disclosed honestly as a known limitation, not glossed over.
4. **Crash after the result is durably persisted.** Reload returns the preserved `execution_status`/`exit_code`/`output_file_count`/`failure_category`, and terminal progression (analysis/report) may continue safely from the reloaded state.

**This milestone never claims to know whether GAUSS actually ran when a crash occurs at or near the helper-invocation boundary.** It claims only that the *invocation-authorization* step is atomic and durable, and that an ambiguous post-authorization state is always disclosed as ambiguous, never silently treated as either success or as safe to retry automatically.

## Confirmation-Expiry Policy

- Confirmation expires **30 minutes** (1800 seconds) after it is durably recorded, measured against the store's own wall-clock (`time.time()`) at the moment `record_confirmation` commits — never against the opaque, caller-supplied `confirmation_timestamp` label, which is an audit string only (existing tests already use non-parseable values like `"t1"`) and is never parsed as a real clock value.
- Confirmation also expires if `authorize_invocation` is called with a `session_id` that does not match the record's own `session_id` — mirroring the in-memory `SessionMismatchError` behavior at the durable layer.
- A consumed confirmation never becomes reusable, regardless of expiry — consumption is monotonic and permanent, exactly as the in-memory design has always specified.
- A process restart does not extend expiry — `confirmation_expires_at` is a persisted, absolute wall-clock value, computed once at confirmation time and never recomputed relative to "now" at reload time.
- A missing, `NULL`, or non-numeric `confirmation_expires_at` value fails closed (treated as already expired), never as "no expiry."

**Revisit trigger:** if a future milestone introduces genuinely long-running, multi-step human review workflows where 30 minutes proves too short in practice, revisit this constant — it is a single named constant (`_DEFAULT_CONFIRMATION_TTL_SECONDS`) in the state-store module, not scattered through the codebase.

## Migration Strategy

`schema_meta` holds exactly one row recording `schema_version`. `initialize()` is idempotent: `CREATE TABLE IF NOT EXISTS` for every table, then a version check — if `schema_meta` is empty, insert `schema_version = 1` and `created_at`; if it holds a version equal to this module's `SCHEMA_VERSION`, proceed normally; if it holds a *different* version, raise `SchemaVersionError` and refuse to proceed (fail closed) rather than attempt a silent, un-reviewed migration. No migration logic beyond this initial version exists yet — a future schema change would require an explicit, reviewed migration function that never discards execution evidence, per the task's own stop condition. This milestone ships only `SCHEMA_VERSION = 1`.

## Retention Policy

No automatic deletion or expiry of durable records exists in this milestone. Records persist until an operator explicitly removes the database file (or a future, separately scoped retention tool is designed) — deleting execution history automatically is out of scope and would risk discarding evidence this layer exists to preserve.

## Redaction Rules

Restated from the Durable Record Model above: no raw code, no `stdout`/`stderr` text, no output-file content, no secrets/credentials, no environment-variable values, no raw conversation text are ever written to the database. The read-only inspection tooling (Stage 5) enforces the same exclusions on every code path — there is no "verbose" or "debug" mode that would bypass redaction.

## Corruption Behavior

On any of: a malformed/unopenable database file, an unsupported `schema_version`, a missing required column/table, an inconsistent transition sequence (a gap or duplicate `sequence_number`), more than one `invocation_attempts` row for one instance, or an internally impossible confirmation state (e.g., `confirmation_consumed = 1` with `confirmation_status != 'consumed'`) — the store fails closed: it raises a typed error and refuses to authorize any invocation for the affected record (or refuses to initialize at all, for database-wide corruption). **No automatic repair of execution-critical records is ever attempted.** Read-only inspection tooling may still report *that* a record is corrupt/ambiguous (for operator visibility), but never silently "fixes" it.

## Backup and Recovery Boundaries

This milestone does not implement backup, replication, or automated recovery beyond what SQLite's own crash-resistant commit semantics already provide (a committed transaction survives a process crash; an uncommitted one does not persist). Restoring from a backup, if an operator chooses to keep one, is an out-of-band filesystem operation this module neither performs nor is aware of.

## Storage Location

- **Default:** `<repository_root>/.gauss_orchestration_state/orchestration.db`, created deliberately (the parent directory is created with `Path.mkdir(parents=True, exist_ok=True)` only when a store is actually constructed — never implicitly, never as a side effect of import).
- **Not** inside any user-provided `working_directory` or `output_directory` — those remain exclusively GAUSS execution sandboxes, never mixed with application state.
- **Not** mixed with `evaluations/` files — a completely separate top-level directory.
- **Configurable for tests:** every `OrchestrationStateStore` is constructed with an explicit `db_path`; tests always pass a disposable temporary path and never touch the default location.
- **No hidden fallback location:** if the default directory cannot be created (e.g., permissions), construction raises rather than silently falling back to another path (such as a system temp directory, which could collide across unrelated invocations or leak state outside the repository).
- **Excluded from version control:** `.gitignore` gains one new entry, `.gauss_orchestration_state/`, so generated database files are never accidentally committed.

## Acceptance Criteria

- Atomic invocation authorization: verified by direct test and by the concurrency test matrix (Stage 4) — exactly one of N racing authorization attempts for the same instance succeeds.
- Confirmation expiry: verified for both the not-yet-expired and expired cases.
- Crash simulation: all four crash points behave exactly as specified above, verified without ever actually crashing a real process (they are simulated by controlling exactly which durable operations commit before a test assertion inspects a fresh connection).
- Corruption: every listed corruption case fails closed.
- No raw code, secrets, or output content is ever found in the database file (verified by a static/content-scanning test).
- Read-only inspection tooling never mutates the database.
- 24 evaluation prompts (`37.x`) pass at 4.0.
- All existing adapter/controller tests continue passing unmodified (default in-memory mode is unaffected when no store is supplied).

## Stop Conditions

As specified in the authorizing task, verbatim in effect: helper or result-schema modification appears necessary; durable state would require storing raw GAUSS code; durable state would require storing secrets or credentials; cross-process protection cannot be implemented atomically; invocation authorization cannot be committed before helper launch; the controller could invoke first and persist afterward; corrupt or missing state would need to fail open; schema migration would silently discard execution evidence; recovery would require automatically rerunning GAUSS; a stale confirmation could become valid after restart; a terminal request could be resurrected; script-path execution would need to be enabled; implementation requires network access; workflows/agents/prompts/existing benchmarks must change; any validation procedure would run GAUSS. None of these were encountered — see the implementation report for the specific design choices (conditional atomic `UPDATE`, wall-clock-based expiry independent of restart, fail-closed corruption handling) that kept every one of these conditions from arising.

## Non-Goals, Restated

This milestone does not: connect execution to conversational agents or workflows; modify agents or prompts; enable automatic execution, retry, or rerun; implement distributed workers, multi-host coordination, cloud databases, or network services; implement cooperative GAUSS cancellation; enable script-path execution; read output-file contents; automatically clean up files; claim cross-platform or cross-version support; validate methodology. **No GAUSS is run at any point in this milestone's own work.**
