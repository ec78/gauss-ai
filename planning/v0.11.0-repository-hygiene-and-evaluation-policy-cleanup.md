# v0.11.0 Repository Hygiene and Evaluation Policy Cleanup Plan

## Release Goal

`v0.10.0` closed real evidence and coverage gaps (`glm`, panel estimation, the tracking guard), but in doing so it surfaced several smaller, accumulated pieces of documentation and evaluation-policy drift: a stale claim in an operational profile, two long-standing but never formally policy'd tracking warnings, a benchmark-authoring pattern that goes stale under its own success, a placeholder file that a later, more complete file has already superseded, and a tooling gap that the panel audit only had room to note in passing. None of these block using the system today, but left alone they compound — every future milestone that touches these files inherits the same ambiguity. `v0.11.0` pays this down deliberately, before adding more capability: it fixes the stale wording, gives the two historical tracking warnings an explicit, written disposition instead of leaving them as tribal knowledge, adds guidance so the `17.5`/`17.6` benchmark-staleness pattern doesn't recur, resolves the `knowledge.md` vs. `BODY_OF_KNOWLEDGE.md` redundancy, and documents (or, only if low-risk, fixes) the `official_docs`/`official_package_docs` tooling gap. No new expert, no new routing type, no new command coverage category, and no runtime orchestration — this is a hygiene and policy-clarity milestone.

## Deliverable 3 — Benchmark authoring guidance

Confirmed: no `evaluations/README.md` exists. `workflows/manual-evaluation.md` is the existing, natural home for process guidance (it already has a numbered "Evaluation Steps" section, a "Scoring Guidance" section, and a "Benchmark Traceability" section), and it's already listed as a "Required Input" for every manual evaluation, so guidance placed there is guaranteed to be in scope every time a benchmark is authored or run — unlike a new standalone file, which would need to be remembered and added to that Required Inputs list separately.

Plan:
- Add a new section to `workflows/manual-evaluation.md` (working title: "Benchmark Authoring Guidance" or "Avoiding Volatile Expected-Behavior Text"), stating:
  - Avoid hardcoding volatile repository counts (prompt-ID counts, coverage-row counts, warning counts, run-file counts) in a benchmark's expected-behavior text, unless the benchmark is explicitly and permanently tied to a fixed, frozen repository state (and says so).
  - Prefer "report the live tool output accurately" as the expected behavior over a fixed count, whenever the count can plausibly change before or during the benchmark's own evaluation (for example, because adding the benchmark's own prompts changes the counts it asks about).
  - If an exact count genuinely must be stated (for illustrative or worked-example purposes), record the specific repository state and timing the count was captured at, so a future reader can tell at a glance whether it's still current.
  - During a multi-prompt batch evaluation, distinguish three distinct states when a benchmark's expected behavior depends on tool output: the **baseline** state (before any of the batch's own run files exist), the **mid-batch** state (some run files created but tracking not yet updated — which can add its own transient warnings, as seen with orphaned-run-file warnings during `v0.10.0`'s `17.x` batch), and the **post-tracking-update** state (after coverage/index files are updated). A benchmark that references tool output should say which of these three states it means, if it isn't simply "whatever is true right now."
- Cite the `17.5`/`17.6` finding directly in the new section as the concrete, real precedent this guidance is drawn from (not a hypothetical).
- Cross-reference this new section from `evaluations/benchmark-prompts.md`'s own top-of-file guidance if one exists, so a benchmark author encounters the rule before drafting new expected-behavior text, not only after the fact in `manual-evaluation.md`.

**Status: Done.** Added a new "## 9. Benchmark Authoring Guidance" section to `workflows/manual-evaluation.md` (after its existing "8. Maintenance Notes" section), covering: avoiding volatile hardcoded counts; preferring live tool output for benchmarks that evaluate a script/guard; what to do if exact counts are genuinely required; the three batch-evaluation states (baseline, mid-batch, post-update); the real `17.5`/`17.6` historical precedent, with the actual figures involved (8 warnings at the `17.6` evaluation point, 12 by the `17.5` point, against the benchmark text's originally-written "2 warnings"); and an explicit "do not weaken expectations" clarification that this is narrowly about volatile repository-state counts, not a license for vague benchmarks generally. Added a two-sentence cross-reference pointing to this new section at the top of `evaluations/benchmark-prompts.md`, right after its existing "reference stable Prompt IDs" guidance. No existing benchmark prompt wording was changed — the `17.5`/`17.6` prompts themselves still read as originally written; only new, forward-looking guidance was added for future prompts.

## Deliverable 5 — Source-type/tooling gap investigation

Confirmed directly (see Current State): the schema already defines `official_package_docs` (`source_authority`) and `official_package_rst` (`source_type`); `scripts/command_doc_lookup.py`'s `map_match_to_schema` (~line 508) never assigns either — it hardcodes `official_docs`/`official_local_rst` for every local `.rst` match regardless of the file's path.

Plan:
- Document the finding precisely (this is already partially done in `KNOWN_LIMITATIONS.md` and the `v0.10.0` panel-estimation audit; consolidate/cross-reference rather than duplicate).
- Evaluate whether a concrete, low-risk fix is available: a small path-based check (e.g., does `file_path` contain a known package-directory segment such as `tsmt/`, `tspdlib/`, `bhatlib/`?) that sets `source_type: official_package_rst` / `source_authority: official_package_docs` instead of the core-docs values when true. This is additive (new classification for a previously-mislabeled case) and does not change any currently-correct classification for core-docs matches, which makes it a plausible low-risk candidate — but implement only if, on inspection, the set of package directories can be enumerated reliably from the local docs layout without guessing at directories that don't actually indicate a separately-licensed package (not every non-`cc/` directory necessarily means "separately licensed"; this needs confirming, not assuming, before writing the check).

- Either way: no schema change. The schema already supports the distinction; this is purely a `command_doc_lookup.py` extraction-logic question.

## Risks and Design Questions

- **Should historical files be repaired or preserved as history?** Preserved, per Deliverable 2's recommendation — rewriting `run-001.md`'s own `Prompt ID:` field would erase what was actually evaluated at the time, which is a worse outcome than a documented, cross-referenced mismatch.
- **Should tracking exceptions live in code, docs, or a small config file?** Recommend docs (extending `benchmark-coverage.md`'s existing section), not a new config file, given only two known exceptions exist and neither is expected to need programmatic lookup beyond what `check_evaluation_tracking.py` already does (surface the mismatch as a warning). Revisit only if a third or fourth exception appears and a pattern emerges.
- **Should benchmark guidance live in `benchmark-prompts.md` or a separate authoring guide?** Recommend `workflows/manual-evaluation.md` as the primary location (already a required input for every evaluation), with an optional short cross-reference at the top of `benchmark-prompts.md` — not a wholly new `evaluations/benchmark-authoring-guidelines.md` file, to avoid adding another document to the required-reading set for a single guidance section.
- **Is `knowledge.md` safe to remove?** Not fully — nothing references it by path today, but removing an expert-directory file outright is a slightly higher-risk, harder-to-reverse action than replacing its content with a stub. Recommend the stub approach (Deliverable 4) over deletion.
- **Is `official_package_docs` a schema issue, a tooling issue, or just documentation?** Confirmed a tooling issue: the schema already fully supports the distinction (both enum values exist); `command_doc_lookup.py`'s extraction logic just doesn't populate them. This should simplify Deliverable 5 to either "implement the tooling check" or "document why not yet," never "change the schema."
- **How much cleanup is enough for `v0.11.0`?** Scoped to exactly the five deliverables above, each tied to a specific `v0.10.0`-surfaced finding — this milestone does not attempt a general repository-wide documentation sweep beyond what those five findings require.
- **Does fixing `experts/econometrics/OPERATIONAL_PROFILE.md` risk also needing to touch `experts/gauss-language/OPERATIONAL_PROFILE.md`?** No stale multi-expert-routing wording was found there during the `v0.10.0` audit (confirmed by grep at the time); this milestone's Deliverable 1 is scoped to the econometrics file only, consistent with that finding.
- **New follow-up found while completing Deliverable 1:** `workflows/expert-routing.md`'s own "Maintenance Notes" section still describes benchmark category `16.x` as a *future* category to add ("Future benchmark category `16.x` should test GAUSS-only, econometrics-only, both-experts, and neither-expert routing..."), which is itself stale now that `16.x` was completed and evaluated in `v0.9.0`. This is a real staleness issue in a file this milestone's Deliverable 1 explicitly did not modify (per its own scope and Task 6-equivalent constraints at the time). Not fixed in this pass; recommend a small follow-up task scoped specifically to updating that one section of `workflows/expert-routing.md`.
