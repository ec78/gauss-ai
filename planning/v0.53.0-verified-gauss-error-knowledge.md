# v0.53.0 - Verified GAUSS Error Knowledge

## Release Goal

Expand the interpreter's verified GAUSS execution knowledge using only trustworthy evidence — real GAUSS runtime reproduction, evidence already present in this repository, or official GAUSS/Aptech documentation. The emphasis is verified knowledge, not more code: no new execution paths, no assisted debugging, no code repair.

## Research Method

Before writing any code, every `error G####` string that actually appears anywhere in this repository's real execution evidence (planning docs, evaluation runs, test fixtures) was traced with a repository-wide search. This found exactly four genuine real-runtime-observed codes: `G0105`, `G0036`, `G0025` (already cataloged as of `v0.51.0`) and `G0014` ("File not found", observed as a side effect of an unrelated `-e`-flag argument-parsing experiment in `planning/v0.28.0-real-gauss-invocation-research.md`, never previously cataloged). `G9999` also appears throughout the repository but is explicitly a synthetic test fixture, never real evidence, and must never become a catalog entry.

Official Aptech documentation was then fetched directly (not recalled from training data) for each of these codes, plus a search for additional well-documented codes in currently-empty catalog categories. This found:

- `G0105`, `G0025`, `G0014`: official documentation title and general cause description match this repository's own real-runtime observations closely.
- `G0036`: official documentation titles this error "Matrices are not conformable," while this repository's own real runtime evidence consistently shows "Matrix dimensions are incompatible" — a genuine wording disagreement, recorded rather than silently resolved (see below).
- `G0290` ("Library not found"): a well-documented Aptech error code for the previously-empty Package or Library category, with no runtime reproduction attempted or needed — official documentation alone is an explicitly accepted verification basis.

No other codes were added. In particular, no code was invented for Numerical, Startup/Licensing (GAUSS License Manager errors exist but without a confirmed `G####` code comparable to the entries above), User Interruption, or Timeout (which is not a GAUSS error code at all, only an interpreter-level classification) — these categories remain defined in `GaussErrorCategory` but deliberately empty, documented as future placeholders in `docs/gauss-error-catalog.md` rather than padded with speculation.

## Catalog Architecture

`GaussErrorCatalogEntry` (`scripts/gauss_error_catalog.py`) gained three fields:

- `verification_status: tuple[VerificationStatus, ...]` — one or more of `REAL_RUNTIME`, `OFFICIAL_DOCUMENTATION`, `REPOSITORY_EVIDENCE`, `UNKNOWN`. Never empty for a real entry; `_build_catalog(...)` raises if it is.
- `verification_source: str` — a human-readable citation (which planning/evaluation document, real invocation, or documentation content this entry's wording is grounded in).
- `documentation_discrepancy: str | None` — set only when official documentation and observed runtime evidence disagree; `None` otherwise.

The catalog's construction changed from a plain dict literal to `_build_catalog(entries: tuple[GaussErrorCatalogEntry, ...])`, which raises `ValueError` on a duplicate `error_code` instead of a plain dict literal's silent last-write-wins behavior — a real, if narrow, correctness risk for a catalog that's expected to keep growing.

## Interpreter Changes

`gauss_execution_interpreter.py` gained no new hardcoded GAUSS knowledge (a dedicated structural test, `test_20_no_hardcoded_error_knowledge_outside_catalog`, asserts none of the catalog's own error-code strings appear literally in the interpreter's source). Two changes:

1. `ExecutionInterpretation` gained `verification_status`, `verification_source`, and `documentation_discrepancy` fields, populated directly from the matched catalog entry (empty/`None` when no cataloged entry matches, including for the `unknown`-code path).
2. The timeout branch now distinguishes an observed real-launch timeout (`gauss_ran: True`) from simulated/injected timeout evidence (`gauss_ran: False`) in both `launch_status` (now consistently `fake_or_non_gauss_runner` for the simulated case, matching every other non-real-evidence branch, instead of the previous `launch_unknown`) and in `user_explanation`/`technical_explanation` wording, which are now structurally different strings for the two cases rather than one shared template.

## Timeout Wording Fix (resolves the `v0.52.0` Minor finding)

`evaluations/runs/2026-07-30-code-assistant-execution-interpretation-run-004.md` (43.4) recorded: "`launch_status` reports `launch_unknown` for injected fake-timeout evidence, rather than the more specific `fake_or_non_gauss_runner` label the completed/failed branches use." Fixed exactly as scoped — no other interpreter branch was touched. Re-evaluated as `44.9`.

## Documentation

`docs/gauss-error-catalog.md` — a human-readable companion to the code, explicit that the module is the source of truth if the two ever disagree. Documents all five verified entries with their verification basis, and a "Future Placeholders" section naming every currently-empty category and why it's empty, so a reader can never mistake "this category exists in the enum" for "this repository has verified something here."

## Benchmarks

`44.x` Verified Error Knowledge, 10 prompts (`evaluations/benchmark-prompts.md`), evaluated 10/10 Pass at 4.0, 0 Critical/Major/Minor. No new real GAUSS invocation was performed — every evaluation is grounded in direct execution of the actual catalog/interpreter code plus the documentation fetches performed during authoring, consistent with "run real GAUSS only when required to verify a newly added catalog entry" (neither new entry required one: `G0014` already had real evidence, `G0290` is documentation-only by design).

## Out of Scope (unchanged)

Assisted debugging, code repair, durable execution sessions, autonomous retry, LLM reasoning inside interpreter components, broad architecture redesign. None implemented.

## Readiness Classification

Ready for continued structured alpha testing of interpretation, now with a broader and more transparently-sourced error catalog. Not ready for assisted debugging, code repair, or durable sessions — unchanged, explicitly out of scope.

**Recommended next milestone:** this evaluation found zero unresolved defects at any severity. Given the project's stated staged progression (Execution → Interpretation → Knowledge → Diagnosis → Repair), the next natural step is bounded diagnosis reasoning that consumes the now-richer catalog/verification metadata to help a user narrow down a failure (e.g., ranking likely causes among a cataloged error's known triggers) — still strictly short of proposing or applying a code repair, which remains a distinct, later-staged milestone.
