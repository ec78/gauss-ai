# v0.37.0 Conversational Execution Workflow Integration — Planning

## Scope

`v0.37.0` connects the GAUSS Code Assistant's user-facing real-execution workflow to the durable runtime orchestration controller established through `v0.31.0`-`v0.36.0`. It introduces one new module, `scripts/gauss_execution_workflow.py`, that sits strictly between conversational interaction and the controller: it classifies interaction mode, collects and validates execution inputs, builds a canonical request through the existing controller primitives, presents an exact plan, validates an explicit confirmation event against `request_hash`, invokes the durable controller (never the adapter or helper directly), and turns the result into safe, response-ready evidence. It narrowly updates `workflows/real-execution-user-workflow.md`, `workflows/code-assistant-response.md`, and `agents/code-assistant/AGENT.md` to reference this new boundary — the first milestone permitted to touch those files since the real-execution foundation began at `v0.30.0`.

**In scope:** the conversational execution-workflow module and its tests; a narrow, additive reference from the three workflow/agent documents to the new boundary; a bounded set of real, end-to-end verification invocations (up to 3) run through the full user-facing-workflow → controller → adapter → helper path; a new evaluation category (`38.x`); documentation and readiness review.

**Out of scope (explicit non-goals):** automatic execution based on code presence alone; execution during review/explanation; implicit confirmation; cross-session confirmation reuse; automatic retry/rerun; script-path execution; arbitrary command execution; network access; credentials/secrets; output-file content reading; automatic cleanup of user-owned files; distributed/multi-machine orchestration; cooperative GAUSS cancellation; cross-platform/cross-version support claims; methodological-validity claims from execution alone; unrelated agent redesign; general-purpose tool autonomy; helper or result-schema changes.

## User Interaction States

The workflow module tracks interaction mode independently of the controller's 13-state machine (`OrchestrationState`). Interaction mode answers "what kind of conversational turn is this?"; orchestration state answers "where is this specific confirmed request in its lifecycle?" The two are related but not identical — e.g. a user can be in `INSPECT_PRIOR_RESULT` mode while the underlying orchestration instance is in any terminal state, and `REVIEW_CODE`/`EXPLAIN_CODE`/`REVISE_CODE` never create an orchestration instance at all.

## Supported Request Modes

`InteractionMode` (typed enum, `scripts/gauss_execution_workflow.py`):

- `ADVISORY` — no code-execution-adjacent request; general help.
- `EXPLAIN_CODE` — explanation only; never executes.
- `REVIEW_CODE` — review only; never executes.
- `REVISE_CODE` — revision/refactor only; never executes.
- `PREPARE_EXECUTION_PLAN` — execution appears eligible; plan display, not yet execution.
- `EXECUTE_AFTER_CONFIRMATION` — the only mode that may reach real execution, and only after a validated confirmation event.
- `CANCEL_PENDING_EXECUTION` — cancels a proposed/awaiting/confirmed/executing instance.
- `INSPECT_PRIOR_RESULT` — reads back a durable record; never mutates orchestration state.
- `REQUEST_RERUN` — always refused with a structured explanation that a fresh request/confirmation cycle is required; this module performs no rerun itself.

## Intent-Classification Contract

`classify_interaction_mode(signal: IntentSignal) -> InteractionMode` is a pure function taking only explicit, structured booleans/enums — never natural-language text. It never trusts an agent-supplied `requested_mode_hint` as authoritative; it re-derives the mode from the structured facts every time. Precedence, evaluated in order (first match wins):

1. `cancellation_requested=True` → `CANCEL_PENDING_EXECUTION`.
2. `rerun_requested=True` → `REQUEST_RERUN`.
3. `inspect_instance_id is not None` → `INSPECT_PRIOR_RESULT`.
4. `confirmation_event is not None` → `EXECUTE_AFTER_CONFIRMATION` (still independently validated by `confirm_execution(...)`/`execute(...)` — classification alone never authorizes anything).
5. `execution_explicitly_requested=True and code_present=True` → `PREPARE_EXECUTION_PLAN`.
6. `requested_mode_hint in (REVIEW_CODE, EXPLAIN_CODE, REVISE_CODE)` → that hint, passed through (these never execute regardless).
7. Anything else, including `execution_explicitly_requested=True and code_present=False` (execution words with no code), `requested_mode_hint=PREPARE_EXECUTION_PLAN` with `execution_explicitly_requested=False` (code presence alone), and every genuinely ambiguous combination → `ADVISORY`.

This makes the fail-closed rule explicit and testable: **only rule 5's exact conjunction reaches plan preparation, and only rule 4 (independently re-validated) can reach execution.** Phrases like "try this" or "check this" never set `execution_explicitly_requested` themselves — that flag must come from the agent's own explicit, separate classification of the user's words as an execution request, matching `workflows/real-execution-user-workflow.md`'s Execution Eligibility Decision ("user explicitly asks to run/test/execute/smoke-test"); this module does not parse text and treats the flag as a claim it still gates behind the eligibility/safety/plan/confirmation pipeline below, never as sufficient on its own.

## Input-Collection Contract

`collect_missing_inputs(...)` returns the tuple of missing/invalid field names given a draft, checked structurally (not a rule engine): code XOR script_path present-and-non-empty, `working_directory` present, `executable_path` present, `timeout_seconds` a positive number, `environment_summary` present. Any missing item routes the interaction to `PREPARE_EXECUTION_PLAN` with a `MissingInputs` result rather than to `ADVISORY` or execution — matching Response Pattern C (`workflows/real-execution-user-workflow.md`).

## Eligibility Decision

`evaluate_eligibility(EligibilityInput) -> EligibilityOutcome` structurally encodes `workflows/real-execution-user-workflow.md`'s Execution Eligibility Decision checklist (script-path rejected, code present, working directory present, executable is the terminal `tgauss`/`tgauss.exe`, no package install/license activation/network access/global-config mutation/writes-outside-working-directory declared, timeout set). It consumes explicit boolean inputs the caller (the agent, informed by the conversation) supplies — it does not infer any of them from free text, and a caller that cannot supply an input honestly must supply the conservative (ineligible) value. This is a direct, non-inventive structural checklist, not a new rule engine — it adds no criteria beyond what the workflow document already specifies.

## Safety-Review Representation

Reuses `gauss_runtime_orchestration.SafetyReviewOutcome`/`SafetyReviewItem` directly rather than defining a parallel type. `evaluate_safety_review(SafetyReviewInput) -> SafetyReviewOutcome` maps the 14-item Pre-Execution Safety Review checklist from the same workflow document onto the same structural-input pattern as eligibility. Both outcomes are attached to the `RequestDraft` before it reaches `build_canonical_request(...)` (via `MockOrchestrationInstance.submit_for_review()`), so a failure in either produces the controller's own existing `BLOCKED` state and `FailureCategory` (`INELIGIBLE_REQUEST`/`UNSAFE_REQUEST`/`SCRIPT_IDENTITY_UNTRUSTED`/`MISSING_INPUTS`) — this module adds no new failure taxonomy.

## Plan-Display Contract

`ExecutionProposal` is the response-ready projection of a `PROPOSED`/`AWAITING_CONFIRMATION` orchestration instance: `orchestration_instance_id`, `request_id`, `request_hash`, `execution_purpose`, `code_digest` (never raw code), `working_directory`, `output_directory`, `executable_path`, `timeout_seconds`, `expected_input_files`, `expected_output_files`, `required_packages`, `environment_summary`, `eligibility_passed`, `safety_review` (outcome + items), `known_limitations` (a fixed tuple of the same limitation strings `workflows/real-execution-user-workflow.md`'s Evidence and Trust Boundaries section already states — `exit_code` unreliable, `output_files` is metadata not content, completion does not prove methodology, etc.), and `plan_digest` (== `request_hash`; confirmation must be bound to this exact value). A proposal is only ever produced by `propose_execution(...)`, which drives `submit_for_review()` then `display_plan()` on a durable-store-backed instance — there is no path that skips straight to confirmation.

## Confirmation-Event Contract

`WorkflowConfirmationEvent`: `session_id`, `orchestration_instance_id`, `request_id`, `request_hash`, `decision` (`"accepted"` or `"rejected"`), `timestamp`, `source_interaction_id`, `plan_digest`. `confirm_execution(event)` independently validates, before ever touching the controller: `plan_digest == request_hash` (else `ConfirmationValidationError` — an altered/rebuilt plan can never reuse a stale digest), `decision` is one of the two literal values, and the instance is currently known to this workflow (loaded from the durable store if not cached in-process). `decision="accepted"` is translated into the controller's own `ConfirmationEvent(scope=request_hash, timestamp=..., session_id=...)` and passed to `MockOrchestrationInstance.confirm(...)`, which performs the authoritative `request_hash`/session/durable checks this module does not duplicate. `decision="rejected"` calls `reject_confirmation()`. **`confirmed=True` alone is never accepted as a parameter anywhere in this module** — only a full `WorkflowConfirmationEvent` with a `request_hash`-bound `plan_digest`.

## Durable-State Relationship

Every orchestration instance this module creates is constructed via `gauss_runtime_orchestration.build_durable_orchestration_instance(...)` — never the bare `MockOrchestrationInstance(...)` constructor — so every workflow-driven request is durable from creation. `ExecutionWorkflow` keeps a process-local `dict[orchestration_instance_id, MockOrchestrationInstance]` purely as a same-process convenience cache; it is never the source of truth. `inspect(...)` and `confirm_execution(...)`/`execute(...)` transparently fall back to `gauss_runtime_orchestration.reload_orchestration_instance(...)` when an instance is not in the local cache (a new process, or a restarted one), so cross-process/restart behavior verified in `v0.36.0` is inherited, not reimplemented.

## Execution-Result Presentation

`ResponseReadyResult`: `executed`, `orchestration_instance_id`, `final_orchestration_state`, `helper_invocation_status`, `execution_status`, `exit_code` (always paired with a `exit_code_is_authoritative=False` disclosure), `runtime_error_detected`, `timed_out`, `missing_expected_output`, `output_files` (tuple of path/size/type/created-by only — no content field exists on the type, so content cannot be carried even by accident, mirroring `OutputFileMeta`), `analysis_status`, `report_status`, `limitations` (tuple of strings, always non-empty when `executed=True`), `methodology_caveat` (a fixed string, always present), `rerun_requires_new_request=True` (constant — this module never offers an in-place rerun path). Built by `_to_response_ready_result(instance)`, reading only `instance.record`/`instance.record.execution_result_reference` — never guessing or fabricating fields absent from the record.

## Cancellation Behavior

`cancel(orchestration_instance_id, note="") -> ResponseReadyResult` delegates entirely to `MockOrchestrationInstance.cancel(...)`, which already distinguishes pre-invocation cancellation (clean `CANCELLED` transition), during-execution cancellation (records intent only — the synchronous fake/adapter call cannot actually be interrupted, an existing, honestly-disclosed limitation this module does not attempt to fix), and post-execution cancellation (skips analysis, force-completes). This module adds no new cancellation semantics.

## Rerun Behavior

`request_rerun(orchestration_instance_id)` always raises `RerunRequiresNewRequestError` with a message identifying the prior `orchestration_instance_id`/`request_hash` for reference. There is no code path in this module that reuses a prior confirmation, prior request identity, or prior durable record to perform a second invocation — a rerun is, structurally, nothing but a fresh call to `propose_execution(...)` with a new `request_id`.

## Session Behavior

`session_id` is accepted as an opaque, caller-supplied string, exactly as the controller already does — this module introduces no new session-identity mechanism. `invalidate_for_session_boundary()` is exposed pass-through for a caller (the higher-level conversational harness) that detects a session boundary and wants to invalidate a specific instance's pending confirmation, per the controller's own existing Section 11 behavior.

## Interaction Identity

Association between a conversation/session, an orchestration instance, a canonical request, a confirmation event, an execution result, follow-up analysis, and a rerun request is entirely keyed by the durable `orchestration_instance_id` (created once, per `propose_execution(...)` call) plus, within it, `request_hash` for confirmation binding. Conversational turn position is never treated as identity: a `WorkflowConfirmationEvent` must name its `orchestration_instance_id`/`request_hash` explicitly, and a rerun always mints a new instance rather than reusing the old one's identity.

## Failure Disclosures

Every failure path (blocked eligibility/safety, stale/rejected/expired/session-mismatched confirmation, duplicate invocation, environment mismatch, runtime error, timeout, missing output, malformed result, durable authorization failure, corrupt/ambiguous durable state) is surfaced through `ResponseReadyResult`/a typed exception — never silently downgraded to a generic error, and never retried automatically by this module.

## Acceptance Criteria

- Advisory/explain/review/revise never create an orchestration instance or reach execution.
- Code presence alone, or an unconfirmed "try this," never executes.
- A changed plan (code, output files, timeout, etc.) always changes `request_hash`, which always invalidates a `plan_digest` computed before the change.
- Confirmation is always bound to `request_hash`, always durable, always consumed at most once, always session-scoped, and always fails closed on staleness/expiry/mismatch.
- The controller (`build_durable_orchestration_instance`/`MockOrchestrationInstance.invoke`) is the only path this module ever uses to reach execution; the adapter and helper are never imported or called directly by this module.
- A rerun always requires a brand-new `propose_execution(...)` call.
- All ordinary tests run against fake runners/hooks; no test in the default suite runs GAUSS.

## Explicit Non-Goals

Restated from the authorizing task: automatic execution from code presence; execution during review/explanation; implicit confirmation; cross-session confirmation reuse; automatic retry/rerun; script-path execution; arbitrary command execution; network access; credentials/secrets; output-file content reading; automatic cleanup of user-owned files; distributed/multi-machine orchestration; cooperative GAUSS cancellation; cross-platform/cross-version claims; methodology validation from execution; unrelated agent redesign; general-purpose tool autonomy; helper/result-schema changes.

## Stop Conditions

As specified in the authorizing task, verbatim in effect: user-facing integration bypassing the durable controller; execution intent indistinguishable from review/explanation; confirmation existing only in conversational memory; execution without an exact displayed plan; confirmation scope not tied to `request_hash`; durable authorization transaction bypassed; agent/workflow instructions permitting automatic execution; stale/cross-session confirmation reuse; helper or result-schema modification appearing necessary; script-path execution being enabled; output-file content reading; arbitrary commands/network/credentials/secrets becoming necessary; production behavior silently falling back to the mock controller; tests needing to run GAUSS by default; the bounded real-execution budget being exceeded; execution behavior failing to fail closed on ambiguous intent/state. None were encountered — see the implementation report for the specific design choices that kept every one of these from arising.
