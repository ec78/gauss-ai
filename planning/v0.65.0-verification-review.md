# v0.65.0 — Verification Review and Outcome Recording

## Position in the reasoning pipeline

```
... -> Repair Application Transaction (gauss_repair_application.py, v0.62.0)
    -> Verification Execution (gauss_verification_execution.py, v0.64.0)
    -> Verification Review (this module, v0.65.0)
    -> (future, not implemented: anything that reads a review's own decision)
```

## Objective

A human review layer over Verification Execution. The review records what a
human concluded after inspecting the evidence a completed verification
execution produced. It must never infer that conclusion automatically —
there is no code path anywhere in `gauss_verification_review.py` capable of
computing `decision` from `ComparisonSummary`'s own fields. `decision` is
always a caller-supplied value, exactly as `recorded_at`/`reviewed_by`/
`notes` are.

## What this module is not

It is not automatic repair validation, automatic repair acceptance,
automatic rollback, automatic planning, or a scoring/ranking system. It does
not call `gauss_repair_application.py`, does not call
`gauss_verification_execution.py`'s own `propose_verification_execution`/
`compare_execution_outcomes` (the caller supplies an already-computed
`ComparisonSummary`; this module never computes one), does not mutate any
approval store, does not mutate `RepairDraft`/`RepairPlan` state, and never
triggers execution, planning, or repair of any kind.

## Dependency direction

`gauss_verification_execution.py` and `gauss_repair_application.py` both
have **zero diff** from this milestone. `gauss_verification_review.py`
imports `gauss_verification_execution` (for the `ComparisonSummary` type,
used only in an `isinstance` check and to compute a content digest over its
fields) — never the reverse. This preserves the same one-way layering this
repository has used at every prior approval boundary: a layer may depend on
the thing it reviews/approves, but the reviewed/approved thing never knows
the reviewing layer exists.

## Model

```python
@dataclass(frozen=True)
class VerificationReview:
    review_id: str
    verification_execution_id: str
    comparison_summary_digest: str
    decision: str                 # one of ReviewDecision's values
    notes: str
    reviewed_at: str
    reviewed_by: str
    boundary: str                 # the fixed VERIFICATION_REVIEW_BOUNDARY string
```

`VerificationReview` deliberately holds **no** field capable of referencing
a `RepairDraft`, `RepairPlan`, `ApplicationResult`, `VerificationExecutionRequest`,
or `ComparisonSummary` object directly — only two opaque strings
(`verification_execution_id`, `comparison_summary_digest`). This is what
makes "the review references only a completed Verification Execution"
structurally true rather than merely conventionally true: there is nowhere
on the type for an in-progress or unverified reference to live.

### `comparison_summary_digest`

No digest function for `ComparisonSummary` exists yet anywhere in the
repository (it was not needed by v0.64.0, since the CLI recomputes the
summary on demand rather than storing or referencing it by identity). This
module adds `comparison_summary_digest(summary) -> str`, hashing all five of
`ComparisonSummary`'s own fields (`original_outcome`, `verification_outcome`,
`same_outcome`, `comparison`, `observation`) via the repository's standard
canonical-JSON/SHA-256 pattern (`hashlib.sha256(json.dumps(canonical,
sort_keys=True).encode()).hexdigest()`), matching
`gauss_repair_draft.repair_draft_digest`'s own convention. Unlike
`repair_draft_digest`, there is no instance-identity field to exclude —
`ComparisonSummary` has none.

### Decision values

```python
class ReviewDecision(enum.Enum):
    ACCEPTED = "accepted"
    REJECTED = "rejected"
    INCONCLUSIVE = "inconclusive"
```

Exposed as three explicit `VerificationReviewStore` methods —
`accept(...)`, `reject(...)`, `mark_inconclusive(...)` — rather than one
generic `record(decision: str, ...)` entry point. This mirrors
`ApplicationApprovalStore.approve(...)`/`.decline(...)`, and additionally
makes an invalid decision value a **type-level impossibility** at the
module's own API surface (the CLI is the only place a string decision value
from a human is parsed and validated, exactly as it already validates
`--fake-success`/`--fake-failure`/etc. for `verify-repair`).

### No revoke

Unlike `RepairApprovalStore` (`v0.57.0`), `DraftApprovalStore` (`v0.60.0`),
and `ApplicationApprovalStore` (`v0.61.0`) — all of which support revoking
an active decision in place — `VerificationReviewStore` supports **no**
revoke operation. This is a deliberate scope decision, not an oversight:
this milestone's task specification lists exactly three decision values
(`accepted`/`rejected`/`inconclusive`), never `revoked`, and the Rules
section never mentions revocation. A `VerificationReview` is therefore
write-once per `verification_execution_id`: attempting a second review for
the same ID raises `DuplicateVerificationReviewError` unconditionally, with
no way to clear it from within this module. If a future milestone needs
revocable reviews, that is new capability requiring its own authorization —
exactly the same posture this repository took toward rerun/rollback in
`v0.62.0`/`v0.63.0`/`v0.64.0`.

### Boundary statement

A single, fixed, decision-invariant string — never reworded per decision,
matching every other layer's fixed-boundary convention:

```
VERIFICATION_REVIEW_BOUNDARY = (
    "This review records a human conclusion about the verification evidence. "
    "The system is not determining whether the repair is correct. No execution, "
    "planning, repair, rollback, or approval mutation has occurred as a result "
    "of this review."
)
```

This directly satisfies the task's own required CLI disclosure text
("This review records a human conclusion." / "The system is not determining
whether the repair is correct.") by construction — the CLI never rewords
this string, it only prints it.

## Errors

```python
class InvalidVerificationReferenceError(Exception): ...
class ComparisonNotAvailableError(Exception): ...
class DuplicateVerificationReviewError(Exception): ...
```

- `InvalidVerificationReferenceError` — raised for an empty/non-string
  `verification_execution_id`.
- `ComparisonNotAvailableError` — raised when `comparison_summary` is not a
  genuine `ComparisonSummary` instance (structurally, this is how "only a
  *completed* Verification Execution can be reviewed" is enforced: a
  verification that has not finished executing has no `ComparisonSummary`
  to pass in at all).
- `DuplicateVerificationReviewError` — raised when a review already exists
  for the supplied `verification_execution_id`.

## `VerificationReviewStore`

In-memory only, process-local, not thread-safe, never persisted — the same
discipline `ApplicationApprovalStore` and its predecessors already
established. One record per `verification_execution_id`; `get_review(...)`
looks it up directly (no digest-based staleness check is needed or
possible, since there is no mutable draft/plan being reviewed — only a
fixed evidence digest).

## CLI

Two new commands, `review-verification` and `show-verification-review`,
wired the same way `apply-repair`/`show-application-result` were. A new
`self._verification_review_store` field is added to `__init__` and cleared
in `_reset()`, alongside the three existing approval stores.

`review-verification --decision {accepted|rejected|inconclusive} [--notes TEXT] [--reviewed-by NAME]`
requires `self.last_verification_request` to exist and the comparison to
already be available (mirrors the exact same `verification_executed` check
`_show_verification_request` already performs) — reviewing an incomplete
verification is refused with a clear error, never silently accepted or
inferred.

The existing inline comparison-computation logic inside
`_show_verification_request` is factored into a small private helper,
`_current_comparison_summary()`, reused by both commands. This is a pure
refactor — `_show_verification_request`'s own behavior and output are
unchanged; regression tests 124–133 must still pass unmodified.

## Testing dimensions

accepted / rejected / inconclusive decisions; duplicate review handling
(second review for the same `verification_execution_id` raises); invalid
verification reference (empty ID, and a verification that has not yet
produced a `ComparisonSummary`); immutability (frozen dataclass, plus a
`hasattr`-based structural check that `VerificationReview` carries no
mutable/verdict-inferring field); CLI (`review-verification`,
`show-verification-review`, before/after states, disclosure text);
regression (full existing suite, especially `gauss_verification_execution.py`,
`gauss_repair_application.py`, and all four approval-layer modules, all with
zero diff from this milestone).

## Not implemented

No revoke. No automatic decision inference. No execution, planning, repair,
or rollback triggered by a review. No mutation of any approval store or of
`RepairDraft`/`RepairPlan`/`ApplicationResult`/`VerificationExecutionRequest`
state. No durable/cross-process storage. No consumer of a recorded review's
decision (that is future, unauthorized work).
