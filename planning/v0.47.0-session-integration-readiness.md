# v0.47.0 Session Integration Readiness — Planning

**This document is planning only. No durable session integration is implemented by `v0.46.0` or by this document.**

## Purpose

`v0.45.0`'s `WorkflowResult.execution_session_reference` currently means `orchestration_instance_id` — a real, stable, traceable identifier, but not a `gauss_execution_session.ExecutionSession` object. `gauss_execution_session.py` (implemented in `v0.40.0`, realizing `v0.39.0`'s design) has never been wired into `gauss_execution_workflow.py` or `gauss_code_assistant_workflow.py`. This document assesses what closing that gap would require, and recommends a narrowly bounded `v0.47.0` scope — it does not close the gap itself.

## Evaluation Evidence Motivating This Document

`v0.46.0`'s evaluation of `40.8` (Provenance reporting) confirmed the current identifier is genuinely stable, traceable, and internally consistent (`WorkflowResult.execution_session_reference == WorkspaceProvenance.execution_session_id` exactly) — the naming gap causes **no observable defect** in any of the 20 evaluated scenarios. `v0.46.0`'s own verification harness additionally surfaced a real, previously-undocumented architectural fact directly relevant to this document's "can a session contain multiple execution instances?" question (see below): **a workspace's own lifecycle supports exactly one execution attempt.** Once a workspace reaches `completed`, `WorkspaceRegistry.update_workspace_status(..., to_status=EXECUTING)` correctly raises `InvalidWorkspaceTransitionError` on any second attempt — verified directly by re-executing against an already-`completed` workspace during evaluation. This is correct, existing, working behavior (not a defect), but it means today's answer to "can one workspace host multiple sequential executions" is **no** — each new execution needs its own fresh, `ready` workspace.

## Current State (What Exists Today)

- **Execution Request** — `gauss_runtime_orchestration.CanonicalExecutionRequest`, an 18-field, hash-bound, frozen record. Fully implemented, unchanged since `v0.31.0`.
- **Execution Session** — `gauss_execution_session.ExecutionSession` (`v0.40.0`): a six-state (`created`/`awaiting_confirmation`/`confirmed`/`ready`/`expired`/`cancelled`), in-memory-only value type with `create_session`/`confirm_session`/`validate_session`/`expire_session`/`cancel_session`/`invalidate_session`/`get_session_state`. **Fully implemented but never wired to anything else in this codebase.**
- **Execution Instance** — conceptually, `gauss_runtime_orchestration.py`'s own `helper_invocation_id` plays this role today; `gauss_execution_session.ExecutionInstance` is a parallel, also-unwired type from `v0.40.0`.
- **Execution Workflow** — `gauss_execution_workflow.ExecutionWorkflow`, the actual, live, wired orchestration layer, built directly on `gauss_runtime_orchestration.MockOrchestrationInstance` (not on `gauss_execution_session.ExecutionSession`).
- **Workspace identity** — `gauss_workspace.WorkspaceRegistry`/`Workspace`, wired into `ExecutionWorkflow` since `v0.43.0`.
- **Analysis lifecycle** — `MockOrchestrationInstance.begin_analysis(...)`/`AnalysisStatus` exist and are fully implemented at the controller layer, but `ExecutionWorkflow` never calls `begin_analysis(...)` — so `analysis_status` is always `"not_started"` by the time it reaches `WorkflowResult`, honestly, not fabricated.

**In short: two independent, non-overlapping session-shaped abstractions exist today** (`gauss_execution_session.ExecutionSession`, unused, and `MockOrchestrationInstance`'s own record, actually used) — and the desired architecture requires reconciling them, not building a third one.

## Key Questions

### Who creates the `ExecutionSession`?

Recommendation: `ExecutionWorkflow.propose_execution(...)` should create it internally, immediately after building the `CanonicalExecutionRequest` and before (or atomically with) `build_durable_orchestration_instance(...)` — mirroring how workspace validation was integrated in `v0.43.0` (a narrow, internal step inside an existing method, not a new public entry point the caller must remember to call separately). The MVP facade (`gauss_code_assistant_workflow.py`) should **not** create the session directly — it should remain a thin caller of `ExecutionWorkflow`, exactly as `v0.45.0`'s own design principle requires ("orchestrates; does not reimplement").

### Should the MVP facade create a session or receive one?

**Receive one** — via whatever `ExecutionWorkflow.propose_execution(...)` returns. The facade's `MvpWorkflowSession` (a `v0.45.0` reporting-only construct, not a durable session) would then hold a reference to the real `ExecutionSession`'s identifier, the same pattern it already uses for `orchestration_instance_id`.

### How is `workspace_id` bound to the session?

Recommendation: as a field on `ExecutionSession` itself (an additive field, matching `v0.39.0`'s own dataclass style), set once at session creation and never mutated — mirroring `ExecutionProposal.workspace_id`'s existing "reference, never duplicated state" pattern from `v0.43.0`.

### How is confirmation bound to the exact request hash?

Unchanged: `ExecutionSession.confirm_session(...)` already requires `confirmation_scope == request_hash == plan_digest` (per `v0.39.0`'s design, implemented in `v0.40.0`). Integration would mean `ExecutionWorkflow.confirm_execution(...)` calls `confirm_session(...)` in addition to (or instead of, if fully migrated) its current direct call into `MockOrchestrationInstance.confirm(...)`. **The two must never disagree** — a design that let the session's own confirmation state diverge from the controller's would be a Critical defect by this repository's own definition (a consent/evidence boundary failing). Whichever call happens second would need to authoritatively fail closed if the first already failed, never silently proceed.

### How are expiration and cancellation represented?

Unchanged: `ExecutionSession` already has `expire_session(...)`/`cancel_session(...)`/`invalidate_session(...)`, all using the same 30-minute-TTL, wall-clock-based policy `gauss_orchestration_state_store.py` already established at `v0.36.0`. Integration would need exactly one authoritative expiry clock, not two independently-computed ones — likely meaning the durable store's own `confirmation_expires_at` remains authoritative, and `ExecutionSession`'s own `expires_at` becomes a synchronized *view*, not a second source of truth.

### Can a session contain multiple execution instances?

**Today: no**, and this document does not recommend changing that in `v0.47.0`. The evaluation evidence above confirms a workspace's own lifecycle is single-shot (`ready → executing → completed`, then only `archived → deleted`). Retrying failed code, or running a second, related piece of code, already correctly requires a brand-new proposal (`v0.37.0`'s `RerunRequiresNewRequestError`) *and*, in practice, typically a fresh workspace too (though a `completed`, not-yet-archived workspace could in principle still be read from, per `v0.44.0`'s reader, which does not require `ready` status). A future design that wanted "one session, several sequential instances" would need to either loosen the workspace's own one-shot lifecycle (a workspace-layer change, not merely a session-layer one) or decouple instance execution from workspace status entirely — both are architecture-level decisions this document flags but does not resolve.

### How should `WorkflowResult` expose both `session_id` and `execution_instance_id`?

Recommendation: rename/reinterpret `execution_session_reference` to genuinely mean `ExecutionSession.execution_session_id`, and add a new, separate `execution_instance_reference` field for the specific attempt (mirroring `WorkspaceProvenance`'s own existing, already-correct three-identifier shape: `workspace_id`/`execution_session_id`/`execution_instance_id` — that type already got this right in `v0.43.0`; `WorkflowResult`'s own top-level field is what needs to catch up to it).

### Where should `begin_analysis()` be invoked?

Recommendation: inside `ExecutionWorkflow.execute(...)`, immediately after a terminal execution result is recorded, using narrow, injected fake-shaped hooks (mirroring the controller's own existing `analysis_hook`/`report_hook` parameters, already exercised by every prior milestone's real-invocation harnesses). This was explicitly out of scope for `v0.45.0` ("real analysis-engine integration... remains untouched") and remains a genuinely separate, non-trivial scope item — wiring it is not merely a session-identity fix.

### What backward compatibility is required?

Every existing, additive, optional parameter must remain optional with its current default behavior: `ExecutionWorkflow(state_store=..., workspace_registry=None)` and `propose_execution(..., workspace_id=None)` must continue to work exactly as today for every caller that never opts into session integration — the same discipline `v0.36.0`, `v0.43.0`, and `v0.44.0` each already applied to their own additive integrations. All 352 existing test functions across 10 suites must continue passing unmodified.

### What test changes are required?

New tests would be needed for: session creation happening automatically inside `propose_execution(...)`; the confirmation-binding-must-never-diverge guarantee above (a genuine new safety-critical test category); `WorkflowResult`'s new two-identifier shape; and a full regression pass of every existing suite. No existing test's *expected* behavior should need to change — only new tests should be added, per the "fully additive" pattern established by every prior integration milestone in this chain.

### What migration path preserves current additive APIs?

1. Add `ExecutionSession` creation inside `propose_execution(...)`, gated behind a new, optional parameter (e.g. `use_durable_session: bool = False`) so existing callers are entirely unaffected until they opt in.
2. Once proven stable and tested, consider flipping the default — but only as an explicitly separate, later decision, never silently, and never within the same milestone that introduces the capability.
3. Never remove `orchestration_instance_id`-based tracking — it remains the actual controller-level identity regardless of what the session layer exposes on top of it.

## Recommended `v0.47.0` Scope (Narrowly Bounded)

1. Wire `ExecutionSession` creation into `ExecutionWorkflow.propose_execution(...)`, additive and opt-in.
2. Bind `workspace_id` onto `ExecutionSession` (new field).
3. Make confirmation binding a single source of truth (resolve the "must never disagree" question above explicitly, in the implementation report).
4. Extend `WorkflowResult` with a genuine `execution_instance_reference`, alongside a now-accurately-named `execution_session_reference`.
5. **Explicitly out of scope for `v0.47.0`:** `begin_analysis()` wiring (a separate, larger scope item); multiple-instances-per-session (an architecture-level decision, not a naming fix); durable persistence of `ExecutionSession` itself (would re-open `v0.36.0`'s own already-closed stop conditions unless separately, explicitly re-authorized); ownership/ACL enforcement (still an unvalidated, opaque reference everywhere in this codebase).

## Release Criteria for This Document

This document itself has no release criteria beyond being reviewed — it authorizes no implementation. `v0.47.0`'s own eventual readiness would be judged against the "Recommended `v0.47.0` Scope" list above, once separately authorized.
