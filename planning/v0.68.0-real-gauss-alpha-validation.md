# v0.68.0 — Real GAUSS End-to-End Alpha Validation

## Objective

Validate the complete, installed `gauss-ai` product against **real GAUSS** (26.1.1, `C:/gauss26/tgauss.exe`), exactly as an alpha tester would use it: install, configure, `doctor`, guided workflow, real execution, repair, verification, human review, session summary. This milestone adds no new product capability — it validates the one shipped in `v0.67.0`.

## What this milestone is not

Not a new reasoning stage, approval layer, durable session, rollback mechanism, multi-file repair capability, cloud execution path, new repair intelligence, autonomous behavior, retry mechanism, database, telemetry, or analytics. Every scenario below drives the exact same, unmodified pipeline `v0.62.0`-`v0.67.0` already shipped.

## Validation methodology

Every alpha scenario is driven through the **installed** `gauss-ai` command (a dedicated, persistent venv with `pip install -e .` run against this real repository, kept for the duration of this milestone), invoked via subprocess exactly as a real tester's shell would — never a direct Python import, except inside `scripts/test_*.py` unit tests where direct import is the established, correct testing convention for this repository's own internal logic.

Real GAUSS is used only for the scenarios that specifically require it (marked below); everything else uses the fake runner, and every piece of evidence in this milestone's `58.x` benchmark run files states explicitly which backend produced it.

## The one piece of instrumentation: `--export-session`

`gauss-ai repair <file.gss> --export-session <path>` writes a structured JSON diagnostic bundle at the end of the same guided-repair process — configuration (redacted), runner, workspace, execution, repair (plan/draft/application digests and outcome), verification (request/comparison), review, the full repair-session summary text, environment, and versions. No secrets are ever included (the bundle contains exactly the same fields `gauss-ai config show`/`gauss-ai version` already disclose, plus the session's own evidence).

**Why not a standalone `gauss-ai export-session` command**: durable sessions are explicitly out of scope for this milestone (and every milestone before it). Each `gauss-ai` process is stateless once it exits — there is no state for a later, separate `export-session` invocation to read. Writing the bundle synchronously, inside the same process that already holds the real session state, is the only design that doesn't smuggle in a persistence layer through the back door. This satisfies the task's own "`gauss-ai export-session` **or equivalent**."

This is the only code change to product behavior in this milestone. It is strictly additive (an optional flag, default off), read-only with respect to the repair pipeline (it inspects already-existing adapter state after the guided sequence completes; it triggers nothing and decides nothing), and covered by its own dedicated tests.

## Real-GAUSS scenarios (explicitly requiring real execution)

- Successful execution of a valid `.gss` file.
- `G0105` (missing statement terminator) — the exact catalog-verified fault class already used throughout this repository's evidence.
- `G0036` (dimension mismatch).
- `G0025` (undefined symbol).
- A full guided repair → application → verification → review cycle against a real, genuinely-failing file, using the real runner throughout (not `--fake-result`).

## Fake-mode scenarios (no real GAUSS required, or specifically testing fake/real disambiguation)

Cancelled approvals (each of the four approval points), blocked application (stale-source and gate-failure paths), completed-workspace behavior, workspace reset behavior, output-file reading, and installation/doctor/init/config behavior (already covered with real evidence in `v0.67.0`'s `57.x`, re-validated here only where this milestone's own scenario list requires it).

## Evaluation

A new `58.x` Real Alpha Validation benchmark category (ten prompts), evaluated with real, captured evidence from the installed CLI — no fabricated output. Any defect found is fixed narrowly, within the smallest module responsible, with no broadening of scope and no architecture change.

## Not implemented

Durable sessions, rollback, multi-file repair, cloud execution, new approval layers, new repair intelligence, autonomous repair, automatic retries, an LLM redesign, new workflow stages, a database, telemetry, or analytics.
