# v0.58.0 - Repair Application Safety Design

## 1. Release Goal

`v0.58.0` defines the safety architecture for a future repair-application workflow. It is design-only.

It does not:

- construct patches
- edit code
- write files
- apply repairs
- rerun GAUSS
- persist approvals
- add durable sessions
- add a repair consumer
- change `safe_to_apply`
- change `safe_to_prepare_draft`

No module in this repository consumes anything defined here. `scripts/gauss_repair_planner.py` and `scripts/gauss_repair_approval.py` have zero diff as of this milestone.

## 2. Current State

- Repair planning exists (`scripts/gauss_repair_planner.py`, `v0.56.0`): `plan_repair(evidence, source_context=None) -> RepairPlan`.
- A repair-plan digest exists: `repair_plan_digest(plan) -> str`, SHA-256 over canonical JSON of every `RepairPlan` field in fixed order.
- Approval/decline/revoke exists (`scripts/gauss_repair_approval.py`, `v0.57.0`): `RepairApprovalStore.approve/decline/revoke/get_decision`.
- Approval is process-local: an ordinary in-memory `dict[str, ApprovalRecord]`, created fresh per adapter process, cleared by `reset`.
- Approval is strategy-level only: it records a decision about a `RepairPlan`'s general direction, never about a concrete edit (no concrete edit exists to approve).
- Source identity is not yet bound: nothing in the repair-planning or approval layer references a specific file's content at a specific point in time. `SourceContext` (repair-planning's own optional input) carries caller-asserted strings (e.g. `code_text`, `matrix_shapes`) — never a hash, never a verified read.
- Draft identity does not exist: no `RepairDraft` type, no draft digest, no representation of a concrete edit anywhere in this repository.
- Application identity does not exist: no `repair_application_id`, no application record, no consumer of `ApprovalRecord`.
- No rollback model exists.
- No stale-source detection exists — there is no source binding to go stale.
- No rerun-approval model exists, separate from execution's own existing confirmation model.
- No atomic file-write utility exists anywhere in this repository (confirmed by a repository-wide search for `os.replace`/temp-file-then-rename patterns — none found). The closest precedent for *any* atomic mutation is `gauss_orchestration_state_store.py`'s SQLite transactional writes (`BEGIN IMMEDIATE`), which protects a database record, not a plain file.
- The closest precedent for a *real*, module-computed content hash is `gauss_workspace_file_reader.py`'s `checksum = hashlib.sha256(raw).hexdigest()`, computed over bytes it actually read under its own safety checks (extension allowlist, binary-content sniff, size ceiling, UTF-8-only). `gauss_workspace.py`'s own `ManifestFileEntry.checksum`/`.size` fields are, by contrast, caller-asserted metadata the workspace module never verifies.
- The closest precedent for a multi-field, expiring, monotonically-confirmed identity chain is `gauss_execution_session.py`'s `ExecutionSession` (`request_hash`/`plan_digest`/`code_digest`/`confirmation_scope`, 30-minute TTL, `created → awaiting_confirmation → confirmed → {ready, expired, cancelled}`) — designed in `v0.40.0`, never wired into the adapter, and the direct structural precedent this design borrows from for the draft→application identity chain.

## 3. Core Safety Question

**How can the system eventually apply an approved repair without allowing stale, broadened, mis-targeted, or unauthorized edits?**

Answer, in one sentence: by making every step of the chain — strategy, draft, application — bind to an exact, content-derived digest of everything it depends on, re-verifying the most safety-critical of those digests (the target file's own content hash) at the last possible moment before any byte is written, and refusing rather than guessing whenever any bound value no longer matches. Nothing in this design trusts that state observed a moment ago is still true; every gate re-checks.

## 4. Approval Layer Separation

Four separate decisions. None may be collapsed into another.

**A. Repair strategy approval** *(exists today, `v0.57.0`)*

Meaning: the user approves the general repair direction described by a `RepairPlan`.

Does not authorize: draft creation, file editing, application, rerun.

**B. Repair draft approval** *(future)*

Meaning: the user approves a specific, concrete, structured edit against a specific, verified source identity — the exact `RepairDraft` they were shown, identified by `draft_digest`.

Does not authorize: application (a separate approval below), rerun.

**C. Repair application approval** *(future)*

Meaning: the user authorizes applying the exact approved draft to the exact, freshly-reverified source state.

Does not authorize: any edit beyond the approved draft's declared scope, creation of new files unless the draft explicitly declared one, or rerun.

**D. Rerun approval** *(future, already conceptually distinct from repair entirely)*

Meaning: the user approves executing the resulting code after application, through the existing `request`/`plan`/`confirm`/`execute` execution-confirmation path — not a repair-specific mechanism at all.

Must remain separate from repair application. Applying a repair is not, and must never become, sufficient authorization to run anything.

Collapsing any two of these into one approval is explicitly prohibited by this design. A tester who approves a strategy has not approved a draft; a tester who approves a draft has not approved applying it; a tester who approves an application has not approved rerunning the result.

## 5. Identity Model

| Identity | Produced by | Content-derived? | Reused precedent |
|---|---|---|---|
| `repair_plan_digest` | `gauss_repair_planner.py` (exists) | Yes, SHA-256/canonical-JSON | `compute_request_hash` |
| `source_artifact_id` | future | No — a stable reference (e.g. `workspace_id` + `relative_path`) | `ManifestFileEntry` naming |
| `source_content_hash` | future | Yes, SHA-256 over raw bytes actually read | `gauss_workspace_file_reader.py`'s `checksum` |
| `repair_draft_id` | future | No — an opaque identifier for a specific drafting attempt | `ExecutionSession.execution_session_id` |
| `repair_draft_digest` | future | Yes, SHA-256/canonical-JSON over the draft's full identifying content (mirrors `repair_plan_digest`) | `repair_plan_digest` |
| `target_workspace_id` | existing `gauss_workspace.py` | No | unchanged |
| `target_relative_path` | existing `gauss_workspace.py` | No | unchanged |
| `repair_application_id` | future | No — an opaque identifier for one application attempt | `ExecutionSession.execution_session_id` |
| `execution_request_id` (rerun) | existing execution-workflow path | No | unchanged, not repair-specific |
| `approval_record_id` | future (today's `ApprovalRecord` has none — it is looked up by `plan_digest` alone) | No | new |
| actor/owner reference | future, optional | No | `ExecutionSession.owner` |

Cardinality:

- One repair plan may produce **multiple drafts** (different attempts, different source context, or a redrafted attempt after the first was declined).
- One draft targets **exactly one exact source state** — one `source_content_hash`, one `target_relative_path`, one `target_workspace_id`. A draft touching more than one file is not a single draft under this model; it would need to be multiple drafts, each independently approved (multi-file repair is an explicit non-goal for the initial scope — see §9, §25).
- One application consumes **exactly one approved draft**. An application is a single, one-shot event against that one draft's exact bound state.
- One applied repair may later lead to **one or more separately approved execution attempts** (reruns) — the relationship between an application and any subsequent rerun is recorded (§16), but a rerun is never implied or auto-triggered by an application.

An orchestration ID (`orchestration_instance_id`, `execution_session_id`) is never reused as a repair identity. Repair identities are a parallel, independent chain — they may *reference* an orchestration/session identity for provenance (e.g. "this draft was drafted in response to evidence from execution instance X"), but a repair draft ID, digest, or application ID is never assigned from, aliased to, or interchangeable with an orchestration ID. This mirrors the same discipline `gauss_repair_planner.py`'s own module docstring already applies (repair planning "does not duplicate" interpretation/diagnosis models — it consumes and references them).

## 6. Source Identity and Binding

A future application must bind to **all** of the following, not any single one alone:

- `target_workspace_id`
- `target_relative_path`
- file type (a fixed, small allowlist — see §9)
- `source_content_hash` (SHA-256 over the exact bytes read, at read time — **authoritative**)
- file size (a cheap, cross-checkable companion to the hash, not a substitute for it)
- last-observed timestamp, if available from the underlying filesystem — advisory only, never authoritative (clock skew, filesystem timestamp granularity, and copy operations that preserve mtime all make timestamps unreliable as a safety signal)
- the workspace's own manifest entry / artifact identity, if one exists for this file
- an optional source-range identity (line range) — only meaningful in conjunction with the content hash of the *whole* file, since a line range alone says nothing about whether lines outside the range changed
- `repair_plan_digest` — the plan this draft claims to be derived from
- `repair_draft_digest` — the draft itself, once one exists

**The source content hash is authoritative for stale-source detection.** Path alone is insufficient (a different file can exist at the same path a moment later). Filename alone is insufficient (multiple paths can share a filename; a filename asserts nothing about content). Workspace ID alone is insufficient (a workspace can contain many files, and — per `gauss_workspace.py`'s existing, caller-asserted `checksum`/`size` fields — nothing today verifies a workspace's own manifest against real file bytes). Only a hash computed over bytes actually read, at the moment they matter, tells the truth about content.

## 7. Stale-Source Detection

**Before draft generation:** revalidate source identity — re-read and re-hash the target through the same explicit, authorized read path a draft's inputs came from; compare against whatever hash the caller's `SourceContext` (or equivalent future input) claims. Do not draft against an assumed, cached, or previously-observed hash.

**Before application:** re-read or re-hash the target through an explicit, authorized path *immediately* before any write; compare against the hash bound in the approved draft; reject if changed. This is the single most safety-critical check in the entire design (§3).

**Invalidate the draft and any approval recorded against it when any of the following changes:**

- source content (`source_content_hash` differs)
- target path
- workspace
- `repair_plan_digest`
- draft content (`repair_draft_digest` differs)
- edit range
- repair strategy
- encoding, where material to interpretation
- line-ending normalization, if it changes the bound content — unless a future implementation explicitly designs and discloses a specific normalization policy as part of the bound identity itself (i.e., normalization becomes part of what is hashed, not something applied silently before hashing)

**Never:**

- silently rebase a draft onto changed content
- auto-merge
- "best effort" apply to content that no longer matches

A mismatch is always a hard stop, never a degraded-but-proceeding path. This mirrors `gauss_repair_approval.py`'s own existing rule that a stale digest is simply not found — there is no fuzzy-match fallback in this repository's approval model today, and this design extends that same discipline to source content.

## 8. Repair Draft Model

A future immutable `RepairDraft`:

```
draft_id
repair_plan_digest
source_artifact_id
source_content_hash
workspace_id
relative_path
edit_scope
proposed_changes          (see representation comparison below)
draft_digest              (SHA-256/canonical-JSON, mirrors repair_plan_digest)
generated_at
generated_by              ("deterministic" | an identified drafting mechanism -- see §10
assumptions
risks
verification_steps
application_preconditions
approval_status
safe_to_apply              (remains False until every future gate in §13 passes)
```

**Representation comparison** for `proposed_changes`:

| Representation | Pros | Cons for this use case |
|---|---|---|
| Unified diff (text patch) | Human-familiar; renderable for review | Context-line matching is inherently fuzzy-tolerant in most patch tools (that fuzziness is a feature for human workflows and a liability for an automated safety gate); parsing/applying requires trusting a patch-apply library's own edge-case handling; nothing prevents a multi-file diff without an extra validation pass |
| Structured edit operations (bounded line-range replacements) | Deterministically validated with no parser ambiguity; trivially bounded to one file and one or a few ranges; trivially reversible (the removed text is recorded alongside the replacement); no dependency on patch-apply fuzzy-matching semantics | Less immediately human-familiar than a diff; a renderer is needed to *display* a diff-like view (see below) |
| Full-file replacement | Simplest to describe | Violates minimal-scope; hardest to review meaningfully; highest risk of silently clobbering unrelated content if the file changed elsewhere; explicitly discouraged by this design (see §9) |
| AST-like structured edit | Would allow semantic-level validation | No verified GAUSS parser/AST tool exists anywhere in this repository or its evidence base; inventing one would itself be an unverified-syntax risk this project's own guardrails forbid; not realistic now |

**Recommendation:** structured, bounded line-range edit operations (`{line_start, line_end, original_text, replacement_text}`, one or a small, explicitly bounded number of ranges, all within one file) as the **authoritative, applied** representation. A unified-diff-style view may be *rendered* from the structured edits for human display in §12, but the diff text itself is never the thing validated or applied — this avoids importing any patch-apply library's own fuzzy-matching behavior into a safety-critical path. Full-file replacement is explicitly not the initial representation (see §9 for the scope decision itself).

## 9. Allowed Edit Scope

Conservative initial scope for any future implementation:

- one existing `.gss` text file
- one bounded workspace
- one approved relative path
- UTF-8 text only (reuses `gauss_workspace_file_reader.py`'s existing encoding policy: explicit rejection, never silent transcoding)
- no binary files
- no directories
- no renames
- no deletes
- no new files
- no changes outside the approved line range(s)
- no package files
- no global configuration
- no GAUSS installation files
- no license files
- no environment files
- no workspace metadata mutation except explicit, structured provenance recording (the same principle `ExecutionWorkflow` already applies when it registers output-file provenance — recording *about* a change is not the same as making an unrelated one)

**Whole-file replacement should be prohibited in the initial scope.** Minimal line-range edits (or a small, explicitly bounded set of them) are strongly preferred: they are smaller to review, smaller to validate, smaller to reverse, and structurally incapable of silently discarding content the draft's author never saw or considered. A future phase could reconsider a bounded "structured full-file replacement" only after the line-range model has real operational evidence behind it — not before.

## 10. Draft Generation Boundary

A future draft generator **may** consume:

- an approved repair plan
- explicitly authorized source content (freshly re-read and re-hashed, per §7)
- exact source identity
- a bounded source range
- verified diagnostic context (from `gauss_execution_diagnostics.py`'s own `DiagnosticAssessment`)

It **must not**:

- read arbitrary source files
- infer omitted source
- broaden edit scope beyond what was explicitly authorized
- alter additional files
- include unapproved cleanup or refactoring alongside the approved fix
- generate a draft from stale source (§7 applies at draft-generation time too, not only at application time)
- use unrelated conversational context as authorization (only explicit, structured input counts — the same principle `SourceContext` already enforces for repair planning)

**Is deterministic draft construction realistic?** Only for a narrow subset of cataloged codes where the fix is genuinely mechanical given exact source text — for example, `G0105` with an exactly-known missing-semicolon location, or `G0290` where the fix is entirely outside the file (install a package) and produces no in-file draft at all. For most codes (e.g. `G0036`'s "which operand needs adjustment," `G0025`'s "what should this symbol resolve to"), a deterministic lookup table cannot generate correct replacement text — that requires understanding the user's intent, which this repository's own catalog-driven design deliberately does not attempt (see `gauss_repair_planner.py`'s own guardrails).

**Conclusion: an LLM-assisted drafting layer will likely be required for general-purpose drafting.** If so:

- it must be **isolated from application** — a drafting component's output is never trusted enough to skip any gate in §11 or §13
- it must produce output that is then run through the exact same **deterministic validation** any other draft would face, with **zero special trust**
- the generated edit is **untrusted input**, identical in standing to a draft a human typed by hand
- **explicit draft approval is still required** — never auto-approved because a model reports high confidence

## 11. Draft Validation

Before draft approval is even offered, a future implementation must validate:

- target identity matches (`workspace_id` + `relative_path` match what the plan/context named)
- source hash matches the freshly re-read file
- the structured edit list parses (well-formed ranges, no overlaps, no out-of-bounds lines)
- edit scope remains bounded (single file, declared ranges only)
- no path traversal in the declared path
- no extra files referenced
- no unsupported file type
- no forbidden tokens or paths, where relevant (e.g. a path pointing outside the workspace root, or at a filename this design's scope excludes — package/license/environment files)
- no edit outside the authorized range
- no hidden whitespace-only expansion that isn't shown as part of the displayed diff
- no encoding change
- no line-ending surprise (the resulting file's line-ending convention must be explicitly accounted for, not silently altered)
- the proposed change is reversible (the original text for every replaced range is recorded, sufficient to reconstruct the pre-application file exactly)
- the resulting file, if constructed in memory, remains decodable UTF-8 text

**Validation does not prove GAUSS correctness.** It proves structural safety only — that the edit is well-formed, bounded, reversible, and targets what it claims to target. Nothing in this design, now or in a future implementation, claims a validated draft is a *correct* fix. That claim would require actually running the result, which is rerun's job (§4.D, §20), not application's.

## 12. Human Review Requirements

Before draft approval, a future implementation must show:

- target file (path, within its workspace)
- workspace
- source hash
- repair-plan digest
- draft digest
- the exact diff (rendered from the structured edit list, per §8)
- lines changed (count, and which line numbers)
- assumptions
- risks
- missing evidence
- expected effect
- verification steps
- an explicit statement that correctness is not guaranteed

Approval must be **tied to the draft digest** — the same discipline `gauss_repair_approval.py` already enforces for plan digests (§4-6 of `docs/gauss-repair-approval.md`). A vague confirmation ("yes," "looks good") unaccompanied by the exact digest of what was just displayed is not acceptable input for draft approval, mirroring how `approve-repair` today requires the caller to supply the exact current `plan_digest`, not merely say "yes."

## 13. Application Gate

All of the following must hold before a future application may proceed. Any single failure blocks the entire application — **no fallback, no partial application**:

- valid strategy approval exists (§4.A)
- valid draft approval exists (§4.B), tied to this exact `draft_digest`
- valid application approval exists (§4.C), tied to this exact `draft_digest`
- the current source hash matches the bound `source_content_hash` (re-checked at this moment, not reused from draft time)
- the workspace remains eligible (mirrors the existing workspace-status eligibility check `ExecutionWorkflow.propose_execution` already performs)
- the target path remains valid (still resolves inside the workspace root, per `gauss_workspace.py`'s existing containment discipline)
- the edit scope remains within what was approved (no silent broadening between draft approval and application)
- the draft digest matches what was approved (no substitution)
- no approval has been revoked
- no approval has expired, if a future implementation adds expiry (mirroring `ExecutionSession`'s existing 30-minute TTL precedent)
- a backup has been prepared (§15) — application never proceeds without one
- a rollback path has been verified as available before the write, not merely assumed
- the application consumer itself is authorized to run (a future, narrow, explicitly-scoped capability — never automatically available just because a draft was approved)
- an audit record has been initialized (§16) before the write begins, so the attempt itself is recorded even if the write later fails

## 14. Application Transaction

The safest available local-file transaction, for a future implementation only:

1. Read and hash the current file through the same authorized read path used throughout this design.
2. Verify source identity (workspace, path, type, hash) against the approved draft's bound values.
3. Create a backup in the bounded workspace (§15), and verify the backup's own hash before proceeding.
4. Write the candidate result to a temporary file **in the same directory as the target** (same filesystem — required for atomic replace to be atomic at all; see platform caveats below).
5. Validate the temporary file: confirm it decodes as UTF-8 text, and re-run the structural checks from §11 against the actual bytes written, not just the in-memory edit list.
6. Atomically replace the target with the temporary file, where the platform supports it (`os.replace`/equivalent — see caveats).
7. Hash the resulting file and confirm it matches the expected post-application hash computed from the approved draft.
8. Record the application result (success/failure, both hashes, backup reference) as part of the audit record opened in §13's final gate.
9. Retain the rollback reference (the backup) — never delete it as part of a successful application.
10. **Do not rerun automatically.** Nothing in this transaction triggers execution; that is §20's separate concern.

**Platform caveats (documented here for a future implementation, not resolved by this design):**

- On Windows, a target file held open elsewhere (an editor, or GAUSS itself) can cause the replace step to fail with a sharing-violation-style error; the transaction must treat this as a hard `write_failed`, never as a signal to retry silently or force-close another process's handle.
- `os.replace` (POSIX `rename(2)` / Windows `MoveFileEx`) is atomic **only within a single filesystem/volume** — the temporary file in step 4 must be created on the same volume as the target, or atomicity is not actually achieved despite the API appearing to succeed.
- File permission and ownership bits are not guaranteed to be preserved identically across a replace on every platform; a future implementation must decide explicitly whether to preserve the original file's permissions rather than accept whatever the temp file happened to have.
- A crash between step 6 (replace succeeds) and step 8 (audit record written) is a real, only-partially-mitigated gap — see §21's "process crash" entry.

**This transaction is not implemented by this milestone.**

## 15. Backup and Rollback

- **Backup location:** workspace-contained — a dedicated subdirectory within the same bounded workspace (never outside it, consistent with `gauss_workspace.py`'s own containment discipline).
- **Backup naming:** derived from the target's relative path plus the pre-application content-hash prefix plus a timestamp, chosen to avoid collisions without needing a separate ID-allocation service.
- **Backup identity:** its own content hash, computed at backup time, over the *original* (pre-application) bytes.
- **Backup hash:** recorded in the audit entry (§16) so a rollback can itself be verified — restoring a backup and finding its hash no longer matches the recorded one is itself a hard failure, not something to paper over.
- **Retention:** kept, not auto-deleted. No silent deletion of any backup, ever, in this design.
- **Rollback authorization:** a separate, explicit confirmation, bound to a specific `repair_application_id` — never an implicit "undo the last thing," since "last thing" is state that can be ambiguous or wrong in a multi-attempt session.
- **Rollback audit event:** yes — its own audit record, distinct from the application record it reverses, cross-referencing it.
- **Behavior if rollback fails:** surface a hard, loud failure; never partially restore; never delete the backup as a result of a failed rollback attempt (the backup is the only recovery path left at that point).
- **Rollback does not imply rerun.** Restoring a file to its pre-application state is not, by itself, authorization to execute anything — §4.D and §20 still apply independently.

## 16. Audit and Provenance

A future audit record should carry:

- `repair_plan_digest`
- strategy-approval reference
- source identity (`workspace_id`, `relative_path`, `source_content_hash`)
- draft identity (`draft_id`, `draft_digest`)
- draft-approval reference
- application-approval reference
- actor/owner reference
- timestamps (draft generated, draft approved, application approved, application attempted, application completed/failed)
- `target_workspace_id` / `target_relative_path`
- pre-application hash
- post-application hash
- backup reference (and its own hash)
- application result (success/failure/failure-stage)
- rollback result, if one occurred
- rerun request identity, if a rerun is later created referencing this application

**No raw secrets.** Consistent with `gauss_orchestration_state_store.py`'s existing "digest-only" discipline (raw code is never persisted there — only `digest_code(code)`), an audit record should avoid storing unnecessary full source copies. The backup file itself is the durable copy of "what the file used to look like"; the audit record should reference it by hash and location rather than duplicating its full content a second time.

## 17. Invalidation Rules

| Event | What becomes invalid |
|---|---|
| Repair plan changed | Strategy approval (already true today — different digest, different record); any draft/draft-approval derived from the old plan |
| Diagnosis changed | The repair plan derived from it (transitively, per the row above), and anything downstream |
| Source content changed | Draft, draft approval, application approval — all bound to the old `source_content_hash` |
| Workspace changed | Draft, both downstream approvals |
| Path changed | Draft, both downstream approvals |
| Draft changed (any field, including scope) | Draft approval, application approval — `draft_digest` differs |
| Draft declined | That specific draft is terminal; a new draft would need its own approval cycle |
| Approval revoked (any layer) | That layer's approval only; does not retroactively un-invalidate anything already invalidated by another row |
| `reset` (existing adapter command) | All process-local state: last plan, all approval records, any future draft/application state held in the same process |
| Process restart | Everything process-local is gone by construction (§18 recommends this remain the case for the first implementation) |
| Timeout/expiry, if later added | The specific expired approval only, mirroring `ExecutionSession`'s own TTL behavior |
| Application partially fails | The application attempt is terminal (failed); the draft approval itself is not automatically invalidated, but a fresh application approval would be required to retry, and source re-verification (§7) would run again regardless |
| Rollback occurs | The application record is marked rolled-back; the file's identity has changed again (it is now back at, and re-hashed to, its pre-application state), so any *later* draft/application referencing the post-application hash is invalidated by the "source content changed" row above |

## 18. Persistence and Durable Sessions

**Does safe repair application require durable execution sessions? No — not for a narrowly constrained first implementation.**

These are four distinct things, and this design deliberately does not treat them as one:

- **Durable repair identity** — not needed. Every identity in §5 is either content-derived (recomputable, and therefore already "durable" in the sense that matters: it doesn't depend on where it's stored) or a simple opaque ID. Losing an in-memory ID on crash loses nothing that can't be recomputed or re-derived from the source of truth (the file itself, and the plan/draft content).
- **Durable approval records** — **recommended against**, for the first implementation, for the same reason `RepairApprovalStore` is process-local today: losing an approval on crash is the *safe* failure mode (fail closed — nothing was silently approved-and-forgotten; everything must be re-confirmed after a restart). This is not a gap to fix; it is the correct default until a concrete, authorized need for cross-process approval durability exists.
- **Durable source/draft references** — not required for identity (both are content-derived and recomputable), though the backup file itself (§15) is a durable *artifact*, which is a different thing from a durable *record*.
- **Durable application audit** — **recommended even for the first implementation**, and this is the one place this design departs from "keep everything process-local." Audit durability protects a different property than approval durability: accountability and forensic reconstruction *after* something happened, not trust continuation *before* it happens. Losing audit history on crash is not a safe default — it is the one scenario (a crash during or immediately after a file write) where losing the record is actively harmful, because it removes the evidence exactly when something might have gone wrong. This is why §21 marks the crash-before-audit-write gap as a real, only-partially-mitigated risk rather than claiming it away.
- **Durable execution session** — not required by repair application itself. It becomes relevant only if a future workflow needs an approval or application decision to survive across conversation turns or process restarts — for example, "approve a draft now, apply it in a later session." No such workflow is authorized or scoped today, and the product's entire existing shape (a single interactive CLI adapter process) creates no such need. Building session durability speculatively ahead of an actual authorized consumer would repeat the exact pattern `planning/v0.47.0-session-integration-readiness.md` already correctly avoided.

**Recommendation: C — a process-local prototype can be safe for a narrowly constrained first implementation**, on the condition that:

1. Content-hash re-verification happens at write time regardless of session age or process lifetime (§7, §13) — this is what actually prevents the dangerous outcome, not session durability.
2. The entire strategy→draft→application chain is required to complete within one continuous, confirmed process lifetime for a first implementation (mirroring `ExecutionSession`'s own confirmation-scope binding pattern, adapted to be process-local rather than durable).
3. Durable *audit* (not durable *session*, not durable *approval*) is added no later than Phase 5 (§23), specifically because it protects a distinct, asymmetric-risk property.

If a future product shape introduces genuine multi-turn or multi-process repair workflows, this recommendation should be revisited — but that is a decision for whichever milestone actually introduces that shape, not one to pre-build here.

| Blocked before write | plan not approved |
| Blocked before write | draft unavailable |
| Blocked before write | draft not approved |
| Blocked before write | application not approved |
| Blocked before write | approval conflict |
| Blocked before write | approval revoked |
| Blocked before write | source stale |
| Blocked before write | path invalid |
| Blocked before write | workspace invalid |
| Blocked before write | scope exceeded |
| Blocked before write | diff (edit list) invalid |
| Blocked before write | backup failed |
| During write | write failed |
| During write | atomic replacement unavailable |
| Post-write | post-write validation failed |
| Post-write (recovery) | rollback failed |
| Post-write (recovery) | audit failed |
| Downstream, separate concern | rerun not approved |

Everything in the "blocked before write" tier means the target file was never touched. Everything in "during write" means an attempt to mutate the target was made and did not complete as expected — these are the failure classes that most need the backup (§15) to already exist before they can occur, per the application gate (§13) requiring a verified backup as a precondition, not a step taken concurrently with the write itself.

## 20. Repair and Rerun Separation

**Applying a repair does not authorize execution.**

A future rerun must:

- create a new execution request, through the existing `request`/`plan`/`confirm`/`execute` path — not a repair-specific shortcut
- show the updated code identity (a new content hash, reflecting the applied change)
- use the updated source hash as the basis for that new request
- produce a new plan (a fresh execution proposal, subject to every existing eligibility/safety check `ExecutionWorkflow.propose_execution` already performs)
- require execution confirmation, exactly as every execution does today — no repair-derived shortcut around hash-bound confirmation
- preserve the relationship to the repair application that produced the code being rerun (via the audit record, §16), for traceability — without that relationship implying any reduced scrutiny

**No automatic rerun.** Nothing in this design proposes, implies, or leaves a code path capable of triggering execution as a consequence of application. This is the same boundary `gauss_repair_planner.py` and `gauss_repair_approval.py` already draw between repair and execution today, extended forward.

## 21. Security Threat Model

| Threat | Mitigation | Status |
|---|---|---|
| Stale approval replay | Content-hash re-verification at write time (§7, §13); digest-bound chain mirrors `ExecutionSession`'s confirmation-scope binding | Mitigated by design |
| Draft substitution | `draft_digest` bound into application approval; gate checks exact match | Mitigated by design |
| Source substitution | `source_content_hash` re-verified immediately before write, not reused from draft time | Mitigated by design |
| Path traversal | Reuse `gauss_workspace.py`'s existing `_resolve_inside` containment check, applied to the application target | Mitigated by design (reused precedent) |
| Symlink escape | `Path.resolve()` already follows symlinks before containment check in the existing workspace precedent; re-verify resolved path immediately before write | Partially unresolved — a TOCTOU window between resolve-check and write remains possible in full generality; narrower in practice since this repository's environment does not casually create symlinks (Windows requires elevated privileges), but not eliminated |
| Workspace swap | `target_workspace_id` bound into draft/application identity; workspace eligibility re-checked at application time (mirrors existing execution-eligibility gating) | Mitigated by design |
| Hash mismatch | Explicit reject-not-merge rule (§7) | Mitigated by design |
| Approval broadening | `edit_scope` is part of what `draft_digest` hashes; any scope change changes the digest and invalidates prior approval | Mitigated by design |
| Hidden extra-file edits | Draft model structurally supports exactly one target file (§8, §9); validation rejects any edit touching an undeclared path | Mitigated by design |
| Partial writes | Write-to-temp-then-atomic-replace (§14); never write in place | Mitigated by design |
| Failed rollback | Backup never deleted, even on rollback failure; failure surfaced loudly (§15) | Mitigated by design |
| Race between validation and write | Minimize the window (re-hash immediately before replace); full elimination would need OS-level exclusive locking, which is platform-inconsistent | Partially unresolved |
| Process crash | Crash before write: nothing touched (process-local state lost safely, §18). Crash between temp-write and replace: only an orphaned temp file, target untouched. Crash between replace and audit-write: file changed but not yet recorded | Partially unresolved — the replace-to-audit gap is real; durable audit (§18 Phase 5) narrows but does not fully close it |
| Untrusted LLM-generated diff | Treated as untrusted input; passes the same deterministic validation gate as any other draft, zero special trust (§10, §11) | Mitigated by design |
| Malicious source content | Source never auto-read; explicit authorization only; reuse file-reader's binary-sniff/size-ceiling/UTF-8-only checks at re-hash time | Mitigated by design (reused precedent) |
| Large patch abuse | Bounded edit scope, file-size ceiling (reuse `ABSOLUTE_MAX_BYTES` precedent); a future implementation should also cap total changed lines | Mitigated by design, with a concrete numeric cap left to implementation |
| Encoding tricks | UTF-8-only, explicit rejection, never silent transcoding (reuses file-reader policy) | Mitigated by design (reused precedent) |
| Newline normalization surprises | Explicitly named as an invalidating condition (§7); any normalization must be disclosed and part of the bound identity, never silent | Mitigated by design |
| Audit tampering | Append-only convention recommended; full tamper-resistance would need the same transactional-integrity conventions as `gauss_orchestration_state_store.py` | Unresolved for a process-local prototype; partially addressed once durable audit (Phase 5) lands; full tamper-proofing against a privileged local actor is out of scope (no ACL/multi-user model exists in this repository) |
| User confusion between plan/draft/application approval | Each layer requires its own digest-bound confirmation, distinct command names, distinct disclosure text (§12, §22) | Mitigated by design |

## 22. UX Flow

A future, **conceptual only**, command sequence — none of these are implemented by this milestone:

```
repair-plan                                    (exists today)
approve-repair <plan-digest>                    (exists today)
repair-draft ...                                (future)
show-repair-diff                                (future)
approve-repair-draft <draft-digest>             (future)
approve-repair-application <draft-digest>       (future)
apply-repair <draft-digest>                     (future)
repair-status                                   (future)
rollback-repair <application-id>                (future)

request / plan / confirm / execute              (existing, separate, for any rerun)
```

These names are conceptual only, chosen to make the four-layer separation (§4) visible in the command surface itself — a tester should never be able to reach `apply-repair` without having passed through a visibly distinct `approve-repair-draft` and `approve-repair-application` first. Minimizing confirmation fatigue matters, but not at the cost of collapsing these boundaries: each command's own name states exactly what it authorizes, mirroring how `approve-repair`/`decline-repair` already state exactly what they do today.

## 23. Proposed Implementation Phases

**Phase 1 — Source identity and draft model.** Define `RepairDraft`, `source_content_hash` computation (reusing the file-reader's existing checksum precedent), and `repair_draft_digest`. No generation, no validation, no approval yet — just the data model and its digest, proven deterministic the same way `repair_plan_digest` was. Depends on: nothing beyond what exists today.

**Phase 2 — Deterministic draft validation.** Implement §11's validation checks against a `RepairDraft`, independent of how the draft was produced. Depends on: Phase 1.

**Phase 3 — Draft-review and approval workflow.** CLI/API surface for displaying a draft (§12) and recording draft approval, mirroring `RepairApprovalStore`'s existing conflict/revoke discipline but keyed by `draft_digest`. Depends on: Phase 1, Phase 2.

**Phase 4 — Local single-file application prototype.** Implement §14's transaction, gated by §13, for the single-file/.gss/bounded-workspace scope in §9 only. This is the first phase that can write to a file at all. Depends on: Phase 1-3, plus an explicit new authorization decision (this design does not pre-authorize implementation).

**Phase 5 — Rollback and audit.** Implement §15/§16, including the durable-audit recommendation from §18. Depends on: Phase 4 (there is nothing to roll back or audit before an application exists).

**Phase 6 — Separate rerun workflow.** Wire an application's resulting code identity into a fresh, ordinary execution request through the existing execution path (§20) — explicitly not a repair-specific execution shortcut. Depends on: Phase 4 (an application must exist to rerun its result), but is otherwise independent of Phase 5.
