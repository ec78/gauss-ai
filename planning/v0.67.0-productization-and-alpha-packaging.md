# v0.67.0 — Productization and Alpha Packaging

## Objective

Move the GAUSS Code Assistant from "capability development" to "installable alpha product," without touching the core reasoning pipeline (Execution → ... → Repair Session Summary, complete as of `v0.66.0`). No new reasoning stage, no new approval layer, no durable session, no autonomous behavior.

## Packaging architecture

**No repository restructure.** `scripts/` remains exactly as it is — flat `gauss_*.py` modules, each importing siblings via `sys.path.insert(0, str(_SCRIPT_DIR)); import gauss_x as x`. Every existing file is untouched; `python scripts/gauss_code_assistant_cli.py` continues to work exactly as before.

A new `pyproject.toml` at the repo root declares `[tool.setuptools] package-dir = {"" = "scripts"}` plus an explicit `py-modules` list naming every non-test module in `scripts/` (the 30 pre-existing modules plus this milestone's 5 new ones). This makes every module in `scripts/` individually installable as a top-level import (`import gauss_code_assistant_cli`) under both `pip install -e .` (editable — the installed shim still points at the real files on disk, so `scripts/` never needs to be copied) and `pip install .` (non-editable — setuptools copies each named module into site-packages as an ordinary top-level module). No dotted package namespace is introduced, so no existing file's own bare-name imports (`import gauss_repair_draft as repair_draft_mod`) need to change.

`[project.scripts]` declares one console-script entry point, `gauss-ai`, pointing at `gauss_ai_cli:main` — a new, thin dispatcher module. It does not reimplement anything; every subcommand either calls an existing function directly (`gauss_code_assistant_cli.main(...)` for the REPL) or a new, small, single-purpose module that itself only composes existing logic (`gauss_environment_check.detect_environment(...)`, `InteractiveMvpAdapter.handle_line(...)`).

## New modules (all in `scripts/`, matching every prior milestone's convention)

- `gauss_ai_config.py` — the local configuration model and CLI-arg > env-var > config-file > default precedence resolver. No secrets, no license credentials, no arbitrary key/value mechanism — exactly four named settings (`gauss_executable`, `default_runner`, `workspace_parent`, `default_timeout_seconds`) plus one display preference (`verbose`).
- `gauss_ai_doctor.py` — read-only diagnostics returning structured PASS/WARN/FAIL results. Reuses `gauss_environment_check.detect_environment(...)` for GAUSS discovery; never runs GAUSS, never installs anything, never mutates configuration.
- `gauss_ai_init.py` — idempotent first-run setup. Reuses `gauss_ai_config`/`gauss_environment_check`; all interactive I/O is injectable (a `prompt_fn`) for testability; writes configuration only after explicit user confirmation.
- `gauss_ai_guided_repair.py` — the `gauss-ai repair <file>` orchestrator. Drives the *same* `InteractiveMvpAdapter.handle_line(...)` sequence a manual REPL tester would type, one command at a time, pausing for real, explicit user input at every approval point. Contains no repair, execution, or approval logic of its own — it is UI/orchestration only, verified by source-scan tests identical in spirit to every prior milestone's "no forbidden import" checks.
- `gauss_ai_cli.py` — the installed entry point. Parses `version` / `config show|set` / `doctor` / `init` / `repair <file>` / (no subcommand → the existing REPL via `gauss_code_assistant_cli.main(argv)`).

## Configuration model

File: `~/.gauss-ai/config.json` (via `Path.home()`, never a hard-coded user-specific path). Precedence, most to least authoritative:

1. Explicit CLI argument (e.g. `--gauss-executable`)
2. Environment variable (`GAUSS_EXECUTABLE`, `GAUSS_AI_DEFAULT_RUNNER`, `GAUSS_AI_WORKSPACE_PARENT`, `GAUSS_AI_TIMEOUT_SECONDS`)
3. Local config file
4. Safe default (`default_runner=fake`, `default_timeout_seconds=30.0`, no configured executable, no configured workspace parent)

This mirrors the architecture already established by `gauss_code_assistant_cli._resolve_real_executable(...)` (CLI arg, then `GAUSS_EXECUTABLE` env var, then error) — this milestone only adds one more fallback rung (the config file) below the two that already exist, and adds the same pattern for `default_runner`/`workspace_parent`/`default_timeout_seconds`, which previously had no env-var or config-file layer at all.

## Doctor

Read-only. Checks: Python version (`>=3.10`, matching this milestone's `requires-python`), required stdlib/module imports succeed, workspace-parent directory (configured or default) is writable, GAUSS executable configuration is present and points at an existing, terminal (`tgauss`/`tgauss.exe`) file — never a GUI `gauss.exe`, package/repository version, and configuration file validity. GAUSS version discovery is done by parsing the executable's own path string (`gauss_environment_check.parse_gauss_version(...)`) — never by launching it. No network access, no package installation, no configuration mutation.

## Init

Idempotent: reads existing configuration first, shows it, and only asks about settings not already confirmed. Uses `gauss_environment_check.detect_environment(...)` for discovery; if multiple candidates are found, always requires an explicit choice — never silently picks one. Writes the config file only after explicit confirmation of every value.

## Guided repair workflow

`gauss-ai repair <file.gss>` walks: workspace create → source identity display → request (using the file's real content) → plan → **confirm (explicit)** → execute → interpret → diagnose → repair-plan → **strategy approval (explicit)** → repair-draft → **draft approval (explicit)** → **application approval (explicit)** → application-gate check → **apply-repair (explicit)** → verify-repair → **confirm (explicit)** → execute → **review-verification (explicit)** → show-repair-session. Every "explicit" step pauses for real terminal input and shows exactly what is being approved (the plan_digest/draft_digest/request_hash involved) before accepting a decision. A stage that does not apply (e.g. the original execution already succeeded, so there is nothing to repair) is skipped with a plain-language explanation, never silently faked.

## Proof of no bypass

A dedicated test module (`scripts/test_gauss_ai_guided_repair.py`) drives the guided command with a scripted, cancel-at-every-step input sequence and asserts, after each cancellation, that the underlying adapter state shows no approval was recorded, no file was written, and no execution occurred beyond what an explicit `confirm` authorized — reusing the exact same adapter-state identity/length assertions every prior milestone's own CLI tests already established.

## Not implemented

Durable sessions, a database, telemetry, a cloud backend, a web app, an IDE plugin, automatic updates, multi-user accounts, authentication, multi-file repair, autonomous repair, automatic retry, rollback, analytics, GAUSS-internal package installation, license activation, an LLM agent redesign, and any new reasoning or approval layer.
