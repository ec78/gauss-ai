# v0.36.0 Implementation Report: Durable Execution State and Cross-Process Safety

## Milestone Purpose

`v0.36.0` replaces the orchestration controller's in-memory-only safeguards with an optional, explicit, standard-library SQLite-backed durable state layer, establishing this invariant across process restarts and across cooperating local processes:

> A confirmed canonical request that has already been authorized or attempted must never be silently invoked again.

**No GAUSS was run at any point in this milestone's own implementation, testing, or evaluation work.** See `planning/v0.36.0-durable-execution-state-and-cross-process-safety.md` for the full upfront design (data model, transaction boundaries, locking model, crash-recovery model, confirmation-expiry policy, corruption behavior).

## Database Schema

Four tables in one SQLite file (default `.gauss_orchestration_state/orchestration.db`, deliberately excluded from version control):

- `schema_meta` — one row, `schema_version INTEGER`, `created_at REAL`.
- `orchestration_records` — one row per orchestration instance, primary key `orchestration_instance_id`; columns for session/request identity, `code_digest` (SHA-256, never raw code), current/previous state, confirmation status/scope/timestamp/consumed/expires_at, invocation status/id, execution_status/exit_code/output_file_count, validation_ok/validation_problems (bounded JSON), failure_category, cancellation/analysis/report status, transition_sequence_number, timestamps, schema_version.
- `transition_events` — ordered transition history, `UNIQUE(orchestration_instance_id, sequence_number)`.
- `invocation_attempts` — at most one row per instance, `UNIQUE(orchestration_instance_id)` — a second, independent enforcement layer beyond the atomic conditional `UPDATE`.

**Never persisted:** raw inline code, stdout/stderr text, output-file content, secrets/credentials, environment-variable values, raw conversation text — verified directly by a whole-file byte scan (`test_51_database_file_never_contains_raw_code_text`) confirming a distinctive marker from real inline code never appears in the produced database file.

## Transaction Boundaries

Every write is one explicit transaction: `BEGIN IMMEDIATE` (acquiring SQLite's write lock immediately, avoiding a deferred-transaction race window) → precondition checks → a single conditional `UPDATE ... WHERE <every precondition>` → `COMMIT`, or `ROLLBACK` on any exception. `authorize_invocation(...)` is the highest-stakes transaction: it verifies record existence, current state (`confirmed`), request-hash match, session match, confirmation acceptance/scope/non-consumption, confirmation non-expiry (against a store-computed wall-clock value, never the caller-supplied opaque timestamp label), and the expected transition-sequence number — only if every condition holds does it atomically consume confirmation, record the invocation ID, transition to `executing`, and append the transition event, all before the controller may call any helper.

## Controller Integration

`scripts/gauss_runtime_orchestration.py` gained an optional `state_store` parameter (default `None`, preserving all 85 pre-existing tests unchanged) threaded through `_transition()`/`_force_complete()`/`_sync_extra()`. `confirm()` calls the store's `record_confirmation(...)` before its in-memory mirror; `invoke()` calls `authorize_invocation(...)` **before** any in-memory mutation or runner call — the hard requirement that the controller can never invoke first and persist afterward. Store-reported failures are translated to the matching in-memory exception types (`DuplicateInvocationError`, `SessionMismatchError`, `GuardFailedError`). Two new module functions: `build_durable_orchestration_instance(...)` (explicit, named "production construction," mirrors `build_production_adapter_runner(...)`'s convention, raises if `state_store` is `None`) and `reload_orchestration_instance(...)` (reconstructs an in-memory view from durable state after a restart; `instance.request` is always `None` post-reload since raw code was never persisted — this is what makes `begin_analysis()`/`invoke()` correctly refuse to proceed on a reloaded instance via their pre-existing `self.request is None` guards, preventing resurrection of execution capability from incomplete state). `scripts/gauss_execution_adapter.py` and `scripts/gauss_code_execution.py` were **not** modified.

## Concurrency Test Evidence

`scripts/test_gauss_orchestration_state_store_concurrency.py`, using real `multiprocessing.Process` workers (not threads), run twice for stability, both runs 15/15 passing:

- **Race (5 processes, same instance):** exactly one success every time; durable record's `invocation_id` matches the winner.
- **Duplicate delivery:** a second delivery of the same `invocation_id` (from a separate process) is refused.
- **Process-restart persistence:** a wholly new process attempting the same instance after the first fully exits is still refused.
- **Same code, new instance, cross-process:** two independent instances sharing one `request_hash`, each authorized by its own separate process, both succeed.
- **Stale sequence, isolated cross-process:** two processes target the same starting sequence number for a non-authorization transition; the loser fails specifically with `StaleTransitionError`.
- **Lock contention:** a holder process holds a real write lock for a controlled duration while a competitor (short `busy_timeout`) attempts authorization — outcome is always either a successful bounded wait or `LockContentionError`, never an inconsistent record.

## Crash-Simulation Evidence

Four scenarios, each verified by inspecting durable state through a fresh store connection after the simulated crash:

1. **Before authorization commit** (a raw, uncommitted partial `UPDATE`, abandoned via `os._exit`): no trace visible; confirmation remains unconsumed; a subsequent real authorization succeeds normally.
2. **After authorization commit, before helper call:** record shows `executing`, an `invocation_id`, no `execution_status` — surfaced by `list_ambiguous_invocations()`/`--list-ambiguous` as requiring manual review; no automatic retry.
3. **After helper call, before result persistence:** identical durable signature to scenario 2 — honestly disclosed as indistinguishable from it, since resolving this would require a helper/schema change (a stop condition).
4. **After result persistence:** `execution_status`/`exit_code`/`output_file_count` preserved exactly; record no longer ambiguous; state (`execution_completed`) safe for a reader to continue from.

## Corruption Behavior

Seven scenarios verified, all failing closed, none auto-repaired: malformed `validation_problems` JSON, an unrecognized `current_state` value, an impossible confirmation state (`confirmation_consumed=1` with `confirmation_status='none'`), a deleted/missing `transition_events` row (detected via `transition_sequence_number` mismatch, not just gap-in-sequence — the initially-drafted gap-only check was found to miss a fully-deleted single-event history, then fixed), a UNIQUE-constraint-blocked duplicate `invocation_attempts` row (verified even via raw SQL bypassing the public API), an unsupported `schema_version` (blocks `initialize()` entirely), and authorization against a corrupted-state record (fails via the ordinary state-mismatch precondition, since `authorize_invocation` reads the raw row directly).

## Persistence and Redaction Audit

- Record, confirmation (pre- and post-expiry), consumed confirmation, execution result, terminal state, and transition history all verified to survive a store close/reopen cycle (single-process) and genuine process exit (cross-process).
- Static content scan confirms no raw code ever appears in the database file.
- `DurableRecord.to_safe_summary()` excludes `code`, `stdout`, `stderr`, and `output_files` full content by construction — verified directly.
- Read-only CLI (`--list`, `--show`, `--history`, `--list-ambiguous`, `--list-expired`, `--list-terminal`, `--list-needs-review`, `--check-integrity`) never mutates the database — verified by comparing a record's safe summary before and after every inspection command.

Two self-correction episodes during test development, disclosed for transparency: (1) `check_integrity()`'s initial gap-detection logic failed to catch a fully-deleted single-transition history (empty history trivially "looks" gap-free) — fixed by additionally comparing history length against the record's own `transition_sequence_number`. (2) Several new controller tests initially assumed distinct `request_id` alone produces a distinct `request_hash` and that authorization failures on an already-past-`confirmed` record raise `DuplicateInvocationError` specifically — both were incorrect assumptions about pre-existing, correct behavior (hash excludes `request_id` by design; a `wrong_state` classification is equally valid and arguably more precise), fixed by correcting the test expectations, not the implementation.

## Limitations, Restated

Scoped to one local machine, multiple cooperating Python processes, one shared SQLite file. Not claimed: distributed exactly-once execution, multi-machine coordination, protection across different database files, protection against manual database tampering, or crash-safe knowledge of whether a real GAUSS process actually launched near the invocation boundary (scenarios 2 and 3 are indistinguishable by design). No automatic repair, retry, or rerun exists anywhere. No conversational, agent, or workflow integration was added or attempted.
