# v0.60.0 - Repair Draft Review and Approval

## Release Goal

Implement Phase 3 of `planning/v0.58.0-repair-application-safety-design.md`: a draft-review and approval workflow. This milestone authorizes a specific, immutable `RepairDraft` — nothing more. It does not authorize editing files, patch application, rerunning GAUSS, or repair application.

Clean working tree. `scripts/gauss_repair_planner.py`, `scripts/gauss_repair_approval.py`, and `scripts/gauss_repair_draft.py` unmodified throughout this milestone — confirmed by `git diff --stat` showing zero lines against any of the three at ship time.

## Architecture

```
RepairDraft (gauss_repair_draft.py, v0.59.0)
    -> repair_draft_digest(draft) -> str      (unchanged)
    -> DraftApprovalStore (this milestone, gauss_repair_draft_approval.py)
        .approve(draft, recorded_at) -> DraftApprovalRecord
        .decline(draft, recorded_at) -> DraftApprovalRecord
        .revoke(draft, recorded_at) -> bool
        .get_decision(draft) -> DraftApprovalRecord | None
```

`scripts/gauss_repair_draft_approval.py` follows the exact architectural discipline `gauss_repair_approval.py` established for strategy-level approval: it imports only `gauss_repair_draft` (for `RepairDraft` and `repair_draft_digest`), never `gauss_repair_planner.py` or `gauss_repair_approval.py`, and never any execution/workspace/orchestration module. It performs zero I/O and holds exactly one piece of state — an in-memory `dict[str, DraftApprovalRecord]` keyed by digest.

## Approval Model

`DraftApprovalDecision`: `approved`, `declined`, `revoked` — a three-value enum, one more than strategy-level `ApprovalDecision`'s two. This is deliberate: the milestone's own instructions listed `approved`/`declined`/`revoked` as three states to support, not two states plus a delete operation.

`DraftApprovalRecord` (frozen): `decision`, `draft_digest`, `recorded_at` (caller-supplied clock value, never computed internally), `repair_draft_id` (informational only — see "Binding" below), `safe_to_apply` (always `False`), `safe_to_prepare_draft` (always `False`), `approval_boundary` (one of two fixed strings, depending on whether the current decision is an approval or not).

**Binding.** The approval binds only to `repair_draft_digest`. The milestone's own instructions were explicit and repeated: never to `repair_plan_digest`, workspace, path, or execution request. `DraftApprovalRecord` therefore does *not* carry `repair_plan_digest`, `workspace_id`, or `relative_path` as fields at all — only `repair_draft_id` (the draft's own opaque instance identifier, informational, never used for lookup) is included, to avoid any appearance that those excluded dimensions play any role in matching. This is checked directly: `test_12_binding_is_draft_digest_only_not_plan_digest` and `test_13_binding_is_draft_digest_only_not_workspace_or_path` construct drafts that share every field except one of the excluded dimensions and confirm the approval store treats them as genuinely different, unrelated digests.

Note that this binding is already maximally strict in a structural sense: `repair_draft_digest` is computed over the draft's *entire* content, which itself includes `repair_plan_digest` and the full `source_identity` (workspace, path, hash, ...). So "bind only to draft_digest" does not mean those other values are ignored — it means they influence the *one* digest a decision is keyed on, rather than being independently checked as additional matching criteria the way, for example, a compound key would work. A single, holistic content hash rather than several independently-verified fields is the design`gauss_repair_planner.repair_plan_digest`/`gauss_repair_approval.RepairApprovalStore` already established, applied consistently here.

## Revoke: A Deliberate Evolution

Strategy-level `RepairApprovalStore.revoke(...)` (`v0.57.0`) deletes a record outright. This milestone's own instructions list `revoked` as a first-class supported *decision value*, not merely an action — so `DraftApprovalStore.revoke(...)` instead **transitions an existing active record to `REVOKED` in place**, preserving it as history rather than erasing it. A `REVOKED` record does not block a fresh `approve`/`decline` call for the same digest (only an *active*, i.e. approved or declined, record does) — so the practical effect on the caller (revoke frees the digest for a new decision) is unchanged from the strategy-level precedent; only the bookkeeping differs (preserved history vs. deletion). `test_06_approve_after_revoke_succeeds` confirms the freed-digest behavior directly; `test_03_revoke_transitions_in_place` confirms the record itself survives with `decision == "revoked"`.

## Duplicate and Conflict Handling

`DraftApprovalConflictError` is raised whenever `approve`/`decline` is called against a digest that already has an *active* record — covering both the duplicate case (recording the identical decision twice) and the conflicting case (declining an already-approved draft, or vice versa) with the same underlying check and exception type. Both scenarios are tested as explicitly named, separate cases (`test_07_duplicate_approval_raises_conflict`, `test_08_conflicting_decision_raises_conflict`) per this milestone's own testing requirements, even though the code path is shared — the distinction matters for what a caller experiences, not for how the store is implemented.

## CLI Changes

Three new commands: `approve-repair-draft <draft_digest>`, `decline-repair-draft <draft_digest>`, `show-repair-draft-approval`. All three operate against the adapter's own `last_repair_draft`, requiring the caller to supply the exact current `draft_digest` — a stale or incorrect digest is rejected with the correct current digest shown for guidance, mirroring `approve-repair`'s own established pattern exactly. No `revoke-repair-draft` CLI command was added, consistent with `v0.57.0`'s own precedent of leaving `revoke` at the module/API level only for its first milestone. `reset` clears `last_repair_draft` and creates a fresh `DraftApprovalStore`. Adapter version string bumped to `v0.60.0 alpha`.

## Disclosures

Every draft-approval CLI response includes the fixed boundary text this milestone's own instructions specified nearly verbatim: for an approval, *"The repair draft has been approved. No files have been modified. No repair has been applied. No execution has occurred. Repair Application remains unavailable."* A distinct, non-claiming variant is shown for declined/revoked decisions, so the word "approved" never appears in a disclosure describing a state that isn't actually an approval.

## Recommendation for the Next Milestone

With Phases 1-3 of the `v0.58.0` design now implemented (source identity, draft model, deterministic validation, draft approval), the pipeline has three independent, properly-separated approval layers (strategy, draft) plus everything needed to describe *what* a bounded edit would be — but nothing yet describes *whether the target file's current state still matches what a draft was approved against at the moment of use*. The design's own Phase 4 (a local single-file application prototype) is the literal next phase in sequence, but it is also the first phase capable of writing to a file, and per the design document's own §18 recommendation, that step still needs its own explicit authorization separate from this one. A defensible, safety-first intermediate step worth considering before Phase 4: a **fourth approval layer (application approval)** and the **application-gate check itself** (re-verifying every precondition from the design's §13, including a fresh source-hash comparison) — implemented and tested as pure logic, with the actual file-write transaction (§14) deliberately deferred one milestone further, so the highest-risk single change (the first line of code in this repository capable of writing to a user's file) can be authorized and reviewed in complete isolation from everything that gates it.
