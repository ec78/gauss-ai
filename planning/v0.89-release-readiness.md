# v0.89.0 — Release Readiness: Design

Status: **approved** (2026-10-21, with every §8 recommendation: 1b, 2a, 3a, 4a, 5 yes, 6a, 7 (a) now and (c) before any listing, 8a, 9a, 11-13 yes; 7(b) and 10 still open) and **implemented** the same day (§9 deviations, Aptech's reply and diffs; §10 testing). Aptech's developers answered decision 7(c)'s questions (§9.3). Not yet committed, released or published; live evaluation 80.x has not run. Baseline for every probe and comparison: HEAD `f9f0f07` (v0.88.0 `be3df16` plus the 79.x record).

This is step 3 on the path to MVP agreed on 2026-10-20 (`PROJECT_STATUS.md`, "Later"). The MVP is a publicly available MCP server that a stranger can install, connect and use safely. Step 4 is a round with one or two outside GAUSS testers on a clean install, so this milestone's job is to make that round possible, and to settle the release decisions that the round depends on.

## 1. Why

Until now every user of gauss-ai has been its developer, on one Windows machine, in a repository checkout:
- an editable install;
- a tracked `.mcp.json`;
- `CLAUDE.md` and memory notes loaded into the client's context;
- a local-scope override for the real-GAUSS opt-in;
- docs on disk that the client can read directly.

A stranger has none of these. Live evaluation 79.x showed what that costs: the client read documentation files from disk five times, three of them for content past the 1,500-character excerpt (`planning/v0.88-search-and-grounding-recall.md` §11.6, finding 1). A stranger's client may have no disk access.

| # | Item | Source | Effect today |
|---|---|---|---|
| 1 | Release decisions: "Private Alpha", PyPI, MCP directories, platforms, quickstart, docs posture | `PROJECT_STATUS.md` "Later" | Undecided. Nothing a stranger can install from, and no instructions written for one. |
| 2 | No tool returns more than the excerpt | 79.x finding 1 | `sqpSolveMT`'s return codes and `dllcall`'s Remarks cannot be reached without disk access. `KNOWN_LIMITATIONS.md` says "the full page is one search away", which is wrong. |
| 3 | A `for t` loop makes an earlier `T` untraced | 79.x finding 2 | Valid code is held at `review_required`. Safe direction, not disclosed. |
| 4 | The run path is narrow | `PROJECT_STATUS.md` open product question | 77.x: 6 of 22 snippets reached a run prompt. 79.x: 2 of 9 snippets. Every held 79.x snippet ran correctly in GAUSS. |
| 5 | Small items: idle sessions, stale tool descriptions, and three found while planning | `PROJECT_STATUS.md`; §2.7 | Unbounded session growth; confusing upgrades; a stale plugin version. |

Goals:
- a stranger can go from nothing to a validated, and optionally executed, GAUSS snippet by following the README alone, on Windows or Linux;
- a client with no disk access can read any part of a documentation page through a read-only, page-bounded tool;
- the build that would go to PyPI is checked by tests, and holds only product modules;
- every release decision is made explicitly. Publishing, listing and contacting Aptech stay the user's own actions, after this milestone.

Constraints (all from `CLAUDE.md`, unchanged):
- zero third-party runtime dependencies for the base CLI (the `mcp` extra stays optional and lazily imported);
- no telemetry;
- documentation is never bundled or redistributed;
- `GAUSS_AI_MCP_ALLOW_REAL_GAUSS` never goes in the tracked `.mcp.json`;
- every safety decision stays deterministic.

**This milestone is not intended to change grounding or the generation gate.** No change to `resolve_concepts`, `ground_multi`, aliases or stopwords is planned, and §6.2 proves gate equivalence. One validator change is proposed (§3.7, finding 2). It can only move verdicts toward `handoff_candidate`, so it gets a verdict diff, and every moved row is reviewed.

Out of scope:
- `.. include::` expansion;
- the 74.x/75.x deferrals in `KNOWN_LIMITATIONS.md`;
- MCP sampling;
- a hosted or remote server;
- any widening of the run path (item 4 is laid out in §3.12 for the user's decision only; nothing in §3.1-§3.11 depends on it).

## 2. Investigation findings

All probes ran on 2026-10-21 against HEAD `f9f0f07`, from a `git archive` (asserted to be the module imported), with the published docs copy (`C:/Users/Owner/.gauss-ai/docs`, 1,826 pages). The scratchpad scripts are not committed.

### 2.1 PyPI: the name and what the build produces

- **The name is free.** `https://pypi.org/pypi/<name>/json` returns 404 for `gauss-ai`, `gauss_ai`, `gaussai` and `gauss-ai-mcp`, and so does the `simple/gauss-ai/` index. A 404 does not guarantee that the first upload is accepted, since PyPI also refuses names that are too close to existing projects or are prohibited. Only a TestPyPI upload checks that, and even then it says nothing about PyPI itself.
- **The build works from a clean archive.** setuptools 83, with `pip wheel --no-build-isolation`, and also `build_meta` directly:
  - `gauss_ai-0.88.0-py3-none-any.whl`: 484 KB, 54 entries (48 modules and 6 metadata files), 1.73 MB unpacked;
  - sdist: 557 KB, 62 entries (`scripts/`, `README.md`, `LICENSE`, `pyproject.toml`).
- **The `py-modules` list is complete.** All 48 non-test modules in `scripts/` are listed, and nothing listed is missing. No test file ships in the wheel.
- **Seven of the 48 are developer tools, installed as top-level modules.** A `pip install gauss-ai` puts them all directly into `site-packages` (no package namespace). Product code imports none of these seven:
  - `build_differential_corpus`, `gauss_differential_harness`, `gauss_syntax_mutations` (the v0.77 differential harness);
  - `check_release_readiness`, `check_evaluation_tracking`, `validate_all_evidence`, `validate_lookup_evidence` (repository checks).

  Generic names such as `check_release_readiness` and `validate_all_evidence` can collide with other packages' modules. The 41 product modules carry the `gauss_` prefix, except `command_doc_lookup`.
- **Build warnings.** setuptools 83 warns twice. Both are deprecations, fixed in two lines, and builds stop working on 2027-02-18:
  - "`project.license` as a TOML table is deprecated" (`license = { file = "LICENSE" }`);
  - "License classifiers are deprecated" (`License :: OSI Approved :: MIT License`).

  The fix is `license = "MIT"` (an SPDX expression) plus `license-files = ["LICENSE"]`. The METADATA `License:` field currently holds the whole license text.
- **The long description is the whole 655-line `README.md`.** On PyPI:
  - its relative links (`docs/…`, `planning/…`) break;
  - "Current Alpha Status" still describes v0.75.0;
  - the first screen is about the repair pipeline, not the MCP server.
- **Runtime data outside the modules.** `gauss_code_execution`, `gauss_environment_check` and `gauss_package_inspection` look for `schemas/*.json` at `repo_root()`. `gauss_orchestration_state_store.default_db_path()` points at `<repo_root>/.gauss_orchestration_state/`. In a wheel install, `repo_root()` is the parent of `site-packages`. Every product path is safe, though:
  - schema validation runs only when the file exists, in self-tests;
  - the CLI, REPL and MCP paths build their state store in a temporary directory;
  - only the state store's own `__main__` uses the default path.

  So nothing in the wheel breaks without these files. They are a latent trap for the future, not a defect today.
- **A fresh install works.** The wheel was installed with `[mcp]` into a new venv, with `HOME`/`USERPROFILE` set to an empty directory:
  - `gauss-ai version` and `gauss-ai doctor` run, with the expected WARNs for docs, executable and workspace;
  - over stdio, an MCP client sees 9 tools, and `gauss_session_start` and `gauss_search_docs` return the "run `gauss-ai docs fetch`" hint.

  The `mcp` extra brings 30 distributions (79 MB, `pywin32` included on Windows). The base install brings none.
- **The plugin manifest is stale.** `.claude-plugin/plugin.json` says `"version": "0.82.0"`, and no test checks it against `pyproject.toml`.

### 2.2 MCP directories: what each requires

- **Official MCP Registry** (`registry.modelcontextprotocol.io`; the docs say it is "currently in preview. Breaking changes or data resets may occur"):
  - it hosts metadata only, and the package must already be on PyPI;
  - a `server.json` with `name`, `description`, `version`, `repository` and `packages: [{registryType: "pypi", identifier: "gauss-ai", version, transport: {type: "stdio"}}]`, plus optional `environmentVariables`;
  - with GitHub authentication, `name` must be `io.github.ec78/<server>`;
  - for PyPI, ownership is proven by the string `mcp-name: io.github.ec78/gauss-ai` in the package README. It may sit in an HTML comment;
  - publishing uses the `mcp-publisher` CLI (`login github`, then `publish`).

  Everything except the publish itself can be prepared in-repo.
- **Claude Desktop extensions (MCPB) and Anthropic's directory:**
  - Anthropic's MCPB page says "Desktop extension listings in the directory are deprecated, and the directory no longer accepts MCPB submissions". A local server reaches the directory only inside a **plugin**;
  - a user can still install an `.mcpb` file by hand;
  - an MCPB `python` server must bundle all its dependencies (`server/lib` or `server/venv`; here 79 MB and platform-specific), or use the `uv` server type (manifest 0.4+), where the host installs from `pyproject.toml`;
  - Claude Desktop runs on `darwin` and `win32` only.
- **The plugin directory** (claude.ai/directory/manage). The pre-submission checklist matters here, because this repo already ships `.claude-plugin/` at its root:
  - the plugin folder is what installs, and "everything the plugin runs has to be inside it";
  - more than 512 files, or any file over 256 KiB, holds the plugin for a reviewer. The repository root has 1,244 tracked files;
  - a local server should be started by "running a file in the plugin". The current `.mcp.json` runs `gauss-ai-mcp` from `PATH`, which assumes a separate `pip install`;
  - a `uvx` launcher must be pinned to an exact version (`uvx --from "gauss-ai[mcp]==0.89.0" gauss-ai-mcp`), and is then always held for a reviewer ("Runs a pinned npx or uvx package");
  - also required: a README of at least 40 words, a license, a data-handling questionnaire, a security scan, and a public repository before going live.

  So a listing needs a dedicated, small plugin folder and a PyPI package first.
- **Smithery:** a local stdio server is published as a pre-built `.mcpb` bundle (`smithery mcp publish ./server.mcpb -n org/server`). The URL option requires a hosted Streamable-HTTP server. Either way it needs the MCPB work above.

Conclusion: all three directories sit downstream of a PyPI package, and two of them also need MCPB or a dedicated plugin folder. None is needed for step 4, where testers get a link.

### 2.3 What is actually Windows-specific

- **The test suite on Linux.** 47 of the 48 test files were run under WSL Ubuntu 24.04 (Python 3.12.3), from the same clean archive, each with its own empty `HOME`:
  - **46 pass.** One of them, `test_gauss_mcp_server.py`, skips without the extra; it passes 36/36 once `[mcp]` is installed into a Linux venv;
  - **1 fails:** `test_gauss_runtime_orchestration.py` `test_74`, one check out of 95 functions. Its fixture reports an output file as `C:\example\work\gauss_output.txt`, and on POSIX `Path(...).name` does not split on `\`. A real Linux GAUSS reports POSIX paths, so this is a fixture's portability, not a product defect;
  - `test_gauss_ai_packaging.py` (slow, builds a venv) was not run on Linux. It already branches on `sys.platform`.
- **CI does not run the test suite at all.** `.github/workflows/release-readiness.yml` runs only `check_release_readiness.py` (evidence and tracking checks), on `ubuntu-latest`, Python 3.11. So Python 3.10, the declared minimum, has never been tested, and neither has macOS.
- **Product code is mostly portable already:**
  - paths use `pathlib` and `Path.home()`. The config lives in `~/.gauss-ai/`, docs in `~/.gauss-ai/docs/`;
  - every executable check accepts `tgauss` or `tgauss.exe` (6 sites);
  - `check_accessible` uses `os.access(X_OK)` off Windows;
  - `subprocess.run` is used without a shell;
  - `gauss_environment_check.detect_platform` knows `windows`/`macos`/`linux`/`wsl`, with location templates for each.
- **What is Windows-only is evidence, not code:**
  - every real-GAUSS run so far is GAUSS 26.1.x `tgauss.exe -b` on Windows;
  - the macOS (`/Applications/GAUSS{v}.app/Contents/MacOS/tgauss`) and Linux (`/opt/gauss{v}/tgauss`) discovery templates are unverified guesses, as the module itself says;
  - `gauss_differential_harness` refuses non-Windows on purpose (`_VERIFIED_PLATFORM`), but it is a dev tool (§2.1);
  - the help strings, the README and `docs/alpha-installation.md` speak in `C:\gauss26\tgauss.exe` terms.
- **The classifier `Operating System :: Microsoft :: Windows`** describes where real execution was verified, not where the package runs.

### 2.4 The quickstart a stranger would need

The README has no such path today. "Installation" says `pip install -e .`, which needs a checkout. "First Time?" leads with the repair pipeline. The MCP setup is in `docs/mcp-server.md`, which also says `pip install -e ".[mcp]"`. The steps a stranger needs, each checked in §2.1 except where noted:
1. **Install:** `pip install "gauss-ai[mcp]"` (or `pipx`/`uv tool install`). `gauss-ai version`.
2. **Docs:** `gauss-ai docs fetch`. It downloads about 8 MB (1,826 pages) and sets `docs-root`. `gauss-ai doctor`.
3. **Connect:**
   - Claude Code: `claude mcp add --transport stdio gauss-ai -- gauss-ai-mcp`;
   - Claude Desktop: an entry in `claude_desktop_config.json`. Desktop's `PATH` may not include Python's `Scripts`/`bin`, so it needs the absolute path to `gauss-ai-mcp` (not verified here; §7 checks it);
   - then `gauss_session_start` in a fresh conversation.
4. **Real GAUSS (optional):** `gauss-ai config set gauss-executable <path to tgauss>`. Then add `GAUSS_AI_MCP_ALLOW_REAL_GAUSS=1` to the server's launch environment, which is the operator's opt-in:
   - Claude Code: `-e GAUSS_AI_MCP_ALLOW_REAL_GAUSS=1` on `claude mcp add`, at user or local scope;
   - Desktop: the entry's `"env"`.

   Confirm with `real_gauss_allowed: true`, which still does not prove the executable launches. 76.x showed how this goes wrong (the override under the wrong project key), so the README must say how to check it.
5. **Upgrade:** stop the running server (on Windows, a running `gauss-ai-mcp.exe` locks the reinstall), upgrade, restart the client, and start a fresh conversation. The stale-tool-description problem below is why the last step matters.

### 2.5 The docs posture

- **No license.** The GitHub API reports `aptech/docs` (public, pushed 2026-10-21) with `license: null`. So the default is all rights reserved; there is no grant to redistribute.
- **docs.aptech.com's `robots.txt`** is Cloudflare's managed content-signals preamble with **no directive lines at all**: no `User-agent`, no `Content-Signal`. By its own clause (c), the operator "neither grants nor restricts permission via content signal". The preamble defines `ai-input` as "inputting content into one or more AI models (e.g., retrieval augmented generation, grounding …)". That is exactly what gauss-ai's MCP excerpts do. Today no signal is set; if Aptech ever sets `ai-input=no`, gauss-ai's use would be the reserved use.
- **The current posture holds up:**
  - each user downloads the docs from Aptech's own public site, on an explicit command;
  - the user agent identifies gauss-ai (`gauss-ai/<v> (+https://github.com/ec78/gauss-ai)`);
  - nothing is bundled (§2.1: the wheel has no docs);
  - retrieval is local.

  A public release raises the stakes, though: many strangers would fetch the whole site, and the product's purpose is model grounding.

### 2.6 Finding 1: content past the excerpt

- **Re-measured over the docs.** Raw pages: median 1,675 characters, p90 5,470, p99 21,412. 1,043 of 1,826 pages exceed 1,500, 283 exceed 4,000, and 112 exceed 8,000. The outlier is `ge/api-reference.rst`, at 2,760,852 characters. Sections (by RST heading; 9,628 of them): median 268, p95 1,919, p99 9,570. 731 sections exceed 1,500, 110 exceed 8,000, and 61 exceed 16,000. `Remarks` (1,074 pages): median 331, and only 7 exceed 4,000.
- **The two 79.x cases:**
  - `dllcall.rst` (5,308 characters): sections Format 889, Remarks 2,328 and Performance Optimization 1,552. The excerpt stops 300 characters into Remarks.
  - `sqpsolvemt.rst` (9,932 characters): Format 5,918, Remarks 3,064. **The return codes are lost by extraction, not by the budget.** Lines 78-86 (`:0: normal convergence.` … `:8: function complex.`) are a nested field list inside the `out` description. `command_doc_lookup.py` lines 271 and 301 skip every indented line that starts with `:` inside a function block, so the excerpt ends `out.retcode - return code:` and then `:rtype out: struct`.
- **The class is wide.** 512 pages have indented field-list lines whose name is not a `param`/`type`/`return`/`rtype` role (1,453 lines; an upper bound, since some sit outside function blocks). Examples: `olsmt` 21, `gmmFit` 20, `glm` 20, `tsmt/varmafit` 18. These are mostly value lists: return codes, option codes, flags.
- **What this rules out:**
  - **A larger excerpt bound alone does not fix `sqpSolveMT`,** because the content never reaches the excerpt. With a larger bound, `dllcall`'s Remarks would show, but not the return codes.
  - **Fixing the extraction** is a change to `command_doc_lookup.py`'s signature parsing (lines 271 and 301 are on the `:param`/`:return` path). CLAUDE.md requires an all-pages signature diff and a verdict diff for that, as in v0.82.0, where one fix moved 131 signatures. That is a milestone of its own.
- **A raw-section read avoids both.** It serves the page's own `.rst` text, sliced by heading, without going through extraction. Nothing it returns feeds grounding, the gate or a verdict.
- **Side finding (§3.9):** `gauss_search_docs` takes its own `docs_root` argument and ignores the session's. A client that set `docs_root` in `gauss_session_start` gets grounded validation but ungrounded search (reproduced: `docs_root_configured: false` from search in a session started with `docs_root`). Today this only bites when there is no config, since `docs fetch` writes the config. A stranger who points `docs_root` at a checkout would hit it.

### 2.7 Finding 2 and the small items

- **Finding 2 reproduced at HEAD:**

  | Program | Verdict |
  |---|---|
  | `T = 200; e = rndn(T, 1); print meanc(e);` | handoff_candidate |
  | the same + `for t (1, 3, 1); endfor;` after | review_required (`rndn`: `argument_untraced`) |
  | `for t …; endfor;` before `T = 200; …` | review_required (same) |
  | the same + `for i (1, 3, 1); endfor;` after | handoff_candidate |

  The cause is `_governing_assignment`. It refuses whenever any statement anywhere writes `name` in a way it does not model (`other_write_res`: member writes, multi-target writes, a `for` header, `clear`), with no regard to position. A `for t` header **after** a call at block depth 0 cannot change the value the call receives. A header before it, or one around the call, might, depending on GAUSS's loop-variable scoping. The 79.x spot checks p1 and p2 say the counter is local to the loop, but this plan does not rely on that.
- **Idle sessions.** `_sessions` and `_repair_sessions` are plain dicts with no cap and no expiry. Cleanup happens only on close or at exit, through `atexit`. A long-running server (one per Claude Code window) accumulates sessions. Each holds up to 8 stored `validation_id`s with their code, and a repair session holds a workspace on disk until close. Not a safety issue (an expired session approves nothing), but a resource leak a stranger would never notice. The server already has an injectable `_clock`.
- **Stale tool descriptions.** Claude Code keeps an old description for a tool whose name did not change across an upgrade (cosmetic, per `PROJECT_STATUS.md`). Since v0.87.0 it is no longer cosmetic: a client using a pre-0.87 `gauss_execution_decide` description omits `request_id` and gets `request_id_required`. The error does say what to send. `gauss_session_start` reports no server version, so neither the user nor a bug report can see the mismatch.
- **Tool annotations.** No tool declares MCP annotations (`readOnlyHint`, `destructiveHint`, …; the `annotations` field is `None` on all 9). Clients use these hints to decide what to auto-approve. A wrong hint is worse than none, and a `readOnlyHint` on `gauss_execution_decide` would be wrong. Correct hints are cheap:
  - read-only: search, validate, session start/close, prepare, and the new read tool;
  - not read-only: decide (it runs GAUSS) and the repair tools (they write in a workspace).

### 3.2 Platforms and CI

The release-readiness job is unchanged. Tests stay network-free; only `pip install` touches the network, in CI.

Real-GAUSS execution is verified on Windows (GAUSS 26.1.x) only. On Linux and macOS the `tgauss` path is implemented but unverified, and reports from users are welcome. Help strings show `tgauss` or `tgauss.exe`, not a `C:\` path.

The discovery templates, the executable checks and the differential harness's Windows-only refusal stay as they are. Without a GAUSS install on Linux or macOS, there is no evidence to change them with.

### 3.6 `gauss_read_doc`: a read-only, page-bounded section read (finding 1)

A new MCP tool. A CLI command is not needed: CLI users have the files.

```
gauss_read_doc(page, section=None, offset=0, docs_root=None, session_id=None)
```

- **`page`** is a citation exactly as `gauss_search_docs` returns it (`sqpsolvemt.rst`, `tspdlib/docs/tspdlib-landing.rst`). It is resolved under the docs root and refused unless:
  - it is relative;
  - it ends in `.rst`;
  - it has no `..` segment;
  - its resolved real path (symlinks followed) stays inside the resolved docs root;
  - it is an existing file.

  These are `gauss_docs_fetch.py`'s untrusted-name rules, reused, not rewritten. A refusal names the rule and reads nothing.
- **Without `section`,** it returns the page's outline: `title`, `sections: [{heading, level, chars}]` and the total size. Nothing else.
- **With `section`** (a heading, case-insensitive; first match; `Remarks`, `Format`, …), it returns that section's **raw RST source**, verbatim, from its heading to the next heading of the same or higher level. At most `READ_DOC_MAX_CHARS = 8000` characters are returned per call, starting at `offset`, with `next_offset` when more remains.
  - 8,000 covers the p99 section (9,570) in two calls and almost every section in one.
  - A continuation is a new call, never a larger answer, so even `ge/api-reference.rst` is read in bounded pieces.
  - `section="*"` reads the whole page under the same bound and paging.
- **Section boundaries** come from a new heading scanner over the raw lines (underline-only and overline RST titles). It does not use `command_doc_lookup.iter_headings`, because sharing that would tie this tool to the extraction code that decision 11 of v0.88 froze. §6.1 tests that sections partition the page exactly.
- **Boundaries:**
  - local and read-only: no network, no write, no model;
  - the output is never a grounding input, so it cannot change `grounding_status`, the gate or any verdict, and an AST check in §6.4 shows those paths unchanged;
  - it reads only the user's own downloaded copy, so it is the same posture as search excerpts (§3.5);
  - without a docs root, it returns the `docs fetch` hint, like search.
- **Discoverability.** Each `gauss_search_docs` source gains a fixed `read_hint` string ("call gauss_read_doc with this citation to read a section in full"), and the tool description names the 79.x cases (return codes, Remarks). The server instructions add one clause to the recommended flow.
- **`KNOWN_LIMITATIONS.md`:** "The full page is one search away" becomes "A long page's excerpt is cut, and some value lists (for example, `sqpSolveMT`'s return codes) are dropped by extraction; `gauss_read_doc` returns any section verbatim." This sentence is corrected whichever option decision 8 picks.

### 3.7 Finding 2: position-aware `for` refusal

In `_governing_assignment`, a `for`/`threadfor` header that writes `name` stops being a refusal when both of these hold:
- the header's statement starts after the call position;
- the call itself sits at block depth 0.

Every other case still refuses, exactly as today:
- a header before the call;
- a header around the call;
- any call inside a block, since a loop's back edge can run a later statement first.

The change uses only the statement positions and depth tracking the function already computes. No new lexing, and no regex over raw text.
- **Expected effect** (§2.7 table): only the "for t after" shape moves, from `review_required` to `handoff_candidate`; "for t before" stays.
- **Spot checks** before implementing: `tgauss.exe -b` from a scratch directory, for "after", "before" and "around" with `T`/`t`, and `rows(e)` printed. The results are recorded in the planning doc's §9 (implementation record). A disagreement with the expected GAUSS behavior drops the change to "disclose only".
- **Wider variant (decision 9b).** Apply the same "after a depth-0 call" rule to all of `other_write_res` (member writes, multi-target writes, `clear`). This plan recommends the narrow version: it is the measured case.
- **`KNOWN_LIMITATIONS.md`** (v0.89.0 paragraph): a `for` counter, or another unmodelled write, before or around a call still makes a same-named variable untraced (GAUSS names are case-insensitive).

### 3.8 Idle-session eviction

`SESSION_IDLE_SECONDS = 8 * 3600` and `MAX_SESSIONS = 64`, for chat/validation sessions and repair sessions alike. At the start of every tool call, a sweep:
- closes each session idle longer than the bound. A repair session closes through the same path `gauss_repair_close` uses, so its workspace cleanup is unchanged;
- if the count still exceeds the cap, closes the least recently used.

The sweep is deterministic and uses the existing injectable `_clock`, made monotonic for this purpose. A call on an evicted id returns `session_expired`, with the idle bound and "start a new session". An expired session's pending request and `validation_id`s die with it, and they never approve anything. `docs/mcp-server.md`'s "There is no idle eviction" is replaced.

### 3.12 The run path: options only (open product question)

**Evidence.** 77.x: 6 of 22 snippets reached a run prompt. 79.x: 2 of 9 snippets with code, and every one of the other 7 (`review_required`) ran correctly in real GAUSS. The 79.x causes were:
- `control_flow_block` (a loop body);
- structures and `sqpSolveMT`;
- a plot;
- untraced arguments, since expressions are never evaluated.

**What protects the user today**, separately from the readiness verdict:
- the system-statement registry: any OS, process, file, directory, web or database statement makes code `not_ready`;
- an unknown function makes code `not_ready`;
- a digest-bound, single-use human approval of the exact code;
- a temporary working directory, deleted afterwards;
- the session timeout.

`handoff_candidate` adds evidence of *likely correctness* on top of these. It is not the safety boundary.

The constraint involved is `CLAUDE.md`: generated code "never executes except through the controlled execution handoff (deterministic `HANDOFF_CANDIDATE` verdict + explicit … approval)".

| Option | What changes | Safety implications |
|---|---|---|
| **A. Validation-first** | Nothing in code. The MVP is pitched as "search the docs, validate GAUSS code deterministically; running is offered when the evidence is strongest". The README says plainly that most real code is `review_required` and why. | No constraint change. Users run review_required code in their own GAUSS, outside gauss-ai, with the verdict as advice. The narrow run path stays a disclosed limitation. |
| **B. Widen within the constraint** | More deterministic coverage, so more code reaches `handoff_candidate`: for example, category/shape inference for a small expression grammar (`x'x`, products of known shapes, `rndn(n, k)`), or a modeled simple `for` body instead of a blanket `control_flow_block`. Each rule needs `tgauss.exe -b` provenance, as today. | No constraint change. Validator complexity grows, and each new rule is a new place for a wrong `handoff_candidate`. The consequence of a wrong one is a GAUSS error that the handoff reports, not I/O, since the registry still blocks I/O. It is a series of milestones, each with a verdict diff. |
| **C. Let `review_required` reach the approval prompt** | The prompt for review_required code states the reasons and coverage gaps verbatim ("gauss-ai could not verify: …"), and the user approves or declines as today. `not_ready` never reaches a prompt. | **Changes the project-wide constraint.** The I/O exposure is unchanged: both states require documented calls and pass the same registry, so the registry's completeness is the barrier in both cases, as it already is. What grows is the code that runs while semantically unverified: wrong results, GAUSS errors, long loops bounded only by the timeout. The approval becomes the only gate on correctness, which weighs more on prompt wording and on clients relaying faithfully (the v0.87.0 binding stays). |
| **C′. C, restricted by cause** | Only some review_required causes may reach the prompt (for example `control_flow_block` and `argument_untraced`, but never an unverified documented precondition such as `invpd` SPD or `inv` singularity). | As C, but a known-risk class (a violated or unverifiable precondition) never runs. It adds a cause allowlist that must itself be maintained deterministically. |

Combinations are possible: A now, with B or C′ as later milestones. No recommendation is made here (decision 10).

## 5. Known limitations this design accepts

- **Real-GAUSS execution is verified on Windows only.** Linux and macOS run search, validation and the server (CI), but the `tgauss` launch path and the discovery templates there are unverified.
- **`gauss_read_doc` returns raw RST,** directives and roles included (`:func:`, `.. list-table::`), not rendered text. Models read RST well, and rendering would be a second extraction path.
- **Extraction still drops nested field lists** in excerpts and signatures (512 pages, upper bound); the read tool is the way around this.
- **Section lookup takes the first heading that matches.** A page with two "Examples" headings needs `section="*"` and paging.
- **Eviction can drop a pending prompt** after 8 idle hours. The user prepares again.
- **The developer modules are no longer installed;** contributors run them from a checkout.
- **The wheel still installs 41 top-level modules** (no package namespace); only `command_doc_lookup` lacks the `gauss_` prefix.
- **Directories are deferred,** so step-4 testers get a link and an install command, not a listing.
- **The run path stays as narrow as it is today** unless decision 10 changes it.
