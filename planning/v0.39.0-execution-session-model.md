# v0.39.0 Execution Session Model — Planning

## Scope

`v0.39.0` defines, in detail, the smallest execution-session abstraction needed to support future persistence safely — resolving `v0.38.0`'s open "session vs. instance vs. request identity" question, specifying a session-only state machine, a confirmation-binding contract, a serializable representation, and a proposed API surface for a future `scripts/gauss_execution_session.py`.

**This milestone is design-only, exactly like `v0.38.0`.** No module is created. `scripts/gauss_execution_session.py` does not exist after this milestone; this document specifies what it *would* contain, precisely enough that a future, separately authorized implementation milestone can build it without re-deriving these decisions. This mirrors Task 6's own framing ("Plan a future module ... Use in-memory storage only if implementation is later approved") and Task 9's ("Do not create tests yet") — both describe work for a later milestone, not this one.

**Explicitly not implemented by `v0.39.0`:** database storage, distributed workers, cross-process execution, background jobs, agent handoff, production persistence, automatic execution, the `scripts/gauss_execution_session.py` module itself, and its tests.

## Identity Model

`v0.38.0` named the open question ("session vs. instance vs. request identity") without resolving it. This milestone resolves it: **three separate concepts, three separate identifiers, never collapsed into one.**

### Execution Request

Represents user intent, code/context, execution parameters, and safety assumptions — i.e., conceptually the same thing `gauss_runtime_orchestration.CanonicalExecutionRequest` already is. This model does not redefine it; it references it.

Fields (a session-layer *projection*, not a new schema):

- `request_hash` — the existing 12-field SHA-256 fingerprint (`compute_request_hash`), unchanged.
- `plan_digest` — the digest the displayed plan was confirmed against; today identical to `request_hash` (per `v0.37.0`'s `ExecutionProposal.plan_digest`), kept conceptually distinct per `v0.38.0`'s own reasoning.
- `code_reference` — a `code_digest` (SHA-256 of inline code, per `gauss_orchestration_state_store.digest_code(...)`), **never raw code**. A session never carries a second copy of the code — this is a reference to evidence that a specific code text was what was hashed, not a way to reconstruct it.
- `environment_reference` — the `EnvironmentSummary` shape already defined in `gauss_runtime_orchestration.py` (`executable_path`, `gauss_version`, `platform`, `detection_provenance`), unchanged.
- `execution_parameters` — the remaining hash-included fields relevant to a session's own bookkeeping (`working_directory`, `output_directory`, `timeout_seconds`, `expected_input_files`, `expected_output_files`, `required_packages`, `allow_output_files`) — carried as metadata, not re-hashed independently (the existing `request_hash` already covers them).

**Immutable once frozen**, exactly like `CanonicalExecutionRequest` today. A session never mutates an Execution Request's fields; a change always produces a new request (new hash), never an in-place edit.

### Execution Session

Represents the lifecycle of a *confirmed* request — the identity a conversational agent, a future worker, or an operator hands across a process/turn boundary.

Fields:

- `execution_session_id` — a new, separate identifier (see "Resolved: Session ≠ Instance" below), generated once per confirmed request, stable for that request's entire lifecycle.
- `request_hash` — copied from the Execution Request at session-creation time; immutable thereafter.
- `confirmation_state` — whether/how confirmation was recorded (mirrors `gauss_runtime_orchestration.ConfirmationStatus`: `none`/`requested`/`accepted`/`rejected`/`stale`/`invalidated`/`consumed`/`expired` — reused, not reinvented).
- `expiration_state` — derived from `expires_at` versus the current wall clock; not a separately stored enum value, to avoid two sources of truth about whether a session has expired (see Session State Model).
- `ownership_metadata` — an opaque owner/context identifier (unchanged from `v0.38.0`'s deliberately-undesigned ownership concept; see Non-goals).
- `created_at` — session-creation timestamp (store-computed, not caller-supplied, matching `v0.36.0`'s existing wall-clock discipline).
- `current_lifecycle_status` — one of the six session states defined below.

### Execution Instance

Represents **one execution attempt** against a confirmed session — the same role `gauss_runtime_orchestration.OrchestrationRecord`'s `helper_invocation_id`/`execution_result_reference` already play at the controller layer, projected into the session model's own vocabulary.

Fields:

- `instance_id` — a new identifier scoped to one attempt (maps naturally onto the existing `helper_invocation_id`/`invocation_id` concept already produced by `MockOrchestrationInstance.invoke(...)`/`OrchestrationStateStore.authorize_invocation(...)`).
- `session_id` — the owning `execution_session_id`.
- `start_time` / `end_time` — wall-clock bounds of this specific attempt.
- `execution_result_reference` — a pointer to a result record matching `schemas/gauss_code_execution.schema.json`'s shape (`execution_status`, `exit_code`, `output_files` metadata, etc.) — never the raw result embedded inline, never `stdout`/`stderr` text.
- `status` — the instance's own outcome (`completed`/`failed`/`timed_out`/etc., reusing the schema's `execution_status` enum — not a new taxonomy).

### Why these must remain separate

1. **Cardinality differs.** One Execution Request may (in principle, per `v0.35.0`'s `test_84`/`v0.36.0`'s equivalent finding) be confirmed and executed as two *independent* sessions if two independent proposals happen to share an identical `request_hash` — session identity is not request identity. One Execution Session may, in a future retry-after-failure design, have more than one Execution Instance recorded against it over time (today's `v0.31.0`-`v0.37.0` controller permits **at most one** instance per confirmed request — this document does not propose relaxing that; it only notes that a session/instance split is what *would* make a future, separately-authorized "record more than one attempt against one durable session" design possible without redefining "session," should that ever be scoped).
2. **Mutability differs.** A Request is frozen at creation. A Session's `current_lifecycle_status`/`confirmation_state` mutate over the session's lifetime (through a small, closed set of transitions — see below). An Instance's `status`/`end_time` mutate only while that one attempt is in flight, then freeze permanently once terminal.
3. **Lifetime differs.** A Request's identity (its hash) is meaningful forever, independent of whether it was ever confirmed. A Session exists only once a request has begun the confirmation lifecycle, and terminates (in the session-state sense) once `ready`/`expired`/`cancelled` is reached — it does not track what happens *during* execution. An Instance exists only for the duration of one execution attempt and is immutable evidence afterward.
4. **Safety boundary differs.** Conflating these — e.g., storing execution-instance status fields (`running`, `completed`, `failed`) *on* the session object — is exactly the mistake Task 3 explicitly forbids, because it would let an execution instance's own transient/terminal status be mistaken for session-level authorization state, potentially making a session look "still good" (or wrongly terminal) based on the wrong layer's data. Keeping them separate is what makes "was this confirmed and not yet consumed" (a session-level question) answerable without also having to interpret "did the underlying GAUSS process succeed" (an instance-level question) — two genuinely different questions with two genuinely different audiences (a confirmation-validity check happens before any instance exists at all).

### Resolved: Session ≠ Instance ≠ `orchestration_instance_id`

`v0.38.0` left open whether `execution_session_id` should equal the controller's existing `orchestration_instance_id` or be a new, separate identifier. **Resolved here: a new, separate identifier**, for three reasons grounded in the model above:

1. `orchestration_instance_id` (in `gauss_runtime_orchestration.py`'s naming) actually corresponds most closely to this document's **Execution Session** concept (one record per confirmed request's lifecycle) — but the word "instance" in that existing name collides with this document's distinct **Execution Instance** concept (one execution *attempt*). Reusing the name across two different concepts in two different documents would be confusing going forward, even though today, incidentally, the controller's `orchestration_instance_id` and this document's `execution_session_id` would map one-to-one.
2. A future Execution Instance concept (a `helper_invocation_id`) already exists as a *sub-record* of an `orchestration_instance_id` in the controller today — meaning the controller's own naming already implicitly distinguishes "the confirmed thing" from "one attempt at invoking it," just without a session-specific vocabulary layered on top. This document's three-identifier model makes that existing, implicit distinction explicit and named consistently.
3. Keeping `execution_session_id` as its own identifier space means a future persistence-layer implementation can choose to map it 1:1 onto `orchestration_instance_id` (the simplest possible mapping, likely the right starting choice for Phase 2 of `v0.38.0`'s implementation phases) without that choice being baked into this document's vocabulary — the mapping is an implementation decision, not an identity-model decision.

## Session State Model

**States** (session-only — deliberately excludes `running`/`completed`/`failed`, which belong to Execution Instances, per Task 3):

- `created`
- `awaiting_confirmation`
- `confirmed`
- `expired`
- `cancelled`
- `ready`

**Allowed transitions:**

```text
created              -> awaiting_confirmation
awaiting_confirmation -> confirmed
confirmed            -> ready
confirmed            -> expired
confirmed            -> cancelled
```

**Forbidden transitions (explicit, matching the task's own list):**

- `expired -> confirmed` — an expired session can never become confirmed again; a new session (new confirmation, new session id) is required.
- `cancelled -> confirmed` — a cancelled session is terminal; it can never be revived.
- **completed instance -> modify session** — an Execution Instance reaching any terminal status (`completed`/`failed`/`timed_out`/etc.) never mutates its owning Session's `current_lifecycle_status`/`confirmation_state`. The session's job ends at `ready` (meaning: validly confirmed, eligible to have an instance created against it); everything that happens to the instance afterward is instance-layer history, not a session-state transition. This is the same separation of concerns as "Why these must remain separate," reason 4, restated as a state-machine rule.
- **changed request -> reuse confirmation** — restated from `v0.38.0` and every prior milestone back to `v0.31.0`: any field change that alters `request_hash` invalidates whatever confirmation existed; there is no transition path from an old session's `confirmed` state onto a new request's hash. A changed request always requires a brand-new session from `created`.

**Where does `queued` (from `v0.38.0`) go?** `v0.38.0`'s state machine included a `queued` state between `confirmed` and `running`, representing "a confirmed session waiting for a worker to pick it up." This document's `ready` state is a deliberate rename/refinement of that idea: `ready` means "validly confirmed and eligible for an Execution Instance to be created against it" — a *session*-level fact — without implying anything about workers, queues, or cross-process handoff, none of which this milestone designs or implements. A future implementation milestone that does design worker handoff may introduce a *separate*, instance-level or infrastructure-level "queued" concept on top of `ready` — but `ready` itself carries no queuing semantics.

## Confirmation Binding

A Session must preserve:

- `request_hash`
- `plan_digest`
- `confirmation_timestamp` — the caller-supplied audit label (never parsed as a real clock value, matching `v0.36.0`'s existing policy).
- `expiration_timestamp` — a store/session-computed wall-clock value, independent of the caller-supplied `confirmation_timestamp`.
- `confirmation_scope` — must equal `request_hash` exactly; this is the field whose equality check *is* the confirmation-binding mechanism, unchanged from `v0.31.0` through `v0.37.0`.

**Rules** (each restates an existing, already-enforced invariant at the controller/workflow layers — this document does not invent new invalidation logic, it names which existing hash-included fields the rule applies to):

- Changed **code** invalidates confirmation — `code` is hash-included.
- Changed **working directory** invalidates confirmation — `working_directory` is hash-included.
- Changed **executable** invalidates confirmation — `executable_path` is hash-included.
- Changed **file-write behavior** invalidates confirmation — `allow_output_files`/`output_directory`/`expected_output_files` are hash-included.
- Changed **timeout policy** *may* invalidate confirmation — `timeout_seconds` is hash-included, so a changed numeric value always invalidates it under the current exact-hash-match design; "may" is used here only to leave room for a future, separately-designed *tolerance* policy (e.g., "a timeout increase alone does not require reconfirmation") that this milestone does not propose and that would need its own explicit review, since it would be the first hash-included field ever granted a fuzzy-match exception.

## Serialization Model

A conceptual, JSON-serializable Session representation (design only — this document does not create a schema file):

```json
{
  "execution_session_id": "es_3f9c1a...",
  "request_hash": "0b8869c7eb686fc561e08e0512ea658834ccda1623cc5b06780998e4b1fc4cd1",
  "plan_digest": "0b8869c7eb686fc561e08e0512ea658834ccda1623cc5b06780998e4b1fc4cd1",
  "code_digest": "fdd92f5fcc387a5146c2ab9ff0ea6697a4c32de8bd83a0b2e0f2b8e31e4b4227",
  "status": "confirmed",
  "created_at": "2026-07-21T00:00:00Z",
  "expires_at": "2026-07-21T00:30:00Z",
  "owner": "opaque-owner-reference",
  "environment_reference": {
    "executable_path": "C:\\gauss26\\tgauss.exe",
    "gauss_version": "GAUSS 26",
    "platform": "Windows",
    "detection_provenance": "direct"
  },
  "confirmation": {
    "confirmed": true,
    "confirmed_at": "2026-07-21T00:01:00Z",
    "session_id_at_confirmation": "s1"
  },
  "latest_instance_reference": {
    "instance_id": null,
    "status": null
  }
}
```

**Do not store:** raw secrets, unnecessary source-code copies (only `code_digest`, never `code`), credentials, license information, sensitive files, `stdout`/`stderr` text, output-file content, raw conversation text. This exact exclusion list mirrors `gauss_orchestration_state_store.py`'s own documented redaction rules — this session model does not loosen it anywhere.

**References versus payload:** every field above is either (a) an identifier, (b) a hash/digest, (c) a status/timestamp, or (d) a *reference* to another record (`latest_instance_reference` points at an Execution Instance; it does not embed that instance's own `execution_result_reference` inline). A session document is a pointer graph, never a payload container — the same principle `v0.38.0`'s "persisted state / transient runtime state / sensitive data" three-way split already established, restated here as a concrete field-by-field example.

## API (Planned, Not Implemented)

A future `scripts/gauss_execution_session.py`'s proposed surface — signatures and behavioral contracts only, for a future, separately authorized implementation milestone to build against. **No code in this file exists as of `v0.39.0`.**

```text
create_session(request_hash, plan_digest, environment_reference, owner=None, clock=...) -> ExecutionSession
    Creates a session in the `created` state. Does not accept raw code, credentials, or
    file content as parameters -- only hashes/digests/references. Raises on a missing
    request_hash or plan_digest.

validate_session(session, *, expected_request_hash, expected_session_id_context) -> ValidationOutcome
    Checks (per Task 7): request_hash matches, confirmation exists, expiration has not
    passed, current_lifecycle_status allows the requested action, ownership rules pass
    (ownership itself remains undesigned -- see Non-goals; this call's ownership check is a
    named hook, not a working implementation). Returns a typed outcome, never a bare bool,
    so a caller can distinguish *why* validation failed (mirrors
    gauss_orchestration_state_store.AuthorizationFailedError's reason_category pattern).

expire_session(session, *, now) -> ExecutionSession
    Transitions confirmed -> expired when `now` is past expires_at. A no-op (returns the
    session unchanged) if the session is not in `confirmed`, or not yet expired -- never
    forces a transition outside the allowed-transitions table.

cancel_session(session, *, reason) -> ExecutionSession
    Transitions confirmed -> cancelled. Refuses (raises, does not silently no-op) from any
    other state, since cancelling a non-confirmed or already-terminal session is either
    meaningless or a caller error that should be surfaced, not swallowed.

get_session_state(session) -> SessionStateSnapshot
    A read-only projection matching the Serialization Model above. Never mutates the
    session it reads.
```

Every function above is presented as accepting and returning **in-memory** values only (per Task 6: "Use in-memory storage only if implementation is later approved") — no database, no file I/O, no network call is proposed in this API sketch. A future implementation milestone remains free to choose whether these functions wrap `gauss_orchestration_state_store.OrchestrationStateStore` (the natural, already-durable, already-redaction-correct choice) or a new, separate in-memory-only structure — this document does not decide that; it only specifies the surface those functions must present regardless of backing storage.

## Validation Rules

A session is valid only if:

- `request_hash` matches the request being acted upon.
- Confirmation exists (`confirmation_state` is `accepted`/`consumed`, not `none`/`requested`/`rejected`).
- Expiration has not passed (`now < expires_at`, computed from a trusted clock, never from a caller-supplied value — matching `v0.36.0`'s existing policy).
- `current_lifecycle_status` allows the requested action (per the Session State Model's allowed-transitions table).
- Ownership rules pass (a named hook per the API above; the rules themselves remain undesigned, per `v0.38.0`'s own deferral and this document's Non-goals).

**Invalid:**

- Stale confirmation (a `plan_digest`/`request_hash` mismatch).
- Modified request (a `request_hash` that no longer matches what the session was created against).
- Expired session (`now >= expires_at`).
- Cancelled session (terminal, `current_lifecycle_status == cancelled`).

Every one of these restates an already-enforced rule at the controller (`v0.31.0`) or durable-store (`v0.36.0`) layer — `validate_session(...)` is proposed as a session-layer *view* of the same invariants, not a new, independent enforcement point that could drift out of sync with them.

## Future Persistence Boundary

Restated from `v0.38.0`, made concrete for the specific fields this document defines:

**Future persistence may store:** session metadata (`execution_session_id`, `status`, `created_at`, `expires_at`, `owner`), hashes (`request_hash`, `plan_digest`, `code_digest`), lifecycle state (`current_lifecycle_status`, `confirmation_state`), and references (`environment_reference`, `latest_instance_reference`, `execution_result_reference` pointers).

**Future persistence should not automatically store:** raw code, raw output (`stdout`/`stderr`/output-file content), user files, credentials, secrets. This is not a new rule — it is the same exclusion list `v0.36.0`'s durable store already enforces and verifies (via its own whole-database-file byte scan), restated here so a future session-persistence implementation is held to the same bar from day one rather than rediscovering it.

## Testing Strategy (Future, Not Created)

Per Task 9, **no tests are created by this milestone.** For a future implementation milestone's own scoping:

**Unit:**
- create session
- validate confirmation
- expire session
- cancel session
- reject changed request

**Security:**
- replay prevention (a consumed confirmation never becomes valid again)
- stale confirmation rejection (`plan_digest`/`request_hash` mismatch)
- ownership mismatch (once ownership rules are actually designed — out of scope here)

**Concurrency:**
- duplicate session creation (two sessions for the same request_hash — legitimate, per `v0.35.0`/`v0.36.0`'s established "content-hash is not instance identity" finding; a future test should confirm the session layer does not accidentally introduce a hash-based uniqueness constraint that would break this)
- duplicate execution prevention (an Execution Instance already exists for a session; a second one must be refused — mirroring the controller's existing `DuplicateInvocationError`)

## Non-goals

Restated from the authorizing task, verbatim in effect: database storage; distributed workers; cross-process execution; background jobs; agent handoff (the *mechanism*, as opposed to the identity model that would support a future one); production persistence; automatic execution; implementing `scripts/gauss_execution_session.py` itself; creating its tests; designing the ownership/permissions model in detail (only a named hook is specified here, matching `v0.38.0`'s own deferral).

## Suggested Task Order (for a future implementation milestone)

1. Implement `ExecutionSession`/`ExecutionInstance` as in-memory dataclasses matching this document's field lists exactly.
2. Implement `create_session`/`validate_session`/`expire_session`/`cancel_session`/`get_session_state` per the API sketch above, backed by plain Python objects only (no store).
3. Add the Task-9 unit/security/concurrency tests against that in-memory implementation.
4. Only then, as a separate, explicitly authorized milestone, decide whether/how to back this with `gauss_orchestration_state_store.py` for real cross-process persistence — the actual gap `v0.38.0` and this document both name but do not close.
