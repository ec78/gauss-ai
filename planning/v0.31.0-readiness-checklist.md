# v0.31.0 Readiness Checklist

## 1. Milestone Scope

**What `v0.31.0` is:** a design-and-mock milestone. It defines the runtime orchestration architecture connecting `v0.30.0`'s user-facing real-execution workflow to the existing, verified `scripts/gauss_code_execution.py` helper, formalizes that architecture into two authoritative contracts (a canonical execution request and a runtime state machine), implements a mock-only, in-memory controller proving those contracts are internally consistent against an injected fake runner, evaluates the *designed* behavior via a new `32.x` benchmark category, and documents all of the above across the repository's user-facing and contributor-facing documentation.

**What `v0.31.0` is not:** it is not real Helper Adapter integration, not a real controller-to-helper connection, not user-facing automatic execution, not durable persistence, not cross-process locking, not production session management, not production script fingerprinting, not cooperative real-process cancellation, not safe output-file content reading, not automatic file cleanup, and not verified GAUSS execution through the orchestration controller. No component described in this checklist has ever imported `scripts/gauss_code_execution.py`, launched a subprocess, or invoked `gauss.exe`/`tgauss.exe`.

**Why readiness can pass without real Helper Adapter integration:** `planning/v0.31.0-runtime-orchestration-design.md`'s own Implementation Phases explicitly sequence this work — Phase 1 (interfaces), Phase 2 (mock controller skeleton), Phase 3 (real Helper Adapter integration), Phase 4 (analysis/reporting integration), Phase 5 (file/session handling), Phase 6 (evaluation/hardening against a real controller). `v0.31.0` completes Phases 1 and 2 plus their evaluation, exactly as scoped. Treating the absence of Phase 3 as a `v0.31.0` failure would penalize the milestone for not doing work it never claimed to do — the Suggested Task Order and Readiness Criteria in the design document both gate Phase 3 on a *separate*, future, explicitly-scoped decision, not on this checklist.

**Which later phase owns production integration:** Phase 3 ("Helper Integration") of `planning/v0.31.0-runtime-orchestration-design.md`'s Implementation Phases, to be scoped as its own future milestone. This checklist does not authorize starting it.

## 11. Contract-to-Implementation Discrepancies

1. **`CanonicalExecutionRequest` has 19 dataclass fields in code, not 18.** Investigated directly (`dataclasses.fields(...)`, executed live). The 19th field is `_frozen`, an internal implementation-only bookkeeping flag supporting the freeze mechanism — it is not one of the contract's 18 conceptual fields, is never hashed, and is never exposed via `to_safe_summary()`. **Not a real discrepancy** — correctly excluded from the contract's field count by design.
2. **State-machine contract §11's lead sentence says "19 categories" but its table has 20 rows.** See §5 above. **Nonblocking documentation staleness** introduced by the (already-approved) Phase 2 transition-18 fix; not in this task's allowed-modify scope for that document; recorded as a follow-up in §13 below.
3. **`FailureCategory` has 22 enum members in code versus 19-20 taxonomy rows in the planning documents.** This is a previously-reviewed, intentional refinement (the mock controller splits "Consent stale" into four finer-grained categories — `confirmation_stale`, `confirmation_invalidated`, `confirmation_expired`, `session_mismatch` — and separately names `confirmation_missing`, `script_identity_untrusted`, `runner_unavailable`, `runner_launch_failure` distinctly, where the taxonomy tables group related outcomes under fewer named rows). No category is missing or contradicted; the implementation is a strict refinement, not a divergence. **Not a new discrepancy** — already documented in the implementation task's own final report.

No other discrepancy was found between either contract and the implementation.
