## Cleanup Summary

### Econometrics operational profile wording

Stale build-status wording was fixed across five passages in `experts/econometrics/OPERATIONAL_PROFILE.md` (Purpose section, Escalation Conditions, Evaluation Criteria, and two entries in "Relationship to Existing Files"). Documented multi-expert routing is now correctly described as completed and evaluated in `v0.9.0` (Multi-Expert Routing benchmarks `16.1`-`16.8`, all passed). No expert behavior — activation triggers, non-activation cases, required inputs/evidence, decision rules, refusal or escalation conditions — changed; only the build-status framing of already-documented content was corrected. Runtime orchestration remains explicitly disclaimed, stated more clearly than before the fix.

### Historical tracking warnings

The two historical evaluation-tracking warnings are preserved, not repaired:
1. The `2.2` coverage row links to a run file (`2026-06-30-code-assistant-manual-run-001.md`) whose own `Prompt ID:` field states `2.3`, a mismatch predating stable Prompt ID assignment.
2. `2026-07-01-code-assistant-smoke-test-v0.3.0.md` predates the Prompt-ID-based tracking system and is intentionally not indexed into it.

Both are now documented in `evaluations/benchmark-coverage.md`'s "Historical Tracking Exceptions" section, with a closing policy statement: historical exceptions may be preserved when rewriting them would distort what was actually evaluated or recorded; they must be documented; the default tracking guard may pass with documented warnings present (a `PASS` never meant "zero warnings," only "zero errors"); `--strict` mode intentionally fails when those warnings are promoted; and new tracking inconsistencies must not be added under cover of this policy. No historical run files were rewritten.

### Benchmark-authoring guidance

Guidance was added to `workflows/manual-evaluation.md` (new section 9, "Benchmark Authoring Guidance"). It warns against hardcoding volatile repository counts (prompt-ID, coverage-row, run-file, index-entry, or warning counts) in expected-behavior text unless a benchmark is explicitly tied to a fixed repository state, and prefers "report live tool output accurately, distinguish errors from warnings" as the expected behavior instead. It uses the real `17.5`/`17.6` precedent (both hardcoded "2 warnings"; the true count was 8 and 12 respectively by the time they were evaluated) and explicitly distinguishes baseline/mid-batch/post-update batch states. It preserves strong expectations for stable facts, exact file paths, and pass/fail behavior — the guidance targets volatile repository-state counts specifically, not precision in general.

### Econometrics knowledge.md disposition

`experts/econometrics/knowledge.md` is now an explicit compatibility placeholder, replacing its prior unexplained one-line stub. It states plainly that `experts/econometrics/BODY_OF_KNOWLEDGE.md` is the active, authoritative knowledge source, and that `knowledge.md` is not a separate or competing source. A repo-wide reference check confirmed nothing depends on the file's prior content — only planning documents discussed its disposition.

### Official package source classification

The evidence schema already supported `official_package_docs`/`official_package_rst` before this milestone; the gap was entirely in `scripts/command_doc_lookup.py`'s classification logic. The tool now classifies a matched file as package documentation if its docs-root-relative path starts with a known GAUSS "Application" (package) directory, derived from the official Applications index (`docs_root/applications.rst`'s own `:link:` targets) — not guessed from command names. `glm` (a top-level, core-docs file) remains `official_docs`/`official_local_rst`, confirmed unaffected. `tscsfit` (`tsmt/tscsfit.rst`) now classifies as `official_package_docs`/`official_package_rst`, confirmed by regenerating its evidence file. The package directory list (`PACKAGE_DOC_DIRECTORIES`) is a hardcoded snapshot of the Applications index and should be refreshed if that index changes; a directory missing from the snapshot falls back to core classification, so a stale snapshot can only under-classify, never mis-classify base GAUSS documentation as a package. This is source classification only, not licensing verification — the Code Assistant must still state a package dependency explicitly whenever it recommends a package-sourced command.

To be explicit about what these results mean: a default **PASS does not mean zero warnings** — it means zero errors, with the 2 (evaluation tracking) and 6 (evidence, across two files) warnings present and accounted for. Evidence validation checks structure only: it **does not prove GAUSS semantic correctness or that any GAUSS code was executed** — a schema-valid evidence file is a claim about documentation shape, not about runtime behavior.

## Important Findings

- Repository hygiene issues can affect evaluation clarity even when core behavior is correct — none of `v0.11.0`'s five cleanup items reflected an actual defect in expert routing, evidence validation, or tracking-guard logic; all were documentation or classification-labeling gaps that could confuse a future reader or evaluator if left alone.
- Documenting historical exceptions is safer than rewriting history — both preserved warnings would have required altering a real historical record (a run file's own `Prompt ID:` field, or forcing a broad smoke test into a schema built for single-Prompt-ID coverage) to make them disappear; documenting them instead preserves an accurate record while still resolving the ambiguity.
- Benchmark prompts should avoid volatile hardcoded counts — demonstrated twice now with real figures (`17.5`/`17.6`), not just as a hypothetical concern; the new guidance is grounded in an actual, dated incident.
- Source authority/source type classification needed code-level handling even though schema support already existed — a schema enum value alone doesn't classify anything; the schema and the tool's classification logic are two separate layers, and this milestone confirmed the gap was entirely in the latter.
- Package classification relies on an `applications.rst`-derived snapshot, not live parsing — a deliberate, documented trade-off (avoids threading `docs_root` through additional function signatures) whose safe-failure direction (under-classify, never mis-classify) was explicitly verified during implementation, not just asserted.
- This audit independently found and fixed additional stale wording beyond the five `18.x`-validated items: `README.md` and `ROADMAP.md` still described `v0.10.0` as the current/in-progress milestone; `KNOWN_LIMITATIONS.md`'s header still said "as of `v0.10.0`"; and `workflows/expert-routing.md` contained three separate stale passages (its Maintenance Notes section, and two "Relationship to Existing Files" entries) claiming `task_modes.md`, `code_assistant_system.md`, and `workflows/code-assistant-response.md` were "not yet updated for multi-expert routing" or that `16.x` was a "future benchmark category" — all of which were completed in `v0.9.0`. All were corrected as part of this task.

## Remaining Limitations

- No runtime orchestration exists anywhere in the expert-routing system; this milestone did not change that.
- Only the GAUSS Language Expert and the Econometrics Expert are operationalized; the Software Engineering, Documentation, and Education experts remain narrative-only.
- `--strict` evidence validation still fails for the two documented HDF5-URI warning false positives (`glm`, `olsmt`) — an accepted, reviewed exception, not a defect to clear before tagging.
- `--strict` tracking guard still fails for the two documented historical warnings (`2.2`/`2.3` mismatch; `v0.3.0` smoke-test file) — also an accepted, reviewed exception.
- The `PACKAGE_DOC_DIRECTORIES` package directory list is a maintained snapshot, not live-parsed from `applications.rst` at lookup time; it should be refreshed if the Applications index changes.
- `experts/gauss-language/knowledge.md` has the identical one-line-placeholder problem as the now-resolved `experts/econometrics/knowledge.md`, and remains unresolved as a separate, explicitly out-of-scope follow-up.
- No CI integration exists for either `scripts/validate_all_evidence.py` or `scripts/check_evaluation_tracking.py`; both remain local-only, manually-run tools.
- No GAUSS execution engine exists; nothing in this milestone changes that.
- Schema validation remains structural (required fields, enum values, types) — it does not and cannot confirm GAUSS semantic correctness or execution.
