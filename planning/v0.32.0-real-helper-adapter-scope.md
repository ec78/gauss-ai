## 1. Milestone Purpose

`v0.32.0` is Phase 3 of `planning/v0.31.0-runtime-orchestration-design.md`'s Implementation Phases: **Real Helper Adapter Integration**. It is the first controlled, real connection between:

- the canonical execution request (`planning/v0.31.0-canonical-execution-request-contract.md`),
- the runtime state machine (`planning/v0.31.0-runtime-state-machine-contract.md`),
- a new Helper Adapter, and
- the existing, verified `execute_gauss_code(...)` (`scripts/gauss_code_execution.py`).

**What this milestone is not:** it is not full user-facing production orchestration. It does not wire orchestration into `workflows/code-assistant-response.md` or `agents/code-assistant/AGENT.md` (that remains later, unscoped work — see §4 and §19). It does not add durable persistence, cross-process locking, cooperative cancellation, output-file content reading, or cross-platform/cross-version support. It proves that the mock controller's proven design (13 states, 18 transitions, the 18-field canonical request, the confirmation model) can drive **one real, controlled, single-process invocation** of the existing helper, with the same safety and consent boundaries the mock controller already enforces — nothing more.

Per `planning/v0.31.0-readiness-checklist.md`'s own verdict, `v0.31.0`'s readiness pass does **not** itself authorize Phase 3; this document is the separate, explicit scoping decision that verdict called for.

## 3. In-Scope Implementation

**This section defines what Phase 3 will implement in a future task. Nothing in this section is implemented by this planning task.**

The minimum viable Phase 3 implementation:

- A dedicated Helper Adapter module or adapter boundary (a single, injectable seam between the orchestration controller and `execute_gauss_code(...)`, mirroring the mock controller's own `FakeRunner` Protocol pattern so the controller's transition logic does not need to change to accept a real adapter — see §19).
- Dependency injection into the existing controller — the adapter is passed into `MockOrchestrationInstance.invoke(...)` (or an equivalent real-adapter-aware successor) the same way a `FakeRunner` is passed today, not hard-imported.
- Projection from the canonical execution request to the verified helper parameters (§6).
- Explicit environment context supplied to every real call — never delegating to the helper's own auto-detection (§8).
- `strict=True` passed on every real call, so the helper never silently re-resolves a different environment than what was shown at confirmation time.
- `allow_network=False` passed explicitly on every real call (the helper's own default; passed explicitly here so the adapter never silently inherits a future default change).
- Continued blocking of GUI `gauss.exe` — the adapter must reject, not merely warn about, an `executable_path` whose basename is not in `{tgauss, tgauss.exe}`, before ever calling the helper.
- Exactly one real helper invocation per confirmed request, enforced the same way the mock controller enforces it today (§9, §10).
- Structural validation of the helper's returned result against `schemas/gauss_code_execution.schema.json` before any downstream use.
- Mapping of the helper's seven verified `execution_status` values into orchestration outcomes (§12) — no new status invented.
- Preservation of the helper's raw structured evidence (`stdout`, `stderr`, `exit_code`, `output_files`, `warnings`, `errors`) unmodified through the adapter.
- No automatic retries on launch failure, timeout, or GAUSS runtime error.
- No automatic reruns — any repeat attempt is a new canonical request with fresh confirmation, exactly as the mock controller already enforces.
- Safe execution-record updates — the same redaction rules `OrchestrationRecord.to_safe_summary()` already implements for the mock controller apply unchanged to a real result.
- Honest user-facing result summaries **at the internal interface level only** — this milestone does not wire a user-facing conversational surface; "honest" here means the adapter/controller boundary never fabricates a result and always surfaces `executed: false` distinctly from `executed: true`, for whatever internal caller consumes it next.

## 7. Script-Path Policy

**Decision: RESOLVED.** Real script-path execution remains blocked in `v0.32.0`. Inline-code requests are the only supported Phase 3 mode.

The mock controller's `SCRIPT_IDENTITY_UNTRUSTED` fail-closed refusal (verified in `submit_for_review()`, tested by `test_07`/`test_37`) is a direct implementation of the canonical request contract's own documented, unresolved gap: `request_hash` fingerprints a script's *path* in script-path mode, not its file *contents*, so a file could in principle be edited on disk between confirmation and invocation without the hash changing. Phase 3 does not resolve this gap — resolving it would require a genuinely new design element (content-based fingerprinting, e.g. a content hash captured at confirmation time and re-verified immediately pre-invocation) that neither `v0.31.0` contract specifies and that this scope document is not the place to invent.

**Decision, explicitly stated:** Phase 3 does not add script-path support. A narrowly scoped content-fingerprinting design would be a **prerequisite for any future milestone** that wants to lift this restriction — not something Phase 3 attempts opportunistically alongside the adapter work. This keeps Phase 3's surface area minimal (inline `code` mode only) and avoids inventing a fingerprinting mechanism under time pressure from an unrelated integration task.

**Explicitly rejected as insufficient:** treating a resolved path, timestamp, size, or `request_hash` alone as proof of unchanged file contents. None of these properties confirms the file's *contents* still match what was shown at confirmation time — the adapter must not adopt any of them as a substitute for real content-based fingerprinting, even informally.

**Required behavior, confirmed as the Phase 3 implementation target:**

- A script-path request fails closed **before** confirmation or invocation — at the same `submit_for_review()`-equivalent point the mock controller already uses, never deferred to a later stage.
- No helper call occurs for a script-path request, under any circumstance.
- Confirmation is not consumed by a script-path refusal — this is a pre-authorization guard failure (§9), identical in kind to every other pre-invocation guard failure.
- The failure is represented distinctly, using `FailureCategory.SCRIPT_IDENTITY_UNTRUSTED` (the same category the mock controller already defines) — never silently folded into a generic "ineligible request" or "unsafe request" category.
- The user-facing (or, for Increment 1's own scope, internal-interface-facing) disclosure states plainly that inline-code execution is the only supported Phase 3 mode, so the refusal reads as a scope boundary, not an unexplained error.

## 8. Environment Binding

The adapter must guarantee, to the extent a single Python process can:

- **Explicit environment context, always.** Every real call supplies `environment_check_result`/`executable_path`/`gauss_version` derived from the confirmed request's `environment_summary` — never omitted, never left to the helper's own auto-detection.
- **`strict=True`, always.** This disables `_resolve_environment_context(...)`'s fallback to calling `gauss_environment_check`'s live detection, closing the determinism gap `planning/v0.31.0-runtime-orchestration-design.md`'s Tool Invocation Boundary already identified.
- **Executable-path identity.** The adapter compares the confirmed `environment_summary.executable_path` against the value about to be passed, immediately before invocation — not merely at confirmation time.
- **Version identity.** Same treatment for `gauss_version`.
- **Architecture or platform identity where verified.** Only the properties `EnvironmentSummary` already captures (`platform`, per the mock controller's existing dataclass) are compared; Phase 3 does not add new environment properties beyond what `v0.31.0`'s contract already defines.
- **Changed or missing environment.** If the executable path no longer exists, is no longer accessible, or its identity no longer matches the confirmed snapshot, the adapter fails closed (`FailureCategory.ENVIRONMENT_MISMATCH`, matching the mock controller's existing category) — no invocation is attempted.
- **Helper re-detection prohibition.** The adapter must never allow a call to reach the helper without `strict=True` and an explicit environment context — this is a hard constraint on every real call, not a default.
- **GUI substitution prohibition.** The adapter independently rejects a non-terminal `executable_path` before calling the helper, in addition to the helper's own refusal (defense in depth, per §6).
- **Fail-closed behavior.** Any ambiguity in environment matching (a filesystem check that errors, an unreadable executable, a value that cannot be conclusively compared) is treated as a mismatch, never as a pass.
- **No cross-platform or cross-version claim.** Phase 3 does not attempt, test, or claim support beyond the already-verified Windows/GAUSS 26.1.1 combination. Environment binding guarantees *consistency between confirmation and invocation on whatever single verified combination is in use* — it does not imply broader portability.

## 9. Pre-Invocation Validation

Immediately before any real helper call, in this order (mirroring the mock controller's existing `check_environment_before_invocation(...)`/`invoke(...)` guard sequence, extended with the two additional real-world checks Phase 3 introduces):

1. State is `confirmed`.
2. Request is frozen.
3. Confirmation is valid (the three-part minimum-evidence test from the canonical contract's §8 holds).
4. Confirmation scope matches `request_hash`.
5. Confirmation belongs to the current session.
6. Request has not already executed (`request_not_already_executed` guard — no `helper_invocation_identifier` already assigned for this `request_hash`).
7. Environment matches (§8).
8. Paths remain valid (`working_directory`/`output_directory`/`expected_input_files` all still resolve and exist).
9. Script identity is trustworthy, **or** script mode remains blocked outright (§7 — in Phase 3, this check always resolves to "blocked," since script-path mode never reaches this point).
10. Safety review remains valid (no field the safety review depended on has changed since it passed).
11. Expected inputs remain available (redundant with 8, restated because the state-machine contract lists it as its own guard — both checks must independently hold, not be collapsed into one).
12. Invocation record can be created (the adapter can actually allocate a `helper_invocation_identifier` — an in-memory allocation failure here is itself a guard failure, not a helper failure).
13. Cancellation has not been accepted for this request before this point.
14. Helper dependency is available (the `execute_gauss_code` module can actually be imported/called in this environment — distinct from "the GAUSS environment is available," which is check 7; this checks the Python-level dependency itself).

**Which failures consume confirmation, and which do not — aligned exactly with the existing contract rule, unchanged by Phase 3:**

- **Confirmation is consumed atomically with invocation authorization** — the same moment guard 14 passes and the real helper call is about to be made, not earlier and not merely checked-then-used.
- **Any failure in guards 1-14 (a pre-authorization guard failure) does not consume confirmation.** The request returns to a state from which a corrected/fresh cycle can proceed (or, per the terminal-instance rule, requires an entirely new request if the failure is unrecoverable for this instance).
- **A launch failure that occurs *after* authorization (guard 14 passed, the real call was attempted, but e.g. the subprocess could not be spawned — `OSError` from the OS itself) does consume confirmation.** This mirrors `RUNNER_LAUNCH_FAILURE` in the mock controller's existing `FailureCategory` enum and its corresponding test (`test_16`) exactly — the only difference in Phase 3 is that the failure can now come from a real OS-level subprocess-spawn error rather than a simulated one.

## 10. Invocation Transaction Boundary

Conceptual ordering for a single real invocation, extending the mock controller's existing `invoke(...)` ordering with the real-call boundary:

1. Final guard validation (§9, guards 1-14).
2. Invocation identifier allocation (`helper_invocation_identifier` assigned; this is what guard 6/12 checks against for any concurrent or repeat attempt within the same process).
3. Confirmation consumption (atomic with step 2, per §9).
4. Invocation-attempt recording (the `OrchestrationRecord` notes an attempt is in flight, before the real call is made — so that if the process crashes between steps 4 and 6, the *fact that an attempt was made* is at least known within this process's own in-memory state for as long as it survives).
5. Helper call (`execute_gauss_code(...)` invoked with the projected parameters from §6, `strict=True`, `allow_network=False`).
6. Helper return (the structured result dict is received; this is a synchronous, blocking call — no intermediate progress is observable).
7. Structural validation (`validate_against_schema(result, schema_path)` called explicitly by the adapter/Result Validator — this is a separate call from `execute_gauss_code(...)` itself, per §5's `validate_schema` no-op finding).
8. Orchestration-state update (`EXECUTING → EXECUTION_COMPLETED`/`EXECUTION_FAILED`, per the helper-status mapping in §12).

**Ambiguous outcomes and process crashes:** if the hosting Python process crashes or is killed between step 4 and step 6, the in-memory `OrchestrationRecord` is lost entirely — there is no durable record in Phase 3's single-process scope. On restart, no code path in Phase 3 attempts to reconcile "was that GAUSS process actually launched, and did it finish?" — this is explicitly out of scope (crash recovery is a Phase 5 item, per §22). The safe posture, inherited unchanged from `planning/v0.31.0-runtime-orchestration-design.md`'s File Lifecycle Design, is: after any such interruption, the interrupted request is treated as `unknown`/unusable, and any further action requires a wholly new request with fresh confirmation — never an assumption that the interrupted run's outcome (even if file changes are visible on disk) can be safely attributed without independent verification.

**What Phase 3 can guarantee — RESOLVED scope (§22, §23, decision 4):** at most one real helper invocation per confirmed canonical request, within **one Python process, one live controller instance, one in-memory invocation registry** — enforced the identical way the mock controller already enforces it (`HelperInvocationStatus`, tested by `test_18`/`test_19`), now guarding a real call instead of a fake one.

**What Phase 3 cannot guarantee without durable persistence or cross-process locking:** true exactly-once behavior across multiple processes, restarts, or concurrent orchestration instances is **not** claimed. If two separate processes somehow held confirmed requests for the same underlying `request_hash` (which nothing in this single-process design prevents at the cross-process level), each could independently invoke the helper — Phase 3 does not add a lock, database, or queue to prevent this. This limitation must be stated plainly in every Phase 3 deliverable's documentation, not glossed over. **This document does not claim true distributed exactly-once behavior anywhere.**

## 11. Result Validation

- **Retention:** the helper's structured result dict is retained in the `OrchestrationRecord` as `helper_result`, exactly as the mock controller already retains a `FakeRunner`'s return value — unmodified, not summarized, not filtered.
- **Schema validation:** `validate_against_schema(result, "schemas/gauss_code_execution.schema.json")` is called explicitly by the adapter/Result Validator immediately after the helper returns (step 7 of §10) — this is a separate function call from `execute_gauss_code(...)` itself, confirmed by direct code inspection (§5).
- **Malformed results:** a schema-invalid result is flagged and routed to `EXECUTION_FAILED`'s malformed sub-case, identical to the mock controller's existing `validate_fake_result(...)` behavior (`test_24`) — never passed downstream as if it were valid.
- **Helper launch failure:** distinguished by the *absence* of a returned result at all (an exception/`OSError` from the subprocess-spawn attempt itself, caught by the adapter, not by the helper — `execute_gauss_code(...)` itself never raises, per its own verified behavior, but the surrounding subprocess machinery it calls into can still fail to launch in ways the helper's own internal exception handling already converts to `execution_status: "error"`, not a raised exception the adapter needs to catch separately).
- **Timeout:** identified via `execution_status == "timed_out"` with `executed: true`.
- **GAUSS runtime error:** identified via `execution_status == "failed"` with `executed: true`.
- **Valid `completed` result:** identified as a *structurally schema-valid* result with `execution_status` equal exactly to `"completed"` — matching the precise definition `planning/v0.31.0-runtime-state-machine-contract.md`'s §12 already establishes for the mock controller, now applied to a real result.
- **Missing expected outputs:** identified by comparing the request's `expected_output_files` against the real result's `output_files` array (§6) — a discrepancy is disclosed, not treated as blocking or as proof the file doesn't exist elsewhere.
- **Output metadata preservation:** `output_files` entries are passed through unmodified; the adapter never opens, reads, or infers the contents of any listed file — the same metadata-only boundary already enforced by `workflows/execution-aware-analysis.md` and the mock controller's `test_26`.

**Raw helper results are retained in memory for the lifetime of the `OrchestrationRecord`** (single-process, non-durable, per §10) — not summarized at retention time. Summarization only happens later, at whatever consumption point eventually reads `to_safe_summary()` for any user-facing or logged purpose.

## 12. Status and Failure Mapping

Authoritative mapping from the helper's seven verified `execution_status` values (confirmed directly against `schemas/gauss_code_execution.schema.json`'s enum: `completed`, `failed`, `timed_out`, `skipped`, `blocked`, `error`, `unknown` — no additional status invented) to orchestration outcomes:

| Helper `execution_status` | `executed` | Orchestration state | Failure category | Analysis eligible? | Reporting eligible? | Confirmation consumed? | Rerun requires new request? | Required user-facing disclosure |
|---|---|---|---|---|---|---|---|---|
| `completed` | `true` | `EXECUTION_COMPLETED` | None | Yes | Yes | Yes | N/A (not a failure) | Report success plainly; never claim methodology validity from this alone |
| `failed` | `true` | `EXECUTION_FAILED` | `GAUSS_RUNTIME_ERROR` | Yes | Yes | Yes | Yes | Report error evidence; never auto-rerun |
| `timed_out` | `true` | `EXECUTION_FAILED` | `TIMEOUT` | Yes | Yes | Yes | Yes | Report timeout and partial output; never claim the code is broken from timeout alone |
| `skipped` | `false` | Never reaches `EXECUTING` — this status only occurs when the helper itself declines an attempt (e.g., no code/script supplied); Phase 3's own pre-invocation guards should already prevent this, so a real `skipped` result indicates a guard gap worth investigating, not a normal outcome | `MISSING_INPUTS` (if actually observed) | N/A | N/A | No | N/A | Treat as a pre-invocation guard failure that reached the helper unexpectedly; do not silently absorb it |
| `blocked` | `false` | Never reaches `EXECUTING` (the helper itself blocked, e.g. missing environment or missing package) | `RUNNER_UNAVAILABLE` or `INELIGIBLE_REQUEST`, depending on the specific `errors`/`warnings` content | Yes (blocked is still interpretable evidence, per `workflows/execution-aware-analysis.md`) | No | No | N/A | Advisory-Mode-style fallback disclosure |
| `error` | `false` | `EXECUTION_FAILED` | `RUNNER_LAUNCH_FAILURE` | Yes (as a tool-error record) | Yes | Yes (confirmation was consumed to attempt the call) | Yes | Honest tool/helper-error disclosure; never conflated with a GAUSS-side runtime error |
| `unknown` | Varies | Treated conservatively as `EXECUTION_FAILED` with an unresolved failure category until a human/future logic can classify it further | Flagged, not silently assigned a specific category | No, until diagnosed | No, until diagnosed | Yes (a call was attempted) | Yes | Flag as an unresolved outcome; do not guess at classification |

No status beyond these seven is invented anywhere in this mapping.

## 13. Error Boundaries

Each handled distinctly, none collapsed into a generic outcome:

- **Adapter dependency unavailable** (the `gauss_code_execution` module cannot be imported in this environment) — pre-invocation guard failure (§9, guard 14); confirmation not consumed.
- **Environment unavailable** (§8) — pre-invocation guard failure; confirmation not consumed.
- **Executable unavailable** — pre-invocation guard failure; confirmation not consumed.
- **Preflight rejection** (any of guards 1-14 fails) — confirmation not consumed, per §9.
- **Invocation launch failure** (guard 14 passed, real call attempted, process could not spawn) — confirmation consumed; `RUNNER_LAUNCH_FAILURE`.
- **Helper internal failure** (`execution_status: "error"`) — confirmation consumed; mapped per §12.
- **Timeout** (`execution_status: "timed_out"`) — confirmation consumed; mapped per §12.
- **GAUSS runtime error** (`execution_status: "failed"`) — confirmation consumed; mapped per §12.
- **Malformed result** (schema-invalid) — confirmation consumed; terminal for this instance; never analyzed as valid evidence (§11).
- **Schema-validation failure** — same as malformed result; this *is* how a malformed result is detected.
- **Expected-output failure** (execution succeeded, a listed output is missing) — non-blocking discrepancy, disclosed, evidence still stands (§11).
- **Analysis failure** — never rewrites `execution_status`; `analysis_status` tracked independently, identical to the mock controller's existing guarantee (`test_29`).
- **Report-generation failure** — never erases a validated result; `report_status` tracked independently (`test_30`).
- **Cancellation request during execution** — disclosed honestly per §14; the synchronous call cannot be interrupted.
- **Process interruption or unknown outcome** — treated as `unknown`/unusable per §10; requires a wholly new request.

## 14. Cancellation

**The verified limitation is preserved unchanged: synchronous execution is not cooperatively cancellable.** `execute_gauss_code(...)`'s default runner is a blocking `subprocess.run(..., timeout=timeout_seconds)` call with no cooperative cancellation hook exposed by the helper today — this was already established in `planning/v0.31.0-runtime-orchestration-design.md`'s File Lifecycle Design and is not revisited or reopened by Phase 3.

Phase 3 behavior, by timing:

- **Cancellation before invocation** (any pre-`EXECUTING` state) — handled identically to the mock controller's `cancel()`: acknowledged, no invocation occurs, terminal `CANCELLED` state, no confirmation consumed if cancellation occurs before authorization (or confirmation consumed-but-abandoned if it occurs after authorization but before the call — see next bullet).
- **Cancellation after authorization but before the helper call** — since authorization and confirmation consumption are atomic with the call itself (§9), there is effectively no window here in Phase 3's synchronous design; authorization *is* the moment the call begins.
- **Cancellation while the helper call is active** — cannot be honored as true interruption. The adapter has no mechanism to stop the blocking `subprocess.run(...)` call once started. The synchronous call runs to completion or to its own timeout, whichever comes first; only once it returns does orchestration have anything to act on.
- **Cancellation after helper return** — the result, once returned, is handled normally (§11, §12); a "cancel" request received after the call has already returned functions as an instruction not to *use* the result for further action, not as an undo of the execution itself.
- **Late results** — since the call is synchronous, there is no "late result" scenario within a single invocation; the call either returns (with whatever outcome) or the process itself is killed externally (§10's crash-recovery posture applies).
- **Timeout** — the helper's own `timeout_seconds` enforcement (capped at `300.0`) is what actually bounds a hung execution; this is existing, verified helper behavior, not new Phase 3 behavior.
- **Required user-facing disclosure:** any "cancellation during execution" scenario must disclose plainly that the synchronous call could not be interrupted, and that the result (if any) reflects what actually ran — identical wording obligation to the mock controller's own `CANCELLATION_DURING_EXECUTION` category (`test_28`). **This document does not claim, and Phase 3 must not claim, that cancellation terminated GAUSS** — no such mechanism exists or is implemented in Phase 3; true process termination (e.g., killing the subprocess) would be a distinct, separately-scoped future capability requiring its own verification, not something Phase 3 opportunistically adds.

## 15. Security Boundaries

Unchanged from, and inherited directly from, the already-verified helper and the mock controller's already-tested guarantees:

- **No shell-string construction anywhere in the adapter** — the adapter calls `execute_gauss_code(...)` with structured keyword arguments; it never builds a command string itself. (The helper's own `_default_command_builder` already returns a `list[str]`, called via `subprocess.run(..., shell=False)` — confirmed by direct inspection in the `v0.31.0` design review; Phase 3 does not touch or duplicate this logic.)
- **Structured helper invocation only** — no new invocation path is added; the adapter's only real-world side effect is calling `execute_gauss_code(...)` exactly as documented in §5/§6.
- **No network access** — `allow_network=False` passed explicitly on every call (§3, §6); the helper has no network capability regardless.
- **No credentials, no secrets** — the canonical request contract already excludes these from every field; the adapter introduces no new field that could carry them.
- **No environment-variable values in records** — `OrchestrationRecord`/`to_safe_summary()`'s existing redaction rules apply unchanged to real results.
- **No arbitrary command execution** — only the verified `execute_gauss_code(...)` surface is used; no shell, no `os.system`, no new subprocess call site outside the helper's own existing, unmodified implementation.
- **No GUI executable** — enforced at two independent points, per §6/§8 (defense in depth).
- **Path containment** — enforced by the helper's existing, unmodified `_resolve_inside(...)` logic; the adapter re-verifies immediately pre-invocation but does not duplicate or reimplement the containment logic itself.
- **Allowed output directory** — `output_directory` resolves inside `working_directory`, unchanged helper behavior.
- **No output-file content reading** — the adapter never opens a file listed in `output_files`; this remains explicitly out of scope (§4).
- **Safe logging and redaction** — any Phase 3 logging must follow the same "must never contain" list already established in `planning/v0.31.0-runtime-orchestration-design.md`'s Observability section: no full code/script content beyond what identity requires, no file contents, no credentials, no environment-variable values, no license tokens, no raw conversational transcript.
- **No raw conversation persistence** — the `OrchestrationRecord` stores structured fields only, never free-text transcript, identical to the mock controller's existing design.

### Real helper smoke tests (future work, explicitly gated — not performed by this planning task)

**Enablement mechanism — RESOLVED.** A two-part opt-in gate, both parts required simultaneously — neither alone is sufficient:

1. An explicit command-line flag, e.g. `--run-real-gauss`, passed to the smoke-test entry point itself.
2. An explicit environment variable, `GAUSS_AI_ALLOW_REAL_EXECUTION=1`, set in the shell invoking the test.

**This mechanism is decided here but not implemented in this task or in Increment 1** (§18's Increment-1 boundary explicitly excludes real smoke tests; the flag/variable are implemented in a later increment, per §18's Increment 7).

A very small, explicitly approved set that may run **only** when all of the following hold simultaneously:

- Both the `--run-real-gauss` flag **and** the `GAUSS_AI_ALLOW_REAL_EXECUTION=1` environment variable are present — the absence of either one means the smoke tests are skipped, with no partial/degraded execution mode.
- GAUSS is available on the machine running the test — availability alone must never itself trigger execution; it is necessary, not sufficient, and is checked only after both gate conditions above already hold.
- The environment matches the already-verified configuration (Windows, GAUSS 26.1.1, terminal `tgauss.exe`) — verified by the smoke test itself immediately before invoking the adapter, not assumed from the gate conditions alone.
- No GUI executable is used.
- No network access is used.
- Output writes are contained to a disposable working directory created for the test run, or to another directory explicitly approved for smoke-test use — never an arbitrary or ambient working directory.
- The executed code is non-destructive and minimal (a trivial `print`/arithmetic script, mirroring the `v0.28.0`/`v0.29.0` smoke-test discipline).
- The user or developer explicitly authorizes execution for that specific run (the two-part gate above *is* this authorization mechanism).

**Additional requirements, resolved as part of this decision:**

- Smoke tests are **skipped by default** — running the adapter's or controller's normal test suite (unit tests, `--self-test`, or any default `python scripts/test_*.py` invocation) must never execute them.
- **Release-readiness checks must never set the environment variable or pass the flag.** `scripts/check_release_readiness.py`, `scripts/check_evaluation_tracking.py`, and any CI workflow must remain entirely unaware of `GAUSS_AI_ALLOW_REAL_EXECUTION` — neither reading it approvingly nor setting it.
- **No import-time or discovery-time execution.** Merely importing the smoke-test module, or a test runner discovering/collecting it, must never itself invoke GAUSS — the two-part gate is checked inside the test body, not at module load.
- **GAUSS availability alone must never trigger execution** — restated from above for emphasis, since this is the single most important invariant of this gate: detecting GAUSS is present is never, by itself, a reason to run it.
- Smoke tests must **verify the environment before invoking the adapter** — an environment-mismatch check runs first, and the smoke test aborts (without invoking the adapter) if the live environment does not match the verified Windows/GAUSS 26.1.1/`tgauss.exe` configuration.
- Smoke tests must **clearly print that real GAUSS execution is enabled** — an unambiguous, unmissable console message stating real execution is about to occur, printed before the adapter is invoked, so a developer running the suite is never surprised by a real GAUSS process starting.
- **CI must not run these tests unless separately and explicitly configured in a future task.** This document does not configure CI; any future CI change enabling real smoke tests requires its own separate, explicit review — never a side effect of an unrelated CI change.

**These tests are not run during this planning task, and this document does not authorize running them.**

## 21. Stop Conditions

Conditions that should stop implementation and require redesign — not proceed-with-a-workaround:

- **Helper interface mismatch** — if `execute_gauss_code(...)`'s actual signature has changed from §5's audit by the time implementation begins, implementation stops until the audit is re-verified against current code.
- **Inability to bind the confirmed environment deterministically** — if `strict=True` plus explicit environment context does not, in practice, guarantee the same environment used at confirmation is what actually executes, this is a fundamental design gap requiring redesign, not a workaround.
- **Silent helper executable substitution** — any code path where a different executable than the one confirmed is used without an explicit, disclosed re-confirmation stops implementation immediately.
- **Inability to distinguish malformed results** — if a real helper result cannot be reliably schema-validated (e.g., the schema itself proves inadequate against real output shapes), implementation stops until the schema or the validation approach is revised.
- **Invocation duplication risk within the claimed single-process support scope** — if any code path allows two real invocations for the same confirmed request within one process, this is a hard stop, since it violates the one invariant this milestone claims to guarantee.
- **Confirmation consumption ambiguity** — if it becomes unclear at implementation time whether confirmation was consumed for a given attempt, implementation stops until the transaction boundary (§10) is clarified.
- **Unexpected file writes** — any real smoke test producing a file outside the disposable working directory stops all further real-execution testing immediately.
- **Any indirect GUI invocation** — any code path that could resolve to `gauss.exe` stops implementation immediately.
- **Any need to weaken path containment** — if implementing the adapter seems to require loosening the helper's existing containment logic, this is a stop condition, not a negotiable trade-off.
- **Any need to store secrets** — a stop condition, full stop.
- **Real execution producing inconsistent or unexplained behavior** — any real smoke test outcome that does not match §12's mapping table stops further real-execution testing until investigated and either explained or the mapping is corrected.
