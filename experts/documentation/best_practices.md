# Best Practices

Practices the Documentation Expert should promote across agents that consult it.

- Start with the user's task, not the implementation (`BODY_OF_KNOWLEDGE.md`, Task-Oriented Usage Guidance).
- Define the intended audience before choosing vocabulary and depth (`BODY_OF_KNOWLEDGE.md`, Audience and Clarity).
- State prerequisites explicitly, before the steps that need them (`BODY_OF_KNOWLEDGE.md`, Task-Oriented Usage Guidance).
- Explain inputs and outputs so the reader can tell whether something worked (`BODY_OF_KNOWLEDGE.md`, Reference Documentation).
- Use examples that match verified syntax, or label them clearly as unverified/pseudocode (`BODY_OF_KNOWLEDGE.md`, Examples).
- Define terms before using them, and keep terminology consistent throughout (`BODY_OF_KNOWLEDGE.md`, Audience and Clarity).
- Keep warnings near the risky step they apply to, not only at the end (`BODY_OF_KNOWLEDGE.md`, Warnings, Caveats, and Assumptions).
- Separate reference from tutorial content where useful, rather than blending the two without structure (`BODY_OF_KNOWLEDGE.md`, Documentation Types).
- Avoid unexplained jargon (`BODY_OF_KNOWLEDGE.md`, Audience and Clarity).
- Document assumptions explicitly, close to where they matter (`BODY_OF_KNOWLEDGE.md`, Warnings, Caveats, and Assumptions).
- Keep examples small and focused on the point being illustrated (`BODY_OF_KNOWLEDGE.md`, Examples).
- Label pseudocode clearly whenever an example is not verified GAUSS syntax (`EXPERT.md`, Response Behavior).
- Avoid duplicating official docs inaccurately — point to them rather than restating from memory (`BODY_OF_KNOWLEDGE.md`, Reference Documentation).
- Link or cite official docs when appropriate, rather than presenting this expert's own paraphrase as authoritative.
- Keep comments focused on intent, not mechanics (`BODY_OF_KNOWLEDGE.md`, Comments and Docstrings).
- Keep parameter and return descriptions concrete — state the type/shape and meaning, not just a vague label (`BODY_OF_KNOWLEDGE.md`, Reference Documentation).
- Provide troubleshooting guidance when useful, ordered by likely cause (`BODY_OF_KNOWLEDGE.md`, Troubleshooting).
- Separate documentation clarity from correctness claims — never let clear writing imply verified syntax, sound methodology, or good design (`reasoning.md`, What Not to Infer).
