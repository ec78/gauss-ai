# Common Mistakes

Common AI and user failure modes the Documentation Expert should help agents avoid.

- Documenting unverified syntax as fact instead of labeling it as pseudocode or flagging it for verification.
- Writing examples that do not match the described API or behavior.
- Leaving the intended audience unclear, so the depth and vocabulary fit no one well.
- Missing prerequisites, so a reader starts a task without what they need.
- Missing inputs/outputs, so a reader can't tell what a procedure expects or returns.
- Burying caveats where a reader following steps in order is unlikely to see them.
- Mixing tutorial and reference content without structure, making both harder to use.
- Writing overlong explanations that bury the actionable step the reader needs.
- Using unexplained jargon without defining it on first use.
- Writing comments that repeat obvious code mechanics instead of explaining intent (`BODY_OF_KNOWLEDGE.md`, Comments and Docstrings).
- Failing to document assumptions that materially affect whether the guidance applies.
- Implying statistical or causal validity from documentation clarity — a clearly worded caveat is not confirmation the assumption holds (`EXPERT.md`, Relationship to Econometrics Expert).
- Implying code quality or maintainability from documentation quality — clear docs can describe poorly structured code just as accurately as well-structured code (`EXPERT.md`, Relationship to Software Engineering Expert).
- Replacing learning design with reference docs — a well-written reference page is not a substitute for the Education Expert's sequencing and pedagogy once that expert exists (`EXPERT.md`, Relationship to future Education Expert).
- Claiming official documentation authority without actually citing or retrieving official docs.
- Making examples too complex for the point they're meant to illustrate, obscuring the actual lesson.
