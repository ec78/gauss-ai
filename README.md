# GAUSS AI

**GAUSS AI** is an open architecture for building specialized AI agents that assist with GAUSS programming, econometrics, documentation, education, and product development. Its flagship, most-implemented product is the **GAUSS Code Assistant** — a governed, human-in-the-loop tool that helps you diagnose and repair GAUSS code, one file at a time, with an explicit approval at every step.

## Current Alpha Status

**Private Alpha.** As of `v0.75.0`, the GAUSS Code Assistant is installable (`pip install -e .`), launches a conversational GAUSS Q&A and code-generation assistant by default (`gauss-ai`) that can use a free, local Ollama model (no API key) or Anthropic's cloud API, has a guided repair command (`gauss-ai repair <file.gss>`) that can propose an AI-assisted repair-draft candidate for review, and has been validated end to end against real GAUSS 26.1.1 through the installed product itself. Deterministic validation/eligibility evidence now applies to ANY code-shaped conversational answer, not only explicit code-generation requests — closing a gap the prior milestone found but did not fix. Generated code is checked against real documented call signatures (now including a coarse documented parameter category/shape where a real `:type` line supports it) and real documented preconditions for four function families (`invpd`, `inv`, `solpd`, `chol`), producing an explicit `INELIGIBLE`/`REQUIRES_CLARIFICATION`/`ELIGIBLE_FOR_VALIDATION` verdict — never presented as correctness, safety, or approval to execute. A model's own claimed "expected output" is now structurally represented and, for a small set of literal patterns, deterministically checked — a wrong claim is flagged, never treated as execution evidence. **Generated code should still be treated as unverified until you check it yourself.** See `planning/v0.75.0-universal-code-validation.md` for the full readiness assessment. It is not production software, does not claim GAUSS correctness, and does not run autonomously.

## Key Capabilities

- **Answer GAUSS questions conversationally** (`gauss-ai`, no subcommand) — multi-turn, grounded against this repository's verified error catalog and (when you configure a local documentation checkout) real official GAUSS documentation, always honest about whether an answer is grounded, uncertain, or has been executed. See [docs/conversational-qa.md](docs/conversational-qa.md).
- **Execute a single, narrow, explicitly-approved conversational code snippet** once it reaches `HANDOFF_CANDIDATE` readiness — exact code shown before approval, single-use digest-bound consent, real evidence returned, no autonomous retry or repair. See [docs/controlled-execution-handoff.md](docs/controlled-execution-handoff.md).
- **Run as a local MCP server** (`gauss-ai mcp` / `gauss-ai-mcp`, optional `pip install -e ".[mcp]"`) so MCP clients (Claude Code, Claude Desktop) can search the official docs, have GAUSS code they write deterministically validated, run validated code through the human-approved execution handoff, and drive the guided repair pipeline — no second model required. See [docs/mcp-server.md](docs/mcp-server.md).
- **Get the official docs in one command** (`gauss-ai docs fetch`), downloaded from docs.aptech.com for local, offline grounding. See [docs/gauss-documentation-setup.md](docs/gauss-documentation-setup.md).
- **Diagnose real GAUSS execution failures** against a verified error catalog (real-runtime-reproduced and/or official-documentation-sourced — see [docs/gauss-error-catalog.md](docs/gauss-error-catalog.md)).
- **Suggest a candidate repair draft** for a small, deliberately narrow set of verified patterns (currently: G0105's own empty-assignment trigger), with its reasoning and confidence shown — always a proposal you accept, edit, or reject, never applied automatically.
- **Propose a bounded, single-file repair** — never multi-file, never autonomous, never applied without your explicit approval at every layer.
- **Apply that repair** through a fail-closed transaction with a mandatory, never-overwritten backup.
- **Verify the repair** by re-executing the repaired file through the same, unmodified execution pipeline and comparing the evidence — never a fabricated correctness claim.
- **Record your own review** of that evidence, and summarize the entire session in one place (`gauss-ai repair`'s own closing output, or `show-repair-session`).

## Safety Model

Every approval layer is independent, digest-bound, and never inferred: execution confirmation, strategy approval, draft approval, application approval, the application gate, explicit file reading, and human verification review. The guided `gauss-ai repair` command may simplify *navigation* through these steps, but it never simplifies *authorization* — see [docs/alpha-tester-guide.md](docs/alpha-tester-guide.md)'s "Current safety boundaries" for the complete list, and `planning/v0.67.0-productization-and-alpha-packaging.md` for the tests that prove the guided command cannot bypass any of them.

## Conversational GAUSS Q&A

```
gauss-ai
```

launches a chat you can ask GAUSS questions in plain language, with follow-up context retained ("What does reshape do?" → "Show me a simple example." → "What's the difference between that and vec?"). It answers from this repository's verified error catalog and, when you configure `docs-root`, real local GAUSS documentation — always disclosing whether an answer is grounded or not. It never applies a repair and never writes a file. As of `v0.78.0`, generated code that reaches `HANDOFF_CANDIDATE` readiness (the strongest deterministic evidence level) can be executed through one narrow, explicit, single-use, digest-bound approval — see [docs/controlled-execution-handoff.md](docs/controlled-execution-handoff.md); asking to "run this" for anything else still gets an honest redirect or a clear "nothing eligible right now" message, never a silent no-op. The prior command-by-command workflow REPL is unchanged and still available at `gauss-ai repl`. See [docs/conversational-qa.md](docs/conversational-qa.md) for the full guide, including how to configure a real model provider.

## What Happens to My Files?

Before you point this at your own code, here is exactly what it does and does not do to your files, in one place:

- **Your original source file is never modified directly.** `gauss-ai repair <file.gss>` copies the named file into a fresh, contained workspace and works there instead.
- **All repair work happens inside that workspace** — not in place, and not anywhere else on disk.
- **Explicit approval is required before every stage** — execution, repair strategy, repair draft, and application are each a separate, independent decision; nothing is inferred or defaulted to "yes."
- **Applying a repair always creates a mandatory, never-overwritten backup** before anything is written.
- **Verification is evidence-based, not assumed.** The repaired file is re-executed and compared against the original run; the result is a factual comparison, never a fabricated correctness claim.
- **You decide whether a repair is accepted.** The final verification review (`accepted` / `rejected` / `inconclusive`) is always your own recorded decision, never inferred automatically.

See "Safety Model" above and [docs/alpha-tester-guide.md](docs/alpha-tester-guide.md) for the complete list of safety boundaries this summarizes.

## First Time?

If this is your first time using GAUSS AI:

1. Install the package (above).
2. Run `gauss-ai` with no arguments and ask it a GAUSS question — no configuration required.
3. Run first-run setup and a read-only health check:
   ```
   gauss-ai init
   gauss-ai doctor
   ```
4. Try the included fake-mode repair demo — no GAUSS installation required (see "Typical First Session" below).
5. Configure your real GAUSS executable: `gauss-ai config set gauss-executable <path to your tgauss/tgauss.exe>`.
6. Run a repair on one of your own `.gss` files: `gauss-ai repair <your-file.gss> --runner gauss`.

Each step is covered in more detail in the sections below.

## Guided Repair Workflow

`gauss-ai repair <file.gss>` is orchestration/UI only over the exact same modules the lower-level command-by-command REPL uses (`python scripts/gauss_code_assistant_cli.py`, still fully supported — see the "Recommended reasoning sequence" section below for its full command reference). It hides internal identifiers by default and shows plain-language next steps; digests and trace IDs are still shown at every approval point, since they are what you are actually approving. As of `v0.69.0`, it also shows the evidence behind a repair immediately after strategy approval and, for a small, verified set of patterns, a candidate replacement you can accept, edit, or reject — never applied without your own decision, and never a substitute for the approval steps that follow.

## Current Status

Current milestone: `v0.82.0` - Bounded Control-Flow Syntax Coverage. Simple `for ... endfor` loops (nested included) are now validated, so the preallocate-and-fill answer that live finding 71.3 showed stuck at `review_required` (`v = zeros(5, 1); for i(1, 5, 1); v[i] = i^2; endfor;`) can reach `HANDOFF_CANDIDATE`. The readiness policy is unchanged. A loop is validated only when its header is exactly `for NAME(a, b, c);`, it is closed by its own `endfor;`, and every body statement is an assignment, an indexed assignment, a `print` or a nested `for`; anything else (`if`, `break`, `do`, `proc`, thread blocks) keeps it unknown. Four new INVALID rules (header shape, block balance, counter reuse, counter assignment) each cite real `tgauss.exe -b` evidence. An indexed write no longer hides a variable's scalar/vector/matrix category, so fill-then-`meanc` reaches candidacy, while values after an indexed write are still never inferred. Fixed along the way: one-line loops and thread blocks that the syntax layer could not see; `let`-shaped assignments (`x = {1, 2, 3}';`) that real GAUSS rejects; the garbled `vcmvcx.rst` Syntax line from 71.5; and, exposed by an all-pages diff of that fix, mis-split nested optional signatures and a variadic `...` counted as one argument (131 signatures corrected). With the user's approval, the system-statement registry was audited against every published page, growing from 50 to 213 entries with new `network` and `database` categories. That closed a real gap: `fred_load` (a FRED web API call) was `HANDOFF_CANDIDATE` in v0.81.0. 23 new deterministic tests; full suite 48 files, all passing; zero diff on every core execution/repair/verification/approval module. Live evaluation `72.1`-`72.16` (real Claude Code client, uncoaxed code): all sixteen pass with no wrong verdict. The 71.3 shape, a recurrence, a step-2 loop and fill-then-`meanc` reached candidacy, and every negative probe held (a hallucinated function, a precondition violated through a variable, a file write, a FRED download, a directory listing). Five minor findings are disclosed in `KNOWN_LIMITATIONS.md`. See `planning/v0.82-bounded-control-flow-syntax-coverage.md`.

Previous milestone: `v0.81.0` - Idiomatic Handoff Candidacy. Code written the way models naturally write GAUSS (assign a value, then call a function on it) can now reach `HANDOFF_CANDIDATE` on real evidence, without loosening the readiness policy (`compute_handoff_readiness`, the evidence profile, and the system-statement gate are unchanged). Planning found that the assumed cause (missing builtin signatures) was wrong on the MCP path; the real causes were: (1) the parameter-type check never traced a variable to its assignment, so `x = {1 2, 3 4}; y = meanc(x);` and `x = rndu(1e5, 4); y = meanc(x);` were always `review_required`; (2) `1e5`-style numerals were unrecognized; (3) a false `MISMATCH` made `meanc({1,2,3})` and `meanc(5)` `not_ready`, although in GAUSS a scalar or vector is a matrix (the docs say so, e.g. `stof.rst`, `meanc.rst`'s own `:rtype y: Kx1 matrix`); and (4) the precondition tracer used the last assignment anywhere in the code, even one written after the call. A new shared resolver traces a variable to its most recent prior top-level assignment -- a literal, or a single call whose docs give a `:rtype` -- and refuses (stays unknown) on any write it does not model (inside a block, indexed, multi-target, loop variable, `clear`). On the chat `ask()` path, a called builtin that is not the grounded topic (e.g. `rndu`) now gets its documented signature too. Every `NOT_READY` protection still holds, now also through traced variables. A re-baseline against the freshly fetched published docs gave identical verdicts to the old local clone, and surfaced one more pre-existing false `not_ready`: a function on a combined doc page (`vcx` on `vcmvcx.rst`) scored ambiguous against a neighbouring page. An ambiguous lookup now resolves when exactly one candidate page actually defines that call. 16 new deterministic tests; full suite 48 files, all passing; zero diff on every core execution/repair/verification/approval module. Live evaluation `71.1`-`71.5` (real Claude Code client, uncoaxed code): three of five ordinary tasks reached `HANDOFF_CANDIDATE`; OLS via `invpd(x'x)` stayed `review_required` by design; a preallocate-and-fill `for` loop stays `review_required` because any block caps syntax coverage at partial (disclosed in `KNOWN_LIMITATIONS.md`). See `planning/v0.81-idiomatic-handoff-candidacy.md`.

Previous milestone: `v0.80.0` - Hybrid MCP Validation, Docs Fetch, and Validation Hardening. The MCP server gains a "hybrid" path that needs no second model: the client's own model (Claude, ChatGPT, ...) searches the docs (`gauss_search_docs`), writes GAUSS code itself, and submits it to `gauss_validate_code`, which computes the readiness verdict deterministically -- code may come from the caller, a verdict never does. Validated `HANDOFF_CANDIDATE` code gets a server-issued, single-use `validation_id` that `gauss_execution_prepare` re-validates before preparing (refusing as `validation_stale` if the docs changed); prepare never accepts code directly. The v0.79.0 `gauss_chat_ask` path remains as an explicit opt-in "strict mode", registered only when `chat-provider` is a real model, since it alone can refuse to generate ungrounded code at all. New `gauss-ai docs fetch` downloads the 1,826 pages published at docs.aptech.com into `~/.gauss-ai/docs/` in one command (no git), all-or-nothing, never overriding a user-chosen `docs-root`, with a narrow `CLAUDE.md` network exception approved for exactly this explicit, user-invoked download; documentation is never bundled or redistributed. Two real, pre-existing validation gaps were found during planning and fixed first: (1) both the call extractor and the unknown-symbol checker skipped any keyword-led line with no word boundary, so `print colmean(x);` was never flagged, `print invpd({2 1, 3 2});` escaped its precondition check, and `printfm`/`format =`/`forecast =` lines were dropped -- now one shared, string-aware `call_scan_text(...)` with a drift-guard test; (2) nothing checked system-touching statements, so `... dos "...";` could reach `HANDOFF_CANDIDATE` while the execution helper does not sandbox GAUSS -- now a 50-entry, doc-verified registry (OS commands, processes, `run`/`#include`, directory changes, file reads/writes/deletes) forces `NOT_READY`. The validation chain was refactored into one shared `validate_generated_code(...)`, proven behavior-preserving by byte-identical `AnswerResult` snapshots across 12 scenarios. A real fetch against docs.aptech.com surfaced rate limiting (transient HTTP 403), handled with polite concurrency and backoff; a parity check found the published docs are more current than the four-month-old `develop` clone earlier evaluations were grounded against. 33 new deterministic, network-free tests (net); full suite passing. Classified **Private Alpha**. See `planning/v0.80-hybrid-mcp-validation.md`, `docs/mcp-server.md`, and `docs/gauss-documentation-setup.md`.

Previous milestone: `v0.79.0` - MCP Server. Exposes both existing subsystems -- the conversational assistant (including the `v0.78.0` controlled execution handoff) and the full guided repair pipeline -- as a local MCP (Model Context Protocol) server, so other MCP clients (Claude Code, Claude Desktop) on the same machine can call them as tools over stdio, alongside the interactive CLI they already have. This is a transport layer only: new module `scripts/gauss_mcp_server.py` implements no new safety, grounding, readiness, digest, or approval logic of its own -- every one of its 9 tools is a thin wrapper that either calls `gauss_conversation_engine.ConversationEngine.ask(...)` whole (never decomposed into separately-callable primitives, since that would hand a safety-relevant readiness judgment to whichever model drives the calling MCP client), reuses the existing `v0.78.0` execution-handoff functions unchanged (`gauss_chat_ask`'s pending code/readiness state feeds `gauss_execution_prepare`/`gauss_execution_decide`, never a caller-supplied argument), or forwards one REPL command at a time to the existing, unmodified `InteractiveMvpAdapter.handle_line(...)` (`gauss_repair_start`/`gauss_repair_command`/`gauss_repair_close`), the same dispatcher `gauss-ai repl` already drives. A new server-operator-only gate, `GAUSS_AI_MCP_ALLOW_REAL_GAUSS=1` (read from the server process's own environment, never a tool argument), is required before a `runner="gauss"` request can even be prepared -- in addition to, not instead of, the existing per-request digest/approval flow, since an MCP client is one step further removed from the human at the keyboard than a terminal user typing `--runner gauss` directly. The `mcp` package (SDK confirmed directly against the published `2.3.0` release, not assumed from training-era memory) is the repository's first-ever optional runtime dependency (`pip install -e ".[mcp]"`); the base CLI remains stdlib-only, since `gauss_ai_cli.py`'s new `mcp` subcommand imports the new module lazily. Runs over stdio only (no network/port/TLS surface), with one long-lived `ConversationEngine`/`InteractiveMvpAdapter` per session and one config load per server process. Ships a Claude Code plugin wrapper (`.claude-plugin/plugin.json`, `.mcp.json`, `.claude-plugin/marketplace.json`) in this same repository. 18 new deterministic, network-free tests (`test_gauss_mcp_server.py`, skips cleanly when the optional extra is not installed); full suite 47 files, all passing; zero diff on every core execution/repair/verification/approval module. No new capability was added beyond transport -- see `planning/v0.79-mcp-server.md` and `docs/mcp-server.md` for the full design and tool reference.

Previous milestone: `v0.78.0` - Controlled Execution Handoff. The FIRST milestone in which conversationally generated GAUSS code can actually execute -- a single, narrow, digest-bound, explicitly user-approved bridge from a `HANDOFF_CANDIDATE` conversational answer to the EXISTING, unmodified GAUSS execution adapter (`gauss_execution_adapter.GaussExecutionAdapter`/`load_real_helper()`, the same production path `v0.77.0`'s own differential harness already used) -- never a new subprocess implementation, never a change to how `HANDOFF_CANDIDATE` itself is computed (`gauss_pre_execution_validation.py` is unmodified). New module `scripts/gauss_execution_handoff.py` implements three immutable value types -- `ExecutionHandoffRequest` (SHA-256-digest-bound over code/runner/executable/timeout/workspace/readiness-state, exact byte-for-byte code text, deliberately no whitespace normalization), `ExecutionHandoffApproval` (binds exactly one request digest, `approved`/`declined`, single-use consumption tracked separately from the frozen object itself), and `ConversationalExecutionResult` (composes the existing `ExecutionEvidence` type rather than re-defining it) -- plus a ten-state failure taxonomy (`NOT_ELIGIBLE`/`DECLINED`/`APPROVAL_MISMATCH`/`STALE_REQUEST`/`ALREADY_CONSUMED`/`EXECUTION_BLOCKED`/`EXECUTION_FAILED`/`EXECUTION_TIMEOUT`/`INFRASTRUCTURE_FAILURE`/`SUCCESS`). Only `HandoffReadiness.HANDOFF_CANDIDATE` code with exactly one generated code block can create a request; approval requires a narrow, exact `yes`/`no` (`approve`/`decline`) response -- any other reply (`"okay"`, `"sure"`, `"looks good"`) is treated as unrecognized, re-asked once, then safely cancelled, never coerced into either decision. A consumed, declined, digest-mismatched, or stale approval always fails closed before the adapter is ever called; changing the code, runner, executable, or timeout after approval invalidates it entirely. After any execution attempt -- success, GAUSS error, or timeout -- nothing retries or repairs automatically; a follow-up diagnostic question is an ordinary advisory turn, and running anything again requires a brand-new request and a brand-new explicit approval. The conversational chat orchestration (`gauss_ai_chat.py`) is the only conversational module that gained this new capability; `gauss_conversation_engine.py`, `gauss_chat_provider.py`, and `command_doc_lookup.py` are unmodified and structurally proven (source-text-scan tests, mirroring `v0.77.0`'s own convention) to have no import path to any execution module, keeping the model/provider layer execution-incapable. A bounded real-GAUSS live evaluation (`68.x`, 12 scenarios) exercised the real `tgauss.exe` end to end -- real success on `meanc`/`invpd`/`chol` documented examples, a real GAUSS runtime failure (`error G0058: Index out of range`) rendered honestly with no retry, explicit decline, both directions of replay semantics (a reused approval object blocked; two independently-approved identical-code requests both legitimately executing), and two independently-caused rejections (`REVIEW_REQUIRED`, `NOT_READY`) that never reached the request-construction stage at all. One pre-existing, out-of-scope defect was found incidentally (`gauss_pre_execution_validation.extract_generated_calls(...)` does not recognize a call wrapped in a bare `print f(...)` statement) and disclosed, not fixed, since it lives entirely outside the new handoff module. 54 new deterministic, network-free tests (`test_gauss_execution_handoff.py`, 45; `test_gauss_ai_chat.py`, +9); full suite 46 files, 1,563 test functions, all passing; zero diff on every core execution/repair/verification/approval module. No source-file execution, no multi-file orchestration, no autonomous repair, and no durable/cross-session approval persistence was added. Classified **Private Alpha**. See `planning/v0.78-controlled-execution-handoff.md` and `docs/controlled-execution-handoff.md` for the full design, consent contract, and readiness assessment.

Previous milestone: `v0.77.0` - Differential GAUSS Syntax Validation & Corpus Hardening. Builds a reusable, reproducible differential-testing harness (`scripts/gauss_differential_harness.py`) comparing the deterministic syntax validator's verdict against real GAUSS across a ~239-item corpus (50 documentation-derived valid snippets, 135 systematic mutations, 29 historical + 25 fresh real model-output snippets) -- directly motivated by `v0.76.0`'s own post-release finding that a second real syntax false negative was discovered by incidental smoke test *after* that milestone's planned 12-scenario live evaluation had already concluded, proving checker completeness was being discovered empirically, one scenario at a time, not measured systematically. Real GAUSS invocation is confined to the harness's own doubly-gated `main()` (`--run-real-gauss` + `GAUSS_AI_ALLOW_REAL_EXECUTION=1`, both required), routed through the existing `gauss_execution_adapter.GaussExecutionAdapter`/`load_real_helper()` production path -- no new subprocess-management code, and structurally proven unreachable from any conversational module. **Baseline differential run: 5 false negatives, 12 false positives. Recommended reasoning sequence once execution evidence exists:

1. `execute`
2. `interpret` — what happened?
3. `diagnose` — what verified causes may explain it?
4. `repair-plan` — what bounded strategy should be considered, and what's needed before any future change?
5. `approve-repair <plan_digest>` / `decline-repair <plan_digest>` — record an explicit human decision about that exact plan
6. `suggest-repair-draft` — bounded, deterministic AI-assisted repair-draft candidate(s) from evidence, diagnosis, the verified error catalog, and the affected source code; always a proposal, never applied or drafted automatically
7. `repair-draft` / `show-repair-draft` — construct and display an immutable, bounded description of an intended edit (not a patch, not applicable) — using a candidate's fields verbatim if you accepted one, or fully manual fields otherwise
8. `approve-repair-draft <draft_digest>` / `decline-repair-draft <draft_digest>` — record an explicit human decision about that exact draft
9. `approve-repair-application <draft_digest>` / `decline-repair-application <draft_digest>` — record a third, still-independent decision about *applying* that exact draft
10. `check-repair-application-gate [--current-content-hash SHA256]` — re-verify every checkable precondition; never itself an authorization
11. `apply-repair <draft_digest> --replacement-text TEXT` — the one, bounded, single-file write transaction; fails closed on any precondition
12. `show-application-result` — inspect the most recent application transaction's outcome
13. `verify-repair [--fake-success|--fake-failure|--fake-timeout|--fake-unknown-error]` — proposes an ordinary execution of the repaired file
14. `confirm <request_hash>` / `execute` — the exact same commands used for any ordinary execution; nothing verification-specific exists here
15. `show-verification-request` — inspect the request and, once execution completes, an evidence-only comparison against the original run
16. `review-verification --decision {accepted|rejected|inconclusive} [--notes TEXT] [--reviewed-by NAME]` — record a human conclusion about that evidence; never inferred automatically
17. `show-verification-review` — inspect the most recently recorded review
18. `show-repair-session` — a read-only, one-place composition of every stage reached so far; no precondition, honest about missing stages
19. `stdout` / `stderr` — inspect captured process text explicitly, when needed
20. `outputs` — inspect output-file metadata
21. `read <path>` — explicitly read a needed file
22. `provenance` — inspect execution provenance
23. `reset` — before a new single-shot attempt

`repair-plan` does not modify code, does not rerun GAUSS, and does not guarantee a fix. `approve-repair`/`decline-repair` record a decision only. `suggest-repair-draft` (`v0.69.0`) never applies, approves, or drafts anything itself — it is assistive tooling only, bounded to one verified source pattern (G0105's own empty-assignment trigger) in this first version; every other case honestly reports no candidate available. `repair-draft` constructs an immutable, validated description of an intended edit — never a patch, never applicable, never generated content. `approve-repair-draft`/`decline-repair-draft` record a second, entirely independent decision about that exact draft. `approve-repair-application`/`decline-repair-application` record a third, entirely independent decision about *applying* that exact draft. `check-repair-application-gate` re-verifies every checkable precondition from the `v0.58.0` design's Application Gate but has no `safe_to_apply` field and never claims application is authorized. `apply-repair` is the one step capable of writing to a file — bounded to a single `.gss` file, a single workspace, and a single approved draft, with a mandatory, never-overwritten backup and a fail-closed transaction. `verify-repair` executes the repaired file through the ordinary, unmodified execution pipeline and `show-verification-request` reports only evidence (what happened), never a correctness verdict, success probability, or statistical claim. `review-verification` records a fourth, entirely independent human decision — about the verification evidence itself, never about applying anything — and has no revoke; a duplicate review attempt is refused. `show-repair-session` owns none of this evidence and mutates none of it — it composes references to whatever already exists, in fixed pipeline order, and is silent (not an error) about whatever has not happened yet. A completed, successful execution never establishes statistical or methodological correctness at any stage of this sequence.

## Interactive MVP Adapter Alpha

`v0.49.0` includes a terminal alpha harness for testing the implemented MVP workflow without writing Python glue. Fake execution remains the default:

```text
python scripts/gauss_code_assistant_cli.py
```

Optional: pass an approved local workspace parent directory:

```text
python scripts/gauss_code_assistant_cli.py --workspace-parent .gauss-ai-alpha-workspaces
```

For explicit local real-GAUSS alpha testing only, select the real backend and provide a terminal executable:

```text
python scripts/gauss_code_assistant_cli.py --runner gauss --gauss-executable C:\gauss26\tgauss.exe
```

If `--gauss-executable` is omitted, the real backend checks `GAUSS_EXECUTABLE`. The CLI argument takes precedence. Missing paths, invalid paths, and GUI executables such as `gauss.exe` block startup with a clear error; there is no silent fallback to the fake runner.

Sample session:

```text
gauss-mvp> workspace create
gauss-mvp> request --fake-success x = 2 + 2; print x;
gauss-mvp> plan
gauss-mvp> confirm <request_hash shown by plan>
gauss-mvp> execute
gauss-mvp> interpret
gauss-mvp> outputs
gauss-mvp> read fake-output.txt
gauss-mvp> provenance
gauss-mvp> exit
```

The adapter invokes `GaussCodeAssistantWorkflow` for planning, confirmation, execution, output metadata, file reading, and provenance. Execution uses a deterministic fake runner by default and clearly labels that fact. In real mode, the plan and execution transcript disclose the selected backend, executable path, workspace path, timeout, request hash, generated-script boundary, exit code, timeout state, duration, and stdout/stderr lengths without printing stdout/stderr contents or output-file contents automatically. Captured stdout/stderr can be inspected only through explicit `stdout`/`stderr` commands. The `interpret` command explains the current execution result from already-captured evidence only; it does not rerun GAUSS, repair code, retry, or read output files. The `diagnose` command reasons over that same evidence plus the verified GAUSS error catalog to surface bounded, low-confidence possible causes, missing evidence, and inspection questions — it never proposes a code repair, and cause confidence stays lower than classification confidence even for a well-classified error. Recommended sequence after `execute`: `interpret`, then `diagnose`, then `stdout`/`stderr` explicitly when needed, then `outputs`, then `read <path>` explicitly when needed, then `provenance`, then `reset` before a new single-shot attempt. Use [docs/manual-alpha-testing-guide.md](docs/manual-alpha-testing-guide.md), [docs/alpha-feedback-template.md](docs/alpha-feedback-template.md), [docs/real-gauss-alpha-testing-guide.md](docs/real-gauss-alpha-testing-guide.md), [docs/real-gauss-debugging-alpha-guide.md](docs/real-gauss-debugging-alpha-guide.md), and [docs/gauss-diagnostic-reasoning.md](docs/gauss-diagnostic-reasoning.md).

## How GAUSS AI Reduces Hallucinations

GAUSS AI is designed to reduce plausible but invalid code by combining source hierarchy, expert guidance, and benchmark evaluation:

* Official GAUSS documentation is the highest authority for syntax, arguments, return values, examples, and version behavior.
* Command categories help discover candidate native GAUSS commands and procedures.
* Command-specific documentation is required before giving exact production-ready syntax.
* Curated command notes are short convenience references, not a replacement for official documentation.
* Benchmark evaluations test known AI failure modes, including cross-language syntax contamination and hallucinated functions.
* Generated code should still be reviewed, verified, and tested before production use.

## Runtime Orchestration Design

`v0.31.0` designs — and, as an explicit mock-only skeleton, partially implements — the architecture that will eventually connect the real-execution user workflow above to the execution helper. In the `Knowledge → Experts → Reasoning → Tools → Agents → Workflows → Evaluations` layering this project uses throughout (see [ARCHITECTURE.md](ARCHITECTURE.md)), runtime orchestration is not a new layer: it is a future **Tools**-layer mechanism that would enforce the existing **Workflows**-layer rules (`workflows/real-execution-user-workflow.md`) consistently across turns, sitting between the GAUSS Code Assistant agent's response reasoning and the existing `scripts/gauss_code_execution.py` execution helper. The GAUSS Code Assistant remains the only agent involved; the helper remains a separate, unmodified tool boundary; and the real, user-facing connection between the workflow and the helper — the thing orchestration would ultimately provide — is **not implemented**.

**The designed (not yet production) orchestration flow:**

1. Classify execution intent (review/explanation/debugging vs. an actual run/test/execute/rerun request).
2. Collect required inputs (code or script, working directory, executable, timeout, expected writes).
3. Review eligibility (GUI executable, unknown working directory, out-of-bounds writes, package/license/network/global-config requirements all fail eligibility).
4. Perform a pre-execution safety review (filesystem impact, timeout, executable, input/output scope, destructive effects).
5. Construct and canonicalize the request (the 18-field Canonical Execution Request, fingerprinted by `request_hash`).
6. Display the exact plan the request represents — never a paraphrase of it.
7. Obtain request-bound confirmation, tied specifically to the displayed `request_hash`.
8. Authorize at most one invocation of the helper for that confirmed request.
9. Validate the structured result against `schemas/gauss_code_execution.schema.json` before any downstream use.
10. Route the validated result to execution-aware analysis and, if requested, report generation.
11. Compose the final, evidence-bounded response.
12. Require a wholly new request and fresh confirmation for any rerun — never a mutation of a completed, cancelled, blocked, or malformed prior request.

This is the *designed* flow the planning documents specify and the mock controller exercises with a fake runner — it is not yet the production runtime path a real conversation follows.

**Canonical execution request contract** (`planning/v0.31.0-canonical-execution-request-contract.md`): 18 fields describing exactly what would be executed (code or script path, working directory, output directory, executable, timeout, expected input/output files, required packages, environment context, safety review, and confirmation fields). The request is deterministically hashed (`request_hash`); confirmation is bound to that exact hash and is invalidated by any execution-relevant change. Inline `code` mode is fully eligible; script-path mode currently **fails closed** and is refused outright, because no trustworthy content-fingerprinting mechanism for on-disk scripts exists yet. This contract is a summary-level internal design document, not a change to the code-execution result schema — see the linked document for the full field table.

**Runtime state-machine contract** (`planning/v0.31.0-runtime-state-machine-contract.md`): 13 authoritative states (`advisory` through `completed`/`cancelled`/`blocked`), 18 valid transitions, and 14 explicitly prohibited transitions (most importantly: no path reaches `executing` without a genuine `confirmed` predecessor, and no `request_hash` is ever invoked more than once). Confirmation is consumed atomically with invocation authorization — never merely "logically before" it. Terminal instances (`completed`, `cancelled`, `blocked`, or a malformed `execution_failed`) are never resurrected; any rerun is a wholly new request with its own lifecycle. State loss (an interrupted process, an ambiguous outcome) fails closed rather than assuming a result. Cancellation during a synchronous execution call does not imply the underlying process was actually terminated — see the linked document for the full transition tables and 20-item invariant list.

**Mock controller boundary:** see [Scripts](scripts/README.md) for `scripts/gauss_runtime_orchestration.py`'s full documentation, including the exact non-GAUSS test command. In short: it is mock-only, in-memory, and fake-runner-only — it never imports `scripts/gauss_code_execution.py`, never launches a subprocess, and never invokes `gauss.exe`/`tgauss.exe`.

## Durable Execution State and Cross-Process Safety (`v0.36.0`)

`v0.36.0` replaces the controller's in-memory-only safeguards with an optional, standard-library SQLite-backed durable state layer. See `planning/v0.36.0-implementation-report.md` for the complete evidence, and `planning/v0.36.0-readiness-checklist.md` for the readiness assessment. **No GAUSS was run anywhere in this milestone's own work.**

- **The store**: `scripts/gauss_orchestration_state_store.py` (new) — a four-table SQLite schema (`schema_meta`, `orchestration_records`, `transition_events`, `invocation_attempts`), idempotent versioned initialization, and one atomic transaction (`authorize_invocation(...)`) that verifies every precondition (state, hash, session, confirmation validity/scope/expiry, no prior invocation) before committing confirmation-consumption, invocation-ID recording, and the transition to `executing` — all before any helper is ever called.
- **Genuine cross-process protection**: five real, separate OS processes racing to authorize the same durable record produce exactly one success, every time (`scripts/test_gauss_orchestration_state_store_concurrency.py`, run twice for stability) — not a single-process simulation.
- **Four modeled crash points, honestly disclosed**: before authorization commit (no trace, confirmation unconsumed), after commit but before the helper call (ambiguous, surfaced for manual review, never auto-retried), after the helper call but before result persistence (identical, indistinguishable signature to the prior point — a disclosed limitation, not silently resolved), and after result persistence (evidence preserved, safe to continue from).
- **Fail-closed on corruption**: seven scenarios (malformed JSON, unrecognized state, impossible confirmation state, a deleted transition-history row, a UNIQUE-blocked duplicate invocation attempt even via raw SQL, an unsupported schema version, authorization against corrupted state) all refuse to proceed; none are auto-repaired.
- **Redaction verified, not just designed**: only a SHA-256 digest of inline code is stored, never the code itself — verified by scanning the produced database file's raw bytes for a distinctive marker and confirming it never appears. `stdout`/`stderr`/output content/secrets/credentials/environment values are never persisted, mirroring this codebase's two pre-existing "safe summary" precedents.
- **Fully optional, fully backward compatible**: `MockOrchestrationInstance` still defaults to `state_store=None`; every one of the 85 pre-existing controller tests passes unmodified. A new explicit factory, `build_durable_orchestration_instance(...)`, is the one named entry point for durable construction.
- **New test coverage**: `scripts/test_gauss_orchestration_state_store.py` (52 tests), `scripts/test_gauss_orchestration_state_store_concurrency.py` (15 genuine multiprocessing/crash-simulation tests), and 10 new controller-integration tests (`scripts/test_gauss_runtime_orchestration.py`, 85 → 95).
- **Evaluation**: the `37.x` Durable Execution State and Cross-Process Safety benchmark category (`37.1`-`37.24`) evaluates conversational judgment about this milestone's evidence, without running GAUSS itself — **24/24 passed at 4.0**.

**What this milestone does not establish**: distributed exactly-once execution, multi-machine coordination, protection across different database files, protection against manual database tampering, crash-safe knowledge of whether GAUSS actually launched near the invocation boundary, automatic repair/retry/rerun, or any conversational/agent/workflow integration. `planning/v0.36.0-readiness-checklist.md` distinguishes explicitly between a bounded, local, durable-state milestone and a production-ready or distributed system.

## Persistent Execution Sessions and the Execution Session Model (`v0.38.0`-`v0.40.0`)

`v0.38.0` (`planning/v0.38.0-persistent-execution-sessions.md`) designed, without implementing, how a confirmed-but-not-yet-invoked request could safely persist across processes and agent turns — directly motivated by `v0.37.0`'s own discovered finding that only the originating process can invoke a confirmed request today. `v0.39.0` (`planning/v0.39.0-execution-session-model.md`) resolved that design's open identity question: Execution Request, Execution Session, and Execution Instance are three separate concepts with three separate identifiers, never collapsed into one, plus a session-only six-state machine (`created`/`awaiting_confirmation`/`confirmed`/`ready`/`expired`/`cancelled` — deliberately excluding `running`/`completed`/`failed`, which belong to instances). `v0.40.0` implemented that model as `scripts/gauss_execution_session.py` — an in-memory-only `ExecutionSession` value type plus `create_session`/`confirm_session`/`validate_session`/`expire_session`/`cancel_session`/`invalidate_session`/`get_session_state`, with `request_hash`/`plan_digest`-bound confirmation and replay prevention (26/26 tests). ## GAUSS Workspace Abstraction and Execution Integration (`v0.41.0`-`v0.43.0`)

`v0.41.0` (`planning/v0.41.0-file-artifact-workflow-design.md`) designed the architecture needed to move from "user provides code" to "user provides a GAUSS project workspace" — a workspace abstraction and lifecycle, a file manifest model, a three-category artifact model (input/execution/derived), file security boundaries, and a safe file-reading workflow, all without implementation. `v0.42.0` implemented the first slice as `scripts/gauss_workspace.py` — an in-memory `WorkspaceRegistry` with workspace identity, a seven-state lifecycle (`created`/`populated`/`ready`/`executing`/`completed`/`archived`/`deleted`), bounded-filesystem path validation (traversal and absolute-path escapes rejected), and a basic metadata-only manifest (24/24 tests; no real filesystem mutation anywhere in the module). `v0.43.0` wired that registry into `scripts/gauss_execution_workflow.py`: `ExecutionWorkflow` gained an optional `workspace_registry` and `propose_execution(...)` gained an optional `workspace_id`, both fully additive; a workspace-bound proposal auto-derives/validates its paths against the workspace root, `execute(...)` drives the workspace's own `ready → executing → completed` lifecycle around invocation (via `try`/`finally`, so it can never be stranded in `executing`), and every output file is automatically registered into the workspace manifest with full provenance (`WorkspaceProvenance`: `workspace_id`, `execution_session_id`, `execution_instance_id`, metadata-only artifacts) — 18/18 new tests, zero regressions across five pre-existing suites.

## Safe Workspace File Reading Workflow (`v0.44.0`)

`v0.44.0` (`planning/v0.44.0-safe-file-reading-workflow.md`) closes the gap every prior workspace milestone deliberately left open: nothing before this could read a file's actual contents. `scripts/gauss_workspace_file_reader.py`'s single entry point, `read_workspace_file(request, *, workspace_registry)`, always requires an explicit `WorkspaceFileReadRequest` — there is no scan, no automatic read after execution, and no read triggered by output metadata alone. Supported formats are bounded to allowlisted text (`.txt`, `.csv`, `.tsv`, `.out`, `.log`, `.gss`, `.dat`), every one of which is still rejected if its actual bytes look binary regardless of extension; reads are capped at a conservative 256 KiB by default (5 MiB absolute ceiling, never exceeded), UTF-8 only, and never silently truncated unless the request explicitly allows it (in which case `truncated=True` and the reported size/checksum describe only the bytes actually returned). Every rejection (missing file, unsupported type, path outside the workspace, oversized, binary content, etc.) is a structured, specifically-coded result — never a raised exception, never described as an execution failure. `ExecutionWorkflow.read_workspace_file(...)` is the only workflow-layer path to a read. Reading content still does not prove methodology or statistical validity — restated, not weakened, from every prior execution-evidence boundary. 25 reader tests + 6 workflow-integration tests, zero regressions across seven pre-existing suites; `39.x` benchmark prompts (`39.1`-`39.10`) were added, not yet evaluated (`Not Run`, deferred to the next evaluation task by this milestone's own instruction).

## Vision

Large language models have become remarkably capable programming assistants, but they often struggle with domain-specific languages like GAUSS. Generic coding assistants frequently hallucinate syntax, recommend nonexistent functions, or ignore established programming conventions.

The goal of GAUSS AI is to build a framework that combines authoritative GAUSS knowledge with structured reasoning and evaluation to produce reliable, explainable, and maintainable AI assistants for the GAUSS ecosystem.

## Guiding Principles

* **Accuracy over confidence.** When uncertain, retrieve authoritative information instead of guessing.
* **Official sources first.** Prefer the official GAUSS documentation and vetted reference repositories.
* **Specialization beats generalization.** Small, focused agents are easier to improve than one large, general-purpose assistant.
* **Reusable architecture.** Expertise, knowledge, prompts, tools, and evaluations should be shared across agents whenever possible.
* **Continuous evaluation.** Every improvement should be measurable using benchmark tasks and scoring criteria.

## Repository Organization

* `agents/` — Agent definitions, behavior, capabilities, and constraints.
* `experts/` — Domain-specific reasoning, best practices, knowledge notes, and common mistakes shared across agents.
* `adr/` — Architecture Decision Records for significant framework decisions.
* `prompts/` — Shared system, developer, and task prompts.
* `configs/` — Knowledge source configuration and runtime settings.
* `tools/` — Tool definitions and integrations.
* `workflows/` — Repeatable workflows and playbooks.
* `evaluations/` — Benchmarks and scoring rubrics.
* `benchmarks/` — Benchmark datasets and evaluation results.
* `examples/` — Representative tasks and reference interactions.
* `scripts/` — Implemented, runnable helpers (see [Scripts](scripts/README.md)) — environment detection, package inspection, code execution, the mock runtime orchestration controller, and validation/tracking guards.
* `planning/` — Per-milestone design documents, including the authoritative `v0.31.0` runtime orchestration contracts.

Expert modules encapsulate reusable domain expertise so multiple specialized agents can draw on consistent reasoning patterns and best practices without duplicating guidance.

## Roadmap

See [ROADMAP.md](ROADMAP.md) for the full, milestone-by-milestone history. Looking forward from the current `v0.68.0` Private Alpha:

* **Private Alpha** (current) — the installable product, validated end to end against real GAUSS, in the hands of a small group of testers.
* **Real-world testing** — feedback from testers repairing their own `.gss` files, not just the bundled demo.
* **Usability improvements** — narrowing any confusing wording or friction points real testers surface, without adding new approval layers, reasoning stages, or autonomous behavior.
* **Expanded verified diagnostics** — growing the verified GAUSS error catalog and repair strategies as new real errors are encountered and reproduced.
* **Platform expansion** — extending verified real-GAUSS execution beyond the current Windows/GAUSS 26.1.1 scope, as evidence supports it.
* **Future public beta** — broader availability once private-alpha feedback and platform coverage support it; not yet scheduled or authorized.
