# Changelog

This file records notable changes to the GAUSS AI framework.

## [Unreleased]

- Added `v0.65.0` Verification Review and Outcome Recording: `scripts/gauss_verification_review.py` is a human review layer over Verification Execution -- it records what a human concluded after inspecting a completed verification's own `ComparisonSummary` evidence, and never infers that conclusion automatically.
- Added `VerificationReview` (immutable; `review_id`, `verification_execution_id`, `comparison_summary_digest`, `decision`, `notes`, `reviewed_at`, `reviewed_by`, `boundary`). Holds no field capable of referencing the underlying `RepairDraft`, `RepairPlan`, `ApplicationResult`, `VerificationExecutionRequest`, or `ComparisonSummary` objects -- only two opaque strings.
- Added `comparison_summary_digest(summary) -> str`: a new SHA-256 content fingerprint over `ComparisonSummary`'s own five fields, using the repository's standard canonical-JSON convention. No such digest existed before this milestone.
- Added `ReviewDecision` (`accepted`/`rejected`/`inconclusive`) and `VerificationReviewStore` with three explicit methods -- `accept(...)`/`reject(...)`/`mark_inconclusive(...)` -- mirroring `ApplicationApprovalStore.approve(...)`/`.decline(...)`. Deliberately **no revoke operation**: a review is write-once per `verification_execution_id`; a second review attempt always raises `DuplicateVerificationReviewError`, even for the identical decision. `InvalidVerificationReferenceError` and `ComparisonNotAvailableError` enforce that only a completed verification (a genuine `ComparisonSummary` instance) can be reviewed.
- Added a fixed, decision-invariant `VERIFICATION_REVIEW_BOUNDARY` string ("This review records a human conclusion about the verification evidence. The system is not determining whether the repair is correct...") present on every record, satisfying this milestone's own required CLI disclosure text by construction.
- Added the CLI `review-verification --decision {accepted|rejected|inconclusive} [--notes TEXT] [--reviewed-by NAME]`/`show-verification-review` commands. Reviewing requires an already-completed verification execution -- the same precondition `show-verification-request`'s own comparison output already enforces; the shared comparison-computation logic was factored out of `_show_verification_request` into a private `_current_comparison_summary()` helper (a pure refactor -- `show-verification-request`'s own output is byte-for-byte unchanged, confirmed by a new regression test). `reset` now also clears the verification-review store.
- Added `scripts/test_gauss_verification_review.py` (27 tests: accepted/rejected/inconclusive, duplicate-review handling, invalid verification reference, comparison-not-available, immutability, structural no-verdict-field checks, and architectural import/definition scans) and 15 new CLI tests (134-148).
- Added a `55.x` Verification Review evaluation category (ten prompts, matching coverage rows) and fully evaluated it against real, executed evidence.
- Added `planning/v0.65.0-verification-review.md`, `release-notes-v0.65.0.md`, and `docs/gauss-verification-review.md`.
- `scripts/gauss_verification_execution.py` and `scripts/gauss_repair_application.py` both have zero diff -- `scripts/gauss_verification_review.py` imports `gauss_verification_execution` only for the `ComparisonSummary` type, never the reverse.
- No automatic decision inference, no revoke, no execution/planning/repair/rollback triggered by a review, no approval-store mutation, and no consumer anywhere of a recorded review's own decision -- none were added, per this milestone's own explicit scope.

- Added `v0.64.0` Verification Execution Workflow: `scripts/gauss_verification_execution.py` executes an already-applied repair's resulting source through the existing, unmodified execution pipeline and collects evidence — not automatic repair validation, automatic acceptance, autonomous retry, autonomous repair, or autonomous planning.
- Added `VerificationExecutionRequest` (immutable; `verification_execution_id`, `repair_application_id`, `application_result_id`, `workspace_id`, `relative_path`, `expected_post_repair_hash`, `reason`, `created_at`) and `build_verification_execution_request(...)`, which references only an already-successful `ApplicationResult` — never a `RepairDraft` directly, structurally. Raises `RepairNotAppliedError` for any non-`"applied"` outcome.
- Added `propose_verification_execution(...)`: re-reads and re-hashes the repaired file (reusing `ExecutionWorkflow.read_workspace_file(...)`), fails closed on a stale hash, then calls `ExecutionWorkflow.propose_execution(...)` — the exact same method, returning the exact same `wf.ProposalOutcome`/`wf.ExecutionProposal` types, any ordinary execution proposal already uses. The proposal deliberately omits `workspace_id=` (the workspace already completed its one-shot lifecycle from the original failing execution) and uses `working_directory=<the workspace's own real root_path>` instead — an already-supported, pre-`v0.43.0` code path, not a new capability.
- Added `compare_execution_outcomes(original, verification) -> ComparisonSummary`: a pure function consuming two already-computed `ExecutionInterpretation` objects and reporting one of five named, evidence-only observations. `ComparisonSummary` has no `repair_correct`, `success_probability`, or `confidence_score` field anywhere.
- Added the CLI `verify-repair [--fake-success|--fake-failure|--fake-timeout|--fake-unknown-error]`/`show-verification-request` commands. `verify-repair` populates the adapter's existing `mvp_session`/`pending_request` fields so the pre-existing, completely unmodified `confirm`/`execute` commands drive the verification run with zero new confirmation/execution code. `show-verification-request` shows the request and, once execution completes, the comparison. `reset` now also clears the verification request and the snapshotted original-execution interpretation.
- Added `scripts/test_gauss_verification_execution.py` (24 tests, including `isinstance` checks proving genuine reuse of `wf.ProposalOutcome`/`wf.ExecutionProposal`/`wf.ConfirmationOutcome`/`wf.ResponseReadyResult`, and structural checks proving no repair-specific execution engine or forbidden import exists) and 10 new CLI tests (124-133, covering all three of the task's own worked comparison examples against real evidence).
- Added a `54.x` Verification Execution Workflow evaluation category (ten prompts, matching coverage rows) and fully evaluated it: 10/10 Passed at 4.0, 0 Critical/Major/Minor defects.
- Added `planning/v0.64.0-verification-execution-workflow.md`, `release-notes-v0.64.0.md`, and `docs/gauss-verification-execution.md`.
- `scripts/gauss_execution_workflow.py` and `scripts/gauss_repair_application.py` both have zero diff — `scripts/gauss_verification_execution.py` is the only module importing both, purely as a translation adapter between them, proving "repair knows nothing about execution, execution knows nothing about repair."
- No automatic retries, automatic repair acceptance, automatic rollback, automatic planning, automatic code editing, repair scoring, LLM repair loops, repair ranking, or autonomous execution were added.

- Added `v0.63.0` Repair Application Evaluation and Hardening: an evaluation milestone exercising `scripts/gauss_repair_application.py` (`v0.62.0`) under real filesystem conditions across twenty named scenarios, using the actual application workflow (direct module calls and the real CLI path) against real, on-disk, temp-directory-backed workspaces and genuine `.gss` files.
- **Fixed a genuine defect**: an empty or whitespace-only `replacement_text` previously applied silently as a full line deletion (zero replacement lines spliced in), rather than being refused — a scope violation ("no deletes") this repository's own design explicitly excludes. Added a new `REPLACEMENT_TEXT_NON_EMPTY` check, blocking with reason `replacement_text_empty` before candidate construction ever runs.
- **Fixed a second genuine defect**: `replacement_text` not representable in UTF-8 (e.g. a lone surrogate) previously raised an uncaught `UnicodeEncodeError` straight out of `apply_repair(...)`, violating the module's own fail-closed design. Added a new `CANDIDATE_ENCODABLE` check, wrapping the encode call and converting the failure into a clean `blocked` result with reason `candidate_not_utf8_encodable`.
- A successful application now reports 18 named checks (previously 16) — purely additive; no existing check's name, ordering, or semantics changed.
- Added `scripts/test_gauss_repair_application.py` tests 28-33 (28-29 are direct regressions for the two fixes; 30-33 directly cover beginning/middle/end-of-file edits, Unicode content, and repeated sequential applications). `test_09` updated to reflect the more specific blocking reason introduced by the first fix. Grew from 27 to 33 tests; full existing regression suite unaffected.

- Added `v0.62.0` Bounded Single-File Repair Application Transaction: `scripts/gauss_repair_application.py`, the first module in this repository capable of writing to a real file. Implements Section 14 of the `v0.58.0` design, bounded to one existing UTF-8 `.gss` file, one workspace, and one already-approved `RepairDraft`.
- Added `apply_repair(...)`: re-validates source identity (a real, hash-verified read), re-evaluates the application gate, creates a workspace-contained backup, constructs and validates an in-memory candidate from caller-supplied `replacement_text`, writes a temp file, atomically replaces the target via `os.replace(...)`, verifies the resulting hash, and returns an immutable `ApplicationResult`. Any single failure blocks (nothing written) or fails (write attempted but unverified) the entire transaction.
- Added `ApplicationTransactionOutcome` (`applied`/`blocked`/`failed`), `ApplicationTransactionCheck` (16 named checks), `ApplicationResult`, `BackupIdentity`.
- Backup is exactly one per attempt, named from the target's relative path plus a content-hash prefix plus a timestamp; never overwritten (a numeric suffix is appended on collision); never deleted, including on a subsequent block or failure.
- `replace_fn`/`write_temp_file_fn` are injectable, mirroring `WorkspaceRegistry`'s own `clock`/`id_factory` convention, enabling deterministic atomic-replace/temp-write failure tests without OS-level flakiness.
- Added the CLI `apply-repair <draft_digest> --replacement-text TEXT`/`show-application-result` commands, mirroring `approve-repair-application`'s own stale-digest-rejection behavior; every response discloses `file_modified`, `backup_created`, and `rerun_performed: false` explicitly. `reset` now also clears `last_application_result`.
