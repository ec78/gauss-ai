# Known Limitations

These limitations apply as of the `v0.22.0` GAUSS Package Inspection Tool milestone.

## Retrieval and Lookup

- The framework does not yet execute GAUSS code.
- Command-specific documentation retrieval has a lightweight local script prototype (`scripts/command_doc_lookup.py`), not a full semantic search system. It depends on having a local official GAUSS documentation checkout available on disk; retrieval is local-first, not hosted.
- The lookup script uses heuristic pattern matching (heading underlines, `.. function::` directives, keyword substring search) rather than a full reStructuredText parser, so it can misparse unusual formatting.
- Extraction may truncate long sections; not every documented field (for example, every member of a large output structure) is guaranteed to be captured.
- Keyword search can miss conceptually relevant text when the official wording differs from the requested keyword (for example, a doc that says "no occurrence is found" will not match a literal search for "not found").
- Retrieval coverage now spans seven real, end-to-end tested commands (`olsmt`, `strindx`, `strsplit`, `dstatmt`, `qnewtonmt`, `pdsummary`, `minimize`) across varied documentation shapes, but this remains a small pilot set relative to the full GAUSS command surface; broader coverage is unverified.
- Curated command notes are a small convenience cache, not a replacement for official GAUSS documentation.
- The Code Assistant must not invent syntax when official docs are unavailable.

## Evidence Schema and Validation

- Schema validation (`schemas/command_lookup_evidence.schema.json`, `scripts/validate_lookup_evidence.py`) checks evidence *structure* — required fields, enum values, types — not GAUSS semantic correctness. A schema-valid object can still describe outdated or incorrect command behavior.
- A schema-valid evidence object is not proof that GAUSS code was executed. Schema validity and execution are unrelated claims.
- The evidence schema does not replace official GAUSS documentation, which remains authoritative for exact syntax, defaults, and return values.
- Evidence can become stale relative to official docs. When exact syntax or defaults matter, evidence should be regenerated against current documentation rather than relied on indefinitely; the schema can represent staleness (`stale_evidence`) but cannot yet detect it automatically.
- Some evidence states (ambiguous, conflict, stale, schema-invalid) are currently represented only by hand-built synthetic fixtures under `examples/retrieval/schema-fixtures/`, not generated automatically from real lookups.
- `conflict` and `stale` retrieval statuses are represented in the schema but not yet automatically generated by `scripts/command_doc_lookup.py` — there is no curated-note comparison logic or staleness-detection logic in the script yet.
- The validator's path-detection warning can produce false positives for official documentation examples that happen to contain path-shaped strings (confirmed: an HDF5 URI example in official `olsmt` documentation triggers two such warnings). This is a known, reviewed exception under the `v0.7.0` strict-mode policy (see below), not a hidden defect.
- Schema-aligned output is available through `--schema-output`, but legacy lookup output remains the default and is not schema-aligned unless the flag is passed. Legacy lookup JSON files (`examples/retrieval/olsmt.lookup.json`, `examples/retrieval/strindx.lookup.json`) predate the schema and may not match the schema-aligned evidence format.
- Current schema-aligned examples cover seven real GAUSS commands (`olsmt`, `strindx`, `strsplit`, `dstatmt`, `qnewtonmt`, `pdsummary`, `minimize`); broader coverage across the full GAUSS command surface remains unverified.
- `scripts/validate_all_evidence.py` aggregates the single-file validator's results across all committed examples and fixtures; it does not add new validation rules of its own, does not execute GAUSS, and does not access the network. The `v0.7.0` release-health bar is the default non-strict run; `--strict` currently fails only because of the two known, reviewed `olsmt.evidence.json` path-warning false positives above — this is documented policy, not a suppressed failure, and improving the path-warning heuristic so this stops triggering is tracked as future work.

## Expert Routing and Operational Modules

- Expert routing (`workflows/expert-routing.md`, `experts/gauss-language/OPERATIONAL_PROFILE.md`, `experts/econometrics/OPERATIONAL_PROFILE.md`, `experts/software-engineering/OPERATIONAL_PROFILE.md`, `experts/documentation/OPERATIONAL_PROFILE.md`, `experts/education/OPERATIONAL_PROFILE.md`, `experts/product/OPERATIONAL_PROFILE.md`, `tools/operational_expert_interface.md`) is a documentation/checkable-workflow contract, not a runtime instrumentation layer. No code parses or enforces these files at runtime; a response is checked against them manually, the same way task-mode fit is checked today.
- Six experts are operationalized as of `v0.17.0`: the GAUSS Language Expert (implementation correctness, `v0.8.0`), the Econometrics Expert (methodological correctness, `v0.9.0`), the Software Engineering Expert (maintainability/design correctness, `v0.14.0`), the Documentation Expert (documentation/explanation correctness, `v0.15.0`), the Education Expert (education/learning-design correctness, `v0.16.0`), and the Product Expert (product/user-value correctness, `v0.17.0`). There is no remaining narrative-only expert placeholder.
- `v0.18.0` added consolidation-only documentation on top of the existing six experts: an expert registry (`experts/EXPERT_REGISTRY.md`), a boundary matrix (`experts/EXPERT_BOUNDARY_MATRIX.md`), a routing cheat sheet (`workflows/expert-routing-cheatsheet.md`), an evaluation dashboard (`evaluations/EVALUATION_DASHBOARD.md`), and a maintenance guide (`workflows/expert-system-maintenance.md`), plus a profile consistency audit (`planning/v0.18.0-operational-profile-audit.md`) that fixed stale cross-reference wording in four `OPERATIONAL_PROFILE.md` files. These are documentation/consolidation references that summarize and cross-reference existing expert behavior — each states this explicitly in its own introduction. None of them implement runtime orchestration, a routing engine, or automated stale-wording detection; routing remains manual/documented/evaluation-driven, exactly as it has been since `v0.8.0`. No expert's correctness dimension should be inferred from another's — this remains true regardless of how many consolidation documents summarize the boundaries.
- Manual evaluation still determines whether correct routing occurred (activation, non-activation, decision-rule application, evidence/context-threshold compliance) — there is no automated multi-expert routing test harness.
- Multi-expert *routing* is documented (`workflows/expert-routing.md` uses a compact activation matrix and common routing patterns as of `v0.17.0` — GAUSS-only, Econometrics-only, Software-engineering-only, Documentation-only, Education-only, Product-only, Product + Documentation, Product + Education, Product + GAUSS, Product + Econometrics, Product + Software Engineering, Documentation + Education + Product, GAUSS + Documentation + Education + Product, GAUSS + Econometrics + Product, all six, and Neither, with coordination rules for every multi-expert case, deliberately not enumerating all 64 mathematically possible combinations), but no runtime multi-expert *orchestration engine* exists, and no automated conflict-resolution engine exists beyond those documented coordination rules — surfacing a conflict or tension between activated experts' conclusions is a response-writing responsibility, not an automated check.
- Expert profiles add domain-specific constraints on top of existing evidence requirements; they do not replace or weaken them. GAUSS command evidence requirements still depend on the retrieval workflow and evidence schema, remain entirely separate from the Econometrics Expert's methodological context requirements, the Software Engineering Expert's design/behavior-preservation context requirements, the Documentation Expert's reader/documentation-type context requirements, the Education Expert's learner/learning-goal/time-horizon context requirements, and the Product Expert's user/problem/workflow context requirements — meeting one is never sufficient to satisfy another. Command availability is never evidence of methodological validity; methodological plausibility never justifies inventing GAUSS syntax; clean, well-organized code is never evidence of statistical or causal validity; valid GAUSS syntax is never evidence of good design; clear documentation is never evidence of syntax correctness, statistical validity, or maintainability; a well-designed lesson is never evidence of syntax correctness, statistical validity, maintainability, or documentation quality; and a compelling product recommendation is never evidence of syntax correctness, statistical validity, maintainability, documentation quality, or education quality.
- The Software Engineering Expert cannot independently verify GAUSS syntax (that remains the GAUSS Language Expert's evidence-backed claim) or independently verify statistical/methodological validity (that remains the Econometrics Expert's claim) — it may recommend structure, refactoring, and tests, but may not invent GAUSS syntax or claim code/tests were executed unless they actually were.
- The Documentation Expert cannot independently verify GAUSS syntax, statistical/methodological validity, or code maintainability/design (those remain the GAUSS Language Expert's, Econometrics Expert's, and Software Engineering Expert's claims respectively) — it may improve wording, structure, examples, and comments/docstrings, but may not invent GAUSS syntax, certify statistical validity, certify maintainability, or claim code/tests were executed unless they actually were. It is also explicitly distinct from the Education Expert: documentation supports task completion and reference use right now, while education supports learning over time through sequencing, scaffolding, exercises, and pedagogy.
- The Education Expert cannot independently verify GAUSS syntax, statistical/methodological validity, code maintainability/design, or documentation/reference clarity (those remain the GAUSS Language Expert's, Econometrics Expert's, Software Engineering Expert's, and Documentation Expert's claims respectively) — it may design learning objectives, sequences, scaffolding, practice, feedback, and assessment, but may not invent GAUSS syntax, certify statistical validity, certify maintainability, certify documentation quality, or claim code/tests were executed unless they actually were. It is also explicitly distinct from the Product Expert: a good training curriculum is never evidence a feature is valuable, that product-market fit exists, or that a feature should be prioritized.
- The Product Expert cannot independently verify GAUSS syntax, statistical/methodological validity, code maintainability/design, documentation/reference clarity, or learning-design quality (those remain the GAUSS Language Expert's, Econometrics Expert's, Software Engineering Expert's, Documentation Expert's, and Education Expert's claims respectively) — it may frame user problems, workflow fit, adoption risk, value propositions, positioning, and prioritization tradeoffs, but may not invent GAUSS syntax, certify statistical validity, certify maintainability, certify documentation quality, certify learning-design quality, or claim code/tests were executed unless they actually were. Market validation, product-market fit, adoption certainty, willingness to pay, or prioritization certainty require actual user/customer evidence — never asserted from an internally plausible narrative alone — and product hypotheses must be labeled as hypotheses when that evidence is missing.
- Schema validation still does not prove GAUSS semantic correctness or that any GAUSS code was executed — this remains true regardless of which expert(s) consulted the evidence.
- Expert activation is internal by default; responses are not required to state which expert(s) were consulted, which means routing correctness can only be confirmed by inspecting response content, not by reading a self-reported label.
- `glm.evidence.json` (real, schema-aligned) now exists locally for logistic/probit and other generalized linear models, closing the gap where a `v0.9.0` benchmark evaluation had to verify `glm` against live official documentation instead.
- A verified native GAUSS panel-estimation command has been confirmed: `tscsFit`, which estimates a pooled time-series-cross-section regression model and returns both fixed-effects and random-effects coefficient estimates (`examples/retrieval/schema-aligned/tscsfit.evidence.json`; full audit in `examples/retrieval/panel-estimation-coverage-audit.md`). It requires the separately licensed TSMT package (not bundled with base GAUSS, requires GAUSS/GAUSS Engine v25+) — this package dependency must be stated whenever it is recommended. `lsdvFit`'s applicability to panel fixed-effects estimation remains unclear and unresolved; no dynamic-panel-GMM command was found in the audited local docs.
- `scripts/command_doc_lookup.py` now distinguishes `official_docs` from `official_package_docs` for package-located files (fixed `v0.11.0`): a matched file's docs-root-relative path is checked against a known set of GAUSS "Application" (package) directories, derived from the official Applications index (`docs_root/applications.rst`). `tsmt/tscsfit.rst` now classifies as `official_package_docs`/`official_package_rst`; core-docs files like `glm.rst`/`olsmt.rst` are unaffected. This classification depends on a hardcoded snapshot of the Applications index (`PACKAGE_DOC_DIRECTORIES` in `command_doc_lookup.py`) that should be refreshed if that index changes; a directory missing from the snapshot is classified as core documentation by default (under-classification, not mis-classification). The concrete refresh steps are documented in `scripts/README.md`'s "PACKAGE_DOC_DIRECTORIES refresh process" section (added `v0.12.0`). The Code Assistant must still state package dependencies explicitly regardless of what the evidence file's `source_authority` field says — this classification is a labeling convenience, not a substitute for stating the dependency in the response.

## GAUSS Environment, Package Inspection, and Execution

- A GAUSS environment detection helper now exists: `scripts/gauss_environment_check.py`, implementing the contract specified in `tools/gauss_environment_check.md` and validated against `schemas/gauss_environment_check.schema.json`. It is read-only (no user file modification, no environment mutation, no package installation, no license activation), returns schema-valid structured output for every detection path, and is both CLI-usable and importable (`detect_environment(...)`). A built-in `--self-test` suite passes (no formal `tests/` directory exists in this repository yet), and the helper has been manually verified against this development machine's real GAUSS 24/25/26 installations.
- The helper selects the newest/highest detected GAUSS version by default when multiple installations are found (for example, selecting GAUSS 26 over GAUSS 24/25 if all three are detected), unless the caller provides a preferred executable path (highest priority) or a preferred GAUSS version (overrides the newest-version default) — both confirmed working in manual verification. A newest-but-inaccessible candidate is never silently downgraded to an older accessible one; the helper returns `ambiguous` with an explicit warning instead, per `planning/v0.21.0-gauss-environment-detection-implementation.md`'s "Default Version Selection Rule."
- `--allow-version-query` is accepted by the helper but does not currently invoke any GAUSS executable, because no safe, confirmed GAUSS version-query command-line flag is documented in this repository yet; passing it only adds an explanatory warning to the result. This remains a documented gap, not a silent omission.
- Real cross-platform GAUSS executable names and installation paths still need broader validation. `scripts/gauss_environment_check.py`'s candidate lists (`PLAUSIBLE_EXECUTABLE_NAMES`, `COMMON_LOCATION_TEMPLATES`) are a conservative starting set confirmed to work against this development machine's Windows installations, not a verified-exhaustive list across Windows/macOS/Linux/WSL/containers.
- `environment_overrides` (from the tool spec's original input contract) remains deliberately unimplemented — safely simulating an alternate environment without risking a misleading result was judged nontrivial for `v0.21.0` and is deferred.
- Installation detection does not prove syntax validity, package availability, statistical validity, maintainability, documentation quality, learning quality, or product value — `planning/v0.20.0-gauss-environment-detection-tool.md`'s "Relationship to Six Experts" and "Expert Boundary Rules" sections state this explicitly for each of the six correctness dimensions plus package availability, applying the same independence principles from `experts/EXPERT_BOUNDARY_MATRIX.md` to the specific, narrower case of environment detection. Detecting and selecting the newest installed GAUSS version is no exception — selecting GAUSS 26 over older versions is an implementation-detail preference, not evidence that any of these six correctness dimensions, or package availability, hold for that version.
- `execution_candidate` (the `operating_mode_recommendation` a `found` detection result carries) is not active execution. A `found`/`execution_candidate` result — from the real helper or a synthetic example — never means GAUSS code has run or that Execution Mode is active; it is a prerequisite signal only, per `tools/gauss_environment_check.md`'s Operating Mode Relationship section. Execution Mode itself remains entirely inactive — no execution tool exists.
- Advisory mode remains the fallback whenever detection fails, GAUSS is unavailable, GAUSS is inaccessible, or detection is ambiguous. This is implemented and confirmed in `scripts/gauss_environment_check.py` (every non-`found` path returns `operating_mode_recommendation: advisory`), and separately validated against documented expected assistant response behavior via the `26.x` benchmark category (8/8 passed at 4.0).
- The framework does not yet actually inspect installed GAUSS packages. The `gauss_package_inspection` tool is fully specified (`tools/gauss_package_inspection.md`), its result schema exists (`schemas/gauss_package_inspection.schema.json`), and five synthetic example outputs (`examples/tools/gauss-package-inspection-complete.json`, `-missing.json`, `-partial.json`, `-unavailable.json`, `-unknown.json`) exist, with an evaluated benchmark category (`27.x`, `27.1`-`27.8`, 8/8 passed at 4.0) — but no implementation exists. The `27.x` benchmarks validate documented expected assistant response behavior against hypothetical/synthetic package-inspection results, not real package inspection; no code has inspected any actual GAUSS installation's packages. Environment detection (`v0.21.0`) confirms whether GAUSS is installed and which executable/version would be used; it does not reveal which GAUSS packages or application modules are installed — package inspection is a separate, dependent capability. Implementation is deferred to `v0.23.0` (`planning/v0.22.0-gauss-package-inspection-tool.md`'s scope decision: `v0.22.0` is the specification/evaluation milestone, not the implementation milestone, because of unresolved risks around real package/application-module locations, version-specific package contexts, licensing, and whether metadata-only inspection can be done safely).
- The project cannot actually determine installed/missing/unknown GAUSS package status for any command yet — `package_inspection_status` (`complete`/`partial`/`unavailable`/`error`/`unknown`) and the per-package `installed` field are specified and schema-validated in synthetic examples, but no real inspection produces them yet.
- Package availability may differ by GAUSS version. Once package inspection exists, it is planned to inspect the same GAUSS version environment detection selected by default (including `v0.21.0`'s newest-version default), and package results for one version must not be assumed to apply to another.
- Package availability, once implemented, will not prove syntax validity, statistical validity, maintainability, documentation quality, education quality, or product value — `planning/v0.22.0-gauss-package-inspection-tool.md`'s "Expert Boundary Rules" section states this explicitly, extending the same independence principles already established for environment detection (`planning/v0.20.0-gauss-environment-detection-tool.md`) and `experts/EXPERT_BOUNDARY_MATRIX.md` to the specific, narrower case of package availability. A missing package will not be treated as proof a method is invalid, and an installed package will not be treated as proof a method is appropriate. A package being installed does not mean any code ran, and a package being unknown is not the same as it being missing.
- Runtime orchestration remains unimplemented across the framework — neither environment detection nor package inspection (specified or, eventually, implemented) introduces any runtime orchestration engine.
- The framework does not yet execute GAUSS code. Code execution is planned but not implemented — there is no `tools/gauss_code_execution.md` or equivalent tool yet. This restates, and does not change, the long-standing limitation already listed above under "Retrieval and Lookup."
- Report generation from actual execution output is not yet implemented — there is no `workflows/analysis-result-reporting.md` or equivalent workflow yet.
- Current behavior remains advisory/verified-knowledge only: the Code Assistant can write, explain, review, document, and teach GAUSS code, and can cite verified command evidence, but cannot run code or confirm output against a real GAUSS session.
- Any future execution mode must be optional and gracefully degrade when GAUSS is unavailable — `planning/v0.19.0-gauss-tooling-strategy-and-execution-modes.md`'s "Graceful Fallback Principle" states this explicitly: the assistant must not break, must not claim execution, and must remain useful in advisory mode whenever GAUSS or an execution tool is unavailable. This is a design requirement for future milestones, not yet a tested behavior, since no execution tool exists to test.
- Successful execution, once implemented, will not prove statistical validity, maintainability, documentation quality, education quality, or product value — `planning/v0.19.0-gauss-tooling-strategy-and-execution-modes.md`'s "Relationship to Six Experts" section states this explicitly for each of the six correctness dimensions, extending the same independence principles already documented in `experts/EXPERT_BOUNDARY_MATRIX.md` to a future execution capability that does not exist yet.

## Evaluation and Process

- Retrieval-backed response behavior has manual evaluation coverage across key states, but it is not automatically enforced by a live agent runtime.
- Benchmark coverage is growing but not exhaustive.
- Preview quickstart materials exist, but they should still be tested by users who were not part of the design process.
- Manual evaluation runs are useful evidence, but automated regression evaluation is not implemented yet.
- Any tracked local machine-specific configuration should be removed, renamed, or clearly documented before broader public use.
- A local evaluation tracking consistency guard (`scripts/check_evaluation_tracking.py`, added `v0.10.0`) checks that `evaluations/benchmark-prompts.md`, `evaluations/benchmark-coverage.md`, `evaluations/runs/INDEX.md`, and the run files under `evaluations/runs/` stay consistent with each other. It runs both locally and in CI (as of `v0.13.0`, via `scripts/check_release_readiness.py`), and it does not check response quality or scoring correctness — that remains a manual-evaluation responsibility. Its default run reports 0 errors and exactly 2 documented historical warnings (a Prompt ID mismatch on a pre-stable-ID run file, and a legacy pre-Prompt-ID-era smoke-test run file that is intentionally not indexed); `--strict` fails only because those two warnings are promoted, which is expected policy, not a defect.
- Benchmark prompts that hardcode specific volatile repository counts (for example, an exact prompt-ID count or warning count) in their expected-behavior text can go stale as soon as later milestones add more prompts or runs, unless the benchmark is explicitly scoped to a fixed, frozen repository state. This was observed directly during the `v0.10.0` `17.5`/`17.6` evaluations; the correct evaluated behavior is to report the true live tool output rather than the prompt's originally-written figures. `v0.11.0` added benchmark-authoring guidance (`workflows/manual-evaluation.md`, "Benchmark Authoring Guidance") to reduce recurrence going forward, but this is process guidance for future authoring, not an automated guard against it — a future benchmark can still be written this way if the guidance isn't followed.
- `scripts/check_release_readiness.py` (added `v0.12.0`) runs the two default guard scripts (`validate_all_evidence.py`, `check_evaluation_tracking.py`) in one command and summarizes pass/fail. As of `v0.13.0`, it also runs automatically in CI (`.github/workflows/release-readiness.yml`) on every push and pull request, using its default (non-strict) mode — the same command a contributor would run locally. Its `--strict` mode remains informational only and does not affect its own exit code (locally or in CI), since strict-mode failure is currently expected for both underlying scripts (see `scripts/README.md`'s "Strict-mode policy and future CI expectations" section). Strict mode is not yet enforced by CI, and no non-blocking strict CI job or machine-readable strict-warning allowlist exists yet — both remain non-blocking follow-ups.
