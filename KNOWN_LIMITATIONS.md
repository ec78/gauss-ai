# Known Limitations

See also [docs/known-alpha-limitations.md](docs/known-alpha-limitations.md) for a shorter, tester-facing summary of current-phase limitations.

`v0.73.0` turned grounding from disclosure-only into an active generation gate, and added deterministic natural-language-to-symbol resolution -- both directly motivated by `v0.72.0`'s own live-evaluation failures and both extending the existing architecture, not a second one. `resolve_concepts(...)` maps natural-language phrases (e.g. "column means", "panel regression") to real, documented GAUSS symbols (`meanc`, `tscsfit`) via a small, explicit, human-curated alias index -- every entry doc-verified before being encoded, and every resolution independently re-verified again against the caller's own `docs-root` at call time, never trusted from the table alone. `compute_generation_gate(...)` turns grounding status into `GenerationPolicy.FULL`/`SUPPORTED_ONLY`/`CLARIFY`/`BLOCK`, computed before the provider is ever called -- `BLOCK`/`CLARIFY` never reach the model at all, confirmed live against a real, reachable Ollama service by instant response latency. `check_generated_symbols(...)` is a conservative post-generation check catching an unsupported function call even if the model still produces one. **Both exact `v0.72.0` failures were directly fixed and re-verified live**: "calculate the column means" now resolves to the real `meanc` (not `colmean`); "write a GAUSS panel regression" now resolves to the real `tscsFit` and generates its real call signature (not the fabricated `panel`/struct-field pattern). Three real defects were found live and fixed within this milestone: a real function (`rndu`) was flagged as unsupported until added to the checker's allowlist; a request with no explicit code-generation trigger phrase classified as QA, so the post-generation check never ran -- fixed by applying it whenever the answer is code-shaped, regardless of intent; a real companion function (`invpd`) documented alongside the resolved topic (`inv`) was flagged as unsupported -- fixed by also treating identifiers in a source's own retrieved content as supported. A `63.x` benchmark category was added and evaluated against the real local model, including a subtle secondary naming error (`tscsmtControl` vs. the real `tscsmtControlCreate`) the post-generation checker caught even in an otherwise successful scenario. Model hallucination is mitigated, not eliminated -- treat all generated code as unverified until checked yourself. This milestone still does not implement: autonomous conversational execution, conversational file writes or source-file editing, automatic repair application, autonomous retry/debug loops, multi-file autonomous changes, durable chat storage, telemetry, or a vector-database/full-RAG rewrite. Alpha readiness classification: **Private Alpha**.

`v0.72.0` added conversational GAUSS code generation and multi-source grounding, layered on the existing `v0.70.0`/`v0.71.0` conversational architecture rather than a second system. The single most significant finding, recorded as a genuine Fail rather than smoothed over: the same real model, asked for a panel regression, confidently fabricated an entire nonexistent syntax pattern with zero disclosed uncertainty and no clarifying question, directly contrary to its own code-generation instructions. **Model suitability verdict: SUITABLE WITH LIMITATIONS**, not unconditionally suitable -- treat all generated code as unverified until checked yourself; conversational execution remains unimplemented specifically because of this finding. A new `62.x` benchmark category was added and evaluated honestly, including the one genuine Fail. `v0.62.0` implemented the bounded, single-file repair application transaction (`scripts/gauss_repair_application.py`, CLI `apply-repair`/`show-application-result`) — Section 14 of the `v0.58.0` design — and nothing beyond that. ## Retrieval and Lookup

- A GAUSS code execution helper now exists (`scripts/gauss_code_execution.py`), but real, safe non-interactive GAUSS invocation is not yet confirmed — see "GAUSS Environment, Package Inspection, and Execution" below for the full finding. Real execution should be treated as experimental, not production-ready.
- Command-specific documentation retrieval has a lightweight local script prototype (`scripts/command_doc_lookup.py`), not a full semantic search system. It depends on having a local official GAUSS documentation checkout available on disk; retrieval is local-first, not hosted.
- The lookup script uses heuristic pattern matching (heading underlines, `.. function::` directives, keyword substring search) rather than a full reStructuredText parser, so it can misparse unusual formatting.
- Extraction may truncate long sections; not every documented field (for example, every member of a large output structure) is guaranteed to be captured.
- Keyword search can miss conceptually relevant text when the official wording differs from the requested keyword (for example, a doc that says "no occurrence is found" will not match a literal search for "not found").
- Retrieval coverage now spans seven real, end-to-end tested commands (`olsmt`, `strindx`, `strsplit`, `dstatmt`, `qnewtonmt`, `pdsummary`, `minimize`) across varied documentation shapes, but this remains a small pilot set relative to the full GAUSS command surface; broader coverage is unverified.
- Curated command notes are a small convenience cache, not a replacement for official GAUSS documentation.
- The Code Assistant must not invent syntax when official docs are unavailable.

## Evidence Schema and Validation

- Schema validation (`schemas/command_lookup_evidence.schema.json`, `scripts/validate_lookup_evidence.py`) checks evidence *structure* — required fields, enum values, types — not GAUSS semantic correctness. A schema-valid object can still describe outdated or incorrect command behavior.
- A schema-valid evidence object is not proof that GAUSS code was executed. Schema validity and execution are unrelated claims.
- The evidence schema does not replace official GAUSS documentation, which remains authoritative for exact syntax, defaults, and return values.
- Evidence can become stale relative to official docs. When exact syntax or defaults matter, evidence should be regenerated against current documentation rather than relied on indefinitely; the schema can represent staleness (`stale_evidence`) but cannot yet detect it automatically.
- Some evidence states (ambiguous, conflict, stale, schema-invalid) are currently represented only by hand-built synthetic fixtures under `examples/retrieval/schema-fixtures/`, not generated automatically from real lookups.
- `conflict` and `stale` retrieval statuses are represented in the schema but not yet automatically generated by `scripts/command_doc_lookup.py` — there is no curated-note comparison logic or staleness-detection logic in the script yet.
- The validator's path-detection warning can produce false positives for official documentation examples that happen to contain path-shaped strings (confirmed: an HDF5 URI example in official `olsmt` documentation triggers two such warnings). This is a known, reviewed exception under the `v0.7.0` strict-mode policy (see below), not a hidden defect.
- Schema-aligned output is available through `--schema-output`, but legacy lookup output remains the default and is not schema-aligned unless the flag is passed. Legacy lookup JSON files (`examples/retrieval/olsmt.lookup.json`, `examples/retrieval/strindx.lookup.json`) predate the schema and may not match the schema-aligned evidence format.
- Current schema-aligned examples cover seven real GAUSS commands (`olsmt`, `strindx`, `strsplit`, `dstatmt`, `qnewtonmt`, `pdsummary`, `minimize`); broader coverage across the full GAUSS command surface remains unverified.
- `scripts/validate_all_evidence.py` aggregates the single-file validator's results across all committed examples and fixtures; it does not add new validation rules of its own, does not execute GAUSS, and does not access the network. The `v0.7.0` release-health bar is the default non-strict run; `--strict` currently fails only because of the two known, reviewed `olsmt.evidence.json` path-warning false positives above — this is documented policy, not a suppressed failure, and improving the path-warning heuristic so this stops triggering is tracked as future work.

## GAUSS Environment, Package Inspection, and Execution

- **Real GAUSS execution exists in three distinct layers; as of `v0.37.0`, the third layer now exists as a dedicated module, though execution still requires the same explicit, per-request confirmation as every prior milestone — this is not automatic execution.** (1) The **verified execution helper** — `scripts/gauss_code_execution.py`, invoked as `tgauss.exe -b <script_path>`, confirmed only on Windows/GAUSS 26.1.1; unmodified by `v0.32.0` through `v0.37.0`. (2) The **mock-and-adapter orchestration layer** — `scripts/gauss_runtime_orchestration.py` (`v0.31.0`) and `scripts/gauss_execution_adapter.py` (`v0.32.0` Increment 1), integrated via `AdapterRunner`, and now the durable state store described below (`v0.36.0`). Every default test, self-test, and evaluation still validates this layer's state-machine/consent/request-contract/projection/status-mapping logic entirely against injected fake helpers. `v0.33.0` verified once, `v0.34.0` twice, and `v0.35.0` five more times that this layer can genuinely drive layer (1) for real, including one genuine controller bug found and fixed along the way (`v0.35.0`'s basename-comparison fix). (3) **The conversational execution-workflow layer** — `scripts/gauss_execution_workflow.py` (new, `v0.37.0`) — is now implemented as the sole permitted boundary between a conversational interaction and layer (2), and `workflows/real-execution-user-workflow.md`, `workflows/code-assistant-response.md`, and `agents/code-assistant/AGENT.md` each now reference it. This is **not** automatic execution: intent classification is a pure function over explicit, pre-classified booleans (never natural-language parsing), code presence or execution-adjacent wording alone never reaches a plan, and only a fully independently validated, `request_hash`-bound confirmation event can ever reach `execute()`. `v0.37.0` verified this complete layer against real GAUSS three times (success, runtime error, contained output-file creation), all through the full `propose_execution → confirm_execution → execute → inspect` sequence. No document in this repository should be read as claiming this layer performs execution without explicit, per-request human confirmation, or that a live, deployed conversational integration triggering this layer automatically exists — the agent document references the workflow boundary's *rules*, it does not itself invoke code. Any future real-execution testing remains gated behind the same two-part opt-in gate every real-invocation harness already implements (`--run-real-gauss` plus `GAUSS_AI_ALLOW_REAL_EXECUTION=1`, both required) that default release-readiness/CI checks never set. `scripts/gauss_code_execution.py` and `schemas/gauss_code_execution.schema.json` remain unmodified by `v0.32.0` through `v0.37.0`.
- **A durable, optional cross-process safety layer now exists underneath the mock-and-adapter orchestration layer (`v0.36.0`), narrowing but not eliminating the "single-process, single-in-memory-registry" limitation stated in every prior milestone.** `scripts/gauss_orchestration_state_store.py` (new) provides an explicit, opt-in SQLite-backed durable store; `MockOrchestrationInstance` defaults to `state_store=None` (fully unaffected, all 85 pre-`v0.36.0` tests pass unmodified) and only gains durability when a caller explicitly supplies a store or calls the new `build_durable_orchestration_instance(...)` factory. When a store IS supplied, invocation authorization is genuinely atomic and durable — verified with real, separate OS processes (not simulated) racing to authorize the same record, exactly one success every time — and this **does** now extend the exactly-once guarantee beyond a single process, **but only as far as: one local machine, multiple cooperating Python processes on that machine, one shared SQLite database file.** Explicitly still not claimed, even with a store: distributed exactly-once execution, multi-machine coordination, protection if cooperating processes are configured with different database file paths, protection against someone manually editing the database file outside this system, or crash-safe knowledge of whether a real GAUSS process actually launched near the invocation boundary — a crash after authorization commits but before the helper is called is durably indistinguishable from a crash after the helper returns but before its result is saved (both leave `executing`/no-result), disclosed honestly as a permanent limitation rather than solved. No automatic repair, retry, or rerun exists for an ambiguous or corrupt record — both are surfaced via read-only inspection tooling (`--list-ambiguous`, `--check-integrity`, `--list-needs-review`, all confirmed never to mutate the database) for manual review only. Only a SHA-256 digest of inline code is ever durably stored, never the code itself (verified by a direct byte-scan of the produced database file) — one consequence is that a reloaded instance's `request` is always `None`, so the pre-existing `begin_analysis()`/`invoke()` guards correctly refuse to proceed on it, preventing this reload path from ever resurrecting execution capability from incomplete durable state. `scripts/gauss_code_execution.py`, `schemas/gauss_code_execution.schema.json`, and `scripts/gauss_execution_adapter.py` were not modified by `v0.36.0`. No GAUSS was run at any point during this milestone's implementation, testing, or evaluation work.
- **A confirmed-but-not-yet-invoked request can only ever be invoked by the process that built it — a genuine architectural finding from `v0.37.0`'s own testing, not a bug.** `gauss_runtime_orchestration.reload_orchestration_instance(...)` always leaves `request=None` (raw code is never durably persisted, per the bullet above), so `gauss_execution_workflow.ExecutionWorkflow.execute(...)` against a reloaded instance — in any process other than the one that produced the original proposal — always fails closed with `GuardFailedError`, before ever reaching the durable controller's own atomic authorization race. This was verified directly with three real, separate racing OS processes, all refused, none corrupting the durable record, with the original process still able to complete the invocation afterward. The practical consequence: this codebase does not currently support handing off a confirmed-but-not-yet-executed request to a different worker process or after a genuine restart of the process that built it — only the durable status fields (confirmation status, execution status once recorded, transition history) survive a restart for inspection; the ability to actually invoke does not. Resolving this would require durably persisting raw code, which is an explicit stop condition this milestone (and `v0.36.0` before it) was barred from crossing.
- **`v0.38.0` (planning only) designed, but did not implement, a response to the limitation above.** `planning/v0.38.0-persistent-execution-sessions.md` defines a conceptual execution-session model, an extended state machine, an agent-handoff diagram, ownership/cancellation/expiration/audit concepts, and explicit security boundaries for how a confirmed request might one day safely persist across processes — without weakening confirmation binding, request immutability, or the existing redaction rules. As of `v0.38.0`: confirmed execution requests still cannot safely resume across processes; persistent execution sessions are not implemented; cancellation across processes is not implemented; durable ownership is not implemented. No code, schema, or database change was made by `v0.38.0`; the limitation described in the bullet above remains fully in effect.

Transitions between the real-execution workflow, the helper, execution-aware analysis, and report generation remain manual (a human or an LLM following the documented workflows decides what happens next at each step) — **except** inside the mock controller skeleton itself, `scripts/gauss_runtime_orchestration.py` (`scripts/test_gauss_runtime_orchestration.py`, 40 passing tests), which now exists but is explicitly **mock-only and in-memory only**: it never imports `scripts/gauss_code_execution.py`, never launches a subprocess, and never invokes `gauss.exe`/`tgauss.exe` — every "execution" goes through an injected fake runner supplied by the caller. No real Helper Adapter integration exists; no automatic tool invocation of the real helper exists; consent state (in the mock controller) is enforced only in-memory, within a single Python process, with no cross-process guarantees, no production session persistence, and no production script fingerprinting (script-path mode is unconditionally blocked with a `SCRIPT_IDENTITY_UNTRUSTED` failure in this phase); duplicate-mock-invocation prevention and cancellation handling are implemented for the mock controller specifically, not for any real execution path; and no user-facing workflow integration exists — nothing in this mock controller is wired into `workflows/code-assistant-response.md` or any agent. Twenty-nine `32.x` benchmark prompts (`evaluations/benchmark-prompts.md`) and matching coverage rows (`evaluations/benchmark-coverage.md`) now exist for this mock controller's design and behavior and have been evaluated: **29/29 passed at 4.0** (run files `evaluations/runs/2026-07-18-code-assistant-runtime-orchestration-run-001.md` through `-029.md`), confirming — at the design/mock level only — confirmation-required gating, exactly-once invocation, atomic confirmation consumption, environment-mismatch and untrusted-script-identity refusals, malformed-result and missing-expected-output handling, cancellation before and during execution, analysis/report-generation failure isolation from execution evidence, session-boundary and stale-confirmation handling, and the request-lineage principle (no same-instance resurrection of a terminal state). **These evaluations do not validate real GAUSS runtime behavior**: they exercise the mock controller's in-memory logic against an injected `FakeRunner`, never `scripts/gauss_code_execution.py` or any real GAUSS process, and real Helper Adapter integration remains unimplemented. Real execution through this workflow is still bounded by every limitation above: this workflow (and its proposed orchestration design) is documentation/decision-rule guidance only and does not itself constitute or add runtime orchestration or automatic Code Assistant execution — real execution remains verified only on Windows/GAUSS 26.1.1, `exit_code` remains unreliable, error detection remains heuristic, `output_files` metadata is still not file content (file contents require explicit user-provided content or an explicit safe file-reading workflow), no automatic rerun/repair loop exists, no package installation/license activation/network access/global configuration mutation occurs, and execution — successful or otherwise — still does not prove statistical or methodological validity.
- Working-directory containment (required, existing, no path traversal for `script_path`/`output_directory`/`input_files`), timeout enforcement (with a hard maximum), stdout/stderr capture and truncation, and output-file metadata discovery (limited to the working directory, `created_by_execution` always `"unknown"` since no before/after comparison is implemented) all exist and are covered by self-tests, independent of whether real non-interactive invocation is ever confirmed.
- Package context handling is implemented conservatively: a non-empty `missing_packages` in a supplied `package_inspection_result` blocks execution with a clear error (never auto-installing), while a non-empty `unknown_packages` only adds a warning. A missing package never means GAUSS itself is missing, and an unknown package is never treated as installed or missing.
- Execution Mode is never a standing state — `operating_mode: execution` is set only for the specific call where the runner actually invoked a subprocess, never persisted as an active mode. Runtime orchestration remains unimplemented across the framework — none of environment detection, package inspection, or code execution introduces any runtime orchestration engine. A dedicated workflow for safely interpreting structured execution results now exists (`workflows/execution-aware-analysis.md`, per the `v0.26.0` plan in `planning/v0.26.0-execution-aware-analysis-workflow.md`), and `workflows/code-assistant-response.md` now references it (a new "Execution-Aware Responses" step, applied only when an execution result object is actually present). The `29.x` response-behavior benchmark category (`29.1`-`29.8`) evaluating this integration is now complete: 8/8 passed at 4.0, confirming that `completed`/`exit_code: 0` is not overclaimed as methodology validity, that stderr/warnings are surfaced even when execution completed, that failed/timed-out execution is debugged without fabricating results, that blocked/skipped results make no execution or output claims, that `output_files` metadata is not mistaken for read file contents, and that fake-runner self-test success is not conflated with production-ready real GAUSS invocation. Environment-detection/package-inspection results still are not consumed by any Code Assistant workflow step — only the code-execution result object is covered by this workflow so far.
- The following behavioral guardrails are implemented in `scripts/gauss_code_execution.py` and validated by both `--self-test` (implementation correctness) and the `28.x` benchmark category (expected assistant response behavior): a completed execution result does not prove statistical or methodological validity; `exit_code: 0` does not prove statistical validity; execution output still requires expert interpretation before being treated as meaningful or trustworthy; a failed execution does not automatically prove a model is wrong (it proves the process failed); a timed-out execution does not automatically prove a model is wrong (it proves the process exceeded its time limit); a missing package does not mean GAUSS itself is missing; a missing package does not trigger automatic installation; and the helper never installs packages, activates licenses, mutates global GAUSS configuration, or accesses the network.
- Report generation from actual execution output has a documented, evaluated workflow but no automatic report export. `v0.27.0 - Report Generation Workflow` (`planning/v0.27.0-report-generation-workflow.md`) has created `workflows/report-generation.md` — defining a seven-tier evidence hierarchy, five report types (Technical Analysis Summary, Econometric Interpretation Note, Debugging Report, Teaching Explanation, Product/User Workflow Summary), a default report structure, and expert-routing rules for turning code, execution evidence, captured output, and expert interpretation into structured reports — and integrated it into `workflows/code-assistant-response.md` (a new "Report-Generation Responses" step, applied only when a report-style response is actually requested). The `30.x` response-behavior benchmark category (`30.1`-`30.8`) evaluating this integration is now complete: 8/8 passed at 4.0, confirming correct report-type selection, evidence-hierarchy adherence, no methodology-validity claims from `completed`/`exit_code: 0`, no fabricated results/coefficients/diagnostics, `output_files` metadata never mistaken for read contents, and outright refusal of unsupported final conclusions in favor of a scoped alternative. Real non-interactive GAUSS invocation remains unresolved — the naive `[executable_path, script_path]` command form entered the interactive GAUSS 26 prompt and timed out during `v0.25.0` implementation, and real execution remains experimental/limited until a safe form is confirmed. No automatic report export to files exists, no automatic file reading exists, and none is planned without separate scoping. Runtime orchestration and automatic execution remain unimplemented across the framework. Output file metadata still does not mean file contents were read, execution results still require expert interpretation before being treated as meaningful, successful execution still does not prove methodology validity, a failed or timed-out execution still does not prove a model is invalid, report generation must not turn weak evidence into strong conclusions, and any eventual final, publication-ready report claims will still require expert review rather than being self-certifying.
- Current behavior remains advisory/verified-knowledge only: the Code Assistant can write, explain, review, document, and teach GAUSS code, and can cite verified command evidence, but cannot run code or confirm output against a real GAUSS session.
- Execution must be optional and gracefully degrade when GAUSS is unavailable — `planning/v0.19.0-gauss-tooling-strategy-and-execution-modes.md`'s "Graceful Fallback Principle" states this explicitly: the assistant must not break, must not claim execution, and must remain useful in advisory mode whenever GAUSS or an execution tool is unavailable. This is now implemented and self-tested (missing/ambiguous environment, missing working directory, missing code/script, and missing packages all return structured `blocked`/`skipped` results rather than breaking), not just a design requirement.
- Successful execution does not prove syntax is generally valid beyond the specific run/context, statistical/methodological validity, maintainability, documentation quality, education quality, or product/user value — `planning/v0.19.0-gauss-tooling-strategy-and-execution-modes.md`'s "Relationship to Six Experts" section and `tools/gauss_code_execution.md`'s "Result Interpretation Policy" both state this explicitly, extending the same independence principles already documented in `experts/EXPERT_BOUNDARY_MATRIX.md` to code execution. Execution output routes interpretation to the relevant operational expert(s) rather than self-certifying anything — this remains true even once real non-interactive invocation is eventually confirmed.

## Evaluation and Process

- Retrieval-backed response behavior has manual evaluation coverage across key states, but it is not automatically enforced by a live agent runtime.
- Benchmark coverage is growing but not exhaustive.
- Preview quickstart materials exist, but they should still be tested by users who were not part of the design process.
- Manual evaluation runs are useful evidence, but automated regression evaluation is not implemented yet.
- Any tracked local machine-specific configuration should be removed, renamed, or clearly documented before broader public use.
- A local evaluation tracking consistency guard (`scripts/check_evaluation_tracking.py`, added `v0.10.0`) checks that `evaluations/benchmark-prompts.md`, `evaluations/benchmark-coverage.md`, `evaluations/runs/INDEX.md`, and the run files under `evaluations/runs/` stay consistent with each other. It runs both locally and in CI (as of `v0.13.0`, via `scripts/check_release_readiness.py`), and it does not check response quality or scoring correctness — that remains a manual-evaluation responsibility. Its default run reports 0 errors and exactly 2 documented historical warnings (a Prompt ID mismatch on a pre-stable-ID run file, and a legacy pre-Prompt-ID-era smoke-test run file that is intentionally not indexed); `--strict` fails only because those two warnings are promoted, which is expected policy, not a defect.
- Benchmark prompts that hardcode specific volatile repository counts (for example, an exact prompt-ID count or warning count) in their expected-behavior text can go stale as soon as later milestones add more prompts or runs, unless the benchmark is explicitly scoped to a fixed, frozen repository state. This was observed directly during the `v0.10.0` `17.5`/`17.6` evaluations; the correct evaluated behavior is to report the true live tool output rather than the prompt's originally-written figures. `v0.11.0` added benchmark-authoring guidance (`workflows/manual-evaluation.md`, "Benchmark Authoring Guidance") to reduce recurrence going forward, but this is process guidance for future authoring, not an automated guard against it — a future benchmark can still be written this way if the guidance isn't followed.
- `scripts/check_release_readiness.py` (added `v0.12.0`) runs the two default guard scripts (`validate_all_evidence.py`, `check_evaluation_tracking.py`) in one command and summarizes pass/fail. As of `v0.13.0`, it also runs automatically in CI (`.github/workflows/release-readiness.yml`) on every push and pull request, using its default (non-strict) mode — the same command a contributor would run locally. Its `--strict` mode remains informational only and does not affect its own exit code (locally or in CI), since strict-mode failure is currently expected for both underlying scripts (see `scripts/README.md`'s "Strict-mode policy and future CI expectations" section). Strict mode is not yet enforced by CI, and no non-blocking strict CI job or machine-readable strict-warning allowlist exists yet — both remain non-blocking follow-ups.
