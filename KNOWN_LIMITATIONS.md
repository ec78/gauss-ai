# Known Limitations

These limitations apply as of the `v0.9.0` Second Operational Expert and Multi-Expert Routing milestone.

## Retrieval and Lookup

- The framework does not yet execute GAUSS code.
- Command-specific documentation retrieval has a lightweight local script prototype (`scripts/command_doc_lookup.py`), not a full semantic search system. It depends on having a local official GAUSS documentation checkout available on disk; retrieval is local-first, not hosted.
- The lookup script uses heuristic pattern matching (heading underlines, `.. function::` directives, keyword substring search) rather than a full reStructuredText parser, so it can misparse unusual formatting.
- Extraction may truncate long sections; not every documented field (for example, every member of a large output structure) is guaranteed to be captured.
- Keyword search can miss conceptually relevant text when the official wording differs from the requested keyword (for example, a doc that says "no occurrence is found" will not match a literal search for "not found").
- Retrieval coverage now spans seven real, end-to-end tested commands (`olsmt`, `strindx`, `strsplit`, `dstatmt`, `qnewtonmt`, `pdsummary`, `minimize`) across varied documentation shapes, but this remains a small pilot set relative to the full GAUSS command surface; broader coverage is unverified.
- Curated command notes are a small convenience cache, not a replacement for official GAUSS documentation.
- The Code Assistant must not invent syntax when official docs are unavailable.

## Evidence Schema and Validation

- Schema validation (`schemas/command_lookup_evidence.schema.json`, `scripts/validate_lookup_evidence.py`) checks evidence *structure* — required fields, enum values, types — not GAUSS semantic correctness. A schema-valid object can still describe outdated or incorrect command behavior.
- A schema-valid evidence object is not proof that GAUSS code was executed. Schema validity and execution are unrelated claims.
- The evidence schema does not replace official GAUSS documentation, which remains authoritative for exact syntax, defaults, and return values.
- Evidence can become stale relative to official docs. When exact syntax or defaults matter, evidence should be regenerated against current documentation rather than relied on indefinitely; the schema can represent staleness (`stale_evidence`) but cannot yet detect it automatically.
- Some evidence states (ambiguous, conflict, stale, schema-invalid) are currently represented only by hand-built synthetic fixtures under `examples/retrieval/schema-fixtures/`, not generated automatically from real lookups.
- `conflict` and `stale` retrieval statuses are represented in the schema but not yet automatically generated by `scripts/command_doc_lookup.py` — there is no curated-note comparison logic or staleness-detection logic in the script yet.
- The validator's path-detection warning can produce false positives for official documentation examples that happen to contain path-shaped strings (confirmed: an HDF5 URI example in official `olsmt` documentation triggers two such warnings). This is a known, reviewed exception under the `v0.7.0` strict-mode policy (see below), not a hidden defect.
- Schema-aligned output is available through `--schema-output`, but legacy lookup output remains the default and is not schema-aligned unless the flag is passed. Legacy lookup JSON files (`examples/retrieval/olsmt.lookup.json`, `examples/retrieval/strindx.lookup.json`) predate the schema and may not match the schema-aligned evidence format.
- Current schema-aligned examples cover seven real GAUSS commands (`olsmt`, `strindx`, `strsplit`, `dstatmt`, `qnewtonmt`, `pdsummary`, `minimize`); broader coverage across the full GAUSS command surface remains unverified.
- `scripts/validate_all_evidence.py` aggregates the single-file validator's results across all committed examples and fixtures; it does not add new validation rules of its own, does not execute GAUSS, and does not access the network. The `v0.7.0` release-health bar is the default non-strict run; `--strict` currently fails only because of the two known, reviewed `olsmt.evidence.json` path-warning false positives above — this is documented policy, not a suppressed failure, and improving the path-warning heuristic so this stops triggering is tracked as future work.

## Expert Routing and Operational Modules

- Expert routing (`workflows/expert-routing.md`, `experts/gauss-language/OPERATIONAL_PROFILE.md`, `experts/econometrics/OPERATIONAL_PROFILE.md`, `tools/operational_expert_interface.md`) is a documentation/checkable-workflow contract, not a runtime instrumentation layer. No code parses or enforces these files at runtime; a response is checked against them manually, the same way task-mode fit is checked today.
- Two experts are operationalized as of `v0.9.0`: the GAUSS Language Expert (implementation correctness) and the Econometrics Expert (methodological correctness). The Software Engineering, Documentation, and Education experts named in `workflows/code-assistant-response.md` remain narrative-only guidance, not backed by an operational profile.
- Manual evaluation still determines whether correct routing occurred (activation, non-activation, decision-rule application, evidence/context-threshold compliance) — there is no automated multi-expert routing test harness.
- Multi-expert *routing* is documented (`workflows/expert-routing.md` defines GAUSS-only, Econometrics-only, Both, and Neither, with coordination rules for the both-experts case), but no runtime multi-expert *orchestration engine* exists, and no automated conflict-resolution engine exists beyond those documented coordination rules — surfacing a conflict or tension between the two experts' conclusions is a response-writing responsibility, not an automated check.
- Expert profiles add domain-specific constraints on top of existing evidence requirements; they do not replace or weaken them. GAUSS command evidence requirements still depend on the retrieval workflow and evidence schema, and remain entirely separate from the Econometrics Expert's methodological context requirements — meeting one is never sufficient to satisfy the other. Command availability is never evidence of methodological validity, and methodological plausibility never justifies inventing GAUSS syntax.
- Schema validation still does not prove GAUSS semantic correctness or that any GAUSS code was executed — this remains true regardless of which expert(s) consulted the evidence.
- Expert activation is internal by default; responses are not required to state which expert(s) were consulted, which means routing correctness can only be confirmed by inspecting response content, not by reading a self-reported label.
- `glm.evidence.json` (real, schema-aligned) now exists locally for logistic/probit and other generalized linear models, closing the gap where a `v0.9.0` benchmark evaluation had to verify `glm` against live official documentation instead.
- A verified native GAUSS panel-estimation command has been confirmed: `tscsFit`, which estimates a pooled time-series-cross-section regression model and returns both fixed-effects and random-effects coefficient estimates (`examples/retrieval/schema-aligned/tscsfit.evidence.json`; full audit in `examples/retrieval/panel-estimation-coverage-audit.md`). It requires the separately licensed TSMT package (not bundled with base GAUSS, requires GAUSS/GAUSS Engine v25+) — this package dependency must be stated whenever it is recommended. `lsdvFit`'s applicability to panel fixed-effects estimation remains unclear and unresolved; no dynamic-panel-GMM command was found in the audited local docs.
- `scripts/command_doc_lookup.py` does not yet distinguish `official_docs` from `official_package_docs` for package-located files (e.g., `tsmt/tscsfit.rst`) — every local `.rst` match is currently labeled `official_docs` regardless of whether it lives in the core documentation tree or a separately licensed package directory. This is a known tooling gap, not a runtime bug; the Code Assistant must still state package dependencies explicitly regardless of what the evidence file's `source_authority` field says.

## Evaluation and Process

- Retrieval-backed response behavior has manual evaluation coverage across key states, but it is not automatically enforced by a live agent runtime.
- Benchmark coverage is growing but not exhaustive.
- Preview quickstart materials exist, but they should still be tested by users who were not part of the design process.
- Manual evaluation runs are useful evidence, but automated regression evaluation is not implemented yet.
- Any tracked local machine-specific configuration should be removed, renamed, or clearly documented before broader public use.
