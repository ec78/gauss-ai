No new subprocess-management code exists anywhere.
- New `scripts/gauss_execution_handoff.py`: `ExecutionHandoffRequest` (frozen, SHA-256-digest-bound over `code`/`runner`/`executable_path`/`gauss_version`/`timeout_seconds`/`workspace_parent`/`readiness_state`, exact byte-for-byte code text — deliberately no newline/whitespace normalization before hashing, unlike the pre-existing `gauss_runtime_orchestration.compute_request_hash`'s own convention, per this milestone's explicit conservatism requirement), `ExecutionHandoffApproval` (frozen, binds exactly one `request_digest`, `approved`/`declined`), `ExecutionHandoffApprovalStore` (in-memory, process-local, per-`approval_id` single-use consumption tracked separately from the frozen approval object — never mutating it), `ConversationalExecutionResult` (composes the existing `gauss_execution_interpreter.ExecutionEvidence` rather than re-defining it), and a ten-value failure taxonomy.
- `create_execution_handoff_request(...)` refuses anything not exactly `HANDOFF_CANDIDATE`. `parse_execution_approval_response(...)` accepts only exact `yes`/`approve` or `no`/`decline`; everything else is `"unrecognized"` (re-asked once by the chat orchestration layer, then safely cancelled — never coerced). Consumption rule: any pre-launch gate failure, or a deterministically-provable adapter-level pre-invocation rejection (`outcome.invoked is False`), never consumes an approval; any actual helper-invocation attempt (success, GAUSS error, timeout, or a post-call adapter anomaly) always consumes it.

## Decisions

- Reused the low-level `GaussExecutionAdapter`/`load_real_helper()` directly (mirroring `gauss_differential_harness.RealGaussRunner`'s exact precedent), NOT the heavier `gauss_execution_workflow.ExecutionWorkflow`/`gauss_runtime_orchestration.MockOrchestrationInstance` state machine — that machinery is purpose-built for the file-based guided-repair pipeline's durable, multi-phase, named-workspace session model, an inappropriate scope expansion for a single ephemeral conversational snippet.
- Digest hashing does NOT normalize code newlines/whitespace before hashing (unlike the pre-existing `compute_request_hash` convention) — exact byte-for-byte code binding was explicitly required by this milestone's brief, and is proven by a dedicated CRLF-vs-LF regression test.
- Approval consumption tracking lives in a separate in-memory store (`ExecutionHandoffApprovalStore`), never by mutating the frozen `ExecutionHandoffApproval` object — mirrors `gauss_repair_application_approval.ApplicationApprovalStore`'s own established shape, adapted to add single-use semantics that repair-application approval doesn't need.
- A "run this" trigger phrase deliberately overlaps two of `gauss_conversation_engine.py`'s own pre-existing fixed execution-boundary-redirect phrases (`"run this"`, `"execute this"`); when a `HANDOFF_CANDIDATE` answer is pending, the new handoff flow takes priority over the old fixed redirect, since a controlled path now genuinely exists — documented inline in `gauss_ai_chat.py` and confirmed not to break any existing test (the one pre-existing test using this phrasing appends a period, which does not match the new exact-phrase trigger).
- The conversational execution offer requires exactly one generated code block per answer (multiple fenced blocks are out of scope for `v0.78.0`) — a deliberate, disclosed scope narrowing, not an oversight.
