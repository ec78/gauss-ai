## Completed Work

- `v0.76.0` adds a bounded, deterministic GAUSS syntax-validation layer (`gauss_pre_execution_validation.validate_syntax(...)`) and hardens validation coverage into a new `HandoffReadiness` verdict (`NOT_READY`/`REVIEW_REQUIRED`/`HANDOFF_CANDIDATE`), strictly downstream of and distinct from `ExecutionEligibility`. Directly motivated by the exact `v0.75.0` live finding (`65.8b`): a real model's matrix literal used `;` as a row separator, and the precondition checker could only report `UNVERIFIED`, never a real syntax problem.
- Real `tgauss.exe -b` execution (this session) confirmed a `;`-separated literal is NOT rejected by GAUSS — it silently misparses into a malformed single row containing a denormal/garbage element. This is the provenance for `matrix_literal_row_separator`, one of six deterministic syntax rules added (`_SYNTAX_RULE_REGISTRY`), each with recorded provenance (official docs, real GAUSS execution, or a narrow structural convention).
- **Two real, live-found defects were fixed within the milestone**: (1) a bare `str.startswith(keyword)` check spuriously flagged the identifier `formula` as starting with the block keyword `for`, fixed via `_starts_with_keyword(...)` requiring a real word boundary; (2) a CLI-subprocess smoke test of the headline regression through the actual installed `gauss-ai` binary produced a real model output using a brace-less bare multi-token literal (`x = -1 0;`), a different invalid shape the original rule had no scope to catch — confirmed genuinely invalid via real `tgauss.exe -b` execution (`error G0063`) and fixed with a new rule, `bare_multi_token_literal_requires_let_or_braces`.
- A genuine, live `HANDOFF_CANDIDATE` was directly confirmed (a bonus scenario, `66.11`): a direct-literal-call prompt reached every coverage dimension `COMPLETE`, evidence profile `BROAD`, and a real `HANDOFF_CANDIDATE` end to end against the real model and real docs — proving the positive readiness path is real, not only a synthetic-test construction.
- A real, disclosed, non-blocking product-design tension was found across three scenarios (`66.1`, `66.2`, `66.10`): idiomatic model output (assign a literal to a variable, then call the function on the variable) leaves the parameter-role checker `UNKNOWN` rather than `MATCH`, since it deliberately never traces a runtime variable back to its literal assignment — keeping otherwise-clean code at `REVIEW_REQUIRED` instead of `HANDOFF_CANDIDATE`.
- One out-of-scope, pre-existing (`v0.72.0`-era) limitation was found and disclosed but NOT fixed (out of this milestone's own scope): `gauss_conversation_engine._candidate_tokens(...)`'s `MAX_TOKEN_LOOKUPS = 6` cap can exhaust its budget on early sentence words before ever reaching a function name mentioned late in a long question.

## Decisions

- `HandoffReadiness` is deliberately a NEW, separate verdict from `ExecutionEligibility` rather than a fourth eligibility state — they answer different questions ("worth validating" vs. "enough evidence for a future handoff workflow to consider"). Documented in `gauss_pre_execution_validation.py`'s own top-of-file docstring and the planning doc's Section 3.5.
- An `UNKNOWN` documented signature or an `UNVERIFIED` runtime-dependent precondition forces `REVIEW_REQUIRED`, never silently `HANDOFF_CANDIDATE` and never punitively `NOT_READY` — `NOT_READY` is reserved for a KNOWN violation.
- `EvidenceProfile` deliberately excludes predicted-output verification from its `BROAD`/`PARTIAL`/`MINIMAL` computation — predicted-output correctness stays orthogonal to readiness, per the milestone's own Phase 17 requirement.
- All other `v0.76.0` design decisions (bounded syntax-check scope, exact rule provenance, why no full parser was built) are recorded in `planning/v0.76.0-gauss-syntax-validation.md` — that file is the durable record.
